# 第 06 章 · 内存池与数据结构:"无 free"的世界观

> 基线:commit `231a60ee`(2026-09-02)。行号均以该版本源码为准。

## 6.0 资源模型:Nginx 的关键钥匙

**对象生命周期与请求/周期绑定,内存只分配不逐个释放,整体随 pool 销毁。** 这换来 O(1) 的错误处理路径——任何中途失败都不需要逐层回滚 malloc,只需销毁 pool 或返回错误码。错误码体系同样极简:`NGX_OK=0 / ERROR=-1 / AGAIN=-2 / BUSY=-3 / DONE=-4 / DECLINED=-5 / ABORT=-6`(ngx_core.h:39-45),全项目共享一组 int,没有 errno 风格的全局错误对象。`NGX_DECLINED` 是模块化 pipeline 的粘合剂,`NGX_AGAIN` 是非阻塞 IO 的心脏。

## 6.1 内存池:双轨设计

```c
struct ngx_pool_s {
    ngx_pool_data_t  d;       /* last/end/next/failed */
    size_t           max;     /* 小块上限 = min(pool大小, pagesize-1) */
    ngx_pool_t      *current; /* 分配起点(跳过耗尽块) */
    ngx_chain_t     *chain;   /* 空闲 chain 回收站 */
    ngx_pool_large_t *large;  /* 大块单链表 */
    ngx_pool_cleanup_t *cleanup; /* 析构回调链 */
};
```

**小块轨道**(bump-pointer):从 `pool->current` 沿链找第一个能装下的块,`d.last` 前移即完成分配。新块只带 16 字节的迷你 header(不像很多 pool 每块复制完整结构)。**"常数 4"的自愈机制**:

```c
for (p = pool->current; p->d.next; p = p->d.next) {
    if (p->d.failed++ > 4) {
        pool->current = p->d.next;   /* 淘汰"碎片化"的块 */
    }
}
```
(ngx_palloc.c:201-205)

申请失败超 4 次的块说明剩余空间太小,后续每次分配都白扫一遍——`current` 前移越过它。**用 O(1) 统计换平均 O(1) 分配**,不做首次适配的复杂索引,只对最坏情形做惰性淘汰。大块登记节点的复用同样只扫前 4 个槽——两处经验常数封顶最坏路径,不引入任何可调参数,是 Nginx"够用且可预测"哲学的浓缩。

**大块轨道**:超过 pool->max(默认 4095)直接 malloc,登记进 large 链;`ngx_pfree` 只对大块有意义(free 内存但保留登记节点);**小块永不单独释放**——这是整个模型的代价与前提。

**生命周期**:destroy 的顺序精心设计——**先跑 cleanup 回调,再 free 大块,最后 free 池块链**(回调往往还依赖池内数据);DEBUG 构建下连"free 大块时打日志"都被禁止,因为 log 本身可能就活在这个池里——**顺序即正确性**。cleanup 链是 Nginx 少见的"析构函数"机制(如请求结束时关闭/删除临时文件)。

## 6.2 buf/chain:一套坐标系统走天下

`ngx_buf_t` 的核心设计:**一个 buf 同时携带内存坐标(pos/last)与文件坐标(file_pos/file_last)**——sendfile 场景"头部在内存、体在文件";`ngx_buf_size` 按标志位判定取哪套。标志位全是 1-bit 位域(temporary/memory/in_file/flush/last_buf/shadow…),构成整条输出链的公共语言。`tag` 字段是多模块共享输出链时的身份证明——发送后回收 chain 时只回收 tag 匹配的节点,防止 A 模块把 B 模块的 buf 塞进自己的 free 链。

`pool->chain` 空闲链让单节点 palloc/free 的开销压到几乎为零;`ngx_chain_update_chains` 是所有输出滤镜共同遵守的回收协议(并入 busy → 逐个检查 tag → size 归零重置坐标入 free);`ngx_chain_update_sent` 按已发送字节数**同时推进**两套坐标——对称性一览无余。

## 6.3 slab 分配器:共享内存里的世界

worker 间共享状态(限流、upstream zone、缓存元数据)落在 `ngx_slab_pool_t` 上。布局:pool 头 → slots[] 槽位数组(按 size class 分桶)→ page 描述符数组 → 数据区。每页由 `{slab, next, prev}` 三元组描述,**一位不浪费**:`prev` 低 2 位存页类型,`slab` 低 4 位存 shift、高位存位图。

**中轴设计**:`ngx_slab_exact_size = ngx_pagesize / (8 * sizeof(uintptr_t))`(4K 页下即 64B)——恰好一个 uintptr_t 位图能管全页的拐点。三类分配:

- 大于半页 → 整页/多页;
- 小于 exact → **位图放页数据区开头**;
- **恰为 exact → 页头 slab 本身就是 64 位完整位图,零额外空间**;
- 大于 exact → 位图塞进 slab 高 32 位。

free 路径按页类型逆向拆解,任何不一致都打 ALERT 并 `ngx_debug_point()`——**共享内存损坏不可恢复,宁可 crash 也要把现场留在日志里**。

## 6.4 字符串与日志

`ngx_str_t` 的 len+data 设计天然 binary-safe;自研 printf 支持自定义格式(`%V` 打 ngx_str_t 免 strlen、`%v`、`%Z/%N`),**`ngx_snprintf` 保证至少还能写 1 字符**,`ngx_sprintf` 传 `last = -1` 即无界(必须确保缓冲够大)。转义位图表逐字节标注 ASCII 顺序——注释是协议声明。

日志九级 + DEBUG 子系统掩码共用一个字段(级别用 `>=` 比较、debug 用 `&` 掩码);`ngx_log_t` 是单链表节点,`error_log` 多次出现按级别降序插链,写日志沿链广播;**非 debug 构建下 `ngx_log_debug0..8` 直接展开为空**——调试日志的格式化开销被编译期剔除,这是 Nginx 敢在热路径铺满 debug 日志的原因。写满磁盘的文件有 1 秒熔断。

## 6.5 FAQ

**Q1:palloc 和 pnalloc 差在哪?**
仅差对齐:结构体用 palloc,字符串/字节流用 pnalloc(省对齐垫片);超 max 都转大块路径。

**Q2:小块阈值是多少?可以更大吗?**
`min(pool大小, pagesize-1)`——硬上限页大小减一,池开大也不会超过;大块走 malloc 有更好的反碎片性。

**Q3:为什么小块没有 free?**
设计前提"对象与请求同寿命";碎片化代价由 failed>4 摊销;真正需回收的对象走 ngx_pfree 大块路径 + chain 空闲链。

**Q4:destroy 时 cleanup 为什么先执行?**
回调可能引用池内数据;先 free 大块会悬空。

**Q5:ngx_buf 的 tag 干什么用?**
输出链回收时按 tag 匹配,防止跨模块误收 buf。

**Q6:slab 需要初始化吗?worker 间如何一致?**
master 首次初始化并记录基址;reload 后新 worker 映射同段共享内存,地址一致直接复用。

## 6.6 小结与深挖方向

本章结论:**Nginx 基建 = 池化世界观(分配即生命周期)+ 位域坐标系统(buf/chain)+ 位图中轴的 slab + 编译期剔除的日志**;每处都以"够用且可预测"为取向,拒绝可调参数,靠经验常数封顶最坏路径。深挖:

1. pool->max 钉死在页大小的量化实验(大池下碎片行为变化);
2. 大块链 O(n) 扫描在长链高频 pfree 下的退化;
3. slab 三分支的统一抽象可能性(上游为何选择复制粘贴);
4. 多级 error_log 的写放大对 P99 的影响(1 秒熔断只防 ENOSPC 不防慢盘)。
