# 第 03 章 · 事件循环与连接:压缩到极限的 accept 锁

> 基线:commit `231a60ee`(2026-09-02)。行号均以该版本源码为准。

## 3.0 全景:事件模块的分层

| 层 | 文件 | 职责 |
|---|---|---|
| 事件核心 | ngx_event.c | worker 主循环入口、accept 锁状态机、与后端无关的 handle_read/write_event |
| 事件后端 | modules/ngx_epoll_module.c 等 | 实现 `ngx_event_actions_t` 九个函数指针 |
| 定时器 | ngx_event_timer.c | 进程级全局红黑树 |
| posted 队列 | ngx_event_posted.c | 三个队列:accept/next/普通 |
| 连接池 | ngx_connection.c | connections 数组 + free 链表 |

两个核心结构把各层缝在一起:`ngx_event_t` **内嵌**红黑树节点与队列节点——一个事件可同时在定时器树和 posted 队列被引用,零额外分配;`ngx_connection_t` 的 `data` 字段空闲时复用为 free 链表 next——连接池零额外元数据。

后端注册是一次函数指针表赋值完成"编译期选择 → 运行时多态"的切换(ngx_event.c:679-696)。epoll 后端设置 `ngx_event_flags = NGX_USE_CLEAR_EVENT | NGX_USE_GREEDY_EVENT`:**边缘触发 + 要求读到 EAGAIN**,这决定了所有读 handler 必须循环 recv。

## 3.1 一轮 ngx_process_events_and_timers(ngx_event.c:194-264)

```
worker A(持锁)                        worker B
trylock ──成功                         trylock ──失败
flags|=POST_EVENTS                     timer=min(42,500)ms, 无 POST
epoll_wait(42ms)                       epoll_wait(42ms)
  accept事件→posted_accept 队列
  读事件→posted_events 队列
处理posted_accept: accept()×n
shmtx_unlock ──────────┬─────────→  trylock ──成功
expire_timers          │            enable_accept_events 重新注册
处理posted_events      │            ...
```

七个步骤的顺序即语义:

1. **计算 timer 与 flags**——两种时钟模式:默认"拉模式"睡到最近定时器;`timer_resolution` 开启则走 SIGALRM/setitimer 周期中断(时间精度与 epoll_wait 超时解耦,适合事件稀疏的长连接);
2. **accept 互斥锁**:抢锁或退避。`ngx_accept_disabled` 在每次 accept 后重算:`connection_n/8 - free_connection_n`——空闲连接不足 1/8 时此 worker **主动退出 accept 竞争**,把名额让给有余量的 worker(进程级负载反馈而非公平锁);未抢到锁最多睡 500ms(accept_mutex_delay)再试;
3. **flush posted_next 队列**:非空则 timer=0 强制 epoll_wait 立即返回——"同一轮内拒绝重复处理、下一轮必达"的让步机制,防短写自旋;
4. **执行后端事件采集**;
5. **处理 accept posted 队列 + 立刻解锁**——**全章最精妙的一处**:epoll 循环里 accept 事件投 `ngx_posted_accept_events`、普通读写投 `ngx_posted_events`(ngx_epoll_module.c:894-899),于是持锁窗口 = "epoll_wait 返回 → accept 完 → unlock",锁的持有时间被压缩到接近裸 accept 的耗时;
6. **到期定时器**;
7. **普通 posted 队列**:队头摘除保证先到先处理,处理中新增的 posted 事件留到下一轮,天然防无限循环。

**"抢锁"的实质是"抢 listening socket 在本进程 epoll 里的注册权"**:锁只是共享内存里的原子标志;未持锁者把 listening 读事件从 epoll 摘除,抢到者重新挂上(ngx_event_accept.c:344-404)。

## 3.2 epoll 后端

- **init**(322-380):epoll_create;三个附属 fd——notify eventfd(跨线程唤醒)、Linux AIO eventfd、**EPOLLRDHUP 能力自检**(用 socketpair + 关闭对端 + epoll_wait 实测内核,而非靠宏猜内核版本——运行时特性探测的教科书做法);
- **注册**:`data.ptr` 低位 1 bit 存 `instance` 代次(621),不占额外内存地给每条事件盖"代次"邮戳;`ngx_epoll_add_connection` 一条 `EPOLLIN|EPOLLOUT|EPOLLET|EPOLLRDHUP` 同时挂读写——**连接型 fd 生命周期内通常只 epoll_ctl 一次**,后续读写开关全靠用户态 ready/active 标志记账;
- **stale 事件判定**(839-854)是 process_events 的灵魂:同批事件里 fd 可能已被前面的事件处理关闭并被新 accept 复用。仅凭 `c->fd == -1` 不够(指针可能已被复用),`ngx_get_connection` 每次分配连接都翻转 instance(ngx_connection.c:1256-1262),注册时烙进 data.ptr,取出时比对;
- **eventfd 通知的 syscall 摊薄**(439-453):读取端累计到 `2^32` 次通知才 `read()` 一次排空计数——依赖"每次 write 恰好产生一次 epoll 唤醒"的内核语义。

## 3.3 红黑树定时器 vs Redis 的时间事件链表

| 维度 | Nginx | Redis ae |
|---|---|---|
| 时间事件组织 | 全局红黑树,key=绝对到期 ms | 单链表无序,find 最近线性扫 O(N) |
| 定时器数量假设 | 与连接同量级(每连接读写超时各一),数十万 | 个位数(serverCron 等) |
| 到期处理 | 只处理到期者,处理一个删一个 | 遍历整表触发 |
| 统一抽象 | 定时器只是"事件的另一种就绪"(timedout 标志) | timeEvent 回调 |

**分叉的根源是数量级决定数据结构**:Redis 时间事件个位数,简单链表反而 cache 友好;Nginx 定时器与连接同数量级且频繁增删,红黑树的 O(log n) 是必需品。两个精巧细节:**惰性更新**——已有 timer 且新旧 key 差 <300ms 时直接复用旧节点(高频续约不值得一次 O(log n) 删+插);**回绕处理**——插入比较用有符号差,恰好容忍 32 位毫秒 49.7 天回绕。

## 3.4 连接池与压力自愈

三块与 worker_connections 等长的数组(connections/read_events/write_events),倒序串成 free 链表,**`c->data` 就是链节**。`ngx_get_connection` 整块 memzero + 翻转 instance;`ngx_close_connection` 的清算顺序严格:删定时器 → epoll 注销(看到 CLOSE 标志直接清标志返回)→ **从 posted 队列摘除**(事件可能已在本轮被 posted,不摘会悬空)→ `c->fd = -1` **先于 close**(close 返回后新连接拿到同号 fd 时,并发读 c->fd 不会看到旧值)。

压力自愈三层防线:free 低于 1/8 退出 accept 竞争(ngx_accept_disabled)→ free 低于 1/16 强拆 idle 连接(ngx_drain_connections,手法是 `c->close=1; c->read->handler(c->read)` 直接调读 handler——**核心层不认识协议层**,复用协议层已有的关闭路径)→ get_connection 返回 NULL 告警。

## 3.5 三代惊群方案共存

1. **accept_mutex**(共享内存互斥):绝对无惊群,但锁轮转粒度 500ms、keep-alive 现代负载下反而制造不均;1.11.3 起默认关闭;
2. **EPOLLEXCLUSIVE**:内核保证一次 EPOLLIN 只唤醒一个 epoll 实例——无惊群无用户态锁,但 Linux "通常只通知第一个 add 的进程"导致负载倾斜;1.21.6 加了 `ngx_reorder_accept_events` 修复:每 16 个请求把 listening 事件 DEL 后重新 EXCLUSIVE ADD,周期性换"第一个 add 的进程";
3. **SO_REUSEPORT**:每 worker clone 自己的 listening socket,内核按四元组哈希分流——**既无惊群也无锁,各 worker 的 accept 路径 cache 独立**;且它改变锁语义:reuseport socket 的 accept 不参与互斥,即使 accept_mutex 同时开着。

Nginx 把三代全留在代码里由配置组合决定路径——这是理解 ngx_event_process_init 那段嵌套 #if 的钥匙。

## 3.6 FAQ

**Q1:为什么持锁期间事件要 posted 而不是直接执行 handler?**
让"epoll_wait 返回 → accept 完 → 解锁"的窗口尽量短;直接执行的话一个慢 handler 会拖住所有 worker 的 accept。

**Q2:instance 位防什么?**
防"同批次 stale 事件":连接已关未复用(fd=-1)或 fd 已被新连接复用(instance 已翻转)。

**Q3:expire_timers 为什么排在解锁之后、普通 posted 之前?**
顺序即语义:accept(持锁)→ 解锁 → 超时 → 普通业务。超时 handler 常关连接,夹在"锁外、业务前"是双保险:既不持锁,又不让过期连接参与本轮业务。

**Q4:epoll 下删除事件为什么常是空操作?**
close(fd) 时内核自动从所有 epoll 实例移除;NGX_CLOSE_EVENT 只需清 active 标志。抽象有裂缝时(OpenVZ)就地打补丁并写明原因。

**Q5:UDP 的"连接"是真实连接吗?**
不是:每新五元组 get_connection 拿到 `shared=1` 的连接(fd 就是 listening 的),逻辑连接按 crc32(sockaddr) 挂红黑树;close 时不关 fd。这套"无连接协议的连接化"让上层用同一套抽象。

**Q6:worker_connections 用尽时系统怎样表现?**
三层防线递进:drain idle 连接 → accept_disabled 退出竞争 → get_connection NULL 告警,accept 路径关闭刚 accept 的 fd。

## 3.7 小结与深挖方向

本章结论:**Nginx 事件层的一切设计都围绕"压缩临界区 + 省syscall"**:accept 锁压缩到接近裸 accept,epoll ET + 用户态记账把注册压缩到每连接一次,eventfd 排空摊薄到 2^32 次,定时器惰性续约省 O(log n)。深挖:

1. eventfd 通知语义的内核依赖(唤醒合并策略改变时通知可能丢失);
2. drain_connections 的重入深度(handler 内再次 get_connection);
3. accept_mutex 与 reuseport 混合配置的行为矩阵;
4. instance 单位的完备性证明(同批次内偶数次复用的漏检窗口);
5. 超时风暴下 expire 循环的最坏延迟。
