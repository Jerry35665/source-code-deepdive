# 第 07 章 · 模块系统、配置解析与工程文化

> 基线:commit `231a60ee`(2026-09-02)。行号均以该版本源码为准。

## 7.1 配置解析:手写 tokenizer

不依赖任何生成器。`ngx_conf_parse` 以 4KB 缓冲读文件,`ngx_conf_read_token` 返回迷你状态机(OK/BLOCK_START/BLOCK_DONE/FILE_DONE/ERROR);三种解析模式对应"读文件/递归块内/-g 命令行参数"。tokenizer 用一组布尔状态变量处理引号、注释、转义与 `${var}`;token 超过 4096 字节直接报错,引号未闭合还会猜出缺的是 `"` 还是 `'`。

指令分发 `ngx_conf_handler` 线性遍历模块表做名字匹配(**没有指令哈希表——启动路径不在乎 O(N)**),依次校验模块类型、位置、收尾、参数个数。最能体现"双编号"价值的是 conf 指针三选一:

```c
if (cmd->type & NGX_DIRECT_CONF) {
    conf = ((void **) cf->ctx)[module->index];          /* core 模块直取 */
} else if (cmd->type & NGX_MAIN_CONF) {
    conf = &(((void **) cf->ctx)[module->index]);       /* main 块取地址 */
} else if (cf->ctx) {
    confp = *(void **) ((char *) cf->ctx + cmd->conf);
    conf = confp[module->ctx_index];                    /* 块内按 ctx_index */
}
```
(ngx_conf_file.c:452-464)

指令回调的返回值约定:NULL=OK,`(void*)-1`=ERROR,其他字符串被拼进报错——**错误消息天然带文件名与行号**。

## 7.2 模块系统:index / ctx_index 双编号

`ngx_module_t` 前置两个编号,后置 8 个生命周期钩子 + 8 个 spare 保留位。**index 面向全局数组与 core conf,ctx_index 面向同类型模块的私有 conf 数组**——两个编号空间解耦了"全局顺序"与"同类序号";`ngx_count_modules` 分配 ctx_index 时检查 old_cycle 保证 reload 后编号稳定。main/srv/loc conf 都是 `void *` 数组按 ctx_index 定位——这是所有指令"由内向外默认值继承"的物理载体。

**动态模块的三重安全绳**:

1. **时机检查**:modules_used 置位后加载直接报 "is specified too late";
2. **ABI 检查**:版本号 + **34 位编译期特征字符串**(逐位编码 epoll/AIO/PCRE/指针宽度等),任一不符即拒绝——避免 .so 与主程序"擦边兼容";
3. **顺序检查**:`ngx_module_order` 允许 .so 声明"我要排在某模块前面",memmove 腾位插入——**HTTP filter 的执行顺序正确性全靠它**。

dlclose 挂在 cycle pool 的 cleanup 上——又一次复用 cleanup 机制。

## 7.3 auto/ 构建体系:反 autoconf 的流派

`auto/configure` 是约 300 行 POSIX sh 脚本;特性探测不用 autoconf 宏,而是 `auto/feature`:现场生成 C 程序、编译、执行,成功则把 `#define NGX_HAVE_XXX 1` 追加进 auto_config.h。`auto/modules` 是模块表的唯一事实来源,最后用 here-doc 直接"打印"出 objs/ngx_modules.c。**零依赖(只需 sh + cc)、完全可控的输出**——与 Linux Kbuild、PostgreSQL autoconf 并列三种流派,Nginx 选择"少工具、多约定"。

## 7.4 工程文化八条观察

1. **常数 4 的哲学**:large 槽位复用扫 4 个、failed>4 淘汰——不引入可调参数,靠经验常数封顶最坏路径;
2. **代码即文档的注释密度**:自研 printf 的 30 行格式说明、hash 指针低 2 位的语义协议、转义位表的 ASCII 序标注——注释是协议声明而非复述代码;
3. **性能注释先于抽象**:memcpy 为何做成宏("gcc3/msvc/icc 会内联 rep movs")、icc 手写展开循环——每个"看似多余"的宏背后有一条具体的编译器行为注释;
4. **诚实的遗留**:从未启用的 block cache 草稿保留 `#if 0`、`/* STUB */ int num` 十几年未清、init_master 死回调——历史包袱就地标注而非掩盖;
5. **版权头即治理结构**:个人署名(Igor Sysoev)与公司署名并存的历史断层,Maxim Dounin 署名正对应动态模块机制的实现;
6. **API 极小且不设防**:palloc 对外仅 10 个函数;hash/rbtree/array 全部暴露内部结构直接操作——信任模块作者,C 生态"库即框架"的取舍;
7. **两遍扫描模式**:先求长度再填充(proxy 请求编码等),杜绝 realloc——与池化世界观配套;
8. **与同类对照**:Apache APR 支持父子池树(更复杂);Linux SLUB 面向通用负载而 Nginx slab 只服务共享内存这一确定场景,因此敢把位图塞进页头——**约束越确定,设计越激进**。

## 7.5 FAQ

**Q1:配置解析为什么没有指令哈希表?**
启动路径不在乎 O(N);真正的哈希(ngx_hash)用在请求路径(server/location/headers_in),而且是**预编译**的——配置期构建、运行期只查。

**Q2:动态模块会 ABI 不兼容吗?**
版本号 + 34 位特征串双保险,任何编译期特性开关不同,签名就不同,加载即拒绝。

**Q3:HTTP filter 顺序由什么保证?**
auto/modules 的注册顺序 + ngx_module_order 的 memmove 插入——静态可预期,无运行期仲裁。

**Q4:为什么 error_log 能多文件广播?**
log 链按级别降序,写日志沿链遍历、级别不够即 break——"低级别日志必然同写"是不变量。

## 7.6 卷五总结

> **Nginx 用"sigsuspend 自动机 + 事务式 init_cycle"组织进程,用"压缩到极限的 accept 锁 + 三代惊群方案"组织并发,用"配置期压平的 11 阶段引擎 + 单向过滤器链"组织请求处理,用"回调换挡的 upstream 状态机 + 装饰器式 LB"组织代理,最后用"池化世界观 + 位图中轴 slab + 双编号模块系统"把 25 万行 C 保持在可被单人理解的边界内。**

与前几卷对照:Redis 的 ae 与 Nginx 的事件循环是"数量级决定数据结构"的双生案例(Redis 时间事件个位数用链表,Nginx 与连接同量级用红黑树);SQLite 的"约束越确定设计越激进"(slab 位图塞页头)与 Nginx 同源;而 Nginx 的 Reload 事务式 init_cycle 与 etcd 的 Ready 四步,都是"把正确性写成语义顺序"的范例。**热路径上没有一件"顺手做的事"**——五卷之后,这条判据依然无一例外。
