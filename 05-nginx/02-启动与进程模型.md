# 第 02 章 · 启动与进程模型:sigsuspend 驱动的 master

> 基线:Nginx 1.31.5 主干,commit `231a60ee`(2026-09-02)。行号均以该版本源码为准。

## 2.0 全景:经典三件套

- **master 进程**:root 运行,持有所有 listening socket,负责配置、fork/监管 worker、信号、平滑升级。**不处理任何连接**,主循环是 `for(;;) sigsuspend()`(ngx_process_cycle.c:139-163),完全由信号驱动;
- **worker 进程**:低权限用户运行,跑事件循环承载连接;worker 之间"无共享",各自竞争同一批监听端口;
- **cache manager/loader**:按需 fork;loader 只在启动后 60 秒做一次索引然后 `exit(0)`,不 respawn。

贯穿三者的是两个核心结构:**ngx_cycle_t**(一"代"运行时配置的总持)与 **ngx_processes[](1024 槽进程表)**。每次 reload 都构造一个新 cycle,成功后替换全局 `ngx_cycle`,旧 cycle 延迟 30 秒回收。

## 2.1 main() 到 master 循环

```
main (nginx.c:199)
 ├─ ngx_get_options(-s stop|quit|reopen|reload → SIGNALLER 模式)
 ├─ ngx_log_init → init_cycle(1KB 池)→ ngx_save_argv → ngx_os_init
 ├─ ngx_add_inherited_sockets: 解析 $NGINX env 的 "fd;fd;..."(平滑升级继承)
 ├─ ngx_preinit_modules(静态模块编号)
 ├─ ngx_init_cycle(&init_cycle) ←── ★ 核心
 ├─ [-t/-T 在此出口; -s 在此读 pidfile 发信号退出]
 ├─ ngx_init_signals(sigaction,daemon 之前!)
 ├─ ngx_daemon(fork→setsid)→ ngx_create_pidfile(此后才写 pid)
 └─ ngx_master_process_cycle / ngx_single_process_cycle
```

**ngx_init_cycle 是全项目最核心的函数**(ngx_cycle.c:38-954),同时服务五种入口(首次启动、-t、-s、reload、平滑升级的新二进制),差异只靠三个开关裁剪。它的内部是一个**事务式设计**:old_cycle 始终作为"未提交状态"的基线被完整保留,新 cycle 的每一步资源申请都可回滚,失败路径与成功路径对称(833-953 与 655-779 几乎是镜像操作)。reload 的语义因此可概括为"两阶段提交":新 cycle 全部就绪(init_module 是 commit 点)之后,才进入清理旧资源的第二阶段。

两个最关键的细节:

1. **listening 差分**:新配置与 old_cycle 的监听逐一 `ngx_cmp_sockaddr`,相同则**直接继承旧 fd**——这是 reload 不间断服务的关键(513-612);
2. **共享内存复用**:新 zone 与 old_cycle 按 name+tag+size 匹配则复用旧映射地址(零拷贝热升级),否则分配 + slab 初始化(417-508)。

**模块初始化分层**:ngx_modules[] 由 configure 脚本链接期生成 → preinit 编号 → create_conf(解析前)→ load_module(动态,校验 version + 34 位编译期特征签名)→ init_conf → init_module(master 一次)→ **init_process(每次 fork 的 worker 内)** → exit_*。注意:`init_master` 回调在 ngx_module.h:243 声明但**全仓库无调用点**——第三方模块在其中放置的初始化逻辑永远不会执行。

## 2.2 master 的信号状态机

信号表硬编码(ngx_process.c:39-83);master 主循环**先 sigprocmask 屏蔽全部信号,再 `sigsuspend(空集)` 原子解锁等待**(87-104)——信号 handler 只置 volatile 标志,真正的逻辑在 sigsuspend 返回后串行执行。这是教科书级的"信号处理最小化"设计;全部状态浓缩在十个全局标志位里,把主循环的每个 if 分支看作状态转移,整个 master 就是一张以 sigsuspend 唤醒为时钟节拍的自动机。

逐信号解读:

- **SIGHUP(reload)**:`ngx_init_cycle` 全量重建;**失败则打回旧 cycle 继续跑,reload 永不致命**(233-251)。成功则以 JUST_RESPAWN 起新 worker,`ngx_msleep(100)` 后向旧 worker 发 QUIT;
- **SIGTERM(terminate)**:**退避升级状态机**——delay 从 50ms 起、每次 SIGALRM 翻倍,sigio 计数器对应子进程确认,超 1 秒后直接 SIGKILL(203-223)。stop 并非一次性广播,而是"先礼后兵"的渐进式绞杀;
- **SIGQUIT(quit)**:走通道命令 NGX_CMD_QUIT,worker 关监听、关 idle 连接、**等所有定时器归零才真正退出**(742-771);
- **SIGUSR2(平滑升级)**:见 2.3;
- **SIGCHLD(reap)**:waitpid 循环收割;**退出码为 2 且原计划 respawn 的,取消 respawn**——exit(2) 是初始化失败的约定值,不禁止会陷入 crash loop(551-557);随后 `ngx_unlock_mutexes` 强制释放死进程持有的 accept mutex 与 slab 锁(564-608)。

worker fork 时继承 master 的屏蔽字,因此 init 里显式 `sigprocmask(SIG_SETMASK, 空集)` 解除。

## 2.3 平滑升级:一次 execve 的接力

USR2 触发 `ngx_exec_new_binary`(nginx.c:715-824),四步:

1. **构造 NGINX 环境变量**:把所有 listening fd 序列化成 `NGINX="7;8;9;"`。**监听 socket 刻意不设 FD_CLOEXEC,而日志/通道 fd 都设了**——execve 后监听 fd 原封不动落在同号新二进制里(ngx_cycle.c:401-408 vs nginx.c:746-754);
2. **pid 改名** `pid → pid.oldbin`,fork + execve 新二进制;
3. 新二进制读 $NGINX 还原 fd,`ngx_set_inherited_sockets` 反向探测重建 listening 元数据;因 inherited 跳过 daemonize;
4. **防呆守卫**:USR2 handler 里 `if (ngx_getppid() == ngx_parent || ngx_new_binary > 0) ignore`——防新旧 master 互相误触发(ngx_process.c:374-391)。

若升级失败(新二进制 crash),旧 master reap 到后把 pid.oldbin 改名回 pid——**回滚是文件名级别的:监听 fd 一直握在旧 master 手里,从未关闭**。升级窗口内两代进程共享同一批监听端口,accept 竞争交给内核;两代的 shm zone 经 init_cycle 复用逻辑映射到同一块物理内存,锁本身是共享的。

## 2.4 worker 的初始化序列

`setpriority → setrlimit → setgid → initgroups → setuid`(先降组再降用户,顺序不可逆)→ CPU 亲和 → `PR_SET_DUMPABLE`(保证 setuid 后仍能 coredump)→ 解除信号屏蔽 → init_process 回调 → **关闭其他所有进程的 channel[1]**(fork 拷来的副本,不关会干扰彼此的 SIGIO)→ 注册 channel 读事件(ngx_process_cycle.c:782-969)。

进程间通道是每个子进程一对 socketpair,通过 `NGX_CMD_OPEN_CHANNEL` 广播形成"所有进程互相知道对方通道"的全互联拓扑——master 与 worker 的命令分发基础设施。

## 2.5 设计动机:为什么 master-worker 而不是线程

1. **隔离故障域**:worker segfault 不殃及其他连接,SIGCHLD 无脑 respawn 自愈;复杂度从"锁代码"转移到"锁的生命周期管理"(死进程强制解锁);
2. **权限分离**:只有 master 需要 root,worker 降权;线程模型无法在同一进程内 setuid;
3. **平滑升级的可行性**:execve 只能替换单个进程镜像,fork 模型天然支持 fd 接力;多线程程序 exec 会杀死所有线程;
4. **信号即控制面**:`nginx -s` 甚至可以是独立启动的进程读完配置后 kill() 就退出——控制面与数据面零耦合;
5. **COW 的低廉启动**:N 个 worker 的边际内存只是各自的事件表和连接池;`ngx_setproctitle` 复用 argv 内存区改写进程标题,让 ps/top 直接读出状态——对排障的价值不亚于日志。

## 2.6 FAQ

**Q1:`nginx -s reload` 新起的进程做了什么?**
完整走 main → init_cycle(所以 -t 能查的它也能查),但提前返回只读 pidfile、kill(pid, SIGHUP) 即退出;不碰监听 socket。

**Q2:reload 时配置有错怎么办?**
init_cycle 返回 NULL,master 回到旧 cycle 继续跑,只留一条 error 日志;监听 fd 从未被旧 cycle 关闭,零影响。

**Q3:QUIT 和 TERM 的实质区别?**
QUIT 走通道命令,worker 排空定时器再退;TERM 在 master 侧 50ms→翻倍退避,超 1 秒 SIGKILL。

**Q4:worker 崩溃后共享内存里的锁怎么办?**
master 在 waitpid 后强制解锁(依赖 shmtx 记录持有者 pid 的机制)。

**Q5:master 为什么用 sigsuspend 而不是 sleep?**
信号可能恰在"检查标志"与"睡眠"之间到达;sigprocmask + sigsuspend 是 POSIX 唯一无竞态方案。

**Q6:pid 文件为什么不在解析完配置立刻写?**
daemon 之前写的 pid 是"将死的父进程"的,必须等 fork 后再写。

**Q7:daemon off / master_process off 分别改变什么?**
前者跳过 daemonize(容器前台);后者不 fork、当前进程直接跑 worker 事件循环(但不降权)。

**Q8:`-s` 能发 USR2/WINCH 吗?**
不能:signals[] 表没有对应名字,官方有意让平滑升级走人工确认路径。

## 2.7 小结与深挖方向

本章结论:**master = sigsuspend 自动机 + 事务式 init_cycle;worker = COW 副本 + 权限递降 + 全互联通道;平滑升级 = fd 继承 + 文件名级回滚**。深挖:

1. 进程表槽位碎片化与两次 reload 间隔 <100ms 时 just_spawn 标志的清理竞态;
2. sigio 计数与 SIGALRM 退避的正确性逐行推演(stop 是否可能停滞);
3. 旧 cycle 延迟回收与 worker 退出时机的竞争(ngx_exit_cycle 静态结构是否为兜底);
4. 共享内存 zone 复用的 tag(模块指针)碰撞面;
5. init_master 死回调的历史与文档空白。
