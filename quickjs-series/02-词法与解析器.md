# 第 02 章 · 词法与解析器:递归下降直出字节码

> 基线:commit `04be246`。行号以 quickjs.c 为主。QuickJS 解析器的最大特色:**无 AST——边解析边向字节码缓冲追加指令**,解析完成后仅做三趟线性 pass。

## 2.0 全景:直出字节码的流水线

```
源码 → next_token(:22829 词法) → js_parse_program(:37078)
        │  递归下降:语句/表达式函数直接 emit_op 落码
        ▼
线性字节码(DynBuf fd->byte_code)+ 变量表 + label 槽表
   → resolve_variables(:34187 变量绑定)
   → resolve_labels(:34796 跳转重写+窥孔+SHORT_OPCODES 降级)
   → compute_stack_size(:35753 栈深上界)
   → js_create_function(:36024)打包 JSFunctionBytecode(:685-724)
```

对照 V8 的 AST 中间层:直出的内存峰值低、单遍完成、代价是"复用/改写困难"——优化只能以线性 pass 的形式后置。三个 pass 的调用点在 js_create_function(:36100/:36115/:36118)。

## 2.1 词法:单 token 缓冲与 / 歧义

next_token 大 switch(:22829-23269):单字符 token 直接用 ASCII 码(:23256);JSToken 双 union(:22111-22132:str/num/ident/regexp 四形态)。**单 token 缓冲,无 lookahead 队列**:前看靠 peek_token/simple_next_token(:23755/:23670)轻量重扫或 seek_token 回卷。`/` 的除法/正则歧义**不在词法层**:词法器总返回 `/`,`js_parse_postfix_expr` 在主表达式位置回退 buf_ptr 重扫为正则(:26878-26914);skip_parens_token 里另有 is_regexp_allowed 启发(:24760,自注对箭头函数失效 :24798)。关键字映射靠"atom 序号-1+TOK_FIRST_KEYWORD"(update_token_ident,:22739-22765)——atom 与 TOK 枚举同序是硬前提。ASI 集中在 js_parse_expect_semi(:22378-22388):EOF/`}`/got_lf 三条件;受限产生式散布于 return(:28971)/throw(:28990)。标识符 Unicode 判定委托 libunicode 的 lre_js_is_ident_first/next(libunicode.h:169-194)。

## 2.2 递归下降:硬编码的优先级阶梯

二元优先级不用表,用**硬编码 level 0-8 递归**:js_parse_expr_binary(:27733-27897)逐级下降——8 层函数对应 8 档优先级。语句分派是全文件最大 switch:js_parse_statement_or_decl(:28901-31360,约 2460 行,27 个 case)。箭头函数判定靠跳读括号(js_parse_skip_parens_token :24800)。错误策略:**报错即停**(js_parse_error_v :22330,无恢复)——单遍直出的天然选择。

## 2.3 直出字节码:emit 与 label 补丁

emit 族直接落码:emit_op/emit_u32/emit_atom(:23864/:23847/:23873);`fd->last_opcode_pos` 记尾指令供窥孔改写(:24918 的 set_object_name)。跳转用"**label 槽号作操作数**"两遍式:LabelSlot(:21927)+RelocEntry 单链表;resolve_labels 搬码时遇已定义 label 直接写相对偏移,未定义则挂 reloc 链、遇 OP_label 回扫回填(:34919-34937;add_reloc :34620)。**同一趟做窥孔与 SHORT_OPCODES 缩编码**(OPTIMIZE=1,文件头 :50):push/drop 删除、i32 neg 合并、常量条件折叠在 :35165-35233——无传统常量折叠器(grep "fold" 为空),优化全部在线性 pass 里。

## 2.4 闭包与函数编译

闭包解析:get_closure_var 递归 parent 链(:32736-32760),父链变量回溯(:33106-33183)——变量解析的栈深度回溯产生 JSVarRef 间接层(03 章展开)。函数编译 js_parse_function_decl2(:36500):rest 参数 OP_rest(:36727/:36765),参数表达式探测(:36692-36697)。try/catch 落码:TOK_TRY 分支(:29387-29502),OP_catch 于 :29401。模块无独立函数:__JS_EvalInternal(:37188)按 JS_EVAL_TYPE_MODULE 强制严格模式(:37230),import/export 在 js_parse_source_element(:32046-32054)分派,只建导入导出表不产码。

## 2.5 设计动机

1. **为什么免 AST**:内存目标(峰值=线性字节码+表)与单遍速度;AST 的"可复用"对一次性脚本无价值——**约束淘汰架构**;
2. **优化后置到线性 pass**:直出后代码已可执行,优化是"搬码+改写"的廉价操作(resolve_labels 同趟完成窥孔+缩码)——把优化器从"树变换"降维成"数组变换";
3. **优先级硬编码 vs 表驱动**:8 层递归的可读性/调试性优于表——Bellard 的反表驱动选择(对照 FFmpeg/Git 的表驱动哲学,见 cross-series 模式 1 的边界);
4. **报错即停**:嵌入式与工具链场景,错误恢复的价值低于实现成本。

## 2.6 FAQ

**Q1:真的完全没有 AST 吗?**
是:唯一中间态是线性字节码+变量/label 表(:22134 起的解析直出);三趟 pass 都是线性变换。

**Q2:`/` 怎么知道是除法还是正则?**
词法层不知道:主表达式位置回退重扫(:26878-26914)——慢一点但零维护。

**Q3:ASI 实现完整吗?**
集中三条件(:22378-22388)+受限产生式散点(:28971 等):规范要求的场景全覆盖。

**Q4:标签跳转怎么回填?**
label 槽号作操作数+reloc 链(:34620),resolve_labels 搬码回填(:34919-34937)。

**Q5:有常量折叠吗?**
无传统折叠器;有窥孔(push/drop 删除等 :35165-35233)——线性 pass 里的局部优化。

**Q6:箭头函数怎么判定?**
跳读括号猜(:24800),对含正则的参数会猜错再恢复(自注 :24798)。

**Q7:parse 错误的行号怎么报?**
解析器维护行号计数,js_parse_error_v(:22330)带上;字节码侧靠 pc2line(:673-676 差分)。

**Q8:模块的 import/export 编译成什么?**
不产码:只建导入导出表(:32046-32054),链接在模块加载期。

**Q9:严格模式怎么传播?**
eval 类型标志强制(:37230)+函数级解析标志——无独立 pass。

**Q10:解析器能被 fuzz 吗?**
能:fuzz/ 目录含解析 target,报错即停使 fuzz 简单(只测不崩)。

## 2.7 小结与深挖方向

本章结论:**解析器="递归下降直出+三趟线性 pass+报错即停"**;AST 缺席是内存约束下的架构自信。深挖:

1. resolve_variables(:34187)的作用域栈与 TDZ 判定;
2. 窥孔规则全集(:35165-35233)的正确性边界;
3. compute_stack_size(:35753)的上界紧度(65534 上限 :211);
4. seek_token 回卷在超长行的性能;
5. 直出模式对 source map 类工具的障碍。
