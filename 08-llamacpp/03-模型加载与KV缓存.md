# 第 03 章 · 模型加载与 KV 缓存:GGUF 与两阶段提交

> 基线:llama.cpp master tarball(2026-09)。行号以当前快照为准。
> 重要勘误:本快照是**重构后的新版本**——经典 defrag 已被整体移除、旧版基于 u_pos 时间戳的驱逐不复存在;社区旧资料的 KV cache 描述对本版已失效。

## 3.0 全景:从 GGUF 到可推理模型

```
GGUF 文件 → gguf_init_from_file(纯元数据视图, no_alloc)
  → llama_model_loader(权重索引 + meta 校验 + 架构分派)
  → load_hparams → load_vocab → load_tensors(mmap 直钉 / 异步上传)
  → llama_context.create_memory(按架构分派内存对象)
  → llama_kv_cache / iswa / hybrid(llama_memory_i 接口族)
```

内存对象按架构分派(create_memory 巨型 switch,llama-model.cpp:2245 起):SWA 模型 → `llama_kv_cache_iswa`;注意力+递归混合 → `llama_memory_hybrid`;纯编码器(BERT 系)→ nullptr。

## 3.1 GGUF 格式:逐字段

```
0x00  "GGUF" magic(4B)
0x04  version u32(=3;v1 直接拒绝)
0x08  n_tensors i64     ← 注意:n_tensors 在 n_kv 之前(与部分博客相反)
0x10  n_kv i64
── KV 元数据区(13 种类型;字符串 = u64 长度 + 内容;重复 key 硬错误)
── 张量信息区(name/n_dims≤4/ne[]/type/offset;int64 溢出检查防恶意文件)
── padding 到 2 的幂对齐(general.alignment 可覆盖,默认 32)
── tensor data 二进制段(offset 必须严格等于前面 PAD 的累加)
```

mmap 友好性是设计的核心:header/KV/索引是一个很小的前缀,`data_offset + tensor.offset` 即绝对偏移——这正是 `llama_tensor_weight{文件, 偏移, 元张量}` 的构造(llama-model-loader.h:46),构造时立刻做边界校验防损坏文件。

## 3.2 加载流水线

- **kv_overrides**:GGUFMeta::GKV 模板带类型检查;支持 bool/int/float/str 四类用户覆盖;`get_key_or_arr` 允许"标量或恰好 n 长数组"——兼容"per-layer 标量升级为数组"的模型演进;
- **create_tensor**(1109-1383):按 LLM_TN 命名表查张量类别与算子;`weight_buft_supported` 为每个候选 buffer type 构造哑算子图试 `ggml_backend_dev_supports_op`;用户可用正则 `tensor_buft_overrides` 强制某些层上/下 GPU;
- **load_all_data 双通道**:mmap 路径把权重直接"钉"在映射地址上(**零拷贝**);非 mmap 路径用 4 个 1MiB pinned staging buffer + event 双缓冲异步上传 GPU。mmap 完成后把头尾未用的页段 unmap 掉;
- **懒加载**:超大张量(默认阈值 4GiB)不进主映射,按行按需 `load_data_range`。

## 3.3 KV cache:两阶段提交的状态机

本版 KV cache 的核心是**带快照回滚的两阶段提交**:`prepare()` 对整批 ubatch 试探性 find_slot + apply_ubatch,失败按状态栈整体恢复(llama-kv-cache.cpp:751-815)。状态机核心:

- **每 cell 一个 256 位 seq 位图** + 每序列按 pos 有序的 `seq_pos` 索引(llama-kv-cells.h:516-524)——使 seq_cp(序列复制)同流零拷贝、seq_pos_min/max O(1),并支撑 apply_ubatch 的连续性 purge 不变式;
- **槽位分配**:head 环形指针 + 空位优先 + SWA 过期 cell 抢占(1042-1061)——旧版"u_pos 时间戳驱逐"已删除;
- **defrag 已被整体删除**:`defrag_thold` 标记 DEPRECATED(默认 -1 禁用),cell 搬移函数被注释废弃——**根因是写入改用 `ggml_set_rows` 散写任意 cell,cell 不再需要连续,碎片整理失去存在前提**(llama-kv-cache.cpp:1350/1385)。这是"硬件能力改变算法"的漂亮案例。

序列操作语义:seq_keep(只保留某序列)、seq_rm(区间删除)、seq_cp(复制——fork 出并行采样的分支,零拷贝共享 cell)。

## 3.4 SWA / Flash Attention / 量化 KV

- **SWA(sliding window attention)模型的层交替**:iswa 容器管理 SW 层与全注意力层的不同 slot 窗口,过期 cell 可被抢占复用;
- **量化 KV 配套 Hadamard 正交旋转**:量化 K/V 时启用 `attn_rot_k/v`(写前旋进、读后旋出,K-shift 按"旋出→RoPE→旋进"处理,llama-kv-cache.cpp:321-363);
- **"量化 V 必须开 Flash Attention"有两处硬检查**(llama-context.cpp:463-467);V 是否转置缓存完全由 `v_trans = !flash_attn` 决定(llama-model.cpp:2569)——FA 路径即"V 不转置缓存"的落点。

## 3.5 FAQ

**Q1:GGUF 头里 n_tensors 和 n_kv 谁在前?**
n_tensors 在前(gguf.cpp:516-536)——与很多博客写的相反。

**Q2:权重可以放一部分在 GPU 吗?**
可以:create_tensor 按 buffer type 逐张量放置(哑算子图试探),正则覆盖可强制某些层上下 GPU。

**Q3:KV cache 会碎片化吗?**
cell 不再要求连续(set_rows 散写),物理碎片失去意义;逻辑碎片由 prepare 失败 → 重试处理。

**Q4:为什么量化 V 必须开 FA?**
非 FA 路径要求 V 转置缓存,量化格式不支持转置后的高效读取;FA 的"V 不转置"正是量化 V 的落点。

**Q5:seq_cp 会复制 KV 数据吗?**
不会:seq 位图让同一 cell 属于多个序列,复制只是位图运算——并行采样的 fork 零拷贝。

## 3.6 小结与深挖方向

本章结论:**加载 = "mmap 零拷贝 + 按算子支持的设备放置";KV = "256 位 seq 位图 + 两阶段提交 + SWA 窗口"**;defrag 之死证明了"接口能力(set_rows 散写)决定数据结构形态"。深挖:

1. 256 位 seq 位图的序列数上限(LLAMA_MAX_SEQ=256?)与扩展性;
2. prepare 失败回滚栈的深度与代价;
3. 懒加载 ranges 的逐行读取对旋转盘的影响;
4. hybrid memory(注意力+递归)的槽位协调。
