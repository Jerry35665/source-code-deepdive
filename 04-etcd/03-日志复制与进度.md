# 第 03 章 · 日志、复制与进度:三段式日志与 Progress 三态机

> 基线:etcd-io/raft,commit `3cbf6a74`(2026-09-02)。行号均以该版本源码为准。
> 一个架构级事实:**本 commit 中旧版的 `Progress.needSnapshotAbort()` 已消失**(全库 grep 无命中),等价判断被搬进 raft.go:1531-1545——Progress 变成不回指 raftLog 的纯数据状态机。理解该库当前架构区别于旧版教程的关键。

## 3.0 全景:日志的三段式视图

```
             索引轴 ──────────────────────────────────────────►
 storage:   [ ...已 compact... | dummy | e1 | e2 | e3 ──────]│
                                                 ▲           │
 unstable:                                       [ e4 | e5 ──]│  offset = storage.LastIndex()+1
                                                 ▲     ▲      │  offsetInProgress(写入中,双缓冲)
 游标:  firstIndex               committed ≤ lastIndex        │
               applied ≤ applying ≤ committed
```

- **Storage**(storage.go:48-96):应用实现的持久层接口,raft 库只读——写动作全部经 Ready 交还应用;契约写明:任何 Storage 方法报错,raft 实例"不可操作并拒绝参与选举";
- **unstable**(log_unstable.go:37-54):内存中尚未确认落盘的条目。两个下标 `offset` 与 `offsetInProgress` 构成**双缓冲**——条目从"待写"翻转到"写入中",再由 stableTo 清空;
- **游标组**:committed(quorum 已持久化)/ applying(已下发 apply)/ applied(确认完成)。

注意与"教科书 Raft"不同的设计:**committed 不要求本地已持久化**(nextCommittedEnts 注释直说,log.go:215-219),由 `allowUnstable` 参数决定是否把 unstable 区间内已提交的条目交给应用。

## 3.1 Append 流程:maybeAppend 的三步走

```go
func (l *raftLog) maybeAppend(a logSlice, committed uint64) (lastnewi uint64, ok bool) {
    if !l.matchTerm(a.prev) { return 0, false }      /* 1) prev 对不上 → 拒绝 */
    lastnewi = a.prev.index + uint64(len(a.entries))
    ci := l.findConflict(a.entries)                  /* 2) 找冲突 */
    switch {
    case ci == 0:                                    /* 无冲突:前缀/延伸 */
    case ci <= l.committed:
        l.logger.Panicf(...)                         /* 与已提交冲突 = 安全性破坏, fail-fast */
    default:
        l.append(a.entries[ci-a.prev.index-1:]...)   /* 3) 从冲突点截断追加 */
    }
    l.commitTo(min(committed, lastnewi))             /* 4) commit 不超过 lastnewi */
    return lastnewi, true
}
```
(log.go:109-131)

maybeAppend 现在接收 `logSlice` 不变式载体(types.go:67-74,声明 4 条良构不变式)——这是近年重构方向(TODO 表明计划下沉到 unstable);代码里的 panic 分支本质是"不变式被破坏后的最后一道闸"。

**commit 的 quorum 计算是"排序取中位数"而非计数**:链路 `raft.maybeCommit` → `tracker.Committed()`(tracker.go:179-181)→ `JointConfig.CommittedIndex` 取两半 min(quorum/joint.go:49-56)→ `MajorityConfig.CommittedIndex` 排序后取 `srt[n-(n/2+1)]`(quorum/majority.go:156-162)。一次排序同时解决"缺席 voter 填 0"与"多数派下界";**联合共识的提交安全性由该算术直接保证而非规则约束**。

isUpToDate(选票比较)用 `(term, index)` 二元组(log.go:442-445):term 大者优先;相同才比 index 且**相等也算通过**——避免等长日志互拒的僵局。

游标推进的防护:commitTo 只进不退,超过 lastIndex 直接 panic("Was the raft log corrupted, truncated, or lost?");`unstable.stableTo` 却做**三重竞态容忍**(条目已不在/命中快照/term 不匹配都只打日志忽略)——落盘确认与日志覆盖之间的竞态是合法的(log_unstable.go:138-164)。

## 3.2 Progress 三态机与 flow control

leader 为每个 follower 维护一个 `Progress`(tracker/progress.go):

```
        ┌────────────┐  MaybeUpdate 成功              ┌───────────────┐
        │ StateProbe │ ──────────────────────────► │ StateReplicate │
        └────────────┘                              └───────────────┘
              ▲  MaybeDecrTo 后(拒绝)                    │  Match+1 ≥ firstIndex
              │ log.term(Next-1) 查不到 → 发快照          ▼ (经 Probe 过渡)
        ┌───────────────┐ ◄── BecomeProbe ─────────  (raft.go:1531-1545)
        │ StateSnapshot │   Next=PendSnap+1, IsPaused 恒 true
        └───────────────┘
```

发送侧 `SentEntries`(165-185)按状态分流:**StateReplicate 是滑动窗口**——乐观推进 Next、Inflights 记账、窗口满即暂停;**StateProbe 是停等式**——每轮探测只发一条。接收侧 `MaybeUpdate`(205-213)单调提升 Match、`Next = max(Next, n+1)` 维持 Match < Next 不变式;`MaybeDecrTo`(226-254)的防伪逻辑两态不同——Replicate 只查 `rejected <= Match`(Match 单调,便宜);Probe 要求 `rejected == Next-1`(探测一次只发一条才使防伪成为可能)。**两种状态各自选择了最便宜的正确性检查**。

Inflights 是教科书级环形缓冲(inflights.go):`FreeLE` 从 start 弹出 index ≤ to 的在途消息;`maxBytes` 是**软限制**——允许最后一条压线消息通过,避免单条大条目死锁。活性细节:Replicate 下窗口满时只发**空 MsgApp**传递 commit 索引,保证全量 inflight 丢包时窗口仍能靠 ack 自清空(raft.go:636-643 注释完整推演了自恢复路径)。

## 3.3 confchange:联合共识的线性化实现

`confchange.Changer` 是**值语义的变换器**:每次 `checkAndCopy()` 深拷贝配置与进度,在副本上应用变更,返回前重跑不变量检查——**校验先行,拒绝发生在配置生效之前**,原配置毫发无损(confchange.go:27-30)。

- `EnterJoint`(51-78):把 `C_old` 变成 `C_{old,new}`——清空 outgoing、把 incoming 复制过去;变更只打在 incoming 上;
- `LeaveJoint`(94-121):`LearnersNext` 暂存的降级节点转正、删除既非 voter 也非 learner 的节点进度、清空 outgoing;
- `Simple`(128-145):单步捷径,用 symdiff 强制"至多改变一个 voter"——超出即必须走联合共识,这是论文"一次一变"安全边界的代码落点。

一个反直觉但关键的保留:**联合期内被移除节点的 Progress 不删**——它的 Match 仍是 outgoing 多数派计票的输入,删了它配置变更日志可能在旧多数派未确认时被误判提交,破坏联合共识的核心保证(240-243)。同理 `LearnersNext` 暂存区解决"节点同时是 outgoing voter 和 learner"的不变量冲突(tracker.go:43-77)。

## 3.4 设计动机七条

1. **unstable 双缓冲**:把"写盘请求已下发"与"确认已返回"分开表达——否则 Ready 会重复吐条目;
2. **三游标而非两游标**:applying 为异步 apply 而生,配合 `maxApplyingEntsSize` 字节配额——应用可流水线 apply 而不淹没状态机;这是"库把流控做厚、并发自由让给应用"的取舍;
3. **quorum 排序取中位数**:≤7 节点栈上数组零分配,无状态可单测;代价是每次 MsgAppResp 重算 O(n log n),划算;
4. **Progress 与 raftLog 解耦**:纯数据状态机可独立构造与测试(旧版 Progress 内嵌 raftLog 指针);
5. **Probe 停等、Replicate 开窗**:各选最便宜的防伪检查;
6. **Changer 值语义**:配置变更半途生效难以回滚,宁可每次深拷贝 ProgressMap(频率极低);
7. **Inflights 字节软上限**:硬限制会让单条大条目死锁。

## 3.5 FAQ

**Q1:committed 在本地未落盘时推进,不安全吗?**
committed 的定义是"quorum 节点上已知持久化"的水位;本地落盘只影响崩溃后能否恢复到该位置,保守应用走 allowUnstable=false 路径。

**Q2:findConflict 命中 committed 区间为什么 panic?**
Raft 保证已提交条目永不被覆盖;若冲突落在此区间说明选举或日志恢复出了根本性错误,静默修复反而危险——fail-fast。

**Q3:Inflights 的 maxBytes 为什么是软限制?**
硬限制会死锁:一条超配额的消息永远无法发出、窗口永远无法释放。

**Q4:联合共识期间被移除节点的 Progress 为什么不删?**
它的 Match 是 outgoing 多数派计票输入;删了会导致配置变更日志被误判提交。

**Q5:MaybeDecrTo 在 Probe 态为什么要求 rejected == Next-1?**
停等式使防伪成为可能;注释承认只是 best effort——误判后果只是多探测几轮。

**Q6:MemoryStorage 为什么用 dummy 条目?**
Compact 后保留复制被删首条 (Index,Term) 的哨兵,维持 `ents[i].Index = ents[0].Index + i` 全局不变式,且 `Term(firstIndex-1)` 仍可查询——Append 匹配的存储侧支撑。

## 3.6 小结与深挖方向

本章结论:**日志 = 三段式 + 三游标 + 双缓冲;复制 = Probe 停等 / Replicate 滑窗的两态流控;提交 = 排序取中位数的纯函数;成员变更 = 值语义试算 + 联合双多数**。深挖:

1. logSlice 不变式下沉尚未完成(TODO 追踪可预判 API 演化);
