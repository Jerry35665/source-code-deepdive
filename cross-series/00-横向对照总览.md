## 二、十大横贯模式

### 模式 1:表驱动一切(回调表+注册表)

| 项目 | 实例 |
|---|---|
| FFmpeg | URLProtocol 回调表(url.h:53-99);编码回调 FF_CODEC_CB(libx264.c:1652);SIMD 分发阶梯(x86/swscale.c:485);swscale ops 后端(ops.c:42);RTP payload 注册表(rtpdec.c:75-132);pixdesc 全格式描述符表(pixdesc.c:203) |
| Git | ref_storage_be 虚函数表约 30 指针(refs-internal.h:567-601);commands[] 分发表 149 条(git.c:533-689);commit-graph chunk 常量表(commit-graph.c:44-53);git_hash_algo 函数表(hash.h:294-335) |
| Redis | redisCommand 命令表(名称→处理函数→arity→标志) |
| Nginx | ngx_module_t 模块数组+phase engine |
| llama.cpp | ggml ops 分发(计算图节点→后端内核) |

**判据**:新增能力=加表项,不改分发器。表是扩展点,分发器是宪法。

### 模式 2:乐观并发+校验回退(先信快路径,错了升级)

| 项目 | 实例 |
|---|---|
| Git | index 的 stat 缓存:racy 三层防线(mtime 锚点 read-cache.c:2313-2314→内容哈希升级 :434-439→写时 smudge :2574-2622);辅助索引校验失败即弃回退(commit.c:625) |
| FFmpeg | get_format 剔除重试:硬解失败自动降级软解(decode.c:1348-1357) |
| K8s | RV 乐观锁+Resync 兜底(事件不可靠的三层保险) |
| etcd | PreVote:试探与正式选举分离,分区回归零扰动 |

**判据**:快路径的"误判"必须有升级路径兜底,且升级只损失性能不损失正确性。

### 模式 3:写时整理(后台压实换前台效率)

| 项目 | 实例 |
|---|---|
| Git | repack 的 delta 三闸门贪心(try_depth/尺寸/类型,pack-objects.c:2808-2859);reftable 几何压实(stack.c:1550-1624);commit-graph split 合并(:2311-2312) |
| LevelDB | LSM 分层 compaction |
| Kafka | 段级 LogCleaner |
| SQLite | WAL checkpoint 回填 |

**判据**:前台写入用最笨格式保快,后台用最聪明算法整理;钳住最坏读取路径比全局最优重要。

### 模式 4:原子替换(temp+rename 的 N 种化身)

| 项目 | 实例 |
|---|---|
| Git | 引用 .lock+fsync+rename(files-backend.c:2058-2077);reftable 写新表+tables.list 单行提交(stack.c:775-848) |
| SQLite | journal/temp 文件+rename |
| FFmpeg | HLS 清单 .tmp+rename(hlsenc.c:1679-1683) |
| LevelDB | MANIFEST 切换 |
| K8s | 滚动更新守恒公式(不中断换血) |

**判据**:文件系统的 rename 原子性是最便宜的分布式原语——能用它就绝不发明新机制。

### 模式 5:不可逆操作的宽限(时间维反悔)

| 项目 | 实例 |
|---|---|
| Git | reflog 写在引用生效前(files-backend.c:1986-2006,:3355-3361);cruft pack 按 mtime 宽限(pack-write.c:333,prune expire :98-99);worktree prune 同款(worktree.c:1004-1013) |
| Kafka | 段保留期 |
| Redis | 渐进过期+淘汰预算 |
| etcd | 历史 compaction |

**判据**:删除类操作必须有时间维度上的反悔窗口;"宁可缓删"是统一安全模式。

### 模式 6:伪装与适配层(让 A 消费者无感地吃 B)

| 项目 | 实例 |
|---|---|
| FFmpeg | RTMP 消息伪装 FLV 文件(rtmpproto.c:2941-2947);HLS 分片流拼成连续字节流(read_data_continuous,hls.c:1761);AES-128 下沉 crypto 协议(hls.c:1528-1544) |
| Git | shallow=nr_parent=-1 的 graft 视错觉(shallow.c:32-45)——对象层零侵入实现"浅" |
| llama.cpp | prefill/decode 同源(差异只是 batch 标志) |
| Nginx | upstream 抽象让 proxy 与 fastpath 同构 |

**判据**:适配层的美德是"被适配方零改动"——能骗过消费者就不改协议。

### 模式 7:唯一汇聚点(全局策略住全局唯一处)

| 项目 | 实例 |
|---|---|
| FFmpeg | 中断/超时唯一汇聚 retry_transfer_wrapper(avio.c:571-614);全局 DTS 节流 schedule_update_locked(ffmpeg_sched.c:1422-1513) |
| Git | config 层级后写覆盖即优先级(config.c:1556-1622 的固定顺序) |
| K8s | apiserver 作为唯一写入口(admission 下推消除 TOCTOU) |
| Redis | serverCron 周期任务汇聚 |

**判据**:全局控制面分散在 if 里是 bug 温床;收权到一个函数,策略才可审计。

### 模式 8:引用与对象分离(声明层与真值层)

| 项目 | 实例 |
|---|---|
| Git | refs(可变)→objects(不可变):分支=41 字节文件,创建 O(1);rebase 只换指针(refs_update_ref,sequencer.c:5245) |
| K8s | desired state(etcd)vs actual state(节点)——调和循环填缝 |
| Kafka | consumer offset 的提交语义(声明位点 vs 实际消费) |
| FFmpeg | AVFrame 引用计数:所有权显式化后零拷贝才安全 |

**判据**:把"你想要的"与"你有的"分两层,系统获得"廉价改主意"的能力。

### 模式 9:找回优于修复(不可变数据的损坏观)

| 项目 | 实例 |
|---|---|
| Git | 对象名=内容哈希 ⇒ "修复"概念不存在,只有"换正确副本";fsck dangling 产品化(builtin/fsck.c:281-351)+--lost-found 落盘(:320-342);三层完整性(写时哈希/fsck 连接性/index-pack 传输) |
| SQLite | journal 回滚+integrity_check |
| LevelDB | 每块 CRC,坏块降级读 |
| Kafka | 副本重挂载(epoch 截断)——一致性靠副本不靠 fsync |

**判据**:不可变+寻址即校验的系统,"找回"路径完备性>修复复杂度;可变系统才需要"修复"。

### 模式 10:按可信度付费(元数据与验证的分级)

| 项目 | 实例 |
|---|---|
| FFmpeg | need_parsing 四档:MOV 可信→HEADERS,TS/裸流→FULL(demux.c:1482-1495);probe 三副面孔(魔数/遍历/统计) |
| Git | --connectivity-only 跳过 blob 校验(builtin/fsck.c:911-919);fsck 分级+--strict 提级(fsck.c:110-112) |
| K8s | Lister 读本地快照(读路径全部本地) |
| Git | 位图复用准入=base 也在复用集(pack-bitmap.c:2366-2367) |

**判据**:验证是成本不是义务——按数据来源可信度分级付费,不可信的才全款。

## 四、分歧面:同一问题的不同答案(没有标准答案,只有约束匹配)

| 问题 | 分歧 | 约束差异 |
|---|---|---|
| 并发模型 | Redis 单线程 / Nginx 多进程 / llama.cpp 线程池+图调度 / FFmpeg 调度器多线程(16 章) | 延迟确定性 vs 多核吞吐 vs 任务异构性 |
| 写路径 | SQLite WAL / Kafka 顺序段 / Git pack+delta / LevelDB LSM | 读放大 vs 写放大 vs 空间的三方取舍 |
| 一致性 | etcd 自研 raft / K8s 全押 etcd / Git 无共识(单人本地) / Kafka 自研 KRaft | 协调成本与故障域的权衡,自研 vs 复用是路线问题 |
| 错误恢复 | Git 找回优于修复 / SQLite 回滚 / Kafka 副本 / FFmpeg 降级(硬解→软解) | 数据是否可重建决定了恢复形态 |
| 配置面 | Git AVOption 伪反射(18 章) / Redis 参数+重写 / K8s 声明式 API | C 的反射是表+offset;声明式系统的反射是 API |

## 六、使用指南

1. **自研系统选型**:先查第二节模式表——你要写的机制大概率有四个先例,差异只在约束;
2. **读源码方法论**:按第三节判据逐条问"为什么在这里";按第四节分歧表定位"这个系统在哪个约束上做了非默认选择";
3. **与 PostgreSQL 系列(第四系列)的衔接**:PG 将验证模式 3(VACUUM=写时整理)、模式 5(事务 ID 反悔/冻结)、模式 10(MVCC 按快照可信度付费)在"多进程+共享内存"约束下的第四种化身。
