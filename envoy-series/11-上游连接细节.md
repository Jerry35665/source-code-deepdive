# 第 11 章 · 上游连接细节:HTTP/2 池、CONNECT 与隧道(卷二)

> 基线:tag v1.39.1。接棒卷一第 05 章(连接池统一公式);本章深入"池之上的协议语义"。

## 11.0 全景:三种容量定义

```
卷一公式 (pending+active+anticipated)×ratio > capacity+active 的协议差异
  全部压缩进 ActiveClient::currentUnusedCapacity():
  H1:恒 1(连接=流);H2:min(SETTINGS 实测, max_concurrent_streams, max_requests 余量);
  TCP:独占(0/1 两态)。池骨架(ready/busy/connecting 链表+pending 队列)不分协议。
CONNECT 是"协议分流器":CONNECT-UDP→UDP 池;CONNECT(或允许的 POST)→TCP 池;其余 HTTP 池
```

## 11.1 HTTP/2 池:容量从哪来

初始容量三取小:配置 max_concurrent_streams(safe 1024/legacy 2^31-1)、**HttpServerPropertiesCache 的 SETTINGS 实测值(只下调)**、max_requests_per_connection 余量。SETTINGS 到达后动态夹逼并迁移 Busy/Ready,实测值写回缓存供下条连接直接用;容量差值同步进 cluster 级账本。代价被注释明示:SETTINGS 前抢跑的多路流仍可能被对端 REFUSE——Envoy 为省一个 RTT 选择"先上车后补票"。流耗尽转 Draining(remaining_streams_ 归零);新连接四个触发时机(newStreamImpl 预建/onUpstreamReady/断连补偿/空池保底)。GOAWAY 半排空:有在途流转 Draining,空闲直接关——**GOAWAY 的协议含义是"别再开新流",不是"在途流作废"**。

## 11.2 CONNECT/升级:101 之后连接归谁

请求侧三个 pause 位(CONNECT/WebSocket/generic upgrade),解除统一在响应侧 CodecBridge:CONNECT 看 2xx;generic upgrade 看 101;4xx/5xx 按开关剥掉 Upgrade 头透传。**101 之后**:H1 upstream 连接"专用化"——隧道是无帧边界字节管道,物理上不可能承载第二个请求,随流终结;H2 则把 WebSocket upgrade 转成 RFC8441 extended CONNECT,仍与其他流复用同一条连接(池只看到多了一个活跃流)。tcp_proxy 的 HTTP 隧道复用同一机制(发 CONNECT/POST 验 2xx/200)。

## 11.3 内部重定向与 hedging

内部重定向:3xx 命中 internalRedirectPolicy 时 convertRequestHeadersForInternalRedirect 全套校验(跨 scheme/max 次数记 FilterState/303 转 GET 清 body/clearRouteCache),**上游流不转移**(旧 UpstreamRequest deferredDelete)——被"重建"的是下游流(recreateStream 重跑 decode 链),3xx 语义就是"对新 URI 发起新请求"。hedging:per-try 软超时不取消原 attempt,doRetry 重新 chooseHost+createConnPool——**同池或新建完全交给池的容量账本**,router 不强制新连接。pool failure→StreamResetReason 映射四级(Overflow/Remote·LocalConnectionFailure/Timeout),响应侧再映射 CoreResponseFlag。

## 11.4 upstream filter 链与 TCP 池

UpstreamRequest 装自己的 FilterManager(默认只有 upstream_codec);已双注册(downstream+upstream)的 filter:buffer/aws_request_signing/header_mutation/ext_proc/composite/credential_injector/lua/wasm。上游链定位"纯出站变换",local reply 直接穿透下游 FM;filter 可在 onHostSelected 建连前中止请求。**TCP 池独立成 Tcp::ConnPoolImpl**:无 SETTINGS 式容量协商(容量恒 0/1)、无 max_requests 断路器、自带 per-connection idle timer;特有竞态——MySQL 等协议上游先说话,Connected 时先 readDisable 压住读,数据留到关联下游后再放。

## 11.5 设计动机

1. **SETTINGS 实测优先只下调**:对端真实容量只有它自己知道;缓存实测避免超发被 REFUSE;
2. **CONNECT 后 H1 专用化**:隧道是无帧字节管道,没有"结束请求"的协议手段;H2 的 CONNECT 是流级的自然分化;
3. **内部重定向重建下游流**:3xx 的 host/scheme/协议都可能变,继续旧上游流违反语义;
4. **GOAWAY 半排空**:立即关连接会对每个流做本可避免的重试;映射到池已有的 Draining 状态;
5. **TCP 池独立**:容量语义/竞态/生命周期完全不同,强行塞进 HTTP 池只会两边变形;
6. **hedging 不捆绑新连接**:池决策归池,router 只表达"我要另一个 attempt"。

## 11.6 FAQ

**Q1:H2 上游初始并发多少?**
min(配置值[默认 1024], SETTINGS 实测缓存, max_requests 余量)。

**Q2:SETTINGS 到达前的流会被拒吗?**
可能:先上车后补票是延迟换正确性的选择(注释明示)。

**Q3:WebSocket 走 H2 上游还专用连接吗?**
不:转 RFC8441 extended CONNECT,与普通流复用。

**Q4:内部重定向转移上游连接吗?**
不:旧上游流 deferredDelete,recreateStream 重建下游流重新选路由。

**Q5:hedge 的第二 attempt 用新连接吗?**
由池容量账本决定;同 host 且池有 ready client 就复用。

**Q6:GOAWAY 后在途流会断吗?**
不会:半排空,在途流自然终结,空闲连接即时回收。

**Q7:upstream 能挂 filter 吗?**
能:默认只有 upstream_codec;buffer/lua/wasm/ext_proc 等已双注册;不支持 upgrade filter chain。

**Q8:TCP 上游为什么先压读?**
MySQL 等协议上游先说话;Connected 即 readDisable,数据留到下游关联后再放。

**Q9:连接超时的 reset 原因是什么?**
PoolFailureReason::Timeout→StreamResetReason::ConnectionTimeout。

**Q10:CONNECT-UDP 走哪个池?**
UDP 池(协议分流在 router 的 createConnPool)。
