# 第 09 章 · 可观测性:stats、tracing 与 access log(卷二)

> 基线:tag v1.39.1。三条管线都由同一 FilterManager 生命周期驱动,StreamInfo 是公共数据底座。

## 9.0 全景:三条管线

```
stats:counterFromStatName→TLS cache(命中即返回引用)→central cache(全局锁)
  →matcher 拒绝?→null_stat;Allocator 创建;inc()=裸 relaxed 原子加
  sink flush 时 latch() 取周期增量;histogram 双桶 beginMerge 免锁归并
tracing:decodeHeaders 时采样决策(request-id %10000 确定性)→startSpan
  →spawnChild(upstream)+injectContext→finalizeSpan 打标→OTel sampled 才入缓冲批量导出
access log:请求结束(或 periodic/start)→过滤链(status/duration/runtime/CEL…)
  →FormatterProvider 列表逐个求值拼行→write() 入用户态缓冲→专职 flush 线程落盘
```

## 9.1 stats:lock-free 的真相与三级查找

递增就是**裸 relaxed 原子加**(allocator.cc:150-157),v1.39 无任何 alignas/防伪共享填充;加锁只在创建/销毁统计对象与引用计数归零摘链(快路径 CAS,触零才拿锁)。`safeMakeStat` 三级查找:TLS 拒绝名单→TLS cache(全程无锁)→全局锁查 central cache+matcher 慢路径。**TLS cache 按 scope 唯一递增 ID 键控而非指针地址**——防"新 scope 复用旧地址导致缓存串号";存 reference_wrapper 把引用递减集中到 central cache,避免 scope 销毁时的锁风暴。被 matcher 拒绝的 stat 返回 null 实现——调用方无需判空。StatName 用进程级符号表把 `.` 分隔 token 互编为 uint32,查找只比较编码字节。histogram 用 circllhist 双桶:flush 合并时 beginMerge 换桶,worker 继续无锁写旧桶。纠偏:卷二基线无 LSA 模块。

## 9.2 tracing:请求级确定性采样

采样决策在 HCM mutateTracingRequestHeader,四级:client tracing(x-client-trace-id)→x-envoy-force-trace→**随机采样=request-id %10000**(确定性:同一请求多跳/重试结论一致)→总闸;route 级可覆盖比例。健康检查请求立即排除。上游无论有无子 span 都要 injectContext 写 trace 头。多 tracer 按**配置 hash 缓存共享**(TracerManagerImpl)——不同 listener 可接不同后端,配置相同则共享。OTel:sampled 才入缓冲,攒满 min_flush_spans(5)或定时器(5s)批量 OTLP 导出;自定义 Sampler 存在时本地决策被忽略。没配 tracer 全程 NullSpan 零成本。

## 9.3 access log:同步格式化+后台落盘

过滤器链:status_code/duration/runtime(采样值优先取 request-id 派生,保证同一请求多次日志判定一致)/health_check/grpc_status/metadata/CEL 表达式(and/or/not 组合)。格式串在配置期解析为 FormatterProvider 列表,每条日志逐个求值拼行——**格式化在 worker 同步发生**(要读"此刻"的 headers/StreamInfo 快照),但磁盘 IO 不阻塞:write() 只入用户态缓冲,专职 flush 线程(AccessLogFlush,惰性创建)按 64KB/10s/reopen 三条件唤醒落盘。reopen 语义就是 SIGUSR1 日志轮转的落点。真正端到端异步的是 gRPC stream logger(1s 批量)。

## 9.4 设计动机

1. **TLS 分桶**:每请求几十次原子自增必须无锁;TLS cache 把查找留在本线程,锁只在冷路径;
2. **tag 创建期正则提取**:内置 stat 名稳定、聚合维度交给配置化正则;热路径靠缓存完全绕开正则;
3. **多 tracer 按配置 hash**:zipkin+OTel 混跑、灰度迁移;生命周期随配置而非进程;
4. **采样基于 request-id**:确定性让 trace 完整性不依赖共享状态,省每请求真随机数;
5. **access log 默认同步格式化**:过滤与格式化必须读到此刻的快照;折中为"worker 拼串、IO 落后台";
6. **CEL 过滤器**:内建过滤器组合不出任意布尔逻辑;CEL 配置期编译、评估有 arena 无回溯。

## 9.5 FAQ

**Q1:counter 递增有锁吗?**
没有:裸 relaxed 原子加;latch 在 sink flush 时取周期增量并清零。

**Q2:防伪共享做了吗?**
没有:v1.39 无 alignas 填充,结构体共享 cache line 是接受的事实。

**Q3:被 matcher 拒绝的 stat 返回什么?**
null 实现(空操作),调用方无需判空;拒绝名单缓存在 TLS 层。

**Q4:histogram 怎么免锁合并?**
双桶:beginMerge 切换 active 桶,worker 写旧桶,合并线程读快照。

**Q5:采样是连接级的吗?**
不是:请求级,以 request-id %10000 确定性采样;health check 直接排除。

**Q6:一个进程能接两个 tracing 后端吗?**
能:按配置 hash 缓存 tracer,不同 listener 不同后端,配置相同共享。

**Q7:access log 写文件会阻塞 worker 吗?**
格式化会(必须同步);磁盘 IO 不会(后台 flush 线程,64KB/10s 条件)。

**Q8:日志轮转(SIGUSR1)怎么生效?**
reopen 广播:各文件置 reopen 标志,flush 线程 close+重开,失败计 reopen_failed。

**Q9:CEL 过滤器失败算匹配吗?**
不:求值出错按 false 处理(放行日志)。

**Q10:%TRACE_ID% 怎么拿到的?**
HCM 打日志时把 active_span 塞进 Formatter::Context——access log 与 tracing 在此交汇。

## 9.6 小结与深挖方向

本章结论:**可观测性="三级 stat 查找+确定性采样+同步格式化异步落盘,StreamInfo 是公共底座"**。深挖:

1. SymbolTable 互编与 StatNameList 单次打包分配;
2. evictUnused 对 evictable scope 的两周期清理;
3. OTel 自定义 Sampler 与本地决策的关系;
4. gRPC access logger 的 StreamAccessLogsMessage 批量;
5. per-host 指标绕过 ThreadLocalStore 的 primitive snapshot 路径。
