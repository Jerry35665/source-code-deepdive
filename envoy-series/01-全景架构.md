# 第 01 章 · 全景架构:main 线程 + N worker 的单进程模型

> 基线:tag v1.39.1(commit `b579d07d`)。行号以仓库根相对路径为准。

## 1.0 全景:对象层次与线程视角

```
envoy 进程(--concurrency = N)
├ main 线程:MainCommon(main_common.cc:158)→ InstanceBase::initialize(server.cc:464-890)
│   ├ ThreadLocal::InstanceImpl + Stats::ThreadLocalStoreImpl(最早创建,stripped_main_base.cc:68-69)
│   ├ ListenerManager(worker ×N)/ ClusterManager / XdsManager / OverloadManager / Admin
└ worker ×N(worker_impl.cc:49-70 构造一次注册齐)
    ├ 独立 libevent dispatcher(event_base_new,libevent_scheduler.cc:26-32)
    ├ tls_.registerThread(*dispatcher_, false)
    └ ConnectionHandler(accept + 连接生命周期)
数据面请求不经过 main 线程;main 只管配置(xDS 订阅)、统计聚合、生命周期
```

README 自述 "cloud-native high-performance edge/middle/service proxy"(README.md:3),并直接给出线程模型/hot restart/stats/UDPA 四篇设计博客索引(README.md:20-23)。与 Nginx/Caddy 的本质差异:Envoy 是给控制面(Mesh)编程的数据面,不是给运维改配置文件的 Web 服务器。

## 1.1 启动链:bootstrap→primary→RTDS→secondary

`main()` 只做一层转发(main.cc:24);真正的主流程在 `InstanceBase::initializeOrThrow`(server.cc:464-890)。官方注释给出总顺序(server.cc:757-770):**①加载 bootstrap 静态配置 → ②ClusterManager 与 primary 集群 → ③各类 bootstrap 级服务 → ④RTDS 用 primary 集群建连 → ⑤secondary 集群(EDS)→ ⑥其余动态配置**。关键步骤:AdminImpl 创建(:653-663)、OverloadManager 刻意早于一切(:673 注释)、ListenerManager 先于 ClusterManager 创建(:737 注释"先注册 thread local 更新")、GuardDog 必须先于 worker 启动(:881 注释)。`config_.initialize` 装载静态资源(configuration_impl.cc:112-159),两阶段集群初始化在 cluster_manager_impl.cc:365-428。

退出路径 `terminate()` 与初始化镜像(thread_local→stats→xDS mux→workers→CM,server.cc:1097-1143)。`MainCommonBase::run()` 同一套 exe 支撑 Serve/Validate/InitOnly 三模式(main_common.cc:80-105)。

## 1.2 线程模型与连接固定

worker 数 = `--concurrency`,一次建齐(listener_manager_impl.cc:429-431),线程名 `wrk:`(worker_impl.cc:126)。监听 socket 默认 NoReusePort——**所有 worker 共享一个 dup 出来的 fd**,内核在共享队列上分散唤醒;配 `reuse_port` 则每 worker 独立 bind(listener_manager.h:102-109)。连接一经某 worker accept,整个生命周期(含 upstream 连接池)固定在该线程,数据面无跨线程锁。`WorkerImpl::threadRoutine` 就是 `dispatcher_->run(Block)`,退出时先在 worker 线程内析构 handler 再 `tls_.shutdownThread()`(worker_impl.cc:168-192)。

## 1.3 ThreadLocal slot:无锁化的基石

`allocateSlot()` 只允许 main 线程调用,slot 即全局下标(thread_local_impl.cc:28-41);`SlotImpl::set` 对每个注册线程 `dispatcher.post`,**数据永远由所属线程自己写**(124-136),读自然无锁;`runOnAllThreads` 支持带完成回调的引用计数版本(191-209);关停时各线程按**逆序**析构 slot——过滤器先于 cluster manager 等底座销毁(225-256 注释)。ClusterManager/Runtime/OverloadManager/stats store 全部经 slot 下发。

## 1.4 设计动机

1. **单进程多线程而非多进程**:连接固定 worker+共享堆让路由表只存一份、统计天然聚合;升级的"不断流"由 hot restart 进程接力补齐(06 章);
2. **ThreadLocal 替代锁**:配置读多写少,main 单点写+各线程私有副本=零锁读;
3. **所有 IO 收敛一个 event loop**:一个连接只被一个线程触碰;GuardDog 只需盯 loop 心跳即可发现死锁;
4. **扩展以 filter 为中心**:listener filter→L4 filter→HCM→L7 filter 统一管线,router/tcp_proxy 皆是 filter;
5. **Bootstrap 与 xDS 分离**:解决"先有 cluster 才能连管理服务器"的自举问题。

## 1.5 FAQ

**Q1:worker 数怎么定?**
`--concurrency`;可通过 `enable_worker_cpu_affinity` 绑核(listener_manager_impl.cc:1106-1119)。

**Q2:数据面有锁吗?**
稳态无锁:连接固定 worker+TLS 私有副本;配置更新是 main 单点写经 post 广播。

**Q3:Admin 端口转发流量吗?**
不:Admin listener 只挂 main 线程 handler(server.cc:810),与 worker 互不相干。

**Q4:改配置要重启吗?**
不要:LDS/CDS/RDS 热更新;只有换二进制才 hot restart。

**Q5:启动第一步做什么?**
加载 bootstrap(server.cc:481),再按 primary→RTDS→secondary 拓扑推进。

**Q6:进程怎么优雅退出?**
terminate() 按初始化镜像顺序拆除(server.cc:1097-1143);SIGHUP 被吞因为热重启不走信号。

**Q7:扩展怎么裁剪?**
extensions_build_config.bzl 按站点裁剪编译;启动日志打印全部静态链接扩展(server.cc:469-472)。

**Q8:main 线程挂了 worker 还活吗?**
活:worker 是独立线程;但 main 负责配置与统计,GuardDog 会监控 main 自身心跳。

**Q9:Init::Manager 是什么?**
两阶段初始化的粘合剂:listener/RDS 等异步组件注册 Init::Target,完成后回调 startWorkers(server.cc:1055-1074)。

**Q10:测试怎么组织?**
单测目录镜像 source/、集成测试 test/integration、mock 全量在 test/mocks;统一 `bazel test`(bazel/README.md:400)。

## 1.6 小结与深挖方向

本章结论:**Envoy 骨架="main 管配置、worker 管数据、TLS 广播当锁用、启动顺序即依赖拓扑"**。深挖:

1. SIGUSR1 重开访问日志与 SIGHUP 吞掉的理由(server.cc:1005-1024);
2. ScaledTimer(按流数缩放的超时)实现与 HttpDownstreamIdleStreamTimeout;
3. validate 模式用 HotRestartNopImpl 的完整路径(stripped_main_base.cc:72);
4. `--disable-extensions` 与 core dump 的启动期处理(stripped_main_base.cc:52-62);
5. LifecycleNotifier 各 Stage 的语义与 ShutdownExit 优雅排空。
