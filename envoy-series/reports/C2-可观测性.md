# C2 · 可观测性:stats、tracing 与 access log 的实现

> 基线:envoy v1.39.1(commit b579d07d)。本文聚焦实现细节;sink 挂载与 ThreadLocalStore 的整体角色已在卷一讲过。
> 所有 `文件:行号` 均以仓库根为相对路径,并经实际读码核对。

## 0. 总览:三条管线

```
【stats:一次 counter->inc() 的旅程】
 worker 线程                          main 线程
    |  counterFromStatName()             |
    v                                    |
 TLS cache 命中? --命中--> Counter& ------+-> c.inc(): value_/pending_increment_ 原子加
    | 未命中(TLS 层)                          (无锁, allocator.cc:150-157)
    v                                    |
 central cache(全局锁 lock_)              |      定时 flush(如 admin/hystrix/sink)
    | 未命中 -> matcher 拒绝? -> null_stat |<-----------+-----------+
    | -> Allocator::makeCounter(allocator.cc:297-314, 独立 mutex_)
    | -> 写回 TLS cache(thread_local_store.cc:597-601)
                                         |
         ParentHistogram.merge():遍历各线程 ThreadLocalHistogram,beginMerge() 换桶后
         hist_accumulate 到 interval/cumulative(thread_local_store.cc:272-291, 1065-1075)

【tracing:一个 span 的一生】
 decodeHeaders -> mutateTracingRequestHeader() 采样决策(conn_manager_utility.cc:390-447)
   -> traceRequest(): shouldTraceRequest() 复核 -> Tracer::startSpan -> Driver::startSpan
   -> annotate: setTag / log(verbose 时序) / setOperation
 upstream 阶段: spawnChild("router <cluster> egress") + injectContext 写入上游请求头
   (upstream_request.cc:115-125, 137-154)
 响应结束 -> finalizeSpan():打 component/response_flags/cluster 等标 -> span.finishSpan()
   -> OTel driver: 若 sampled 则入 span_buffer_,按 min_flush_spans/定时器批量 OTLP 导出

【access log:匹配/输出管线】
 请求结束(或 periodic/start) -> ActiveStream::log(conn_manager_impl.cc:1022-1032)
   -> 逐个 Instance: ImplBase::log 先跑 Filter::evaluate
        (status_code/duration/runtime/health_check/grpc_status/metadata/CEL, and/or/not 组合)
   -> 通过后 emitLog():FormatterImpl::format() 把预编译好的 FormatterProvider 列表
        逐个 format(context, stream_info) 拼成一行
   -> FileAccessLog::emitLog -> log_file_->write():写入用户态 flush_buffer_
   -> 专职 flush 线程被 min_flush_size_/timer/reopen 条件变量唤醒,doWrite() 落盘
```

## 1. stats

### 1.1 lock-free 递增:裸原子,无对齐填充

计数器在 `Allocator` 内定义(注意:不是接口头文件,而是 allocator.cc):

```cpp
// source/common/stats/allocator.cc:137-165(节选)
class CounterImpl : public StatsSharedImpl<Counter> {
  void add(uint64_t amount) override {
    // Note that a reader may see a new value but an old pending_increment_ or
    // used(). From a system perspective this should be eventually consistent.
    value_ += amount;
    pending_increment_ += amount;
    flags_ |= Flags::Used;
  }
  void inc() override { add(1); }
  uint64_t latch() override { return pending_increment_.exchange(0); }
private:
  std::atomic<uint64_t> value_{0};
  std::atomic<uint64_t> pending_increment_{0};
};
```

递增就是 relaxed 原子加(allocator.cc:150-157、163-164),`latch()` 在 sink flush 时取回"本周期增量"并清零——这是 Envoy 对 counter 的"合并":每周期只向 sink 报增量。注意 `add()` 里那句注释:读方可能看到新 value 配旧 pending_increment_,Envoy 接受这种最终一致(allocator.cc:151-153)。

gauge 则是双字段模型:`value() = child_value_ + parent_value_`(allocator.cc:214)。worker 侧改 `child_value_`,热重启归并时主进程写入 `parent_value_`;`ImportMode`(Accumulate/NeverImport/HiddenAccumulate)决定跨重启是否累加,以 flags 位存储(allocator.cc:172-190、216-259)。text_readout 用 `absl::Mutex` + string 拷贝实现 get/set,是四类 metric 中唯一有锁的值操作(allocator.cc:280-295)。**v1.39.1 中没有任何 `alignas`/cache-line padding**(全 `source/common/stats/` 目录 grep `alignas` 零命中),防伪共享并未在这里做,结构体成员共享 cache line 是接受的事实。真正的加锁点只有两个:创建/销毁统计对象(`Allocator::makeCounter` 的 `mutex_`,allocator.cc:297-314)与引用计数归零时的摘链(`decRefCount` 慢路径,allocator.cc:93-110)。

引用计数本身也做了 lock-free 优化:非归零递减走 CAS 快路径 `tryDecRefCountFastPath`,只有可能触零的递减才拿 `alloc_.mutex_` 以便原子地从集合摘除(allocator.cc:94-109、122-132)。

### 1.2 ThreadLocalStoreImpl:TLS cache + central cache 两级

`safeMakeStat()` 是所有 stat 获取的汇合点(thread_local_store.cc:536-605),查找顺序:

1. TLS 层"已拒绝名单"命中 → 返回 null_stat(543-546);
2. TLS cache 命中 → 直接返回引用,**全程无锁**(549-554);
3. 加全局 `lock_` 查 central cache;未命中则跑 matcher 慢路径、检查 scope 配额(`max_counters/max_gauges`,超出则 `*_overflow_` 计数并返回 null,569-587),最后 `Allocator::make*` 创建并写回两级缓存(590-601)。

TLS cache 按 **scope 唯一递增 ID** 键控而非指针地址,防止"新 scope 复用旧地址导致缓存串号"——注释明确说这是 fast path 无锁的必要复杂度(thread_local_store.h:544-560、490-491;scope ID 在 ScopeImpl 构造时分配,thread_local_store.cc:437-444)。TLS cache 存 `reference_wrapper` 而非 shared_ptr,把引用计数递减集中到 central cache,避免 scope 销毁时的锁风暴(thread_local_store.h:247-256)。scope 删除时通过 `runOnAllThreads` 批量清理并合并 post(thread_local_store.h:666-677)。

```cpp
// source/common/stats/thread_local_store.cc:556-601(节选)
// We must now look in the central store so we must be locked. ...
Thread::LockGuard lock(parent_.lock_);
auto iter = central_cache_map.find(full_stat_name);
RefcountPtr<StatType>* central_ref = nullptr;
if (iter != central_cache_map.end()) {
  central_ref = &(iter->second);
} else if (parent_.checkAndRememberRejection(
               full_stat_name, fast_reject_result, central_rejected_stats,
               tls_rejected_stats, effectiveMatcher())) {
  return null_stat;
} else { /* 创建并写回 central cache */ }
// If we have a TLS cache, insert the stat.
StatType& ret = **central_ref;
if (tls_cache) { tls_cache->insert({ret.statName(), std::reference_wrapper<StatType>(ret)}); }
```

被 matcher 拒绝的 stat 返回 `null_counter_/null_gauge_` 等 Null 实现(创建、递增皆空操作,thread_local_store.h:173-174、639-642),调用方拿到的引用永远可用,无需判空——这是"引用稳定性"与"拒绝"并存的关键。

### 1.2.1 StatName:互编符号表是快路径的地基

stat 名与 tag 值不存 C++ string,而是在进程级 `SymbolTable` 里把 `.` 分隔的 token 互编为 uint32 符号,再打包成变长字节数组 `StatName`(symbol_table.h:37-41、49-84);encode 与 free 都必须持全局锁(symbol_table.h:443-446),但只在创建期发生;之后 TLS 命中的查找只比较编码后的字节,无需加锁、无需构造字符串(symbol_table.h:90-92 的注释)。MetriImpl 的 tags 与 tag_extracted_name 打进同一块连续内存(symbol_table.h:94-102),单个 stat 的元数据因此非常紧凑。

### 1.3 tag 提取:创建期一次,正则驱动

tag 从 stat 名里"运行期正则提取",但只发生在**创建期**、且每 stat 一次:命中 TLS/central 缓存后不再触碰正则。`StatNameTagHelper` 在 stat 未命中缓存时调用 `tagProducer().produceTags()`(thread_local_store.cc:471-495);新式 `TagScopeImpl` 则把 scope 级 tag 随名字直接带上,连提取都省了(thread_local_store.h:508-542)。提取器按配置生成,RE2 或 std::regex 二选一:

```cpp
// source/common/stats/tag_extractor_impl.cc:70-86(节选)
TagExtractorImplBase::createTagExtractor(absl::string_view name, absl::string_view regex, ...) {
  if (regex.empty()) { throw EnvoyException(... "No regex specified for tag specifier ..."); }
  if (use_default_regex || !substr.empty()) {
    return std::make_unique<TagExtractorRe2Impl>(name, regex, substr, negative_match);
  }
  return std::make_unique<TagExtractorStdRegexImpl>(name, regex, substr);
}
```

`TagProducerImpl` 会把带字面前缀的 tag specifier 按 prefix 建索引,提取时只跑前缀匹配的子集(tag_producer_impl.h:109-122)。提取出的 tag 与"去 tag 名"(tag_extracted_name)都经 SymbolTable 互编为 StatName 存储;同一批 tag 打包进单次连续分配(symbol_table.h:94-102)。

### 1.4 scope 语义:前缀拼接 + 命名空间

```cpp
// source/common/stats/thread_local_store.cc:189-207(节选)
ScopeSharedPtr ThreadLocalStoreImpl::ScopeImpl::scopeFromTaggedName(...) {
  ...
  SymbolTable::StoragePtr joined = symbolTable().join({prefix_.statName(), base_name});
  // Use explicit matcher if provided; otherwise inherit scope_matcher_ ...
  StatsMatcherSharedPtr child_matcher = matcher ? std::move(matcher) : scope_matcher_;
  auto new_scope = std::make_shared<ScopeImpl>(parent_, StatName(joined.get()), evictable, ...);
  parent_.addScope(new_scope);
  return new_scope;
}
```

`scopeFromStatName` 把子 scope 名与父前缀在 SymbolTable 里 join 成新前缀,子 scope 继承父的 matcher(未显式指定时)(thread_local_store.cc:189-207)。store 仅以 weak_ptr 登记所有 scope(thread_local_store.cc:209-212,thread_local_store.h:628),scope 生命周期完全归调用方。典型分工:Listener/Cluster/线程等各自 `createScope("cluster.foo.")`,同名 stat 在不同 scope 下是不同对象;两个同名 scope 则指向同一 backing stat(重叠 scope 去重,`gauges()`/`counters()` 返回前按名去重,thread_local_store.cc:214-216;`source/docs/stats.md`)。默认 scope 为 root;开启 `use_tag_scope` 后 root 是 `TagScopeImpl`,支持携带 scope 级 tag(thread_local_store.h:649-650,508-542)。scope 还可携带 `ScopeStatsLimitSettings`(per-scope max_counters/max_gauges/max_histograms),超限时递增 `stats.overflow.*` 并返回 null 实现(thread_local_store.cc:569-587、803-807)。

### 1.5 histogram 与 summary 的分桶

histogram 用 circllhist(对数-线性混合分桶),每 stat 两层:main 线程 `ParentHistogramImpl` + 每线程 `ThreadLocalHistogramImpl`(双桶缓冲,`beginMerge()` 时切换 active 桶,免锁采集,thread_local_store.h:32-77)。TLS 侧 `recordValue` 就是 `hist_insert_intscale` 一次(thread_local_store.cc:1065-1069);合并时 flush 流程先广播 `beginMerge()`,再在 main 线程 `hist_accumulate` 到 interval/cumulative(thread_local_store.cc:272-291、1071-1075)。对外可配置:按 stat 名匹配的自定义 buckets 或固定 bins 数,在创建 ParentHistogram 时解析一次(thread_local_store.cc:791-794,histogram_impl.h:20-39);Prometheus summary 渲染用的"漂亮分桶"是内置缺省表(histogram_impl.cc:138-142)。`deliverHistogramToSinks` 则把 timer/histogram 值推给注册的 sink(如 dog_statsd)(thread_local_store.cc:655-668)。

### 1.6 stats matcher:省内存的三道闸

`StatsMatcherImpl` 支持 reject_all / inclusion_list / exclusion_list(stats_matcher_impl.cc:23-35)。检查分"快慢两段":快段是 O(1) 判定(accepts_all/rejects_all,`fastRejects`,stats_matcher_impl.cc:72-90),慢段才是逐条 matcher 匹配;被拒绝的名字连同 TLS 层拒绝名单一起缓存,之后同名的创建请求直接在无锁 TLS 层返回 null(thread_local_store.h:270-276,thread_local_store.cc:506-533)。此外还有 scope 级配额(1.2 节的 `*_overflow_`)与 `evictUnused()`:对 evictable scope 双向清理 central/TLS 缓存中两周期未用的 stat,gauges 须为 0 才可逐出(thread_local_store.cc:1319-1411)。

### 1.7 热路径成本与 lsa

一次 HTTP 请求的 stats 操作量级:HCM 每 stream 一条 Timespan(`downstream_rq_time_` 直写 TLS histogram,conn_manager_impl.cc:913)+ 十几次 counter 原子自增(如 `downstream_rq_total_` conn_manager_impl.cc:958、`downstream_cx_total_` conn_manager_impl.cc:185、virtual cluster/route 的 `upstream_rq_total_` router.cc:1734-1740),外加 cluster/listener 级若干。所有这些都落在 TLS 命中后的纯原子加路径;需要"合并"的是:sink flush 时的 counter latch(1.1)、跨线程 histogram 归并(1.5)、以及 gauge 的 hot-restart `StatMerger` 归并(stat_merger.h:17-79)。关于 **lsa(线性内存分配器)**:v1.39.1 源码树中并无名为 LSA 的模块(全仓库检索无命中),stat 名字内存由 SymbolTable 的加锁 encode/free 管理(symbol_table.h:443-446),近似"线性分配"的只有 StatNameList/MetricImpl 的单次打包连续分配(symbol_table.h:94-102);卷二按下不表,读者若在新版本看到 LSA,应视作这一层的后续演进。

## 2. tracing

### 2.1 抽象:Tracer → Driver → Span

`Tracing::Tracer` 只有一个方法 `startSpan`(envoy/tracing/tracer.h:17-24);`TracerImpl` 持有具体 `Driver`(如 Zipkin/OTel)并补打 node/zone 标(tracer_impl.cc:137-153)。`Span` 接口定义生命周期原语(envoy/tracing/trace_driver.h:69-141):

```cpp
// envoy/tracing/trace_driver.h:61-141(节选)
class Span {
public:
  virtual void setOperation(absl::string_view operation) PURE;              // :69
  virtual void setTag(absl::string_view name, absl::string_view value) PURE; // :76
  virtual void log(SystemTime timestamp, const std::string& event) PURE;    // :83
  virtual void finishSpan() PURE;                                           // :89
  virtual void injectContext(TraceContext&, const UpstreamContext&) PURE;   // :97
  virtual SpanPtr spawnChild(const Config&, const std::string&, SystemTime) PURE; // :105
  virtual void setSampled(bool sampled) PURE;                               // :114
  virtual bool exportedSpan() const PURE;                                   // :124
  virtual bool useLocalDecision() const PURE;                               // :141
  ...
};
```

没配 tracer 时全程 NullSpan(单例、全空操作,null_span_impl.h:13-25),零成本。

### 2.2 生命周期与 finalize

HCM 在 decodeHeaders 阶段 `traceRequest()` 起 span:先 `shouldTraceRequest()` 复核(conn_manager_impl.cc:1610-1637):

```cpp
// source/common/tracing/tracer_impl.cc:70-85(节选)
Decision TracerUtility::shouldTraceRequest(const StreamInfo::StreamInfo& stream_info) {
  // Exclude health check requests immediately.
  if (stream_info.healthCheck()) { return {Reason::HealthCheck, false}; }
  const Tracing::Reason trace_reason = stream_info.traceReason();
  switch (trace_reason) {
  case Reason::ClientForced:
  case Reason::ServiceForced:
  case Reason::Sampling:
    return {trace_reason, true};
  default:
    return {trace_reason, false};
  }
}
```

失败原因计入 `tracing_stats`(client_enabled_/random_sampling_/service_forced_/not_traceable_,conn_manager_impl.cc:855-870)。上游侧由 router 视 `spawnUpstreamSpan()`/`start_child_span` 决定是否 `spawnChild`,然后**无论有无子 span**都要 `injectContext` 把 trace 上下文写进上游请求头(可被 `noContextPropagation` 关闭)(upstream_request.cc:115-154)。请求终结时 `finalizeSpan()` 统一打标(component=proxy、response_flags、upstream cluster/observability_name/address、verbose 时序 log、gRPC status error 判定见 http_tracer_impl.cc:69-121、228-235),最后 `modifySpan` 回调(自定义 tag 注入点,conn_manager_impl.cc:2226-2241)与 `finishSpan()`(tracer_impl.cc:87-135,finish 在 :126)。

### 2.3 采样决策:每请求,基于 request-id

决策点在 HCM 的 `mutateTracingRequestHeader()`,逐请求执行(conn_manager_utility.cc:390-447):client tracing(x-client-trace-id + `tracing.client_enabled`)→ `x-envoy-force-trace` → 随机采样(request-id 整数 % 10000 作确定性随机源 + `tracing.random_sampling`)→ 总闸 `tracing.global_enabled`;route 级可覆盖三个比例(416-421)。注意这是**请求级**采样:没有"连接级"开关;确定性来自 request-id,同 id 的重试/跨 hop 结论一致。路由刷新后决策会被重算一次(conn_manager_impl.cc:1850-1856),span 是否接受本地决策由 driver 决定(`useLocalDecision`,trace_driver.h:141-152)。

### 2.4 多 tracer 共存

`TracerManagerImpl`(单例)按 **tracing 配置的 hash** 缓存 tracer(weak_ptr,过期懒清理),不同 HCM/listener 配不同 tracer 即自动各建各的,配置相同则共享(tracer_manager_impl.h:26-40,tracer_manager_impl.cc:14-26)。因此"每个 listener 独立 tracer、全局共享同一配置的 tracer"是设计内行为;不存在名为 dynamic forwarder 的机制。

### 2.5 OpenTelemetry tracer 的导出路径

OTel 扩展的 span 是本地的 `opentelemetry::proto` Span;`finishSpan()` 打时间戳,**sampled 才入队**(opentelemetry/tracer.cc:86-93);入队超 `max_cache_size` 丢 span 并立即冲刷,攒满 `min_flush_spans`(默认 5)或 flush timer(默认 5000ms,runtime 可调)时组装 `ExportTraceServiceRequest`(ResourceSpans→ScopeSpans,scope 名 "envoy")经 gRPC `exporter_->log()` 发出(tracer.cc:216-227、230-289)。自定义 Sampler 存在时 Envoy 本地决策被忽略,改由 sampler 决定 sampled(tracer.cc:290-315)。

## 3. access log

### 3.1 Instance 与过滤器链

接口只有 `Filter::evaluate` 与 `Instance::log`(envoy/access_log/access_log.h:66-91)。通用实现 `Common::ImplBase::log` 先过过滤器再 `emitLog`(access_loggers/common/access_log_base.cc:11-20)。内建过滤器由 `FilterFactory::fromProto` 按类型构造(access_log_impl.cc:60-84):status_code/duration(比较器,支持 runtime 折叠)、runtime(按 request-id 或独立随机数采样)、health_check/not_health_check、grpc_status、metadata(matcher)、and/or/not 组合。以 runtime 过滤器为例,采样值优先取 request-id 派生,保证同一请求在 start/complete/periodic 多次日志判定一致:

```cpp
// source/common/access_log/access_log_impl.cc:135-156(节选)
bool RuntimeFilter::evaluate(const Formatter::Context&,
                             const StreamInfo::StreamInfo& stream_info) const {
  uint64_t random_value;
  if (use_independent_randomness_) {
    random_value = random_.random();
  } else if (stream_info.getStreamIdProvider().has_value() &&
             stream_info.getStreamIdProvider()->toInteger().has_value()) {
    random_value = stream_info.getStreamIdProvider()->toInteger().value() %
        ProtobufPercentHelper::fractionalPercentDenominatorToInt(percent_.denominator());
  } else {
    random_value = random_.random();
  }
  return runtime_.snapshot().featureEnabled(runtime_key_, percent_.numerator(), random_value, ...);
}
```

扩展过滤器是 CEL(3.4):表达式在配置期编译为 `CompiledExpression`,运行期仅求值,出错按 false 处理(access_loggers/filters/cel/cel.cc:25-46;filters/common/expr/evaluator.h:140-168)。

### 3.2 格式化:format string 编译为 provider 列表

是的,编译为"Op 抽象"——`FormatterProvider` 列表:`SubstitutionFormatParser::parse` 把 `%...%` 命令与字面量解析成有序 providers(substitution_formatter.h:71-76),`FormatterImpl::format` 每条日志逐 provider 求值拼接(substitution_formatter.h:82-107);JSON/typed_json 走 `JsonFormatterImpl`(预解析的 key→providers 结构,substitution_formatter.h:91-130)。文件 logger 支持纯文本/json/typed_json/log_format 四种配置形态,缺省用默认格式(access_loggers/file/config.cc:27-87)。

### 3.3 文件 sink:write() 只是入 buffer

```cpp
// source/common/access_log/access_log_manager_impl.cc:213-226(节选)
void AccessLogFileImpl::write(absl::string_view data) {
  Thread::LockGuard lock(write_lock_);
  if (flush_thread_ == nullptr) { createFlushStructures(); }   // 惰性起 flush 线程
  stats_.write_buffered_.inc();
  flush_buffer_.add(data.data(), data.size());
  if (flush_buffer_.length() > min_flush_size_) { flush_event_.notifyOne(); }
}
```

每个文件一个专职 flush 线程("AccessLogFlush",惰性创建于首次 write,access_log_manager_impl.cc:228-231),在 `flush_buffer_ 超过 min_flush_size(默认 64KB,access_log_manager_impl.h:54)/定时器(默认 10s,--file-flush-interval-msec,options_impl.cc:143-146)/reopen/退出` 四种事件下醒来,把 buffer 搬运到 `about_to_write_buffer_` 后在锁外写盘(access_log_manager_impl.cc:133-187、104-131)。**reopen 语义**:管理器对全部文件广播,各文件置 `reopen_file_=true` 并唤醒 flush 线程,由它 close+重开,失败计 `reopen_failed`(access_log_manager_impl.cc:30-34、76-80、171-183)——这正是 `SIGUSR1`(log rotate)的落点。`flush()` 同步排空,供测试/关闭用(189-211)。同一磁盘文件被多个 `AccessLogFileImpl` 打开时靠跨进程锁串行写(104-114)。

### 3.4 异步现状

HCM 的触发点:请求起始(可选 `flushAccessLogOnNewRequest`)、请求完成(`completeRequest` 路径)、以及可选的周期性 mid-flight 日志(`access_log_flush_interval`,类型 DownstreamPeriodic)(conn_manager_impl.cc:999-1019、1571-1572)。触发时构造 `Formatter::Context`(请求/响应头、trailers、trace span、log type)并逐个调用 Instance(conn_manager_impl.cc:1022-1032):

```cpp
// source/common/http/conn_manager_impl.cc:1022-1032(节选)
void ConnectionManagerImpl::ActiveStream::log(AccessLog::AccessLogType type) {
  const Formatter::Context log_context{
      request_headers_.get(), response_headers_.get(), response_trailers_.get(), {}, type,
      active_span_.get()};
  filter_manager_.log(log_context);
  for (const auto& access_logger : connection_manager_.config_->accessLogs()) {
    access_logger->log(log_context, filter_manager_.streamInfo());
  }
}
```

默认文件路径是"同步格式化 + 用户态缓冲 + 后台线程落盘":格式化在 worker 线程同步发生,但磁盘 IO 不阻塞 worker。真正端到端异步/批量的是 gRPC stream logger(`envoy.access_loggers.http_grpc`/`tcp_grpc`):条目先 `Add` 进共享的 `StreamAccessLogsMessage`(http/tcp 条目互斥,grpc/grpc_access_log_impl.cc:33-54),按 `buffer_flush_interval`(默认 1000ms)定时冲刷(access_loggers/common/grpc_access_logger.h:112-119、223-224)。

## 4. 三者联动:StreamInfo 是公共数据底座

一条 stream 的 `StreamInfo` 同时供三方消费:tracing 采样与健康检查判定(`traceReason()` stream_info.h:1044、`healthCheck()` 经 `shouldTraceRequest`)、span finalize 的标签来源(response flags/上下游地址/时序,tracer_impl.cc:87-135)、access log 的过滤与格式化上下文(response code、duration、metadata、filter state)。HCM 打日志时把请求/响应头、trailers、**active_span** 一并塞进 `Formatter::Context`(conn_manager_impl.cc:1022-1027),于是 `%TRACE_ID%` 之类格式化命令与 CEL 过滤器都能摸到 trace 上下文——access log 与 tracing 在此交汇。stats 不读 StreamInfo,但三者都由同一 `FilterManager` 生命周期驱动,共享 `timeSource` 保证时序一致。

## 5. admin 视角:/stats/prometheus(衔接卷一)

admin 在启动时注册 `/stats/prometheus`(source/server/admin/admin.cc:239),处理链 `StatsHandler::prometheusStats → prometheusFlushAndRender → prometheusRender`(stats_handler.cc:149-176):沿卷一讲过的 `forEach*` 迭代把 counters/gauges 按标签 sanitize 成 Prometheus 文本,histogram 按 `tagExtractedName` 分组聚合并查表渲染成 summary 分桶(prometheus_stats.cc:33-53、751-775)。挂载方式(sink 的定时 flush)与本文 1.5 的分桶在此对上。

## 6. 设计动机

1. **为什么 TLS 分桶 stats**:worker 线程每请求几十次原子自增必须无锁、无跨核 cache line 争用;TLS cache 把"查找+返回引用"留在本线程,central cache 与 allocator 锁只在冷路径(创建/销毁)出现(thread_local_store.cc:536-605,allocator.cc:93-110)。
2. **为什么 tag 运行期(创建期)正则提取**:让二进制内置 stat 名保持稳定、聚合维度交给配置化正则,运维加 tag 不改代码;代价只付在创建期一次,热路径靠缓存与 tag-aware scope 完全绕开正则(thread_local_store.cc:471-495,thread_local_store.h:508-542)。
3. **为什么 span 支持多 tracer(按配置 hash 缓存)**:一个进程多个 listener 可接不同后端(zipkin+OTel 混跑、灰度迁移),共享同一份采样决策与 StreamInfo,tracer 的生命周期随配置而非进程(tracer_manager_impl.cc:14-26)。
4. **为什么采样基于 request-id、请求级**:确定性的 `%10000` 让同一请求在多跳/重试间采样结论一致,trace 完整性不依赖共享状态;同时省掉每请求真随机数与跨线程协商(conn_manager_utility.cc:402-444)。
5. **为什么 access log 默认同步(格式化)而非异步**:过滤器和格式化必须读到"此刻"的 headers/trailers/StreamInfo 快照,异步化要么复制要么失效;Envoy 折中为"worker 同步拼串、IO 落后台线程",把最贵的磁盘等待移出热路径,内存上限由 min_flush_size 控制(access_log_manager_impl.cc:104-131、213-226)。
6. **为什么 CEL/表达式过滤器**:runtime/状态码等内建过滤器组合不出"header+metadata+filter state 的任意布尔逻辑";CEL 在配置期编译成表达式树,评估有 arena、无正则回溯,同时保持了与 tracing/日志一致的 StreamInfo 视图(cel.cc:29-46,evaluator.h:140-168)。
7. **为什么 histogram 双桶(beginMerge)**:flush 合并可能耗时长,交换 active 桶后 worker 继续无锁写入旧桶,合并线程读的是快照,采集与归并互不阻塞(thread_local_store.h:49-53)。
