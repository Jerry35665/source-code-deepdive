for (const UrlHandler& handler : handlers_) {

      const absl::string_view method = admin_stream.getRequestHeaders().getMethodValue();
      if (method != Http::Headers::get().MethodValues.Post) {

## 1. /config_dump:ConfigTracker 的"注册-回调"组装

`/config_dump` 不持有任何配置:它只遍历 `ConfigTracker` 里的回调表。`ConfigTracker`
文档自述其语义——弱所有权,RAI 注销,键即资源描述符(`envoy/server/config_tracker.h:15-23`);
实现是 `map<string, Cb>` + `EntryOwnerImpl` 析构时 `map_->erase(key_)`
(`source/server/admin/config_tracker_impl.cc:6-22`)。各组件在构造时持住 EntryOwner:

- `"clusters"`:ClusterManagerImpl 构造函数,`source/common/upstream/cluster_manager_impl.cc:335-341`;
- `"listeners"`:ListenerManagerImpl 构造函数,`source/common/listener_manager/listener_manager_impl.cc:422-427`;
- `"routes"`:RouteConfigProviderManager(键名可参数化),`source/common/rds/route_config_provider_manager.cc:14-22`;
- `"secrets"`:SecretManagerImpl 构造,`source/common/secret/secret_manager_impl.cc:20-25`;
- 另有 `"bootstrap"`:server 启动时注册,`source/server/server.cc:806-809`。

组装流程(`source/server/admin/config_dump_handler.cc:152-187`):取 `callbacks_map`,
逐个调用回调得到消息,`PackFrom` 进 `ConfigDump.configs`,最后 `MessageUtil::redact(dump)`
抹掉敏感字段(182 行),以 pretty-print JSON 返回(184-185 行)——注意 config_dump 只有
JSON 一种形态,prometheus 化只发生在 stats。参数有四个:.resource / ?mask / ?name_regex /
?include_eds(注册处 `admin.cc:138-148`,解析处 `config_dump_handler.cc:156-160`):

- `?resource=clusters` 等按 repeated 字段名过滤;非 repeated 字段直接报 400 并提示改用
  mask(210-217 行);
- `?mask=` 是 protobuf FieldMask。难点是 ConfigDump 资源把内容包在 `google.protobuf.Any`
  里,内建 FieldMask 无法穿透 Any,于是 `trimResourceMessage` 拆出"外层 mask + 内层
  mask",对 Any 做 unpack→trim→pack(`config_dump_handler.cc:33-122`,注释在 36-51 行);
- `?name_regex=` 转成 StringMatcher,回调内部按资源 name 匹配(129-145 行);
- `?include_eds` 是唯一的"伪注册":endpoint 并不在 tracker 里,而是在请求时往回调表
  副本里 `emplace("endpoint", ...)`(193-201 与 246-254 行),由
  `dumpEndpointConfigs` 从 ClusterManager 现算 ClusterLoadAssignment(284-352 行),
  包括 drop_overload(302-310 行)、per-locality 权重(315-327 行)。

## 2. /clusters:host 状态机的两种渲染

`handlerClusters` 支持 `?filter=<re2>`(编译失败返回 400)与 `?format=json|text`
(`source/server/admin/clusters_handler.cc:48-72`;filter 注册在 `admin.cc:133-134`)。

text 版按 `cluster::host::key::value` 逐行输出,host 一行状态机字段齐全:
hostname(292)、health_flags(293-294,借助 `HostUtility::healthFlagsToString`)、
weight(296)、region/zone/sub_zone(297-302)、canary(304)、priority(306)、
success_rate 与 local_origin_success_rate(307-314);cluster 级有 observability_name(258)、
四项熔断阈值(262-267,格式化函数 19-31)、added_via_api(269-270)、eds_service_name(271-273)、
outlier 均值/驱逐阈值(345-366)。

json 版则把健康位结构化为 `HostHealthStatus`:`setHealthFlag` 对每个 `HealthFlag` 做
switch 映射——FAILED_ACTIVE_HC、FAILED_OUTLIER_CHECK、EDS 健康/降级、DEGRADED_ACTIVE_HC、
PENDING_DYNAMIC_REMOVAL、PENDING_ACTIVE_HC、EXCLUDED_VIA_IMMEDIATE_HC_FAIL、
ACTIVE_HC_TIMEOUT、EDS_STATUS_DRAINING、DEGRADED_OUTLIER_DETECTION
(`clusters_handler.cc:76-127`),再用宏 `HEALTH_FLAG_ENUM_VALUES` 逐位调用(199-202 行),
保证新增健康位必须同步出现在 admin 输出。host 统计走 counters()/gauges() 两条循环
(182-194 行)。本版还把 cluster 的合成 admin 端点(非负载均衡 host)也渲染成 host_statuses
(json 221-240 行、text 318-337 行,health_flags 小写对齐普通 host 的 token)。

## 3. /stats 的 prometheus 化:Sanitizer 与名字映射

入口分流在 `makeRequest`:`format=prometheus` 走一次性生成的 `PrometheusRequest`
(TODO #16139:暂不流式,`source/server/admin/stats_handler.cc:109-118`);其余格式在
flushOnAdmin 时先 `server_.flushStats()`(125-127 行)。prometheus 路径同样先校验参数
再 flush(164-179 行)。参数解析 `StatsParams::parse` 覆盖 usedonly/pretty/text_readouts/
filter/histogram_buckets/native_histogram_max_buckets/type/hidden/format
(`source/server/admin/stats_params.cc:6-106`);可见性由 `shouldShowMetric` 统一裁剪:
used-only、hidden 三态(include/only/exclude)、re2 filter(`stats_params.h:86-110`)。

prometheus 化的三步:

1. **Sanitize**:指标名中 `[^a-zA-Z0-9_]` 一律替换为 `_`(预编译正则 + 就地版,
   `source/server/admin/prometheus_stats.cc:26-47`);label 值转义 `\`、换行、`"`
   (53-63 行,对齐 prometheus common 的 text 序列化)。
2. **名字映射**:`metricName` 先剥离自定义 stat 命名空间——自定义指标不加前缀原样暴露,
   但要求首字符不得为数字,否则整个指标被丢弃(953-956 行);普通指标统一加
   `envoy_` 前缀(962-963 行)。同一 tag-extracted 名下多个指标先按 symboltable 排序
   再成组输出,以满足 prometheus 按组排序的建议(717-790 行)。
3. **双格式输出**:按 Accept 头协商,`application/vnd.google.protobuf` 走
   MetricFamily delimited protobuf,否则 text(857-900 行判定,1064-1079 行分派,
   protobuf 时显式设置 Content-Type 1055-1057 行)。histogram 支持
   cumulative/summary/prometheusnative 三种模式,prometheusnative 仅限 protobuf 格式,
   由 `validateParams` 拒绝非法组合(914-937 行);native histogram 由 circllhist 桶
   映射到 span/delta 编码,schema 自适应选 4→-4(486-681 行)。per-host 指标不进
   ThreadLocalStore,而是经 `HostUtility::forEachHostMetric` 以 primitive snapshot
   单独成组输出(1013-1028 行)。

## 4. 安全面:dangerous endpoint、POST 强制与 admin access log

Envoy 没有"dangerous"编译开关,危险端点的防线是三层显式约束:

- **POST 强制**:`/quitquitquit`、`/healthcheck/fail|ok`、`/drain_listeners`、
  `/reset_counters`、`/logging`、`/runtime_modify`、`/reopen_logs`、三个 profiler 注册时
  `mutates_server_state=true`(`admin.cc:182-185,196-210,216-219,220-233,271-279`),
  分发处校验方法并打 error 日志(`admin.cc:422-431`);/help 会给这些端点标 `(POST)`
  (463-478 行)。
- **handler 本体极小**:`handlerQuitQuitQuit` 仅调 `server_.shutdown()`,
  `handlerHealthcheckFail/Ok` 仅置 `failHealthcheck` 布尔
  (`source/server/admin/server_cmd_handler.cc:8-27`)。
- **可插拔端点的防注入**:运行期 `addStreamingHandler` 拒绝 prefix 里含 `&"'<>?:`
  的注册——防止扩展借 admin 首页 HTML 注入 XSS(注释明说,`admin.cc:492-506`);
  另有 allowlist 机制,未命中路径直接 403(`admin.cc:413-418`,注册入口 327-329 行)。

admin 的访问日志与数据面共用 HCM 管线:`AdminImpl` 同时实现
`Http::ConnectionManagerConfig`(`source/server/admin/admin.h:65-71`),
`accessLogs()` 返回 `admin.access_log` 配置构造的实例
(`source/server/configuration_impl.cc:285-304`:先逐条 factory 创建,再兼容旧的
`access_log_path` 默认接 `envoy.file_access_log`),listener 启动时注入
(`admin.cc:54-57`)。也就是说,`curl -X POST .../quitquitquit` 是否留痕,取决于
运维是否配置了 `admin.access_log`——代码不强制,这本身就是"显式而非隐式"的取舍。

## 5. readiness 与 drain:/ready 状态机、graceful drain、lifecycle

`/ready` 的状态映射极薄:`Utility::serverState` 把 Init::Manager 三态映射为
PRE_INITIALIZING/INITIALIZING,Initialized 后按 `healthCheckFailed()` 分为
DRAINING/LIVE(`source/server/utils.cc:11-24`);非 LIVE 一律 503
(`source/server/admin/server_info_handler.cc:71-80`)。`/server_info` 用同一函数填
state 字段,并附 uptime、命令行与 node(82-111 行)。所以 `/ready` 报 DRAINING 的
唯一触发是 `/healthcheck/fail`(server 端 `source/server/server.cc:165,309`),与
listener 的 drain 是两条独立的轴。

`/drain_listeners` 才是真正的排水阀(`source/server/admin/listeners_handler.cc:15-57`):
`?inboundonly` 选方向(20-23 行),`?graceful` 进入 `drainManager().startDrainSequence`,
完成后按 `?skip_exit` 决定是否 `stopListeners`(46-50 行);重复 drain 幂等返回 200
(40-43 行)。非 graceful 则直接停 listener(52 行)。进程退出侧,`server_.shutdown()`
先通知 `Stage::ShutdownExit` 回调再退出 dispatcher(`server.cc:1147-1151`);lifecycle
notifier 共 Startup/PostInit/ShutdownExit 三段,带 completion 的回调只在 worker 已启动时
通知,且 server 会等全部完成才退出(`envoy/server/lifecycle_notifier.h:18-39`,
`server.cc:1181-1215`)——这是 wasm 等有状态扩展的"最后清理"通道。

## 6. overload 联动:admin 为何活到最后

过载动作是一组具名常量:stop_accepting_requests / disable_http_keepalive /
stop_accepting_connections / reject_incoming_connections / shrink_heap /
reduce_timeouts / reset_high_memory_stream / close_idle_http_connections
(`envoy/server/overload/overload_manager.h:23-57`)。HCM 在构造时抓取
StopAcceptingRequests 与 DisableHttpKeepAlive 的状态引用
(`source/common/http/conn_manager_impl.cc:140-143`),在请求入口判定
(1412 行附近)。**没有一个 admin handler 被单独限流**:admin 的网络过滤链显式传
`server_.nullOverloadManager()`,注释直言"admin 在过载时仍可访问"
(`admin.cc:309-318`;null 实例成员在 117 行)。这正是设计意图——过载时
`/server_info`、`/healthcheck/fail`、`/quitquitquit` 必须可用,否则运维失去最后手段;
代价是 admin 自身不再有背压,TODO #31087 承认 admin http 端口暂无 flow control
(`source/server/admin/admin_filter.cc:95-96`)。此外 `admin.ignore_global_conn_limit`
可让 admin 不受全局连接上限约束(`source/server/configuration_impl.cc:271`)。

## 8. 编译裁剪与 contrib 分界

扩展默认全量编译,但每个都是可关的开关:`envoy_extension_package` 在每个 BUILD 里生成
`enabled` bool flag 与 `is_enabled` 配置(`bazel/envoy_build_system.bzl:71-81`);
`envoy_cc_extension` 生成 `xxx_envoy_extension` 目标,disabled 时 select 为空库
(`bazel/envoy_library.bzl:48-69`)。总注册表 `extensions_build_config.bzl` 有 331 条,
可被下游 `@envoy_build_config` 覆盖(`source/extensions/extensions_build_config.bzl:1-677`;
覆盖入口 `envoy_build_system.bzl:3`);`all_extensions.bzl` 另有 3 条必须扩展(uuid request_id、
round_robin、xff 探测)与 denylist 机制(`source/extensions/all_extensions.bzl:7-20`),
`source/exe/BUILD:38-56` 按平台 select(如 HTTP3 缺席清单)拼装 `all_extensions_lib`。
admin 的 HTML 亦同法可裁:stats html/active-html 格式在 `--define=admin_html=disabled`
下直接报错(`stats_params.cc:86-98`,宏开关 `stats_handler.cc:130-134`)。

**contrib 是另一个世界**:38 个不承诺安全加固/第三方授权风险的扩展(golang 过滤器、
mysql/kafka/rocketmq/sip/postgres 代理、qat/qatzip 硬件加速、istio 附属件等)住在顶层
`contrib/`,有自己的 `contrib_build_config.bzl`(38 条)、`all_contrib_extensions.bzl`、
独立的 `contrib/extensions_metadata.yaml`,包可见性用
`CONTRIB_EXTENSION_PACKAGE_VISIBILITY`(`bazel/envoy_build_system.bzl:88-90`,
`contrib/contrib_build_config.bzl:1-30`,`contrib/config/source/BUILD:1-9`)。主仓库
`source/extensions` 不依赖 contrib;发行文档按 security posture 渲染时给 contrib 项打
"(contrib builds only)" 标记(`docs/tools/generate_extensions_security_rst.py:15-31`)。

## 9. 版本与 API 兼容:metadata status 与如实说明

`source/extensions/extensions_metadata.yaml` 收录 350 个扩展,字段为 categories、
security_posture、status、type_urls。status 三值如实统计:**stable 184、alpha 127、
wip 39**(grep 计数);不存在 "deprecated" 状态——下线中的 API 走
`envoy_deprecated_` 注解而非扩展状态。status 语义由 schema 定义:stable=生产可用,

(`tools/extensions/extensions_schema.yaml:166-176`);security_posture 五值
(robust_to_untrusted_downstream 等)在同文件 40-64 行,扩展必须显式标注对上下游

把关一致性,并被 `source/extensions/BUILD:9-15` 导出为数据。至于任务中提到的
`BuildExtensionsMetadata`:本快照内(grep 全仓)不存在该名字的目标——metadata 的

version/revision 等字段(`source/common/version/version.cc:41-87`),不含扩展清单,
此点如实记录。

## 11. 设计动机

1. **为什么 config_dump 走 ConfigTracker 注册而非集中 dump**:配置的所有权分散在
   ClusterManager/ListenerManager/RDS/Secret 各组件,集中式 dump 会造成循环依赖与
   过期快照;回调表 + 弱所有权 EntryOwner 让"谁能提供配置谁注册",组件析构即注销
   (`envoy/server/config_tracker.h:15-23`、`config_tracker_impl.cc:19-22`),dump
   永远现算现发,且天然支持组件级裁剪(如 admin 编译缺席时 OptRef 为空,
   `server.cc:651-664`)。
2. **为什么 dangerous endpoint 显式(mutates_server_state + POST)**:把"危险"编码进
   数据结构而非文档,分发器才能机械地强制 POST 并留 error 日志(`admin.cc:422-431`),
   /help 自动标注;显式声明同时让审计工具可以静态枚举全部写端点,而不靠 URL 黑名单猜。
3. **为什么扩展按目录即分类**:目录层级 = 工厂 category = 配置注入点,三者对齐让
   "新扩展放哪、注册到哪个 factory、bootstrap 里怎么写 typed_config"成为同一个问题;
   BUILD 的 enabled flag 再把分类转成可裁剪的编译单元(`envoy_build_system.bzl:71-81`),
   生态规模(331 条)因此不与管理复杂度同涨。
4. **为什么 metadata status/security_posture 是必填 schema**:扩展的质量承诺是发行件
   的一部分——status(alpha/wip)让用户对成熟度有准确预期,security_posture 把
   "这个过滤器敢不敢面对不可信流量"变成一个机器可查的字段
   (`extensions_schema.yaml:40-64`),文档按 posture 分节渲染,供应链评估不再读代码。
5. **为什么 contrib 分仓**:contrib 扩展(第三方 SDK 依赖、非 Apache 许可、无安全加固
   承诺)一旦混入主表,主发行版要么背上它们的构建/审计负担,要么被迫维护两套标准;
   物理分仓 + 独立 metadata + 可见性隔离(`envoy_build_system.bzl:88-90`)让
   "核心最小可信集"与"长尾适配"各自演进。
6. **为什么 admin 用 null overload manager**:管理面是过载时最不能失效的路径,把它从
   过载判定中豁免(`admin.cc:309-318`)等价于给运维留一条带外通道;这比"给 admin 配置
   更高阈值"更可靠,因为后者在极端过载下仍可能被波及。
7. **为什么 /ready 把 healthcheck 失败也归为 DRAINING**:对 LB 而言,"主动声明不健康"
   与"正在排水"在语义上等价——都应摘除流量;把两轴合并成一个只读信号,让 k8s
   readinessProbe 无需理解 Envoy 内部就有正确的摘除行为(`utils.cc:11-24`)。
