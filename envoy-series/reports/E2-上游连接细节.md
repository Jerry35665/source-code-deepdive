# E2. 上游连接细节：HTTP/2 池、CONNECT、WebSocket 与 upgrade

> 基线：tag v1.39.1，commit b579d07d3ad7ee11d32b105e91a5a39ad24718d7。所有行号均以该检出实测为准。
> 本报告接棒卷一（E）：卷一讲连接池统一公式 `shouldConnect` 与分相（Connecting→Ready→Busy/Draining）；本章深入"池之上的协议语义"——同一套池骨架上，HTTP/2 的容量协商、HTTP/1.1 的 close/半关、CONNECT/WebSocket 隧道、内部重定向、hedging、upstream filter 链、GOAWAY drain 与 TCP 池各自如何落到代码。

## 0. 全景图：一条上游连接上的字节路径

```
HTTP/1.1 upstream（一连接一请求，池=排队器）          HTTP/2 upstream（一连接多流，池=容量账本）
 D0 ──req1──▶ [TCP/TLS cx1] ──▶ upstream              D0 ──req1──┐
      (req2 只能等)                ◀──resp1            D1 ──req2──┼─▶ [TCP/TLS cx1] ─SETTINGS─▶ upstream
 D1 ──req2──▶ cx1 空闲后复用                            D2 ──req3──┘     HEADERS(stream3)… 流编号上限 2^31-1
                                                       池账本: currentUnusedCapacity = concurrent_stream_limit_ − numActiveStreams()
                                                         = min(SETTINGS 实测, max_concurrent_streams 配置, max_requests_per_connection 余量)

CONNECT / WebSocket 隧道（HTTP/1.1 upstream，连接"专用化"）
 D0 ── CONNECT api:443 ──▶ Envoy router ──▶ upstream HTTP 池 (paused_for_connect_)
      …暂停下游数据… upstream 返回 2xx/101 → CodecBridge::decodeHeaders 解除暂停 (upstream_codec_filter.cc:158)
 D0 ◀══ 双向裸字节 ══▶ cx1（连接被该下游流独占，流结束=连接半关/关闭，http1/codec_impl.cc:307-313）
 HTTP/2 upstream 则无"专用化"：WebSocket upgrade 头被转成 RFC8441 extended CONNECT（:protocol），
 仍与其他流复用同一条 H2 连接（http2/codec_impl.cc:400-410）。
```

卷一的容量公式 `(pending+active+anticipated) × ratio > connecting_and_connected_capacity + active`（source/common/conn_pool/conn_pool_base.cc:94-114）里，协议差异全部被压缩进 `ActiveClient::currentUnusedCapacity()`（source/common/conn_pool/conn_pool_base.h:64-69，`min(remaining_streams_, concurrent_limit − active)`）——本章反复出现的三类 client（H1/H2/TCP）就是三种容量定义。池骨架的三个 client 链表 `ready_clients_/busy_clients_/connecting_clients_`（conn_pool_base.h:378-386）与 `pending_streams_` 队列也不区分协议，协议语义只决定"何时进 Busy、何时能回 Ready"。

## 1. HTTP/2 upstream 池：容量从哪来，流耗尽后怎么办

### 1.1 初始容量：三个上限取最小

```cpp
// source/common/http/http2/conn_pool.cc:21-38
uint32_t initial_streams =
    host->cluster().httpProtocolOptions().http2Options().max_concurrent_streams().value();
if (http_server_properties_cache && origin.has_value()) {
  uint32_t cached_concurrency = http_server_properties_cache->getConcurrentStreams(origin.value());
  if (cached_concurrency != 0 && cached_concurrency < initial_streams) {
    // Only use the cached concurrency if it lowers the streams below the
    // configured max_concurrent_streams as Envoy should never send more
    // than max_concurrent_streams at once.
    initial_streams = cached_concurrency;
  }
}
uint32_t max_requests = MultiplexedActiveClientBase::maxStreamsPerConnection(
    host->cluster().maxRequestsPerConnection());
if (max_requests < initial_streams) { initial_streams = max_requests; }
```

`max_concurrent_streams` 未配置时的默认值：safe 模式 1024，legacy 2^31-1（http_option_limits.h:22,24，回填逻辑 source/common/http/utility.cc:204-212）。三者进 `MultiplexedActiveClientBase` 构造（http/conn_pool_base.cc:203-213）：`remaining_streams_`（lifetime = max_requests_per_connection，0 映射 2^29，http/conn_pool_base.cc:107-109,199-201）、`concurrent_stream_limit_`（上式结果）、`configured_stream_limit_`（纯配置值，供 SETTINGS 到来后夹逼；字段注释 source/common/conn_pool/conn_pool_base.h:127-141）。HTTP/2 池是 `FixedHttpConnPoolImpl` + `CodecClientProd(CodecType::HTTP2)`（http2/conn_pool.cc:62-82），codec 工厂若被 cluster 的 `typed_extension_protocol_options` 覆写则用自定义 client codec（codec_client.cc:300-303）。

### 1.3 流耗尽与新连接的创建时机

流分配时逐个扣减（source/common/conn_pool/conn_pool_base.cc:255-264）：`remaining_streams_--` 归零即转 `Draining`（寿命用尽，计 `upstream_cx_max_requests_`）；`capacity==1` 即转 `Busy`（并发用尽）。Busy/Draining 两个状态共用 `busy_clients_` 链表（owningList，:422-437）。新连接的四个触发时机：

- `newStreamImpl`：拿到 ready client 之后仍调 `tryCreateNewConnections()` 预建下一条（:333-340）；
- `onUpstreamReady`：清完 pending 后若队列仍非空（:417-419）；
- 连接断开后的补偿建连（:647-650）；
- 断路器满但池内一条连接都没有时强制建连，防止 pending 被排到一个永远无法服务的 host（:208-209，卷一 §6.3）。

流结束的回位对称发生在 `onStreamClosed`（:283-325）：Draining 且无活跃流→关连接；Busy 且 `currentUnusedCapacity()>0`→转回 Ready（或 0-RTT 的 ReadyForEarlyData）并调度 `onUpstreamReady`（:309-324）。HTTP/3 特例不在此列：QUIC 的容量由 MAX_STREAMS 帧驱动，`trackStreamCapacity()=false`（conn_pool_base.h:196-197, cc:294-296）。若配置了多协议（H3+H2），外层是 `ConnectivityGrid` 把两个池组成竞速网格做 failover 与 happy-eyeballs（conn_pool_grid.h:16-31）。

## 2. HTTP/1.1：Connection: close、半关与池回收时机

H1 client 恒为"并发 1"（http1/conn_pool.cc:82-88 传 `effective_concurrent_stream_limit=1`），且 `numActiveStreams()` 看 `stream_wrapper_` 而非 codec 计数——H1 codec 的流销毁先于 decode 完成，过早暴露容量会让池把新请求塞进半完成的连接（http1/conn_pool.h:28-34）。

```cpp
// source/common/http/http1/conn_pool.cc:58-76（节选）
void ActiveClient::StreamWrapper::onDecodeComplete() {
  ...
  if (!encode_complete_) {
    ENVOY_CONN_LOG(debug, "response before request complete", *parent_.codec_client_);
    parent_.codec_client_->close();                        // 响应先于请求结束：关
  } else if (close_connection_ || parent_.codec_client_->remoteClosed()) {
    parent_.codec_client_->close();                        // Connection: close / 对端已半关：关
  } else {
    pool->scheduleOnUpstreamReady();                       // 连接回收进池，唤醒 pending
    parent_.stream_wrapper_.reset();
    pool->checkForIdleAndCloseIdleConnsIfDraining();
  }
}
```

`close_connection_` 在响应头到达时判定：`HeaderUtility::shouldCloseConnection`（http1/conn_pool.cc:49-56；header_utility.cc:486-512）——HTTP/1.0 无 `keep-alive` token 即关、HTTP/1.1 有 `close` token 即关、`Proxy-Connection: close` 兼容旧代理。`~StreamWrapper` 用 `delay=true` 调 `onStreamClosed`（:40-45，注释引 issue#2715：上游可能在响应完成后立即关连接，pending 要推迟到下一个 dispatcher 循环再接手）；reset 即关连接（:78-80）。

半关（对端先 FIN）单独处理：codec client 构造时 `detectEarlyCloseWhenReadDisabled(false)`，让连接先吃数据再处理 FIN（codec_client.cc:32-37，引 issue#1679）；读过滤器见 `end_stream` 且半关启用则 close（codec_client.h:228-237）；H1 上"以断连表示响应结束"由 `onEvent` 对 RemoteClose 补一次 `onData(empty)` 收尾（codec_client.cc:117-122）。H1 的 `ActiveRequest` 也不等 encode 完成（`wait_encode_complete_=false`，codec_client.h:256-267），与 H2/H3 的 true 不同。

## 3. CONNECT 与升级隧道：101 之后连接归谁

### 3.1 选池：CONNECT 是"协议分流器"

router 在 `createConnPool` 里按方法改写 upstream 协议：

```cpp
// source/common/router/router.cc:996-1007（节选）
UpstreamProtocol upstream_protocol = UpstreamProtocol::HTTP;
if (route_entry_->connectConfig().has_value()) {
  auto method = downstream_headers_->getMethodValue();
  if (Http::HeaderUtility::isConnectUdpRequest(*downstream_headers_)) {
    upstream_protocol = UpstreamProtocol::UDP;
  } else if (method == Http::Headers::get().MethodValues.Connect ||
             (route_entry_->connectConfig()->allow_post() &&
              method == Http::Headers::get().MethodValues.Post)) {
    upstream_protocol = UpstreamProtocol::TCP;
  }
}
```

即"Enhanced CONNECT"的入口：CONNECT-UDP → UDP 池，CONNECT（或允许的 POST）→ 原生 TCP 池，其余走 HTTP 池。工厂分发在 `extensions/upstreams/http/generic`（config.cc:15-36）；TCP 版 `TcpConnPool` 经 `thread_local_cluster.tcpConnPool` 取 §9 的池（extensions/upstreams/http/tcp/upstream_request.h:22-41）。CONNECT 请求禁止 shadow/mirror（router.cc:856-857），带请求体的早数据 CONNECT 可按 runtime 开关拒绝（`isEarlyConnectData`，:1078-1086）。

### 3.2 暂停与解除：字节路径的关键闸门

请求头经 `UpstreamRequest::acceptHeadersFromRouter` 时按类型打 pause 位（upstream_request.cc:420-445）：CONNECT→`paused_for_connect_`；WebSocket→`paused_for_websocket_`（并按 runtime flag 提前装 per-try/route 超时，:429-437）；其他 generic upgrade→`paused_for_generic_upgrade_`。请求下行走到链尾 `UpstreamCodecFilter`，若 upstream 未就绪则 latch 头并返回 `StopAllIterationAndWatermark`（upstream_codec_filter.cc:54-61）；编码后处于 pause 同样停在原地（:90-96）。解除统一在响应侧 `CodecBridge::decodeHeaders`（:151-240）：CONNECT 看 2xx（:158-162）；generic upgrade 看 101 或非 H1 协议上的 2xx（:164-173）；WebSocket 看 101/非 H1 2xx，成功即顺手关掉 route 与 per-try 超时（:175-186，配 upstream_request.cc:903-913 的定时器清理）；4xx/5xx 握手失败按 runtime 开关剥掉 `Upgrade`/`Connection: upgrade` 头后透传（:187-216）；其余状态码转 local reply 并抄写响应头（:217-233，注释说明 H2 的 200 会在 codec 层规范化为 101）。非 HTTP upstream（TCP/UDP 池）没有 HTTP 语义，`onPoolReady` 里直接清掉三个 pause 位（upstream_request.cc:657-665）。

### 3.3 101 之后：H1 专用化，H2 复用

- **HTTP/1.1 upstream**：升级响应不分块（`chunk_encoding_ = !Utility::isUpgrade(headers) && !is_response_to_head_request_ && !is_response_to_connect_request_`，http1/codec_impl.cc:223-231，引 RFC7231 §4.3.6）。101 后该流持续活跃，H1 client 的"并发 1"使连接天然被这条下游流独占，直到隧道任一侧半关/关闭——连接随流终结，不回池复用（回收路径即 §2 的 onDecodeComplete/close 分支）。CONNECT/TCP tunneling 下 `endEncode` 主动 `FlushWrite` 半关表示 end stream（http1/codec_impl.cc:307-313），`enableTcpTunneling` 置 `is_tcp_tunneling_`（http1/codec_impl.h:204）。
- **HTTP/2 upstream**：不存在连接专用化。WebSocket upgrade 请求被转成 RFC8441 extended CONNECT（`transformUpgradeRequestFromH1toH2`，http2/codec_impl.cc:400-404；utility.cc:1198+），普通 CONNECT 则剥 scheme/path/protocol（:405-410），响应侧对称转换（:431-437）。其他流照常在同一条 H2 连接上多路复用，池容量只看到"多了一个活跃流"。`enableTcpTunneling` 在 H2 是 no-op（http2/codec_impl.h:573）——H2 的 CONNECT 本身就是字节隧道。

tcp_proxy 的 HTTP 隧道（§9）复用同一套机制：向上游发 `CONNECT`/`POST` 并以 2xx（H1）/200（H2/H3）为隧道建立成功的判据（tcp_proxy/upstream.cc:171-203, 160-169）。

## 4. 内部重定向：redirect 位置与流所有权

```cpp
// source/common/router/router.cc:2168-2182（节选）
bool Filter::setupRedirect(const Http::ResponseHeaderMap& headers) {
  const Http::HeaderEntry* location = headers.Location();
  const uint64_t status_code = Http::Utility::getResponseStatus(headers);
  // Redirects are not supported for streaming requests yet.
  if (downstream_end_stream_ && (!request_buffer_overflowed_) && location != nullptr &&
      convertRequestHeadersForInternalRedirect(*downstream_headers_, headers, *location,
                                               status_code) &&
      callbacks_->recreateStream(&headers)) {
    cluster_->trafficStats()->upstream_internal_redirect_succeeded_total_.inc();
    return true;
  }
```

判定点在 `Filter::onUpstreamHeaders`：3xx 且 `internalRedirectPolicy` 开启且响应码命中则 `setupRedirect`（router.cc:1956-1963）。`convertRequestHeadersForInternalRedirect`（:2197-2345）做全套校验与改写：跨 scheme 校验（:2220-2229）、`max_internal_redirects` 记在 FilterState（:2231-2250）、`response_headers_to_copy`（:2257-2276）、失败经 `Cleanup restore_original_headers` 回滚（:2278-2287）、303 改 GET 并清 body/Content-Length（:2329-2339）、`clearRouteCache` 后重新选路由（:2304-2315）。

所有权的答案：**上游流不转移**。旧 `UpstreamRequest` 在收到可重试/可重定向的响应头时已被 `removeFromList + deferredDelete`（:1942-1943，reset 路径同 :1618-1619）；被"转移"的是下游流——`recreateStream` 在同一条下游连接上重建流、重跑 decode 链，router 再走一遍 `chooseHost → createConnPool → newStream`。内部重定向等价于把 3xx 消化在 Envoy 内部后发起一个全新请求，统计走 `upstream_internal_redirect_succeeded/failed_total`（:2180, :2193）。

## 6. upstream_http_filters：除了 codec 还挂了什么

`UpstreamRequest` 构造时装 filter 链，优先级为 cluster 定制链 → router 定制链 → 默认链（upstream_request.cc:174-185），默认链只有 `envoy.filters.http.upstream_codec`（upstream_codec_filter.cc:300-324）。这是一套完整的 `Http::FilterManager`（`UpstreamFilterManager`，upstream_request.cc:46-97）：请求下行经各 filter 到 `UpstreamCodecFilter` 再发往 codec，响应上行经 `CodecBridge` 反向走链（头注释 upstream_request.h:42-66）。已双注册（downstream+upstream 各一个 factory）的 filter：buffer（buffer/config.cc:50-53）、aws_request_signing（aws_request_signing/config.cc:176-179）、header_mutation（header_mutation/config.cc:51-53）、ext_proc（ext_proc/config.cc:174-177）、composite（composite/config.cc:178-180）、credential_injector（credential_injector/config.cc:67-70）、lua（lua/config.cc:52）、wasm（wasm/config.cc:15）。三个限制值得记录：upstream 链不支持 upgrade filter chain（upstream_codec_filter.cc:312-316）；filter 可通过 `onHostSelected` 在建连前中止请求（upstream_request.cc:452-456 + `UpstreamFilterManager::notifyHostSelected` :83-95）；上游 filter 的 local reply 直接穿透到下游 FM（upstream_request.cc:62-75）。转换注意事项官方文档在 source/docs/upstream_filters.md:1-38（勿用 downstreamCallbacks、local reply/streamInfo 与 hedging 的并行交互等）。

## 7. drain 与 GOAWAY：池转 Draining 的全部条件

```cpp
// source/common/http/conn_pool_base.cc:111-121
void MultiplexedActiveClientBase::onGoAway(Http::GoAwayErrorCode) {
  parent_.host()->cluster().trafficStats()->upstream_cx_close_notify_.inc();
  if (state() != ActiveClient::State::Draining) {
    if (codec_client_->numActiveRequests() == 0) {
      codec_client_->close();                    // 空闲连接：直接关
    } else {
      parent_.transitionActiveClientState(*this, ActiveClient::State::Draining);  // 半排空
    }
  }
}
```

codec 层保证 GOAWAY 只上抛一次（http2/codec_impl.cc:1273-1283），优雅 GOAWAY 关闭不计为 protocol error（codec_client.cc:194-201）。池转 Draining 的完整清单：① GOAWAY（有在途流时半排空，如上）；② 管理面 `drainConnections`：`DrainAndDelete` 整池等空闲后删除，普通模式关空闲连接 + 把 ready/busy 全转 Draining（source/common/conn_pool/conn_pool_base.cc:498-527；空闲判定 `closeIdleConnectionsForDrainingPool` :457-485）；③ `remaining_streams_` 耗尽（max_requests_per_connection，:257-260）；④ `max_connection_duration` 定时器（conn_pool_base.cc:903-932）。进入 Draining 时 `ActiveClient::drain()` 把 `remaining_streams_` 清零并把剩余容量从 cluster 账本扣回（:934-949），在途流跑完后 `onStreamClosed` 关连接（:309-311）。连接粒度之外还有池粒度的删除：host 的 `ConnPoolsContainer` 引用归零后整池 `DrainAndDelete`（卷一 §6.1 的池生命周期）。

## 8. 超时与重置传播：pool failure reason → StreamResetReason 映射表

池失败在 router 边界被翻译（upstream_request.cc:616-639）：

```cpp

}(reason);
```

四个 reason 的典型来源：Overflow 来自 requests/pending 断路器与负载 shed（conn_pool_base.cc:242-251, :352-358, :384-388）；连接失败来自握手前断连（codec_client.cc:130-132：握手前 Remote/Local→连接失败，握手后→`ConnectionTermination`，协议错误再覆写为 `ProtocolError`）；Timeout 来自 `connect_timeout`（conn_pool_base.cc:896-901 置 `timed_out_`，:596-597 转成 PoolFailureReason::Timeout）。池侧另按原因计分并决定连接生死（http/conn_pool_base.cc:170-197：连接类失败 eject 计数并置 `closed_with_active_rq_`，LocalReset/ProtocolError/OverloadManager 计 tx reset，RemoteReset 计 rx reset）。`StreamResetReason → CoreResponseFlag` 的响应侧映射在 router.cc:1744-1773：连接类→`UpstreamConnectionFailure`，`ConnectionTermination`→`UpstreamConnectionTermination`，`ConnectError`（H2 CONNECT 被拒，http2/codec_impl.cc:184-208 与 OGHTTP2 互转）→`UpstreamRemoteReset`，`Http1PrematureUpstreamHalfClose`→`LocalReset`，`OverloadManager`→`OverloadManager`。per-try/per-try-idle 超时的装填与豁免在 upstream_request.cc:565-609（下游已开始响应则忽略 per-try timeout，:597-608）。

## 9. tcp_proxy 的 TCP 池：独立语义与隧道

TCP 池复用同一 `ConnPoolImplBase` 骨架（source/common/tcp/conn_pool.h:146-192），但有三处协议化差异：`enforceMaxRequests()=false`（不做 max_requests 断路器，:186）；一条连接就是一个"流"（`numActiveStreams = callbacks_?1:0`，:117）；自带 per-connection idle timeout（conn_pool.cc:43-46, 123-141）。两个特有的竞态处理：

```cpp

  connection_->readDisable(true);   // MySQL 等协议上游先说话：先压住读，数据留到关联下游后再放
}
...
if (event == Network::ConnectionEvent::LocalClose ||
    event == Network::ConnectionEvent::RemoteClose) {
  disableIdleTimer();

```

被下游取用时 `readEnableIfNew` 恢复读并关掉早 FIN 检测（:63-74）；`onPoolReady` 交出 `TcpConnectionData` 并停 idle timer（:195-208）；释放时 `clearCallbacks` 唤醒 pending 并重挂 idle timer（:80-90）；旧版 drain 语义把 connecting 连接的剩余额度压到 1（:143-160）。tcp_proxy 的 HTTP 隧道模式 `HttpUpstream` 发 CONNECT/POST 并对响应验证 2xx/200（upstream.cc:160-169, 174-184）；流 reset 按 runtime flag `map_http_stream_reset_to_tcp_rst` 映射为 TCP RST 语义（`onResetStream`→RemoteClose/LocalClose，:246-274）；下游关连接对 H1 走半关 FlushWrite（`TcpUpstream::onDownstreamEvent`，:127-146）。新路径 `CombinedUpstream` 把 tcp_proxy 的上游也装进 router 的 upstream filter 体系（`RouterUpstreamRequest` + enable_tcp_tunneling，:433-441；实现 :505-662，2xx/200 校验 :574-590）。池取消策略也有讲究：HTTP 池柄用 `Default`、TCP 池柄用 `CloseExcess`（:419-428, :329-333）。

## 10. 设计动机

1. **SETTINGS 实测值优先、但只下调不上调**：对端真实容量只有它自己知道，缓存实测值（HttpServerPropertiesCache）避免每条新连接都超发被 REFUSE；夹在 `configured_stream_limit_` 之下则保证 Envoy 永不越过自己声明的上限（http2/conn_pool.cc:26-31）。代价——SETTINGS 前抢跑的流可能被拒——被注释明示为延迟换正确性的选择（http/conn_pool_base.cc:124-129）。
2. **CONNECT/升级后 H1 连接专用化**：H1 隧道建立后连接退化成无帧边界的字节管道，没有"结束请求"的协议手段（只能半关 TCP），物理上不可能再承载第二个请求；而 H2 的 CONNECT 是流级的，连接仍可复用。同一语义在两种协议上自然分化：H1 的并发 1 + 流尽连接亡 vs H2 的 `enableTcpTunneling` no-op（http2/codec_impl.h:573）。
3. **内部重定向在下游 recreateStream，而非转移上游流**：3xx 的语义是"对新 URI 发起新请求"——host、scheme、乃至集群和协议都可能变（clearRouteCache 重新选路由，router.cc:2304-2315），继续在旧上游流上发送反而违反语义；且请求头已被改写、可能 303 转 GET 清 body。放弃旧 UpstreamRequest（deferredDelete）+ 重建下游流是唯一自洽实现。
4. **GOAWAY 半排空**：GOAWAY 的协议含义是"别再开新流"，不是"在途流作废"。若有在途流就立刻关连接，Envoy 必须对每个流做一次本可避免的重试/失败传播；半排空让在途流自然终结、空闲连接即时回收，正好把协议语义映射到池已有的 Draining 状态（http/conn_pool_base.cc:111-121）。
5. **TCP 池独立于 HTTP 池**：TCP 没有 SETTINGS 式容量协商、没有流边界，容量恒为"独占"（0/1 两态）；且有自己的竞态（上游先发数据须先压读缓存，tcp/conn_pool.cc:92-99）与生命周期（idle timer 挂连接而非挂流）。强行塞进 HTTP 池只会让两边变形，于是共享 `ConnPoolImplBase` 骨架但独立成 `Tcp::ConnPoolImpl`（tcp/conn_pool.h:146-192），并豁免 max_requests 断路器（:186）。
6. **hedging 不捆绑新连接**：是否复用/新建连接本质是池的容量决策；router 只表达"我要另一个 attempt"，池按统一公式决定是否建连，避免 router 层重复实现一套连接策略，也让 hedge 的第二 attempt 与普通请求在池内完全同构（router.cc:2415-2430）。
7. **upstream filter 链与 downstream 分治**：上游链定位为"纯出站变换"（签名、改头、限流），凡涉及下游状态（路由缓存、重定向、recreateStream、本地回复细节）都留在下游链——local reply 直接穿透（upstream_request.cc:62-75）、`onHostSelected` 只给中止权（:452-456），这是双 filter 转换清单第一条禁令的由来（upstream_filters.md:6-7）。
