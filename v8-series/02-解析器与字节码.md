# 第 02 章 · 解析器与字节码:惰性两层与反馈向量

> 基线:commit `c6a1f7c2`。行号以 src/parsing/、src/ast/、src/interpreter/ 为准。

## 2.0 全景:JS 到执行的管线

```
源码 → Parser(全量)/ PreParser(惰性) → AST(Zone 分配)
  → BytecodeGenerator(AST→字节码,累加器+寄存器混合)
  → Ignition 解释执行(埋反馈)→ 热函数 → Sparkplug/Maglev/TurboFan
惰性两层:①惰性解析(内部函数只 PreParser 校验)②惰性编译(调用时才生成字节码)
```

源码自述:"**we need to parse more eagerly than we compile**"(parser.cc:2850)——语法错误要早报,编译可以晚。

## 2.1 惰性解析:PreParser 的"校验不建树"

PreParser 与 Parser **共用 ParserBase 模板骨架,只换掉节点工厂**,传哑对象 PreParserExpression(preparser.h:15-21)——同一个文法两份语义(一份建 AST 一份只验证)。`should_preparse` 决策(:2923-2924):内部函数按大小/懒编译开关;SkipFunction 跳体(:3039);**失败回退书签**:PreParser 发现错误时 scanner 回退重做全解析(:3118)。preparse 产物(LogFunction,:362-371:函数尾位置/参数数/内部函数数)可被二次编译复用,**连扫描都跳过**(:3056-3082)。惰性函数被调用时的重解析入口 parser.cc:1060(编译触发 compiler.cc:3012)。

## 2.2 AST 与 Zone

AST 节点体系(AST_NODE_LIST 总表,ast.h:121-127;:3087)全部 Zone 工厂分配(A 章 Zone)——AST 的生命周期=一次编译,完事整段归还。与 quickjs(第五系列二 02 章)对照:quickjs 免 AST 直出字节码;V8 保留 AST 是因为 TurboFan 需要完整树做优化。

## 2.3 字节码生成:累加器+寄存器与 peephole

BytecodeGenerator(:1698 主入口)是**累加器+寄存器混合模型**:寄存器线性分配(bytecode-register-allocator.h:37-40),冗余 Ldar/Star/Mov 由 BytecodeRegisterOptimizer 消除(:15-21,官方自述"peephole 层")。属性加载发射带 IC 槽(:5140-5145)。字节码总表约 193 条(bytecodes.h:60 起)。**本 commit 的重要新发现**:二元运算的类型反馈已不进 FeedbackVector,改为**嵌在字节码里的 1 字节操作数 kEmbeddedFeedback**(bytecodes.h:213;bytecode-operands.h:46)——反馈的位置在演进(少一次间接);IC 类槽(load/store/call)仍走编译期 FeedbackVectorSpec 登记(:593,:618-644)+执行期 IC 填形态,供 TurboFan 消费——**反馈向量是分层编译的桥**。

## 2.4 设计动机

1. **惰性解析的工程学**:网页里大量函数永不执行——preparse 只花"语法校验"的钱;"回退重做"保证正确性零妥协;
2. **反馈向量是分层编译的桥**:Ignition 执行期填形态(类型/调用数),TurboFan 读形态做特化——没有它,优化器只能盲猜;
3. **共用模板骨架(PreParser)**:文法只写一遍,建树/不建树两种行为——C++ 模板的教科书用法;
4. **嵌入式反馈**(:213):把高频的二元运算反馈搬进指令操作数——少一次内存间接,即使牺牲"反馈独立存储"的规整。

## 2.5 FAQ

**Q1:V8 是先全量解析吗?**
不是:顶层解析+函数体 preparse;调用才真解析+编译(:2923-2924,:1060)。

**Q2:PreParser 会漏语法错误吗?**
不会(校验完整),但 preparse 路径发现错误时回退全解析(:3118)——错误信息以全解析为准。

**Q3:AST 存在多久?**
一次编译:Zone 分配,字节码生成完 DeleteAll(A 章 Zone)。

**Q4:累加器+寄存器为什么混合?**
累加器省操作数编码(隐式源/目标),寄存器存中间值——编码密度与消冗余的折中。

**Q5:FeedbackVector 何时创建?**
函数第一次执行时(从 FeedbackCell 实例化):B 报告 :618-644。

**Q6:字节码有多少条?**
约 193 条(bytecodes.h:60 起)+SHORT 变体。

**Q7:与 quickjs 字节码的差异?**
quickjs 栈机+66 条 SHORT 变体;V8 累加器+寄存器 193 条+反馈槽——反馈是 V8 的本质增量。

**Q8:编译缓存跨进程吗?**
code cache 序列化存在(编译产物缓存):冷启动优化,细节留扩展卷。

**Q9:eval 的编译路径?**
直接 eval 同步编译;间接 eval 独立——与作用域联动。

**Q10:kEmbeddedFeedback 为什么要嵌字节码?**
(:213):二元运算的反馈只差几位——嵌操作数省 FeedbackVector 槽。

## 2.6 小结与深挖方向

本章结论:**解析与字节码="惰性两层+共用文法模板+反馈向量桥"**。深挖:

3. kEmbeddedFeedback(:213)在 Sparplug 直译的处理;
