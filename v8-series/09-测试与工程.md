## 9.1 natives-syntax 驱动:V8 最独特的手法

`--allow-natives-syntax`(flag-definitions.h:3334,默认关)开启 % 内部函数(runtime-test.cc 2949 行/156 个测试后门):

```js
// 标准三段式(compiler/abstract-equal-oddball.js:12-25)
%PrepareFunctionForOptimization(f);   /* 确保反馈向量 runtime-test.cc:634 */
%OptimizeFunctionOnNextCall(f);        /* 强制优化 :374-419 */
assertOptimized(f);                    /* 断言确实在优化态 mjsunit.js:819 */
```

**assertOptimized/assertUnoptimized**(:784/:819)用 `%GetOptimizationStatus` 的 **23 个状态位**(mjsunit.js:186-210,kMaglevved/kTurboFanned/kInterpreted…)——**黑盒测不到的"优化器内部行为"由此变成一行断言**;分层每级都有探针(isInterpreted :872/isBaseline :880/isMaglevved :899/isTurboFanned :929)。

## 9.5 FAQ

**Q1:%OptimizeFunctionOnNextCall 为什么需要 Prepare?**
(:634):反馈向量必须先建立——直接 Optimize 会缺形态信息。

**Q2:assertOptimized 断言的是什么?**
23 位状态位图(:186-210)中的优化层位——精确到 Ignition/Sparkplug/Maglev/TurboFan。

**Q3:stress 变体为什么能扫时序?**
--gc-interval=500 等 flag 让 GC/编译在固定间隔高频触发(:59-64)——稀有事件高频化。

**Q4:mjsunit.status 的 [FAIL] 是失败吗?**
是已知 bug 的档案(:47-48);修复后自动变"意外通过"报警(同 Git known breakage)。

**Q5:foozzie 的差分原理?**
同一 JS 跑多配置(如不同 GC 模式),输出必须语义一致(v8_foozzie.py:24)。

**Q6:test262 为什么钉版本?**
(DEPS:220-221):语料漂移会让通过率不可比。

**Q7:cctest 为什么不用 gtest?**
自研 TEST 宏(:72-78):历史+对 V8 内部设施(隔离区)的定制。

**Q8:版本号 15.5 对应 Chrome 什么?**
milestone÷10(docs/version-numbers.md:5-11):V8 版本即 Chrome 大版本×10。

**Q9:V8 先于 Chromium 发布意味着什么?**
V8 的 API 变更先落地,Chromium 拉取验证——上游先行。

**Q10:wasm fuzz 怎么生成合法模块?**
结构化生成(test/fuzzer/wasm/compile.cc:12-33):合法语法约束下的随机。
