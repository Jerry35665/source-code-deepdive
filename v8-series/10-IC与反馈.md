# 第 10 章 · IC 与反馈:动态属性访问的静态化

> 基线:commit `c6a1f7c2`。行号以 src/ic/ic.cc、src/ic/accessor-assembler.cc、src/objects/feedback-vector.h 为准。

## 10.0 全景:一次属性加载的 IC 旅程

```
字节码 GetNamedProperty → 反馈槽读 handler → 快路径(map 检查→偏移加载)
  → miss → LookupIterator 全量查找 → 写反馈槽(状态迁移)→ 下次走快路径
四态:UNINITIALIZED → MONOMORPHIC(单 Map) → POLYMORPHIC(≤4 Map 分支) → MEGAMORPHIC(全局 StubCache)
```

状态机迁移总表 IC::SetCache(ic.cc:1000-1059);**实际为 9 态**(globals.h:1896-1915,新增 HOMOMORPHIC/MEGADOM/RECOMPUTE_HANDLER)。槽内容即状态:弱 Map=MONOMORPHIC,WeakFixedArray=POLYMORPHIC,megamorphic 哨兵 Symbol=MEGAMORPHIC(feedback-vector.cc:698-770)。

## 10.1 handler"编译":数据化 handler + CSA 共享机器码

**现代 handler 多为 Smi 位域**(LoadHandler/StoreHandler,handler-configuration.h:28/:259;Kind 枚举 :35-53),不是逐站点生成的代码——AccessorAssembler 用 CSA **预编译一棵分派树**,运行期只换槽内数据。路径:字节码 GetNamedProperty→LoadIC_BytecodeHandler 免栈帧快路径(accessor-assembler.cc:3392-3464)→TryMonomorphicCase 一次弱比较+两次读(:71-102)→HandlePolymorphicCase 倒序扫(map,handler)对(:104-145)→megamorphic 走 TryProbeStubCache(:3355-3388)→全 miss 进 Runtime_LoadIC_Miss(:3456-3463;ic.cc:3238-3270)。

kField handler 核心:解码 StorageOffsetBits→LoadObjectField 偏移加载(:600-631)——map 检查已由单态比较完成。

## 10.2 megamorphic:全局 StubCache

megamorphic 全局 StubCache:主表 2^12+次表 2^10,Entry={key,value,map}(stub-cache.h:34-43,:88-91),**两套不同哈希**(stub-cache.cc:32-56),更新时主表旧条目退休到次表、直接覆盖无失效(:89-119;handler 自验原型链故无需失效,stub-cache.h:15-18)。多态上限 10(flag-definitions.h:3286-3287);同 map+同 handler 重复=无进展→megamorphic(ic.cc:758-779);字典 rehash 直接 megamorphic 防 deopt 循环(:788-793)。

## 10.3 deopt 互动

优化编译时未初始化槽会预埋**立即 deopt**(js-type-hint-lowering.cc:757-772;js-native-context-specialization.cc:2782-2786;js-call-reducer.cc:6451-6472),原因族 InsufficientTypeFeedbackFor*(deoptimize-reason.h:34-56)——**soft deopt**:丢优化代码回解释器重新热身。deopt 结算:重置 interrupt budget+打 was_once_deoptimized 烙印(deoptimizer.cc:1900-1908);烙印=invocation_count_before_stable 写 0xff(feedback-vector-inl.h:259-262)。反馈槽本身不清空,只有调试器 ClearSlots(debug.cc:1960)。**反向通道**:IC 改槽即 NotifyICChanged→按 minimum_invocations_after_ic_update=500 重算 tier-up 预算(ic.cc:334-351;tiering-manager.cc:475-520)。

## 10.4 设计动机

1. **为什么 IC 是自修改代码**:动态语言的属性访问在编译时不可知——IC 把"运行时发现的形态"编码为可执行的快路径 handler,一次 miss 换 N 次快跳;
2. **为什么 megamorphic 要全局 StubCache**:每站点私有 cache 在 megamorphic 态浪费;全局 cache 空间共享,哈希冲突由两表哈希分散;
3. **为什么 feedback 是"分层编译的桥"**:解释器填形态→Sparkplug/Maglev 读形态编译基线→TurboFan 读形态做推测特化——**每一层的优化决策都基于下一层的运行时观察**;
4. **deopt 后预算重置**:was_once_deoptimized 烙印让二次 deopt 的预算更高(更难再优化)——防止"优化→deopt→优化"死循环。

## 10.5 FAQ

**Q1:IC handler 是代码还是数据?**
现代是数据(Smi 位域)+ CSA 预编译的分派树:运行期只换槽内数据。

**Q2:多态上限为什么是 10?**
(flag-definitions.h:3286-3287):超过后收益不抵分支树爆炸——megamorphic 是兜底。

**Q3:megamorphic 后还能优化吗?**
TurboFan 可按"猜测模式"(带守卫)特化,或放弃属性优化走通用路径。

**Q4:deopt 后反馈会清空吗?**
不会:只有调试器 ClearSlots 清(:1960);deopt 只打烙印+重置预算。

**Q5:IC 和内联有什么关系?**
IC 收集的形态(单态/多态)是 TurboFan 内联决策的输入——多态调用点不内联。

**Q6:Sparkplug 会内联 IC 吗?**
会:baseline 代码的字面补丁 call 目标(:844-916,:970-994)。

**Q7:validity cell 是什么?**
原型链有效性 cell(map.cc:2599-2656):原型一改 O(1) 全体失效——handler 的"撤销按钮"。

**Q8:rehash 为什么直接 megamorphic?**
(:788-793):字典 rehash 后 map 变了,旧 handler 全失效——防 deopt 循环。

**Q9:IC 状态会"降级"吗?**
UpdatePolymorphicIC 只加不减(:731-842);GC 可清死 map 的弱引用间接降级。

**Q10:最小 invocations_after_ic_update 为什么是 500?**
(:334-351):IC 改槽后的冷却期——防止刚更新的 IC 又被频繁重算。

## 10.6 小结与深挖方向

本章结论:**IC="四态状态机+CSA 预编译分派树+反馈向量桥接分层编译"**。深挖:

1. megamorphic StubCache 在多租户(高 Map 多样性)的冲突率;
2. polymorphic 上限 10(:3286)对 React 高阶组件的属性访问影响;
3. IC→tiering 预算反馈环(:334-351)的稳定性;
4. was_once_deoptimized 烙印在 AOT 快照的持久化;
5. baseline 字面补丁(:844-916)与 OSR 的交互。
