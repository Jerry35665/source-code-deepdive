# 第 03 章 · 订阅匹配:subject 通配、sublist 与队列组

> 基线:commit `8f3f31b0`。核心文件 server/sublist.go(1744 行)。

## 3.0 全景:trie 与一次 Match

```
订阅 foo.*.bar 与 foo.> 的树(level/node 交替,pwc/fwc 是每层通配指针):
root{nodes:{foo}} → foo{next level} → pwc(*):next{nodes:{bar}}→bar{psubs:S1}
                                    → fwc(>){psubs:S2}
Match("foo.baz.bar"):i=0 字面量下沉 foo → i=1 先收 fwc(S2)、再递归 pwc 分支收 S1、
  字面量 baz 不存在 → l=nil → 结果 psubs=[S1,S2](sublist.go:771-796)
```

通配规则:`*` 单层、`>` 必须尾 token,二者须独占 token——`foo.a*b` 是合法字面量,走普通哈希槽(isValidSubject,sublist.go:1205-1246)。`>` 尾部限定使 fwc 检查退化为"进层时看一眼常量指针",近零开销。

## 3.1 两级缓存:命中率是吞吐第一指标

L2(每账号共享):`cache[subject]*SublistResult`,上限 1024,超限后台随机清到 256(CAS 单飞清扫);命中即 O(1) 返回**共享**结果。L1(每连接):`c.in.results` + genid 时代戳——genid 不变直接用本地缓存,连 L2 的锁都省掉(client.go:4465-4494)。未命中走树时若启用缓存则**升级写锁**做遍历+写缓存(防 match-store 竞争,并发 miss 串行,sublist.go:596-605);空结果用共享单例 emptyResult,连分配都省。

**失效按波及面分级**:订阅→深拷贝"修补"缓存条目(热点 subject 不抖动);退订→作废键(下次 Match 重建);批量退订(连接关闭)→整表重建;权重更新→仅作废+genid++(sublist.go:490-525,946-961)。极高频 churn 场景可用 NoSublistCache 整体关掉 L2 退回纯树遍历。

## 3.2 队列组:匹配层分桶、投递层选一

`node.qsubs[队列名]成员集合`——**队列组在匹配层就聚合**。远端队列订阅按 `sub.qw` 权重**影子复制**多次塞进桶里(sublist.go:741-746):匹配结果自身编码了选择概率。投递层随机起点环形选一;消息来自 ROUTE 时先过滤出本地成员,远端只留兜底 rsub,LEAF 与 ROUTER 候选间掷硬币(client.go:5505-5533)。队列兴趣的传播权重由 route 协议携带并在聚合侧写入 nsub.qw(route.go:2625-2636)。

## 3.3 兴趣快速判定

`HasInterest/NumInterest` 走 matchLevelForAny:遇到 fwc 节点立即返回 true,不继续收集(sublist.go:798-846)。调用方遍布"只关心有没有"的路径:发布主路径无兴趣直接短路丢弃(client.go:4500)、gateway interest-only 逐条决定转发、JetStream 判断 deliver subject。**漏判丢消息、误判退化成广播**——兴趣统计必须精确。

## 3.4 设计动机

1. **树而非哈希**:通配订阅无法以全串为键;trie 让 `*`/`>` 成为每层的指针,复杂度只随主题长度增长;
2. **两级缓存**:L1 消除热点连接重复加锁,L2 连接间共享;genid 让失效只需一次原子加法;
3. **`>` 限尾**:中间 `>` 会让每层都要回溯"匹配零或多层",线性递归结构不成立;
4. **队列组匹配层聚合**:影子副本让选择概率编码进匹配结果,投递层只需随机下标;
5. **失效分级**:按改动波及面选择最小正确动作,高频 churn 打不穿命中率。

## 3.5 FAQ

**Q1:百万订阅会变慢吗?**
不会:匹配代价只与主题长度和分支相关;缓存命中时退化为一次 map 查找。

**Q2:`>` 为什么只能在尾部?**
其语义是"剩余全部层",中间出现则每层需要回溯,树的线性遍历不成立。

**Q3:同一 subject 反复发布每次都走树吗?**
不:L1/L2 命中直接返回共享结果;同一次盲读内还有 readCache。

**Q4:退订会打断其他订阅者的缓存吗?**
字面量退订只删该键;通配退订删被命中的键;都是作废重建,不做搬移。

**Q5:队列组的负载均衡策略?**
纯随机起点环形选择;权重经影子副本表达;无优先级/最少连接策略。

**Q6:并发 Match 安全吗?**
RWMutex+原子计数;未命中升级写锁遍历;统计走 atomic。

**Q7:命中率怎么看?**
SublistStats.CacheHitRate,/varz 的 subsz 聚合(monitor.go:1047-1068)。

**Q8:`foo.a*b` 是通配符吗?**
不是:通配符须独占 token,它按字面量走哈希槽。

**Q9:断开连接的退订怎么优化?**
RemoveBatch 整体关缓存后重建空表——"quick and dirty"但实测最优。

**Q10:谁能用反向匹配?**
订阅权限检查:新 SUB 用 allow 表 ReverseMatch 反查(sublist.go:1665-1728)。

## 3.6 小结与深挖方向
