# 第 01 章 · 全景架构:一个 client struct,七个 kind

> 基线:commit `8f3f31b0`(版本 2.15.0-dev,const.go:69)。

## 1.0 全景:对象层次与三层网络

```
Server(server.go:169)
├ CLIENT :4222(数据面)      ┐
├ LEAF   :7422(数据面边缘)  ├ 一切连接都是 *client,靠 kind 分型(client.go:45-60)
├ ROUTER (cluster 端口)     │ 对外四种 + 对内三种(SYSTEM/JETSTREAM/ACCOUNT 无 socket)
├ GATEWAY(gateway 端口)     ┘ MQTT/WS 只是 CLIENT 的扩展类型(client.go:70-79)
└ monitor :8222(HTTP)+ $SYS 事件(events.go:49-72)
一条消息:readLoop(client.go:1467)→parser(parser.go:17)→权限→acc.sl.Match(sublist.go:532)
        →deliverMsg(client.go:3778)→对方 writeLoop(client.go:1376)flushOutbound
```

README 一句话定位:"simple, secure and performant communications system"(README.md:5),CNCF 项目、40+ 客户端语言、可跑树莓派。与 Kafka 一句话差异:Kafka 是分布式提交日志,持久化+拉取+offset 重放;NATS 核心是主题总线,at-most-once、broker 不落盘——持久化是可选的 JetStream(server.go:2443-2462 显式开启)。

## 1.1 启动 14 步:监控先于一切

`main.go` 极薄(98-135):ConfigureOptions→NewServer→Run→WaitForShutdown。真正的顺序在 `Start()`(server.go:2267-2580),关键步骤:写 PID(2374)→建 $SYS 账号(2382)→**启动监控 HTTP(2394,注释明说"先于其他子系统,便于启动期观测")**→JetStream(2443)→**startGateways 先于 route(2514,需先解析 gateway 地址供 INFO 通告)**→WebSocket/Leaf/MQTT→StartRouting 等 client 端口就绪信号(2556)→AcceptLoop 阻塞(2574)。关闭链 Shutdown(server.go:2588)恰好把 Start 反着走一遍——启动与关闭共用同一张监听器清单。

## 1.2 每连接两个 goroutine,写侧条件变量驱动

accept 循环每连接起一个 goroutine 执行 createClient,末尾拉起**两个**常驻 goroutine(server.go:3579-3582):readLoop 阻塞读 socket 喂 parser,发布/订阅/转发全在读 goroutine 内同步完成;writeLoop 平时挂在 `out.sg.Wait()` 条件变量上休眠,被唤醒后 `flushOutbound` 把待写缓冲折叠(`collapsePtoNB`)用 writev 一次写出(client.go:1729-1760)。**顺路冲刷**:发布者的 readLoop 把消息排进订阅者写缓冲后记入 pcd 集合,攒一批按时间预算就地冲刷,超预算才异步唤醒(client.go:1423-1455)——小消息高频场景省一轮 goroutine 唤醒。

与 Envoy 对照:Envoy 用 C++ 必须自己做事件循环,NATS 用 Go 把并发外包给 runtime——连接数即 goroutine 数,代码是顺序过程无回调地狱;默认 64K 连接上限(const.go:105)下完全够用。

## 1.3 kind 不只是枚举

kind 决定 IO 参数与集群行为:`initClient` 按 kind 快照写超时策略——CLIENT 默认 Close(写卡即断),ROUTER/GATEWAY/LEAF 默认 Retry(client.go:733-750,"不能因为一次写堵塞就拆掉集群链路")。慢消费者判定也只对 CLIENT 生效(见 02 章)。ROUTE 还能按账号建池(`accRoutes`,默认池 3 条,高吞吐账号独占集群链路)。

## 1.4 设计动机

1. **每连接两 goroutine**:读写解耦让慢消费者不阻塞生产者;close 竞态收敛到 writeLoop 单点收尾;
2. **文本协议**:telnet 可调试、抓包可读、40+ 客户端零门槛;parser 在 CPU 上不构成瓶颈(02 章);
3. **单二进制 10 依赖**:边缘部署物就是一个静态文件;监控内嵌,运维面一个进程一个端口;
4. **client/route/gateway/leaf 四层拓扑**:单机→集群→超级集群→多租户边缘,同一 client 抽象+kind 常量表达;
5. **监控先于其他子系统**:分布式系统的排障窗口往往就在启动那几秒。

## 1.5 FAQ

**Q1:连接类型到底几种?**
七个 kind 常量:CLIENT/ROUTER/GATEWAY/SYSTEM/LEAF/JETSTREAM/ACCOUNT(client.go:45-60);MQTT/WS 是 CLIENT 扩展类型。

**Q2:内嵌 NATS 怎么用?**
`InProcessConn()` 返回 net.Pipe 直连绕过 TCP(server.go:2886-2897)。

**Q3:为什么 gateway 比 route 先启动?**
route 的 INFO 要通告 gateway 的 host:port,先启动才能解析(server.go:2514 注释)。

**Q4:accept 出错会崩吗?**
临时性错误按 10ms→1s 指数退避重试(server.go:2900-2908),变慢而不是崩溃。

**Q5:一条消息的完整路径?**
readLoop→parser→权限→Match→deliverMsg→queueOutbound→(顺路冲刷或 writeLoop)。

**Q6:监控有哪些端点?**
/varz /connz /routez /gatewayz /leafz /subsz /jsz /healthz 等(server.go:3044-3061),一行一个 handler。

**Q7:版本怎么注入?**
VERSION 常量+运行时 debug.ReadBuildInfo 读 vcs.revision 前 7 位(const.go:54-65)。

**Q8:配置格式是什么?**
自有 JSON 超集语法,自研 lexer/conf/parse.go:1-8,不选 YAML 为了零依赖。

**Q9:$SYS 事件是什么?**
运维事件就是 PUB 到 $SYS 主题(connect/disconnect/lameduck 等),给程序消费,HTTP 给人看。

**Q10:启动完成如何判定?**
`close(s.startupComplete)`(server.go:2571);healthz 端点可查询。
