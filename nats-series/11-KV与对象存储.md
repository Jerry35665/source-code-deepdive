# 第 11 章 · KV、ObjectStore 与 Micro:JetStream 之上的三层(卷二)

> 基线:commit `8f3f31b0`。卷一报告 E 讲了 JetStream 本身;本章讲架在其上的 KV/ObjectStore/Micro。**核心勘误**:nats-server 里没有任何 $KV/$OBJ/$SRV API handler——KV 与 ObjectStore 是 nats.go 客户端的"物化视图"库,Micro 是纯客户端规范;服务端做的是原语正确、语义中立。

## 11.0 全景:两层 abstraction 的布局

```
KV:bucket=stream,key=subject;"最新值"靠 per-subject 保留
  put=常规 PUB;get=$JS.API.DIRECT.GET.<stream>.<key>(注释点名 KeyValue,raw 直返无 JSON)
  watch=普通 consumer(marker 也是普通消息);TTL=Nats-TTL 头+存储层时间轮
ObjectStore:bucket=meta 流+chunk 流两条普通流(布局是客户端约定)
  meta 小而频繁 CAS 更新(Expected-Last-Subject-Sequence);chunk 大而只追加
Micro:服务端零实现——$SRV 全仓 0 命中;路由/负载均衡/版本协商用 subject 通配
  +request-reply 即完备,放服务端只会引入第二个 API 面
```

## 11.1 KV:服务端为它专门加的特性

服务端"懂 KV"的证据在流选项:AllowDirect("E.g. KeyValue")/MirrorDirect/DiscardNewPer(per-subject 丢弃)/MaxMsgsPer(每 key 历史)。**get 走 DIRECT.GET**:stream 与 key 编进主题——免 JSON 编解码直返原始消息,权限直接复用核心 NATS 的 subject 级授权;队列组让 mirror 追平后也可择优应答。put 的 CAS 基础是 `Nats-Expected-Last-Subject-Sequence` 头(不匹配报 WrongLastSequence);delete 是 put nil(`KV-Operation: PURGE` 值有服务端感知,触发 rollup sub 清场);watch 零专用代码=consumer。**KV 语义全部约化为流参数**——一份存储引擎、一套 Raft 复用所有 view(注释自称 materialized views)。

## 11.2 TTL 与删除 marker:存储层的点睛之笔

per-message TTL(`Nats-TTL` 头,支持 never)进**持久化时间轮 thw.db**(重启恢复回填),到期删除。点睛:当一个 key 的**最后一条**消息因 TTL/MaxAge 消失时,存储层不是默默删除,而是"提案"一条墓碑消息(带 Nats-Marker-Reason+Nats-TTL+`Nats-Rollup: sub`)经 pmsgcb 回流发布路径——**集群模式下进 Raft 提案,watcher 天然看到删除事件**;marker 自己的寿命=SubjectDeleteMarkerTTL。SDM 配置下启动恢复不走静默批量过期,坚持逐条提案——"过期即事件"在集群与重启后仍成立。

## 11.3 ObjectStore 与 Micro

ObjectStore 的 meta/chunk 两流布局、chunk 大小、SHA256 digest 全是客户端约定;服务端只提供积木:meta 的 CAS、chunk 顺序性(流序号单调)、直读(批量 ≤1024,无服务端聚合——digest 校验必须发生在数据端,聚合不省带宽)、purge 原语(filter/keep)。**为什么存两流**:meta 是小而频繁 CAS 的热数据,chunk 是大而只追加的冷数据;分流后保留策略/TTL/清理互不牵连。Micro 纯客户端规范:服务发现/调用就是核心 NATS 的 request-reply,放服务端违背"机制在服务端、策略在边缘"的一贯取舍。

## 11.4 设计动机

1. **KV 建在 stream 上**:历史/每 key 限制/复制/权限全部约化为流参数;一份引擎一套 Raft 复用所有 view;
2. **get 走 DIRECT.GET**:免编解码低延迟+subject 级安全+mirror 择优;
3. **删除用 rollup marker**:清场与通知合二为一;TTL 过期由存储层提案进 Raft;
4. **TTL 做进存储层时间轮**:key 过期不依赖客户端在线;持久化+重启恢复;
5. **watch 用 consumer**:回放起点/按 key 过滤/流控全是现成 ConsumerConfig 字段,零新增协议;
6. **Micro 放客户端**:主题命名约定即可解决,服务端只留机制不留策略。

## 11.5 FAQ

**Q1:服务端有 $KV API 吗?**
没有:$KV 只出现在 deny 列表与 domain 映射;操作复用 $JS.API.STREAM.*/CONSUMER.*。

**Q2:KV get 为什么快?**
DIRECT.GET 直返原始消息,无 JSON 编解码;流与 key 编进主题享受 subject 级权限。

**Q3:key 不存在返回什么?**
404 Message Not Found 裸头响应(stream.go:6333)。

**Q4:KV 的 CAS 怎么做?**
Nats-Expected-Last-Subject-Sequence 头;不匹配报 WrongLastSequence。

**Q5:delete 后 watch 能看到吗?**
能看到:墓碑 marker 是写进流的普通消息;get 则返回 404(get/watch 分工)。

**Q6:TTL 到期谁删?**
存储层时间轮(thw.db 持久化);SDM 配置下过期走 marker 提案进 Raft。

**Q7:ObjectStore 的 meta 流为什么单独一条?**
小而频繁 CAS 的热数据与只追加的冷 chunk 分流,保留策略互不牵连。

**Q8:大文件 get 服务端聚合吗?**
不:直读单条/批量 ≤1024,chunk 拼接与 SHA256 校验在客户端。

**Q9:Micro 有服务端代码吗?**
零:$SRV 全仓 0 命中;它是 nats.go micro 包的客户端规范。

**Q10:跨 domain 访问 KV 怎么寻址?**
照旧发 $KV.>,服务端映射表补 domain 前缀($JS.<domain>.API.$KV.>→$KV.>)。

## 11.6 小结与深挖方向

本章结论:**三层 abstraction="KV 语义约化为流参数+TTL 存储层时间轮+SDM 墓碑进 Raft;服务端机制中立,策略在客户端"**。深挖:

1. DIRECT.GET 批量/多 key 的响应头模板与 EOB 标记;
2. mirror 的 dgetCaughtUpThresh=10 追平阈值;
3. SubjectDeleteMarkerTTL 对普通消息 TTL 的最小值抬升;
4. SDM 的 2 秒去重窗口;
5. MaxMsgsPer=-1(不限)的归一化与 pedantic 报错。
