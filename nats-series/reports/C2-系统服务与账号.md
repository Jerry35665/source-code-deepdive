## 1. 内部客户端:无 socket 的 client 复用

kind 常量里 CLIENT=0、ROUTER=1、GATEWAY=2、SYSTEM=3、LEAF=4、JETSTREAM=5、ACCOUNT=6,其中后三者被 `isInternalClient` 归为内部客户端(`client.go:44-65`)。`createInternalClient` 不建任何网络连接,只构造 `client{srv, kind, opts: internalOpts}` 并设 `echo=false`、`headers=true`、`noReconnect`(`server.go:1934-1948`;`internalOpts` 在 `client.go:711`),再包出三个语义化包装(`server.go:1919-1931`)。它与真实连接共用同一套协议处理:订阅走 `processSubEx`,发布走同一 `pubArg` 结构——"内部走 client 抽象"即由此而来。

```go
// server.go:1934-1948(摘录)
func (s *Server) createInternalClient(kind int) *client {
    if !isInternalClient(kind) {
        return nil
    }
    now := time.Now()
    c := &client{srv: s, kind: kind, opts: internalOpts, msubs: -1, mpay: -1,
        start: now, last: now}
    c.initClient()
    c.echo = false
    c.headers = true
    c.flags.set(noReconnect)
    return c
}
```

系统账号在 `setSystemAccountWithClaims` 中完成挂接:`s.sys = &internal{...}` 初始化 sendq/recvq/recvqp 三个 IPQueue、replies 映射、shash 等(`server.go:1860-1880`,字段定义 `events.go:121-145`);随后 `s.sys.client.registerWithAccount(acc)` 把 SYSTEM client 记入 $SYS 账号连接表(`server.go:1884`;内部客户端豁免"已关闭连接"检查,`client.go:894-897`),`addSystemAccountExports(acc)` 装配 $SYS 导出(`server.go:1886`),最后拉起三个循环(`server.go:1890-1895`):

- `internalSendLoop`(`events.go:499-620`):从 sendq 批量取 `pubMsg`,补齐 ServerInfo(序号、版本、tags、JS 能力 flags),锁住目标 client 按 PUB 语义填 `c.pa.subject/reply/szb` 写出;支持 gzip/snappy 压缩,载荷可为 string/[]byte/任意 JSON 可序列化对象。
- `internalReceiveLoop`(`events.go:480-496`):消费 `inSysMsg`(`events.go:112-119`)并回调 `m.cb`;recvqp 专供 STATZ/Ping,与普通事件分流。

发送入口分两层。发到 $SYS:`sendInternalMsg` 只入队(`events.go:763-768`),另有 `sendInternalMsgLocked`/`sendInternalResponse`/`c.sendInternalMsg`(后者绕 no-echo,`events.go:755-759,771-777,782-795`)。发到任意账号:`sendInternalAccountMsg(WithReply)` 临时把 client 换成目标账号的 `a.internalClient()`(`events.go:708-737`),消息因此走**该账号** sublist——这是 latency 结果、应答回执等落点的关键。`newSendQ` 还会另建一个 `noIcb=true` 的 SYSTEM client 做出栈优化(`sendq.go:36-51`)。

## 3. $SYS 的服务化:自动导出、自动导入与请求应答

`addSystemAccountExports` 在 $SYS 上自动导出四类服务(`events.go:1597-1652`):`$SYS.REQ.ACCOUNT.*.CONNZ` 与 `...STATZ` 用 `addServiceExportWithResponseAndAccountPos(..., Streamed, nil, 4)`(`events.go:1599-1615`)——Streamed 应答、`accountPos=4` 把请求方账号名"夹"进主题;另有 `$SYS.DEBUG.SUBSCRIBERS`(`events.go:84`)与用户自查询 `$SYS.REQ.USER.*.INFO`(`events.go:77`,`events.go:1617-1633`)。

反向地,`registerSystemImports` 给每个普通账号注入到 $SYS 的内部 service import(`events.go:2380-2407`):`$SYS.REQ.ACCOUNT.PING.CONNZ` 与 `$SYS.REQ.SERVER.PING.CONNZ` 都映射到 `$SYS.REQ.ACCOUNT.<本账号>.CONNZ`,STATZ 同理,再加用户自查询映射。关键在 `internal=true`:`addServiceImportWithClaim` 以此跳过 `checkServiceImportAuthorized` 授权检查——否则会陷入"先有授权才能装配、先装配才有授权"的引导悖论(`accounts.go:1670-1682`)。claim 更新则由 `accountClaimUpdate` 处理(`events.go:1647`)。`enableAccountTracking` 对每个新账号发首条 CONNS 请求开启统计(`events.go:2415-2424`)。

请求-应答的接收端是两条机制:

- 定向回包:`newRespInbox` 生成 `$SYS._INBOX.<shash>.<rand62x8>`(`events.go:73,2996-3010`);`initEventTracking` 订阅通配 `$SYS._INBOX.<shash>.*`(`events.go:1196-1211`),`inboxReply` 查 `s.sys.replies` 表把回包分发给具体回调(`events.go:2979-2988`)。集群内 `$SYS.REQ.SERVER.PING.*`(`events.go:68`)的应答由此归位。
- 账号直查:`$SYS.REQ.ACCOUNT.<acc>.CONNZ/STATZ` 经上述自动 import 进入各账号,外部监控端可直接发起;`$SYS.REQ.ACCOUNT.NSUBS` 广播各服务器再聚合(`events.go:81,3180`);claim 查找走 `$SYS.REQ.ACCOUNT.%s.CLAIMS.LOOKUP`(`events.go:43`)。

## 4. service import 运行时:影子订阅、改写与应答回流

`addServiceImport` 建 `serviceImport`(`accounts.go:166-188`)。若 `to` 含通配且异于 `from`,先 tokenize 再用 `NewSubjectTransformStrict(to, transformTokenize(from))` 造反向 transform 并 `reverse()`,得到按实例映射的 `si.tr`(`accounts.go:2184-2204`)。随后 `addServiceImportSub` 以 `a.ic`(ACCOUNT client)为宿主,把 `si.from` 插进**请求方账号** sublist:

```go
// accounts.go:2276-2291(摘录)

    c.pa.delivered = c.processServiceImport(si, acc, msg)
}
sub, err := c.processSubEx([]byte(subject), nil, []byte(sid), cb, true, true, false)
...
a.updateLeafNodes(sub, 1)
```

`processSubEx(..., noForward=true, si=true, rsi=false)` 对发布路径而言只是 A 账号 sublist 里一条带 icb 的普通订阅,在 `processInboundClientMsg` 的 `acc.sl.Match` 之后零拷贝触发——这就是 shadow subscription 的运行时本体(`accounts.go:2261-2294`)。末尾 `updateLeafNodes` 主动向叶子传播兴趣,弥补"叶子引流入站消息但不回发 SUB"的缺口(`accounts.go:2286-2290`)。

`processServiceImport`(`client.go:4860-5140`)的骨架:

- GW/ROUTE 上的非应答 import 直接忽略;用 `c.pa.psi` 检测 import 链环(`client.go:4863-4873`)。
- 有 reply 时 `setupResponseServiceImport` 建应答 import(`addRespServiceImport`,`accounts.go:2667`)并把 reply 改写为新应答主题(`client.go:4905-4921`);唯 `$JS.ACK` 前缀例外,以免破坏跨账号 pull 消费(`client.go:4907`)。
- 逐实例映射与账号映射叠加(`client.go:4931-4949`);按 share 策略注入 `Nats-Client-Info` 头,leaf 场景以本地认证身份覆盖转发值(`client.go:5010-5016` 及其上文)。
- 最后带 `pmrMsgImportedFromService` 标志,在 **siAcc(B 账号)** 上 `sl.Match(to)` 并 `processMsgResults` 投递(`client.go:5029-5095`)。
- 回收:未投递、Singleton 应答或 EOF(`\r\n`)时移除应答 import;追踪未发出则抑制移除(`client.go:5107-5117`)。

## 5. subject 映射运行时:两端执行点

账号映射只在两个运行时点执行。**发布端**:仅当 `kind == CLIENT|LEAF` 且账号 `hasMappings` 时,解析器在 MSG 收尾态调 `c.selectMappedSubject()` 改写 `c.pa.subject`(`parser.go:517-527`;readcache 标志在账号变更/重载时维护,`client.go:487,1542-1550`)。`Account.selectMappedSubject` 先精确后子集匹配,支持按集群覆盖(`cdests`)与权重随机分流,单目的地 100% 走快路径(`accounts.go:951-1029`)。所谓 "mapping_token" 并无同名符号:令牌替换即 `$1..$9`/`{{wildcard(n)}}`,由 `subjectTransform` 的 `dtokmftypes`/`dtokmftokindexesargs` 承载(`subject_transform.go:61-68`);partition/split/slice/left/right/random 函数族的正则与类型见 `subject_transform.go:24-48`,partition 用 FNV-32 对桶数取模(`subject_transform.go:469-482`)。**投递端**:service import 内 `si.tr.TransformSubject` 与 `siAcc.selectMappedSubject` 先后作用(`client.go:4931-4949`);stream import 的影子订阅在 `processMsgResults` 重算投递主题 `dsubj`,且 `pmrMsgImportedFromService` 消息不得再经 stream export 外泄形成回环(`client.go:5380-5415`)。MQTT 三处发布点同样接了该钩子(`mqtt.go:2434,3923,4284`)。

## 7. 账号的统计与事件

连接级计费事件按账号发布:`accountConnectEvent`/`accountDisconnectEvent` 组装 `ConnectEventMsg`/`DisconnectEventMsg`(TypedEvent 带 type/id/timestamp,`events.go:470-477`)后发往 `$SYS.ACCOUNT.<acc>.CONNECT|DISCONNECT`(`events.go:2573-2679`;主题 `events.go:49-50`)。账号活连接数走 `$SYS.ACCOUNT.<acc>.SERVER.CONNS`(旧主题 `$SYS.SERVER.ACCOUNT.<acc>.CONNS` 兼容保留,`events.go:58-59`,双发点 `events.go:2561`)。

STATZ 心跳由 `startStatszTimer` 周期驱动(`events.go:1148`),`STATZ` handler(`events.go:1428-1462`)对 `$SYS.REQ.ACCOUNT.PING.STATZ` 的应答经 recvqp 优先处理(注册 `events.go:1464-1466`)。订阅数查询 `$SYS.REQ.ACCOUNT.NSUBS` 由 `nsubsRequest` 应答(`events.go:81,3180`);CONNZ 支持按账号过滤(`events.go:1383-1390`)。远端服务器视图为防"失联僵尸"设了双阈值:正常心跳间隔 `statsz`,孤儿判定 `orphMax = 5*eventsHBInterval`,超时即模拟其离开(`server.go:1872-1874` 处初始化;清扫循环 `events.go:837-849`,启动 `events.go:1157`)。

## 8. 内部请求的权限豁免面

豁免不是白名单放行,而是**检查根本不触发**:发布权限仅当 `c.perms != nil`(`client.go:4385-4393`),而 perms 只装在 CLIENT/LEAF 上;订阅权限要求 `kind == CLIENT`(`client.go:3087-3105`)。显式保留面:CLIENT 禁发 `$NRG.`(非系统账号,`client.go:4395-4400`)与保留应答(`client.go:4403`);非 $SYS 账号默认拒绝 `$JS.API.>`/`$KV.>`/`$OBJ.>`(`jetstream_api.go:371-372`),须经 service import 进入;CLIENT 被 deny 掉 `$SYS.REQ.USER.AUTH` 以防伪造 callout 请求(`auth.go:761`);内部 import 凭 `internal=true` 免授权(`accounts.go:1682`)。

## 9. $JS.API 与 $SYS.REQ 的分发差异

两者都以订阅挂在 $SYS 账号 sublist 上,后续分道:

| 维度 | $JS.API(`jsDispatch`) | $SYS.REQ(系统事件) |
| --- | --- | --- |
| 订阅 | `sysSubscribe("$JS.API.>")`(`jetstream_api.go:1107`) | `sysSubscribe` + `noInlineCallback`(`events.go:2811`) |
| 匹配 | `js.apiSubs` 二次精确匹配(`jetstream_api.go:951`) | 直接按订阅主题命中 |
| 并发 | IPQueue + 至多 16 个长驻 goroutine(`jetstream_api.go:1093-1105,1039`) | recvq 单消费者串行(recvqp 供 STATZ) |
| 账户限制 | 凭 `Nats-Client-Info` 头强制(`jetstream_api.go:953-972`) | 调用方即服务器/监控端 |
| 回包 | `sendAPIResponse` 服务导出应答 | `$SYS._INBOX` + replies 表(§3) |
| 过滤 | meta 指令(stepdown/remove/rescue)回主流程(`jetstream_api.go:943-949`) | 无 |

JS 在 $SYS 上的导出(`jetstream_api.go:1111`)让跨账号 API 成为 service import;`setupJetStreamExports` 还把 `$JS.<domain>.API.>` 用系统账号 `AddMapping` 映射到 `$JS.API.>`,使隔离域可寻址(`jetstream.go:638-654`);普通账号的自动 import 见 `jetstream.go:807-814`。

```go
case errStr = <-respCh:
    if authorized = errStr == _EMPTY_; !authorized {
        s.Warnf(errStr)
    }
case <-time.After(authTimeout):
    s.Debugf(fmt.Sprintf(
        "Authorization callout response not received in time on account %q", acc.Name))
}
```

`processReply` 解密、校验 `AuthorizationResponseClaims`,成功即 `RegisterNkeyUser` 把内部用户绑到目标账号(`:300-306`);超时即拒绝。应答订阅经 `defer acc.unsubscribeInternal(sub)` 清理(`:331-334`)。

## 11. mapping 与 import/export、leaf 的组合

- **通配 service import**:transform 在注册期预生成并缓存为 `si.tr`(`accounts.go:2184-2204`),运行时逐消息执行(§4);导入方账号映射在其后再叠一层(`client.go:4946`)。
- **stream import 影子订阅**:客户端订阅命中 import 时,`addShadowSubscriptions` 在**导出方**账号 sublist 插入改写主题的影子订阅,动态/重叠场景用 `im.rtr`(tr 的 reverse)反算主题,并按 leaf/hub 决定远端传播(`client.go:3194-3360`);叶子/路由转发时按影子重写主题(`client.go:3638-3643`)。
- **leaf**:service import 订阅建成后 `updateLeafNodes(sub, 1)` 主动下发(`accounts.go:2286-2290`);非 hub 叶子的影子订阅只在本服务器的 leaf 连接上传播(`client.go:3351-3360`)。
- **网关**:`_R_` 应答主题在 GW 上按服务应答短路,不向远端集群扩散普通兴趣(`gateway.go:3040-3057`);GW/ROUTE 上禁止非应答 service import 触发(`client.go:4863-4866`)。
- **JS domain**:域前缀 API 靠系统账号上的静态映射寻址(§9)。

## 12. 运行时边界与坑

- **echo=false 的两面性**:内部客户端 `c.echo=false` 意味着自己的发布不会回流自己的订阅;跨 client 上下文发内部消息须用 `c.sendInternalMsg`(带原 client)绕过 no-echo,否则同机回环请求会收不到自己的消息(`events.go:782-795`)。
- **关停期发送**:系统关停时 `sendInternalAccountMsgWithReply` 对 `isShuttingDown` 静默返回 nil,避免关停日志风暴(`events.go:713-724`)。
- **应答 import 的生命周期**:未投递、Singleton 应答、EOF 即回收;但追踪未实际发出(`didSendTL==false`)时强制保留,等待远端 M2 配对,否则指标丢失(`client.go:5107-5117`)。
- **`$JS.ACK` reply 直通**:跨账号 pull 消费的 ACK 主题不改写,原样透传(`client.go:4907-4913`);这是 processMsgResults 中 `remapped` 重写逻辑的配对约束(`client.go:5271-5278`)。
- **响应阈值**:可对导出设 `SetServiceExportResponseThreshold`,过期应答由 `checkExpiredResponses` 定期清扫(`accounts.go:2627,2570-2582`)。
- **叶子身份不信任转发头**:leaf 场景 `Nats-Client-Info` 一律以本地认证身份重建,仅保留原 Reply 等必要字段(`client.go:4975-4990` 一带)。

## 13. 设计动机

1. **内部走 client 抽象**:SYSTEM/JETSTREAM/ACCOUNT client 无 socket 却复用 `processSub/processMsgResults/deliverMsg` 全链路,内部消息与网络消息共享同一套匹配、账号、统计与头处理语义(§1);新功能(头、映射、追踪)自动对内部消息生效,不需要第二套代码路径。
2. **发送序列化 + 接收分流队列**:internalSendLoop 统一盖 ServerInfo 戳与压缩;noInlineCallback 把 JSON 解析从 route/gw 热路径挪进 recvq,STATZ/Ping 再单列 recvqp,防大响应饿死普通事件(§1、§2)。
3. **service import 影子订阅 + `_R_` 通配应答**:import 订阅让跨账号请求"零分支"进入正常投递;一条 `_R_.<前缀>>` 订阅服务全部在途请求,免去逐请求 SUB/UNSUB 的集群传播;`.T` 后缀让遥测精准回源(§4、§6)。
4. **映射在运行时执行**:partition/random/权重/集群覆盖依赖每消息上下文,无法预编译;发布端以账号级 `hasMappings` readcache 标志把成本隔离到受影响账号,service import 端则预编译 `si.tr` 复用(§4、§5)。
5. **$SYS 也走 NATS**:监控/计费做成系统账号上的服务与事件流,运维端用一个普通订阅者即可消费,服务器无需旁路传输;`accountPos`/`_R_` 复用同一应答机制,自动 import 免授权解决引导悖论(§3)。
6. **callout 独立成服务**:认证决策委托给账号内的普通应用,服务器只做 JWT 结果校验与 nkey 注册;一次性 nkey + AuthTimeout + 可选加密把信任面收窄到单次请求,且天然适用于 leaf(§10)。
7. **JS 与 $SYS 分发路径不同**:JS API 高频且需账户限制,故二次匹配 + 并发池;$SYS 事件低频且要保序聚合,故串行队列——同一 sublist 基础设施承载两种负载画像(§9)。
