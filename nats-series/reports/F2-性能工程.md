## 0. 热路径分配总图:一条 PUB 从读到写的完整生命周期

```text
 readLoop (per-conn goroutine)                    写侧 (writeLoop goroutine)
 ─────────────────────────────                    ─────────────────────────
 socket ──read──▶ b []byte (自适应 64B~64KB)       out.sg.Cond 唤醒 (client.go:355)
                   │  零拷贝:解析不复制            writeLoop (client.go:1376)
                   ▼                               └ flushOutbound (client.go:1729)
            parse() 状态机                             └ collapsePtoNB (client.go:1719)
                   │  split 才落 scratch[4KB]              │  非WS:直接引用 out.nb (零拷贝)
                   ▼  (parser.go:34,1205)                  ▼
            processInboundClientMsg                  wnb.WriteTo(nc) writev
                   │  L1 命中?原子genid比对              │  一次最多 1024 向量×64KB
                   ├─ 是▶ in.results (零分配)            ▼
                   ├─ 否▶ sl.Match:RLock查缓存          nbPoolPut 逐帧归还
                   │     miss 才写锁+回填                ├─ ≤512B → nbPoolSmall
                   ▼                                     ├─ ≤4KB  → nbPoolMedium
            processMsgResults / deliverMsg               └─ 其余  → nbPoolLarge
                   │  mh 头写进 msgb[1KB](栈内嵌)         (client.go:371/378/385)
                   │  msg/payload 全程零拷贝引用
                   ▼
            queueOutbound (client.go:2582)
                   │  尾帧先补满(免多取池)
                   │  每帧从 nbPoolGet 取(池化,唯一"复制"点)
                   ▼
            out.nb net.Buffers ──flush信号──▶ 写侧
  [复制点仅两处: ①拆包拼接落 scratch/msgBuf  ②queueOutbound 把 payload 拷入池化定长帧]
```

关键事实:正常(非拆包)路径上,subject/reply/payload 始终是读缓冲 `b` 的切片引用;只有进入 `queueOutbound` 时才被 copy 进池化定长帧——这是写聚合的代价,也是唯一一次大块 memcpy。

## 1. 发布热路径的内存审计

### 1.1 解析层:scratch/argsa 每连接复用

`parseState` 直接内嵌进 `client` 结构体(client.go:268),每个连接自带两块永久 scratch:4KB 控制行缓冲与 8 个参数槽。

```go
type parseState struct {
	state   parserState
	op      byte
	as      int
	drop    int
	pa      pubArg
	argBuf  []byte
	msgBuf  []byte
	header  http.Header // access via getHeader
	scratch [MAX_CONTROL_LINE_SIZE]byte
	argsa   [MAX_HMSG_ARGS + 1][]byte // pre-allocated args array to avoid per-call heap escape
}
```
(parser.go:25-36;`MAX_CONTROL_LINE_SIZE=4096` 见 const.go:90,`MAX_HMSG_ARGS=7` 见 const.go:180)

- 只有消息跨 TCP 读边界(拆包)时才动 `scratch`:`argBuf = c.scratch[:0]` 后 append(parser.go:1204-1207);payload 拆包时优先也落 scratch 残余空间,放不下才 `make`(parser.go:1230-1243)。argBuf/msgBuf 复位为 nil 即可复用,无池开销。
- ROUTER/LEAF 的 MSG 参数展开也用每连接 `argsa`,注释直言"Unroll splitArgs to avoid runtime/heap issues"(route.go:188):

```go

	start := -1
	for i, b := range arg {
		switch b {
		case ' ', '\t', '\r', '\n':
			if start >= 0 {
				args = append(args, arg[start:i])
				start = -1
			}
```
(route.go:187-196;同一手法见 route.go:287、383,leafnode.go:3140、3228)
- 出站头 `mh` 写进每连接 1KB 的 `msgb` 数组(client.go:295,初始化 client.go:772-776,`msgScratchSize=1024` client.go:105):`mh := c.msgb[:msgHeadProtoLen]`(client.go:3610,client 侧 client.go:3700/3703,gateway.go:2686-2687)。

### 1.2 匹配层:三级缓存,miss 才碰共享结构

发布匹配有 L0/L1/L2 三层:`acc.sl` 的全局 subject 缓存(L2)+ 每连接 `in.results` L1 结果缓存 + `in.pacache` 按账号缓存。L1 用 `atomic.LoadUint64(&acc.sl.genid)` 免锁校验,genid 未变且命中则零分配零锁(client.go:4467-4474);miss 才 `acc.sl.Match(string(c.pa.subject))`(client.go:4479,上限 512 条 client.go:474)。Sublist 内部又是先 RLock 查缓存(sublist.go:563-574,命中即返回),未命中才升写锁回填,超 `slCacheMax=1024`(sublist.go:51)后 CAS 触发异步清扫 goroutine(sublist.go:623-629)。匹配器内部 token 数组也是栈上 `tsa := [32]string{}`(sublist.go:576-577)。Subject 零拷贝转 string 用 `unsafe.String`(store.go:850-856),只在确认生命周期同 read buffer 时使用。

`deliverMsg` 对目标客户端只做零拷贝入队——两个参数都是读缓冲切片,不复制:

```go

	client.queueOutbound(msg)

		// Need to add CR_LF since MQTT producers don't send CR_LF
```

(client.go:4010-4016)

`queueOutbound` 是全路径唯一大块复制:先把尾帧补满避免多取池(client.go:2599-2608),再循环 `nbPoolGet` + copy 进定长帧(client.go:2613-2618);顺带做慢消费者检测与 75% 水位建 stall 门:

### 1.4 写侧:三级 sync.Pool + writev

out.nb 每帧来自三个按容量分级的池(client.go:366-368:512/4096/65536):

```go
func nbPoolGet(sz int) []byte {
	switch {
	case sz <= nbPoolSizeSmall:
		return nbPoolSmall.Get().(*[nbPoolSizeSmall]byte)[:0]
	case sz <= nbPoolSizeMedium:
		return nbPoolMedium.Get().(*[nbPoolSizeMedium]byte)[:0]

		return nbPoolLarge.Get().(*[nbPoolSizeLarge]byte)[:0]
	}
}
```
(client.go:395-404;池定义 client.go:371-390;Put 按 cap 严格分流、错误容量直接丢弃防串池 client.go:410-424)

`flushOutbound` 的细节:非 WebSocket 时 `collapsePtoNB` 返回 `c.out.nb` 本体——零拷贝(client.go:1717-1724);IO 期间释放 `c.mu`(client.go:1790-1791),用工作副本 `wnb` 承接并发修改(client.go:1762-1772);核心写循环只有一次系统调用面:

```go

		// which if 1024, will mean a maximum of 64MB in one go.
```

## 2. pse:进程自计量(process statistics exchange)

`server/pse/` 是独立包,16 个文件按平台分文件(pse_linux/darwin/windows/freebsd_cgo/…/pse_zos.go),`ProcUsage(pcpu, rss, vss)` 是唯一对外接口。Linux 实现: init 里定位 `/proc/<pid>/stat` 并启动 1 秒周期的 `periodic` 采样(pse_linux.go:42-48),采样算出窗口 CPU 千分比存原子量(pse_linux.go:51-88);查询时免锁读原子量、现场解析 RSS/VSS 字段(pse_linux.go:91-107),字段偏移 utime=13/rss=23 等硬编码(pse_linux.go:34-40),数字解析手写免 fmt 分配(pse_linux.go:117-128)。注意 `ticks = 100` 的注释"Avoiding to generate docker image without CGO"(pse_linux.go:43-44)——为了 CGO-less 镜像放弃 sysconf。

用途:① 集群 `STATS`/`statsz` 上报 `updateServerUsage`(events.go:855);② 监控端点 `Varz`(monitor.go:1625)与 `HandleVarz`(monitor.go:2025),都在服务器锁外调用。采样核心一目了然:

```go
	// Adjust to current time window
	total -= lt
	seconds -= ls

	if seconds > 0 {
		atomic.StoreInt64(&ipcpu, (total*1000/ticks)/seconds)
	}

	time.AfterFunc(1*time.Second, periodic)
```
(pse_linux.go:80-88;查询侧 `*pcpu = float64(atomic.LoadInt64(&ipcpu)) / 10.0` 在 pse_linux.go:104)

也就是说服务器自己产出自已的 CPU/RSS 指标,零外部依赖,监控与运维链路无需 node_exporter 即可工作;`updateServerUsage` 还顺带记录 Cores/GOMAXPROCS 与 Go 内存软限(events.go:856-861)。

## 3. 缓冲自适应与写聚合

读缓冲从 512B 起步(为 INFO/CONNECT 块),满读即倍增至 64KB 上限,连续 2 次半满读就减半缩回(下限 64B,伺服 PING/PONG 场景):

```go
		if n >= cap(b) {
			c.in.srs = 0
		} else if n < cap(b)/2 { // divide by 2 b/c we want less than what we would shrink to.
			c.in.srs++
		}
		// Update read buffer size as/if needed.
		if n >= cap(b) && cap(b) < maxBufSize {
			// Grow
			c.in.rsz = int32(cap(b) * 2)
			b = make([]byte, c.in.rsz)
		} else if n < cap(b) && cap(b) > minBufSize && c.in.srs > shortsToShrink {
			// Shrink, for now don't accelerate, ping/pong will eventually sort it out.
			c.in.rsz = int32(cap(b) / 2)
			b = make([]byte, c.in.rsz)
		}
```
(client.go:1656-1671,节选)

```go
startBufSize    = 512   // For INFO/CONNECT block
minBufSize      = 64    // Smallest to shrink to for PING/PONG
maxBufSize      = 65536 // 64k
shortsToShrink  = 2     // Trigger to shrink dynamic buffers
maxFlushPending = 10    // Max fsps to have in order to wait for writeLoop
```
(client.go:110-114;初值 client.go:1482,首缓冲 client.go:1506;伸缩判定 client.go:1656-1671)

写聚合两层:微观上 `queueOutbound` 尾帧补满 + 定长帧切分(见 1.3);宏观上 `writeLoop` 用 `owtf := c.out.fsp > 0 && c.out.pb < maxBufSize && c.out.fsp < maxFlushPending` 决定"再等一波"(client.go:1395),`flushClients(budget)` 还会按时间预算就地刷或转信号(client.go:1426-1455)。快速生产者压制:fan-in 过载时让消费者在 `stalledWait` 中最多停 `stallTotalAllowed=10ms`(client.go:123-126,3733-3751),读循环卡顿累计超 5ms 会限流告警(client.go:1458-1463)。

## 6. 大负载调优面:需要 OS 与配置配合的参数

| 参数 | 默认/上限 | 位置 | 行为 |
|---|---|---|---|
| max_payload | 1MB,预警 8MB | const.go:94,96-99;默认装配 opts.go:6137-6138 | 超预警仅告警(server.go:2358) |
| max_pending | 64MB/连接 | const.go:101-102;opts.go:6140-6141 | 超限判慢消费者并断连(client.go:2622-2637) |
| 启动校验 | max_payload ≤ max_pending | server.go:1172-1174 | 违反拒绝启动 |
| max_control_line | 4KB(客户端) | const.go:90 | LEAF/ROUTER/GATEWAY ×16=64KB(parser.go:1274-1293) |
| DEFAULT_MAX_CONNECTIONS | 64K | const.go:105 | 要求 OS ulimit 配合 |

- `max_payload` 与 `max_pending` 是大负载的主旋钮,且二者被启动校验绑定(server.go:1172-1174);大 payload 场景还应意识到写侧单次 writev 上限 1024×64KB(client.go:1839-1844)与读缓冲 64KB 上限(client.go:112)意味着一个 1MB 消息天然要跨多个读块,拆包路径(scratch/msgBuf)会被反复触发。
- 文件描述符:仓库唯一指引是测试注释——"open files 至少 8192,linux/macOS 用 `ulimit -n 8192`"(test/bench_test.go:15-17),gateway 测试也提示 ulimit 不足会导致外连数不足(gateway_test.go:5144);服务端代码不做 setrlimit,fd 是纯 OS 侧参数。
- 拆包防御:控制行超限按 `max_control_line` 判定,注释明言这是抗内存耗尽攻击的第一道闸,且"不够精确,但性能代价太大"(parser.go:1208-1211);默认 scratch 只有 4KB,超限走堆,检测在 append 后以近似值进行。

| 目标 `client.mu` | client.go:3793 | deliverMsg 逐目标加锁(权限/echo/stall 判定) | IO 在锁外(1790-1791),flushOutbound 竞争时 Gosched 让路(1730-1737) |
| `acc.stats.Lock` | client.go:5321-5333 | 每消息一次聚合统计(非每订阅) | 收口在 updateStats 闭包 |
| `out.sg` sync.Cond | client.go:355,2126 | 目标端写唤醒 | 与 c.mu 同域,signal 廉价 |
| genid / 慢消费计数 | client.go:4467,2628 | 原子读,无锁 L1 判定 | 化锁为原子 |
| ipQueue.Mutex | ipqueue.go:28 | 不在核心发布路径 | 批量 pop+recycle 摊薄 |

三点补充:① `flushOutbound` 发现 writeLoop 与 readLoop 争用时的处理是"放锁 + `runtime.Gosched()` + 重取"(client.go:1730-1738),这是热路径上仅有的主动让渡;② L1 缓存失效(账号订阅 genid 变化)时整表重建 `make(map[string]*SublistResult)`(client.go:4472)——订阅频繁变动的账号会周期性付一次重建代价;③ 慢消费者计数的三个落点(服务器原子量、客户端统计、账号统计,client.go:2628-2634)全部为无锁或短临界区,不阻塞投递主流程。

结论:核心发布路径的锁压力集中在"每个目标订阅者的 client.mu",其余全部通过原子量、每连接 scratch 与缓存读锁规避;唯一可能升级为写锁的是 subject 缓存 miss。

## 8. 硬件/内核配合:如实记录

- 未发现 `SO_REUSEPORT`:全仓 grep(case-insensitive "reuseport")零命中,server 只支持 `port`/`clients` 等常规监听配置;多实例水平扩展靠客户端侧多 URL,不靠内核多队列分流。
- 未发现 busy poll、NUMA 亲和相关代码或注释(grep 零命中);单 goroutine per connection 的 `readLoop/writeLoop` 模型(client.go:1376,1467)把调度交给 Go runtime,不做 CPU 绑核。
- 依赖内核的只有通用项:writev(`net.Buffers.WriteTo`,client.go:1851,`nbMaxVectorSize` 注释 "IOV_MAX on Linux/Darwin" client.go:363)、`SetWriteDeadline` 按批设置(client.go:1850)与 OS 层 ulimit(test/bench_test.go:15-17)。性能叙事完全建立在"减少分配、批量写"之上,而非特定内核特性。

## 9. 设计动机(≥5 条)

1. **scratch 为什么 per-connection**:解析是每连接串行的,把 4KB scratch、argsa、msgb 内嵌 client(parser.go:34-35,client.go:295/776)意味着热路径零池交互、零原子操作、天然缓存行亲和;代价是每连接常驻 ~6KB,64K 连接也只 ~400MB 级,是明确的用空间换无竞争。
2. **为什么三级池(512/4K/64K)**:帧容量固定才能 `nbPoolPut` 按 `cap` 精确归位、避免 append 重分配(client.go:410-424 的 default 分支宁可丢弃也不混池);单级大池会让小消息浪费内存、大消息碎片化,三级正好对应控制帧/常规/大负载。
3. **为什么 ipqueue 批量(pop 整段 + recycle)**:JS/RAFT 的消费循环一轮处理成百上千条,批量 slice 把"锁交互、channel 信号、池交互"都摊薄为 O(1);`push` 仅在从空到非空时发一次信号(ipqueue.go:135-140),消费端 `pop` 后立刻把队列槽位让给生产者(ipqueue.go:210-217)——锁竞争窗口与 GC 扫描对象数同步最小化。
4. **为什么 self-instrument(pse)**:监控自身的 CPU/RSS 不能反过来成为负载(外部抓取、CGO 依赖都会);1 秒周期采样 + 原子量读取(pse_linux.go:51-107)让 `/varz`、statsz 在任意平台(含 wasm/zos)零依赖输出,这也是监控端点在服务器锁外调用它的原因(monitor.go:1620-1625)。
5. **为什么 benchmark 进仓库**:基准是回归测试的"性能断言"——`BenchmarkPublish` 的尺寸×订阅形态矩阵(benchmark_publish_test.go:47-83)与 core 的 TLS 扇出矩阵(core_benchmarks_test.go:99-120)把历次优化(如 nbPool 重写、flush 合并)变成可复验的对照;`b.ReportMetric` 记录错误数、`bench_results.txt` 沉淀历史基线,让"性能不回退"成为 CI 可讨论的事实。
6. **为什么唯一复制点放在 queueOutbound**:读侧零拷贝保证解析层与 subject 生命周期解耦(写侧消费时源缓冲早已可复用),而写聚合必须拷贝;把 memcpy 集中到一处,既让"帧补满"逻辑局部化(queueOutbound 尾帧续写),也让慢消费者/stall 判定在同一临界区顺手完成(client.go:2620-2646)。
