## 1. 通道一:HTTP 监控端点(server/monitor.go)

### 1.1 挂载骨架

14 个路径常量集中在 `server/server.go:3044-3061`(含 `/debug/vars` 与 `/accstatz`),`startMonitoring`(server.go:3100)用一个 `http.ServeMux` 全部挂上:server.go:3150-3178 逐个 `mux.HandleFunc`,server.go:3180 挂 `expvar.Handler()`;另给 `/subsz` 保留 `/subscriptionsz` 别名(server.go:3164)。两个细节:

```go
// server/server.go:3182-3191
// Do not set a WriteTimeout because it could cause cURL/browser
// to return empty response or unable to display page if the
// server needs more time to build the response.
srv := &http.Server{

    Handler:           mux,
```

### 1.2 /varz:配置+运行时的唯一聚合快照

`Varz` 结构(monitor.go:1225-1303)是全服务器仪表盘:静态配置(host/port/TLS/各协议端口)、运行计数(monitor.go:1270-1282)、质量指标 `SlowConsumers`(1283)、`StaleConnections`(1284)、`StalledClients`(1285)、自省项 `HTTPReqStats`(每端点命中计数,1287)与 `ConfigDigest`(1289),还有 `SlowConsumersStats`/`StaleConnectionStats`/`DiskIOWaitStats` 三个分型统计(1298-1300,结构体在 1444-1466)。磁盘 IO 信号量争用也做成了指标(diskIOWaitStats,monitor.go:2007-2017)。实现上最讲究的是锁顺序:

```go
// server/monitor.go:2034-2046(节选)
s.varzMu.Lock()
// Use server lock to create/update the server's varz object.
s.mu.Lock()
s.httpReqStats[VarzPath]++
if s.varz == nil {
    s.varz = s.createVarz(pcpu, rss)
    created = true
} else {
    s.updateVarzRuntimeFields(s.varz, false, pcpu, rss)
}
s.mu.Unlock()
```

`HandleVarz`(2020-2076)先在锁外取进程 CPU/RSS(`pse.ProcUsage`,2025),用专门的 `varzMu` 串行化并发请求,服务端锁内只做创建或增量更新;增量更新 `updateVarzRuntimeFields`(1897-1949)全部走 atomic load + 订阅数遍历,JS 部分因"锁序 js→Server"被挪到服务端锁外刷新(2047-2064),最后**锁外** marshal(2066-2068)——监控大响应永不持全局锁编码。CPU/RSS 来自 `pse.ProcUsage`(1620-1638 同样锁外)。

### 1.3 /connz:连接表,分页 + 六种过滤器

`ConnzOptions`(monitor.go:60-100)支持 sort/auth/subs/subs_detail/offset/limit/cid/state,以及 auth=true 下的 user/acc/mqtt_client/filter_subject。默认 `limit=1024`(`DefaultConnListSize`,monitor.go:170)、`state=open`;`sort=stop|reason` 只在 `state=closed` 下合法(251-257)。数据来源分三路:

- 普通连接:`s.clients`+`s.leafs` 在 `s.mu.RLock` 下浅拷贝成 map(monitor.go:304-318);
- 指定 `acc`:改遍历该账号 `a.clients`(a.mu.RLock,287-301);
- `state=closed`:来自**闭环环形缓冲** `s.closed.closedClients()`(monitor.go:326;缓冲区在 server.go:898 创建,容量默认 1 万,server/const.go:191-192)。

过滤逐连接在 client 锁下比对 user/acc/mqtt(397-418);`filter_subject` 用 `SubjectsCollide` 做通配兴趣匹配,且强制要求同时给定 acc(264-269,423-437)。`ConnInfo.fill`(578-625)逐连接取 inMsgs/inBytes/stalls 原子读(599-603),TLS 版本/密码套件/对端证书指纹只在 `handshakeComplete` 后读取以免阻塞握手中连接(607-619);`rtt` 为空且是真实客户端时会**现场发 RTT ping** 探测(650-666,底层 client.go:2682-2693)——首次查询某连接时 rtt 字段可能为空,再查才有。排序支持 cid/uptime/subs/pending/in/out/last/idle/stop/reason/rtt 等(monitor.go:531-558),分页在排序后裁剪:

### 1.4 /routez、/gatewayz、/leafz:三张拓扑表

`Routez`(monitor.go:852-924)与 connz 最大的不同:整个遍历持 **`s.mu.Lock` 写锁**(862,unlock 于 922)——因为要 `forEachRoute` 并填每条 route 的权限/压缩/账号名(875-916),参数只有 subs/subs_detail(926-933)。集群规模大时频繁拉 /routez 会与路由写入竞争,这点与 connz 的读锁策略形成对照。

`Gatewayz`(2129-2158):网关未启用时返回空 map 而非错误(2134-2143);outbound 表按 `gw_name` 过滤,每条 `RemoteGatewayz` 复用 `ConnInfo.fill` 填连接详情,`IsConfigured` 区分配置对端与隐式发现对端(2212-2232);`accs/acc_name` 追加每账号兴趣模式(`outsim` 表,2237-2253);inbound 表镜像同名账号聚合(2155)。`Leafz`(2458-2517)在 `s.mu` 下快照 leaf 列表并按 acc 过滤(2461-2476),逐 leaf 锁填 `LeafInfo`(is_spoke/is_isolated/compression/proxy 等,2483-2499),subs=true 时附加订阅列表(2500-2505)。`/accstatz`(2590-2614)按账号出统计,默认跳过无本地连接/叶的账号(2568),`unused=true` 才全量。

### 1.7 /ipqueuesz、/raftz、/stacksz:三个"急救"端点

`/ipqueuesz`(1208-1222)遍历 `s.ipQueues` 暴露内部 IP 队列 pending/in_progress;默认只报非空队列,`all=true` 全量,`queues=` 子串过滤(1183-1206)——JS API 路由积压(`jsAPIRoutedReqs`)的观察窗,/jsz 的 meta.pending 同源(monitor.go:1607-1613)。`/raftz`(4263-4283)无 raft 节点直接 404;`acc` 默认取系统账号(4288-4294),`group` 定点;对每个节点**一次性拿读锁**填充 term/commit/applied/leader/overrun/WAL 状态/四个 IPQ 长度/peers 最近复制位点(4331-4379),注释明说避免反复取锁(4331-4332)。`/stacksz`(1156-1174)最特别:

```go
// server/monitor.go:1157-1165
func (s *Server) HandleStacksz(w http.ResponseWriter, r *http.Request) {
    // Do not get any lock here that would prevent getting the stacks
    // if we were to have a deadlock somewhere.
    var defaultBuf [defaultStackBufSize]byte
    size := defaultStackBufSize
    buf := defaultBuf[:size]
    n := 0
    for {
        n = runtime.Stack(buf, true)
        if n < size {
            break
        }
        size *= 2
        buf = make([]byte, size)
    }
```

**故意不取任何锁**——"即便某处死锁也能拿到全 goroutine 栈",缓冲 10KB 起指数翻倍(常量在 monitor.go:175)。这是线上死锁排查的最后手段。

### 1.8 expvar /debug/vars 与 pprof

`/debug/vars` 直接挂 Go 标准库 `expvar.Handler()`(server.go:3180),内容是 memstats/cmdline 等标准 expvar;nats 另封 `expvarz()`(monitor.go:4162-4179)只挑 memstats/cmdline 两块供 `$SYS.REQ...EXPVARZ` 使用。**没有 /debug/pprof HTTP 端点**:pprof 只能经系统请求 `PROFILEZ` 获取——`profilez`(monitor.go:4186-4222)支持 `cpu`(时长须在 0-15s,4194-4198 起 StartCPUProfile 并睡眠采样,4199-4205)与任意 `pprof.Lookup` 具名 profile(heap/goroutine/block/mutex 等,4207-4217),`debug` 参数控制输出格式。因 CPU 采样耗秒级,PROFILEZ 处理器专门再开 goroutine 异步执行(events.go:1328-1340)。

## 2. Prometheus:如实说明——没有原生 /metrics

对 `server/*.go` 与 `go.mod` 全文 grep `prometheus` 零命中:仓库内**不存在** Prometheus 文本端点、registry 或指标注册。官方路径是外部导出器(如 nats-io/nats-exporter,不在本仓库)抓取监控口 JSON 翻译成 `/metrics`;textfile 方案同理用脚本轮询。生态里 `nats_varz_*` 等指标名的语义完全由本报告第 1 节的 JSON 字段决定:如 slow_consumers 对应 Varz.SlowConsumers(monitor.go:1283)与 ServerStats.SlowConsumers(events.go:380)两个字段。另注意 `/varz` 自带 `HTTPReqStats`(monitor.go:1287)记录每个监控端点被访问的次数——监控自身也被监控。

## 3. 通道二:$SYS 事件全景

### 3.2 statsz:启动加密、随后退避的周期广播

`lameDuckMode`(server.go:4448-4457)第一步就发 `$SYS.SERVER.<id>.LAMEDUCK`(events.go:60),随后关 listener、转移 raft leader、关 JetStream、按宽限期把客户端**分批踢散**以防重连风暴(server.go:4459-4527)。真正的 `sendShutdownEvent`(events.go:689-705)发 `$SYS.SERVER.<id>.SHUTDOWN`(events.go:61)并置 `sendq=nil`、清空 replies——最后遗言。集群成员收到后把 `nodeToInfo` 标 offline 并从 `s.sys.servers` 摘除(events.go:1704-1740,1681-1697);对方静默退出时由 sweeper 定时器按 `chkOrph` 周期兜底检测孤儿(events.go:1157-1159,837-852)。集群因此能实时维护"在线服务器表"——statsz 里的 `active_servers`(events.go:1019)即由此而来。

### 3.4 account claim 更新

`accountClaimUpdate`(events.go:1647-1676)订阅新旧两个 claim 主题(events.go:55-56,1256-1268):从主题取账号公钥 → `jwt.DecodeAccountClaims` 解码 → 校验 claim.subject 与主题一致 → `updateAccountWithClaimJWT` 热更新,并逐分支回写 "jwt updated/skipped/error" 应答。这是去中心化 JWT 的热更新通道:运维端 `nats pub $SYS.REQ.ACCOUNT.<pubkey>.CLAIMS.UPDATE <jwt>` 即可改账号配置而无需重启。

## 4. 事件消费:任意监控端如何看到 $SYS.>

直接订阅 `$SYS.>` 需要**系统账号凭据**——事件都发布在系统账号内,服务器不会替普通账号转发。但代码做了两件"半开放":①系统账号自动**导出** `$SYS.REQ.ACCOUNT.*.CONNZ|STATZ`,且用 `addServiceExportWithResponseAndAccountPos` 把账号名钳制进主题第 4 段(events.go:1595-1615);②给每个普通账号**自动注入 service import**:

```go

// Add in this object to the account in 2 places.
// "$SYS.REQ.SERVER.PING.CONNZ" and "$SYS.REQ.ACCOUNT.PING.CONNZ"
mappedConnzSubj := fmt.Sprintf(accDirectReqSubj, a.Name, "CONNZ")
importSrvc(fmt.Sprintf(accPingReqSubj, "CONNZ"), mappedConnzSubj)
importSrvc(fmt.Sprintf(serverPingReqSubj, "CONNZ"), mappedConnzSubj)
importSrvc(fmt.Sprintf(accPingReqSubj, "STATZ"), fmt.Sprintf(accDirectReqSubj, a.Name, "STATZ"))
```

(registration at events.go:2380-2411;USER.INFO import 在 2407-2410。)于是普通账号的监控端**无需系统凭据**即可查询"本账号"的连接表/统计/自身权限;要消费全局事件流(connect/disconnect、statsz、lameduck/shutdown、claim 更新),运维侧建一个系统账号用户后 `nats sub "$SYS.>"` 即可,全部事件都在该通配下。服务端内部订阅经 `sysSubscribe`(events.go:2847-2860,含队列组与 internal 变体)注册,响应复用 `$SYS._INBOX.<shash>.*` 通配(events.go:1209-1214;shash 是服务器名 8 字符哈希,1162-1178)。

## 5. 运维动作 API:$SYS.REQ.SERVER.*(内部请求-应答)

`initEventTracking`(events.go:1196-1519)一次注册整个管理面。监控查询表 `monSrvc`(1275-1327)含 IDZ/STATSZ/VARZ/SUBSZ/CONNZ/ROUTEZ/GATEWAYZ/LEAFZ/ACCOUNTZ/JSZ/HEALTHZ/PROFILEZ/EXPVARZ/IPQUEUESZ/RAFTZ,每个**同时挂两个主题**(1351-1360):`$SYS.REQ.SERVER.<server_id>.<NAME>`(定点)与 `$SYS.REQ.SERVER.PING.<NAME>`(广播全集群)。统一封装 `zReq`(2301-2329):解析 `EventFilterOptions{name,cluster,host,tags,domain,exact_match}`(1995-2002)做服务器过滤(实现 filterRequest,2101 起),应答包 `ServerAPIResponse`,且按请求头 `Accept-Encoding` 支持 s2/snappy/gzip 压缩(2287-2299,2325-2327)——跨集群回传大 JSON 时的带宽优化。账号级 `monAccSrvc`(1369-1448)挂 `$SYS.REQ.ACCOUNT.<acc>.<NAME>`(SUBSZ/CONNZ/LEAFZ/JSZ/INFO/STATZ/CONNS)。

**动作类**只有四个:KICK(`{"cid":123}` 断开指定连接,3239-3255)、LDM(对指定 cid 触发慢消费者式优雅断开,3257-3272)、RELOAD(热加载,1500-1505)、调试服务 `$SYS.DEBUG.SUBSCRIBERS`(84,1494-1498;实现 3050-3176,可跨服务器 solicit 某主题的订阅者数)。另有 `$SYS.REQ.USER.INFO` 让任意客户端自查自身权限与账号(76-77,1521-1569)。

## 6. SLI 建议:哪些信号适合进告警

- **Slow consumers**(client.go:1972-2017):写超时即 `atomic.AddInt64(&c.srv.slowConsumers,1)`(1997)并按 kind 分类计数(1998-2010,账号级 2011-2015);三处同源可见:/varz 总量+分型(monitor.go:1283,1923-1928)、每轮 statsz(events.go:959-980)。速率上升是订阅侧过载/网络劣化的第一信号,适合 rate-of-increase 告警。
- **Stalled clients / stale connections**:/varz `StalledClients`(monitor.go:1922,客户端发送窗口停顿计数)与 `StaleConnections`(1929,ping 判死);statsz 同步携带(events.go:970-980)。
- **内存/资源拒绝**:JetStream `JSMemoryResourcesExceededErr`(errors.json:656)可从 JS advisory 聚合;/varz 暴露 `Mem`/`gomemlimit`(monitor.go:1265,1268)与 DiskIOWaitStats(2007-2017)供趋势外推。
- **健康分层**:/healthz 裸探针=进程活着;js-enabled-only=JS 就绪(3723-3726);默认全量=流/consumer 状态一致(4114-4145)。liveness 用裸探针、readiness 用带 JS 探针是结构上现成的分层。
- **连接质量回溯**:/connz `state=closed` + `sort=reason` 直接回答"为何掉线"(monitor.go:552-556);`filter_subject` 定位某主题兴趣持有者(264-269);disconnect 事件(events.go:167-177)则提供全集群的掉线原因流。
- **元层积压**:/jsz 的 `meta.pending_requests/pending_infos`(monitor.go:3110-3112)与 /raftz 的 ipq 长度(4355-4358)反映 JS API 与 raft 管道健康,适合作为延迟预算耗尽的先行指标。

## 7. 设计动机

1. **HTTP 与 $SYS 双通道**:快照接口(拉)实现简单、无回放负担,但受探测间隔限制;事件流(推)给全集群时间序列与秒级感知(statsz 起步 250ms,events.go:1150)。两者共用同一批 `*z()` 快照函数——`$SYS.REQ...CONNZ` 只是 HTTP handler 的远调用封装(events.go:1286-1289),一套数据语义两种交付拓扑,避免双实现漂移。
2. **分页而非全量**:`DefaultConnListSize=1024`(monitor.go:170)与 connz/jsz/subsz 的 offset/limit,本质是快照接口的背压:监控查询不该比业务流量更贵。monitor.go:566-569 的 TODO 坦承 offset 分页在超大规模下的一致性弱点——设计者知情而取舍。
3. **statsz 周期广播 + 限速 + 兴趣检查**:集群监控不靠逐台轮询,而靠每台自发广播形成组播式视图;1s 限速(events.go:104,1092-1118)防 ping 风暴雪崩,单机无订阅者整条跳发(931-945)让空闲单机零成本,启动期倍增退避(1122-1132)兼顾收敛速度与稳态开销。
4. **监控与故障态解耦**:stacksz 不取锁(monitor.go:1158-1159)、varz 锁外 marshal(2066-2068)、lameduck 事件发完不关 sendq(events.go:675-686)——可观测性组件被刻意设计成"任何故障态下仍可用",前提是它们不依赖健康路径的锁与队列;死锁时唯一还能工作的端点就是 /stacksz。
5. **pprof 内嵌而非侧车**:profilez 复用 $SYS 请求-应答(events.go:1328-1340 + monitor.go:4186-4222),让"对集群所有节点同时采 CPU profile"变成一条 `$SYS.REQ.SERVER.PING.PROFILEZ` 广播;无需开第二个调试端口,攻击面收敛进系统账号权限。
6. **系统账号作为唯一权限边界**:监控凭证=系统账号凭证;普通账号靠自动注入的账号钳制 import 只能自查询(events.go:2380-2411)——可观测性粒度与多租户隔离用同一套 service export/import 机制表达,不需要独立的监控 RBAC。
