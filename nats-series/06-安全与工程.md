# 第 06 章 · 账号、安全与工程文化

> 基线:commit `8f3f31b0`。核心文件 server/auth.go、accounts.go、events.go。

## 6.0 全景:三层 JWT 链与质询-应答

```
Operator claim(根,自签)→ 私钥签 Account claim → 账号私钥/scoped signer 签 User claim
服务器只内置 operator 公钥(trustedKeys);账号 claim 经 resolver 按需取回:
  Mem(sync.Map)/URL(http GET)/Dir(目录+NATS 同步),过期自动重取+1 秒防抖
裸 nkey 认证:INFO 带 nonce → 客户端 Ed25519 签名 → 服务端只用公钥验签(auth.go:1195-1203)
公钥即身份:用户名就是 Base32 的 Ed25519 公钥;服务器永不接触私钥,无需口令库
```

认证判定顺序写死在注释里(auth.go:435-437):**custom → JWT → nkey → TLS 证书映射 → token → user/pass**。nkey 与 JWT 统一在同一密钥空间:JWT 的 Subject 就是用户公钥,验签对象是 claim Subject(auth.go:1103-1108)。

## 6.1 权限:发布侧拒绝,订阅侧不创建

权限编译进各自的 sublist(allow/deny),强制点两个方向:发送侧 processInboundClientMsg 拒绝已发出的 PUB(client.go:4386-4391);订阅侧 canSubscribe 不通过则 SUB 直接失败、**账号 sublist 里不留兴趣痕迹**(client.go:3367-3414)。deny 通配符可能"事后"命中具体订阅,投递期 mperms 过滤兜底。response 权限是观察式 m/m 收件箱:只登记真实观察到的 reply 主题,默认 1 条/2 分钟——静态 allow 无法表达"只能回最近请求方"。

**为什么权限做进协议层**:客户端库鱼龙混杂,唯一可信执行点是服务器——权限因此对 40+ 种客户端语言一视同仁。服务间授权 export/import 完全编码进 subject 与 claim:导入必须通过对端 exportAuth 检查+环检测(上限 1024 层)。

## 6.2 $SYS:用 NATS 自身做运维事件

事件就是 PUB:`$SYS.ACCOUNT.<acc>.CONNECT/DISCONNECT`(断连事件被注释为 billing event)、`$SYS.REQ.CLAIMS.UPDATE` 双向流动、LAMEDUCK/SHUTDOWN 传播——零新协议,天然按账号订阅,随集群路由到任意监控点。claim 更新与 resolver 取回也复用同一条总线:**自举无旁路**。

## 6.3 TLS 与 reload

TLS 全线支持热重载:IsTLSChange 精确圈定需重建的监听器,diff-then-apply 让不可热更字段显式报错(reload.go:1427-1497)。Curve(X25519)不是 TLS 而是服务器间消息端到端加密的 xkey,仅非 FIPS 构建生成。本基线的最新提交正是一个 reload 边角修复——reload 是一等公民的证据。

`go.mod` 仅 10 个依赖且过半是 NATS 自家库;贡献指南明文"拒绝非必要新依赖……我们会非常苛刻"(CONTRIBUTING.md:34)+"新功能没有测试覆盖不予接受"。测试密度:server/ 下 75 个 _test.go(auth_test 23 个 Test 函数、client_test 104 个)、5 个专用 benchmark、3 个 fuzz 入口;锁序约束单独成文(locksordering.txt);错误处理声明式登记在 errors.json 由 go generate 生成。第三方安全审计公开披露(Trail of Bits,README.md:66)。

## 6.5 设计动机

1. **decentralized JWT**:权限数据彻底离开服务器配置文件——变更无需触碰任何服务器,天然多租户多集群一致;
2. **nkey 公钥即身份**:免口令库免 PKI,nonce 质询防重放,与 JWT 统一密钥空间;
3. **权限进协议层**:服务器是唯一可信执行点,对所有客户端语言一致;
4. **零依赖**:依赖面即攻击面与编译面;边缘/树莓派场景要求静态单文件可控;
5. **$SYS 自举**:运维事件复用消息总线本身,监控点任意部署。

## 6.6 FAQ

**Q1:nkey 用户名是什么?**
Base32 编码的 Ed25519 公钥;认证=对服务器 nonce 的签名。

**Q2:JWT 的信任根在哪?**
服务器内置 operator 公钥(trustedKeys);账号 claim 必须由 operator 签发。

**Q3:scoped signer 是什么?**
账号可授权子签名者发用户 claim,mustache 模板展开权限,笛卡尔积上限 4096。

**Q4:账号 claim 怎么分发?**
三种 resolver:内存/HTTP URL/目录+NATS 同步;过期自动重取。

**Q5:deny 了订阅还会收到消息吗?**
不会创建兴趣;但 deny 通配可能事后命中,投递期 mperms 再滤一次。

**Q6:auth callout 是什么?**
把未命中声明式规则的连接委托给 $SYS.REQ.USER.AUTH 的外部服务裁决。

**Q7:TLS 能热更新吗?**
能:IsTLSChange 圈定重建监听器;不可热更字段显式报错。

**Q8:xkey 是什么?**
Curve(X25519)服务器间消息加密,非 TLS,非 FIPS 构建。

**Q9:测试怎么组织?**
与生产文件同目录同名(75 个),5 benchmark+3 fuzz,跨模块集成在顶层 test/。

**Q10:AI 能提交贡献吗?**
可以辅助但须披露,且"最终决定永远由人做出"(CONTRIBUTING.md:36-40)。
