# 第 12 章 · 性能工程:热路径、分配与基准方法(卷二·收尾)

> 基线:commit `8f3f31b0`。横向盘点:发布热路径的每一次内存分配与回收、对象池全景、自计量与基准方法。性能叙事完全建立在"减分配、批量写"之上——仓库无 SO_REUSEPORT/busy poll/NUMA 相关代码(grep 零命中,如实)。

## 12.0 全景:一条 PUB 的内存生命周期

```
readLoop:socket→自适应缓冲(64B-64KB)→parse 状态机(零拷贝,split 才落 4KB scratch)
 →匹配:L1 每连接缓存(genid 原子判定零锁)→L2 RLock 查缓存→miss 才写锁回填
 →deliverMsg:零拷贝入队(两个参数都是读缓冲切片引用)
 →queueOutbound:唯一大块 memcpy——payload 拷入三级池化定长帧(512B/4KB/64KB)
写侧 writeLoop:collapsePtoNB(非 WS 零拷贝引用 out.nb)→writev 一次最多 1024 向量×64KB
  →已消费帧归还 nbPool(按 cap 严格分流,错误容量直接丢弃防串池)
复制点仅两处:①拆包拼接落 scratch/msgBuf ②queueOutbound 的写聚合拷贝
```

## 12.1 热路径内存审计

解析层:parseState 内嵌进 client——每连接自带 4KB scratch+8 参数槽+1KB msgb,**热路径零池交互零原子操作,天然缓存行亲和**;代价是每连接常驻 ~6KB,64K 连接也只 ~400MB,明确的用空间换无竞争。argsa 注释直言"avoid per-call heap escape"。匹配层三级缓存:L1(每连接,genid 原子判定)→L2(RLock 命中即返回,miss 才升写锁回填)→异步清扫;token 数组是栈上 [32]string。投递层零拷贝入队+慢消费者判定(超 64MB 踢)与 75% 水位 stall 门顺手完成。写侧三级池按容量精确归位;flushOutbound 争用时"放锁+Gosched+重取"是热路径仅有的主动让渡。

## 12.2 pse 自计量与缓冲自适应

server/pse 是独立自计量包:1 秒周期采样 /proc/stat,查询免锁读原子量——**服务器自己产生自己的 CPU/RSS 指标,零外部依赖**,监控链路无需 node_exporter;为 CGO-less 镜像放弃 sysconf(ticks=100 手写)。读缓冲自适应:512B 起(INFO/CONNECT 块)满读倍增至 64KB,连续 2 次半读缩回 64B(伺服 PING/PONG)。写聚合两层:微观尾帧补满+定长切分;宏观 writeLoop 的"再等一波"(未决 flush<10 且缓冲未满)与 flushClients 时间预算。快速生产者压制:stall 门让消费者最多停 10ms 反向限流。

## 12.3 池全景与 benchmark 方法

server 包约 20 处 sync.Pool 盘点:nbPool 三级(热路径)、JS consumer/stream 各五六个、filestore 块四级、RAFT 编解码五池、ipQueue 内嵌池。逃逸规避两手法:对象池+栈上定长数组(sublist token [32]string、_dsubj [128]byte)。ipQueue 的批量语义(pop 一次拿走整段、recycle 超 4KB 不回池防大对象驻留)让 JS/RAFT 消费端每轮 O(1) 次池交互;注意**核心发布路径不用 ipqueue**——它是 JS/RAFT/系统 sendq 的基础设施。benchmark 五文件矩阵:BenchmarkPublish(尺寸×订阅形态全矩阵)、core(请求-回应/TLS 扇出)、jetstream(13 个场景)、meta raft 写放大、raft 单文件写;方法论:SetBytes+ChaCha8 随机载荷避免压缩干扰、错误数作为 ReportMetric;历史基线是纯文本 bench_results.txt(2017 iMac Pro:Pub0b 55.1ns/op)。

## 12.4 锁盘点与调优面

发布路径锁压力集中在**每个目标订阅者的 client.mu**(权限/echo/stall 判定,IO 在锁外);其余全靠原子量、每连接 scratch 与缓存读锁规避;唯一可能升写锁的是 subject 缓存 miss。调优面:max_payload(1MB,预警 8MB)与 max_pending(64MB/连接)被启动校验绑定;fd 是纯 OS 参数(测试注释 ulimit -n 8192);大 payload 场景注意读缓冲 64KB 上限意味着 1MB 消息要跨多个读块,拆包路径反复触发。

## 12.5 设计动机

1. **scratch per-connection**:解析每连接串行,零池交互+缓存行亲和,用 ~6KB/连接换无竞争;
2. **三级池**:帧容量固定才能按 cap 精确归位;单级大池小消息浪费内存大消息碎片化;
3. **ipqueue 批量**:JS/RAFT 消费一轮处理成百上千条,锁交互/信号/池交互摊薄为 O(1);
4. **self-instrument**:监控自身的 CPU/RSS 不能反过来成为负载;1s 采样+原子量零依赖;
5. **benchmark 进仓库**:基准是性能断言,历次优化变成可复验对照;bench_results.txt 让"不回退"成为 CI 可讨论的事实;
6. **唯一复制点在 queueOutbound**:读侧零拷贝使解析与 subject 生命周期解耦;memcpy 集中一处让慢消费者/stall 判定局部化。

## 12.6 FAQ

**Q1:发布路径哪一步拷贝?**
只有 queueOutbound 把 payload 拷入池化定长帧(写聚合代价);其余全零拷贝引用。

**Q2:读缓冲多大?**
512B→满读倍增至 64KB;连续 2 次半读缩回 64B。

**Q3:慢消费者阈值?**
max_pending 默认 64MB 超限踢;75% 建 stall 门(最多 10ms 压制快速生产者)。

**Q4:自计量怎么实现?**
pse 包 1 秒采样 /proc/stat,查询免锁读原子量;为免 CGO 手写数字解析。

**Q5:为什么单次 writev 是 1024 向量?**
IOV_MAX 限制;最大约 64MB 一发,超过分批。

**Q6:锁在发布路径哪里?**
每个目标订阅者的 client.mu(短临界区);匹配走缓存读锁;统计每消息一次聚合。

**Q7:sync.Pool 用在哪?**
约 20 处:出站帧/JS 消费与发布/filestore 块/RAFT 编解码/内部消息——按容量或类型严格分流。

**Q8:有 NUMA 绑核吗?**
没有(grep 零命中);调度交给 Go runtime。

**Q9:benchmark 怎么跑?**
go test -bench 约定,白盒(package server);JS 两个文件有 build tag;需 ulimit -n 8192。

**Q10:大消息有什么隐含代价?**
1MB 消息跨多个 64KB 读块,拆包路径(scratch/msgBuf)反复触发;writev 分批。
