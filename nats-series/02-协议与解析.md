# 第 02 章 · 协议与解析:一个状态机吃掉全部流量

> 基线:commit `8f3f31b0`。核心文件 server/parser.go(1339 行)与 server/client.go(7065 行)。

## 2.0 全景:PUB 状态机转移与 INFO/CONNECT 握手

```
OP_START → 'P''U''B' → PUB_ARG('\n' 定界,arg=buf[as:i-drop],parser.go:445)
  → processPub → MSG_PAYLOAD(索引跳跃 i=as+size-2,payload 一字节都不 switch,:462)
  → MSG_END_N(msgBuf=buf[as:i+1] 零拷贝,:509)→ processInboundMsg → 回 OP_START
握手:accept 后同步直发 INFO(server.go:3357,sendProtoNow,writeLoop 未起)
  → CONNECT(json.Unmarshal 进 c.opts,鉴权+协议协商 headers/no_responders)
  → 客户端 PING → 服务端 PONG(firstPongSent 置位,附 ConnectInfo INFO)
```

协议全集:INFO/CONNECT/PUB/HPUB/SUB/UNSUB/MSG/HMSG/PING/PONG/+OK/-ERR,控制行上限 4096 字节、参数个数编译期定死(const.go:174-186);集群扩展 RS+/RS-(route)、LS+/LS-(leaf 兴趣)、A+/A-(账号级)在同一状态机上多开分支——**一台状态机服务四种连接**,ARG 终点按 c.kind 分派 process 函数(parser.go:682-711)。

## 2.1 零拷贝的三层含义

①参数行:`arg = buf[as : i-drop]`,直接引用读缓冲;②payload:不跨读缓冲时 `msgBuf = buf[as:i+1]` 只有切片头,投递时把入站 buffer 的 slice 直接塞进目标连接的 out.nb(client.go:4011-4012)——publish 一次字节拷贝都没有;③跨读缓冲时:控制行复用每连接的 4KB scratch 数组(parser.go:1205),payload 装不下才落堆,此时 pubArg 若还引用旧 buffer 必须 clonePubArg(parser.go:1297)——**用罕见路径多拷一次换常见路径零拷贝**。subject 映射改写也在原 slice 上就地进行(parser.go:519-528)。

## 2.2 握手与协商

服务端 accept 后**先发 INFO**(客户端需要 max_payload/tls_required/connect_urls 才能决定后续行为);CONNECT 到来后 processConnect 在锁内解析、鉴权、协商:headers 仅当双方都声明才成立(client.go:2368);no_responders 依赖 headers,否则 -ERR 关连(:2483-2490);verbose 时每操作回 +OK。鉴权失败(authViolation)必断连,权限违例只报错不断连——**身份不可信就该断,策略问题断连只会引发重连风暴**。

## 2.3 心跳与慢消费者

PING/PONG 内联在状态机(3 个状态、应答只是常量入队),PONG 顺带承担 RTT 测量(用于压缩选档)。服务端 2 分钟一次、最多 2 次未答即发 -ERR 'Stale Connection' 关连(client.go:5842-5900);懒惰探测:窗口内收到过数据就推迟本轮 PING(但 ROUTER/GATEWAY 一律照发)。慢消费者:硬上限 64MB(out.mp)超限只对 CLIENT 判死;75% 软水位造 stall 门闩,让 fast producer 在 deliverMsg 里原地小睡(总量封顶 10ms)反向限流(client.go:2622-2637,3733-3771)。写超时策略与 kind 联动:CLIENT Close,集群链路 Retry。

## 2.4 设计动机

1. **文本协议扛千万级 msg/s**:热路径每字节一次 switch;payload 索引跳跃;文本无封帧层;
2. **零拷贝**:payload 生命周期止于本轮投递,slice 直接入队;
3. **握手先 INFO**:客户端没有 max_payload 等信息无法构造正确 CONNECT;
4. **PING 内联**:最高频控制指令,解析路径最短,还兼任 RTT 测量;
5. **慢消费者直接踢**:扇出枢纽一个 64MB pending 会拖垮所有 fast producer,踢掉是保护多数。

## 2.5 FAQ

**Q1:payload 会被状态机逐字节处理吗?**
不会:PUB_ARG 直接跳 i=as+size-2,一个字节都不 switch(parser.go:462)。

**Q2:指令劈成两半怎么办?**
argBuf 复用 scratch,payload 跨读时拷贝补齐后重放 process 函数(parser.go:1204-1243)。

**Q3:subject 合法性默认校验吗?**
发布侧默认不校验,CONNECT 声明 pedantic 才检查(client.go:3006-3008)。

**Q4:权限违例会断连吗?**
pub/sub 违例只回 -ERR 不断连;鉴权违例必断连。

**Q5:PING 间隔多少?**
2 分钟,最多 2 次未答;集群可配独立间隔;懒惰探测可推迟。

**Q6:慢消费者 64MB 是谁的上限?**
每连接出站 pending;超限只踢 CLIENT,集群连接宁可堆积。

**Q7:HMSG 的头部怎么切?**
msgParts 用三索引切片 data[:hdr:hdr], cap 限定防止追加越界(client.go:2875-2880)。

**Q8:no_responders 503 是谁发的?**
服务端直接 Sprintf 一条 HMSG 入队(client.go:4528-4538)。

**Q9:读缓冲会伸缩吗?**
满读倍增到 64KB,连续两次半读收缩到 64B——PING/PONG 连接保持小缓冲。

**Q10:UNSUB max 语义?**
两段式:未到 max 只设 sub.nm 上限,投递时恰好等于则先投再自动退订。
