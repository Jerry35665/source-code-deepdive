# 第 09 章 · 系统服务与账号:$SYS、service import 与内部客户端(卷二)

> 基线:commit `8f3f31b0`。核心:server/events.go、accounts.go、subject_transform.go、auth_callout.go。卷一 06 讲过 claim 校验,本报告聚焦运行时。

## 9.0 全景:内部客户端三兄弟与应答路由

```
内部客户端(无 socket,复用 client 结构,echo=false/headers=true):
  SYSTEM(发 $SYS 事件;挂 $SYS 服务的"服务端"订阅)
  JETSTREAM(JS 引擎内部 pub,绕 echo/计费/权限面)
  ACCOUNT(每账号一个 a.ic:承载 service import 订阅、callout 应答)
发送:sendInternalMsg→s.sys.sendq(IPQueue)→internalSendLoop 串行化(补 ServerInfo/压缩)
接收:noInlineCallback 入 recvq(recvqp 专供 STATZ/Ping 优先)
service import 运行时:请求方账号 sublist 里一条带 icb 的影子订阅
  →processServiceImport:reply 改写 _R_.<rand>[.sh.T]→投递到导出方
  →应答经 _R_.<前缀>> 通配影子订阅回流(一条订阅服务所有在途请求)
```

## 9.1 内部客户端:无 socket 的复用

createInternalClient 不建任何网络连接,只构造 client 结构——**内部消息与网络消息共享同一套匹配、账号、统计与头处理语义**,新功能(头/映射/追踪)自动对内部消息生效,不需要第二套代码路径。sysSubscribe 家族把订阅插进 $SYS 账号 sublist(kind 非 CLIENT 故权限检查整体跳过);`noInlineCallback` 把 JSON 解析挪出 route/gw 热路径(回调只做切头拷贝入队)。发到任意账号时 sendInternalAccountMsg 临时把 client 换成目标账号的 a.ic——消息走该账号 sublist,这是 latency 结果与应答回执落点的关键。

## 9.2 service import:影子订阅与 _R_ 通配应答

运行时本体是"请求方账号 sublist 里一条带 icb 的影子订阅"——跨账号请求零分支进入正常投递。processServiceImport:psi 环检测→reply 改写为新应答主题($JS.ACK 例外,保跨账号 pull 消费)→逐实例映射叠加→在导出方账号上 Match+投递。**应答回流的巧思**:_R_.<前缀>> 一条通配订阅服务所有在途请求,免去逐请求 SUB/UNSUB 的集群兴趣传播;开启追踪时追加 .<shash>.T 让遥测精准回源。防护:CLIENT 禁发 _R_/$JS.ACK/_GR_ 保留应答;GW 阻止 _R_ 外泄。

## 9.3 subject 映射与延迟追踪

映射只在两个运行时点:发布端 parser 钩子(MSG 收尾态改写 pa.subject,账号级 hasMappings readcache 隔离成本)与 import/投递端;令牌替换 $1..$9 由 subject_transform 的 dtokmftypes 承载,partition 用 FNV-32 取模。**service latency 两半程测量**:请求方记 si.rc/ts,应答返回时算 RequestStart/ServiceLatency/TotalLatency;应答者不在本机时改写应答带 .<shash>.T,响应方服务器测 M2 经 $SYS.LATENCY.M2.<shash> 回传合并;采样决策识别 Zipkin/W3C 四种头的 sampled 位。

## 9.4 $SYS 服务化与 callout

$SYS 自动导出 CONNZ/STATZ 服务(accountPos=4 把账号名夹进主题),给每个普通账号**自动注入免授权(internal=true)的 service import**——普通账号的监控端无需系统凭据即可自查;自动导入解决了"先有授权才能装配、先装配才有授权"的引导悖论。$JS.API 与 $SYS.REQ 同挂 $SYS sublist 但分道:JS 二次精确匹配+16 并发 goroutine 池(高频需账户限制);$SYS 事件串行队列(低频要保序)。auth callout:一次性 nkey 防重放、目标账号挂应答订阅、AuthTimeout select——认证决策委托给账号内普通应用,服务器只做 JWT 结果校验。

## 9.5 设计动机

1. **内部走 client 抽象**:共享全部语义,新功能自动生效;
2. **影子订阅+_R_ 通配**:跨账号请求零分支;一条订阅服务全部在途请求;
3. **映射运行时执行**:partition/random 依赖每消息上下文;发布端以 readcache 隔离成本;
4. **$SYS 也走 NATS**:监控/计费做成系统账号上的服务与事件流,运维端一个普通订阅者即可消费;
5. **callout 独立成服务**:一次性 nkey+AuthTimeout 把信任面收窄到单次请求。

## 9.7 FAQ

**Q1:内部客户端有 socket 吗?**
没有:纯 client 结构复用;echo=false 意味着自己的发布不回流自己的订阅。

**Q2:跨账号应答怎么回到请求方?**
_R_.<前缀>> 通配影子订阅+exports.responses 应答表;过期清扫。

**Q3:subject mapping 在哪执行?**
发布端 parser 收尾态与 import/投递端两个点;MQTT 三处发布点也接了钩子。

**Q4:service latency 怎么跨服务器测?**
应答主题追加 .<shash>.T,响应方测 M2 经 $SYS.LATENCY.M2 回传合并。

**Q5:内部订阅会传播到集群吗?**
sysSubscribeInternal(internalOnly)不传播;普通 sysSubscribe 传播。

**Q6:JS API 为什么用并发池而 $SYS 串行?**
JS 高频需账户限制(16 goroutine);$SYS 事件低频要保序聚合——同一 sublist 承载两种负载画像。

**Q7:auth callout 超时会怎样?**
拒绝;一次性用户 nkey 防重放,应答订阅 defer 清理。

**Q8:内部请求有权限检查吗?**
检查不触发(perms 只装 CLIENT/LEAF);但保留主题($NRG./_R_/$JS.ACK/$SYS.REQ.USER.AUTH)显式拒绝。

**Q9:leaf 场景的 ClientInfo 头可信吗?**
不可信:发往 leaf 前以本地认证身份重建(leafnode 场景一律换头)。

**Q10:$SYS.LATENCY 谁消费?**
导出方配置 tracking 时注册的 results 主题;服务方应用订阅它看调用延迟分布。
