# 第 17 章 · 事件系统:内存总线与丢失语义

> 基线:commit `f6132db`。行号以 core/events/exchange/exchange.go、core/metadata/db.go、pkg/shim/publisher.go、internal/cri/server/ 为准。**勘误**:Exchange 是一层 go-events Broadcaster 封装,无持久化;GRPC EventService 是双协议(grpc+ttrpc)。

## 17.0 全景:事件的产生→分发→消费

```
产生源:
  shim 进程 /tasks/*(forward 循环 → ttrpc Forward → daemon)
  daemon 内部 /containers /images /snapshot /content /namespaces /sandboxes /tasks/oom
  外部注入(Publish RPC)
     ↓ 全部汇入
Exchange(一层 go-events.Broadcaster 封装)
     ↓ 每订阅者一条 sink 链 Filter→无界 Queue→无缓冲 Channel
GRPC EventService Subscribe 循环 srv.Send 推给外部流
```

Publish 强制 namespace、发布时刻打时间戳、入总线即返回(exchange.go:86/:99/:118);Topic 校验必须 `/资源/动作` 两级(:201-222);订阅 sink 链 Channel(0)+无界 Queue+ParseAll 过滤(:130-148);filter 字段 namespace/topic/event.*,语法 == != ~= any-match(events.go:36-62+pkg/filters)。

## 17.1 丢失语义:三层

1. **不丢但涨内存**:慢订阅者→go-events Queue 无界(vendor queue.go:10-12)——背压变现为内存堆积;
2. **真丢的缝**:进程重启;broadcaster sink 写失败仅打日志(broadcast.go:120-124);shim 侧本地队列 2048、重试 5 次超限丢弃(pkg/shim/publisher.go:36-37,:102-108);GC 补发 commit 后异步、失败仅 debug;
3. **无回放**:订阅从当下开始,断连期间事件不补——**契约是"事件是提醒不是事实"**,消费方须 List 对账(CRI 启动 recover+TaskExit 主路径走 Wait 而非总线)。

## 17.2 GC 补发与 shim 死亡兜底

GC 补发:事务内 Publisher 返回 nil,commit 后异步只发 ImageDelete/SnapshotRemove(db.go:288-298,:348-368,:440-443)。**shim 死亡兜底补发 TaskExit+TaskDelete**(已投递过则跳过,core/runtime/v2/shim.go:163-195)。CRI 内部走 EventMonitor(只订 /tasks/oom 与 /images/),internal/cri/server/events/events.go:120-152。

## 17.3 设计动机

1. **为什么不持久化事件**:事件的消费者(kubelet/dockerd)要的是"现在发生了什么",历史由元数据承载——**持久观感靠元数据,不靠事件日志**(卷一 A 章);
2. **无界 Queue 的取舍**:背压=内存堆积 vs 丢弃=信息丢失——containerd 选了前者(内存比信息便宜);
3. **Topic 命名空间设计**:`/资源/动作` 两级——资源的 CRUD 语义自然映射到 Topic。

## 17.4 FAQ

**Q1:事件会丢吗?**
会:进程重启/sink 写失败/shim 队列溢出(:36-37,:102-108)——消费方须 List 对账。

**Q2:慢订阅者会怎样?**
无界 Queue 涨内存(vendor queue.go:10-12)——不丢不背压,靠消费方自律。

**Q3:事件有顺序保证吗?**
单订阅者内有序;跨 Topic 无序——排序是消费方职责。

**Q4:CRI 消费哪些事件?**
只订 /tasks/oom 与 /images/(internal/cri/server/events :120-152);TaskExit 走独立 Wait 不走总线。

**Q5:shim 死了事件会丢吗?**
shim 死亡兜底补发 TaskExit+TaskDelete(shim.go:163-195)——已投递过则跳过。

**Q6:GC 删镜像后事件从哪来?**
commit 后异步补发 ImageDelete(db.go:348-368)——失败仅 debug 不重试。

**Q7:filter 语法是什么?**
== != ~= any-match(events.go:36-62):namespace/topic/event 字段级过滤。

**Q8:事件的 Topic 有哪些?**
/tasks/* /images/* /snapshot/* /content/* /namespaces/* /sandboxes/*:资源 CRUD 全映射。

**Q9:订阅断连后重连能补吗?**
不能:订阅从当下开始——消费方须 List 对账。

**Q10:Exchange 是持久化的吗?**
不是:纯内存 Broadcaster(exchange.go:36-45)——持久观感靠元数据+GC 补发。

## 17.5 小结与深挖方向

本章结论:**事件系统="内存总线+无界 Queue+Topic 过滤+三层丢失语义"**;契约是"提醒不是事实"。深挖:

1. 无界 Queue(:10-12)在高频发布场景的内存水位;
2. filter 语法的 CEL 表达式扩展空间;
3. shim 本地 2048 队列(:36-37)与大 Pod 的容量;
4. CRI EventMonitor 的 OOM 事件延迟;
5. 事件持久化如果要做,WAL 事件流的成本收益。
