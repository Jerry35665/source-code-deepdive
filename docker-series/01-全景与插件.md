# 第 01 章 · containerd 全景:插件 DAG 与 boltDB 元数据

> 基线:commit `f6132db`(2.x 主干)。行号以 cmd/containerd/、plugins/、core/、vendor/github.com/containerd/plugin/ 为准。**勘误**:插件框架已独立为外部模块(仓库内是 vendor 副本);事件总线不持久化。

## 1.0 全景:容器栈中的位置与插件 DAG

```
dockerd / nerdctl / kubelet(CRI)
        │ GRPC
   containerd daemon ── 插件依赖 DAG(初始化即拓扑排序)
        ├── content / snapshots / events ──┐
        ├── metadata(boltDB)←─ Requires 三者
        ├── shim manager → task manager ────→ 每容器一个 shim 进程(03 章)
        └── GRPC 聚合 / CRI 插件
```

插件框架:`Registration{Type,ID,Requires,InitFn}`(vendor/.../plugin/plugin.go:61-84);初始化顺序=Registry.Graph 对 Requires 做 **DFS 拓扑排序**,环依赖直接 panic(:114-135,:146)。类型全集(plugins/types.go:25-88):Metadata/Content/Snapshot/RuntimeV2/GRPC/Service/Event/GC…。主依赖链:content/snapshotter/event→**metadata bolt**(Requires 三者,plugins/metadata/plugin.go:98-102)→shim manager(:63-70)→task manager→GRPC(:65-68)→CRI(:52-60)。daemon 入口仅 35 行 blank-import builtins(cmd/containerd/main.go:26-35)——**一切皆插件,main 只负责 import**。

## 1.1 metadata store:boltDB 是唯一真相

boltDB 布局 `<v1>/<namespace>/<object>/<key>`(core/metadata/buckets.go:29,schema 注释 :60-138);隔离=桶路径第一层,全部走 `namespaces.NamespaceRequired(ctx)`。事务模型:`DB.Update` 持 wlock.RLock(db.go:272-284)——**读锁包写事务,为 GC 让路**(GC 要排他);ctx 携带事务可组合;**事件禁止在事务内发布**(db.go:288-298,防死锁)。所有 GRPC 门面经 GetSingle(MetadataPlugin) 收敛到同一 bolt DB——元数据只有一个真相源。

## 1.2 事件总线与 GC

事件总线是**纯内存 pub/sub**:Exchange 只是 go-events Broadcaster(core/events/exchange/exchange.go:36-45),Publish 打时间戳/ns/topic 后广播(:80-119),Subscribe 按 filter 转投 channel(:128-199)。**不持久化**——"历史事件"的观感来自元数据本身+GC 删除时补发 /images/delete、/snapshot/remove(db.go:348-368)。

GC(gc 主流程 db.go:383-489):引用靠 label `containerd.io/gc.ref.*`(gc.go:73-75);`GarbageCollect` 持 wlock.Lock→getMarked 用 **gc.Tricolor 三色标记**(db.go:492-536;pkg/gc/gc.go:64-105)→单写事务 sweep 元数据→**异步**清 snapshotter/content(:449-479);由 gc/scheduler 插件按阈值触发(plugins/gc/scheduler.go:96-102)。三色标记+两阶段删除——与 Git GC(PG 式可达性)同构,见 cross-series 模式。

## 1.3 设计动机

1. **为什么一切皆插件**:containerd 的定位是"基础设施组件"而非产品——每种 snapshotters/runtimes/proxies 由部署方选配;proxy 插件(第三方 snapshotter)经 GRPC 注入同一张图(server.go:316-382);
2. **为什么元数据用 bolt 而非 SQL**:单文件嵌入式+事务+零运维;元数据规模(万级容器)远低于 SQL 的甜蜜点;
3. **为什么事件不落盘**:事件的消费者(kubelet/dockerd)要的是"现在发生了什么",历史由对象状态承载——**持久观感靠元数据,不靠事件日志**;
4. **GC 的三色标记**:引用图存于 bolt 标签前缀(gc.ref.*),扫描即遍历——**把可达性编码进标签协议**,任何插件都能参与 GC。

## 1.4 FAQ

**Q1:containerd 2.x 和 1.x 的差别大吗?**
路径全面迁移(content→core/content 等,A 报告开头映射表);概念模型稳定——旧资料的概念仍适用,行号全换。

**Q2:插件崩了会怎样?**
required_plugins 必须成功(:197-208),可选插件可跳过——启动的失败边界显式声明。

**Q3:为什么事务内禁止发事件?**
bolt 事务与事件回调可能重入同一 DB(:288-298):死锁防线。

**Q4:第三方 snapshotter 怎么接入?**
proxy 插件:GRPC 客户端注入插件图(server.go:316-382)——进程外插件与进程内同权。

**Q5:元数据会无限增长吗?**
不会:GC 三色标记+调度器按阈值触发(:96-102)。

**Q6:namespace 隔离的实现粒度?**
桶路径第一层(buckets.go:29):同 DB 内逻辑隔离,物理共享。

**Q7:事件会丢吗?**
会(内存):订阅者需在重连时按元数据重建状态——at-least-once 不在承诺内。

**Q8:dockerd 和 containerd 什么关系?**
dockerd 内嵌 containerd 库(或连接外部 containerd):镜像/快照能力来自 containerd,网络/卷来自 dockerd。

**Q9:插件初始化失败的日志在哪找?**
server.New 的初始化循环(:125-234)逐插件报错——带插件 ID。

**Q10:GRPC 聚合是什么?**
(:108-131)所有 GRPCPlugin 挂到一个 Server:一个 socket 服务全部 API。

## 1.5 小结与深挖方向

本章结论:**containerd="插件 DAG 的一切皆插件+boltDB 单一真相+内存事件+标签协议 GC"**。深挖:

1. plugin.go 拓扑排序(:114-135)对动态注册(运行时加载插件)的扩展;
2. bolt wlock.RLock 包写事务(:272-284)的并发语义论证;
3. gc.ref 标签协议在自定义对象上的扩展面;
4. proxy 插件的鉴权边界(:316-382);
5. 事件总线换成 WAL 持久化的迁移成本。
