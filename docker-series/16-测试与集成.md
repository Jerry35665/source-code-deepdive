# 第 16 章 · 测试与集成:containerd vs runc 的工程对照(卷末)

> 基线:containerd `f6132db` / runc `579be22`。行号以 Makefile、.github/workflows/、integration/、tests/ 为准。**两处与直觉相反的事实**:containerd 的 integration/ 是 Go test(非脚本);runc 的 integration/ 是 bats 框架(非裸 shell)。

## 16.0 全景:两项目的工程四柱对照

| 柱 | containerd | runc |
|---|---|---|
| 测试 | 单测 make test(:224 起)→client API 集成(integration/,Go test)→**CRI 白盒集成**(编成 cri-integration.test 二进制由 shell 驱动)+critest 黑盒+K8s node-e2e | go test 单测+bats 端到端+**rootless 幂集**(tests/rootless.sh:174-190) |
| CI | 按"部署形态"矩阵(OS×go×cgroup 驱动×发行版 VM×Windows×UserNS) | 按"特性开关"矩阵(libpathrs×rootless×race×criu) |
| 发布 | 4 个月一版对齐 K8s(RELEASES.md:44-48);常规支持 8 个月、年度 LTS 2 年+ | 6 个月节奏;容器内 8 架构静态构建 |
| vendor | 全量入库+verify-vendor(57 个顶级目录) | 抽独立模块(opencontainers/cgroups v0.1.0;vendor 仅 15 个顶级目录) |

## 16.1 containerd:三层测试与 failpoint 注入

- **CRI 集成的白盒形态**:integration/ 被 `go test -c` 编成 bin/cri-integration.test(Makefile:224-231),由 script/test/cri-integration.sh:53-61 传 `--cri-endpoint/--runtime-handler` 驱动;TestMain 连接 CRI gRPC+containerd 双客户端(integration/main_test.go:76-134),**支持测试中重启守护进程**(:843-859);
- **failpoint 故障注入**:四包装器(shim/CNI/runc/loopback,Makefile:233-251)+Pod 注解通配(script/test/utils.sh:100-103)——在任意点注入失败验证鲁棒性;
- **同套件双跑**:每 PR 集成测试跑两遍(串行 -race+并行),注释溯源 PR #1759(ci.yml:504-533);
- CI 矩阵:go 1.26.8/1.27.1(:203-204,注释:1.25 不支持因 K8s 1.36)、ubuntu-22.04/24.04/arm×cgroupfs/systemd(:401-410)、**Lima 10 组 VM**(fedora-44/almalinux 8/9/10×crun :605-636);
- fuzz:contrib/fuzz 8 目标+fuzz.yml 双 job(oss-fuzz cifuzz 300s+go test -fuzz 5 万次,script/go-test-fuzz.sh:26-33)。

## 16.2 runc:特性幂集与静态发布

- bats 端到端:`localintegration=bats -t tests/integration`(Makefile:175-189);**rootless 以特性幂集循环**(2^n:idmap×cgroup 全组合,rootless.sh:25,:174-190);
- **发布=容器内 8 架构静态构建**(Makefile:114-128;script/release_build.sh:22-65):自编 libseccomp 2.6.1/libpathrs 0.2.6 后静态链接,`-w -s -buildid=` 可复现——**runc 二进制的"零 glibc 依赖"是造出来的**;
- 版本:VERSION 文件(1.5.0-rc.1+dev)vs containerd 的 git describe(Makefile:35);
- lint 分化:containerd depguard **禁 import runc**(.golangci.yml:21-22);runc forbidigo **禁 os.Create**(点名 CVE-2024-45310,.golangci.yml:39-45)且增量加严走 `--new-from-rev=HEAD~1`(validate.yml:62)——**lint 规则=事故记忆**。

## 16.3 设计动机

1. **containerd 为什么需要 heavyweight CI**:K8s 全生态依赖它——它坏一个版本,半个云坏;矩阵按部署形态展开,每一格都是真实用户组合;
2. **runc 的"规范即测试"**:OCI spec 的每条语义都有对应 bats 用例;rootless 幂集把"特性组合爆炸"显式穷举——**测试矩阵=承诺清单**;
3. **vendor 两种姿态**:containerd 全量入库(可审计可复现)vs runc 抽独立模块(刚发生的 cgroups 外置)——Go 大项目在"可复现"与"模块化"间的两种平衡;
4. **串行+并行双跑**(:504-533):并发 bug(竞态)与串行 bug(逻辑)需要不同执行形态——同一套用例两种形态才完整。

## 16.4 FAQ

**Q1:cri-integration.test 是怎么跑的?**
go test -c 编译成二进制,shell 传 CRI endpoint 驱动(Makefile:224-231;cri-integration.sh:53-61)——白盒:能直接操控 containerd 内部。

**Q2:failpoint 怎么注入故障?**
四包装器+Pod 注解通配(:233-251):在 shim/CNI/runc/loopback 任意点模拟失败。

**Q3:runc 的静态二进制怎么构建?**
容器内自编 libseccomp/libpathrs 再静态链接,8 架构(:22-65):可复现 ldflags。

**Q4:为什么 containerd 禁 import runc?**
(:21-22):架构上 containerd 是 runc 的上游编排者——依赖方向单向。

**Q5:两个项目多久发一版?**
containerd 4 个月(对齐 K8s);runc 6 个月:跟随生态节奏而非自身意愿。

**Q6:-race 双跑的动机?**
(:504-533):竞态与逻辑 bug 分开暴露——PR #1759 的教训。

**Q7:rootless 幂集测试多大?**
idmap×cgroup 全组合 2^n(rootless.sh:174-190):CI 的重头。

**Q8:为什么 runc 禁 os.Create?**
(:39-45):CVE-2024-45310(符号链接攻击)的 lint 化——禁止不安全文件创建原语。

**Q9:containerd 的版本号哪来?**
git describe+ldflags 注入(:35;version/version.go:26-27):无 VERSION 文件。

**Q10:Lima VM 矩阵测什么?**
(:605-636):不同发行版(crun 运行时)的真实兼容性——发行版碎片化的现实。

## 16.5 小结与卷三卷末语

本章结论:**containerd="部署形态矩阵+白盒 CRI 集成+failpoint";runc="规范即测试+幂集矩阵+静态可复现发布"**——同一生态两种工程性格。
