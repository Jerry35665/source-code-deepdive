# 第 02 章 · 镜像与快照:pull 管道与 overlayfs

> 基线:commit `f6132db`(2.x)。行号以 core/content/、core/snapshots/、plugins/content/local/、plugins/snapshots/overlay/、core/remotes/docker/、core/unpack/ 为准。**勘误**:2.x 布局已迁移——content 接口在 core/content/,blob 落盘在 plugins/content/local/,snapshotter 接口在 core/snapshots/snapshotter.go。

## 2.0 全景:一次 docker pull 的数据流

```
registry → Resolver.Resolve(manifest,401→token 认证)
  → Fetcher Range 分块并行下载 → images.Dispatch(handler 链):
      FetchHandler(blob 下载入 content) + childrenHandler(打 gc.ref.content 标签)
  → Unpacker:config 下载完才触发 unpack
      逐层 Prepare→Apply→Commit(snapshotter 层叠)
  → 全部完成才写 image 记录(client/pull.go:162-177)
```

Pull 链从 client/pull.go:43 起:WithLease 建 **GC 租约**(:86)——下载中的 blob 不会被 GC 收走。token 认证:401 触发 authorizer.go:153 解析 challenge→:275 doBearerAuth(有凭据先 OAuth POST :316,405/404/401/400 退回 GET token :324,无凭据匿名 :342),token 按 scope 缓存(:289)。Resolve 信任 `Docker-Content-Digest` 头(resolver.go:393-405)。

## 2.1 content store:digest 寻址与 resumable

blob 路径 `blobs/<alg>/<hex>`(plugins/content/local/store.go:646-652)——**内容寻址:路径即校验**。ingest 目录 ref/data/startedat/updatedat/total(:589-605,:666-674);**resumable 的核心是重放 data 求偏移**(:501-529):断点续传=读已写部分重新计数(:524 io.CopyBuffer 进哈希器),offset 后继续。Commit 三重校验+rename 转正+去写位(writer.go:111-156,:198-202)——01 章"原子替换"模式的内容存储版。

## 2.2 snapshotter 与 overlayfs

Snapshotter 接口五方法:Prepare/View/Mounts/Commit/Remove(core/snapshots/snapshotter.go:281-377)。overlayfs 实现(plugins/snapshots/overlay/overlay.go):每快照目录 `snapshots/<id>/{fs,work}`(:536-553);**mounts() 三分支**(:555-618):无父层→bind mount;active+有父→workdir+upperdir+lowerdir(父层 upperPath 按 ParentIDs 顺序拼接 :604-608);View 单父→ro bind。committed 快照以 **chainID 命名**,层链=镜像 rootfs 链——容器启动把 Mount{Type,Source,Options}(core/mount/mount.go:35-53)填进 CreateTaskRequest.Rootfs 交 runc(03/05 章)。**chainID 快照去重**:Prepare 撞 chainID 即跳过 unpack(core/unpack/unpacker.go:499-509);解包后回链 gc.ref.snapshot(:745-751)。

## 2.3 pull 的流水线与 GC

Unpacker 包装进 pull 链(pull.go:137-154):manifest 阶段摘出 layer 挂到 config 名下,**config 下载完才触发 unpack**(unpacker.go:285-321);下载与解包流水线并行,层只等自己的下载信号(:612-618)。GC:标签协议 gc.root/gc.ref./gc.bref./gc.expire(core/metadata/gc.go:66-118);根=未过期 image/container/lease/gc.root 标记对象/active(:495);三色标记(pkg/gc/gc.go:64-100)后**两阶段删除**(meta 删除+异步物理删除 db.go:400-455);调度器按"均耗时/pause 阈值"自适应(:236-350)。

## 2.4 与前作对照及设计动机

1. **content 与 snapshotter 分离**:blob 存储(全局去重)与层视图(每 OS/每后端)正交——同一 blob 可被多个 snapshotter 用;对照 LevelDB(单引擎)vs Git odb 多后端(Git 卷一 01 章);
2. **ingest 可恢复**:大 blob 上传/下载的中断是常态,resumable 用"重放求偏移"替代"记录偏移"——**一致性靠重算而非记帐**;
3. **chainID 去重**:同一层链的快照只建一次(:499-509)——镜像间共享层的物理基础;
4. **unpack 的时机门控**:config 到位才 unpack(:285-321)——避免下载到错误的层白解。

## 2.5 FAQ

**Q1:为什么 config 下载完才 unpack?**
config 摘出 layer 顺序与 diffID(:285-321):没有 config 无从校验层。

**Q2:下载中断了要重来吗?**
不用:ingest 重放求偏移(:501-529),续传从断点。

**Q3:两个镜像共享一层,磁盘几份?**
content 一份 blob+snapshotter 按 chainID 一个快照(:499-509)——双层去重。

**Q4:GC 会删正在下载的 blob 吗?**
不会:WithLease 租约(:86)给下载期对象上保险。

**Q5:overlayfs 的 lowerdir 顺序?**
ParentIDs 顺序拼接(:604-608):最老层在最下。

**Q6:View 和 Prepare 差在哪?**
View 只读(单父 ro bind);Prepare 可写(active)——只读挂载的语义区分。

**Q7:pull 多快?**
Range 分块并行(fetcher.go:488-560)+下载解包流水线(:612-618)。

**Q8:token 缓存多久?**
按 scope 缓存(:289),过期由 registry 的 challenge 重新触发。

**Q9:快照的 work 目录是干什么的?**
overlayfs 的 workdir(原子 copy-up 的暂存区,:536-553)。

**Q10:GC 触发条件?**
调度器按均耗时/pause 阈值自适应(:236-350):不靠定时器。

## 2.6 小结与深挖方向

本章结论:**镜像层="digest 寻址 blob+可恢复 ingest+chainID 快照去重+标签协议 GC"**。深挖:

3. unpacker 并行度(:612-618)与磁盘 IO 的竞争;
4. gc.expire 标签(:66-118)的 TTL 语义;
