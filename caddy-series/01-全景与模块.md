# 第 01 章 · 全景与模块:配置即类型

> 基线:commit `56e3a88`。行号以 caddy.go、modules.go、context.go、admin.go 为准。

## 1.0 全景:配置加载的生命周期

```
JSON/Caddyfile → Load → changeConfig(caddy.go:115/158)
  → unsyncedDecodeAndRun(:337) → run(:419) → provisionContext(:484)
      (顺序:日志→存储→admin→apps)
  → 新配置完全 Start 后:currentCtx = ctx 单指针换(:368-372)
  → 才 unsyncedStop(oldCtx)(:375)——旧 app 逐个 Stop(:724-742)+Cleanup
```

**热重载的原子切换**:新配置完全跑起来才换指针,失败回滚三层——模块级 Cleanup、config 级 cancel+恢复 certmagic 存储(:505-520)、rawCfg 级重新 unmarshal 旧 JSON(:248-264);配置未变时 errSameConfig 跳过(:220-223)。某 app Start 失败回滚已启动 apps(:449-457)。

## 1.1 模块体系:注册类型,运行时造实例

`caddy.Module` 接口只有一个方法 `CaddyModule() ModuleInfo{ID, New}`(modules.go:54-77)——**注册的是类型,实例由 LoadModuleByID 运行期现场制造**(同一 ID 可多实例)。注册表是 `map[string]ModuleInfo`(:379-382),RegisterModule 在包 init 期调用,重复/保留 ID 一律 panic(:138-161,:144-146)。模块 ID 是 `<namespace>.<name>` 约定(http、http.handlers/http.matchers、caddy.storage.file_system、admin.api.load)。

**配置即类型**:`LoadModuleByID` 四步=New→StrictUnmarshalJSON(DisallowUnknownFields)→Provision→Validate→记入实例账本(context.go:364-465);宿主用 struct tag `caddy:"namespace=... inline_key=..."` 声明插槽,反射加载(:188-287)。标准发行版只是 modules/standard/imports.go:7-19 的 **13 个空导入**——官方版与定制版结构等价,xcaddy 的插件经济学(构建=import+编译)由此成立。

## 1.2 Admin API 与 Replacer

Admin API 默认 **localhost:2019**(admin.go:1450-1459;/load 端点本身是模块 admin.api.load,caddyconfig/load.go:47-66,支持 Content-Type 自动适配 Caddyfile);@id 索引与 /id/ 短路径内部重定向(caddy.go:290-327);DNS rebinding/Origin 校验(:871-896)——**默认只听 localhost 的安全默认**。Replacer 占位符系统(replacer.go:39-45)三级 provider 链(全局 env/system/time→file.*→static),请求级由 addHTTPVarsToReplacer 动态 Map(caddyhttp/replacer.go:58)。

## 1.3 设计动机

1. **为什么 JSON 是核心格式而 Caddyfile 是糖**:JSON 可编程(API 可生成/修改),Caddyfile 可人写——**两种受众两种格式,单向编译**;
2. **为什么模块是类型**:热重载时同一模块可多实例并存(新旧配置各一份)——注册实例会锁死重载;
3. **原子切换的单指针**:currentCtx 一根指针的交换是重载的全部"事务"——回滚=不换指针+恢复现场;
4. **默认安全作为产品**:admin 锁 localhost、自动 HTTPS、零信任 XFF——安全不是选项是出厂状态。

## 1.4 FAQ

**Q1:Caddyfile 和 JSON 什么关系?**
单向编译:Caddyfile→JSON(:load 端点自动适配);JSON 是运行时唯一真相。

**Q2:热重载会断连接吗?**
不会:新配置完全 Start 后才停旧实例(:368-375)——套接字由存活的旧实例保持到交接完成。

**Q3:插件怎么装?**
xcaddy build:插件=Go 包,构建=空导入+编译(README.md:143-158)——Go 生态的模块分发。

**Q4:admin API 暴露公网危险吗?**
默认只听 localhost:2019(:1450-1459)+Origin/DNS-rebinding 校验(:871-896)。

**Q5:未知字段会报错吗?**
会:StrictUnmarshalJSON(:390)——配置打错字当场发现。

**Q6:模块 ID 能随便起吗?**
命名空间约定+保留 ID panic(:144-146):caddy/admin 保留。

**Q7:占位符的性能?**
三级 provider 链+请求级动态 Map(:39-45):常用的在链头。

**Q8:失败回滚会恢复证书状态吗?**
会:certmagic 存储换绑也回滚(:505-520)。

**Q9:日志怎么按模块分流?**
配置驱动 zap 组装,按模块 ID Tee 多路(logging.go:219-246),writer 用 UsagePool 跨重载共享。

**Q10:事件系统能干嘛?**
同步 DOM 冒泡事件总线(caddyevents/app.go:208 起):证书/配置生命周期可挂钩。

## 1.5 小结与深挖方向

本章结论:**模块体系="注册类型+运行时造实例+单指针原子切换+三层回滚"**。深挖:

1. StrictUnmarshalJSON(:390)对嵌套模块的错误信息质量;
2. instance 账本(:364-465)在频繁重载下的泄漏面;
3. Replacer 链在模板重负载的耗时占比;
4. events 总线(:208)的同步冒泡在慢订阅者的阻塞;
5. UsagePool 跨重载共享的清理时机。
