# 第 02 章 · 页面与文件布局:16 字节页头与"无序列化"的 B+ 树镜像

> 基线:commit `fd01fc79`(boltdb/bolt 归档版 master)。核心:page.go / freelist.go / db.go。

## 2.0 全景:单文件逐页布局

```
文件偏移   页    类型       内容
0x0000   p0   meta      magic=0xED0CDAED ver=2 pageSize=root={3} freelist=2 pgid txid(偶) cksum
0x1000   p1   meta      上一份快照(txid 奇偶交替写,db.go:1008)
0x2000   p2   freelist  [16B 页头|count|排序 pgid 数组(ids+pending 全量落盘)]
0x3000   p3   branch/leaf  根 bucket:子 bucket 以 16B {root,sequence} 值内联
0x4000   p4   leaf      [16B 页头|count×16B 元素|key/value 数据区](可接 overflow 连续页)
                        p5 p6 ... 高水位 meta.pgid 之前的已分配页
```

纠偏:页头是 **16 字节**而非常被误传的 8/12——它由 `unsafe.Offsetof(page.ptr)` 求得,`ptr` 只是标记元数据区起点的占位字段,一个字节都不落盘(page.go:10, 30-36);"4KB 页"也不是常量,默认取 `os.Getpagesize()`,旧库以 meta 自述的 pageSize 为准(db.go:40, 204-218)。

## 2.1 页头四字段与 bptr 取址

`page` 四字段:id(pgid)/flags/count/overflow(page.go:30-36)。flags 只有 4 个位可组合:branch 0x01、leaf 0x02、meta 0x04、freelist 0x10;元素级另有 bucketLeafFlag=0x01 表示"这个 entry 的值是一个子 bucket"(page.go:17-26)。分支/叶子元素都是 16 字节定长,branch 是 pos+ksize+pgid,leaf 多 flags/vsize(page.go:97-115)。key/value 不存在元素里,集中排在元素数组之后,元素只记**相对自身地址**的偏移:

```go
// page.go:118-127
func (n *leafPageElement) key() []byte {
    buf := (*[maxAllocSize]byte)(unsafe.Pointer(n))
    return (*[maxAllocSize]byte)(unsafe.Pointer(&buf[n.pos]))[:n.ksize:n.ksize]
}
func (n *leafPageElement) value() []byte {
    buf := (*[maxAllocSize]byte)(unsafe.Pointer(n))
    return (*[maxAllocSize]byte)(unsafe.Pointer(&buf[n.pos+n.ksize]))[:n.vsize:n.vsize]
}
```

`[maxAllocSize]byte` 巨型数组只是 Go 的指针运算语法,零实际分配(page.go:59);写入时 `elem.pos = &b[0] - elem`,先排 count 个元素再连续追加 key/value(node.go:210-243)。

## 2.2 无序列化层:文件即内存

全库非测试代码 **0 处 encoding/binary**(grep 核实):写盘是 Go struct 内存原样 `WriteAt`(tx.go:500),读是只读 mmap 直接 cast 指针——

```go
// db.go:792-795
func (db *DB) page(id pgid) *page {
    pos := id * pgid(db.pageSize)
    return (*page)(unsafe.Pointer(&db.data[pos]))
}
```

推论:**文件端序 = 宿主机端序**,跨大小端机器拷库无任何转换层(代码层核实;官方兼容性声明未核实)。count 超过 0xFFFF 时 `node.write` 直接 panic(node.go:199-202)。

## 2.3 meta 页:双页交替与窄校验

meta 结构 64 字节:magic/version/pageSize/flags/根 bucket/freelist 页号/高水位 pgid/txid/checksum(db.go:970-980)。三个纠偏:校验是 **FNV-1a 64** 而非 CRC,只哈希 checksum 之前的 56 字节,且 **checksum==0 时完全跳过校验**(db.go:988, 1018-1022);数据页没有任何校验,完整性全靠"先写数据页并 fdatasync、再写 meta"的顺序(tx.go:196-224)。meta 写到 p0 还是 p1 由 txid 奇偶决定,读端取 txid 较高且 validate 通过的一份,失败回退另一份,双双失败才 panic(db.go:1007-1012, 803-824)。

## 2.4 overflow 与 freelist:页级记账

大 value 不拆节点:spill 按 `node.size()` 一次分配连续多页,页头 overflow 记录"紧随的额外页数"(页级 uint32,不是 per-value 链表;page.go:34, node.go:368);释放时按 `p.id..p.id+overflow` 区间展开入 freelist,cache 判重防双 free(freelist.go:116-128)。freelist 三件套:`ids` 有序可分配、`pending[txid]` 等读事务退出、`cache` 并集判重(freelist.go:11-15);分配是 O(n) **首适应**找连续段(freelist.go:67-107)。纠偏:**freelist 页恒存在于文件**——建库即写空页(page 2),每次 commit 释放旧页、把 ids+pending 排序合并后全量重写一页,pending 也落盘因为崩溃后必成空闲(db.go:366-370; tx.go:174-186);count≥0xFFFF 表示真实条数藏在数据区第一个 pgid 里(freelist.go:166-170, 205-209)。

新建文件 `Init` 一次写 4 页:meta0(txid=0)/meta1(txid=1)/空 freelist/空根叶页,`root={3}`、高水位 4(db.go:345-377)。

## 2.5 设计动机

1. **零拷贝读**:mmap+cast,读路径无反序列化、无复制(bolt_unix.go:47; db.go:792-795);
2. **pos 相对偏移**:页数据可放任意地址直接 cast,无需重定位(page.go:118-127);
3. **双 meta 原子切换**:写坏一份用另一份回退,免去 WAL(db.go:803-824);
4. **freelist 全量重写**:页级写放大换来格式极简,单文件无日志(tx.go:174-186);
5. **pending 按 txid 分组**:已释放页在所有可能引用它的读事务退出前不可复用,MVCC 长读的前提(db.go:530-539);
6. **页大小跟 OS 页**:与 page cache 单位一致减少写放大(db.go:40)。

## 2.6 FAQ

**Q1:为什么有两份 meta?**
txid 奇偶交替写 p0/p1,崩溃后回退到上一份一致快照(db.go:1008)。

**Q2:page.ptr 会落盘吗?**
不会,仅标记页头结束,页头大小即其偏移 16B(page.go:10, 35)。

**Q3:页内元素数组 `[0x7FFFFFF]T` 会分配内存吗?**
不会,只是指针运算惯用法(page.go:59)。

**Q4:value 比一页大怎么办?**
一次分配连续多页,页头 overflow 计数,node 不拆(node.go:368; page.go:34)。

**Q5:key/value 最大多少?**
MaxKeySize=32768、MaxValueSize=(1<<31)-2(bucket.go:11-15)。

**Q6:数据页有校验吗?**
没有;只有 meta 前 56 字节的 FNV-1a,且 0 值跳过(db.go:988, 1018-1022)。

**Q7:空库文件多大?**
4 页:meta0/meta1/空 freelist/空根叶(db.go:348-377)。

**Q8:freelist 页 count=0xFFFF?**
真实条数在数据区第一个 pgid 里,突破 16 位上限(freelist.go:166-170)。

**Q9:文件能跨大小端吗?**
格式即宿主端序原始内存,代码无转换层;跨端序行为未在代码层处理。

**Q10:崩溃瞬间写了一半的页怎么办?**
meta 未更新则整事务不可见;已更新则数据页必已 fdatasync——顺序是唯一保障(tx.go:196-224)。

## 2.7 小结与深挖方向

本章结论:**布局="16B 页头+定长元素+尾部数据区,pos 相对偏移,零序列化,双 meta 原子切换,页级 overflow/freelist 记账"**。深挖:

1. bbolt 把 O(n) 首适应分配器改成 hint/hash 版,对比本 commit 衡量收益(freelist.go:67-107);
2. bolt_windows.go 的 mmap 与 `grow()` 跳过 Truncate 分支对布局可靠性的影响(db.go:875-884);
3. s390x(brokenUnaligned)上生成的库在 x86 上读取的实际后果;
4. `Tx.Page()` 把 free 页作为第 5 种类型暴露给 `cmd/bolt info` 的实现边界(tx.go:601-624);
5. mmap 尺寸策略(倍增→1GB 步进,db.go:308-340)与 InitialMmapSize 的适用场景。
