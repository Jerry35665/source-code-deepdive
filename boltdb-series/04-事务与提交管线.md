# 第 04 章 · 事务与提交管线:无 WAL 的影子分页与两次 fdatasync

> 基线:commit `fd01fc79`。核心:tx.go / db.go / freelist.go。

## 4.0 全景:commit 六阶段与磁盘状态

```
 事务内(内存)              commit 流水线                      磁盘 / meta
 node 改动全在堆    [1] rebalance   tx.go:156              (旧 B 树完整有效)
 tx.pages 脏页缓冲 ─[2] spill       tx.go:163  旧页→pending[txid],新页→脏页缓冲
                   [3] 重写 freelist tx.go:176-186          新 FL 页已写(未发布)
                   [4] grow         tx.go:189  增长才 Truncate+Sync(Windows 免 Truncate)
                   [5] 写脏页+落盘   tx.go:198  按 pgid 排序 WriteAt ──► fdatasync①(数据持久)
                   [6] writeMeta    tx.go:221  p.id=txid%2(db.go:1008)─► fdatasync②(发布)
                   [7] close:rwlock.Unlock;OnCommit
 崩溃于[5]前:meta_old 原样,新页是垃圾   崩溃于[6]中:两份 meta 取 txid 高且校验过者(db.go:803-824)
```

纠偏:mmap 对**所有人**都是 `PROT_READ|MAP_SHARED`,连写者也无法原地改页(bolt_unix.go:48-50)——写事务的一切变更在堆内存 node 上,commit 才经 `writeAt` 系统调用落盘(tx.go:500);"两次落盘都是 fsync"也不准确,Linux 下是 `syscall.Fdatasync`(bolt_linux.go:8-9),文件增长的 commit 最多三次同步(另有一次 grow 的 Truncate+Sync,db.go:875-884)。

## 4.1 四把锁与开启序列

rwlock(全局单写者)/metalock(meta 读取+txs 表)/mmaplock(remap 期间保护映射)/statlock(统计)(db.go:118-121)。读通道 beginTx 先 metalock 后 mmaplock(与写事务同序防死锁),metalock 临界区内完成快照拷贝并挂入 txs(db.go:470-493);写通道 beginRWTx 先 `rwlock.Lock()`(解锁权移交 tx.close,tx.go:272)→ 挂 `db.rwtx` → 顺手 release 过期 pending(db.go:512-539),它不碰 mmaplock——remap 推迟到 commit 需要 allocate 时。快照本体就是一次 64 字节 meta 结构体赋值,ro 事务 txid 不递增(tx.go:48-61)。

## 4.2 读快照为何稳定:三重保障

1. **页内容不可变**:修改一律写新页,mmap 只读,已发布页从不原地改写;
2. **pending 协议**:释放的旧页挂 `pending[释放者txid]`,只有最老读事务退场后才转正(freelist.go:111-129);
3. **映射稳定**:ro 事务从 beginTx 起持 `mmaplock.RLock` 直到 removeTx(db.go:475, 547),remap 的写锁拿不到,读者脚下的 mmap 不会被换掉。

写事务内部读页走 `tx.page`:先查脏页缓存再落 mmap(tx.go:571-581),所以写者看到的是自己的新版本。

## 4.3 页复用闸门:minid-1 的保守语义

beginRWTx 尾部(db.go:530-539):取现存读事务最小 txid,`release(minid-1)` 把"释放者代际 ≤ minid-1"的 pending 页整体排序合并进可分配链(freelist.go:132-144)——因为 txid=T 释放的页只可能被 txid<T 的读者引用,保守留 1 的间隔恰保证引用者全部退场;无读事务时一次放行全部积压。**长读事务的双重后果**:pending 永不 release → 写者只能追加新页,文件膨胀(tx.go:20-23 文档原话);文件增长触发 remap → 写者卡在 `db.allocate → db.mmap`(db.go:847)。同一 goroutine 先 View 后 Update 会**自我死锁**,文档明确警告(db.go:448-455),解药是预设 InitialMmapSize(db.go:911-919)。

## 4.4 rollback:零磁盘写

rw 回滚两步:`freelist.rollback` 删本 txid 的 pending,`freelist.reload` **整表重读**盘上 freelist 页并与盘面对齐(tx.go:249-258)——新分配页从未上盘 freelist,撤掉 pending 后内存视图与"上次提交"完全一致;meta 未写,WriteAt 过的数据页沦为不可达垃圾等未来收编。ro 事务只能 Rollback:对它 Commit 得到的是 **ErrTxNotWritable** 而非 ErrTxClosed(tx.go:148-150),View 统一以 Rollback 收尾(db.go:636);托管事务手动 Commit/Rollback 即 panic(tx.go:145, 241)。

## 4.5 Update 与 Batch:独占事务 vs 单事务合并

第二个并发写事务阻塞在 rwlock 上直到前者 close,完全串行(db.go:512; tx.go:272)。Update = 独占一个写事务,fn 出错回滚、panic 被 defer 兜底(db.go:581-606)。Batch 是延迟合并:1000 个调用或 10ms 触发(db.go:34-35),**所有 fn 在同一个 Update 事务里顺序执行**,失败者摘出、给其提交者回 trySolo 单独重跑,其余继续(db.go:717-743)——fn 可能被执行多次,幂等是硬要求(db.go:649-654)。

## 4.6 tx.check:唯一能抓"rollback 泄漏页"的检查

四类校验(tx.go:383-454):freelist 全集无重复页(防双重释放)、meta/freelist 页标记可达、递归检查每页越界/多重引用/可达已释放/非法类型、线性扫描高水位以下"不可达且未释放"。StrictMode 使其随每次 commit 执行并 panic(tx.go:205-218)——大库上成本极高(db.go:46-49)。

## 4.7 FAQ

**Q1:并发两个写事务?**
第二个阻塞在 rwlock 直到前者 close,串行(db.go:512)。

**Q2:View 里 Put 报什么?**
ErrTxNotWritable(bucket.go:289);已关闭是 ErrTxClosed。

**Q3:快照拷的是什么、何时拷?**
metalock 下拷 64 字节 meta 结构体+根 bucket(tx.go:48-55)。

**Q4:长读事务最坏拖垮什么?**
文件膨胀(tx.go:20-23)+写者卡死在 remap(db.go:847)。

**Q5:commit 中途失败会坏库吗?**
不会,meta 未写则旧版生效,每步失败即 rollback(tx.go:164 等)。

**Q6:txid 何时递增?**
仅写事务 init 时 +1,同时决定 commit 写哪份 meta(tx.go:58-61; db.go:1008)。

**Q7:NoSync 省掉什么?**
两次 fdatasync;NoGrowSync 另管增长的 Truncate+Sync(tx.go:520-524, 557-561; db.go:875-884)。

**Q8:Batch 的 10ms 是固定延迟吗?**
是上限:凑满 1000 个立即触发,不满则等到超时(db.go:664-675)。

**Q9:本版有 Mlock 吗?**
没有,全仓 grep 为空;Mlock 是 bbolt 后期特性(bolt_unix.go:48-59)。

**Q10:WriteTo 复制时 meta 有什么讲究?**
给第二份 meta 人为减 1 保持奇偶互补,保证副本可从任一份恢复(tx.go:328-330)。

## 4.8 小结与深挖方向

本章结论:**提交=堆上影子分页+排序落盘+fdatasync+meta 奇偶翻转;读快照=64 字节拷贝+pending 协议+mmaplock**。深挖:

1. FillPercent 与 25% 合并阈值对写放大的量化(node.go:419; bucket.go:33);
2. mmapSize 增长曲线与 InitialMmapSize 对长读死锁的规避(db.go:308-340);
3. 连续段分配的碎片化与大事务下的空间退化(freelist.go:67-107);
4. Windows 免 Truncate 的 grow 与 fdatasync 退化对提交延迟的影响(db.go:876);
5. 与 bbolt 的 NoFreelistSync/Mlock/idle 超时对照,反推本版痛点。
