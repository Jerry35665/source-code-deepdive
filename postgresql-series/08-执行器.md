# 第 08 章 · 执行器:volcano 拉模型与表达式虚拟机

> 基线:commit `8c7a74c`。行号以 src/backend/executor/ 为准(README 先读:计划树是 "demand-pull pipeline",README:6-11)。PG 是拉模型(volcano)最后一代主流实现——本章讲它为什么活了 30 年、以及它如何用三招削平解释开销。

## 8.0 全景:计划树与拉流

```
计划树(规划器产物,只读) ──ExecInitNode 递归──→ 状态树(可变,镜像结构)
                                                     │
用户 ExecFetch ← Gather ← HashJoin ←←←←←←← 每行一次函数指针调用
                                              (node->ExecProcNode(node))
```

**计划树只读+状态树镜像**(README:47-59)是 EXPLAIN/计划缓存/并行的共同地基。分发行数极少:`ExecProcNode` 是 static inline(executor.h:321-328,包装在 execProcnode.c:448-470):查 chgParam 触发 ReScan,然后一次函数指针调用——无 switch 无虚表。节点四函数约定(nodeSeqscan.c 样本):Init(:220)/Exec(:119)/End(:303)/ReScan(:347),真正取数在 SeqNext(:52-93)经 table AM。

## 8.1 三种 join:三种状态机

- **HashJoin**(nodeHashjoin.c:182-189 状态机,:224-793 实现):build(内表建哈希)→probe(外表探测);**批溢出**:内表超 work_mem 按哈希位分批写批文件(:507-529,:1570-1602),批数恒 2 的幂、增长即翻倍(nodeHash.c:1055)——溢出不是失败,是降速续跑;
- **MergeJoin**(nodeMergejoin.c:107-117,11 状态):有序双流归并;mark/restore(:153,:995,:1106)——重复键时回滚内表游标重扫;
- **NestLoop**(nodeNestloop.c:120-142):参数化内表——外行值写 PARAM_EXEC 强制内子树 ReScan,把"每行一次子查询"变成"每行一次参数化重扫"。

hash agg 的溢出三段(:1864 检查→:1908 spill 模式→:2681 批次栈递归重灌)与并行聚合的 combinefn 替换(nodeAgg.c:3939-3950)同属"内存不够就分层"一族。

## 8.2 表达式虚拟机:EEOP 操作码

`ExecInitExpr`(execExpr.c:143)把表达式树**编译成扁平步骤数组**(ExprState->steps[],约 120 个 EEOP opcode,execExpr.h:66-296);首步 FETCHSOME 预 deform,Var 步退化为数组下标。解释器 `ExecInterpExpr`(execExprInterp.c:470)双派发:**gcc/clang 用 computed-goto 直通线程**(:104-143 宏,:121),否则 switch(:126);约 20 个 ExecJust* 快路径(:158-178)。**JIT 选择点** ExecReadyExpr(execExpr.c:902-908):先试 jit_compile_expr,失败回解释器;阈值 jit_above_cost=100000(jit.c:40,planner.c:699-721),GUC 默认 off(guc_parameters.dat:1453-1456)。对照 SQLite VDBE(02 卷):VDBE 字节码一次编译永远解释,PG 的 EEOP 是"解释与 JIT 之间可滑动的中间层"。

## 8.3 并行:Gather 与 chunk 协作

Gather 惰性启 worker:首次 Exec 才建 DSM 段(nodeGather.c:152-216,:263-391),reader 轮询+WaitLatch。**并行 scan 的分工**:table scan 按逻辑 2048 行的 chunk 分块,64 位原子变量领块(tableam.c:42-46,:521-531,:543-624),ramp-down 阶段逐块回收——worker 之间零通信,靠"原子领号"切分扫描空间。为什么不全默认并行:进程级 worker(01 章 fork)启动贵,小查询并行是负收益——**Gather 节点的代价模型决定一切**。

## 8.4 内存上下文:每 tuple 的 Reset

PG 的内存纪律:ExecutorState/ExprContext 分层(memnodes.h:117-134,AllocSet aset.c:546);每处理完一行 `ResetExprContext`(executor.h:659-660)= MemoryContextReset——三个 join 节点行首各一句(nodeHashjoin.c:250-254 等)。**不用逐对象 free,用上下文整块重置**——与 llama.cpp 的 bump allocator(第一系列)同宗:**生命周期分层,一次释放一层**。泄漏在 PG 里几乎不可能:上下文销毁即全清。

## 8.5 设计动机

1. **为什么 volcano 活了 30 年**:代价模型可控(每节点成本独立)、慢路径罕见(常量折叠+EEOP 扁平化+按需 JIT 三招削平解释开销,nodeSeqscan.c:119-215)、背压/提前终止自然表达(ExecShutdownNode,execProcnode.c:753)——**DuckDB 向量化是对的解释,PG 的回答是让解释变快**;
2. **溢出即降速**:hashjoin/agg 的 batch 机制把"内存不足"从错误变成慢路径——数据库的鲁棒性=所有资源约束都有降级路径;
3. **状态树镜像**:计划(不可变)与执行状态分离——计划缓存、EXPLAIN、并行复制计划树全部免费;
4. **原子领块**:并行 scan 的"自服务分工"零协调成本——与 FFmpeg 并行 scan 切片(15 章)、Git 无锁 clock(02 卷)同族。

## 8.6 FAQ

**Q1:volcano 一次一行,性能怎么够?**
三招:节点内常量折叠、EEOP 扁平化+computed-goto、按代价 JIT(execExpr.c:902-908)——解释开销被逐层摊薄。

**Q2:hashjoin 内存不够会失败吗?**
不会:分批写文件(:507-529),批数翻倍直到装下——降速不失败。

**Q3:mergejoin 为什么要 mark/restore?**
外表重复键时内表游标要回滚重扫(:995):有序归并的唯一复杂点。

**Q4:JIT 为什么默认关?**
编译成本高(llvm 依赖+首查询延迟),小查询负收益;jit_above_cost=100000 只对大查询划算(jit.c:40)。

**Q5:并行 worker 是进程还是线程?**
进程(01 章 fork),经 DSM 共享计划/元组队列——隔离公理贯穿到执行器。

**Q6:每行 Reset 内存,不慢吗?**
AllocSet 的 reset 是指针回卷(aset.c:546),O(1);比逐对象 free 便宜。

**Q7:表达式里的函数调用怎么处理?**
EEOP_FUNC 步骤:函数管理器查找后直调;SQL 内联(SQL functions)可在规划期展开。

**Q8:参数化内表的 ReScan 会重扫全表吗?**
不一定:内表若有索引,参数化作索引条件——NestLoop+索引是经典组合(:120-142)。

**Q9:并行 scan 怎么保证不重不漏?**
2048 行 chunk 的 64 位原子领号(tableam.c:521-531)——领号即所有权。

**Q10:EXPLAIN ANALYZE 的额外开销哪来的?**
 instrumentation 计时挂在每个节点——状态树镜像(:47-59)使插桩零侵入计划。

## 8.7 小结与深挖方向

本章结论:**执行器="volcano 骨架+EEOP 中间层+溢出降速+上下文内存"**;解释开销的持续摊薄是它对抗向量化浪潮的答案。深挖:

1. computed-goto(:121)在不同编译器的实际收益;
2. hashjoin 批翻倍(:1055)在倾斜数据的最坏批数;
3. Gather 惰性 DSM(:152-216)的 worker 启动延迟分布;
4. EEOP 120 个 opcode 的热点分布(真实负载采样);
5. JIT 表达式与 EEOP 步骤的混合执行边界。
