# 第 02 章 · 缓冲管理器:ReadBuffer 决策树与 clock sweep

> 基线:commit `8c7a74c`。行号以 src/backend/storage/buffer/(README 是官方设计文档,先读它是理解全文的地图)为准。

## 2.0 全景:一次 ReadBuffer 的决策树

```
ReadBuffer(bufmgr.c:879)→ReadBufferExtended(:926)→ReadBuffer_common(:1276)
 ├ 临时表 → LocalBufferAlloc(localbuf.c:119)——会话私有,零锁
 └ PinBufferForBlock(:1223)→BufferAlloc(:2197):
   ① InitBufferTag(:2216)→BufTableHashCode→分区锁 SHARED(:2223)
   ② BufTableLookup(:2224) 命中→PinBuffer(:2237)→放锁返回
   ③ miss→放锁→GetVictimBuffer(:2268):
        有 strategy→先试 ring(freelist.c:196-204)
        clock sweep:pin≠0 跳过(:263);usage≠0 CAS-1(:286);usage=0 CAS 抢 pin(:300)
   ④ 分区锁 EXCLUSIVE+BufTableInsert(:2276);撞车改用对方 buf(:2278-2317)
   ⑤ BM_TAG_VALID+usage=1(:2336)→StartBufferIO 置 BM_IO_IN_PROGRESS(:7290)
      抢到者读盘置 BM_VALID;他人 WaitIO 等 io_wref(:7188-7247)
```

**BufferDesc 双状态**:tag(在哪)+状态字;master 已合入 AIO——内容锁不再用 LWLock 而是状态字高位实现(buf_internals.h:303-310)。状态字是**单个 64 位原子字**:18 位 refcount+4 位 usage+12 位 BM 标志+锁位(buf_internals.h:34-55);BM_ 标志(BM_PIN_COUNT_WAITER/BM_IO_IN_PROGRESS 等,:106-127);BufferDesc 强制 64B 缓存行 pad 防伪共享(:326-359)。

## 2.1 Pin 语义:最小临界区

Pin=引用计数+1 的 CAS,持有期间页内容可依赖。设计要点:PinBuffer 的 CAS 加 pin(bufmgr.c:3295-3380);**LockBufferForCleanup 的 BM_PIN_COUNT_WAITER 协议**(单等待者限制 :6735-6740,热备恢复冲突处理 :6781-6814,bufmgr.c:6693-6859)——"等所有人放开"是窄场景专用,且一次只许一个等待者。**Pin 的哲学:持有时间最小化**,数据结构操作完立刻放,页的"逻辑锁"由上层(05 章 heavyweight)承担——锁语义分层。

## 2.2 clock sweep:有损计数器换掉 LRU 链表

淘汰走 clock 算法(freelist.c):时针 `nextVictimBuffer` 是 `pg_atomic_fetch_add_u32` 单调推进(ClockSweepTick,:119-127),仅回绕者持 strategy 自旋锁修 completePasses(:153-161);**扫描循环全 CAS 无锁**(:240-316):pin≠0 跳过、usage≠0 则 CAS-1、usage=0 则 CAS 抢 pin。usage_count 上限 5(buf_internals.h:144),pin 时 +1(bufmgr.c:3335-3340)——热页最坏要被扫 6 圈才逐出。

**为什么不用 LRU 链表**(对照 Redis LFU/LevelDB LRU):多进程下链表移动需要全局锁,clock 的"路过就衰减"把驱逐变成无锁扫描——**牺牲局部性精度换并发自由度**,这是 1 章"多进程共享内存"公理在内存策略上的投影。

## 2.3 哈希表与分区锁

BufMappingTag{rnode,fork,blocknum}→buffer id(buf_table.c),表大小 NBuffers+128(:62);**分区锁**:hashcode % NUM_BUFFER_PARTITIONS(bufmgr.c:250),128 个分区(lwlock.h:83)——查找只锁 1/128。整个 BufferAlloc 只在①④两步拿分区锁,其余全 CAS——**锁的粒度被切到"必须互斥的最小窗口"**。

## 2.4 ring buffer:扫描预算思想的又一现身

大表扫描会冲刷整个缓冲池——PG 的解法是 BufferAccessStrategy:VACUUM 用 2MB ring(:490,GUC vacuum_buffer_usage_limit)、BULKREAD 256KB(:459)、BULKWRITE 16MB(:487),封顶 NBuffers/8(:526);ring 内循环复用,BULKREAD 还会**踢脏页重挑**(StrategyRejectBuffer,:752-770)。对照:Git 的 --window/--depth、FFmpeg probesize、Redis 淘汰预算——**"给批处理任务配小预算"是跨领域共识**。

## 2.5 脏页与写路径分工

MarkBufferDirty 只置 BM_DIRTY 不触发 I/O(bufmgr.c:3170-3219);写盘三方:**victim 路径 backend 自刷**(:2634)、bgwriter 沿时针前方清扫(BgBufferSync :3854,读时针不推时针 freelist.c:331——只帮别人擦,不抢针)、checkpointer 全池 BufferSync(:3575)。**WAL 先行铁律**:数据页写盘前必先 XLogFlush 页 LSN(:4584-4585)——03 章的地基。

## 2.6 设计动机

1. **为什么 8KB 页+共享缓冲池**:磁盘 I/O 单位×多进程共享——池住在 shmem(01 章),锁设计全部围绕"多进程并发访问同一数组";
2. **Pin 是锁语义分层的支点**:缓冲结构保护(物理)与数据一致性保护(逻辑)分离,05 章三层锁金字塔由此展开;
3. **clock 的 O(1) 无锁推进**:多进程下"精确的 LRU"成本高于"近似的 clock"——又一次"数量级决定数据结构"(Redis 事件循环单线程才敢用真 LRU 链);
4. **ring buffer 是产品级自律**:VACUUM 主动放弃缓存局部性换取"不伤及他人"——批处理代码主动约束自己,是工程文化的体现。

## 2.7 FAQ

**Q1:缓冲池命中了还要拿锁吗?**
要,但只拿 1/128 的分区共享锁(bufmgr.c:2223-2240)——128 分区把竞争切到 1/128。

**Q2:clock 和 LRU 差在哪?**
clock 无链表:路过衰减 usage(0-5),逐出扫到 0 为止——多进程无锁,代价是"最坏 6 圈"(buf_internals.h:144)。

**Q3:VACUUM 为什么反而少用缓冲?**
ring 2MB(:490):大表扫描若正常缓存会冲刷全池——主动小预算保护 OLTP 热页。

**Q4:两个 backend 同时 miss 同一页怎么办?**
StartBufferIO:抢到 BM_IO_IN_PROGRESS 者读盘,他人 WaitIO(:7188-7247)——IO 去重。

**Q5:脏页谁写盘?**
三方分工:淘汰时 backend 自刷(:2634)/bgwriter 前方清扫(:3854)/checkpointer 全池(:3575)——各自触发时机不同。

**Q6:为什么写数据页前要 XLogFlush?**
WAL 先行(:4584-4585):崩溃后重放必须能覆盖页的新内容——03 章的地基铁律。

**Q7:临时表走共享池吗?**
不走:LocalBufferAlloc(localbuf.c:119)会话私有,零锁——隔离换简单。

**Q8:refcount 是 18 位,会溢出吗?**
单连接最多 10M pin;超限报错——数组型资源天然有界。

**Q9:AIO 合入后锁变了什么?**
内容锁从 LWLock 变状态字高位(buf_internals.h:303-310),等待走 io_wref 条件变量——待 I/O 语义仍在演进。

**Q10:usage_count 为什么封顶 5?**
4bit 字段(:34-55)+"够区分冷热即可"——有损计数器的位数就是精度的预算。

## 2.8 小结与深挖方向

本章结论:**缓冲管理器 = "64 位原子状态字 + 128 分区锁 + 无锁 clock + ring 预算"**;所有并发设计都在回答 01 章"多进程共享内存"公理。深挖:

1. 128 分区数(lwlock.h:83)在高核数下的竞争水位;
2. StrategyRejectBuffer(:752-770)的"踢脏页"与 WAL 先行的交互;
3. AIO 状态字锁(:303-310)与 PG17 前 LWLock 版本的吞吐对比;
4. ring 封顶 NBuffers/8(:526)对小 shared_buffers 部署的失配;
5. clock 6 圈 worst-case 在顺序扫描负载的实际命中率。
