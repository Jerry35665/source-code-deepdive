# 第 10 章 · 复制与逻辑解码:WAL 的三类消费者(卷末)

> 基线:commit `8c7a74c`。行号以 src/backend/replication/ 为准。卷一 03 章 WAL 是本地日志——本章讲它的三类消费者:本地恢复(03 章)、物理 standby(字节流)、逻辑订阅(解码为变更流)。

## 10.0 全景:一张日志,三种读法

```
WAL ─┬─ 本地恢复:startup 重放(卷一 03 章,xlogrecovery.c:1897)
     ├─ 物理 standby:walsender 原样转发字节流 → walreceiver 落盘
     └─ 逻辑订阅:walsender → decode → snapbuild → reorderbuffer → 输出插件 → apply worker
```

**物理=不改一个字节**(复制正确性锚定在 03 章刷盘纪律:walsender.c:3489 只发本机已 GetFlushRecPtr 的 WAL);**逻辑=读侧重排**(把内部恢复日志升格为公共 API)。

## 10.1 walsender 状态机与流式协议

状态机:STARTUP→CATCHUP(StartReplication,walsender.c:991)→**STREAMING(仅当追上且输出缓冲空**,:3134-3139——同步复制以此为硬分界)→STOPPING;逻辑侧同一循环换 send_data=XLogSendLogical(:1601)。协议消息 'w'(数据)/'k'(keepalive)/'r'(反馈)/'h'(hsfeedback)(protocol.h:75-84);心跳=半超时 ping(:4466,:4485)。两个正确性细节:**只发已 flush 的 WAL**(:3489);**MAX_SEND_SIZE 页边界截断,绝不拆 WAL 记录跨消息**(:3558-3587)——walreceiver 隐含依赖此契约。接收端 walreceiver:fsync→共享内存 flushedUpto→唤醒恢复/级联/主库反馈(XLogWalRcvFlush,:1093)。**'r' 反馈一箭三雕**(:2642-2648):喂 pgstat、SyncRepReleaseWaiters、槽推进。

## 10.2 同步复制:等待与不可回滚

`SyncRepWaitForLSN`(syncrep.c:149):XLogFlush(03 章)之后,按 LSN 有序入队(:382),**latch 无超时等待**(:341);等待中不可转为回滚——事务已本地提交(:301-335)。walsender 收 'r' 反馈调 SyncRepReleaseWaiters(:484):优先级模式取最老 LSN(:669),`ANY n` quorum 取第 n 新(:702;语法 syncrep_gram.y:70)。**全部同步 standby 掉线则 primary 提交挂起**——这是设计立场:同步复制的承诺就是"宁可停,不丢"。

## 10.3 复制槽:回收的额外边界

槽(slot.c)是"订阅者的锚":物理槽单锚 restart_lsn(walsender.c:2512 推进);逻辑槽双锚 restart_lsn+**confirmed_flush**(logical.c:1902,**只进不退** :1930-1931,防重复投递)。槽是 checkpoint WAL 回收的额外下界(xlog.c:8571 KeepLogSeg←slot.c:1306)——卷一 04 章"WAL 段在 pg_control 更新后才回收"的第三重边界(槽/catalog_xmin/检查点);逻辑槽还锁 catalog_xmin(:1224)防止系统表被 vacuum 掉(订阅端还可能要读)。**失效防御**:`max_slot_wal_keep_size_mb` 闸门触发五类失效(slot.c:116-120,执行 :2218,调用点 xlog.c:7909/8382/9280)——**宁可订阅者重建,不可主库磁盘卡死**;这与 G 章 failsafe 同款哲学:正确性债优先于可用性债。

## 10.4 逻辑解码:最难的十进制问题

变更记录只带 xmin,解码器回放历史 WAL 时"**先见 commit、变更在前**",且启动点任意——无法从 WAL 本身重建可见性快照。解法:primary 周期写 xl_running_xacts,snapbuild.c:1244 `SnapBuildFindSnapshot` **四路状态机**(START→BUILDING_SNAPSHOT→FULL_SNAPSHOT→CONSISTENT,:1300/:1330/:1350/:1384/:1408),每级等上一代运行事务真正终结。关键陷阱(:1345-1348):running_xacts 的 xids 数组**不可信**——事务被标记 running 时其 commit 记录可能已入 WAL,只能以 nextXid 为界等待。reorderbuffer 按提交序重排,超 logical_decoding_work_mem 时**挑最大事务 spill 到磁盘**(ReorderBufferCheckMemoryLimit :3928,:4029)或流式发出(:4374);输出插件回调 begin/change/commit(logical.c)由 apply worker(worker.c)消费,pgoutput 是官方插件。

## 10.5 物理与逻辑对比、与前作对照

| | 物理复制 | 逻辑解码 |
|---|---|---|
| 单元 | WAL 字节(页级) | begin/change/commit(行级) |
| schema | 两端必须一致 | 可不同(表映射) |
| 用途 | HA/灾备 | 订阅/CDC/升级 |
| 延迟语义 | flush 位点 | confirmed_flush(确认点) |

对照:etcd raft 的日志即共识(日志成员资格是协议的一部分);PG 物理复制=**日志是备份**(协议外挂);MySQL binlog 是双日志(内部 redo+对外 binlog),PG 逻辑解码用**读侧 reorder 换掉双日志**——一份日志两用,复杂度压进读端。K8s informer 的 List+watch(第一系列)与逻辑槽的"锚+游标"同构。

## 10.6 设计动机

1. **为什么流复制不改 WAL 格式**:字节流转发零 CPU 逻辑损耗,且与恢复共用同一正确性基础(:3489)——**同一日志服务三类消费者是 PG 存储层的总纲**;
2. **逻辑解码把复杂度放读端**:写端(WAL)保持为恢复优化的形态;解码的 reorder/snapbuild 全在订阅侧——写路径零污染;
3. **槽是"订阅即资源"**:订阅者能拖死生产者(WAL 不回收),所以槽必须是显式对象+可失效(:2218)——外部依赖的显式化管理;
4. **同步复制的不可回滚**(:301-335):等待期间事务已提交,这个"不完美"换来语义清晰——一旦等,只等成功或显式失败。

## 10.7 FAQ

**Q1:为什么 CATCHUP 之后才算 STREAMING?**
追上+缓冲空(:3134-3139)才承诺实时;同步复制依赖这个硬分界。

**Q2:同步复制会永久挂起吗?**
会:全部同步 standby 掉线时(:341 无超时)——管理员需降级 synchronous_standby_names,这是立场不是缺陷。

**Q3:逻辑槽的 WAL 积压怎么自愈?**
max_slot_wal_keep_size_mb 触发失效(:2218):槽标记丢失,订阅端重建——主库优先。

**Q4:解码为什么不能直接用 running_xacts 的列表?**
xids 数组不可信(:1345-1348):标记 running 时 commit 可能已在 WAL——以 nextXid 为界等终结。

**Q5:reorderbuffer 溢出到磁盘会丢吗?**
不会:spill 是完整事务落盘(:4029),回放时按 commit 序重组;流式(:4374)是增量发送。

**Q6:物理 standby 能读吗?**
能(hot standby):恢复重放+只读查询共存,冲突处理在 02 章 LockBufferForCleanup(:6781-6814)。

**Q7:confirmed_flush 为什么只进不退?**
倒退=重复投递(:1930-1931):订阅端至少一次语义的锚。

**Q8:'r' 反馈为什么三用?**
一条消息喂 stat/同步复制/槽推进(:2642-2648)——反馈通道最小化。

**Q9:大事务对逻辑解码的影响?**
先攒 reorder(内存→spill),提交时才发:大事务延迟到 commit——流式(:4374)是 PG14+ 的缓解。

**Q10:timeline 在复制里的角色?**
TLI 分支记录 promote 历史,standby 跟随新 TLI(简);坑位在卷三展开。

## 10.8 小结与卷二终语

本章结论:**复制="一份 WAL 三类消费者+槽作为显式订阅资源+逻辑解码的读侧复杂度"**。
