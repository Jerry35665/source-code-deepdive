# 第 11 章 · 查询规划器:代价模型与路径支配

> 基线:commit `8c7a74c`。行号以 src/backend/optimizer/ 为准。卷二 08 章讲了执行器(拉模型的下游)——本章讲上游:规划器如何在 join 顺序×访问方法的组合空间里选计划。

## 11.0 全景:流水线与两个自由度

```

    自由度① join 顺序   │  自由度② 每个关系的方法
```

## 11.1 Path 与支配淘汰

Path 五元组:rows/disabled_nodes/startup/total/pathkeys(pathnodes.h:2005-2011;PATH_REQ_OUTER :2015 是参数化依赖)。**add_path 的支配淘汰**(pathnode.c:43,459,473,518-526):新路径加入前按代价域比较——startup 与 total 是两个维度(物化/LIMIT 场景 startup 小的胜),fuzz 1.01 容差避免数值抖动,**参数化路径视为无 pathkeys**(:630-631)。每个 RelOptInfo 维护"不被支配的好路径集合"——**穷举的替代不是启发式,是支配剪枝**(对照 Git add_path 的"好路径集"与 IDA* 的剪枝思想)。

## 11.2 代价模型:常数与公式

锚点常数(cost.h:24-28):seq_page_cost=1.0、random_page_cost=4.0、cpu_tuple_cost=0.01(GUC 注册 guc_parameters.dat:553/2437/2652,支持表空间级覆盖)。cost_seqscan(costsize.c:271)一行式(:339):页数×顺序代价+(cpu+过滤)×tuples+目标列表×rows。**cost_index 的相关性修正**(:546):amcostestimate 回调给选择率与 correlation(:618);堆 I/O 用 Mackert-Lohman 缓存公式(:898)估 max_IO,完全相关时 min_IO=1 次随机+其余顺序,按 **correlation² 线性插值**(:785-787:`run_cost += max_IO + csquared*(min_IO-max_IO)`)——物理序与逻辑序的相关性(07 章统计量)直接决定索引扫描的 I/O 估计。行数=tuples×clauselist_selectivity(:5607,:5614-5618),终点是 eqsel 读 pg_statistic(selfuncs.c:302,N 章的消费入口)。

## 11.3 join 搜索:DP、GEQO 与塌缩上限

DP 标准搜索逐层 set_cheapest(allpaths.c:3942,:3977,:4014;join_search_one_level joinrels.c:78);表数超阈值时切 **GEQO 遗传算法**(enable_geqo && levels_needed >= geqo_threshold=12,allpaths.c:3905;染色体=Gene 排列,适应度=cheapest_total_path->total_cost,geqo_gene.h:33,geqo_eval.c:115)——**精确搜索空间指数增长时的实用主义**。笛卡尔积控制的塌缩上限:from/join_collapse_limit 默认 8(initsplan.c:1568,:1754)——超过后显式 JOIN 语法也不再约束顺序,这是"用户意图 vs 优化器自由"的仲裁点。

## 11.4 参数化路径与计划缓存

参数化路径(required_outer 传播,relnode.c:1897,:1934-1939;joinpath.c:840-842,:881,:971)把"外表当前行"作为内表的索引条件——NestLoop 的动力源(08 章)。**plancache**:前 5 次必 custom(常量内联),之后 generic_cost<平均 custom_cost 则转通用计划(plancache.c:1184,:1212,:1227,:1280);重规划成本按 1000×cpu_operator_cost×(nrel+1) 估计;失效注册 PlanCacheRelCallback(:156,DDL 触发)。通用计划省解析规划,定制计划吃到常量——**动态权衡,不是二选一**。

## 11.5 与前作对照与设计动机

| | PG 规划器 | SQLite | MySQL |
|---|---|---|---|
| 形态 | 模块化 Path 体系 | 单文件 NTM | 启发式+直方图 |
| join 搜索 | DP/GEQO 可切 | 深度有限 | 规则+有限枚举 |
| 代价可信度 | 依赖统计(N 章) | 内嵌小模型 | 依赖引擎反馈 |

1. **支配淘汰是搜索空间的正确压缩**:保留全部 Pareto 前沿(startup/total 双维),丢掉的只是被支配者——对照 FFmpeg add_path 式注册表的"先注册后竞选";
2. **代价参数可调是诚实的声明**:random_page_cost=4 是"SSD 时代该调到 1.1"的著名旋钮——模型常数暴露为 GUC,是对统计局限的坦白;
3. **GEQO 的存在本身是认知**:12 表以上的 DP 已不可行,宁可次优也要有限时间——规划器对自身复杂度的清醒;
4. **generic vs custom 的动态切换**(plancache.c):OLTP(参数化、高频)与 OLAP(字面量、一次)两种负载的折中自动化。

## 11.6 FAQ

**Q1:为什么小表走 seqscan 而不走索引?**
cost_index 的页 I/O+heap 回表估计超过顺序扫(:546 公式);correlation 差时更差。

**Q2:random_page_cost=1.1 是什么场景?**
SSD:随机与顺序差距缩小——代价常数与硬件匹配(默认 4 是机械盘时代)。

**Q3:GEQO 结果不稳定吗?**
遗传算法有随机性:同 SQL 不同时间可能计划不同——关键查询设 geqo_threshold=0 关闭。

**Q4:from_collapse_limit=8 的实际影响?**
8 表以上 JOIN 语法不再固定顺序(:1568):写子查询强制边界是唯一控制手段。

**Q5:计划缓存什么时候失效?**
DDL(PlanCacheRelCallback :156);统计更新不失效(N 章)——统计错了计划不会自动重选。

**Q6:LIMIT 为什么偏爱 startup 代价?**
get_cheapest_fractional_path(:537)按 fraction 加权 startup/total——LIMIT 10% 时 startup 小的计划胜。

**Q7:参数化路径和预编译语句什么关系?**
generic 计划的 PARAM_EXEC 槽位(:840-842):一次规划多次执行,参数从外部注入。

**Q8:为什么 PG 不做向量化?**
见 08 章:EEOP+JIT 是 PG 的回答——规划器/执行器的接口形状决定优化空间。

**Q9:统计多久更新一次?**
不自动失效缓存;ANALYZE 触发见 N 章(mod_since_analyze)——统计陈旧是慢性病。

**Q10:join 顺序为什么 DP 从小关系起?**
join_search_one_level(:78):每层取 cheapes 最小者扩展——贪心起点+完整层内枚举。

## 11.7 小结与深挖方向

本章结论:**规划器="路径支配淘汰+可调代价模型+DP/GEQO 分级搜索+动态计划缓存"**。深挖:

1. add_path fuzz 1.01(:459)在近似同代价路径的抖动;
2. correlation²(:785-787)在聚簇/乱序混合表的插值误差;
3. GEQO 种子与代数的收敛性(geqo_main.c);
4. generic 计划在慢参数(极端值)的负优化;
