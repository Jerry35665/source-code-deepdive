# 第 12 章 · 分区:逻辑统一与物理分散

> 基线:commit `8c7a74c`。行号以 src/backend/partitioning/、src/backend/executor/execPartition.c、src/backend/optimizer/path/partprune.c 为准。

## 12.0 全景:路由与剪枝的双面

```
INSERT → 根表 → 逐层 bound 判定(get_partition_for_tuple)→ 叶子(可能列映射转换)
SELECT → 剪枝(三时机)→ 多叶 Append/MergeAppend → 各叶子各自走 09 章 nbtree
```

共享边界结构 `PartitionBoundInfoData`:datums[]+indexes[]+null/default(partbounds.h:79-96)。三种策略的定位算法**刻意不同**:

- **hash**:各分区 (modulus,remainder) 排序后取最大 modulus 铺满 indexes[](create_hash_bounds,partbounds.c:347-421),定位纯取模 `indexes[rowHash % nindexes]`(execPartition.c:1619)——O(1),rowHash 由各列哈希+固定种子 HASH_PARTITION_SEED 合成(:4710);
- **list**:值收集排序(create_list_bounds :460),定位是**二分而非哈希**(partition_list_bsearch,:3594)——boundinfo 还要支撑规范化比较(:886)、join 边界合并(:1107)与剪枝区间推理,值域结构比"找位置"承担更多;
- **range**:上下界展开排序(:730,比较器 partition_rbound_cmp :3476),lower 界 indexes=-1、upper 界=分区号、nindexes=ndatums+1(:807/:844),定位二分后取 `indexes[offset+1]`(execPartition.c:1748)——**range 必须比较型:分区是有序区间不是等价类**。

## 12.1 路由:下降、映射与跨分区 UPDATE

`ExecFindPartition`(execPartition.c:268)逐层下降:FormPartitionKeyDatum(:317)→get_partition_for_tuple(:1581);**列序不同的层用 tupmap 转换**(build_attrmap_by_name_if_req :436-446,execute_attr_map_slot :1339);叶子层转根布局在 ExecInitRoutingInfo(:1199-1211)。热路径缓存:同一槽位连中 16 次(:1535)后先验缓存。**跨分区 UPDATE**(nodeModifyTable.c):分区约束失败(:2489)→ExecCrossPartitionUpdate(:2215)=ExecDelete(:2284)+转根布局(:2350)+从根重路由 insert(:2358)——**CTID 链不能跨关系,删不成就不插**(:2298-2307)。

## 12.2 剪枝:三次机会

子句编译成 step 链(gen_partprune_steps,partprune.c:744),三时机:

1. **规划期常量**:prune_append_rel_partitions(:780,调用点 inherit.c:350)——被剪分区不生成 RelOptInfo;
2. **启动期 stable 非常量**:ExecDoInitialPruning(execPartition.c:2006,execMain.c:882 统一调用)——被剪子计划**不初始化**;
3. **运行时参数**:每次扫描 ExecFindMatchingSubPlans(:2678,nodeAppend.c:584/:651/:727)。

计划传递经 make_partition_pruneinfo(partprune.c:225;createplan.c:1428/:1610)。三次时机=常量→stable→参数的"信息到达顺序"分级——与 06 章 hint bits 的"信息何时可用何时用"同构。

## 12.3 DDL:绑定校验与两阶段 DETACH

绑定校验 check_new_partition_bound(partbounds.c:2884,调用 tablecmds.c:1209):**重叠=错误**(:3225);hash 的 modulus 因子规则(:2926-3005);新分区落地前验证 default 存量数据(tablecmds.c:1219)。**并发 DETACH 两阶段**(PG14+):第一事务 ShareUpdateExclusive+标记 inhdetachpending(tablecmds.c:18528),第二事务 Finalize 等旧快照退出再删 pg_inherits(:22169/:22183);有 default 分区时禁止并发 DETACH(:21693)——default 会"收编"被拆走的行,窗口期语义复杂,宁可禁止。唯一约束须含分区键(indexcmds.c:993-1127)——**本地索引无全局唯一性的折衷**。

## 12.4 与前作对照与设计动机

| | PG 分区 | MySQL 分区 | Kafka 分区 |
|---|---|---|---|
| 粒度 | 表(可嵌套) | 表 | 消息流 |
| 定位 | bound 判定/取模 | 同类 | 哈希/键 |
| 剪枝 | 规划期+运行时 | 有限 | 无(全消费组) |

1. **分区是"逻辑统一/物理分散"的通用解**:每分区独立 vacuum(G 章)/索引/vacuum 全生命周期——运维粒度随之分散(按月删分区=瞬间 truncate);
2. **range 用二分而 list 也用二分的原因不同**:range 因有序必须比较;list 因边界结构要服务规范化/join 合并——同一个数据结构,两种负载约束;
3. **两阶段 DETACH 是快照语义的 DDL 化**:等待旧快照退出(卷一 01 章 ERROR/FATAL 的污染声明)——DDL 的并发正确性也要走 MVCC 的路;
4. **路由缓存 16 次**(:1535):先验缓存是"重复输入分布"的赌注,与 FFmpeg framesync 的帧缓存同族。

## 12.5 FAQ

**Q1:hash 分区为什么 O(1) 而其他二分?**
取模天然定位(:1619);range/list 的边界结构要服务比较语义——定位成本随策略语义走。

**Q2:跨分区 UPDATE 是原子的吗?**
delete+insert 在同一事务(:2215-2358):失败整体回滚;但 CTID 变了,并发 semantics 注意。

**Q3:为什么唯一约束必须含分区键?**
本地索引只保证分区内唯一(:993-1127):含分区键才能推出全局唯一——全局唯一索引仍是社区议题。

**Q4:分区能嵌套吗?**
能:子分区也是表,路由逐层下降(:268 的 while)。

**Q5:运行时剪枝对 prepared statement 生效吗?**
生效:第三次时机就是 PARAM_EXEC(:2678)——参数到达时逐次剪。

**Q6:default 分区有什么坑?**
收编一切未匹配行;DETACH 时窗口期语义复杂→有 default 禁止并发 DETACH(:21693)。

**Q7:分区数上限?**
无硬限,但 bound 判定/锁/规划成本线性——数百到数千是实用边界。

**Q8:剪枝失败(函数不稳定)会怎样?**
退化为全分区扫描:正确性永远优先(:2006 的 stable 要求)。

**Q9:分区的 VACUUM 是每分区独立吗?**
是:各叶子独立 autovacuum(G 章)——热分区先触发,天然负载分离。

**Q10:DETACH 后数据去哪?**
独立成普通表(:18528):数据保留在原文件——detach 即"退货不拆包"。
