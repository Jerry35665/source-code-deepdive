# 第 22 章 · 安全体系:认证、角色与 ACL

> 基线:commit `8c7a74c`。行号以 src/backend/libpq/auth.c、src/backend/libpq/hba.c、src/backend/commands/user.c、acl.c 为准。RLS(卷五 21 章)之外的**连接安全与权限体系**。

## 22.0 全景:一次客户端连接的认证→授权

```
客户端连接 → pg_hba.conf 规则匹配(hba.c:2429-2431 第一匹配赢)
  → 认证方法分派(auth.c:428-634):trust/password/md5/scram/gss/cert/peer
  → SCRAM-SHA-256 三步(Nonce→Proof→ServerSignature)
  → 认证成功 → 角色加载(roles_is_member_of 递归展开 acl.c:5178)
  → ACL 检查(aclmask 位掩码三段 :1412)
```

## 22.1 认证方法:SCRAM 替代 md5

pg_hba.conf 规则解析的顺序语义:第一匹配赢(hba.c:2429-2431);**任一行出错→整个文件作废保留旧规则**(hba.c:2524-2531)——"保守整体失效"的安全哲学。md5 的根本缺陷:**存储哈希即应答材料**——可离线重放(crypt.c:265-287)。**SCRAM-SHA-256 的三步**:服务端 18 字节随机 nonce+盐+4096 迭代(:1232-1254);验 proof:ClientKey=Proof XOR Signature(:1181-1182)、H(ClientKey) 比对 StoredKey(:1185-1189);回 `v=ServerSignature`(:1459)做服务器自证。**信道绑定**必须 tls-server-end-point(auth-scram.c:1053),PLUS 仅 TLS 时启用(:256-257)——防中间人。用户不存在走 mock 认证防枚举(auth.c:848-860)。

## 22.2 角色系统:嵌套与属性

CREATE_ROLE(user.c:133)属性默认值 :145-152、落盘 :417-422/:464;GRANT role 写 pg_auth_members 带 admin/inherit/set 选项(user.c:1493)。**递归展开 roles_is_member_of**(:5178):工作列表边扫边加+bloom filter 防环(:5264);权限链跳过 inherit_option=false 边(:5252-5253);pg_database_owner 隐式注入(:5269-5271)。BYPASSRLS 与 FORCE RLS 交汇于 check_enable_rls(rls.c:52):BYPASSRLS 优先(:87-88),属主被 relforcerowsecurity 罩住(:98-114),RI 检查的 SECURITY_NOFORCE_RLS 上下文例外(miscadmin.h:323,miscinit.c:649)。

## 22.3 ACL:位掩码与列级权限

AclItem 三体(grantee/grantor/64 位权限,acl.h:54-59):高 32 位 grant option;字母表 "arwdDxtXUCTcsAm"(acl.h:154)。aclmask(:1412)三段:属主隐式 grant option(:1436)→直授/PUBLIC(:1451)→间接角色(:1471)。**列级权限是补差并集**:execMain.c:684-685 先表级 mask、剩余位逐列查,COUNT(*) 放宽为任一列(:711-716)。默认 ACL 双来源:硬编码 acldefault(acl.c:827)+pg_default_acl 查询(aclchk.c:4277)。**非 superuser 对系统目录直接砍写权限位**(aclchk.c:3317-3331);超用户短路返回(:3336-3339)。

## 22.4 设计动机

1. **为什么 pg_hba.conf 是文件而非系统表**:认证先于数据库可用(鸡生蛋)——文件在数据目录外,数据库挂了也能改;保守整体失效(任一行错→全文件作废)是安全哲学;
2. **为什么 SCRAM 替代 md5**:零知识(服务端不存等价密码)+双向认证+信道绑定——**存储哈希即应答材料**的 md5 根本不可救;
3. **为什么 ACL 用位掩码**:目录内联存储(acl.h:154 的字母表)+纯位运算判定——**紧凑+快**,代价是权限种类上限(16 种足够);
4. **列级权限的补差并集**:(:684-685):表级给了多少,列级只限制"多给的"——**叠加语义而非替换语义**。

## 22.5 FAQ

**Q1:pg_hba.conf 两条规则都匹配,用哪条?**
第一匹配赢(hba.c:2429-2431);顺序即优先级,最严格的放前面。

**Q2:pg_hba.conf 写错了会怎样?**
整个文件作废保留旧规则(hba.c:2524-2531)——不会因为一行错而全开放。

**Q3:md5 为什么不安全?**
(:265-287):存储的 md5 哈希就是应答材料——拿到 pg_authid 就能直接连,无需破解原文。

**Q4:SCRAM 的信道绑定是什么?**
tls-server-end-point(:1053):将 TLS 证书指纹混入认证——防中间人将认证转发到真服务器。

**Q5:角色嵌套的环怎么处理?**
bloom filter 防环(:5264):已访问的角色不重复展开。

**Q6:BYPASSRLS 和超级用户的区别?**
都是绕 RLS(:87-88);BYPASSRLS 是角色属性(可精确授予),超级用户是全局身份。

**Q7:列级权限怎么查?**
(:684-685):表级 mask+剩余位逐列——先查表级再看列级,叠加而非替换。

**Q8:GRANT role WITH ADMIN OPTION 是什么?**
允许被授予者再把该角色授予别人(user.c:1493):权限的传递链。

**Q9:FORCE ROW LEVEL SECURITY 罩住谁?**
表 owner(:98-114):默认 owner 绕过 RLS,FORCE 后也受约束。

**Q10:列级权限的 COUNT(*) 为什么放宽?**
(:711-716):COUNT(*) 不读具体列的值——"知道有多少行"不等于"知道行内容"。

## 22.6 小结与深挖方向

本章结论:**安全体系="文件认证(第一匹配)+SCRAM 零知识+角色递归嵌套+ACL 位掩码补差并集"**;md5→SCRAM 的迁移是安全债务的清偿。深挖:

1. mock 认证(:848-860)在时序攻击(用户枚举)的防护完备性;
2. bloom filter 防环(:5264)在深嵌套角色的碰撞率;
3. aclmask 三段(:1412)在跨角色多级授予的合成正确性;
4. FORCE RLS(:98-114)与 pg_dump 的交互(导出权限的边界);
5. 信道绑定(:1053)在非 TLS 场景(Unix socket)的等价物。

> 安全体系完——PG 的信任锚与权限链全闭合。
