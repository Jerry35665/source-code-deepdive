# 第 01 章 · 进程架构:postmaster 纯监管与崩溃级联

> 基线:commit `8c7a74c`。行号以 src/backend/postmaster/、src/backend/tcop/、src/backend/storage/ipc/ 为准。PG 的第一公理:**多进程,fork 隔离地址空间;共享内存是唯一真通信介质**。

## 1.0 全景:进程拓扑

```
postmaster(单线程,纯监管:accept→fork→waitpid→发信号)
 ├── backend ×N(每连接一个,fork)
 ├── checkpointer / bgwriter / walwriter / autovacuum launcher / walsummarizer
 ├── startup(恢复时重放 WAL)/ walsender(复制)/ syslogger(唯一不挂 shmem)
 └──────────── System V 共享内存+信号量(命脉)────────────
```

进程类型总表在 proctypelist.h:34-53(`BackendType` 枚举,miscadmin.h:340-385);每个类型只有三要素:**Main 函数、是否挂 shmem**(syslogger 唯一不挂,miscadmin.h:380-384)。postmaster 自身单线程且周期断言 `pthread_is_threaded_np()==0`(postmaster.c:1752-1758)——**监管者必须无线程**,否则 fork 语义不可信。

## 1.1 postmaster 主循环与启动链

`ServerLoop`(postmaster.c:1676-1827)是事件驱动:WaitEventSetWait,WL_SOCKET_ACCEPT→BackendStartup(:1722-1727),每轮 `LaunchMissingBackgroundProcesses` 补种辅助进程(:1742)——**辅助进程不是启动一次,而是"缺失即补种"**,这是自愈的第一层。启动顺序:PostmasterMain 先 fork checkpointer/bgwriter/startup 再进循环(:1393-1414)。

`BackendStartup`(:3588-3668):canAcceptConnections(:3607)→PMChild 槽位→fork;**连接满时转入 dead-end child**(:3618-3631)——不是拒绝连接,而是给一个"只能收到错误然后断开"的空壳。fork 细节在 fork_process.c:32-126:fork 前阻塞全部信号防竞态、fflush 防 stdio 双写、调 OOM score——三个"fork 前必做"的教科书法则。参数传递走 launch_backend.c:204-273:fork→MyBackendType→ClosePostmasterPorts→main_fn(Windows 的 EXEC_BACKEND 走 internal_forkexec 临时文件传参 :284-378——fork 不可用时的一切复杂度都装在这个分支里)。

## 1.2 崩溃级联:一个 backend 崩,全员重启

这是 PG 进程模型最反直觉也最重要的决策:

```
backend 异常退出(退出码非 0/1,CleanupBackend postmaster.c:2631)
  → HandleChildCrash(:2830)→ HandleFatalError(:2745)
  → 其余全员 SIGQUIT、置 FatalError、5 秒后升级 SIGKILL(:1780)
  → 全员 quickdie 直接 _exit(2) 不做任何清理(postgres.c:3092-3106)
  → 全灭后 PostmasterStateMachine 重建 shmem、重新 fork startup 重放 WAL(:3248-3288)
  → 成功 → PM_RUN(:2360-2375)
```

**为什么连坐**:崩溃进程的锁/buffer pin 状态留在共享内存里不可信——阻塞在它锁上的进程无法自救。quickdie 的 `_exit(2)` 注释明言"shmem 可能已损坏"——**崩溃域=全部共享状态**,所以恢复=重置一切。PM 状态机 PM_INIT→PM_STARTUP→PM_RUN→…→PM_NO_CHILDREN(:336-353,讲解 :293-335)是这条链的骨架。

## 1.3 backend 生命周期与错误恢复

`PostgresMain`(postgres.c:4363 入口,:4696 for(;;),:4878 ReadCommand 阻塞点;'Q'→exec_simple_query :4946)。错误恢复用 **sigsetjmp 锚点**(:4573)三级分流(elog.c:528-622):

- **ERROR**→longjmp+AbortCurrentTransaction:进程和连接都活着(这是应用层看到的大部分 SQL 报错);
- **FATAL**→proc_exit(1) 体面死(连接断,postmaster 不连坐);
- **PANIC**→abort()→非正常退出码→触发 1.2 的级联。

**错误级别的本质是"污染范围"的声明**:ERROR 污染当前事务,FATAL 污染当前连接,PANIC 污染共享内存。多语句简单协议默认同一事务(:1107-1114,:2874-2935,事务懒启动)。

## 1.4 共享内存:命脉与目录

System V 共享内存+信号量;bump 分配器(shmem.c:840-885)+ ShmemIndex 名字→地址目录(:259-279,:1099-1135);`ShmemInitStruct` 查重→分配→写全局指针三合一(:529-595),ShmemIndexLock 保护。**子进程不重挂 shmem**——fork 继承映射(shmem.c:96-103 注释:仅 EXEC_BACKEND 需重挂)。listen socket 靠子进程主动关(postmaster.c:1879-1924)——fork 继承的 fd 是默认共享,谁该用谁显式关。

## 1.5 设计动机

1. **为什么 fork-per-connection**:崩溃域隔离(1.2)+地址空间天然防野指针跨连接破坏+fork 后 COS 成本由连接复用摊销——对照 Redis(单线程,崩溃即进程死,持久化兜底)、Nginx(多进程 worker 但无共享可变状态,崩溃只丢连接)、FFmpeg(线程池,一个线程崩全进程死,16 章)——**PG 的选择买的是"内存级故障隔离"**,代价是连接建立慢与上下文切换;
2. **postmaster 纯监管**:业务逻辑为零——监管者越简单越不会先死;"补种式"辅助进程(:1742)让辅助进程崩溃也自愈;
3. **共享内存是唯一真 IPC**:管道只传控制信号,数据全在 shmem——所有后续章节(缓冲/锁/WAL)的结构都住在这块内存里,它们的并发设计(02/05 章)由此展开;
4. **错误级别=污染范围声明**:elog 三级与进程/事务/集群三层恢复一一对应——把错误处理做成状态机而非约定。

## 1.6 FAQ

**Q1:一个连接崩了,为什么整个 PG 短暂不可用?**
崩溃进程的锁/pin 在 shmem 中不可信(:2830-2852):全员 SIGQUIT→重建 shmem→startup 重放 WAL(:3248-3288)。秒级窗口,这是隔离与共享的交换。

**Q2:SQL 报错(ERROR)会断连接吗?**
不会:ERROR 只 longjmp 回事务边界(postgres.c:4573);FATAL 才断连接,PANIC 才级联。

**Q3:连接满了会拒绝新连接吗?**
给 dead-end child(:3618-3631):收一个错误响应后关闭——客户端拿到明确错误而非超时。

**Q4:syslogger 为什么不挂 shmem?**
日志只写文件不共享状态(miscadmin.h:380-384)——唯一例外的进程类型,佐证"挂 shmem"是按需声明。

**Q5:postmaster 会自己执行查询吗?**
绝不:纯监管(:1676-1827),业务全在 backend。监管者死=全集群死(无快速重启保护是历史决策)。

**Q6:为什么不用线程?**
fork 隔离+错误恢复简单+历史(1996 年);线程模型的隔离损失在 1.2 的崩溃语义下不可接受。

**Q7:Windows 上怎么办?**
fork 不可用:EXEC_BACKEND 分支 internal_forkexec 临时文件传参(launch_backend.c:284-378)——所有"fork 继承"的隐式状态显式化。

**Q8:辅助进程崩了也全灭吗?**
是(同一个 shmem 污染逻辑);但每轮补种(:1742)保证它们回来。

**Q9:fork 前为什么要阻塞信号?**
信号竞态:fork 后子进程继承挂起的信号处理时机不确定(fork_process.c:32-126)。

**Q10:共享内存多大、谁分配?**
启动时按参数计算一次(shmem.c bump 分配 :840-885),固定大小——动态化正在逐步推进。

## 1.7 小结与深挖方向

本章结论:**PG 进程模型 = "fork 隔离(崩溃域最小)+共享内存(唯一命脉)+错误级别=污染范围声明+崩溃级联=全量重置"**。深挖:

1. PM 状态机(:336-353)在 bgworker 动态注册下的边界;
2. dead-end child(:3618-3631)的资源占用与恶意连接;
3. EXEC_BACKEND(Windows)路径的性能税实测;
4. postgres.c 主循环(:4696)的内存上下文重置点;
5. postmaster 无"监管者重启"(如 systemd 层面)时的单点风险。
