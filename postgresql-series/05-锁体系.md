# 第 05 章 · 锁体系:三层金字塔(卷末)

> 基线:commit `8c7a74c`。行号以 src/backend/storage/lmgr/ 为准。PG 的并发控制是教科书级的完整栈:spinlock→LWLock→heavyweight lock 三层各司其职,等待策略从"自旋"到"睡眠"到"死锁检测"逐级升级。

## 5.0 全景:三层金字塔

```
heavyweight(lock.c,4900 行)——数据库语义对象(表/行/事务)
    等待:latch 睡眠;deadlock_timeout 后 DFS 找环,软解重排/硬解杀事务
LWLock(lwlock.c,1900 行)——共享内存数据结构(缓冲描述符/WAL 锁/SLRU)
    等待:CAS 直取;失败排队睡信号量,释放者唤醒
spinlock(s_lock.c,300 行)——指令级原语(LWLock 内部的"锁中锁")
    等待:纯自旋+随机指数退避,1000 次后 PANIC stuck
```

**持锁时长决定等待机制**:纳秒级→自旋;微秒~毫秒→LWLock;任意长(用户事务)→heavyweight+死锁检测。三层缺一不可:自旋太快会烧 CPU,LWLock 等待太长会饿死,heavyweight 没有死锁检测会永久挂起。

## 5.1 spinlock:平台抽象与自适应退避

S_LOCK=先试一次 TAS,失败才进平台无关自旋循环(s_lock.h:665-668);x86_64 的 TAS_SPIN **先无锁读**(s_lock.h:212,缓存行热点检查),SPIN_DELAY 即 PAUSE 指令(:189-191)。**自适应退避**:spins_per_delay 全局估计 +100/-1 单调调整,退出时 15/16 EMA 汇入(s_lock.c:185-199,:217-231),单核收敛 10、多核收敛 1000——**锁的历史负载决定后来的等待姿态**。为什么自研不用 pthread 自旋:平台矩阵(s_lock.h 各架构分支)把 TAS 做到每平台最紧,且要与非 pthread 场景(WAL 内部)兼容。

## 5.2 LWLock:32 位原子字的状态机

LWLock 仅 3 字段:tranche(16b)+state(32b 原子字)+waiters 链(lwlock.h:41-50)。**state 位布局**(lwlock.c:96-118):高 3 位标志(HAS_WAITERS/WAKE_IN_PROGRESS/LOCKED)+18 位共享计数+独占哨兵 MAX_BACKENDS+1——独占被编码成"共享数越界"。**acquire 两阶段协议**(:1215,:1235,:1238,:1267-1273):CAS→排队→再 CAS→睡信号量——解决"排队期间锁已释放"的竞态(协议注释 :66-75 是全文件最该读的 10 行)。**唤醒协议**:FIFO 连续放行共享、遇独占即止(:916-956,:961-986,:1006-1008);3 个标志一次 CAS 收拾+pg_write_barrier 后 PGSemaphoreUnlock。tranche 是 X-macro 表驱动(lwlock.c:137-147;lwlocklist.h:36-142——老 lwlocknames.txt 已并入由脚本生成)。

## 5.3 heavyweight:八模式冲突矩阵与 fast path

LOCK 结构+八种模式(DEFAULT/USER 两方法共用常量冲突矩阵,lock.c:68-108;lockdefs.h:36-48):AccessShare→AccessExclusive,SELECT 与 UPDATE 的兼容性由矩阵行定义。锁表 16 分区(lwlock.h:86-87,分区锁宏 lock.h:355-361)——02 章缓冲哈希分区同款。**fast path**(lock.c:270-275,:303-309,:2812-2848,:2891-2929):弱关系锁记入 PGPROC 私有数组(proc.h:330-336)免碰共享表;1024 个原子强锁计数器证伪冲突;强锁到来才把 fastpath 锁搬回主表——**死锁检测因此无需看 fastpath**(README:331-333):乐观路径的正确性由"计数器必然暴露强锁"保证(03 章 FPW 判据同款思维)。行级锁确认走 heavyweight:SELECT FOR UPDATE→LockTuple 加 LOCKTAG_TUPLE(heapam.c:169-176,:5457-5486;lmgr.c:562-567);普通 MVCC 更新不进锁表,只写 xmax/infomask(lmgr.c:663)——**MVCC 把"写写冲突"从锁表赶到了元组头**。

## 5.4 死锁检测:惰性+图搜索+软解

默认 deadlock_timeout=1000ms,等待时才挂定时器(proc.c:61,:1408-1432,:1896-1897)——**先赌死锁不存在**(绝大多数等待是短暂阻塞);超时后按分区号顺序锁全部 16 分区再跑 DeadLockCheck。检测:等待图 DFS 回起点即环(deadlock.c:477-488);**软边=队列序**——不死锁但饿死的排队被识别为"可重排约束",递归+拓扑排序找无环配置(:561-626,:627-767,:309-358);无解才杀事务(:217-279)。**为什么检测而非预防**:预防(全局序)会拒绝大量本可成功的并发;检测把代价放在 1 秒超时这个尾部。

## 5.5 设计动机

1. **三层是持锁时长谱系的函数**:等待机制的成本必须与临界区时长匹配——自旋在长临界区烧 CPU,睡眠在短临界区亏延迟;
2. **状态字是"锁的 SIMD"**:LWLock 把共享数/独占/等待者塞进一个原子字——一次 CAS 完成"判断+修改+通知"三件事;
3. **fast path 是乐观并发的极致**:多数锁是弱关系(读为主),私有数组+计数器把 90% 的加锁做成零共享内存写——与 Git fastpath 校验、K8s CAS 同族;
4. **MVCC 与锁表的分工**:行版本(xmax)承载乐观写写判定,锁表只兜"显式锁"——这是 04 章"按可信度付费"的写路径版。

## 5.6 FAQ

**Q1:为什么 spinlock 自研不用 pthread?**
平台最紧 TAS+不依赖线程库初始化(s_lock.h 各架构分支);PAUSE 指令的省电版即 SPIN_DELAY(:189-191)。

**Q2:LWLock 独占怎么表示?**
共享数越界哨兵 MAX_BACKENDS+1(lwlock.c:96-118)——一个字段两种模式。

**Q3:排队后锁释放了怎么办?**
两阶段协议(:66-75 注释):排队后必须再 CAS 一次——竞态窗口的经典补丁。

**Q4:SELECT 之间会冲突吗?**
AccessShare 互兼容(冲突矩阵 :68-108)——只读负载零锁表竞争(fastpath :270-275)。

**Q5:死锁检测为什么等 1 秒?**
惰性:多数等待毫秒级结束(:1408-1432);检测本身要锁 16 分区,成本高——赌短等待是正期望。

**Q6:软解是什么?**
不死锁但饿死的队列被重排(:561-626):把"等错了顺序"的事务换位,能解就不杀。

**Q7:行锁在锁表里吗?**
仅显式锁(FOR UPDATE,:5457-5486);普通更新只写 xmax(lmgr.c:663)——MVCC 分流。

**Q8:fastpath 的正确性靠什么?**
1024 个原子计数器:强锁到来必然看到 fastpath 的存在(:2812-2848)——乐观路径必须可证伪。

**Q9:spins_per_delay 会不会震荡?**
+100/-1 单调+EMA 汇入(:185-199):只升不降的粗粒度+慢速回落。

**Q10:三层各举一个真实使用点?**
spin=buf header 内容锁(02 章)/LWLock=WALWriteLock(03 章)/heavyweight=表上的 AccessExclusive(DDL)。

## 5.7 小结与卷末语
