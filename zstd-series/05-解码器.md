# 第 05 章 · 解码器:每 GB 数 GB 吞吐的另一半

> 基线:commit `d79e723`。行号以 lib/decompress/zstd_decompress.c、zstd_decompress_block.c、zstd_ddict.c 为准。压缩可以慢,解压必须快——解码器是 zstd 性能口碑的核心。

## 5.0 全景:解压一帧的数据流

```
ZSTD_decompress → ZSTD_decompressMultiFrame(:1068)
  ├─ 逐帧:decompressBegin(重置熵表/rep,:1558)→checkContinuity(:1140)→ZSTD_decompressFrame(:951)
  │    ├─ 帧头:getFrameHeader_advanced(:445)→decodeFrameHeader(:700)
  │    └─ while 逐块(:984-1041):3B 块头 getcBlockSize→bt_raw/rle/compressed 分派(:1012-1028)
  │         bt_compressed→ZSTD_decompressBlock_internal(:2168)
  │              ├─ decodeLiteralsBlock(:133):Huffman 1/4 流→litBuffer 三形态
  │              ├─ decodeSeqHeaders(:694):nbSeq+LL/OF/ML 三张 FSE 表
  │              └─ decodeSequence↔execSequence 循环;块尾 rep 写回(:1776)
  └─ 帧尾:frameContentSize 校验(:1043)+XXH64(:1047)
```

输出三形态:单缓冲整帧/bufferless 逐块直写(不连续即 extDict,checkContinuity :2280-2288)/流式内部 outBuff(windowSize+2×blockSize+2×WILDCOPY_OVERLENGTH,:1978)。字面量另有三形态 litLocation:in_dst/not_in_dst/split(internal.h:120-124)——**in_dst 时零拷贝藏进输出缓冲**(allocateLiteralsBuffer,:79-123)。

## 5.1 字面量与熵表的跨块状态

**set_repeat 复用上块 Huffman 表**(:146-149):litEntropy/fseEntropy 双标志跨块持久——04 章 repeat 的解码侧对偶。`decodeSeqHeaders`(:694-777):1 字节描述符装 LL/OF/ML 三表模式+保留位校验(:729);`buildFSETable` 两阶段 symbol spreading **消分支**(:484-602)——02 章构建数学的解码端实现。

## 5.2 序列解码与 match 拷贝(性能的心脏)

`decodeSequence`(:1236-1447)三表交织一次产出 litLength+offset+matchLength;**last seq 不更新状态**(:1435-1442,链尾是哨兵);`temp -= !temp` 钳损坏 offset(:1408)——防解压炸写的最后防线。**match 拷贝的重叠处理**是全库最精的性能代码:

- offset≥16→`ZSTD_wildcopy(no_overlap)` 16B 宽拷,**无重叠检查**;允许越界写 32B(WILDCOPY_OVERLENGTH),故 oend_w=oend-32(:1016;拷贝 :1084-1091);
- offset<16→`ZSTD_overlapCopy8`(:806-827)用 dec32table/dec64table(承 LZ4)把重复周期摊到 ≥8(断言 op-ip≥8 :826),再 wildcopy(overlap 模式退化 8B 循环,zstd_internal.h:225-229);
- 逐字节只在慢路径 safecopy(:849-851,:877);extDict 源一律 memmove,跨界劈两段(:1062-1073);快慢路径仅一条 UNLIKELY 判定(:1032-1036)。

变体矩阵:SplitLitBuffer(:1504-1711)+**DSB 对齐(.p2align :1583-1597,波动可达 10%)**;Long 预取版(:1833-1990,STORED_SEQS=8 :1852)。

## 5.3 Huffman 解码的 X1/X2 与派发

X1 4 流 16 符/轮(:603-699);fast 循环 5 符/轮(`bits>>53` 查表+`read64|1` 哨兵 ctz 重载,:722-832,:788-794);asm/BMI2 派发;选型 HUF_selectDecoder(:1830)——与 02 章编码侧 4 流切分严格镜像。

## 5.4 DDict:字典的 double indirection

DDict 三层间接(dctx->LLTptr→ddict->entropy.LLTable,zstd_ddict.c:36-44,:58-86,:120-135):**字典的熵表由所有使用它的解压上下文共享指认**;dlm_byCopy 复制字典使调用方可提前释放(:166 注释)——所有权语义显式化(系列模式 3)。冷字典启发式预取(:195/:672/:2218)。

## 5.5 性能手法盘点与设计动机

盘点:wildcopy 宽拷+越界预算(预分配契约)/分支消除(buildFSETable)/p2align 对齐/预取批量(STORED_SEQS=8)/汇编热循环/错误钳制(temp-=!temp)。设计动机:①**解码无搜索**——压缩的花销换来解码的纯查表,这是 LZ 家族不对称性的根源;②越界写 32B 是"调用方预分配契约"换性能——契约写在 API 文档里;③前块熵表保存(blockState.prevC)=repeat 语义的解码端义务;④解压不可信输入的边界:每个 magic/size/crc 校验点+钳制常数。

## 5.6 FAQ

**Q1:为什么解压比压缩快好几倍?**
压缩要搜索(03 章),解码纯查表+拷贝——LZ 家族的不对称性。

**Q2:wildcopy 为什么敢越界写?**
调用方按契约预留 WILDCOPY_OVERLENGTH=32B(:1016):性能换预分配义务。

**Q3:offset<16 的重叠拷贝为什么慢?**
源与目标重叠,宽拷会自我污染:dec32table 摊周期到 ≥8(:806-827)。

**Q4:in_dst 字面量是什么?**
字面量直接解到输出缓冲的正确位置(:79-123):零拷贝路径。

**Q5:last seq 为什么不更新状态?**
链尾是哨兵(:1435-1442):状态机的"最后一步无下一步"。

**Q6:字典会被多个解压上下文共享吗?**
会,DDict 三层间接(:36-44):熵表只存一份,指针指认。

**Q7:repeat 在解码端怎么实现?**
litEntropy/fseEntropy 标志+prevC 保存(:146-149):与编码端对偶。

**Q8:损坏数据会写崩内存吗?**
钳制常数(temp-=!temp :1408)+帧长校验(:1043)+XXH64:不可信输入的边界。

**Q9:extDict 模式是什么?**
流式窗口滚动后旧数据不在当前缓冲(:2280-2288):匹配源跨缓冲 memmove(:1062-1073)。

**Q10:p2align 为什么影响 10%?**
循环体对齐改变取指/缓存行(:1583-1597)——微架构层的现实。

## 5.7 小结与深挖方向

本章结论:**解码器="镜像状态机+wildcopy 宽拷契约+三层表变体+钳制边界"**。深挖:

1. WILDCOPY_OVERLENGTH=32 的推导(最大 mls× копия 步长);
2. dec32table/dec64table(:811-812)的 LZ4 血统与最优摊销;
3. Long 预取版(STORED_SEQS=8)对 L3 的实际占用;
4. DDict 共享在多线程解压的缓存行竞争;
5. X1/X2 派发表(:1830)在不同数据分布的误判率。
