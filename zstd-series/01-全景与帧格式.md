# 第 01 章 · 全景与帧格式:一个压缩文件的解剖

> 基线:commit `d79e723`。行号以 doc/zstd_compression_format.md、lib/zstd.h、lib/compress/zstd_compress.c、lib/decompress/zstd_decompress.c 为准。格式是全库的锚——先读懂字节布局,后面的代码才有坐标。

## 1.0 全景:一个文件的字节布局

```
┌─────────────── 一个 .zst 文件 = 多帧串联 ───────────────┐
│ Zstandard 帧(magic 0xFD2FB528)                          │
│   Magic(4B) │ Frame_Header(2-14B) │ Block×N │ [Checksum 4B] │
│ Skippable 帧(0x184D2A50-5F):只跳不解——前向兼容的"旁注"   │
│ legacy 帧(v0.1-0.7):独立 magic,lib/legacy/ 单独目录隔离  │
└──────────────────────────────────────────────────────────┘
```

三种 magic 常量(lib/zstd.h:142-148);BLOCKSIZELOG_MAX=17→单块上限 128KiB。**帧是解压的独立性单位**,块是压缩的工作单位。

## 1.1 帧头:FHD 逐位与窗口公式

Frame_Header_Descriptor(FHD)逐位(doc/zstd_compression_format.md:157-164):bit7-6=Frame_Content_Size 宽度(0/2/4/8B,2B 形式带 +256 偏移)、bit5=单段模式(省 Window_Descriptor,WindowSize=FCS)、bit2=校验和开关、bit1-0=字典 ID 宽度(0/1/2/4B)、bit3=保留必须 0。**Window_Descriptor 用 5 位指数+3 位尾数**编码(doc:245-256):`windowLog=10+Exp; size=(1<<log)+(size/8)*Man`,范围 1KB-3.75TB——参考实现编码时尾数恒 0(取 2 的幂),尾数是给未来留的。

压缩端拼帧头在 zstd_compress.c:4723-4771(FHD 组装/单段判定/windowLogByte);解码端对称解析 zstd_decompress.c:500-544(FHD 拆位/window 计算/+256 偏移)。

## 1.2 块层:24 位头与三种类型

块头 24 位小端(doc:333-340):bit0=last_block、bit1-2=类型(Raw/RLE/Compressed/Reserved)、bit3-23=块大小。**块大小上限=min(Window_Size,128KiB)**(doc:388-396)——这个上限的推论极重要:**解压只需"窗口+块缓冲"两块内存**,与输入文件大小无关。压缩端逐块循环在 zstd_compress.c:4638-4688(frameChunk :4619):LE24 写块头、RLE 降级判定;解码端对称分派 zstd_decompress.c:984-1041(LE24 解析 zstd_decompress_block.c:62-76)。

## 1.3 window:流式解压的红线

window 是"能引用多远以前的数据"。流式解压有默认窗口红线 `(1<<27)+1`(约 128MB,zstd_decompress.c:39-40,:2227-2230;ZSTD_WINDOWLOG_LIMIT_DEFAULT=27 在 lib/zstd.h:1287)——超过需要显式调 `ZSTD_d_windowLogMax`。序列的三张基值表 LL_base/OF_base/ML_base(zstd_decompress_internal.h:30-56;MaxLL=35/MaxML=52/MaxOff=31 在 lib/common/zstd_internal.h:103-111)是 02/04 章熵编码的锚。

## 1.4 API 三层:简单、流式、高级

zstd.h 的公开 API 分三层:**简单层**(ZSTD_compress/decompress+compressBound+getFrameContentSize 三态返回)、**字典层**(ZSTD_CDict/DDict 预编译,06 章)、**流式层**(ZSTD_CStream==ZSTD_CCtx,v1.3.0 起同一对象;compressStream2 三档 endOp:continue/flush/end)。高级层 ZSTD_compress2=reset+一次 e_end 的流式调用;参数两阶段管道:setParameter→requestedParams→启动时校验→appliedParams。**级别即数据**:clevels.h:25-130 的 4×23 参数表(按源大小分档)把 22 个级别映射为 windowLog/策略等 7 元组(03 章展开)。

## 1.5 设计动机

1. **解压内存与输入无关**:块上限≤窗口,窗口写进帧头——解压器预先知道自己需要多少内存,这是 zstd 能进内核/嵌入式的根本;
2. **magic 分层的前向兼容**:skippable 帧"只跳不解"=老解码器天然跳过新功能段;legacy 独立目录=老格式永不污染主代码(F 报告:legacy 默认编译关闭);
3. **单段模式**(bit5):小文件免传 Window_Descriptor——每一个格式位都对应一类真实负载;
4. **API 三层同对象**:CStream==CCtx 的合并消灭了"两套状态机"——流式只是简单层的分帧视图。

## 1.6 FAQ

**Q1:解压 10GB 文件需要多少内存?**
窗口大小+128KiB 块缓冲——与文件大小无关(doc:388-396);窗口写在帧头,解压器提前知道。

**Q2:帧头最多多大?**
2-14B:FHD(1)+Window(1)+字典 ID(0-4)+FCS(0-8)。

**Q3:为什么有 skippable 帧?**
新功能(如未来元数据)可以塞进 skippable 段,老解码器按 magic 范围跳过——前向兼容不需要协商。

**Q4:单段模式什么时候触发?**
小文件+未开 window 参数:WindowSize=FCS,省 1 字节 Window 描述符(bit5)。

**Q5:校验和是什么算法?**
XXH64(帧尾 4B,bit2 开关)——非加密校验,速度优先。

**Q6:zstd 能解压老版本(0.x)压缩的文件吗?**
可选编译:ZSTD_LEGACY_SUPPORT 开关+lib/legacy/ 目录(F 报告);v1.6.0 起默认关闭。

**Q7:级别 1 和 22 差在哪?**
clevels.h 的参数表:windowLog/策略(fast→btultra2)/搜索深度——同一套代码,参数决定一切(03 章)。

**Q8:流式接口和一次性接口压缩结果一样吗?**
可能不同:块边界不同导致选择差异;字节级兼容(都能互解)。

**Q9:checksum 默认开吗?**
压缩端默认关(参数 bit2);ZSTD_compress2 显式开启才写。

**Q10:一个文件多个帧怎么来的?**
flush 边界(ZSTD_e_flush)或多线程压缩各自产出帧——帧独立所以可拼接。

## 1.7 小结与深挖方向

本章结论:**格式="帧头自描述内存需求+块三类型+三层 magic 前向兼容"**;所有后续章节都在这套坐标上展开。深挖:
