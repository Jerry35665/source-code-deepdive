# 第 02 章 · 熵编码:FSE 状态机与 Huffman 4 流

> 基线:commit `d79e723`。行号以 lib/common/fse.h、fse_decompress.c、lib/compress/fse_compress.c、huf_compress.c、lib/decompress/huf_decompress.c、lib/common/bitstream.h 为准。FSE(Finite State Entropy,tANS 变体)与 Huffman 是 zstd 压缩率的数学引擎。

## 2.0 全景:熵编码在块内的位置

```
压缩块 = 字面量段(Huffman Huff0) + 序列段(LL/ML/Off 三张 FSE 表)
连 Huffman 树的权重串本身也用 FSE 压(doc/zstd_compression_format.md:1034-1039)
```

**分工的账**:字面量分布平缓(字符频率),Huffman 足够且解码极快;序列的三种"长度"分布尖锐(多数是短匹配),FSE 的分数比特精度收益大。zstd 不做单一最优,做**按数据形状分工**。

## 2.1 FSE:tANS 的状态机本质

一张 `2^AccuracyLog` 行的表,每行三个字段:{newState, symbol, nbBits}(fse.h:505-515)。**解码一步=查表出符号+读 nbBits 位加 newState 得下一状态**(fse.h:540-549)。概率为 P 的符号占 P 行,每行摊 log2(2^n/P) 的分数比特——这就是"分数比特"的来源:tANS 用查表把算术编码的精度装进了 O(1) 每符号。解码表构建的全部数学三行(fse_decompress.c:150-156):

```c
nbBits   = tableLog - highbit32(nextState);
newState = (nextState << nbBits) - tableSize;
```

概率 -1 的符号(表示"太稀有")置表尾+fastMode 判定(概率>50% 关闭快速路径,:78-87)。

## 2.2 归一化:表构建的较劲之处

`FSE_normalizeCount`(fse_compress.c:465-525)把真实计数分配到 2^tableLog 个表槽:预除法 `step=2^62/total` 一次除法(:478),proba<8 用 rtbTable 查表修正进位(:494-497),残差记给最大符号(:502-507),失败退 FSE_normalizeM2(:379-463)。**为什么归一化值得较劲**:归一化误差直接变成压缩率损失;低概率符号配额记 -1 还是 1 由 nbSeq≥2048 决策(zstd_compress_sequences.c:57-64)——样本少时稀符号的误差会放大。

## 2.3 spread:为什么符号要"打散"

符号副本沿步长 `(size>>1)+(size>>3)+3` 撒表(fse.h:623,与格式文档一致)——**保证同符号的状态数值均匀间隔**:解码时读出的低 bits 与状态强相关,不打散则压缩率崩塌(fse_compress.c:93-94 引作者博客);工程上先 8 字节批量铺再免分支双展开(:116-153)。

## 2.4 位流模型:正写倒读的 LIFO

BIT_DStream 一次性把末尾 64 位读进寄存器,bitsConsumed 当游标,每 8 字节 reload 一次(bitstream.h:90-96,:412-444);64 位机保证 57 个有效位(:43-44)。**编码端正写、解码端倒读**的 LIFO 语义(:52-55)由 tANS 的互逆性决定;endMark 1 位收尾使末字节必非 0(:236-242;doc:1244-1252)——流长度自描述。

## 2.5 Huffman:深度推平与 4 流

- **深度限制 11/12**(huf.h:37-38):`HUF_setMaxHeight`(huf_compress.c:376-499)做代价守恒推平——超深叶子统一压到目标深度累计 totalCost,再用 rankLast[] 贪心还债,**O(alphabet) 无需重建树**;
- **4 流设计**:输入四等分+6 字节 jumpTable(:1168-1216),解码端 4 个独立位流交织(X1 主循环 16 符/轮,huf_decompress.c:653-676)——**消除符号间数据依赖,喂饱乱序流水**,甚至有手写汇编版(huf_decompress_amd64.S);
- **表变体**:X1 表 2 字节项单符号直出(:330,:522-529);X2 表 4 字节项一次吐两符号(:954,:1606-1615);X1/X2 由预标定耗时表选择(:1803-1852)。

## 2.6 NCount 序列化的位级技巧

表头(FSE_Table_Description)的紧凑序列化:tableLog 只存低 4 位+5(entropy_common.c:72);**概率字段宽度随剩余配额的对数缩窄**,低值区"逃逸"少读 1 位(:135-142;fse_compress.c:291-302);概率 0 后接 2bit 游程标志,≥24 游程直接写 0xFFFF,读端用 CTZ 指令一次数完(entropy_common.c:88-103)——**"常见情形最短编码"贯穿到表头本身**。

## 2.7 与 deflate 对照及设计动机

deflate 只有 Huffman(整比特边界);zstd 字面量也用 Huffman 但加 4 流并行,序列则交给 FSE 拿回分数比特。与 rANS 家族(现代 LZ4 变体/kraken)对照:tANS 用"表"换掉了 rANS 的乘除,**解码每符号 O(1) 无分支**。设计动机:①归一化的每一点精度都是压缩率;②spread 是"数学正确性靠工程纪律保证"的样本;③4 流是 SIMD 时代的必然——**数据并行从算法层就设计进去**。

## 2.8 FAQ

**Q1:FSE 和 Huffman 什么时候各用?**
字面量永远 Huffman;序列 LL/ML/Off 各一张 FSE 表;连 Huffman 权重串也 FSE 压(doc:1034-1039)。

**Q2:AccuracyLog 越大越好吗?**
表越大越精确但表头越贵、构建越慢:FSE_optimalTableLog=log2(srcSize)-2 封顶。

**Q3:为什么解码能每符号 O(1)?**
一步=查表出符号+读定长位——把算术编码的乘除固化成表(:510-515)。

**Q4:4 流为什么是 4 不是 8?**
四等分+6 字节 jumpTable 的对齐(:1168-1216);4 流已喂饱乱序流水,更多流表头开销不划算。

**Q5:概率 -1 是什么?**
"太稀有"符号:不占表槽,出现在表尾+逃逸位表示(:78-87)——低概率事件的表示成本问题。

**Q6:位流为什么要倒读?**
tANS 编解码互逆要求状态回溯方向相反(:52-55):编码正写、解码倒读,同一张表。

**Q7:endMark 是干什么的?**
1 位收尾保证末字节非 0(:236-242)——位流长度自描述,免传长度。

**Q8:表头能多大?**
NCount 序列化本身用"剩余配额对数"缩窄字段(:135-142):表头的自我压缩。

**Q9:X1 和 X2 表差在哪?**
X1 单符号 2 字节项;X2 双符号 4 字节项(:1606-1615):预标定耗时选型(:1803-1852)。

**Q10:有汇编吗?**
有:huf_decompress_amd64.S 手写 4 流热循环——库级性能优化的最后一层。

## 2.9 小结与深挖方向

本章结论:**熵编码="tANS 状态机(分数比特)+Huffman 4 流(并行)+位级表头自压缩"**;归一化与 spread 是压缩率的命门。深挖:

1. FSE_normalizeCount 残差给最大符号(:502-507)的失真上界;
2. spread 步长常数(:623)的数学证明(作者博客的论证);
3. HUF_setMaxHeight 贪心还债(:376-499)的最优性;
4. amd64.S 手写汇编与 C 版的吞吐差;
5. rANS 互操作:为什么 zstd 不换 rANS(解码表 O(1) 的护城河)。
