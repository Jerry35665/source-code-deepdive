# 第 06 章 · 字典训练与工程文化(卷末)

> 基线:commit `d79e723`。行号以 lib/dictBuilder/cover.c、fastcover.c、zdict.c 与 tests/、lib/libzstd.mk 为准。前五章讲本体,本章讲两个外围但关键的板块:字典(小数据压缩的命门)与工程实践。

## 6.0 全景:字典的两种来源与预编译价值

字典两种来源:**训练生成**(cover/fastcover 算法,8 字节头 magic 0xEC30A437+dictID+熵表+内容段)vs **raw content**(任意缓冲);运行时由 `ZSTD_dct_auto/rawContent/fullDict` 分流(lib/zstd.h:1374-1376)。CDict/DDict 的价值在**预编译**:创建时建好熵表与参数(zstd_compress.c:5620-5622,zstd_ddict.c:111-115),小输入(<128KB 或 <6 倍字典)走 attach 共享(:5260-5290)——**小数据场景把"传表"成本摊销掉**,这就是 zstd 在短消息压缩(日志/JSON/传感器)的胜负手。

## 6.1 cover:分治与"按样本数计分"

cover 源自 WWW 2016 论文(cover.c:12-18)。核心洞见:段评分 Score(S)=ΣF(S_i),而 **d-mer 只按"出现在多少个不同样本"计数,不按出现次数**(cover.c:453-456)——样本内的重复 zstd 本可自引用,字典应该存"跨样本共性"。部分后缀数组+epoch 分治(每 epoch≥10k 字节);**字典从尾部向前填**,让高分段落在最小偏移(:795-799)——偏移小=编码便宜。(d,k) 网格搜索:d∈{6,8}、k∈[50,2000]、40 步、线程池并行,用真实 `ZSTD_compress_usingCDict` 压测试集选优(:1197-1333)——**用最终指标选参数,不用代理指标**。

## 6.2 fastcover:10 倍加速的演进

fastcover 用 2^f 哈希频次表(f 默认 20)替代后缀数组+accel 抽样(每 skip+1 个 d-mer 采一个,accel≤10)(fastcover.c:101-113)——约 10 倍加速。`ZDICT_trainFromBuffer` 已默认绑定 fastCover d=8/steps=4(zdict.c:1111-1127),cover 降级为精度选项。**evolution:更好的默认+保留旧的精确选项**,与 Git cover→fastcover? 与 FFmpeg fast 组合异曲同工。finalize 细节:dictID=XXH64(内容)映射进 [32768,2^31)(zdict.c:883-885);熵表由把字典当 raw content 建 CDict 逐块压缩统计而来(:703);**统计出的最优 repcode 被算出但 `#if 0` 掉、实际写默认值**(:828-838)——一处诚实的技术债;minimum 样本 5 个、建议 100×字典大小(cover.c:648-650,zdict.h:132)。

## 6.3 测试文化:反证法与 fuzz 优先

三层 CI(TESTING.md:4-44):short=编译矩阵+playTests.sh;medium=ASan/UBSan/MSan+三大 fuzzer+Tsan+valgrind;long=全量+版本互解。**decodecorpus 的反证法**(tests/decodecorpus.c:1272-1285 generateFrame):从随机种子**按规范手写合法帧**,交真解码器 round-trip——解码器理解错规范或生成器写错规范都会炸。这与 fuzz 的"不该崩的不崩"成对偶:**正向构造+负向破坏**。fuzz 优先:tests/fuzz/ 21 个 target(字典相关占 5 个),libfuzzer/afl/regression 三引擎统一驱动,OSS-Fuzz 徽章挂 README;兼容三重防线:tests/legacy.c 硬编码 v0.1-v0.7 真实帧(:26-49)、test-zstd-versions.py 全历史版本互解、ZSTD_LEGACY_SUPPORT 按版本切片编译(libzstd.mk:198-203,v1.6.0 起 legacy 默认关闭)。

## 6.4 构建联邦与最小发行

构建系统联邦:Make/CMake/Meson/VS 手工工程/bazel 外置 Central Registry/单文件 combine.py 拼接(WASM 解码器约 26kB)——**多生态用户面+零依赖小库的产物**。`ZSTD_LIB_MINIFY` 一键最小构建(libzstd.mk:27-42):强制 x1 Huffman、剥错误串、-Oz;legacy 默认 0(:32)。发布节奏 v1.0.0(2016-09)→v1.6.0(2025-12)约 40 版,近年一年一版——**成熟库的慢发布**。

## 6.5 与前作对照与设计动机

1. **字典 vs 通用压缩的分层**:通用匹配器(03 章)面向"数据内部冗余",字典面向"跨样本冗余"——两套机制正交组合;对照 06 章 PG 统计(数据形状的先验)、FFmpeg 字典? 与 Git 无字典(全量对象);
2. **cover 的"按样本数计分"**:信息论的正确粒度——跨样本泛化才是字典的价值;fastcover 的 accel 抽样是"精度可买"的工程化;
3. **decodecorpus 的哲学**:格式理解的最高证明是"能从零构造它"——与 Git decodecorpus? 与 FFmpeg FATE 的"样本回归"不同,这是"生成式回归";
4. **`#if 0` 的诚实**:算得出最优 repcode 但不敢用(:828-838)——技术债显式标注而非悄悄绕过。

## 6.6 FAQ

**Q1:什么数据该用字典?**
小且同构(1KB 级 JSON/日志/传感器帧):样本间共性>数据内部冗余;大文件不需要(:5260-5290 的启发式)。

**Q2:字典多大合适?**
建议训练样本 ≥100×字典大小(:132);字典本身 110KB 是常见默认。

**Q3:cover 和 fastcover 选哪个?**
默认 fastcover(zdict.c:1111-1127);追求极限比率用 cover(慢 10 倍)。

**Q4:字典能跨 zstd 版本用吗?**
能:字典含完整熵表,格式稳定;dictID 冲突时用显式 ID。

**Q5:decodecorpus 是怎么"反证"的?**
按规范手写帧+round-trip(:1272-1285):两份独立实现(生成器/解码器)必须一致。

**Q6:为什么 legacy 默认关闭?**
v1.6.0 起(libzstd.mk:32):十年了,0.x 文件已是考古对象——默认面收敛。

**Q7:最小构建能小到多少?**
ZSTD_LIB_MINIFY:x1 Huffman+剥错误串+-Oz(:27-42):嵌入式可裁到几十 KB。

**Q8:fuzz 21 个 target 都在测什么?**
流式边界/字典/拆分帧/seekable 等:每个 API 面一个 fuzzer——覆盖面跟着 API 走。

**Q9:训练字典需要多少 CPU?**
fastcover 秒级(accel 抽样);cover 网格搜索分钟级——训练是一次性成本。

**Q10:字典能提升多少?**
README 的 1 万条 1KB JSON 样例:3:1→10:1 级别的跃迁——小数据的杠杆。
