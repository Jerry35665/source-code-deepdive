# 第 09 章 · 工程文化与测试体系:可靠性神话的地基

> 基线:SQLite 3.54.0。行号以该版本源码为准。
> 版本标识说明:git 镜像的 HEAD 是 `492e7fc0`,而仓库内 Fossil 的 `manifest.uuid` 是 `5251f4d7`——SQLite 官方用 Fossil 管理(Git 只是镜像),两种哈希指向同一棵树。读它的仓库时要习惯这种"双 SCM 身份"。

## 9.0 "boring engineering" 的六条实证

"boring engineering" 在 SQLite 不是口号,而是逐条可指认的制度:

1. **所有制与贡献模型写死在文档里**:`AGENTS.md` 开宗明义源码是 public domain,顶部 "blessing" 注释必须原样保留;不接受未经法律文书(贡献入公共领域)的 PR,人类开发者把 PR 当 proof-of-concept 审阅后**自己重新实现**;甚至明文"SQLite does not accept agentic code",但接受带可复现用例的 bug 报告——知识产权洁净性高于贡献速度;
2. **每次提交前至少跑 devtest**:`main.mk:1848-1853` 注释原话 "The devs run `make devtest` prior to each check-in, at a minimum";devtest 先做 srctree-check(校验生成文件与源树一致)再跑测试——纪律靠 Makefile 固化,不靠 CI 提醒;
3. **生成文件一律不手改**:`AGENTS.md` 给出完整对照表(sqlite3.h ← mksqlite3h.tcl;parse.c ← lemon + parse.y;opcodes.h ← mkopcodeh.tcl;keywordhash.h、pragma.h、sqlite3.c ← mksqlite3c.tcl);连编译选项自省文件 ctime.c 都是生成的——仓库里根本不存在;
4. **编码规约保守到刻板**:仅 C89/C99 兼容 C,无 VLA;所有内存分配必须走 sqlite3Malloc;可能超 2G 的数值一律 i64 禁裸 long;OOM 统一 `db->mallocFailed` 延迟判错;"Assert liberally for invariants";
5. **历史包袱平静保留**:test/select1.test 里仍留着 CVS 时代的 `$Id:` 标签;连文件名拼错的 `temptrigfault.tes` 都不改——改名会让外部引用失效,收益只是名字好看;
6. **量级**:test/ 1,194 个 .test 文件 + 36 个 `src/test_*.c` C 侧钩子(test1.c 一个就 9,535 行);静态断言调用约 44,000 处。

## 9.1 测试金字塔:七层结构

```
第0层 testfixture     被测库直接编进 TCL 解释器(main.mk TESTSRC)
第1层 TCL 单元测试     1,194 个 .test,44k 断言,slave interpreter 隔离
第2层 故障注入        OOM/IO 错误的"第 K 次失败"枚举
第3层 permutation     同一套测试 × 63 种运行配置重跑
第4层 mptest 多进程    5-50 进程并发,专攻锁协议
第5层 模糊测试        5 套工具覆盖语法/数据库/损坏文件三种攻击面
第6层 releasetest     24 构建 × 28 置换的发布矩阵(testrunner 调度)
第7层 TH3(私有)     100% MC/DC 覆盖,真实设备,安全关键认证依据
```

**"百万测试用例"的量级来源**(重要澄清):不是静态断言数,而是**故障枚举 × 置换系数**——`do_malloc_test` 内部循环对"第 1 次、第 2 次……第 N 次 malloc 失败"各跑一遍(malloc_common.tcl:681),`do_ioerr_test` 对 I/O 调用同理;44,000 个静态断言乘上这些系数,运行时用例数高出一到两个数量级。

**故障注入是一等公民**:`sqlite3_memdebug_fail N -repeat R` 让第 N 次 malloc 失败(test_malloc.c:544);FAULTSIM 框架统一驱动 OOM/IO 错误(malloc_common.tcl:32-46)——OOM 路径因此获得与正常路径同等的覆盖。

**隔离性**:`slave_test_file` 保证每个 .test 在新建的 slave interpreter 里执行,跑完检查文件句柄归零、全局开关未被篡改(tester.tcl:2415-2428)。

**模糊测试的五套工具**:纯 TCL SQL 语法模糊器、fuzzcheck(外部 fuzzer 产出的**回归回放器**,带 8 个种子库,配套 fuzzinvariants 做"替代查询等价性"断言)、ossfuzz(OSS-Fuzz 官方入口)、dbfuzz2(损坏数据库文件)、sessionfuzz(头文件里写明"run for a while. Weeks, maybe.")。**fuzzer 找新病,回放器防旧病复发**——这个组合比单跑 fuzzer 可复现得多。

**testrunner 吃自家狗粮**:2,205 行的 testrunner.tcl 用一张带依赖/优先级/状态约束的 SQLite `jobs` 表调度并行任务(testrunner.tcl:400-431)——用被测系统自己当消息队列。

## 9.2 test1.c:把"上帝视角"暴露给测试

`test1.c`(9,535 行)不进 amalgamation,只编进 testfixture。注册机制是表驱动:两张静态表(aCmd/aObjCmd,100+ 项)注册 TCL 命令,加十几组 `Tcl_LinkVar` 把 C 全局计数器**双向绑定**为 TCL 变量:`sqlite_search_count`(扫描行数)、`sqlite_sort_count`、`sqlite_open_file_count`、`sqlite_sync_count` 等(test1.c:9442-9533)。

这直接改变测试的表达力:TCL 脚本可以 `if {$sqlite_search_count>100}` **对优化器行为做数值断言**——"是否用了覆盖索引""是否做了 xfer 优化"不依赖输出解析。

三个具体例子:最短的绑定 `sqlite3_libversion_number`(一行包装,让脚本校验被测库版本);`sqlite3_test_control` 的 TCL 化(官方测试后门:注入 localtime 失败、制造 imposter 假表测损坏库);`add_test_collate` 注册**用 TCL 脚本实现的排序规则**(C 回调经 Tcl_EvalObjEx 调回 TCL 比较——专门测 UTF-16 编码路径)。还有个工程细节:指针传给 TCL 用全局哈希表而非 `%p` 字符串——某些安全关键编译器不允许对从字符串解码的指针解引用(test1.c:42-59)。

**双层 TCL 设计**:`tclsqlite.c`(产品级扩展,"正常用户视角")与 test1.c 等("上帝视角"测试钩子)在代码里物理隔离,tester.tcl 负责在测试环境把后者挂上。

## 9.3 permutation:一套测试,63 种世界

`test/permutations.test`(1,273 行)是重跑注册中心:`test_suite NAME OPTIONS` 声明套件(description/initialize/presql/files/dbconfig),共 **63 个**命名套件。四类旋钮:

- 运行时配置:singlethread、nolookaside、memsys3/5(切换内置分配器);
- 预置 SQL:persistent_journal、inmemory_journal、utf16、exclusive;
- 连接参数:nomutex、onefile(换 VFS);
- 文件选择:veryquick(排除 *malloc* *ioerr* *fault*)、coverage-* 套件(**覆盖率需求反过来组织测试运行**)。

`test/all.test` 顺序执行 25+ 个套件——"全量测试"不是"跑一遍所有文件",而是**跑约 25 遍所有文件**。permutation 只改运行时状态(同一二进制),编译期旋钮(SQLITE_OMIT_* 等 69 个宏)由 testrunner 的构建矩阵覆盖(linux 17 + osx 2 + win 5 个配置)——两级矩阵正交,组合才是完整覆盖。

## 9.4 API 稳定性与可插拔

**可插拔枢纽 `sqlite3_config`**:约 30 个 SQLITE_CONFIG_* 选项,可整体替换内存分配器(MALLOC)、页缓存(PCACHE2)、互斥实现(MUTEX)、堆与 lookaside;库初始化后调用默认报 MISUSE,仅白名单两个选项可任意时刻调。VFS 层由 sqlite3_vfs_register 支撑——**存储栈每层都可被测试替换**(test_vfs.c 提供注入点)。

**稳定性的三个机制**:

1. **单一权威头文件**:sqlite.h.in:12-16 原话——"If a C-function ... does not appear in this file, then it is not a published API of SQLite, is subject to change without notice";216 处 CAPI3REF 注释块直接生成官方文档;
2. **EVIDENCE-OF 闭环**:文档中每条"可测试语句"编号化(R-xxxxx),代码侧 105 处标注、测试侧 e_*.test 25 个文件反向校验——**文档腐化会立刻变成测试失败**;
3. **版本断言惯例**:官方建议应用层 assert `sqlite3_libversion_number()==SQLITE_VERSION_NUMBER`。

与之对照,**测试接口的反稳定性**:`sqlite3_test_control` 被官方明文声明"subject to change without notice",38 个 TESTCTRL 编号从不承诺跨版本一致。公共 API 二十年不变、测试后门随时可变——这两条并存才是兼容性策略的完整表达。连弃用告警(SQLITE_DEPRECATED)都因"generated such a flurry of bug reports"退化为空宏——只能靠文档纪律。

## 9.5 发布流程与供应链完整性

- **版本单源**:VERSION 文件是唯一事实来源,sqlite3.h、资源文件全部生成,连 SCM 哈希都烧进头文件(3.54 新增 SQLITE_SCM_BRANCH/TAGS/DATETIME 宏);
- **SQLITE_SOURCE_ID 的哈希由 mksourceid.c 对整树计算(SHA3),源码被动过,哈希末 4 位就会变**(sqlite.h.in:140-143 官方规则)——"你手里的 sqlite3.c 是否被篡改"可以在运行时查出来,供应链完整性的朴素实现;
- **amalgamation 生成**:mksqlite3c.tcl 按依赖顺序读入每个文件,白名单头文件递归内联一次、再次遇到则注释掉;给所有函数自动加 SQLITE_API/SQLITE_PRIVATE 链接标记——发布形态是生成物,开发形态是 src/ 多文件,两者都被测试矩阵覆盖(Default 构建显式 --disable-amalgamation)。

## 9.6 对其他项目的十条可借鉴清单

1. 把"提交前测试"写成构建目标 + 注释,并挂上源树一致性校验(忘记再生成在开发循环早期失败);
2. 测试代码与产品代码**物理隔离但同仓**:36 个 test_*.c 只编进 testfixture 绝不进发布物;
3. 故障注入做成一等公民:"第 K 次失败"枚举比随机 chaos 可复现;
4. permutation 思想:一套测试 + 一张声明表,重跑 63 遍,优于 60 份专属测试;
5. 测试调度器吃自家狗粮;
6. 文档即测试的锚点(EVIDENCE-OF 编号);
7. 模糊测试配"回放器 + 种子库" + 等价性不变量;
8. 防御式宏配覆盖率豁免(ALWAYS/NEVER 在 coverage 构建被硬编码,免得"不可达分支"污染统计——想让团队敢写防御代码,必须同时给覆盖率工具打补丁);
9. 生成文件 Never-Edit 纪律 + 机器校验;
10. 版本号单源化。

## 9.7 FAQ

**Q1:为什么 2026 年还在用 TCL 测试?**
历史惯性 + 工程理性:testfixture 模式(被测库直接链进解释器,注册上帝视角命令)是纯外部黑盒框架做不到的;tclsqlite.c 同时是产品级扩展,维护成本两用摊薄。

**Q2:测试为什么放 src/ 而不是 test/?**
分工:test/ 放 TCL 脚本,需要链进 testfixture 的 C 钩子按惯例叫 src/test_*.c,在 amalgamation 生成清单之外——不污染发布物。

**Q3:TH3 在仓库里吗?**
不在。TH3 是私有测试工具(100% MC/DC、真实设备);开源层保证可复现性,私有层保证穷尽性。

**Q4:四万多用例跑完要多久?**
分层:veryquick 数分钟,quick 约 10 分钟,devtest 是提交前最低要求,releasetest 走 24 构建 × 28 置换矩阵由 testrunner 并行。

**Q5:permutation 和 build 配置会不会重复?**
正交:permutation 改运行时状态(同一二进制跑 63 套件),build 配置改编译期宏(需重建)。

**Q6:测试基础设施自己怎么被测试?**
TEST_FAILURE 环境变量强制注入一次失败来测框架本身;slave_test_file 做句柄泄漏与全局状态检查。

**Q7:amalgamation 与多文件哪个被测?**
都被测:发布矩阵 Default 构建显式 --disable-amalgamation 专测多文件路径。

## 9.8 卷末总结

把卷二九章串成一句话:

> **SQLite 用"public domain + 刻板规约 + 单一事实来源"消灭协作噪音,用"编译→字节码→解释执行"的一条流水线消化 SQL 的全部复杂度,用"自描述记录 + 动态类型 + 函数指针单态化"在 22 万行里同时实现内存效率与语义弹性,用"回滚日志/WAL 双引擎"覆盖从网络文件系统到单机并发的全部场景,最后用 44,000 静态断言 × 故障枚举 × 63 置换 × 24 构建把这一切钉进"安全关键"级可靠性的地基里。**

与卷一《Redis》互为镜像:Redis 用一个事件循环和一个全局单例追求延迟确定性,SQLite 用一个巨型 switch 和一套故障注入追求正确性穷尽;前者把复杂度推给"单线程内的预算制",后者把复杂度推给"编译期的一次性付出"。两者的共同点只有一条——**所有热路径上没有任何一件"顺手做的事",每一行代码都能回答"为什么在这里"。**

深挖方向:

1. permutation 隔离边界(sqlite3_config 进程级全局的泄漏风险);
2. fuzzinvariants 替代查询的误报防线;
3. mptest 客户端崩溃后的任务行清理协议;
4. EVIDENCE-OF 编号体系与文档数据库的同步机制;
5. ALWAYS/NEVER 防御分支在 release 构建的体积/预测代价核算。

> 卷二完。卷三《LevelDB》将进入 LSM-Tree 的世界:与 SQLite 的 B-tree 原地更新相反,"顺序写 + 分层压缩"是存储引擎的另一极。
