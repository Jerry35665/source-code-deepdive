# 第 05 章 · 记录格式与类型系统:类型跟着值走

> 基线:SQLite 3.54.0,commit `492e7fc`。行号均以该版本源码为准。
> **版本勘误**:调研开始时按惯例找 `src/record.c`,发现该文件在本版本**已不存在**——序列化一侧自 2022-04-02 起被内联进 `OP_MakeRecord`(vdbeaux.c:3867 注释明确记载),`sqlite3VdbeSerialType()` 被 `#if 0` 保留("STAT3 support has ended")。旧资料引用时需做位置映射:`SerialPut`→vdbe.c:3834-3921,`SerialGet`→vdbeaux.c:4090-4186,比较器族→vdbeaux.c:4705-5130。

## 5.0 三层类型系统:存储类别 × 亲和性 × STRICT

传统行存 RDBMS 的行格式由 schema 唯一决定;SQLite 反其道而行——**类型跟着值走,不跟列走**。整个类型系统是三层正交叠加:

1. **存储类别**(NULL/INTEGER/REAL/TEXT/BLOB):文件格式的物理事实,由每列的 serial type 决定;
2. **亲和性**(affinity):schema 对写入/比较的"建议",只影响转换时机;
3. **STRICT 严格模式**:API 层把"建议"升级为"约束",刻意不碰文件格式。

比较器必须给任意两个值一个全序——因为索引 b-tree 的 key 就是记录本身:`NULL < 数字 < TEXT < BLOB`(vdbeaux.c:4544-4547)。另一个全局分叉:**表 b-tree 的 key 是 8 字节 rowid,根本不走记录比较器**(btree.c:6144 直接断言索引路径)——"intkey 快路径"不是比较器的一个分支,而是整棵 b-tree 层面的分叉。

## 5.1 记录格式:逐字节解剖

```
| hdr-size | type 0 | type 1 | ... | type N-1 | data0 | ... | data N-1 |
    ^varint     ^每列一个 varint(serial type)     ^数据区紧密排列
```

`hdr-size` 是**含它自身**的头长(vdbe.c:3776-3779)。实例:`INSERT INTO t VALUES(127,'ab',x'01',NULL,1)` 的 payload 共 10 字节:

```
字节:  06   01   11   0e   00   09  | 7f 61 62 01
       hdr  t0   t1   t2   t3   t4     data
t0: 127 → type 01,  data=7f(8位补码)
t1: 'ab' → 0x11=17(奇数=TEXT,长度(17-13)/2=2), data='ab'
t2: x'01' → 0x0e=14(偶数=BLOB,长度1), data=01
t3: NULL → 00, 无数据字节
t4: 1 → 09(常量1,零数据长度)
```

**serial type 全表**(vdbeaux.c:3881-3897):

| type | 字节数 | 含义 |
|---|---|---|
| 0 | 0 | NULL |
| 1-6 | 1/2/3/4/6/8 | 大端二补码整数 |
| 7 | 8 | IEEE 754 大端浮点(读回 NaN 即转 NULL,4076-4079) |
| 8/9 | 0 | 常量 0 / 1(文件格式 4 起,零数据长度) |
| 10 | 0 | 内部哨兵:虚表 UPDATE"未变更"列(vdbe.c:3684-3699) |
| N≥12 偶/奇 | (N-12)/2 | BLOB / TEXT(奇偶性承载"是不是 text") |

三个妙处:整型按值选宽度(127 占 1 字节,InnoDB 的 BIGINT 恒占 8 字节);`0` 和 `1` 一个数据字节都不占;48 位整数上限 `MAX_6BYTE = 2^47-1`(vdbeaux.c:3926)是兼容旧格式的历史尺寸。

**编码侧两遍扫描**(OP_MakeRecord,vdbe.c:3577-3928):从最后一列向前算 serial type;负数用 `~i` 而非 `-i` 归一化绝对值(防最小负数溢出);头长自指问题(`nHdr += sqlite3VarintLen(nHdr)`)用兜底修正。还有个隐藏优化:字节序编译期已知时多分配 7 字节 OVERRUN,定长整数用"8 字节整体翻转 + 算术右移"写出,免去逐字节大端化(3799-3803、3863-3868)。

**解码侧惰性解析**(OP_Column):游标缓存 `aType[]` 与 `aOffset[]`,只解析到本次需要的列为止;头长上限 98307 字节(32768 列 × 3 + 3)有硬校验(vdbe.c:3123-3134)。text/blob 解码只挂指针不拷贝(MEM_Ephem)。

## 5.2 比较器族:函数指针单态化的三级体系

这是本章最值得学习的工程:`RecordCompare` 不是"一个带分支的函数",而是**为每次 b-tree 搜索选择一个专用函数**——把"是否 DESC、是否 BINARY、首列类型"这些循环不变量在搜索前物化掉(vdbeaux.c:5085-5130):

```c
RecordCompare sqlite3VdbeFindCompare(UnpackedRecord *p){
  if( p->pKeyInfo->nAllField<=13 ){
    int flags = p->aMem[0].flags;
    if( p->pKeyInfo->aSortFlags[0] ){          /* DESC */
      p->r1 = 1;  p->r2 = -1;                  /* 预先对调 */
    }else{ p->r1 = -1; p->r2 = 1; }
    if( (flags & MEM_Int) ){ p->u.i = p->aMem[0].u.i;
      return vdbeRecordCompareInt; }           /* 快路径1: 整型首列 */
    if( ...aColl[0]==0 ){ p->u.z = ...; p->n = ...;
      return vdbeRecordCompareString; }        /* 快路径2: BINARY 文本首列 */
  }
  return sqlite3VdbeRecordCompare; }           /* 通用版 */
```

**快路径 1(整型首列)**的精华(vdbeaux.c:4947-5006):不按宽度 switch,而是统一读 8 字节、按 serial type 查表算术右移——因为键中整数宽度经常混布,switch 会分支误预测。注释坦承算术右移是"not defined by the C standards",靠 assert+testcase 兜底(4970-4981)——**用 UB-adjacent 技巧换分支预测的教科书案例**。

**为什么是 13 列上限**:快路径假设头部 varint 单字节且可越界读;13 列时最大合法头 62 字节 ≤ 63,配合调用方提供的 74 字节 padding 契约刚好安全(vdbeaux.c:5086-5098)。溢出页 buffer 无法满足契约,**主动降级**回通用版并只给 18 字节 padding(btree.c:6199-6228)。这条"74 字节 padding"链路是跨文件数值契约,没有任何编译期保护。

`UnpackedRecord` 的 `default_rc`(前缀全等时的默认返回值)让二分分别落在非唯一索引的第一个/最后一个匹配项;`r1/r2` 把 DESC 翻转前移到初始化期(sqliteInt.h:2747-2764)。调试态下 `vdbeRecordCompareDebug` 用朴素实现对拍优化版(vdbeaux.c:4271-4377)。

表树则完全绕过这一切:`sqlite3VdbeIdxRowid`(vdbeaux.c:5140-5210)靠"头长 varint 定位最后一个 type、从尾部反向取整数"免解码直取 rowid——索引记录的最后一个字段固定是 rowid。

## 5.3 类型亲和性:三种转换强度

建表时亲和性判定:标准类型名直查 `sqlite3StdType[]` 表;自定义类型(如 VARCHAR(10))用滑动哈希找子串,**优先级 INT > CHAR/CLOB/TEXT > BLOB > REAL/FLOA/DOUB > 都不含则 NUMERIC**(build.c:1696-1776)——所以 `BLOBINT` 是 INTEGER(INT 命中即 break)。

同一个"把字符串变成数",SQLite 有三种强度截然不同的实现,这是本章最重要的语义区分:

| 强度 | 函数 | 语义 | 使用场景 |
|---|---|---|---|
| 建议 | `applyNumericAffinity`(vdbe.c:354-372) | **无损才转**,失败保留原值 | 亲和性、比较 |
| 断言 | `sqlite3VdbeMemNumerify`(vdbemem.c:893-917) | **尽力解析前缀**,忽略尾部垃圾 | CAST |
| 事实 | OP_Column | 不做任何转换 | 读取 |

`applyAffinity` 的三要点(vdbe.c:397-428):TEXT 亲和只转"有数值表示的值",blob 与 NULL 永不转;NUMERIC/INTEGER/REAL 只对字符串动手,且"能无损转整数就转整数——即使亲和是 REAL,因为整型在磁盘上更省";文本转数后**必须剥离文本表示**('4.0' 这种非规范形式不能留在 Mem 里,注释引用 ticket 343634942dd54ab57b7024)。

转换时机清单:写入时(INSERT 生成 `OP_Affinity`,P4 是逐列亲和性字符串);比较时(OP_Eq/Lt 的 P5 编码比较亲和性,两侧都无数值亲和则 BLOB 即不转换——防 `WHERE text_col = int_col` 造成索引失效);CAST 时(强制);**读取时不转**。

**MEM_IntReal 折中**:REAL 亲和的值尽量整型落盘,但身份是 REAL——既省空间又保证 `typeof()` 语义正确(6 字节范围内无损,超出才降级 double)。这是 SQLite 把"整型更省"的文件格式原则与"类型上报正确"调和的关键标志位。

## 5.4 STRICT 与 collation

**STRICT 表**(build.c:2756-2792)的运行时落点是新 opcode **OP_TypeCheck**(vdbe.c:3426-3514):代码生成器把刚生成的 OP_MakeRecord 原地改名再补插(insert.c:182-201)——记录造出来之前先验类型;类型不符报 `SQLITE_CONSTRAINT_DATATYPE`。存量数据的体检走 **OP_IsType**——直接用游标已解析的 serial type 位掩码判型,**不物化列值**(vdbe.c:2860-2920);唯一例外是 NaN:serial type 7 读出的 NaN 等价 NULL,OP_IsType 检测不到,必须真的读值(pragma.c:1965-1972)。

collation 最终汇聚到 `KeyInfo.aColl[]`:**BINARY 存成 NULL**(build.c:5748-5749),使比较器在无 collation 时走 memcmp 快路径——FindCompare 的 `aColl[0]==0` 检查因此成立。NULL 的全序位置定死为最小;`NULLS FIRST/LAST` 语法只允许出现在 ORDER BY,索引用它直接报错(build.c:3992-4006);索引内部唯一需要"NULL 视为最大"的是 min() 优化:设 `KEYINFO_ORDER_BIGNULL` 让顺扫跳过前导 NULL(select.c:5481-5485)。

**ROWID 别名**:单列 INTEGER ASC 的 PRIMARY KEY 不建索引,把列下标记进 `pTab->iPKey`(build.c:1885-1963)——IPK 的索引就是表本身。

## 5.5 FAQ

**Q1:把 '1.0' 存进 INTEGER 列,读出来是什么?**
整数 1(可无损转 → IntegerAffinity 往返无损 → MEM_Int 落盘)。存 'abc' 则原样保留文本。反过来 5 存进 TEXT 列变 '5' 且 Mem 里整数表示被剥离。

**Q2:STRICT 表的 REAL 列存 5,typeof 是什么?**
'real'——以 6 字节整型落盘但身份是 REAL(MEM_IntReal);超 6 字节范围才降级 double。

**Q3:BLOBINT 的亲和性?**
INTEGER。INT 子串最先判且 break(build.c:1742-1745)。

**Q4:TEXT 和 BLOB 谁大?**
NULL < 数字 < TEXT < BLOB;TEXT 内部按 collation,BLOB 按 memcmp。

**Q5:为什么比较快路径只服务 ≤13 列?**
头部单字节 varint + 74 字节 padding 契约的数值边界;多列索引自动退回通用比较器,只影响速度不影响正确性。

**Q6:`CAST('12abc' AS INTEGER)` 得到什么?**
12。CAST 是"断言"(解析前缀);WHERE 里的转换是"建议"(无损才转)。

**Q7:文件里的 NaN 读出来是什么?**
NULL;排序时 NaN 被当作 NULL,任何整数都大于它。

**Q8:default_rc 是干什么的?**
非唯一索引上让二分收敛到第一个/最后一个匹配;eqSeen 告诉上层是否存在精确等值。

## 5.6 小结与深挖方向

本章结论:**记录格式 = 自描述头(每行 1+K 字节)换逐行最优存储与 schema 弹性;类型系统 = 存储类别(物理)× 亲和性(建议)× STRICT(约束)三层正交;性能 = 函数指针单态化 + 越界读契约**。深挖方向:

1. record.c 消亡史:把热点摊进 opcode 替代独立翻译单元的内联收益量化;
2. 算术右移 UB 契约在各编译器/UBSAN 下的实测;
3. 74 字节 padding 契约的传递链验证(最大合法头 63 + 8 + 余量?);
4. BIGNULL × DESC 的真值表逐格验证;
5. FLEXNUM(3.54 新语义:子查询 CAST 列的"只比较时转数"亲和)与 NUMERIC 在三个场景的精确差异。
