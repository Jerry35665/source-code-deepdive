# 第 01 章 · 全景与代码地图:22 万行的"无聊"工程

> 基线:SQLite 3.54.0,commit `492e7fc`(2026-08-27,trunk 滚动开发分支)。

## 1.1 一组数字认识这个项目

| 指标 | 数值 |
|---|---|
| src 下 .c / .h 文件数 | 125 / 24(其中 44 个 .c 是测试扩展 test*.c) |
| 源码总行数(.c + .h) | 220,515 |
| TCL 测试脚本 | 1,194 个(test/*.test) |

**与 Redis 卷对照**:两者同为 15-22 万行级,但 SQLite 的"单文件自包含、零外部依赖、测试密度(1194 个测试文件对 ~140 个源文件)"是另一个极端。它是世界上部署最广的数据库(每部手机、每个浏览器、每架波音 787 里都有),却保持着罕见的工程纪律。

## 1.4 构建体系与代码生成

SQLite 的构建是"双轨"的:仓库内 `autosetup/`(configure)+ 各平台 Makefile;发行时 amalgamation 一把梭。**三处代码生成**值得知道:

1. **lemon**(tool/lemon.c):SQLite 自研的 LALR 解析器生成器,比 yacc 多了"归约冲突消解规则"与错误恢复语法,parse.y → parse.c/parse.h;
2. **mkopcodeh.tcl / mkopcodec.tcl**:从 vdbe.c 的注释里抽取 opcode 清单生成 opcode.h —— opcode 的权威定义就写在实现函数上方的注释里;
3. **pragma.h**:由 pragma 清单表格生成。

这解释了为什么读 SQLite 源码要"以生成物为辅、以源头为主":opcode、解析表、pragma 都有单一事实来源。

## 1.5 测试体系:1194 个测试文件如何组织

- `test/*.test`:TCL 脚本,配 `test1.c` 暴露的数百个内部钩子(如 `db_leave`、`sqlite3_test_control`),能注入 malloc 失败、IO 错误、页损坏;
- `test/*.inc` / `permutations.test`:同一套测试在不同编译选项(WAL 开关、mmap、安全删除)下全组合重跑;
- **TH3**(未随开源仓库发布):100% 分支覆盖的军用级测试,配合 mutation testing(改变源码某行,断言必有测试失败);
- **SQLLogicTest**:数百个第三方 SQL 语义测试全部通过;
- **mptest/**:5-50 进程并发读写压测,专攻锁协议;
- fuzz:fuzzcheck + SQL 语法模糊器 + valgrind 常态化。

这套体系支撑了 SQLite 的两个公开承诺:**每个 release 100% 分支覆盖**,以及"比大多数应用的宿主代码更可靠"的架构性目标(第 09 章展开)。

## 1.6 三条阅读路线

1. **自底向上**(存储视角,推荐先读):03 B-tree → 04 事务/WAL → 05 记录格式 → 08 VDBE。理解"数据在盘上和内存里的样子";
2. **自顶向下**(SQL 视角):02 执行框架 → 06 编译前端 → 07 优化器 → 08 VDBE → 03/04。理解"一条 SQL 的一生";
3. **排障路线**(SRE 视角):04 的锁与 BUSY 清单 → 03 的损坏判定 → 09 的测试与 PRAGMA 工具箱。
