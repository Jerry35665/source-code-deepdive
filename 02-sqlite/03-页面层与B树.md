# 第 03 章 · 页面层与 B-tree:唯一理解文件字节布局的模块

> 基线:SQLite 3.54.0,commit `492e7fc`(2026-08-27)。行号均以该版本源码为准。
> 分层定位:btree.c 处于 VDBE 之下、Pager 之上,是**唯一理解数据库文件字节布局的模块**——pager 把文件看作"编号页面的数组",pcache 负责缓存页面,而"页面上每个字节是什么"完全是 btree 层的知识(btree.c:12-14)。

## 3.0 四个核心结构

| 结构 | 位置 | 职责 |
|---|---|---|
| `MemPage` | btreeInt.h:273-304 | 一页的解析视图,含按页类型"虚分发"的 `xCellSize/xParseCell` 函数指针 |
| `BtShared` | btreeInt.h:425-460 | 一个数据库文件一份:Pager、页大小、阈值参数、游标链表、常驻的页 1 |
| `BtCursor` | btreeInt.h:531-560 | 游标 = 父页栈 `apPage[]` + 每层下标 `aiIdx[]`,树深上限 20 层,超限即判损坏 |
| `CellInfo` | btreeInt.h:480-486 | 一次 cell 解析产物:nKey、pPayload、nPayload、nLocal、nSize |

两个句柄刻意分离:`Btree` 是连接私有薄壳,`BtShared` 才是文件级共享体。非 shared-cache 编译下 `sqlite3BtreeEnter()/Leave()` 被宏成空操作(btree.h:406-411)——真正的并发正确性主要由 pager 层保证。游标结构由调用者(VDBE)按 `sqlite3BtreeCursorSize()` **预分配**,btree 层绝不越权扩展它;所有附加缓存(aOverflow、pKey)单独 malloc(btree.c:4821-4823、4878-4881)。

## 3.1 数据库文件格式:100 字节头与页内布局

文件被划分为 512B~65536B(2 的幂)的页,页号从 1 开始。页 1 永远是 schema 表 `sqlite_master` 的根,前 100 字节是文件头(btreeInt.h:57-82):

```
偏移  长度  内容
0     16   "SQLite format 3\0" 魔数
16    2    页大小(值 1 表示 65536)
18/19 1+1  写/读版本(1=rollback, 2=WAL)
20    1    每页末尾保留字节数(留给加密扩展)
21-23 3    payload 分数,恒为 64/32/32
24    4    file change counter
28    4    数据库页数
32/36 4+4  freelist 首个 trunk 页 / 空闲页总数
40    60   15 个 4 字节 meta 值
92/96 4+4  version-valid-for / SQLITE_VERSION_NUMBER
```

三个容易被忽略的文件级事实:

1. **所有空间计算用 `usableSize = pageSize - 保留字节`**(btree.c:3103-3134),而非页大小;
2. **1GB 处有一个"锁字节区"**(PENDING_BYTE,0x40000000):落在哪个页,那个页就不得存数据(btreeInt.h:612)——页大小必须是 2 的幂的原因之一,就是让锁字节恰好顶在页首(btree.c:3092-3095);
3. 打开时的校验入口 `lockBtree()`(btree.c:3312-3489)会校验魔数、读写版本、以及 21-23 三字节必须 `\100\040\040`("自 3.6.0 起固定")。页大小读取一行代码很妙:`pageSize = (page1[16]<<8) | (page1[17]<<16)`(3401)——值 1 经 `<<16` 恰好变成 65536,一举两得。

四个本地负载阈值在 lockBtree 末尾计算(3471-3479):

```c
pBt->maxLocal = (u16)((pBt->usableSize-12)*64/255 - 23);
pBt->minLocal = (u16)((pBt->usableSize-12)*32/255 - 23);
pBt->maxLeaf  = (u16)(pBt->usableSize - 35);
pBt->minLeaf  = (u16)((pBt->usableSize-12)*32/255 - 23);
```

-23 的来历:预留 2 字节 cell 指针 + 4 字节孩子指针 + 9 字节 nKey + 4 字节 nData,保证一页至少能装 4 个 cell。4096 页下:maxLocal≈990、minLocal≈483、maxLeaf=4061。

### 页内布局

```
+---------------------------+ 0
| 文件头 100B(仅页 1)      |
+---------------------------+ 0 或 100
| 页头 8B(叶)/12B(内)      |  flags; 首个freeblock; cell数;
|                           |  cell内容区起点; 碎片总数; 最右孩子(内页)
+---------------------------+
| cell 指针数组(每项 2B)   |  按 key 升序,向下增长
|---------------------------|
| 未分配空间(gap)          |
|---------------------------|
| freeblock 链 + 碎片       |
|---------------------------|  ^
| cell 内容区               |  |  自页尾向上增长,无序
+---------------------------+ usableSize
```

页内自由空间有三个实体(btreeInt.h:152-159):未分配区、**freeblock 链**(≥4 字节的洞按地址升序串链,头 4 字节 = 下一个偏移 + 本块大小)、**碎片**(1~3 字节挂不上链的小洞,总数记页头偏移 7,上限 60)。

分配路径 `allocateSpace()`(btree.c:1846-1930):先试 freeblock 链(`pageFindSlot`,余量 <4 字节就计为碎片,碎片超 57 就放弃该洞)→ 不够则 `defragmentPage()` 整页整理 → 最后从未分配区顶端下切。**cell 指针数组与内容区相向增长**,让"加 cell"通常无需移动任何已有数据——只有两者相遇才触发整理。释放路径 `freeSpace()`(1945-2041)做双向合并;若释放块正好顶着内容区起点,直接扩大未分配区而不建 freeblock。

## 3.2 表 B-tree 与索引 B-tree:同页管理,不同 cell

页类型只有 4 种(btree.c:2048-2053):`0x05` 表内页、`0x0D` 表叶、`0x02` 索引内页、`0x0A` 索引叶。`decodeFlags()` 按类型安装对应的解析函数与阈值(2055-2112)。

```
表叶(0x0D)               表内页(0x05)            索引内页(0x02)        索引叶(0x0A)
+------------------+      +---------------+        +---------------+     +----------------+
| var payload 长度  |      | 4 左孩子页号   |        | 4 左孩子页号   |     | var payload长度 |
| var rowid(key)   |      | var 分割 rowid |        | var payload长度|     | payload(完整记录)|
| payload(记录)    |      +---------------+        | payload(记录)  |     | 4 首溢出页(可选) |
| 4 首溢出页(可选) |                                | 4 首溢出页(可选)|    +----------------+
+------------------+                                +---------------+
```

差异的本质三点:

1. **key 的存储**:表树 key 是 64 位 rowid,直接编码进 cell 头(btreeParseCellPtr 对 varint 做了含 9 字节符号修正的完全展开手工解码,btree.c:1325-1354);索引树 key 就是整条记录(`nKey = nPayload`,1395);
2. **内页是否有负载**:表树内页 cell 只有"左孩子 + 分割 rowid"(1280-1283);索引树内页与叶子同构——分割 key 会真实复制进父页。所以 balance 时索引树还要把 divider 从父页摘下再插回;
3. **阈值不同**:表叶用 maxLeaf(≈整页),索引页用 maxLocal/minLocal(为 4 cell 留余量)。

**溢出截断公式**是文件格式兼容性的关键(btree.c:1205-1234):

```c
surplus = minLocal + (nPayload - minLocal) % (usableSize - 4);
if( surplus <= maxLocal ){ nLocal = surplus; } else { nLocal = minLocal; }
nSize = &pPayload[nLocal] - pCell + 4;   /* +4 是末尾的溢出页号 */
```

动机:让溢出链的**尾页尽量填满**(余数交给尾页),本地部分保持在 [minLocal, maxLocal]。溢出页本体是"4 字节下一页号 + usableSize-4 数据"的单链表;读取路径 `accessPayload()`(5155-5430)维护游标级缓存 `aOverflow[]` 惰性填充。上限哨兵:`MX_CELL = (pageSize-8)/6`(最小 cell 6 字节假设),btreeInitPage 超限即判损坏(2277-2280)。

| 维度 | 表 B-tree(intkey) | 索引 B-tree(index) |
|---|---|---|
| key | rowid 内嵌 cell 头 | 整条记录即 key |
| 内页 cell | 4B 左孩子 + 分割 rowid | 4B 左孩子 + 完整记录 |
| 本地负载阈值 | maxLeaf(≈整页) | maxLocal/minLocal |
| 查找入口 | TableMoveto(5837) | IndexMoveto(6068) |
| balance 特化 | balance_quick 可用 | 无 quick 路径 |

## 3.3 查找:到处是"用历史位置作弊"

`moveToRoot()`(5586-5663)先做"同表连续查找不重复走根"的复用;`sqlite3BtreeTableMoveto()`(5837-5978)三个快捷短路先行:已停在同一 key、已停在 AtLast 且目标更大、目标 key 恰为当前 key+1 时改用一次 Next 试探。主体是页内二分 + 沿左孩子下探。

`sqlite3BtreeIndexMoveto()`(6068-6299)多两件事:两个基于"游标在树最右页"的短路避免回根(6104-6127);局部优化 `indexCellCompare`(5996-6026)——负载全本地且首字节 varint 足够小时直接比较,否则返回 99 迫使走慢路径(溢出 cell 要 malloc 缓冲拼出完整记录)。

跨页移动交给 NOINLINE 的 btreeNext/btreePrev;游标被写操作"甩出"后进入 `CURSOR_REQUIRESEEK`(保存 `(pKey,nKey)` 待重 seek)。保存动作有个细节:表树只存一个 rowid(**零拷贝**),索引树要把整条 key malloc 并多垫 17 字节——注释解释:防 key 损坏时 restore 阶段越读(btree.c:742-746)。

读到数据是独立路径:`fetchPayload()`(5433-5455)是**零拷贝快路径**,直接把页内 payload 指针交出去,调用方保证下次 btree 调用前用完——这是 VDBE 大多数读行的实际通道。

## 3.4 插入与 balance:与教科书 B-tree 的三大不同

`sqlite3BtreeInsert()`(9441-9742)流程:同表多游标先 saveAllCursors → 定位(表树有 `BTCF_ValidNKey` 快捷判断 + BTREE_APPEND 偏右定位)→ `fillInCell()` 在 pTmpSpace 构造 cell → 同尺寸直接 memcpy 覆写(9657-9678,注释:实验证明"变小后回收余量"并不更快)→ 否则 dropCell + insertCell;**页内放不下时先把 cell 暂存在 `MemPage.apOvfl[4]`,页本身保持不变**,等 balance 统一处理(7478-7488)。

balance 的三大不同:

**其一,没有"最小占用"约束。** `balance()`(9162-9291)自叶向根循环,退出条件是"无溢出 cell 且空闲不足 2/3"(9175-9180)——**只要空闲不超过 2/3 就不动**。教科书 B-tree 的"至少半满"不变量被有意放弃:删除后页可以长期保持很空,写放大换实现简单。

**其二,加层只靠 balance_deeper。** 根页有溢出 cell 时,把根内容整体复制到新页,根变内页只留一个右孩子(9081-9126)——唯一的"加层"操作。

**其三,顺序追加走四条件特化路径 balance_quick。** 表叶子 + 恰好 1 个溢出 cell 且在末尾 + 父页非页 1 + 该页是父页最右孩子(9217-9222)——直接新建右兄弟页、追加 divider,完全不动已有页(8039-8133)。其余情形走 `balance_nonroot()`(8277-9080):取当前页 + 左右各 1 个兄弟(NB=3,注释"从未测过其他值"),全部 cell 倒进 CellArray 重新贪婪装箱;**然后把新页按页号排序,用 sqlite3PagerRekey 交换缓存中的页身份,让磁盘上兄弟页页号连续**——注释称这个"把 B-tree 写放大转化为顺序 I/O"的优化使大批量插入快约 25%(8724-8738)。

配合 Insert 刻意把游标留在最后位置(9703-9711,自增主键的顺序追加无需重新 seek),这就是 **SQLite 顺序写快的机制级原因**。

删除路径 `sqlite3BtreeDelete()`(9873-10073):内页删除不做子树合并,而是找**前驱叶子 cell 提升填补**(9955-10015),之后统一按"叶子少了一个 cell"处理;空闲 >2/3 才触发 balance。

## 3.5 页供给:freelist 与 ptrmap

`allocateBtreePage()`(6546-6854)优先从 freelist 取——文件头偏移 32/36 是 trunk 页号与空闲页总数;trunk 页结构是"下一 trunk 页号 + leaf 数 + leaf 页号数组"(btreeInt.h:211-214),取页时按 nearby 参数挑最近页号。freelist 空则从文件尾追加,撞上 ptrmap 页或锁字节页则跳过。

**auto_vacuum 的 ptrmap**:每 usableSize/5+1 个数据页配一张指针映射页,每项 5 字节"类型(1B)+父页号(4B)"(btreeInt.h:664-668)。它回答"谁指向我"——收缩文件、搬移页时,O(1) 定位所有引用(溢出链、freelist 链的父不固定)。代价约 0.2% 页数。非 auto_vacuum 库删页只进 freelist,文件永不缩小。

## 3.6 设计动机十条

1. **页即解析缓存**:MemPage 挂在 pager extra 区随缓存存活,解析成本摊到缓存生命周期;
2. **双 B-tree 而非单格式**:intkey 树让 `WHERE rowid=?` 无需解码记录;索引树内页带完整记录,范围扫描无需 sibling 指针;
3. **无最小占用 + 2/3 阈值**:简化平衡,牺牲密度换写放大可控;
4. **溢出页给 cell 尺寸设上界**:保证 balance_nonroot 的装箱在常量个页内完成;
5. **写时暂存 apOvfl**:先记账不搬数据,避免"放不下就整理"的抖动;
6. **页号重排换扫描局部性**(约 25% 提速);
7. **5 字节/页的 ptrmap 换 auto_vacuum 的 O(1) 挪页**;
8. **游标零拷贝但脆弱**:REQUIRESEEK/SKIPNEXT 状态机 + saveAllCursors 兜底;
9. **大量"避免从根开始"的短路**——B-tree 层把精力花在别回根,而不是优化单次下探;
10. **防御式编程密度**:页字段读取几乎都伴随损坏检查,错误定位到页号(`SQLITE_CORRUPT_PGNO`);`PRAGMA integrity_check` 复用同一批检查函数——**btree 层同时是文件格式的第一道免疫系统**。

## 3.7 FAQ

**Q1:SQLite 的 B-tree 页至少要半满吗?**
不是。没有任何最小占用强制;balance 只在"溢出或空闲超 2/3"时触发(9175-9180)。

**Q2:大记录为什么从 minLocal+余数处截断,而不是 maxLocal?**
让溢出链尾页尽量填满(余数落尾页);若一律取 maxLocal,尾页平均只剩一半数据。

**Q3:1~3 字节的小空洞去哪了?**
挂不上 freeblock 链(头就要 4 字节),记为碎片,总数存页头偏移 7,上限 60。

**Q4:cell 内容区为什么从页尾向页头增长?**
与指针数组相向增长,"加 cell"通常零搬移;相遇才整页整理。

**Q5:删除内页条目时两棵子树怎么办?**
不做合并:提升前驱叶子 cell 填洞,之后只对叶子做常规 balance。

**Q6:65536 页大小有什么特殊处理?**
两个 2 字节字段存不下:页大小用值 1 表示、读取时 `<<16` 还原;内容区起点用 0 表示,特判处理。

**Q7:同一 key 的 UPDATE 为什么可能零 I/O 重排?**
同尺寸覆写短路:新旧 cell nSize 相同且本地存放时直接 memcpy;同长同内容走 btreeOverwriteCell 的 memcmp 跳过(9296-9333),溢出内容甚至沿链原位覆写。

**Q8:balance_quick 为什么触发条件那么苛刻?**
它只服务顺序追加(表叶 + 末尾单个溢出 cell + 父页最右孩子),此时新建右兄弟即可,不动任何已有页。

**Q9:游标为什么不需要 malloc?带来什么约束?**
由 VDBE 预分配;btree 层绝不扩展它,附加缓存(aOverflow、pKey)单独 malloc 并在 close 释放——"借来的内存"约束。

**Q10:auto_vacuum 没有_ptrmap 不能收缩文件吗?**
收缩要修改所有"父→子"指针;溢出链、freelist 的父不固定,没有反向索引就只能全库扫描。

## 3.8 小结与深挖方向

本章结论:**SQLite 的 B-tree 层 = "页格式 + 双树分叉 + 无不变量的惰性平衡 + 到处避免回根"**。它不是教科书 B-tree,而是一台围绕"顺序访问快、实现简单、可校验"三个目标调校过的机器。深挖方向:

1. balance_nonroot 多页写序与 pager 回滚日志的崩溃一致性配合;
2. PAGER_GET_NOCONTENT 与 freelist 灰区的读盘判定;
3. aOverflow 游标缓存在 SAVEPOINT 回滚间的失效完备性;
4. PagerRekey 三步换位与锁字节页冲突的极端序列;
5. BTREE_FORDELETE 与增量 blob I/O 对 balance 前置保存的反压。
