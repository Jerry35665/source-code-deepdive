# 第 07 章 · 查询编译与优化器:束宽 12 的"够好"规划器

> 基线:SQLite 3.54.0,commit `492e7fc`。行号均以该版本源码为准。
> 一句话定位:**SQLite 优化器内嵌于代码生成、无计划缓存**——`sqlite3WhereBegin()` 直接生成嵌套循环字节码(3 张表就是三层 foreach,where.c:6764-6774),没有独立的"计划树"中间层。这是它与 MySQL/PG 最本质的架构差异。

## 7.0 基础数据结构:LogEst 与三类对象

- **WhereLoop**(whereInt.h:129-173):"对某张表的一种实现算法",核心字段 `prereq`(依赖表位图)、`rSetup/rRun/nOut`——三者都是 **LogEst**(以 10 为底的整数对数,33≈10 倍、100=10^10),用整数对数避免浮点运算以保证跨平台确定性;
- **WherePath**(whereInt.h:213-221):一个部分 join 计划(maskLoop、rCost、nRow、isOrdered);
- **WhereTerm/WhereClause**:WHERE 被 AND 切分后的项,eOperator 用 WO_* 位掩码一次匹配多操作符。

join 表数上限 64 来自 Bitmask 位宽(whereInt.h:270-272;运行时报错 where.c:6888-6891)。

## 7.1 第〇阶段:单表捷径 whereShortCut

单表查询且无 INDEXED BY 时,若存在无前置依赖的 `rowid=?`(rRun=33,即 10)或唯一索引全列等值(rRun=39,即 15),**直接定型,跳过整个枚举**(where.c:6362-6452)。注释"TUNING: Cost of a rowid lookup is 10"是代价常数风格的代表——`SELECT * FROM t WHERE rowid=5` 不需要 ANALYZE 也能秒出计划。

## 7.2 第一阶段:WhereLoop 枚举

`whereLoopAddAll()`(where.c:4941)从左到右逐表枚举。CROSS/OUTER/RIGHT JOIN 右侧通过 `mPrereq |= mPrior` 禁止重排到前面。**防病态 SQL 的硬限流**:规划搜索总量上限 `iPlanLimit = 20000 + 1000×表序`(whereInt.h:442-460),耗尽时打日志 "abbreviated query algorithm search" 并降级继续——最坏规划时间被钉死。

`whereLoopAddBtree`(where.c:4007)生成三类基本算法,代价公式全部是显式 TUNING 魔数:

**FULLSCAN**(全表扫):

```c
/* TUNING: Cost of full table scan is 3.0*N.  The 3.0 factor is an
** extra cost designed to discourage the use of full table scans,
** since index lookups have better worst-case performance if our
** stat guesses are wrong.  Reduce the 3.0 penalty slightly
** (to 2.75) if we have valid STAT4 information for the table. */
pNew->rRun = rSize + 16;      /* 有 STAT4 时 -2,即 2.75×N */
```
(where.c:4156-4175)

**INDEX SCAN**:`rRun = rSize + 1 + (15*szIdxRow)/szTabRow`(N × K,K 在 1.1~3.0 随索引行/表行大小比例浮动);非覆盖时叠加回表代价 `nLookup = rSize + 16`(3×N)。

**逐列约束扩展**(whereLoopAddBtreeIndex,where.c:3223),关键估计公式:

- `x IN (SELECT...)` 固定假设 **25 行**(nIn=46 LogEst,where.c:3338-3341,assert 注明 46==sqlite3LogEst(25));
- **IN 用索引还是顺序扫**的判据:`M*log(K) < K*log(N)`(M=前缀匹配行数,K=列表长度,N=表行数)时放弃索引,加 10(LogEst,2 倍)安全裕度**偏向索引**(where.c:3368-3411);
- 等值行数估计直接用 stat1 直方:`nOut += aiRowLogEst[nEq] - aiRowLogEst[nEq-1]`(3537);
- **Skip-scan**:最左列无约束但 stat1 显示其重复度足够时,跳过最左列生成计划,并加 1.375 惩罚系数(3616-3652)。

**范围估计**(whereRangeScanEst,where.c:2087):无 STAT4 时每个边界默认 1/4 行、双边界(BETWEEN)1/64 行,下限 2 行(2225-2240)。

**auto-index**(4067-4120):一次性建索引代价 `rSetup = rLogSize + rSize + 28`(X·N·logN,X=7);回报检验在路径层——**外层循环预计运行不足 1.25 次不用自动索引、首 28 行内建索引成本收不回来也不用**(5929-5932)。

**OR 多路**(whereLoopAddOr,4814):每个 OR 分支各建子 WhereLoop 集合(保优 3 组合),笛卡尔合并后加 ≈1.07× 惩罚,避免"全表扫 OR 索引查找"的畸形组合。

WhereLoop 之间靠**支配剪枝**控制数量:"约束项更少且全部被包含"者支配(`whereLoopCheaperProperSubset`,2652-2682),超集代价必高于子集。

## 7.3 第二阶段:WherePath 束搜索

`wherePathSolver()`(where.c:5846)是保优束搜索而非完整 DP:

- **每层保留路径数 mxChoice**:1 表取 1;2 表取 5;≥3 表取 12;星型查询(≥5 表、事实表连 ≥3 个内连接维表)取 18,且**维表的全表扫代价被人为抬高以保住"事实表在外层"的计划**(5607-5638)。computeMxChoice 的注释完整记录了 2024-05 引入、随后三起性能回归、后改为"只抬高维表 SCAN 代价"的演化——启发式优化器安全演进的一手材料;
- 状态转移在 LogEst 对数域累加(LogEstAdd≈概率乘法):`rUnsort = rRun + nRow + rSetup`,排序代价 `whereSortingCost() = K·N·log(N)` 按 ORDER BY 列数缩放,已满足 k 项时总代价 = LogEstAdd(rUnsort, sortCost) + 3(轻微偏向免排序计划,5970-6006);
- 同一 maskLoop+isOrdered 等价类只保留 mxChoice 个最优(6028-6062)。

完整求解次序(`sqlite3WhereBegin`,where.c:6838):whereShortCut → whereLoopAddAll → wherePathSolver;带 ORDER BY 时再做一次带行数估计的二次求解(7115-7121)。DISTINCT 子查询统一再减 30(LogEst,即 ÷8,7123-7131)。

## 7.2b select.c:查询编译主流程

`sqlite3Select()` 开头有自带编号大纲(select.c:7638-7670,tag 0100..1000):SelectPrep(展开 `*`、CTE 绑定)→ 名字解析 → **FROM 逐项优化**(外连接强度削减/去无用 ORDER BY/子查询扁平化)→ 复合 SELECT → WHERE 常量传播 → 子查询落地 → DISTINCT+ORDER BY→GROUP BY 改写 → 聚合/非聚合两条代码生成路径。

**子查询扁平化 flattenSubquery**(select.c:4355)的动机:避免"子查询先物化成无索引临时表、外层再扫两遍"。**28 条编号约束**全部落在注释与判定处,最常"失效"的条件按频率排:DISTINCT 子查询(4407)、两层都有 ORDER BY(4411)、窗口函数(4391)、**聚合子查询(7883-7890,直接放弃——若外层非 join,子查询会走协程,物化开销本就不存在,扁平化无收益)**、MATERIALIZED CTE(优化屏障)。每条约束都引用 ticket 号——这是二十年间被 bug 驱动逐步收紧的护栏,不是一次设计出来的。

**FROM 子查询落地**(tag-0400)按优先级四种方式:协程(数据不落盘)→ CTE 复用(同 CTE 多次引用共享一次物化)→ 同 FROM 重复视图复用 → 物化(非相关子查询外包 OP_Once)。物化前的谓词下推要求子查询非递归、无 LIMIT、谓词是单表约束。

**复合 SELECT**:UNION ALL 且无 ORDER BY 时顺序执行两段(用 LIMIT 计数器提前跳过右段);有 ORDER BY 或 EXCEPT/INTERSECT/UNION 一律走**归并算法**,必要时凭空造一个 ORDER BY 1(select.c:3052-3104)。**递归 CTE** = 经典 Queue/Current 双表循环:setup 结果进 Queue,循环体每次取一行进 Current、执行递归部分回灌 Queue,UNION 去重用独立 ephemeral 表(select.c:2707-2869)。

**聚合**:HAVING 先经 havingToWhere 搬到 WHERE;GROUP BY 若优化器已用索引交付分组序则取消排序;无 GROUP BY 的 `count(*)` 有专门特化——一条 OP_Count 直接读最小索引;min/max 单函数查询退化成带 ORDER BY 的扫描以走索引提前终止。有 GROUP BY 时行数估计被压到 100 行(LogEst 66)——这个常数直接喂给 join 顺序选择。

## 7.4 analyze.c:stat1 如何喂给优化器

`ANALYZE` 为每张表生成一段 VDBE 程序,用 stat_init/stat_push/stat_get 三个内置聚合函数扫描每个索引,写进 `sqlite_stat1(tbl, idx, stat)`。stat 列格式:K+1 个整数——第 1 个是索引行数,第 i+1 个是前 i 列等值时的平均重复数;可后缀 `unordered`/`noskipscan`/`sz=` 关键字(analyze.c:41-65、1559-1578)。加载时填进 `Index.aiRowLogEst[]` 与 `Table.nRowLogEst`。**没有 stat1 时全部用默认猜测(N=1048576,CTE 临时表 100 行)**。STAT4(可选编译)提供每索引 10-40 个样本的直方。一个反向联动:非唯一索引被用于计划时,表被打上 TF_MaybeReanalyze 提示统计过期(where.c:4297-4305)。

## 7.5 设计动机与三处哲学

自我定位:**一个运行在 prepare 时刻、单机嵌入式的"够好"规划器**——不做计划缓存、不做运行时重优化,用束搜索 + 硬限流把最坏规划时间钉死,用 LogEst 整数对数保证跨平台确定性,用 TUNING 魔数(3.0× 全表扫、25 行子查询、18 次 skip-scan、1.25 次 auto-index 回报线)编码工程经验而非测量模型。与 MySQL 8(显式 cost model + histogram + 计划缓存)相比,SQLite 更像"每次 prepare 现算的精简 System R";与 PostgreSQL(GEQO + 完整 DP + 细粒度代价参数)相比,选择了"束宽 12/18 的近似 DP + 64 表硬上限"的保守路线,换几 KB 内存与微秒级规划时间。

三处哲学:

1. **优先改写树,而不是到处特判代码生成**:扁平化、谓词下推、DISTINCT→GROUP BY、HAVING→WHERE、常量传播全部发生在 AST 层,where.c 只面对已化简的查询;
2. **语义正确性约束写进注释与断言而非实现**:flattenSubquery 的约束每条引用 ticket 号;
3. **代价模型"宁可信其有"**:没有统计的输入一律保守默认,因为嵌入式场景下"错误地放弃索引"通常比"错误地使用索引"代价大得多(where.c:3383-3389 的安全裕度注释)。

## 7.6 FAQ

**Q1:`x IN (SELECT ...)` 子查询行数为什么假设 25?**
写死的 TUNING(nIn=46 LogEst);没有 stat4 时不去估子查询基数,统一保守值。

**Q2:为什么有时 IN (值列表) 反而不用索引?**
`M*log(K) < K*log(N)` 成立时顺序扫更便宜;安全裕度偏向索引,故临界情形仍会用索引。

**Q3:子查询扁平化最常失效的条件?**
DISTINCT、两层 ORDER BY、窗口函数、聚合子查询(整体放弃)、MATERIALIZED CTE。

**Q4:UNION ALL 和 UNION 的实现差异?**
UNION ALL 无 ORDER BY 顺序执行两段;其余一律归并,必要时伪造 ORDER BY 1。

**Q5:递归 CTE 怎么执行?**
Queue/Current 双表循环,UNION 去重用独立 ephemeral 表。

**Q6:join 为什么最多 64 张表?**
依赖/覆盖信息编码在 Bitmask 位图,位宽即上限。

**Q7:count(*) 为什么快?**
isSimpleCount 特化成一条 OP_Count 直接读最小索引(select.c:8852-8912)。

**Q8:GROUP BY 什么时候不需要排序?**
`sqlite3WhereIsOrdered()==nExpr` 即优化器用索引交付了分组序,直接取消排序算子(select.c:8627-8633)。

## 7.7 小结与深挖方向

本章结论:**优化器 = WhereLoop 枚举(支配剪枝)+ WherePath 束搜索(宽度 12/18)+ 显式 TUNING 代价公式 + 硬限流**;一切为"prepare 时刻毫秒级现算"服务。深挖方向:

1. 外连接强度削减与扁平化的交互(EP_OuterON 标记迁移);
2. 窗口函数重写与扁平化的边界(重写产物能否被二次吸收);
3. CteUse 生命周期与 CTE 复用计数的状态图;
4. 星型查询启发式的回归史(where.c:5645-5661 注释);
5. IN/SeekScan/Skip-scan 三者"有序前缀离散跳变"的统一代价模型。
