# 第 04 章 · 日志存储与副本管理:顺序写的极致

> 基线:Kafka 4.5.0-SNAPSHOT,commit `f6149f1c`。行号均以该版本源码为准。
> 说明:本章由主会话亲读 UnifiedLog/LogSegment/ReplicaManager/Partition 核心段落后撰写(agent 通道受限期间),行号均经核对。

## 4.0 存储哲学:日志即一切

Kafka 的全部存储是一组**只追加、按 offset 排序、永不修改(除清理)的段文件**。没有 B-tree、没有页缓存一致性协议——读靠稀疏索引定位后顺序扫,写靠追加。与 LevelDB 卷对照:LSM 把随机写变成追加 + 后台 compaction,Kafka 干脆只支持追加写,compaction 退化为可选的日志清理。

## 4.1 物理结构:段 + 双稀疏索引

```
topic-partition/
├── 00000000000000000000.log          ← FileRecords(消息批次,顺序追加)
├── 00000000000000000000.index        ← OffsetIndex(mmap,offset→物理位置,稀疏)
├── 00000000000000000000.timeindex    ← TimeIndex(mmap,timestamp→offset,稀疏)
├── 00000000000000000512.log ...      ← 按 log.segment.bytes 滚动
└── leader-epoch-checkpoint           ← LeaderEpochFileCache 持久化
```

**稀疏索引的写入规则**(LogSegment.append,251-281):每追加一个批次,累计 `bytesSinceLastIndexEntry`,**超过 index.interval.bytes(默认 4096)才写一条索引**——offset 索引记 `(batchLastOffset, physicalPosition)`,time 索引记 `(maxTimestampSoFar, offset)`,然后清零累计。代价:查找需在索引定位后再顺序扫描最多 4KB;收益:索引恒定在内存(mmap)且极小。

```java
if (bytesSinceLastIndexEntry > indexIntervalBytes) {
    offsetIndex().append(batchLastOffset, physicalPosition);
    timeIndex().maybeAppend(maxTimestampSoFar(), shallowOffsetOfMaxTimestampSoFar());
    bytesSinceLastIndexEntry = 0;
}
```

**recover**(483 起):崩溃恢复时重置索引、逐批次校验重建(`validBytes - lastIndexEntry > indexIntervalBytes` 同规则),并从批次头恢复 partitionLeaderEpoch 进 epoch 缓存——**文件格式与元数据的自愈一体化**。

## 4.2 追加路径(UnifiedLog.append,1150-1292)

完整序列:校验 → epoch 缓存更新(`assignEpochStartOffset(batch.partitionLeaderEpoch, baseOffset)`,magic v2 才有;**降级场景直接清空 epoch 缓存**以保安全,1217-1223)→ `maybeRoll`(段满滚动)→ **重复批次检测**(analyzeAndValidateProducerState,幂等去重返回原 AppendInfo)→ `localLog.append` → **`updateHighWatermarkWithLogEndOffset()`**(单副本分区 HW 即时推进)→ producer 状态更新 → 事务索引写入并计算 **LSO(last stable offset)** → 超过 `flushInterval` 才 flush(主动 flush 已退化为可选)。

两个安全细节:① **先 append 后写事务索引**,注释明说"事务索引写失败时,未来 append 的 offset 仍单调增长,不一致由目录恢复清理"(1256-1262);② duplicate 命中时**复用原批的 first/last offset** 构造返回——幂等语义在存储层闭合。

## 4.3 读取路径(LogSegment.read,436-464)

```java
LogOffsetPosition startOffsetAndSize = translateOffset(startOffset);  /* 稀疏索引二分 */
int fetchSize = Math.min((int) (maxPositionOpt.get() - startPosition), adjustedMaxSize);
return new FetchDataInfo(offsetMetadata, log.slice(startPosition, fetchSize), ...);
```

`translateOffset` 经 OffsetIndex(mmap)二分定位到 ≤startOffset 的最大索引项,再顺序扫到精确位置;`minOneMessage` 把 maxSize 抬到至少一条完整批次(防超大消息永远读不出来);`maxPosition` 来自 HW 约束(见下)。**UnifiedLog.read 的隔离级别**(1649-1660)三选:`LOG_END`(follower 拉取)/ `HIGH_WATERMARK`(消费者)/ `TXN_COMMITTED`(LSO,read_committed)——**HW 就是消费者的可见性边界**。

## 4.4 HW 与 leader epoch

**HW 语义**:LEO(每副本日志末端)与 HW(已被 ISR 多数持久化的水位)之间是"已写入但未提交"的灰色带。`maybeIncrementLeaderHW`(Partition.scala:1010-1040)取**所有 maximalIsr 成员 LEO 的最小值**,注释强调"hot path,避免不必要的集合生成"——直接遍历 forEach 找 min。`isUnderMinIsr` 时拒绝推进。

**leader epoch 双重角色**:

1. ** fencing**(副本请求校验):`checkCurrentLeaderEpoch`(Partition.scala:369-376)对 follower 带来的旧 epoch 返回 `FENCED_LEADER_EPOCH`——防止旧 leader 的过期副本请求污染新任期;
2. **截断依据**:LeaderEpochFileCache(持久化为 leader-epoch-checkpoint)记录"每个 epoch 从哪个 offset 开始",leader 变更后副本用 `endOffsetForEpoch` 精确截断到与 leader 一致的分叉点——**这取代了旧版按 HW 截断的往返收敛**,是 KIP-101 对数据丢失/不一致问题的根治。

**makeLeader**(Partition.scala:588-678)的守卫:partitionEpoch 小于当前直接跳过("leader 已在更新的 epoch"),`inWriteLock(leaderIsrUpdateLock)` 内完成 assignment/ISR 更新,返回 `leaderHWIncremented`。

## 4.5 副本写入与 Purgatory

`ReplicaManager.appendRecords`(638-678)三步:`appendToLocalLog`(逐分区写本地日志)→ `buildProducePartitionStatus` → `maybeAddDelayedProduce`。**acks=all 的等待语义不在写路径里忙等**,而是构造 DelayedProduce 挂进 Purgatory(server-common 的 DelayedOperation):ISR 任一副本 fetch 到位时触发 tryComplete,超时或满足即回调——**写路径与复制进度完全解耦**,这正是"顺序写吞吐"与"acks 语义"兼得的结构基础。

## 4.6 日志清理概览

LogCleaner 已 Java 化迁移到 storage 模块(storage/src/main/java/org/apache/kafka/storage/internals/log/LogCleaner.java)。两种保留策略:按时间/大小删除(deletion,段级整删);compact(键级合并,保留每 key 最新版本,供 __consumer_offsets 等 compacted 主题使用)。清理器复制活跃段做归并,与 LevelDB 的 compaction 思想同源但粒度不同——**Kafka 以段为单位、LevelDB 以 key 重叠度驱动**。

## 4.7 FAQ

**Q1:顺序写为什么快?**
追加写把磁盘当 tape:无需寻道、无需页内一致性协议,OS 页缓存顺序预读全部生效;索引稀疏化让 mmap 常驻,读路径"索引二分 + 顺序扫"也全程顺序。

**Q2:HW 与 LSO 的区别?**
HW 是 ISR 复制水位(消费可见性上限);LSO 是事务水位(read_committed 的上限),取 HW 与未决事务首条 offset 的较小者。

**Q3:leader epoch 解决什么问题?**
旧版按 HW 截断:leader 切换后 HW 本身可能回退,需要多轮往返收敛,极端时序下丢数据;epoch 缓存让副本可以精确算出"我的日志与 leader 分叉在哪",一次截断到位。

**Q4:重复批次怎么去重?**
producer state(每 (pid,epoch) 的 sequence 快照,持久化为 snapshot 文件)在 append 前检测,命中直接返回原批 offset——幂等语义由存储层保证,与客户端(第 02 章)闭环。

**Q5:索引为什么不每条都写?**
默认 4KB 一条:索引常驻内存的大小可控;顺序扫描 4KB 在现代存储上近似免费。

**Q6:flush 为什么被废弃为可选?**
acks=all 的持久性由副本保证(单机 fsync 只防本机掉电);依赖 flush 反而制造吞吐悬崖——"用副本换 fsync"是 Kafka 与传统数据库最根本的分歧。

## 4.8 小结与深挖方向

本章结论:**Kafka 存储 = "追加日志 + 稀疏 mmap 索引 + HW 可见性 + epoch 截断"四件套**;一致性不靠页结构靠水位,不靠 fsync 靠副本。深挖:

1. index.interval.bytes 的查找放大实测(大 batch 场景);
2. producer snapshot 的恢复窗口与 UNKNOWN_PRODUCER_ID 的交互;
3. remote storage(tiered storage)加入后 read 路径的三态分支;
4. LogCleaner 段级归并在高更新率 compacted 主题上的写放大;
5. partitionEpoch 与 leaderEpoch 两套纪元的职责边界。
