# 第 02 章 · 生产者:两级流水线与幂等三件套

> 基线:Kafka 4.5.0-SNAPSHOT,commit `f6149f1c`(2026-09-05)。行号以 `clients/src/main/java/org/apache/kafka/` 为根。

## 2.0 线程模型:用户线程 + 单一 IO 线程

- **用户线程**(可多个):`send()` 完成拦截 → 序列化 → 分区 → 追加进累加器,立即返回 Future;
- **Sender IO 线程**:ready 检查 → drain 批次 → 组装 ProduceRequest → client.poll() 收响应 → 回调。

| 组件 | 归属线程 | 职责 |
|---|---|---|
| ProducerInterceptors / Serializer / Partitioner | 用户线程 | 拦截、序列化、定分区 |
| RecordAccumulator | 双方共享 | 按 partition 分桶缓冲 ProducerBatch,锁粒度=分区 Deque |
| BufferPool | 双方共享 | 有限内存池,满了让用户线程阻塞 |
| TransactionManager | 双方共享 | PID/epoch/sequence、事务状态机 |
| Sender + NetworkClient | IO 线程 | 网络收发、InFlightBatches、ack/重试 |

一个新变化:**4.5 的 Sender 被包装为 `SenderThread`**,让 TransactionManager 能用 `Thread.currentThread() instanceof Sender.SenderThread` 判断非法状态迁移发生在哪条线程——用户线程上的只抛异常,IO 线程上的**自毒化为 FATAL_ERROR**(TransactionManager.java:313-315,引 KAFKA-14831)。线程身份成为正确性的一部分。

## 2.1 一条 send 的完整旅程

```
用户线程                                     Sender IO 线程
send → interceptors.onSend → doSend          runOnce
  → waitOnMetadata(≤ max.block.ms)            → maybeResolveSequences / bumpId
  → serialize(用户线程同步做)                  → accumulator.ready()
  → partition(指定 > 自定义 > murmur2(key))    → drain(幂等批出队即赋号)
  → accumulator.append(双检锁+重试)             → sendProduceRequests
  → wakeup(sender)                             → client.poll → handleProduceResponse
  → FutureRecordMetadata                       → completeBatch(回调在 IO 线程)
```

关键细节:

- **waitOnMetadata 的循环条件**:即使拿到 topic 元数据,若**指定分区号超出已知分区数**仍继续刷新——覆盖"扩分区后旧缓存不含新分区";这就是"第一条消息可能阻塞"的根源,`partitionsFor()` 预热可消除;
- **双检锁 append**:锁内只尝试写队尾批(tryAppend);写不进先释放锁再去 BufferPool 申请内存——避免持锁阻塞;拿锁后再验 sticky 分区是否被并发改写;
- **批终态机允许一次"翻案"**:失败→成功是唯一合法迁移(对应"本地已判失败但 broker 实际写入成功"),成功之后任何迁移抛异常(ProducerBatch.java:296-316);
- **Future 的链式语义**:批被 MESSAGE_TOO_LARGE 拒绝而拆分时,原 Thunk 的 future 被 chain 到新批——`flush()` 对拆分后的子批仍然有效;
- **回调在 IO 线程执行**:文档明确要求快速,否则拖慢所有分区投递。

## 2.2 RecordAccumulator 与 BufferPool

分桶:每 topic 一个 `TopicInfo{batches, BuiltInPartitioner}`,锁粒度是**单个分区的 Deque**,外层 CopyOnWriteMap 读不加锁。

**sticky batching(KIP-794)**:无 key 消息旧 round-robin 会把每分区批都打成半满(请求放大 N 倍);sticky 让流量集中一个分区直到累计 ≥ batch.size 且**队列全部为满**才切换——消除 4KB"尾巴批"。切换用 Sender 侧统计的积压构建累计频率表加权随机,还支持机架感知与可用性剔除。

**BufferPool 只回收整块**(poolableSize=batch.size):分配/回收 O(1)、零碎片;非整块(压缩膨胀)折算成可用字节。`waiters` 是 **FIFO 的 Condition 队列,只唤醒队首**——防止大请求被后来小请求饿死(注释点名防死锁)。新特性 **incremental(chunked)策略**:每批由 16KB chunk 按需挂载,内存随实际写入量而非 `分区数 × batch.size` 增长(实验性,暂不支持压缩)。

**Sender 主循环的事务纪律**:runOnce 第一步永远先照料事务(maybeResolveSequences → fatal 处理 → 幂等补号 → 事务请求独占轮次);pollTimeout 取"最近 linger 到期/批过期/节点可连接"的最小,避免空转。

## 2.3 幂等与事务:pid + epoch + sequence 三件套

每个分区维护 `TxnPartitionEntry{nextSequence, lastAckedSequence, inflightBatchesBySequence}`。drain 时赋 baseSequence 并递增;broker 按 (pid, epoch, sequence) 连续性去重。客户端的精细处置:

- **OutOfOrderSequence**:只有"不是 lastAcked+1 或存在未决序列"时才重试(等前面的批落地);真空洞则幂等生产者 bump epoch 重试、事务生产者转 abortable;
- **未决序列(unresolved)**:批本地超期但可能已到达 broker,(sequence, epoch) 最终状态未知 → 冻结该分区新批 drain,所有在途请求落定后 maybeResolveSequences 收口;
- **UNKNOWN_PRODUCER_ID**:用响应里的 logStartOffset 区分"日志头部被 retention 删除"(从 0 重发)与"数据真的丢了";
- **epoch bump 是客户端本地的**,bump 后 `startSequencesAtBeginning` 会**重写所有在途批的 header sequence**。

**事务状态机**:UNINITIALIZED → INITIALIZING → READY → IN_TRANSACTION → COMMITTING/ABORTING → READY;FATAL_ERROR 不可恢复。事务请求走独立优先级队列 + **单在途请求** + correlationId 校验——用吞吐换可推理的正确性。`commitTransaction` 语义上的 flush 是实现出来的:EndTxn 在 accumulator 完全 drained 前不会出队。

**事务 V2(TV2,KIP-890)**:EndTxn v5+ 响应回传新 pid/epoch、每事务自动 bump epoch,消除客户端与服务端的 bump 协调;未启用时 ProduceRequest 钉在 ≤v11。**两阶段提交(KIP-939)**:`prepareTransaction` 返回 `(pid, epoch)` 令牌——**把"是否提交"的决定权从生产进程剥离**,崩溃后重入的进程能拿到同一份 preparedTxnState 与外部协调器比对;prepare 状态只存在于客户端视角,broker 看到的仍是普通 IN_TRANSACTION。

四道闸门合起来保证事务原子性:**任何未登记进事务的字节,永远不可能越过 accumulator 到达网络**(未入事务不发、无效 pid/epoch 不发、旧 epoch 在途不发、未决序列不发)。

## 2.4 FAQ

**Q1:send() 什么时候会阻塞?**
两类:首次拉元数据(≤max.block.ms)、BufferPool 内存不足排队;序列化/分区是纯 CPU。

**Q2:linger.ms=0 还会批量化吗?**
会:满批立即 ready,高并发下批天然聚起来;linger 只影响半满批。

**Q3:callback 在哪条线程执行?**
IO 线程;必须快速或自建线程池。

**Q4:acks=0 时错误能感知吗?**
不能:客户端不注册响应处理器,RecordMetadata.offset 为 -1。

**Q5:commitTransaction 的 max.block.ms 超时代表失败吗?**
不代表:请求可能已到达,只能重试同一操作,不能改 abort。

**Q6:max.in.flight>1 为什么不破坏顺序?**
幂等后 broker 按 sequence 重排;客户端只在重试发生时退化排队 + 重入队按 sequence 有序插入。

## 2.5 小结与深挖方向

本章结论:**生产者 = 双线程流水线(用户线程算、IO 线程传)+ 分区锁粒度聚合 + "sequence/epoch 客户端三件套"承担幂等正确性**;TV2 与 chunked accumulator 都是把复杂度"下沉/按需化"的统一思路。深挖:

1. chunked 扩展与压缩的交互(KAFKA-20579 落地后上界估算还准吗);
2. unresolved-sequence 对 LSO 的放大窗口;
3. sticky 加权表跨线程陈旧窗口在大分区数下的倾斜;
4. TV2 升级窗口的序列重置保证;
5. KAFKA-19012 的缓冲生命周期(挂起连接时内存滞留多久)。
