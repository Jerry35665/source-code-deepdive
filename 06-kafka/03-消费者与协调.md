# 第 03 章 · 消费者与协调:三代协议的演进

> 基线:Kafka 4.5.0-SNAPSHOT,commit `f6149f1c`。行号以仓库根目录为基准。
> 版本事实:KIP-848 在本版本**尚未成为客户端默认**(`group.protocol=classic`,ConsumerConfig.java:121),但服务端三种协议已默认全开——"服务端先行、客户端渐进"的推进节奏。

## 3.0 三代消费协议

| 维度 | eager (classic) | cooperative-sticky | KIP-848 consumer |
|---|---|---|---|
| 分配位置 | Leader 客户端 | Leader 客户端 | **服务端 assignor** |
| 交还范围 | 全量 revoke | 仅属主转移分区 | 仅 revoked 差集,逐成员增量 |
| 协议 RPC | Join/Sync/Heartbeat ×3 | 同左(两轮) | Heartbeat 单 RPC |
| Fenced | 基本致命 | 基本致命 | **自动 rejoin** |
| 心跳间隔 | 客户端配置 | 客户端配置 | 服务端下发 |

另有 ShareGroup(KIP-932):互斥单元是**记录**(ack 状态)而非分区,见 3.5。

## 3.1 AsyncKafkaConsumer 的双线程事件模型

```
应用线程                                    网络线程 consumer_background_thread
poll/commitSync/seek ──ApplicationEvent──▶ runOnce:
                                              1. processApplicationEvents
◀──BackgroundEvent──(错误/回调弹回)─           2. 各 RequestManager.poll
FetchBuffer ◀════共享(线程安全)════▶           3. NetworkClientDelegate.poll(NIO)
                                              4. reap 超时事件
```

- **ApplicationEvent 队列**:所有"要做事"封装为 CompletableApplicationEvent,方法内 `addAndGet` 阻塞在事件 future 上;
- **BackgroundEvent 队列**:网络线程只回传两类——错误(应用线程直接 throw)与必须在应用线程执行的回调(rebalance listener);
- **"事件 + future + reaper"** 统一了 classic 版层层嵌套的 RequestFuture/定时器组合;
- **回调必须"弹回"应用线程**:ConsumerRebalanceListener 必须与 poll 同线程(用户假设),网络线程只发事件,应用线程在下次 poll 内执行回调再通知后台继续——应用线程长时间不调 poll,rebalance 就卡在等待回调 ack。

## 3.2 poll 的四阶段(网络线程侧真相)

`AsyncPollEvent` 到达后台后按序执行四步:

1. **调和检查**(canCommit=true 的 revoke/提交)→ `markReconciliationCheckComplete()`——应用线程的 collectFetch **显式等待这个标记**,防止把即将被 revoke 的分区里的数据返回给用户;
2. **自动提交 + poll 计时器喂狗**(KIP-848 下 max.poll.interval 的喂狗点);
3. **校验/更新 Position**(应用线程同样要等这个标记——防两线程并发改 position);
4. **创建 Fetch 请求**(按节点分组、经 FetchSessionHandler 增量)。

FetchCollector 的三道防线:分区已不被持有则丢弃(rebalance 发生在取回前);`nextFetchOffset != position.offset` 视为过期响应丢弃;**先更新 position 再标记 buffer 耗尽**(防后台线程看到 isConsumed 但 position 未更新而重复请求)。`Fetch.nextOffsets`("最后一条 +1")就是自动提交的数据来源——**自动提交的语义是 at-least-once 处理进度,而非已处理完成**。

inflight poll 事件管理有一处精妙:上一轮 poll 事件已完成**且**填满 fetch buffer 时不提交新事件——注释给出反例:若每次 poll(0) 都强制发新事件,新事件的"校验 position"会先于 buffer 数据被消费,导致 buffer 数据被无限期搁置。

## 3.3 Rebalance:三种协议逐段

**Classic eager**:客户端 AbstractCoordinator 负责 RPC 时序与心跳,ConsumerCoordinator 负责"入组之后"(onJoinComplete 先 revoke 旧全部再 assign 新增)。服务端状态机:`EMPTY → PREPARING_REBALANCE → COMPLETING_REBALANCE → STABLE`。**这套逻辑全部运行在应用线程**——任何 rebalance 都要求用户及时 poll 才能推进,这正是 KIP-848 双线程改造的直接动因。

**Cooperative sticky**:关键在 adjustAssignment——"属主转移集合"(A 交出、B 接收)先从 B 的新 assignment 里剔除,本轮 A 只 revoke 这些分区,**下一轮** B 才拿到——用两轮 rebalance 换未被移动的分区全程不中断。

**KIP-848**:三个 RPC 合并为单个 ConsumerGroupHeartbeat,分配在服务端。服务端心跳处理四步:create group/member(memberEpoch==0 才创建)→ 订阅变化 bump **group epoch** → group epoch > target epoch 时重算目标分配 → 对未收敛成员 maybeReconcile。客户端增量调和:计算 added/revoked 差集 → revoke 分区暂停 fetch → 自动提交 → onPartitionsRevoked → onPartitionsAssigned → ack 新 assignment。**部分调和也可 ack**(assignment localEpoch 保证幂等)——rebalance 从组级 STW 变为成员级增量收敛的关键。fenced 自动恢复:清空 assignment 即 rejoin,无需重启。

**静态成员 group.instance.id**(KIP-345):Classic 下若组 STABLE 且协议不变,**重启不触发 rebalance**直接沿用原 assignment;代价是 session timeout 内的"僵尸实例"问题。

## 3.4 提交与位移语义

三类提交共用一条路径(commitSync/Async 都构造 CommitEvent 交后台)。**未显式给 offsets 时,offsetsReady future 保证后台线程在取 allConsumed 快照前不会有新的消费推进**——从根上消除 classic 版"提交位置竞态"。自动提交三处触发:周期异步、**rebalance 前同步**(重试至成功/致命/超时,可延迟 rebalance)、KIP-848 调和起点。

服务端把位移当 record 写 `__consumer_offsets`(tombstone 删除/过期),经 CoordinatorRuntime 按 shard 单线程写日志再回放内存态——**状态即日志前缀,天然获得与 KRaft 一致的"日志即真相"模型**(4.x 重写时对旧 Purgatory 模型的替换)。

## 3.5 ShareGroup(KIP-932)概览

"共享消费":组内成员可**同时消费同一分区**,互斥单元是记录(ack)而非分区——没有 position/重置/rebalance 分区转移。ack 三选一映射记录状态:ACCEPT→ACKNOWLEDGED、RELEASE→AVAILABLE、REJECT→ARCHIVED;超过 max.delivery.count 转入 ARCHIVED("毒丸消息"自动进死信态)。典型场景:多实例分摊同一队列但不想经历 rebalance 抖动,或消息按条 ack(近似队列语义)而保持 Kafka 存储模型不变。

## 3.6 FAQ

**Q1:本版本 KIP-848 是默认吗?**
不是:group.protocol 默认 classic;服务端三协议默认全开,客户端渐进。

**Q2:poll 返回的记录会重复返回吗?**
正常不会:过期响应(offset 不匹配)直接丢弃,position 在返回前已推进。

**Q3:commitSync 不指定 offsets 会提交错吗?**
不会:offsetsReady future 保证先取快照且阻塞应用线程至取走。

**Q4:max.poll.interval 超时后发生什么?**
KIP-848:网络线程检测到即发 LeaveGroup 心跳自杀,再次 poll 尝试 rejoin。

**Q5:cooperative 为什么常常要两轮?**
属主转移分区必须先由旧属主 revoke、服务端确认后才能给新属主;两轮换其余分区不中断。

**Q6:FetchSession 有什么用?**
KIP-227 增量拉取:请求/响应体积从 O(分区数) 降到 O(变化量);session 冲突/非法响应/网络错误都回退全量重建。

## 3.7 小结与深挖方向

本章结论:**消费侧的演进主线 = 把"必须用户 poll 驱动"的协调,改造成"后台线程 + 增量调和"**;每一步都有代价(双线程握手、服务端负担),但都指向同一个目标——rebalance 不再是 STW。深挖:

1. canCommit=false 的调和被跳过后的 ack 缺失窗口(是否连锁 STALE rejoin);
2. __consumer_offsets 双写者问题(classic 与 consumer 组共写,shard 有序性);
3. FetchBuffer 与 inflight poll 的边界竞态(丢唤醒);
4. 服务端 assignor 的 rack 感知与粘性实现程度;
5. SharePartition 内存状态与 share-coordinator 的崩溃恢复协议。
