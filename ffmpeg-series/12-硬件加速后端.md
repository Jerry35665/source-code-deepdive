# 第 12 章 · 硬件加速三大后端:VAAPI、NVDEC、VideoToolbox

> 基线:commit `9f63b36a`。行号以 libavutil/hwcontext_*.c、libavcodec/ 为准。首卷 05 章已讲 hwcontext 通用抽象(AVHWDeviceContext/AVHWFramesContext),本章只讲**三个后端如何实现同一套接口**。两处文件名勘误:本树中 NVDEC 逻辑全在 libavcodec/nvdec.c(无 hwcontext_nvdec.c 的解码职责);VideoToolbox 解码器是 libavcodec/videotoolbox.c。

## 12.0 全景:同一接口,三种原生对象

hwcontext 通用层定义了"设备"与"帧池"两个抽象,三个后端的全部差异收敛为一个问题:**一帧硬解画面在本平台的原生对象是什么**:

| | VAAPI | NVDEC | VideoToolbox |
|---|---|---|---|
| 原生帧对象 | `VASurfaceID`(挂 data[3]) | `CUdeviceptr`/`CUarray` | `CVPixelBuffer`(挂 data[3]) |
| 设备建立 | DRI 节点 + libva | CUDA context | 系统默认 |
| 解码入口 | hwaccel(vaapi_decode.c) | hwaccel(nvdec.c) | hwaccel(videotoolbox.c) |
| 输出模型 | 同步 render | 同步 map | **异步回调** |
| 平台怪癖 | quirk 表治驱动碎片 | surface 数=硬约束 | session 可中途失效 |

三个 hwconfig 都声明 device+frames 双方法(hwconfig.h:68-77)——即都支持"外部提供设备"与"外部提供帧池"两种工作方式,这是与通用层对接的完整姿势。

## 12.1 协商链:一次 get_format 决定一切

硬解不是编译期选择,而是**每个流打开时的运行时协商**。完整链路:

```
解码器解析 SPS(h264_slice.c:935)
   ↓ 得知真实像素格式/位深
ff_get_format(decode.c:1229) 列出候选格式数组
   ↓
avctx->get_format 回调(decode.c:1258)
   ├→ 用户未设:默认实现(decode.c:1006-1067)
   │   设了 hw_device_ctx → 优先匹配 device_type 的硬件格式(:1014-1031)
   ↓
hw_config 校验 + hwaccel_init(decode.c:1305-1344,1182)
   ↓ 失败 → 从候选剔除后重试(:1348-1357)
   ↓ 全军覆没 → 回退软解("软件格式必须垫底"约定 :1242-1248)
```

**这条链是整章的纲**:①像素格式即硬解方式(`AV_PIX_FMT_VAAPI` 出现在 get_format 候选里 = 用户应答"我要硬解");②硬解失败自动降级软解的本体就在剔除重试循环(decode.c:1348-1357);③逐帧流程由解码器宏调 `start_frame/decode_slice/end_frame`(h264dec.c:714,722;h264_picture.c:207),异步后端的产物在统一出口 decode.c:706 的 post_process 钩子挂上帧。

## 12.2 VAAPI:profile 双层匹配与 quirk 逃生舱

**profile 协商是双层的**(vaapi_decode.c:520-545):先查 FFmpeg 自己的映射表 `vaapi_profile_map`(vaapi_decode.c:409-472),再用 `vaQueryConfigProfiles` 问驱动支持集(:508),取交集;`exact_match` 不中且无 `ALLOW_PROFILE_MISMATCH` 旗标即拒(:554-570);通过后 `vaCreateConfig` 用 `VAEntrypointVLD`(位流解码入口,:572-574)。

**surface pool 按 codec 加参考帧余量**(vaapi_decode.c:628-649):H264/HEVC/AV1 加 16、VP9 加 8、VP8 加 3、其他加 2——余量即 DPB 深度,分配不足会在解码中途挂死;整个 `surface_ids` 数组一次性传给 `vaCreateContext`(:715-720)。

VAAPI 最沉重的包袱是**驱动碎片**,解法是数据化的 quirk 表(hwcontext_vaapi.c:392-415):

- 老 Intel i965 → `RENDER_PARAM_BUFFERS`:解码 issue 后立即销毁参数 buffer(vaapi_decode.c:213-222);
- Intel iHD("ubit" 字符串)→ `ATTRIB_MEMTYPE`(DMABUF 导出需要);
- VDPAU wrapper → `SURFACE_ATTRIBUTES`。

按驱动 vendor 字符串匹配(:470-498)。**quirk 表是开源硬件栈历史的化石层**——每一行背后都是一轮 bug 报告。

帧导出路径:pool 项即 `vaCreateSurfaces` 产物,id 塞进 AVBufferRef->data(hwcontext_vaapi.c:531-573,663-665);frames_init 结尾试分配一次探测 `vaDeriveImage` 可用性(:675-718);map 时 derive 直读或 `vaGetImage` 拷贝(:824-969,注释明言 Gen7-9 架构读路径慢,:874-880)。

## 12.3 NVDEC:surface 数量是硬约束

NVDEC 后端(注意与编码侧 nvenc 无关)在 libavcodec/nvdec.c:

- 打开前 `cuvidGetDecoderCaps` 预检能力(分辨率/profile/chroma,:115-173)——**驱动不支持当场失败**,不进解码循环;
- session 参数 `ulNumDecodeSurfaces = FFMIN(pool, 32)`(nvdec.c:628-629),超限时明确提示"降线程数"(:633-638);`ulNumOutputSurfaces`:opaque 模式 0、unsafe 模式 ≤64、常规模式 1;
- surface 池是 refstruct 管理的**顺序发号索引池**(nvdec.c:279-290,池大小 = DPB+2 :1130-1134);耗尽时报错的正是那句著名的 "No decoder surfaces left"(:967);
- 帧输出:`cuvidMapVideoFrame` 得 `CUdeviceptr`,unmap 时挂 `buf[1]`(:893-911);新版 CUARRAY opaque 模式零拷贝直出 CUarray,用 `surface_in_use` 原子变量簿记(:664-678,759-768)。

## 12.4 VideoToolbox:把异步回调塞进同步框架

Apple 的 `VTDecompressionSession` 是回调式(解码完成随时 call you),而 FFmpeg 解码框架是同步的(start_frame→decode_slice→end_frame 之间拿结果)。videotoolbox.c 的适配:

```c
/* videotoolbox.c(节选) */
/* 异步回调(:717-744):只 Retain 并暂存 */
vtctx->frame = CVPixelBufferRetain(...);
/* end_frame(:766)同步收干 */
WaitForAsynchronousFrames(...);
```

回调里只做 `CVPixelBufferRetain` 存到 `vtctx->frame`(:717-744,:1056-1086),`end_frame` 里 `WaitForAsynchronousFrames` 收干转同步(:766)——**用一帧的等待粒度把异步抹平**。故障恢复:session 报 malfunction 或吐空帧时置 `reconfig_needed`,下一帧整体重建 session(:1062-1077);macOS 11 的补充解码器注册在 :975-979。

## 12.5 三后端对比:同一抽象下的三种性格

| 维度 | VAAPI | NVDEC | VideoToolbox |
|---|---|---|---|
| 失败时机 | profile 协商期 | caps 预检期(:115-173) | 运行中途(malfunction) |
| 池策略 | codec 相关加余量(:628-649) | FFMIN(pool,32) 硬顶(:628-629) | 系统管理 |
| 历史包袱 | quirk 表(:392-415) | surface 数×线程数耦合 | 异步/同步边界 |
| 降级路径 | get_format 剔除重试 | 同左 | 重建 session(:1062-1077) |

## 12.6 设计动机

1. **get_format 而非编译期开关**:同一二进制跑在有无硬件的机器上,协商必须在打开流的那一刻发生——decode.c:1348-1357 的剔除重试让"硬解失败自动软解"成为框架行为而非用户责任;
2. **quirk 表 vs if-else 山**:驱动 bug 治理数据化,新增怪癖 = 加一行表项 + 一个 flag 位,审查面积极小——这是把"平台碎片"当成数据建模;
3. **NVDEC 把约束写进错误消息**:"No decoder surfaces left"(nvdec.c:967)直说池耗尽、:633-638 直接教用户降线程——GPU 资源不可分页换出,溢出必须是显式错误而非静默降质;
4. **VT 的最小等待策略**:每帧只等一帧的异步收干(:766),不在解码器里做流水线,把并行性留给调用方的多线程解码(首卷 08 章)。

## 12.7 FAQ

**Q1:硬解失败会崩吗?**
不会。ff_get_format 剔除失败候选重试,全部失败回退软解(decode.c:1348-1357);前提是 get_format 候选里保留了软件格式(默认实现保证垫底,:1242-1248)。

**Q2:为什么用像素格式来选硬解?**
get_format 协商的实质是"帧内存由谁分配":选 AV_PIX_FMT_VAAPI = 帧将是 VASurface。像素格式是 FFmpeg 里"内存布局+所有权"的联合声明,天然适合承载这个决定。

**Q3:不设 get_format 回调能硬解吗?**
能。设 `hw_device_ctx` 后默认实现自动优先硬件格式(decode.c:1006-1067);不设 device_ctx 则永远软解。

**Q4:VAAPI profile 稍微不匹配会怎样?**
拒。exact_match 不中且无 ALLOW_PROFILE_MISMATCH 即失败(vaapi_decode.c:554-570)——硬解器不支持就是不支持,静默错配产出花屏比失败更糟。

**Q5:surface 池为什么各 codec 余量不同?**
余量=DPB 深度:H264/HEVC/AV1 多参考加 16,VP9 加 8,VP8 加 3(vaapi_decode.c:628-649)。池分配不足不是慢,是死锁。

**Q6:"No decoder surfaces left" 是谁抛的?**
NVDEC surface 索引池耗尽(nvdec.c:967);池=DPB+2(:1130-1134),调整 -threads 或加大池可解(:633-638 提示语)。

**Q7:VideoToolbox session 中途坏了怎么办?**
malfunction/空输出置 reconfig_needed,下一帧销毁重建 session(videotoolbox.c:1062-1077)——按 Apple 语义,session 状态不可信,重建是唯一恢复路径。

**Q8:VT 是异步的,FFmpeg 怎么变同步?**
回调只 Retain 暂存帧(:717-744),end_frame 用 WaitForAsynchronousFrames 收干(:766)。异步窗口被压缩到一帧。

**Q9:nvdec 和 cuvid 是什么关系?**
同一硬件入口的两种封装:cuviddec 是"原生解码器"(hwaccel=NULL,不进 hwaccel 体系,cuviddec.c:1799),nvdec 是标准 hwaccel;两者运行期会争同一 NVDEC 引擎(双 session 之争),cuviddec 自己也调 ff_get_format(:387)。

**Q10:VAAPI 的 i965/iHD quirk 对普通用户意味着什么?**
老驱动(i965)需要参数 buffer 生命周期 hack(vaapi_decode.c:213-222),新驱动(iHD)走 DMABUF 导出(hwcontext_vaapi.c:392-415)——用户无感,但 map/download 性能差异巨大(Gen7-9 读路径慢,:874-880)。

## 12.8 小结与深挖方向

本章结论:**三个后端的全部差异 = "原生帧对象是什么" + "失败发生在哪个阶段"**;协商链(decode.c:1229-1365)是唯一必须精读的共享代码。深挖:

1. vaDeriveImage 直读 vs vaGetImage 拷贝的性能分水岭(:824-969)与零拷贝导出到 DMABUF 的条件;
2. NVDEC CUARRAY opaque 模式的零拷贝路径与 surface_in_use 原子簿记(:664-678,759-768);
3. hwdownload/hwmap 滤镜如何把 12.0 表中的原生对象搬回系统内存;
4. NVDEC 线程数与 surface 数的联合约束(:633-638)在 4K 多路场景的容量规划;
5. macOS 补充解码器注册(:975-979)反映的 VT API 版本碎片与 FFmpeg 的版本适配策略。
