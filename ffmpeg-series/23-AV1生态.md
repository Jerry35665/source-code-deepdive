# 第 23 章 · AV1 生态:三种解码路径与三种编码 wrapper

> 基线:commit `9f63b36a`。行号以 libavcodec/ 为准。08 章解码讲了 H.264/HEVC/VP9,14 章 wrapper 讲了 x264/x265——本章补齐 AV1,并把"同名编解码器多实现如何选"讲透。

## 23.0 全景:一张地图

```
解码(3 路)                          编码(3 路)
├ libdav1d     生产默认,双向零拷贝   ├ libaom-av1   参考编码器,ctl 枚举翻译官
├ libaom-av1   参考实现,整帧拷贝     ├ libsvtav1    管线式 send/receive
└ av1          native,hwaccel-only   └ librav1e     Rust 状态机+显式背压
     │
支撑层:av1_parse(轻量 OBU 切分)/ cbs_av1(完整语法读写)/ av1_parser(22 章)
注册序:libdav1d > libaom-av1 > av1(allcodecs.c:778,849,851)
```

**av1dec 必须有硬解**:`get_pixel_format` 末尾无 hwaccel 即返回 ENOSYS,注释明言 "doesn't support native decode"(av1dec.c:693-698)——它只做 CBS 语法解析+硬解转发,不是软解器。

## 23.1 解码三路对比:零拷贝的两端

| | libdav1d | libaom-av1 | av1(hwaccel-only) |
|---|---|---|---|
| 输入 | `dav1d_data_wrap` 挂 pkt->buf,零拷贝(:309-325) | 拷贝进 aom | CBS 解析 OBU 后转发硬解 |
| 输出 | 自定义 allocator+AVBufferPool(:77-123) | ff_get_buffer+av_image_copy(:229,264) | 硬解表面 |
| 线程 | 库内 n_threads 单参数(:229-232) | 上限 16(:50-51) | 单线程(caps 仅 DR1 :1555) |
| 8/10bit | seq_hdr->hbd 查表(:59-64) | 16→8 拷贝路径(:258) | 硬解决定 |

**libdav1d 是双向零拷贝的范本**:输入侧 `dav1d_data_wrap` 直接挂 packet 的 AVBufferRef,所有权移交,原 packet 作 user_data 回传时间戳(libdav1d.c:318,428);输出侧自定义 picture allocator 用 AVBufferPool 分配(128 对齐+手工对齐到 DAV1D_PICTURE_ALIGNMENT),`frame->buf[0]` 直接引 allocator_data(:392)。对照 14 章:x264 输出必须 memcpy(dav1d 证明了可避免的路径)。**"8/10bit 双 API"是 dav1d 0.x 旧事**,现行 API 只有 `dav1d_get_picture`(:343)。

**av1dec 的价值在语法层**:主循环是 OBU 状态机(:1232-1474)——序列头存原始字节喂 hwaccel 的 decode_params(:1281-1288);frame_header 后做 **CBS 不覆盖的半语法推导**(global motion/skip mode/lossless,av1dec.c:46-408);tile 边界表(:428-471)交 decode_slice(:1370);tg_end 收齐后 end_frame 并滚动参考帧槽(:1421-1435)。

## 23.2 CBS:AV1 的公共语法层

av1_parse 是轻量 OBU 切分器(只服务 av1_parser 与 extract_extradata BSF);cbs_av1 是完整语法读写。extradata 双格式判定:`data[0]&0x80` 即 config record(跳 4 字节),否则裸 OBU(cbs_av1.c:722-753;libdav1d.c:172-187 复刻同逻辑)。对照 14 章:x264 要**手工拼 avcC**,AV1 的 extradata 殊途同归于裸 OBU——aom 借 extract_extradata BSF(libaomenc.c:1079-1099)、svt 用 stream header(libsvtav1.c:523-545)、rav1e 用 container_sequence_header(librav1e.c:405-420)。**新代编解码器把元数据标准化进码流语法,wrapper 的胶水就薄了**。

## 23.3 编码三路对比

- **libaomenc**:选项翻译官。RC 四态推导:min==max==bitrate→CBR、crf→CQ/Q、默认 CRF=32(:834-852);cpu-used 是运行时参数(:1586);
- **libsvtav1**:管线式。rc 映射 max≠avg→VBR(1)/==→CBR(2)/crf→0(:240-267);**wrapper 不传线程数**——SVT 自己是全库内流水线;输出 pool+一次 memcpy(:721-731);
- **librav1e**:Rust 状态机。**显式背压**——返回 ENOUGH_DATA 时 RaFrame 存 ctx->rframe 下次重试(:494-501);参数全走字符串配置(:254-274)。

三个 wrapper 三种上游哲学:枚举控制(aom)/黑盒流水线(svt)/协程式背压(rav1e)。

## 23.4 同名多实现的选择机制

`avcodec_find_decoder("av1")` 按 codec_list 声明序遍历,命中即返回(allcodecs.c:964-983):声明序 libdav1d(:778)> libaom-av1(:849)> av1(:851),顺序由 configure 检测结果生成(configure:4609-4614,8970)。experimental 标记的实现排最后兜底。**选择机制=静态声明序,无运行时打分**——想换实现必须显式 `avcodec_find_decoder_by_name`。与 12 章 get_format 的运行时协商对照:实现选择在编译期,像素格式选择在运行期——两层各自解决"库有没有"与"这个流怎么解"。

## 23.5 设计动机

1. **为什么 AV1 有 CBS 而 H264 没有**:AV1 生于 2015+,把"语法读写"设计成公共库(CBS 最初为 AV1 引入后反哺 H264/HEVC 的 metadata BSF);H264 的手工解析是 2003 年代码的考古层;
2. **为什么 dav1d 成为默认**:零拷贝契约(输入借用/输出池化)是架构级的,而 aom 是参考实现优先正确性——FFmpeg 用声明序让市场选择落地为默认值;
3. **av1dec 的 hwaccel-only 是务实**:AV1 软解成本极高,CBS 语法已由 dav1d 覆盖,FFmpeg 只保留"硬解调度+语法校验"的薄层;
4. **svt 的不传线程**:上游已经是任务流水线,再暴露线程数只会双重调度——wrapper 诚实反映上游并发模型。

## 23.6 FAQ

**Q1:编译了多个 AV1 解码器,用哪个?**
codec_list 声明序第一个可用者:libdav1d>libaom>av1(allcodecs.c:778-851);显式指定用 find_decoder_by_name。

**Q2:libdav1d 的"零拷贝"到底零在哪?**
两端:输入 data_wrap 借用 packet 缓冲(:309-325),输出 allocator 池化直出 frame->buf[0](:77-123,:392)——全程无像素 memcpy。

**Q3:native av1 decoder 为什么没装硬件会失败?**
av1dec 只做 CBS 语法+硬解转发,无软解路径,get_pixel_format 找不到 hwaccel 返回 ENOSYS(av1dec.c:693-698)。

**Q4:AV1 的 extradata 是 avcC 那种盒子吗?**
不是,是裸 OBU 序列(或带 4 字节头的 config record,`data[0]&0x80` 判定,cbs_av1.c:722-753)——元数据标准化让 wrapper 不必手工拼。

**Q5:svt-av1 该设几线程?**
不用设,wrapper 不暴露(:240-267):SVT 是库内流水线,外部线程数无意义。

**Q6:rav1e 推帧返回 ENOUGH_DATA 怎么办?**
等下一帧时重试,未收下的 RaFrame 存在 ctx->rframe(:494-501)——显式背压,与 16 章 tq_send 的阻塞语义相反。

**Q7:aom 的 cpu-used 是什么?**
运行时质量-速度旋钮(:1586),0-8(实时 0-6),映射到内部编码策略集。

**Q8:AV1 的 SVT/libaom/dav1d 都开了,enc 会用哪个?**
编码无同名冲突:aom-av1 与 libsvtav1 与 librav1e 是三个不同 codec 名,显式 -c:v 选择。

**Q9:dav1d 的 10bit 要 special build 吗?**
不要,运行时按 seq_hdr->hbd 分派(:59-64)——对照 x264 的双编译(14 章),新代编解码器都内建多 bit 深度。

**Q10:硬件 AV1 解码怎么启用?**
标准 hwaccel 路径(12 章):get_format 候选里出现 AV_PIX_FMT_VAAPI/NVDEC 等,av1dec 的 OBU 状态机驱动 start/decode_slice/end_frame 三回调(:1342,1370,1428)。

## 23.7 小结与深挖方向

本章结论:**AV1 生态 = "dav1d 零拷贝范式 + CBS 公共语法层 + 三种编码上游哲学"**;同名多实现的选择是静态声明序,简单但有效。深挖:

1. dav1d allocator 的 AVBufferPool 与 12 章 NVDEC surface 池的池化策略对照;
2. cbs_av1 的语法模板(cbs_av1_syntax_template.c)与 H264 手工解析的维护成本差;
3. svt-av1 的 lookahead 与 FFmpeg send/receive 节拍的相互作用;
4. av1dec 半语法推导(av1dec.c:46-408)哪些字段是 hwaccel 合同必需;
5. film grain 合成的应用侧位置(dav1d 内 vs FFmpeg film_grain 滤镜)。
