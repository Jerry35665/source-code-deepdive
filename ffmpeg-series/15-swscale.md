# 第 15 章 · libswscale:视频像素管线——缩放、色彩空间与 SIMD 分发

> 基线:commit `9f63b36a`。行号以 libswscale/ 为准。本章是 07 章(音频管线 swresample)的视频对标篇:swresample 管"采样率/位深/声道",swscale 管"分辨率/像素格式/色彩空间"。注意:该库正处在重构期,**legacy 引擎与新 graph/ops 引擎并存**(15.6)。

## 15.0 全景:四段流水线与 swresample 的对照

```
AVFrame(src)                                             AVFrame(dst)
   │                                                        ▲
┌──▼─────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──┴───────────┐
│ input 描述符   │→ │ hscale 水平  │→ │ vscale 垂直  │→ │ output 描述符│
│ src格式→内部   │  │ 系数卷积     │  │ 系数卷积     │  │ 内部→dst格式 │
│ (色度升采样)  │  │ (15/19bit)  │  │ (15/19bit)  │  │ (色度降采样)│
└────────────────┘  └──────────────┘  └──────────────┘  └──────────────┘
      desc[0..srcW]      系数数组 int16      系数数组 int16     desc[chrEnd..]
```

与 07 章对照:swresample 的五级流水线靠**指针别名**短路,swscale 的四段靠**描述符链 `c->desc[]`** 装配(slice.c:246)——每个描述符是一段"对一行像素做什么"的函数+参数,环形行缓冲在段间传递(ring slice :309,rotate :120)。**中间一律定点**:水平精度 1<<14、垂直 1<<12,内部精度 15/19bit 二选一(utils.c:1404-1413)。

## 15.1 建立期:算法如何变成系数数组

`sws_getContext`(utils.c:1922)→ `sws_init_context`(:1887)→ 单上下文初始化 `ff_sws_init_single_context`(:1137)。四个关键决策:

1. **格式改写**:JPEG 变体自动归一(:773);
2. **算法选择**:flag 默认 BICUBIC(:1209-1216);`scale_algorithms[]` 表把算法映射为核宽(utils.c:184-194)——bicubic 核宽 4,sinc/spline 核宽 20;
3. **系数生成**:`initFilter`(utils.c:197)把解析式变成 int16 定点数组:bicubic 系数闭式解(:312-332),归一化压到 int16(:568-588);
4. **级联兜底**:核宽超过上限时降级为**几何平均两段级联**(先缩到中间尺寸,:492-496 决策,1806-1836 执行)——60 倍缩放不是一根 60 抽头的棍子,而是两根短棍。

色度降采样策略在 :1362/:1372 选定。随后 `ff_init_filters`(slice.c:246)按"源格式→hscale→vscale→output"装配描述符链并分配环形行缓冲。

## 15.2 运行期:逐行驱动的主循环

`sws_scale`(swscale.c:1626)→ `scale_internal`(:1022,分流 gamma/级联/unscaled)→ 核心循环 `ff_swscale`(:263):

```c
/* swscale.c(骨架):按目标行推进 */
for (; dstY < h; dstY++) {
    /* 先跑 input+hscale 描述符(desc[0..chrEnd],:498-510) */
    /* 凑够 vFilterSize 行源数据后跑 vscale+output(:533-534) */
}
```

**输出行是驱动轴**:为产出 dstY 这一行,先保证上游描述符把所需的 `vFilterSize` 行源数据准备进行缓冲,再执行垂直滤波+输出。末两行禁用 MMX 是为了规避 SSE 对齐问题(:523-531)——一行注释背后是一次历史崩溃修复。

多线程按**输出行切片**:每线程复制完整上下文后处理自己的行区间(utils.c:1840-1885,worker=swscale.c:1645)——系数只读所以可复制,行缓冲按切片划分所以无锁。

## 15.3 unscaled 快路径:30 条特判的直通车

尺寸不变且无附加处理时,逐行流水线是浪费——`ff_get_unscaled_swscale`(swscale_unscaled.c:2392)用 30+ 条特判把"格式对+尺寸同"的组合直接映射到整帧转换函数(如 yuyv→yuv420p 的专用循环),同格式则退化为按平面拷贝兜底(:2676-2695)。**这条快路径是 swscale 被大规模用于"只转格式不缩放"场景(硬件下载、色彩修正前处理)的性能基础**。垂直缩放还有 4096 双 tap 特判(vscale.c:135-148):双线性最常见,值得一条无循环的快道。

## 15.4 色彩空间:三层架构

1. **固定矩阵表**:`ff_yuv2rgb_coeffs[11][4]`(yuv2rgb.c:47)——BT.601/709/FCC/SMPTEN 等标准各一行,查表建表(:717);
2. **`sws_setColorspaceDetails`**(utils.c:849):运行时注入自定义矩阵;**YUV→YUV 异色彩空间转换的实现是经 RGB 域级联**(:915-989)——两次矩阵乘,而非直接 YUV↔YUV 解析解;
3. **CMS 色彩管理**(cms.c):基于 IPT 感知均匀空间做色域映射与色调映射——这是 HDR 时代 SDR 兼容管线的新地层,与 legacy 矩阵层并存。

gamma 校正在 scale_internal 入口分流(:1022),通过内部 15/19bit 高精度缓冲避免中间量化损失——**内部精度位数的存在意义就是吃掉 gamma/矩阵运算的舍入误差**。

## 15.5 SIMD 分发:又是那张表

x86 后端提供按 CPU 特性阶梯选择的函数入口(x86/swscale.c:485):

```
yuv2yuvX: sse2 → sse3 → avx2(:513-524 阶梯)
```

与 URLProtocol、AVCodec 同款模式:**运行期按能力探针(caps)查表替换函数指针**,上层无感。这是第 20 章要总结的"表驱动"模式的第四次现身。

## 15.6 新架构:graph 与 ops 后端

重构期的 swscale 在 legacy 单上下文之外新增了内部 graph 层(graph.c):**双引擎选择**——常规转换走 legacy,浮点格式或 `SWS_UNSTABLE` 优先新 ops 后端(graph.c:727);ops 引擎把转换拆成操作码序列(ops.c:42 注册表,ops.h:36-75)。目前对用户透明,但方向明确:**swscale 正在把"四段流水线"泛化为可调度的转换图**——与 avfilter 的 activate 调度殊途同归。

## 15.7 设计动机

1. **固定点内部精度**:15/19bit 是 SIMD 吞吐与精度的交点——16bit 寄存器装得下 14bit 系数×16bit 像素的部分积;浮点在 AVX-512 时代仍不占优,精度反而靠 19bit 路径补;
2. **unscaled 特判表 vs 通用流水线**:格式转换是"离散组合爆炸+每组合有平凡解"的典型问题——通用引擎保底,特判表吃掉 90% 的真实流量;
3. **输出行为驱动轴**:因为垂直滤波的消费节奏由目标行距决定,倒推上游最自然——这是"从消费端调度生产端"的流水线设计;
4. **级联优于长核**:大倍率缩放的频域正确做法本来就是多级,数学上等价、缓存上完胜。

## 15.8 FAQ

**Q1:sws_scale 一次调用处理整帧吗?**
是,但内部按输出行逐行推进(swscale.c:412 起的主循环),多线程再按行区间切分(utils.c:1840-1885)——API 面是整帧,执行面是行。

**Q2:bicubic 的系数在哪算?**
initFilter(utils.c:197)闭式解(:312-332),归一化为 int16(:568-588)。系数只算一次存在上下文里。

**Q3:60 倍缩小会生成 60 抽头滤波器吗?**
不会,核宽超限触发几何平均级联(utils.c:492-496,1806-1836)——两段短核,质量与性能都更好。

**Q4:尺寸相同还要过完整流水线吗?**
不用,ff_get_unscaled_swscale 特判表直通(swscale_unscaled.c:2392),同格式甚至只是平面拷贝(:2676-2695)。

**Q5:YUV601 转 YUV709 走 RGB 吗?**
走。异矩阵 YUV→YUV 经 RGB 域级联(utils.c:915-989),两次矩阵乘。这也是精度要 19bit 的地方。

**Q6:为什么输出第一行可能卡很久?**
垂直滤波要凑 vFilterSize 行源数据(swscale.c:533-534),核宽 20 的 spline 首行要准备约 10 行上游——行缓冲的环形结构(:309)就是为此。

**Q7:多线程会复制整个上下文吗?**
会(utils.c:1840-1885)。系数只读可安全复制,行缓冲按线程切片划分,零锁竞争。

**Q8:swscale 和 swresample 为什么是两个库?**
抽象轴不同:像素的"格式×尺寸×色彩空间"与音频的"格式×采样率×声道"没有共享的系数结构,强行合库只会互相拖累;两者共享的只有"内部高精度+定点系数"的设计思想。

**Q9:新 ops 引擎什么时候启用?**
浮点格式或显式 SWS_UNSTABLE 时优先(graph.c:727),其余仍走 legacy——重构期用户无感,行为差异被开关隔离。

**Q10:HDR→SDR 色调映射在 swscale 里吗?**
新 CMS 层支持(基于 IPT 感知空间,cms.c);legacy 矩阵层不管色调映射,只管矩阵与范围。

## 15.9 小结与深挖方向

本章结论:**swscale = "描述符链四段流水线 + int16 定点系数 + unscaled 特判表 + SIMD 分发表"**,正处在向 graph/ops 泛化的重构中点。深挖:

1. initFilter 的 lanczos 窗函数与 sinc 截断的振铃特性(对照 bicubic :312-332);
2. 环形行缓冲的回绕开销与 slice rotate 策略(slice.c:309,120);
3. CMS 的 IPT 空间色域映射算法与 AV1 HDR 元数据的衔接;
4. ops 操作码序列的调度潜力(能否与 avfilter activate 统一);
5. AVX-512/zen4 路径 vs 19bit 高精度路径的取舍实测。
