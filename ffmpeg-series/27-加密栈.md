# 第 27 章 · 加密栈:从 AES 原语到容器级 CENC

> 基线:commit `9f63b36a`。行号以 libavutil/aes.c、libavformat/crypto.c、hls_sample_encryption.c、mov.c、movenccenc.c 为准。09 章说过"HLS 的 AES-128 分片下沉给 crypto 协议"——本章把这层与包级 SAMPLE-AES、容器级 CENC 讲透。纠偏:树中**确有** RTMPE(rtmpproto.c:1264-1310)与 SRTP(srtp.c:42-95,复用 av_aes_crypt+av_hmac),老资料"FFmpeg 无 SRTP"已过时。

## 27.0 全景:四个层次的职责切分

```
L4 容器级 CENC      mov.c 解盒(tenc/senc/saiz/saio/pssh)→就地解密或挂 side data
                    movenc+movenccenc 写出(仅 cenc-aes-ctr)
L3 包级 SAMPLE-AES  hls.c 识别 METHOD=SAMPLE-AES:TS 本地逐 NALU 解密,
                    fMP4 则透传 decryption_key 给 mov.c 走 CENC
L2 流式 crypto:     URLProtocol,整段 AES-128-CBC+PKCS7 —— HLS AES-128 的下沉点
L1 AES 原语         libavutil/aes.c(CBC/ECB,IV 就地推进)+ aes_ctr.c(CTR 封装)
```

定位三句话:**解密为主**(写出加密只支持 cenc-aes-ctr 一种);**key 管理全在树外**(DRM 的 license/key server 不是 FFmpeg 的事);TLS 走外部库,自带 AES 是为媒体加密(含 RTMPE/SRTP)服务。

## 27.1 L1 原语与 L2 crypto: 协议

`av_aes_crypt` 的契约是全栈的地基:iv=NULL 即 ECB,**非 NULL 即 CBC 且 IV 就地推进**(解密侧 memcpy(iv,src,16),aes.h:63,aes.c:149/163)——"IV 随流推进"这个细节是 crypto: seek 正确性的前提。

crypto: 是 URLProtocol(09 章 L2):仅支持 AES-128(set_aes_arg 强制 16 字节,crypto.c:104-109,159/174)。HLS 的完整参数流(hls.c:1436-1464):read_key 读 16 字节→ff_data_to_hex→拼出 `crypto+URL`/`crypto:URL`→hex 经 AVDict "key"/"iv" 传给协议;无 IV 时默认 **IV=媒体序号大端 64 位垫底**(hls.c:1070-1076,RFC 8216 的规定落在这一行)。

**seek 的 IV 重建**(crypto.c:275-325):CBC 是链式的,seek 回块 0 恢复种子 IV,否则回退一块做"丢弃式读"——用一次额外解密换正确 IV。注意一个已知局限:重建仅从通用 iv 选项恢复(decryption_iv-only 是缺陷路径)。

## 27.2 L3 SAMPLE-AES:为什么必须包级

AES-128(整分片加密)可以用流式协议挡在 IO 层;SAMPLE-AES 只加密码流内的部分样本(如 H264 的 NALU 主体),**密文与明文交织在包内**——流式协议无能为力,必须进格式层。hls.c 分流(:2526-2539):fMP4 分片把 decryption_key 透传给 mov demuxer 走 CENC(:2807-2811);TS 才由 hls_sample_encryption.c 本地逐 NALU 解密:规则是 NALU type 1/5 且 >48 字节、**前 32 字节明文、解 16 跳 144、每 NALU 重置 IV**(hls_sample_encryption.c:203-233,:210/:217-220/:228);AAC 帧头+16 字节明文其余全解(:353-357)。"解 16 跳 144"这种怪节奏是苹果规范对块边界的规定——**加密方案是被传输格式倒着设计的**。

## 27.3 L4 CENC:写出与读入

**写出**(movenccenc.c,仅 cenc-aes-ctr,movenc.c:8469-8487):每帧流程——senc 盒记 8 字节 IV(start_packet,:120)→CTR 加密→**IV+1**(end_packet,:147);subsample 固定 6 字节(clear2+enc4);盒子链 senc/saio/saiz(:495-550)与 sinf/frma/schm/tenc(:552-590)。CTR 模式的流式性(无需链式 IV)使写出端极简——对比 cbcs 需要模式,FFmpeg 写出端干脆不支持。

**读入**(mov.c):四个 scheme 分派 cenc/cbc1/cens/cbcs(:8883-8897);**cbcs 每 subsample 重置 IV**(:8847)、cbc1 链式、pattern 仅 cens/cbcs 非零;tenc 的 pattern 拆 nibble 仅 v>0(:8489-8492)。`cenc_filter` 无 key 时把加密信息挂 `AV_PKT_DATA_ENCRYPTION_INFO` side data,**有 key 就地解密**(mov.c:8917-8990,调用点 :12232)。

## 27.4 side data:只出不进的契约

`AV_PKT_DATA_ENCRYPTION_INFO`(packet.h:250-253;结构 encryption_info.h:157-167)的设计意图是"解密与格式解耦"——但现状是:**生产者仅 mov.c:8977 一处,全树无消费者**(解码器不读它,解密都在 mov.c 内完成);pssh→ENCRYPTION_INIT_INFO 同样只出不进(:8308-8420)。这是 FFmpeg 加密栈的真实边界:**解密内聚在 demuxer,side data 是留给外部 DRM 代理的接口预留**。

## 27.5 设计动机

1. **crypto: 为什么是 URLProtocol**(呼应 09 章):加密作用于"字节流",与格式无关——放 IO 层使 HLS/MOV/MKV 任何封装都能复用;SAMPLE-AES 则相反,密文结构依赖码流格式,必须进格式层——**加密层次跟着密文结构走**;
2. **写出端只支持 cenc-aes-ctr**:CTR 无链式依赖、可并行、段边界自由——实现成本最低且足够覆盖"生产加密内容"的主要场景;cbcs(流媒体 DRM 主流)只在读端支持,因为读端面对的是既有生态;
3. **不碰 key management**:pssh 只做透传,key 获取留给 KID→key 的外部系统——FFmpeg 定位为"格式处理库"而非"DRM 客户端";
4. **每 NALU 重置 IV**:TS 的抗丢包需求(丢一个 NALU 不能毁掉后续解密)——加密粒度的选择同样是传输可靠性的函数。

## 27.6 FAQ

**Q1:HLS 的 key URL 是谁下载的?**
demuxer 自己:hls.c:1436-1464 读 16 字节转 hex 后传给 crypto 协议——FFmpeg 不做 key server 协议。

**Q2:crypto: 支持 AES-256 吗?**
不支持,强制 16 字节 AES-128(crypto.c:104-109)——RFC 8216 SAMPLE-AES 之外的 HLS 标准只定义了 AES-128。

**Q3:为什么 SAMPLE-AES 不能用 crypto: 协议?**
密文/明文交织在包内(前 32 字节明文、解 16 跳 144),流式 CBC 无法表达这种粒度(hls_sample_encryption.c:203-233)。

**Q4:cbcs 和 cenc 模式差在哪?**
cenc=CTR(IV 递增,FFmpeg 可写出);cbcs=CBC 且每 subsample 重置 IV(:8847)——流媒体 DRM 主流,只读。

**Q5:加密 MP4 转封装会保留加密吗?**
流复制保留(tenc/senc 随盒搬移);转码则产明文,key 语义随码流消失。

**Q6:ENCRYPTION_INFO side data 谁消费?**
当前无人(mov.c:8977 生产,树内零消费)——是外部 DRM 代理的接口预留。

**Q7:RTMPE/SRTP 在树里吗?**
在:RTMPE(rtmpproto.c:1264-1310)用 FFmpeg 自带 crypto;SRTP(srtp.c:42-95)复用 av_aes_crypt+av_hmac。

**Q8:HLS 无 IV 标签时 IV 是什么?**
媒体序号大端 64 位垫底(hls.c:1070-1076)——同分片重播 IV 可复现。

**Q9:crypto: seek 后解密还对吗?**
对,seek 重建 IV:块 0 用种子,否则回退一块丢弃式读(crypto.c:275-325);但仅从通用 iv 选项恢复是已知局限。

**Q10:FATE 怎么验证 CENC 解密?**
tests/fate/mov.mak:63/66/69 用 `-decryption_key` 解密样本比对——解密路径有回归测试覆盖。

## 27.7 小结与深挖方向

本章结论:**加密栈 = "密文结构决定层次"(流式→IO 层、包级→格式层、容器级→盒解析)+ "解密为主、key 外置"**。深挖:

1. crypto_seek 回退式 IV 重建(:275-325)与 09 章 HLS seek 的交互成本;
2. mov.c cenc_filter 就地解密(:8917-8990)与流复制(零解密)的性能分水岭;
3. ENCRYPTION_INFO side data 若被解码器消费,可支撑外置 DRM 代理的管道化;
4. RTMPE 的握手混淆(handshake0)与 SRTP 的密钥推导链;
5. SAMPLE-AES"解 16 跳 144"规范节奏的抗丢包论证。
