# 第 14 章 · x264/x265 编码器封装:外部库如何被包成 AVCodec

> 基线:commit `9f63b36a`。行号以 libavcodec/libx264.c、libx265.c、encode.c 为准。首卷 03 章讲过 send/receive 通用管线,本章讲它的另一端:外部编码器库如何挂在管线上。一处纠偏:`ff_af_queue_add` 在本 commit 只用于音频编码器(aacenc.c:1234 等),视频 wrapper 的 pts 归还走 opaque 环(见 14.3)。

## 14.0 全景:wrapper 的位置与零拷贝链路

x264/x265 wrapper 是 `AVCodec` 的普通实例,注册进 codec 表(allcodecs.c:826-828),编码回调经 `FF_CODEC_ENCODE_CB` 装配(libx264.c:1652;libx265.c:1097)——本树已无 `AVCodec.encode2` 字段,回调挂在 `FFCodec.cb.encode`,由 `ff_encode_encode_cb` 分发(encode.c:293-340)。

```
AVFrame(send_frame 缓存)
   │ receive_packet → encode_simple_internal(encode.c:342)
   ▼
X264_frame / libx265_encode_frame
   │ AVFrame 平面指针直借给 pic_in(零像素拷贝)
   │   libx264.c:499-504 / libx265.c:749-755
   ▼
x264_encoder_encode / x265 api->encoder_encode
   │ 返回 NAL 数组
   ▼
ff_get_encode_buffer + memcpy → AVPacket
   libx264.c:152-193(单次整体 memcpy)
   libx265.c:888-904(逐 NAL + keyframe 探测)
```

**像素零拷贝,比特流一次拷贝**:输入侧只借指针(调用方需在编码完成前保活 frame——send/receive 框架的 refcount 保证这点),输出侧必须拷,因为 NAL 数组是库内私有内存。

## 14.1 init:一台选项翻译机

`X264_init` 的本质是把三源选项合并进 `x264_param_t`,**优先级 = 代码书写顺序**(后写覆盖先写):

```
① preset 铺底            libx264.c:1106
② 通用 AVCodecContext 字段:
   bit_rate(:1132)、gop/bf(:1174-1177)、
   colorspace→VUI(:1363)
③ 私有 AVOption 表        :1519-1598(crf/qp/preset/tune/...)
④ profile                 :1318
⑤ x264opts 字符串透传     :1380-1398(x264_param_parse)
⑥ x264-params AVDictionary::1404-1417(最高优先级)
```

通用字段的哨兵默认值由 `FFCodecDefault` 表注入(libx264.c:1600-1627),应用点在 options.c:137-145——**"gop=250"这类默认不属于 wrapper 硬编码,而属于框架的统一默认表**。⑤⑥ 的存在让 x264 的全部原生选项无需等 FFmpeg 建模即可用:字符串直接进 `x264_param_parse`。这是 wrapper 类代码的通用哲学:**建模高频选项,透传长尾选项**。

x265 侧同构,外加一处特色:10bit/12bit 靠 `x265_api_get(depth)` 在**多份编译体**中选 API(libx265.c:279-281,能力探测 :1017-1039)——x265 允许 8/10/12bit 三体共存一个 .so。

## 14.2 编码循环与 pts 归还:opaque 环形队列

B 帧重排意味着输入顺序≠输出顺序,AVFrame 上的 duration/opaque 等元数据必须跟着"内容"一起重排。x264 wrapper 的机制:

```c
/* libx264.c(节选) */
/* 入队(:506-523):元数据存槽,槽指针挂 pic->opaque */
pic->opaque = &x4->seq + (out_seq % 槽深);  /* 槽深 +17,:1448 */
x264_encoder_encode(...);
/* 出队(:676-688):按 pic_out.opaque 找回槽 */
out_frame = pic_out.opaque;
pkt->duration = out_frame->duration;
```

槽深是 `maximum_delayed_frames+17`(:1448)——比理论最大延迟多 17 个槽作安全余量。x265 用等价但更省内存的变体:`userData` 只存下标+1,槽池动态分配(libx265.c:785,936-949,分配器 rd_get:109-134)。**两者解法同构:把元数据挂在编码器原样带回的 opaque 指针上,信任库的重排保真**。

## 14.3 delay 与 flush:谁负责排水

两 wrapper 均声明 `AV_CODEC_CAP_DELAY`——框架因此跳过通用时间戳回填(encode.c:312-330),pts/dts 由 wrapper 自设(libx264.c:673-674;libx265.c:906-907)。EOF 排水:框架传 frame=NULL(encode.c:360-367),wrapper 循环调 `x264_encoder_delayed_frames` 直到吐干(libx264.c:668)。

中途 flush(`avcodec_flush_packets`)能力不对等:**仅 x264 支持**(cap 声明 libx264.c:1645,实现 X264_flush:752-768),x265 是告警 no-op(avcodec.c:396-402)——实时推流场景(切换场景需重置编码器状态)这是 x264 仍不可替代的原因之一。

## 14.4 extradata:头两套写法

`AV_CODEC_FLAG_GLOBAL_HEADER` 时,头数据写进 extradata:

- x264:`x264_encoder_headers` 取出(libx264.c:976);若目标不是 annexb(MP4/MKV 场景),**手工把 SPS/PPS 拼成 avcC record**(:882-966);SEI 存起随首帧发送(:179-186);
- x265:`encoder_headers` 取 nal[0] 整段拷(libx265.c:615,630)。

annexb(裸流/TS)与 length-prefixed(avcC)双形态的转换全部发生在 wrapper 内——上层 muxer 只认 extradata,不再关心库的输出格式。

## 14.5 x264 与 x265 wrapper 差异速览

| 维度 | libx264.c | libx265.c |
|---|---|---|
| 编码回调 | FF_CODEC_ENCODE_CB(X264_frame)(:1652) | 同构(:1097) |
| 输出封包 | 单次整体 memcpy(:152-193) | 逐 NAL+keyframe 探测(:888-904) |
| 元数据回传 | opaque 槽,静态环形(:506-523) | userData 下标+动态池(:936-949) |
| 多位深 | 编译期(8/10bit 分体) | x265_api_get(depth) 运行期选(:279-281) |
| flush | 支持(:1645,752-768) | no-op(avcodec.c:396-402) |
| 头写法 | headers+手工 avcC(:976,882-966) | nal[0] 整段(:615,630) |

## 14.6 设计动机

1. **wrap 而非重写**:x264 的率控是十年调参的结晶,FFmpeg 的价值在框架(I/O/滤镜/容器)而非重造编码器。wrapper 层因此刻意做薄:翻译选项、搬运缓冲、归还元数据,三件事之外不添加任何策略;
2. **AVOption 表是"外部库选项的 FFmpeg 化"**:高频选项建模成结构化字段(可枚举/可文档化),长尾经 x264opts 透传。边界清晰:FFmpeg 不追平外部库的全部选项面,只保证最常用的可移植表达;
3. **opaque 环是"信任外部库重排"的最小机制**:不维护自己的重排队列,只把元数据指针随帧交给库、等它原样带回。前提是编码器契约保证 opaque 透传——x264/x265 均遵守;
4. **编译期解耦**:wrapper 依赖 pkg-config 检测,`--enable-libx264` 要求 `X264_BUILD>=155`(configure:7501-7505,依赖声明 :3915)——FFmpeg 核心零依赖,外部库全部可裁剪,发行版按需拼装。

## 14.7 FAQ

**Q1:编码时像素会被拷贝吗?**
不会。AVFrame 平面指针直借给 pic_in(libx264.c:499-504),send/receive 的 refcount 保证 frame 活到编码完成;只有输出比特流必须 memcpy。

**Q2:crf、preset 这些选项定义在哪?**
wrapper 私有 AVOption 表(libx264.c:1519-1598),init 时写入 x264_param_t;不是 x264 库自带的枚举,是 FFmpeg 的建模层。

**Q3:x264opts 和 x264-params 冲突听谁的?**
x264-params(字典)最后写(:1404-1417),覆盖 x264opts(字符串 :1380-1398);两者都在通用字段与 preset 之后,即总是赢过 FFmpeg 建模选项。

**Q4:B 帧重排后 packet 的 pts/duration 怎么对上原 frame?**
opaque 环形队列:输入时元数据存槽挂 pic->opaque(:506-523),输出按 pic_out.opaque 找回(:676-688)。槽深留 17 余量(:1448)。

**Q5:编码器有延迟,EOF 后怎么把帧吐干净?**
AV_CODEC_CAP_DELAY 使框架在 frame=NULL 时继续调回调(encode.c:360-367),wrapper 循环 x264_encoder_delayed_frames 排水(libx264.c:668)。

**Q6:avcodec_flush_packets 对 x265 为什么无效?**
x265 未实现 flush,框架走告警 no-op(avcodec.c:396-402);x264 实现了 X264_flush(libx264.c:752-768,cap :1645)。需要中途重置的实时场景选 x264。

**Q7:MP4 封装时的 avcC 谁拼的?**
wrapper:x264 路径在 !annexb 时手工拼 avcC record(libx264.c:882-966),头来自 x264_encoder_headers(:976);x265 直接整拷 nal[0](libx265.c:630)。

**Q8:一个二进制能同时编 8bit 和 10bit 的 x265 吗?**
能。x265 支持多编译体共存,`x265_api_get(depth)` 运行期选对应位深 API(libx265.c:279-281,探测 :1017-1039);x264 则需 10bit 版单独编译。

**Q9:视频编码为什么不用 ff_af_queue_add 管 pts?**
那个队列只服务音频编码器(aacenc.c:1234 等);视频 wrapper 用 opaque 环(14.3)——音频无重排所以队列够了,视频的元数据必须随 B 帧重排走。

**Q10:怎么让 FFmpeg 带上 x264?**
`--enable-libx264`;configure 经 pkg-config 校验且要求 X264_BUILD>=155(configure:7501-7505),依赖关系注册在 :3915。

## 14.8 小结与深挖方向

本章结论:**wrapper = "选项翻译机 + 零拷贝搬运 + opaque 环元数据归还"三件套**;外部库集成的一切复杂性都被压在这 2000 行以内,框架其余部分对 x264 一无所知。深挖:

1. SEI 延迟随首帧发送的机制(libx264.c:179-186)与 HDR10+/DVB-RCC 元数据注入点;
2. libx265 动态槽池 rd_get 的分配策略(libx265.c:109-134)与极端 B 帧深度下的行为;
3. FFCodecDefault 哨兵(options.c:137-145)与用户显式赋值的区分方式;
4. libx265 逐 NAL 封包的 keyframe 探测(:888-904)与 libx264 单次 memcpy 的取舍;
5. 头两套写法(avcC vs annexb)在流复制场景(c:s copy)下出错的经典案例。
