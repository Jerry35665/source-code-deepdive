# M 篇 · 外部编码器封装层：libx264.c 与 libx265.c 深读

> 基线：FFmpeg master，commit `9f63b36a`。所有行号均为仓库相对路径，已用 grep/Read 实际核对。
> 本章主角：`libavcodec/libx264.c`（1727 行）、`libavcodec/libx265.c`（1103 行）——两个把外部编码库"包装"成 FFmpeg 原生 codec 的适配层。

---

## 1. 全景：wrapper 层在编码框架中的位置

FFmpeg 对外的编码 API 只有三个：`avcodec_send_frame` / `avcodec_receive_packet` / `avcodec_flush_buffers`。所有编码器（内置 H.264 解码器同族的 native 编码器、硬件编码器、外部库 wrapper）都收敛到同一个内部结构 `FFCodec`（`libavcodec/codec_internal.h`），wrapper 与 native 编码器的唯一区别是：**`cb.encode` 回调里调的不是自己的熵编码/运动估计代码，而是 `x264_encoder_encode()` / `x265_encoder_encode()` 这样的外部符号**。

需要先纠正一个常见（也是本书初稿素材里的）历史印象：在本 commit 中，`AVCodec` 已无 `encode2` 函数指针字段。回调统一收进 `FFCodec.cb` 联合体，由宏 `FF_CODEC_ENCODE_CB(func)` 装配（`libavcodec/codec_internal.h:386-389`，置 `cb_type = FF_CODEC_CB_TYPE_ENCODE` 并赋 `cb.encode`）。两个 wrapper 的装配点分别是 `libavcodec/libx264.c:1652` 与 `libavcodec/libx265.c:1097`。同理，`encode.h` 里也没有 `AVCodecEncoder` 结构体——它只放编码侧辅助函数原型（`libavcodec/encode.h:45-91`），编码器私有结构在 `codec_internal.h`。

完整数据通路（以 x264 为例）：

```
avcodec_send_frame()                    encode.c:545
  └─ encode_send_frame_internal()       encode.c:481   (AVFrame 暂存到 avci->buffer_frame)
avcodec_receive_packet()                encode.c:578
  └─ encode_receive_packet_internal()   encode.c:400
      └─ encode_simple_receive_packet() encode.c:387   (循环直到吐出 packet)
          └─ encode_simple_internal()   encode.c:342
              ├─ ff_encode_get_frame()  encode.c:218   (取走暂存帧; EOF 时 frame=NULL)
              └─ ff_encode_encode_cb()  encode.c:293
                  └─ cb.encode = X264_frame()          libx264.c:619
                      ├─ setup_frame()   AVFrame ──► x264_picture_t   libx264.c:476
                      │    plane[i]=frame->data[i], stride=linesize   libx264.c:499-502
                      │    pic->i_pts = frame->pts                     libx264.c:504
                      ├─ x264_encoder_encode(&nal,&nnal,pic_in,&pic_out) libx264.c:635
                      └─ encode_nals(): ff_get_encode_buffer + memcpy    libx264.c:152-193
                          └─ AVPacket(Annex-B NAL 顺序拼接)
```

关键点：**wrapper 不拷贝像素**。`pic->img.plane[i] = frame->data[i]`（`libx264.c:500`）、`x265pic.planes[i] = pic->data[i]`（`libx265.c:750`）只是把 AVFrame 的平面指针借给外部库，前提是外部库在 `x264_encoder_encode` 返回前读完（x264/x265 均满足）。`AV_CODEC_CAP_DR1`（`libx264.c:1642`、`libx265.c:1089`）即声明了这种"直接引用输入缓冲"的能力。

输出侧也没有二次打包：x264 保证所有 NAL payload 在内存中连续（`libx264.c:188-190` 注释），所以 `encode_nals` 一次 `ff_get_encode_buffer` + 一次 `memcpy` 搞定（`libx264.c:174-190`）；x265 的 NAL 数组不保证连续，于是逐个 memcpy 并顺带探测 keyframe NAL 类型置 `AV_PKT_FLAG_KEY`（`libx265.c:888-904`）。

## 2. init 专节：选项的三大来源与合并优先级

`X264_init`（`libavcodec/libx264.c:1086-1457`）约 370 行，本质是一台"选项翻译机"。输入有三个来源，写入同一个 `x264_param_t`，**后写者覆盖先写者**，于是合并优先级由代码顺序决定：

**第 0 层：x264 自己的默认值与 preset/tune 基线。**
`x264_param_default`（`libx264.c:1102`）；若用户给了 `preset`/`tune` 则 `x264_param_default_preset` 整体覆写（`libx264.c:1106-1119`）。preset 先行，才能让后续显式选项覆盖 preset。

**第 1 层：通用 AVCodecContext 字段**（由 `libavcodec/options_table.h` 的通用 AVOption 表定义，如 `g`→`gop_size` 在 `options_table.h:96`、`qmin/qmax` 在 `:106-107`、`bf`→`max_b_frames` 在 `:109`、`refs` 在 `:268`）。`X264_init` 逐个搬运：
- `avctx->bit_rate` → `params.rc.i_bitrate`，模式 ABR（`libx264.c:1132-1139`）
- `avctx->gop_size` → `i_keyint_max`、`avctx->max_b_frames` → `i_bframe`（`libx264.c:1174-1177`）
- `qmin/qmax/max_qdiff/qblur/qcompress/refs/trellis/me_range/subq` 等（`libx264.c:1182-1214`）
- 时基与帧率：`i_timebase_*`（`libx264.c:1334-1335`）、`i_fps_*` 优先取 `avctx->framerate`（`libx264.c:1336-1342`）
- 色彩：`color_range`→`vui.b_fullrange`（`:1356-1361`）、**`colorspace`→`vui.i_colmatrix`（`:1363-1364`）**、`color_primaries/color_trc`→VUI（`:1365-1368`）
- 宽高/SAR/线程数（`libx264.c:1329-1348`）

**第 2 层：wrapper 私有 AVOption 表**（`libavcodec/libx264.c:1519-1598`，挂在 `x264_class` 上 `:1630-1635`）。这些是 x264 特有、通用表装不下的选项（`crf` `:1529`、`aq-mode` `:1532`、`psy-rd` `:1539`、`nal-hrd` `:1570`、`x264opts` `:1528`、`x264-params` `:1595`……），先落到 `X264Context` 字段，再由 `X264_init` 应用。应用有两种形态：
- 宏 `PARSE_X264_OPT(name, var)`：直接调 `x264_param_parse` 透传字符串（定义 `libx264.c:1005-1009`，用于 `psy-rd/deblock/partitions/stats` 等，调用点 `:1220-1223`）；
- 直接赋值：如 `x4->crf` → `X264_RC_CRF`（`:1146-1148`）、`x4->aq_mode` → `rc.i_aq_mode`（`:1216-1217`）。

**第 3 层（最高优先级）：自由字符串。** `x264opts` 是冒号分隔的 `key=value` 串，`X264_init` 手写解析循环，`sscanf("%4095[^:=]=%4095[^:]")` 切分后逐个调 `parse_opts`（`libx264.c:1380-1398`；`parse_opts` 是 `x264_param_parse` 的错误翻译壳，`:805-829`）。`x264-params` 则是 `AV_OPT_TYPE_DICT`（`libx264.c:1595`），在 init 末尾字典序迭代透传（`:1404-1417`）。因为排最后，**它们能覆盖前面所有层的设置**——选项帮助文本里"Override the x264 configuration"即此意。

x265 侧结构同构但风格不同：`libx265_encode_init`（`libavcodec/libx265.c:272-635`）先 `param_default_preset`（`:289`），通用字段能直写的直写（宽高/帧率/线程 `:307-317`），其余**全部退化成字符串再 `param_parse`**——`libx265_param_parse_int/float` 把 int/float `snprintf` 成字符串（`:162-190`），`qmin→"qpmin"`（`:448-451`）、`gop_size→"keyint"`（`:497-500`）、`i_quant_factor→"ipratio"`（`:473-476`）等。`x265-params` 字典在 `:518-550` 透传，`pass`/`stats` 在 `:552-568`，profile 最后收口（`:575-585`）。

另一个翻转优先级的细节：通用层与私有层冲突时谁赢？答案是**都不输**——wrapper 把大量通用项的默认值改成了"哨兵值"，用户没显式设置就不碰 x264 默认。机制是 `FFCodecDefault x264_defaults[]`（`libx264.c:1600-1627`：`g=-1`、`qmin=-1`、`bf=-1`、`refs=-1`……），在 `avcodec_alloc_context3` 里经 `av_opt_set` 逐条覆写通用默认（`libavcodec/options.c:137-145`）。`X264_init` 里满屏的 `if (xxx >= 0)`（如 `:1182`、`:1192`）就是在检测哨兵。这正是"通用选项表 + 每编码器默认表"两段式设计的精髓：`options_table.h` 定义"有哪些通用旋钮"，`FFCodecDefault` 定义"本编码器如何解释'用户没拧'".

## 3. 编码循环专节：B 帧重排下的 pts 归还、delay 语义与 flush

### 3.1 延迟与时间戳的分工

`ff_encode_encode_cb`（`libavcodec/encode.c:293-340`）在调完 `codec->cb.encode` 后做通用收尾：packet 强制 refcounted（`encode.c:305-309`）；**但有 `AV_CODEC_CAP_DELAY` 的编码器，通用时间戳回填被跳过**（`encode.c:312-323` 的 if 条件），`dts=pts` 的兜底同理（`:325-330`）。注释写得很直白："encoders with delay have to set the timestamps themselves"。两个 wrapper 都带 `AV_CODEC_CAP_DELAY`（`libx264.c:1642`、`libx265.c:1089`），所以 `pkt->pts = pic_out.i_pts; pkt->dts = pic_out.i_dts`（`libx264.c:673-674`）、`pkt->pts = x265pic_out->pts; pkt->dts = x265pic_out->dts`（`libx265.c:906-907`）由 wrapper 自己负责。

### 3.2 重排后"找回"输入元数据：环形 opaque 队列（本文最重要的机制）

x264 内部有 lookahead + B 帧重排，**输出 packet 的顺序 ≠ 输入 AVFrame 的顺序**。而 `duration`、wallclock、`AV_CODEC_FLAG_COPY_OPAQUE` 的 opaque 指针都绑定在"输入帧"上，必须跟着内容回到正确的输出包。x264 API 为此提供了 `x264_picture_t.opaque` 指针：输入时塞进去，输出 `pic_out.opaque` 原样带出。

wrapper 据此维护一个环形槽位数组 `X264Opaque *reordered_opaque`（`libx264.c:119-120`），槽位大小 `x264_encoder_maximum_delayed_frames() + 17`（`libx264.c:1448`，注释解释 +17 是防运行期 reconfig 增大 delay）：

```c
// libx264.c:506-523（输入侧）
opaque_uninit(opaque);
...
opaque->duration = frame->duration;
opaque->wallclock = wallclock;          // export PRFT 时取 av_gettime()
...
pic->opaque = opaque;                   // 挂到输入 picture 上
x4->next_reordered_opaque++;
x4->next_reordered_opaque %= x4->nb_reordered_opaque;
```

输出侧拿 `pic_out.opaque` 校验指针落在环形数组区间内，然后取回 `duration`/`wallclock`/opaque 并归还槽位（`libx264.c:676-688`）。x265 版本更绕一点：`x265_picture.userData` 只有 intptr 宽，所以存的是"槽位下标 +1"（`libx265.c:785`），槽位池 `ReorderedData *rd` 用惰性扩容的 `rd_get()` 分配（`libx265.c:109-134`），输出时 `-1` 还原下标取回 duration/opaque（`libx265.c:936-949`）。

**关于 `ff_af_queue_add` 的澄清**：`ff_af_queue_add/remove` 是 **audio 专用**的 pts 队列（audio_frame_queue），本 commit 中只有 AAC/AC3/APTX 等音频编码器使用（如 `libavcodec/aacenc.c:1234`、`libavcodec/ac3enc.c:2003`）。视频 wrapper 从未用过它——x264/x265 解决的是同一个问题（重排后找回 pts/元数据），但用的是上述 opaque 环形队列：音频帧无重排、定长，队列 FIFO 即可；视频有 B 帧乱序，所以让外部库自己把 opaque "穿越"重排带回来。写本章时务必不要把 af_queue 安到 x264 头上。

### 3.3 delay 与吐帧循环

`X264_frame` 的 `do...while` 是理解吐帧节奏的钥匙（`libx264.c:634-668`）：

```c
do {
    if (x264_encoder_encode(x4->enc, &nal, &nnal, pic_in, &pic_out) < 0)
        return AVERROR_EXTERNAL;
    ...                                   // RECON_FRAME 处理
    ret = encode_nals(ctx, pkt, nal, nnal);
} while (!ret && !frame && x264_encoder_delayed_frames(x4->enc));
```

`frame == NULL`（EOF 排水，由 `encode.c:360-367` 置 NULL 并要求 `AV_CODEC_CAP_DELAY`）时循环到 `x264_encoder_delayed_frames()==0`，把滞留帧一次吐光；正常送帧时只调一次，没输出就 `got_packet=0` 让上层循环再来（`encode.c:391-395`）。x265 没有这个内层循环，EOF 排水靠 `encode_simple_receive_packet` 外层反复回调 `libx265_encode_frame(NULL)`，每次 `encoder_encode(..., NULL, ...)`（`libx265.c:874-875`）吐一个。

### 3.4 flush（avcodec_flush_buffers，非 EOF）

EOF 排水是"正常交班"，flush 则是"中途清仓"。框架层只认 `AV_CODEC_CAP_ENCODER_FLUSH`：没有该 cap 的编码器调 `avcodec_flush_buffers` 直接告警 no-op（`libavcodec/avcodec.c:393-402`），有的才走 `ff_encode_flush_buffers`（`encode.c:1024-1032`，仅清 `in_frame`/`recon_frame`）+ `codec->flush`（`avcodec.c:417-418`）。

- **x264 支持 flush**：声明 cap（`libx264.c:1645`），`X264_flush`（`:752-768`）连调 `x264_encoder_encode(NULL)` 排干延迟帧、复位 opaque 环、并把 `sei_size` 的负号取反以便 SEI 重发（`:766-767`，写入侧 `:184-185` 用 `-sei_size` 标记"已随首帧发过"）。
- **x265 不支持**：`ff_libx265_encoder` 无 `flush` 字段、无该 cap（`libx265.c:1089-1103`），中途 flush 对 libx265 是显式 no-op。

## 4. x264 与 x265 wrapper 差异对照

| 维度 | libx264.c | libx265.c |
|---|---|---|
| 私有选项风格 | 大量类型化 AVOption 直映射 `x264_param_t` 字段（`1519-1598`）| 极简 11 个选项（`1043-1059`），一切靠 `x265-params` 字典 + `param_parse` 字符串 |
| 字符串透传 | `x264opts`（冒号分隔，手写解析 `1380-1398`）+ `x264-params` 字典（`1404-1417`）| 仅 `x265-params` 字典（`518-550`），无串式选项 |
| 场景切换 | 私有项 `sc_threshold`→`i_scenecut_threshold`（`:1592`, `:1179-1180`）| 无通用映射，须走 `x265-params` 的 `scenecut` |
| 编码入口 | `x264_encoder_encode`，NAL payload 内存连续，一次 memcpy（`:635`,`:190`）| `api->encoder_encode` 返回 `x265_nal` 数组，逐个 memcpy + keyframe 探测（`:871-876`,`:888-904`）|
| NAL 类型判断 | `pic_out.i_type` 枚举（`:695-710`）| `x265pic_out->sliceType` + `is_keyframe(NAL type)`（`:910-925`,`:94-107`）|
| 元数据回传 | `pic->opaque` 指针直传，环形定长槽（`:1448-1450`）| `userData` 存下标+1，槽位池动态扩容（`:785`,`:109-134`）|
| 10bit | 单库多深度：`X264_CSP_HIGH_DEPTH` 位（`csp_to_pixfmt` `:313-333`），pix_fmts_all 一张表全含 8/10bit（`:1485-1506`）| **双/三份编译**：`x265_api_get(bitdepth)` 返回 8/10/12 各自的 API 表（`:279-281`），运行时探测可用深度列 pix_fmts（`:1017-1039`）|
| 多层/Alpha | 无 | `x265pic_out[FF_X265_MAX_LAYERS]`（`:727`），X265_BUILD>=210 支持双层 alpha（`:44-50`,`:595-602`）|
| flush | 支持（`AV_CODEC_CAP_ENCODER_FLUSH` + `X264_flush` `:752-768`）| 不支持（`avcodec.c:396-402` 告警 no-op）|
| 运行期重配置 | `AV_CODEC_CAP_ENCODER_RECONF` + `X264_reconf`/`reconfig_encoder`（`:1646`,`:770-781`,`:195-240`，crf/vbv/sar 等热更）| 无 reconf 能力 |
| Dolby Vision | 无（HDR10 侧数据进 param，`CONFIG_LIBX264_HDR10` 门控 `:1059-1084`）| `ff_dovi_configure` + 每帧生成 RPU（`X265_BUILD>=167`，`:587-593`,`:847-864`）|
| extradata | Annex-B 拼接或手工构造 avcC record（`:969-1003`,`:882-966`）| `encoder_headers` 返回整体，单次 memcpy nal[0]（`:611-632`）|

10bit 一项值得展开：x264 主线库同一份代码含 8/10bit（高位深度标志内嵌在 csp 枚举里），wrapper 无感知；x265 官方发布是 `libx265_main`/`main10`/`main12` 多体库，FFmpeg 侧用 `x265_api_get(desc->comp[0].depth)` 拿对应 API，失败再回落 `x265_api_get(0)`（`libx265.c:279-281`）——如果链接的是单体 8bit 库，10bit 像素格式会被 `libx265_get_supported_config` 从可支持列表里剔除（`libx265.c:1023-1035`），用户看到的就是"libx265 不支持 yuv420p10"的经典报错根源。

## 5. extradata / 头写入

两条路线，由 `b_annexb` 与 `AV_CODEC_FLAG_GLOBAL_HEADER` 控制。

x264：`X264_init` 末尾，仅当 `GLOBAL_HEADER` 时调 `set_extradata`（`libx264.c:1433-1437`）。`set_extradata` 先 `x264_encoder_headers(x4->enc, &nal, &nnal)` 取 SPS/PPS/SEI（**`libx264.c:976`**）；若 `!b_annexb`（容器要 avcC）走 `set_avcc_extradata`（`:980-983` → `:882-966`），从 SPS NAL 里抠出 profile/level 字节手工拼 AVCDecoderConfigurationRecord（`:915-963`），并用 GetBitContext 解 SSP 的 chroma_format/bit_depth 补齐高 profile 字段（`:934-960`）；Annex-B 情形则跳过 SEI 逐条 memcpy（`:989-1000`），SEI 单独存进 `x4->sei`（`save_sei`，`:866-879`）随首个编码帧发出（`encode_nals` 的 `:179-186`）。配合 `GLOBAL_HEADER` 还会关掉 `b_repeat_headers`（`:1374-1375`）；反之不开 GLOBAL_HEADER 时 x264 默认每个关键帧重复头。

x265：`AV_CODEC_FLAG_GLOBAL_HEADER` 的语义反过来写成 `!(flags) → bRepeatHeaders = 1`（`libx265.c:494-495`），头获取在 `encoder_open` 之后 `api->encoder_headers(...)`（**`libx265.c:615`**），返回值即总长，`nal[0].payload` 起整段 memcpy（`:630`）——x265 的 HEVC 参数集天然已打包为一条连续缓冲（含 VPS/SPS/PPS）。

## 6. 设计动机：为什么 wrap 而不重写

1. **工程现实**。x264 十余年打磨的码控/psy/汇编内核不可能在 FFmpeg 内复刻，native H.264 编码器长期只能做实验用途；wrapper 让 `ffmpeg -c:v libx264` 一行命令把外部库纳入统一 CLI/API（`-vcodec` 按名字查 `allcodecs.c:826-828` 注册的 `ff_libx264_encoder`/`ff_libx265_encoder`）。
2. **AVOption 表 = 外部库选项的 FFmpeg 化**。`options[]` 表（`libx264.c:1519-1598`）本质是 x264 CLI 选项名空间在 av_opt 体系里的投影：能类型化的（`crf`、`aq-mode`）类型化，纯字符串的（`psy-rd` 的 `strength:trellis` 复合格式）保持字符串透传给 `x264_param_parse`；实在追不完的尾巴留给 `x264opts`/`x264-params` 两个"逃生舱"。这让 `av_opt` 的枚举/帮助/运行期参数（`VER` 标记，`libx264.c:1518`）对外部库统一生效。
3. **统一编码器契约**。框架只认 `FFCodec` 的 init/encode/flush/close/capabilities 契约；wrapper 把 x264 的 `b_stat_write/PASS1`（`libx264.c:1142-1144`）、线程（`i_threads = avctx->thread_count`，`:1346`，`AV_CODEC_CAP_OTHER_THREADS` 表示库内自线程 `:1643`）、CPB side data（`ff_encode_add_cpb_side_data`，`:1439-1444`、`libx265.c:487-492`）逐一翻译成框架语义。上层容器/CLI 完全无需知道编码器是 native 还是外挂。
4. **独立 codec 而非插件**。wrapper 与 native 编码器同构地编译进 libavcodec（`libavcodec/Makefile:1236-1238`），configure 检测到头文件与库才启用：`--enable-libx264`（`configure:303`）→ `require_pkg_config libx264 x264 ... x264_encoder_encode` 且要求 `X264_BUILD >= 155`（`configure:7501-7505`）→ `libx264_encoder_deps="libx264"`（`configure:3915`）生成 `CONFIG_LIBX264_ENCODER` 宏门控编译。license 上这也是为何 libx264/x265 版 FFmpeg 须以 GPL 发布（x264 为 GPL）。

## 7. FAQ 素材

1. **`-c:v libx264` 时 `-crf 23` 走的哪条路？** 私有 AVOption `crf`（`libx264.c:1529`）→ `X264Context.crf` → init 中 `X264_RC_CRF`（`:1146-1148`）。`-qscale` 则被显式拒绝并告警（`:1093-1094`）。
2. **preset/tune 和显式选项冲突听谁的？** preset 先铺底（`:1106`），显式选项后写覆盖；`x264opts`/`x264-params` 最后写、优先级最高（`:1380-1398`,`:1404-1417`）。
3. **为什么 `-bf`/`-g` 设了但 x264 报告值不同？** wrapper 仅当用户显式设置（非哨兵 -1）才覆盖；且 init 结束会**反向回写** `avctx->has_b_frames`（按 bframe_pyramid 折算，`:1422-1423`）与 `avctx->bit_rate`（`:1427`）。
4. **B 帧重排后 packet 的 pts 怎么对上输入帧？** 输入时把 duration/wallclock/opaque 存进环形槽并挂到 `pic->opaque`（`libx264.c:506-523`），x264 输出时原样带回 `pic_out.opaque`（`:676-688`）；x265 用 `userData=下标+1`（`libx265.c:785`,`:936-949`）。x264 的槽位数 = 最大延迟帧数+17（`:1448`）。
5. **编码器支持中途 flush 吗？** x264 支持（cap `:1645` + `X264_flush` `:752`），x265 不支持，`avcodec_flush_buffers` 对它是告警 no-op（`avcodec.c:396-402`）。EOF 排水是另一回事，两者都靠 `AV_CODEC_CAP_DELAY` + NULL frame 驱动（`encode.c:360-367`）。
6. **`AV_CODEC_FLAG_COPY_OPAQUE` 在 wrapper 里如何落地？** 槽位里额外存 `frame_opaque/frame_opaque_ref`（`libx264.c:508-513`,`:682-686`；`libx265.c:775-783`,`:942-946`），输出时搬进 packet。
7. **10bit 编码报"pixel format not supported"？** x265 的 8/10/12bit 是不同编译体，`x265_api_get(depth)` 探测失败即从支持列表剔除（`libx265.c:279-281`,`:1023-1035`）；x264 单库多深度无此问题（`libx264.c:1485-1506`）。
8. **mp4/mov 里的 avcC extradata 是谁生成的？** `GLOBAL_HEADER` + `!b_annexb` 时 `set_avcc_extradata` 手工拼 AVCDecoderConfigurationRecord（`libx264.c:882-966`）；x265 直接整体拷 `encoder_headers` 输出（`:611-632`）。
9. **ROI/闭环字幕 SEI 怎么进外部库？** 帧级 side data 在 `setup_frame`/`libx265_encode_frame` 里翻译：A53 CC → SEI payload（`libx264.c:541-564`、`libx265.c:787-814`），ROI → `quant_offsets`（`libx264.c:403-474`、`libx265.c:637-699`），均要求开启 AQ 否则告警跳过。
10. **`ff_af_queue_add` 在 libx264 里在哪？** 不存在。那是音频编码器的 pts 队列（`aacenc.c:1234` 等）；视频 wrapper 用 opaque 环形队列解决同类问题（见 FAQ 4）。

## 8. 深挖方向

1. **frame-thread 与 wrapper 的交互**：`ff_encode_preinit` 里的 `ff_frame_thread_encoder_init`（`encode.c:980-984`）与 `AV_CODEC_CAP_OTHER_THREADS` 的取舍——x264 声明 OTHER_THREADS（库内自带线程池），FFmpeg 是否还会在外层再包一层 frame-thread（`encode.c:373-376` 的 `ff_thread_video_encode_frame` 分支）？两套线程叠用时的 pts 一致性值得实测。
2. **`x264_encoder_reconfig` 热更新路径**：`reconfig_encoder`（`libx264.c:195-240`）+ `X264_reconf`/`ff_encode_reconf_parse_dict`（`:770-781`、`encode.c:599`）+ `VER` 运行期选项三者如何协同，crf 运行期修改的生效时机。
3. **RECON_FRAME 调试特性**：`X264_frame` 里把 `pic_out` 重构像素借回 `avci->recon_frame`（`libx264.c:638-663`）及 `csp_to_pixfmt` 的逆映射（`:313-333`），可与 ffprobe 的 debug 编码流程串讲。
4. **HDR/动态元数据透传全家桶**：x264 的 `CONFIG_LIBX264_HDR10`（master-display/CLL 进 param，`libx264.c:1011-1084`）对比 x265 的字符串化 `master-display`（`libx265.c:192-252`）与 DOVI RPU 生成（`:847-864`），可做 HDR 封装专题。
5. **`x264opts` 解析器的边界**：`sscanf("%4095[^:=]=%4095[^:]")`（`libx264.c:1384`）对含 `:` 值（如某些 SAR/分析串）的处理缺陷，以及为何新代码推荐 `x264-params` 字典。
