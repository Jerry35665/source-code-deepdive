# 第 09 章 · 网络流协议:RTMP 握手、HLS 状态机与 DASH 时间轴

> 基线:commit `9f63b36a`。行号以 libavformat/ 为准。本章纠正一个流传极广的旧认知:**当前代码中 hls/dash 都不是 URLProtocol**——HLS 的 `hls://` 协议早已移除(hls.c 只注册 `ff_hls_demuxer`,hls.c:3178),DASH 同构(dashdec.c:1962-1964)。

## 9.0 全景:所有传输都是一张回调表

FFmpeg 没有"网络模块"这个概念。RTMP、HTTP、TCP 与 file、pipe 一样,都是 `URLProtocol` 回调表的一个实例:

```c
/* libavformat/url.h:53-99(节选) */
typedef struct URLProtocol {
    const char *name;
    int     (*url_open2)(URLContext *h, const char *url,
                         int flags, AVDictionary **options);
    int     (*url_read)(URLContext *h, unsigned char *buf, int size);
    int64_t (*url_seek)(URLContext *h, int64_t pos, int whence);
    int     (*url_close)(URLContext *h);
    int     (*url_read_seek)(URLContext *h, int stream_index,
                             int64_t timestamp, int flags); /* RTMP 用 */
    int     (*url_read_pause)(URLContext *h, int pause);
    int flags;              /* 协议能力声明(网络/目录/嵌套) */
} URLProtocol;
```

`URLContext` 上挂着两个全局可控点:用户中断回调与读写超时(url.h:44-45)。整条链路:

```
avformat_open_input("rtmp://host/app/stream")
        │
┌───────▼───────────────────────────────────────────┐
│ 第一层 URLProtocol(protocols.c 注册表)           │
│   file │ tcp │ http │ rtmp │ crypto │ data │ ...  │
│   协议可嵌套:crypto+http(url.h:32 NESTED_SCHEME)│
└───────┬───────────────────────────────────────────┘
        │ ffio_fdopen(avio.c:470-527)
┌───────▼────────┐
│  AVIOContext   │ 所有阻塞读汇聚于 retry_transfer_wrapper
└───────┬────────┘
        │
┌───────▼───────────────────────────────────────────┐
│ 第二层 demuxer                                    │
│  mpegts(m3u8/hls 场景)│ flv(rtmp 场景)│ dashdec│
│  hls/dash:自建内存 AVIOContext + 自管拉流回调    │
└───────────────────────────────────────────────────┘
```

本章先给三个结论:①中断与超时只有一个汇聚点(9.1);②RTMP 把直播协议伪装成"一个可读的文件"(9.2);③HLS/DASH 把"分片下载"实现成 demuxer 的自定义读回调(9.3/9.4)。

## 9.1 唯一汇聚点:retry_transfer_wrapper

用户取消(`AVIOInterruptCB`)和 `rw_timeout` 不是每个协议各自实现的——所有阻塞读最终进同一个循环(libavformat/avio.c:571-614):

```
/* 骨架,avio.c:581-601 */
while (ret < 0) {
    if (ff_check_interrupt(&h->interrupt_callback))
        return AVERROR_EXIT;              /* :582 用户回调即断 */
    ret = h->prot->url_read(...);
    if (ret == EAGAIN) {
        if (fast_retries--) continue;     /* 先快速重试数次 */
        if (now - wait_since > rw_timeout)
            return AVERROR(EIO);          /* :595-600 超时判死 */
        av_usleep(1000);                  /* 1ms 粒度轮询 */
    }
}
```

三个细节:

1. `ffurl_read2` 要求"至少读 1 字节",`ffurl_read_complete` 要求"读满 size"(avio.c:616,625)——上层 demuxer 依赖后者保证包完整性;
2. TCP 层另有 `SO_RCVTIMEO` 兜底(tcp.c:174-176,275),avio 层的轮询计时是第二道闸;
3. `url_open2` 优先于 `url_open`(avio.c:249-254),协议嵌套(`crypto+http`、`tls+tcp`)由此实现——这是 HLS 加密分片的基石。

## 9.2 RTMP:一场伪装成文件的协议对话

### 握手

`rtmp_handshake`(libavformat/rtmpproto.c:1264-1458)是 1536 字节×3 的混沌版:

```
客户端                         服务器
  │── C0(0x03)+C1(1536B) ────→│  :1314
  │←── S0+S1(1536B) ──────────│  :1320
  │←── ... 收 C2 验证 ─────────│  :1326
  │  digest 偏移取 772/8 两试   │  :1336-1353
  │  HMAC 签名不符 → EIO       │  :1387-1390
  │── C2(带签名回写) ─────────→│  :1416
  │  老服务器:S1 原样回传分支   │  :1427-1446
```

签名校验失败直接返回 EIO——FFmpeg 不给"降级尝试"留机会,因为 Adobe 官方握手本身就定义了两种(带 digest 的 FP9+ 与明文老式),分支(:1427-1446)覆盖后者。

### 命令链:connect → createStream → play/publish

握手之后是一串 AMF0 编码的 RPC,由 `handle_invoke_result`(rtmpproto.c:2132-2202)按返回结果接力驱动:

```
connect 的 _result 到达 ──→ 发 WindowAckSize + createStream (:2154-2158)
createStream 的 _result ──→ getStreamLength + play + bufferTime (:2185-2190)
推流侧(_result 前置)  ──→ releaseStream + FCPublish (:2148) → publish (:2181)
live==-1(Edge 服务器) ──→ 追加 FCSubscribe (:2167)
```

### chunk 分块与"半成品"状态

RTMP 把消息切成 chunk 复用单条 TCP。`ff_rtmp_packet_read`(libavformat/rtmppkt.c:276-292)的核心是**每 channel 一份半成品缓存 `prev_pkt[]`**:单次只读 `FFMIN(剩余量, chunk_size)`,没读完就挂回缓存并返回 EAGAIN,外层循环(rtmppkt.c:298-311)反复驱动直到消息完整。默认 chunk size 128(rtmpproto.c:2779-2780),对端发 `SetChunkSize` 消息时由 `handle_chunk_size` 更新并回显(rtmpproto.c:1575-1607)。

### 直播输出为什么伪装成 FLV

RTMP 消息格式与 FLV tag 几乎同构,于是 `url_open` 时直接预造 13 字节 FLV 头(rtmpproto.c:2941-2947),`append_flv_data` 把收到的 chunk 重排成 FLV tag(rtmpproto.c:2296-2332),`rtmp_read` 搬运缓冲(rtmpproto.c:2992-3017)。**上层 flv demuxer 读 `rtmp://` 与读一个 `.flv` 文件完全无感**。seek 也被协议化:`gen_seek` 置 `STATE_SEEKING` 后吞掉服务器回放快进期间的包(rtmpproto.c:3019-3038,2542-2547)。

## 9.3 HLS:一个自己造字节的 demuxer

### 结构反转:demuxer 内部再起 AVIO

用户打开的是 `https://.../index.m3u8`,probe 命中 HLS demuxer。它内部用 `ffio_init_context` 造一个**内存 AVIOContext**(hls.c:2449-2450),其读回调 `read_data_continuous`(hls.c:1761)完成真正的网络工作:

```
mpegts 子 demuxer ──读──→ 内存 AVIOContext(无上限缓冲)
                              ↑ read_data_continuous(hls.c:1761)
                              │
                    reload playlist(过期时)→ 选下一个分片
                    → avio_open(分片 URL)→ 边下边喂 → 跨分片续读
```

这就是"demuxer 内部再起 AVIO"的真实形态:不是递归 open m3u8,而是**把分片流无缝拼接成一条连续字节流**。

### playlist 解析与 reload 状态机

`parse_playlist`(hls.c:830-1186)单函数解析主/媒体两级 playlist:`EXT-X-KEY`(:917)、`EXT-X-MAP`(fMP4 初始化段,:972,无 IV 默认取序列号 :987)、`ENDLIST`→finished(:1029)、`EXTINF`(:1032)。直播核心在 `reload_playlist`(hls.c:1684-1759):

- reload 间隔 = 末分片时长(:1631),失败则间隔减半(:1726);
- 一轮无新分片,`m3u8_hold_counters` 计数,到 1000 判 EOF(:1738-1741);
- 等待期间 100ms 粒度轮询且每轮检查 interrupt 回调(:1748-1752)。

VOD 与直播的起点差异:直播起播 `live_start_index` 默认 -3——从倒数第三个分片开始(:2118-2123),这是"追直播要留缓冲余量"的行业惯例在代码里的位置。多码率不做带宽探测,而是 `AVProgram`+`AVDISCARD` 标记驱动(:2385-2393):用户 set discard 后,`playlist_needed` 判定哪些子 playlist 可以停止下载(:1638-1682)。

### 加密分片:能下沉就不自己做

AES-128 分片 FFmpeg **不自己解密**,而是把 URL 包装成 `crypto://` 交给 crypto 协议下沉处理(hls.c:1528-1544)——复用 9.1 的协议嵌套机制。只有 SAMPLE-AES(fMP4/samples 级加密)才在包级由 `hls_sample_encryption.c` 处理(hls.c:2807-2812)。

### HLS 的 seek

`hls_read_seek`(hls.c:2934-3092):目标超出已缓存窗口先强制重拉 playlist(:2966-2984);`AVSEEK_FLAG_BACKWARD` 时吸附到分片起点(:3002-3008);随后**关闭当前连接并对所有 playlist 执行 `ff_read_frame_flush`**(:3026-3047)——状态机复位,下一读重新进入 reload 循环。

## 9.4 DASH:把 MPD 编译成时间轴

调用链(dashdec.c):`parse_manifest`(:1271,MPD type=dynamic → is_live :1330)→ `parse_manifest_representation`(:899,`SegmentTemplate` :985 / `SegmentTimeline` :1047-1063 / `SegmentList` :1078)→ `calc_cur_seg_no`(:1445,直播 timeline 模式取**末端前 60 秒** :1457)→ `get_current_fragment`(:1654,模板填参 `ff_dash_fill_tmpl_params` :1725)→ `read_data`(:1848,先吐 init 段 :1888,单段 EOF 后序号 ++ :1909)。

与 HLS 的结构差异:DASH 用 `$Time$/$Number$` 模板算出分片 URL,不需要逐分片重载 manifest(直播 timeline 模式除外),所以其 reload 压力小于 HLS——**HLS 把状态放在服务器文本里,DASH 把状态物化在客户端时间轴上**。

## 9.5 mux 侧:hlsenc 与 dashenc 的切割器

写直播流的本质是"编码器输出 → 按规则切割 → 原子替换清单":

| | HLS(hlsenc.c) | DASH(dashenc.c) |
|---|---|---|
| 切割点 | 视频关键帧(:2492-2495)且累计时长 ≥ hls_time(:2469,2519-2521;默认 2s :3141) | 关键帧且 elapsed ≥ seg_duration(:2049-2051;默认 5s :2281) |
| 清单 | `hls_window`(:1547)算 target_duration(:1600),逐分片 `ff_hls_write_file_entry`(hlsplaylist.c:144) | flush 各流后 `write_manifest`(:1919-1922;音频先 `dash_flush` 同步 :1829-1839) |
| 原子性 | 写 `.tmp` 再 rename(:1679-1683) | 同为临时文件+替换 |
| 滚动窗 | hls_list_size 默认 5,摘头同时删分片文件(:1123-1136) | window_size + extra_window_size 清理(:1879-1886) |

注意切割判定"关键帧 **且** 时长达标"——只有后者会导致非关键帧起始分片,播放端将花屏;这是两个 muxer 共同的硬约束,也是直播切片必须配 GOP 对齐的原因。

## 9.6 设计动机

1. **协议=回调表**:把传输与格式正交,`avformat_open_input` 对 `file://` 与 `rtmp://` 一视同仁。代价是 RTMP 这类有状态协议必须把会话藏在 URLContext 私有数据里,`url_read_seek` 这种协议级 seek 才需要加进回调表(url.h:79);
2. **中断必须全局可达**:网络栈任何一层都可能阻塞 30 秒,于是检查点收敛到一个函数(9.1)——这是"资源取消"问题的标准解法:与其在 20 处轮询,不如让所有阻塞收口;
3. **HLS/DASH 选 demuxer 而非协议**:因为它们的输出是"流"而协议层只会给"字节"。分片边界、加密、多码率都是**格式语义**,塞进 URLProtocol 会破坏抽象;
4. **能复用就下沉**:AES-128 交给 crypto 协议、TS 解析交给既有 mpegts demuxer——HLS demuxer 自己只写"状态机",不写"格式"。

## 9.7 FAQ

**Q1:为什么我的 interrupt_callback 在 connect 阶段也能生效?**
因为建连后的每次阻塞读都过 retry_transfer_wrapper,第一件事就是查回调(avio.c:582)。但 DNS 解析阶段不经过它——那是 getaddrinfo 的阻塞,FFmpeg 管不到。

**Q2:rw_timeout 和 TCP SO_RCVTIMEO 什么关系?**
双保险。avio 层以 1ms 粒度计时判 EIO(avio.c:595-600),TCP 层 SO_RCVTIMEO 兜底(tcp.c:174-176,275)。前者可跨协议统一,后者防内核态挂死。

**Q3:还有 hls:// 协议吗?**
没有。hls.c 只注册 demuxer(hls.c:3178)。打开 `https://.../m3u8` 靠格式探测命中,分片下载走通用 http 协议。

**Q4:HLS AES-128 密钥谁拿、谁解密?**
demuxer 只负责把 key URL 和 IV 拼进 crypto URL(hls.c:1528-1544),解密在 crypto 协议内完成。SAMPLE-AES 是包级加密,才由 hls 自己解(:2807-2812)。

**Q5:直播 HLS 怎么判断"主播下播了"?**
playlist 出现 ENDLIST 置 finished(hls.c:1029);没出 ENDLIST 但连续 1000 轮无新分片也判 EOF(:1738-1741)——防止服务器挂了导致无限等待。

**Q6:为什么 RTMP 拉流输出长得像 FLV?**
RTMP 消息与 FLV tag 同构,rtmpproto 预造 FLV 头并把 chunk 重排为 FLV tag(rtmpproto.c:2941-2947,2296-2332),上层直接用 flv demuxer 消费,零解析成本。

**Q7:RTMP 握手校验失败会自动降级吗?**
不会,HMAC 不符直接 EIO(rtmpproto.c:1387-1390)。老式明文握手走独立分支(:1427-1446),那是协议定义的两种模式,不是错误恢复。

**Q8:live_start_index 为什么默认 -3?**
从倒数第三个分片起播(hls.c:2118-2123):新分片还在增长,从最末尾开始会立刻触发边界竞争;留两个分片余量是直播延时与起播速度的折中。

**Q9:DASH 直播从哪个分片开始播?**
timeline 模式取最末端分片再回退 60 秒(dashdec.c:1457)——与 HLS 的 -3 分片同一思想,只是计量单位换成了秒。

**Q10:FFmpeg 切 HLS 时音频分片为什么和视频不完全同步?**
切割只在视频关键帧判定(hlsenc.c:2492-2495),音频流被动跟随;`dash_flush` 专门在 flush 时把音频凑齐(dashenc.c:1829-1839),HLS 则靠 `split_by_time` 等选项近似对齐。

## 9.8 小结与深挖方向

本章结论:**网络栈 = 一张 URLProtocol 回调表 + 一个唯一中断/超时汇聚点 + "协议伪装成文件"与"分片流伪装成字节流"两种伪装术**。深挖:

1. crypto 协议的 AES-CBC 流式解密如何处理分片边界重置 IV;
2. RTMPT(HTTP 隧道 RTMP)把二进制消息 base64 后的吞吐损失;
3. HLS 幕后:ID3 时间戳拦截用于多码率切换时的跨流同步;
4. rtmp_write 把 FLV 反解回 chunk 的推流路径(rtmpproto.c 对称实现);
5. `AVDISCARD` 驱动多码率切换时,已在下载的分片如何被 `playlist_needed` 优雅中止。
