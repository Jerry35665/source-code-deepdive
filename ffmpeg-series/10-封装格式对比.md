# 第 10 章 · 封装格式三方对比:MKV 语法表、TS 统计流、MOV 坐标系

> 基线:commit `9f63b36a`。行号以 libavformat/matroskadec.c、mpegts.c、mov.c 为准。首卷 02 章讲过 MP4 盒子解析的入口流程,本章以**三方横向对比**为纲,不再单讲 MOV 基础。

## 10.0 全景:三种哲学

| 维度 | MKV(matroskadec.c) | TS(mpegts.c) | MOV(mov.c) |
|---|---|---|---|
| 结构哲学 | 递归自描述元素 | 无元数据统计流 | 全量坐标系查表 |
| 索引 | 尾部 Cues(惰性解析) | 无(边播边建) | stbl 六表(启动即展开) |
| seek 精度 | cluster 级+关键帧门控 | 线性扫描 | 单样本级 O(log n) |
| 错误恢复 | 滑窗重同步 | 0x47 逐字节 resync | 依赖盒子结构完整 |
| 时间戳 | 纳秒(1/1e9) | 90kHz/33bit 回绕 | 每轨 timescale+ctts+elst |
| 多轨/附件 | 全能(字幕/附件/章节) | 复用 PID,无附件 | 有,但弱于 MKV |
| 典型场景 | 收藏/母版 | 广播/直播传输 | 剪辑/分发母版 |

一句话:**MKV 靠语法表向后兼容,TS 靠统计对抗丢包,MOV 靠物化索引换取随机访问**。三个 demuxer 的入口分别是 `matroska_probe`/`mpegts probe`/`mov_probe`,但真正的性格差异在解析循环内部。

## 10.1 MKV:一张静态语法表驱动的递归下降

EBML 的根基是变长整数:**首字节前导 0 的个数定长度**(ebml_read_num,matroskadec.c:914)。整个 demuxer 绕一张静态 `EbmlSyntax` 表递归下降,元素解析、默认值、子表挂接全部数据化——**新增一个元素只需要加一行表项,不改代码**。

时间基是 MKV 的标志性决定:每轨 `avpriv_set_pts_info(st, 64, scale×track_scale, 1e9)`(matroskadec.c:3294-3295)——**全程 64bit 纳秒**。时间戳永远够用,代价是与其他格式交互时处处要做有理数缩放(首卷 04 章的 av_reduce)。

两个反直觉设计:

1. **Cues(索引)在 header 阶段被跳过**,首次 seek 才回尾解析(matroskadec.c:1984-1986,4510-4514)——顺序播放永远不付索引解析成本;
2. 容错用 `matroska_resync`:失步后逐字节滑动,匹配 8 个顶层元素 ID 之一才重新同步(matroskadec.c:867-899)——比 TS 粗糙,因为 EBML 本来就不是为丢包设计的。

## 10.2 TS:没有元数据的统计流

TS 没有"文件头"。probe 靠统计:在 188/192/204 三种步长下检查 0x47 同步字节的命中率(mpegts.c:3470,3485-3488)——**格式身份 = 采样假设的验证**。

轨道发现是动态的:PAT/PMT 周期性重发,demuxer 置 `AVFMTCTX_NOHEADER` 随时新增流。PES 重组是三态状态机(mpegts_push_data,mpegts.c:1224,1262,1356-1364):找 `00 00 01` 前缀 → 解 header → 收 payload;PTS/DTS 是 33bit 的 `ff_parse_pes_pts` 装配(libavformat/mpeg.h:69)。

33bit@90kHz 约 26.5 小时回绕一次。TS demuxer 的处理方式极简:**声明 33bit 时间基 + 打 `AVFMT_TS_DISCONT` 标志**(mpegts.c:3880),把不连续的裁决上交通用层——细节留给第 13 章。

最重要的结构事实:`ff_mpegts_demuxer` **没有 read_seek,只有 read_timestamp=mpegts_get_dts**(mpegts.c:3877-3889,3783)——TS 的 seek 能力完全来自通用层的二分扫描机制,见 10.4。

## 10.3 MOV:先建坐标系,再读数据

`mov_read_default` 递归遍历盒子,深度上限 10,未注册 tag 直接 `avio_skip` 跳过(mov.c:10126,10132-10135,10209)——**未知盒子无害**是 MOV 演进性的来源(每一代新盒子老播放器都跳得过)。

moov 读完后 `mov_build_index` 把 stbl 六表物化为每轨的 sample 数组(mov.c:4960,5058):时间→字节、序号→大小、关键帧表一次展开。此后**读包即寻址**:按当前 sample 的偏移直接 `avio_seek`(mov.c:12124)。这是三种容器里唯一"启动时全量建坐标系"的:moov 在文件尾的 MP4(未 faststart)必须先回卷重扫,首卷 05 章的 faststart 两遍空写正是为消掉这次回扫。

时间戳三件套:每轨独立 timescale;`ctts` 给 B 帧合成 DTS→PTS 偏移;`elst` 编辑列表做起点平移——首项空编辑把初始 DTS 平移,AAC priming 样本转为 `initial_padding`(mov.c:6735,4977-5024)。**MOV 是唯一需要"编辑列表"概念的**:剪辑软件的入点信息被编码进时间轴本身。

## 10.4 seek 三方对比:精确度与成本的倒挂

```
MOV  mov_read_seek(mov.c:12394)
     └→ stbl 索引二分(mov_seek_stream :12320)+ 关键帧回退(:12327)
        O(log n),精确到单样本
MKV  matroska_read_seek(matroskadec.c:4501-4566)
     └→ 首次:回尾解析 Cues → cluster 级定位 → 关键帧门控
        失败则退回 generic 扫描(:4557-4560 注释明示兜底)
TS   无 read_seek
     └→ 通用层 ff_seek_frame_binary:read_timestamp 边读边建索引
        (seek.c:630-633 + mpegts.c:3810-3811),首次 seek = 线性读
```

**seek 能力排序 MOV > MKV > TS,恰好与错误恢复能力排序 TS > MKV > MOV 相反**:索引与鲁棒性争夺同一份"元数据冗余"预算。TS 把预算全花在周期性重发(PAT/PMT 每 0.1s 量级重复),MOV 花在一次性大索引,MKV 折中——索引放文件尾,丢了也能顺序播。

## 10.5 设计动机

1. **TS 为信道而生**:卫星/有线链路随时丢包、观众随时加入。所以没有索引(加不进去)、没有文件头(接不中途)、包定长(断点重同步 O(1))。188 字节是 ATM 信元(53×4≈212)减去 RS 前向纠错开销的历史残留,但**定长本身**才是鲁棒性的来源;
2. **MOV 为剪辑而生**:非线性编辑要求任意精度跳转,所以把时间↔字节映射完全物化;代价是索引必须先于媒体可得(moov 前置),以及"编辑列表"这种面向时间轴操作的语义层;
3. **MKV 为收藏而生**:目标是"一个文件装下一切并永不失配"——EBML 递归让未来元素可被跳过,纳秒时间基让任何采样率整除,附件系统直接把字体/封面塞进容器。它不追求任何场景的最优,追求所有场景的不落后;
4. **probe 的三副面孔**:MKV 靠魔数(EBML 头),MOV 靠盒子 tag 遍历,TS 靠统计命中率——探测策略是格式哲学的第一面镜子。

## 10.6 FAQ

**Q1:为什么 TS 包是 188 字节?**
ATM 时代按信元封装倒推:4×47=188 恰好装进 ATM 载荷。工程上真正重要的是"定长"——任意字节流以 188 取模即得候选包头,重同步 O(1)。

**Q2:FFmpeg 怎么区分 TS 与 MPEG-PS?**
probe 在 188/192/204 步长下统计 0x47 命中率(mpegts.c:3470,3485-3488)。192 是 M2TS(BDAV)的变体,204 是加 RS 纠错的广播流。

**Q3:MKV 文件第一次 seek 为什么明显卡顿?**
Cues 在 header 阶段被跳过(matroskadec.c:1984-1986),首次 seek 才回文件尾解析(:4510-4514)。网络播放场景这一次回扫可能要重新拉数据。

**Q4:TS 播放中途出现新节目怎么办?**
PAT/PMT 周期重发,demuxer 以 AVFMTCTX_NOHEADER 模式运行,随时追加流。这也是 TS 不能预知总时长/总轨数的根源。

**Q5:33bit 时间戳回绕谁处理?**
TS demuxer 只声明 33bit 时间基并打 AVFMT_TS_DISCONT(mpegts.c:3880),回绕补偿在通用 demux 层做——格式层不藏策略。

**Q6:ctts 和 elst 分别解决什么?**
ctts 是 B 帧的合成偏移(解码序→显示序);elst 是编辑列表,mov.c:6735,4977-5024:空编辑平移初始 DTS,AAC priming 样本转成 initial_padding,让"剪辑入点"成为时间轴事实。

**Q7:三种格式哪个最能装字幕和附件?**
MKV:原生 attachments/章节/多字幕轨(matroskadec.c:3508-3551);MOV 支持但还是时间轴中心;TS 基本没有容器级附件,字幕只能走 DVB/ARIB 子流。

**Q8:MOV 遇到不认识的盒子会失败吗?**
不会,mov_read_default 对未注册 tag 直接 avio_skip(mov.c:10209),递归深度上限 10(:10132-10135)防栈溢出。这是 MOV 二十年向前兼容的机制基础。

**Q9:为什么 MOV 读包有时还会触发 avio_seek?**
因为"读包即寻址"(mov.c:12124):stbl 展开后每个 sample 的偏移独立,多轨交错不保证单调,按需跳转是坐标系模型的一部分。

**Q10:MKV 的 resync 和 TS 的 resync 差在哪?**
TS 匹配单字节 0x47,毫秒级恢复(mpegts.c resync);MKV 滑窗匹配 8 个顶层元素 ID(matroskadec.c:867-899),粒度粗——但 MKV 面向本地文件,失步本身已属异常。

## 10.7 小结与深挖方向

本章结论:**容器的性格 = 它把"元数据预算"花在哪里**——TS 花在重发,MOV 花在索引,MKV 花在自描述。深挖:

1. EBML 无限长度元素(unknown-size)的终止判定与 MKV 的流式写入;
2. TS 的 204 步长(RS 纠错)与 192 步长(M2TS)在 probe 统计中的优先级仲裁;
3. mov elst 完整模型(多段编辑/空编辑/轨间偏移)与剪辑软件行为的对齐;
4. SimpleBlock 的 keyframe/discard 标志位如何参与 MKV seek 门控;
5. 三格式元数据模型对比:MKV Tags → MOV udta/ilst → TS 几乎为零,对播放器 UI 的反向塑造。
