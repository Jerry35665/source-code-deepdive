# 第 26 章 · 硬件后端补全:QSV、MediaCodec、D3D12VA 与 AMF

> 基线:commit `9f63b36a`。行号以 libavcodec/、libavutil/hwcontext_*.c 为准。12 章讲了 VAAPI/NVDEC/VideoToolbox 三后端与协商链——本章讲剩余主要后端如何实现**同一套 hwaccel 接口**,只讲差异。两处勘误:①AMF 不是"只有编码",树中有 h264/hevc/vp9/av1 四个 AMF 解码器(amfdec.c:840-843,configure 帮助文本仍是旧话 :351);②QSV/AMF/MediaCodec 严格说不是 hwaccel,是 **wrapper 解码器**。

## 26.0 全景:接口形态的分裂

12 章的三个后端都是真 hwaccel(挂 `AVCodec.hwaccel`,走 12.1 协商链的逐帧三回调)。本章四家的形态不同:

| 后端 | 形态 | 平台 | 原生帧对象 |
|---|---|---|---|
| QSV | wrapper(独立 `h264_qsv` 等) | Intel 全平台 | mfxFrameSurface1(VASurface 包装) |
| MediaCodec | wrapper(`xxx_mediacodec`) | Android | Surface buffer(令牌) |
| AMF | wrapper(`xxx_amf`) | AMD | AMFSurface(SDK 内池) |
| D3D12VA | **真 hwaccel** | Windows | ID3D12Resource 纹理 |

关键概念:wrapper 解码器也调 ff_get_format(12 章),但返回值只决定"**出 hw 帧还是系统内存帧**"——不经过 hwaccel 的 start/decode_slice/end_frame 三回调,整个解码循环在 SDK 内部。**接口的语法相同,语义分叉**:hwaccel 是"框架驱动 SDK",wrapper 是"SDK 驱动框架"。

## 26.1 QSV:跨后端网关的标本

QSV 的独特性:**mfx 在 Linux 上没有自有设备层**,必须网关到 VAAPI。建链(qsv.c):

1. 平台判定:`AVCODEC_QSV_LINUX_SESSION_HANDLE` 仅 `CONFIG_VAAPI && !_WIN32` 定义(qsv_internal.h:26-28);
2. 网关核心:创建 VAAPI 子设备并**强制 vendor_id=0x8086、driver=iHD**,再 `MFXVideoCORE_SetHandle(MFX_HANDLE_VA_DISPLAY)`(qsv.c:471-474)——QSV 在 Linux 上就是"iHD 驱动的 VAAPI 加了一层会话管理";
3. 子 session 经 `MFXJoinSession` 挂到父 session(≥1.25,qsv.c:1092-1097)。

内存模型:表面池直接建在 child VAAPI 设备上(VASurfaceID 包成 mfxHDLPair)——**QSV↔VAAPI 的 map/derive 只是拆包贴标签**,零真拷贝。池大小:oneVPL 2.9+ 且非 D3D9 时 `initial_pool_size=0`(动态池,qsvdec.c:344-347),否则 `suggest_pool_size+16+extra_hw_frames`。同步模型:解码异步,sync point 入 fifo,**只有系统内存输出才当场 SyncOperation**(qsvdec.c:883-887)——hw 帧输出时同步责任转给消费者(与 12 章 VT 的"收干"策略相反:QSV 把异步留给下游)。opaque 模式仅旧 MediaSDK 有效,oneVPL 已废弃。

## 26.2 MediaCodec:Surface 令牌模式

Android 后端的硬件现实:**解码器输出直接进 Surface(显示层),像素根本不经过 CPU**。configure 时一次定型输出模式:`ff_AMediaCodec_configure(codec, format, s->surface, NULL, 0)`(mediacodecdec_common.c:854)——传 surface 即 Surface 模式,否则 Buffer 模式(可回读像素)。

Surface 模式的帧是**令牌而非像素**:`data[3]` 指向 AVMediaCodecBuffer(mediacodecdec_common.c:352;mediacodec.c:88-118),帧里没有可下载的位图;上屏靠公开 API `av_mediacodec_render_buffer`——这就是 12 章提过的 AD_HOC config 方法存在的真实原因(该后端的"帧"语义由外部渲染契约定义)。wrapper 有 JNI/NDK 双实现;`setAsyncNotifyCallback` 已实现但树内无人调用——**解码是同步轮询**,异步性靠下游渲染时机自然发生。hwcontext 是纯 surface 载体、无 frames 方法(没有池可管,Buffer 由 MediaCodec 系统 service 分配)。

## 26.3 D3D12VA:显式同步的后现代后端

D3D12 没有隐式同步,一切并行必须显式屏障——这个后端是"命令队列哲学"的教学样本:

- 解码走**专用 VIDEO_DECODE 队列**+命令列表+显式 barrier;
- 每帧提交尾:DecodeFrame→Close→ExecuteCommandLists→**Signal 两把 fence**(帧 fence+全局 fence,d3d12va_decode.c:667-680);
- **帧级 fence 在纹理被复用时才等**(:644)——同步点后移到资源生命周期边界,而非解码完成点;
- 下载走 COPY 队列 + `ID3D12CommandQueue_Wait`(hwcontext_d3d12va.c:558):**GPU 等 GPU,CPU 不阻塞**。

码流结构复用 dxva2_internal.h(D3D12 的解码 API 本来就是 DXVA 的 D3D12 化);tier<2 的设备直接拒绝。

## 26.4 AMF:SDK 内池与事件状态机

AMF(AMD)四个解码器在树(h264/hevc/vp9/av1,amfdec.c:840-843)。组件事件模型:SubmitInput(池满返回 NO_FREE_SURFACES 自旋重试)/QueryOutput/Drain 状态机——与 QSV 的 sync fifo、MediaCodec 的轮询又是一种驱动形态。**表面池在 SDK 内部**(36+可扩展、上限 100),FFmpeg 的 hwframes 池只是 dummy 占位——12 章"池策略"一表的第四种答案:池完全外置。

## 26.5 设计动机

1. **两种形态对应两种上游架构**:SDK 自己有完整解码管线(QSV/MediaCodec/AMF)→wrapper;SDK 只提供"逐帧解码原语"(VAAPI/NVDEC/VT/D3D12)→hwaccel。FFmpeg 不强迫任何一方改造;
2. **QSV 网关是平台妥协的活化石**:Intel 一套 API 跨三 OS,但 Linux 底层必须落到 VAAPI——适配层里藏着一个"默认驱动+厂商 ID"的硬编码(qsv.c:471-474),开源驱动生态的现实浓缩;
3. **MediaCodec 的令牌帧是零拷贝的尽头**:像素从未存在于 CPU 地址空间,"帧"退化为 buffer 句柄+渲染契约——对比 12 章 NVDEC 的 CUdeviceptr(至少还在 GPU 地址空间),Android 的 Surface 模式连地址空间都放弃了;
4. **D3D12 的显式同步反哺了理解**:12 章三个后端的"隐式同步"其实是驱动在替你排 barrier——D3D12VA 把这些写明,是学习 GPU 同步的最好教材。

## 26.6 FAQ

**Q1:h264_qsv 和 h264(VAAPI 硬解)什么关系?**
两个独立实现:前者 mfx 管线(内部仍走 iHD/VAAPI 硬件),后者标准 hwaccel。同一硬件,两种驱动路径,选一即可。

**Q2:QSV 在 Linux 上还需要装 Media SDK 吗?**
oneVPL 运行时即可;底层驱动是 iHD(VAAPI)——qsv.c:471-474 硬编码了这一组合。

**Q3:MediaCodec 的帧能下载成像素吗?**
Surface 模式不能(data[3] 只是令牌);要像素用 Buffer 模式(configure 时不传 surface,:854)。

**Q4:为什么 MediaCodec 没有帧池?**
Buffer 由系统 service 管理,FFmpeg 侧 hwcontext 无 frames 方法——12 章池策略表的第五种:无池。

**Q5:D3D12VA 解码会阻塞 CPU 吗?**
下载路径 GPU 等 GPU(CommandQueue_Wait,:558);提交本身异步,fence 等待发生在纹理复用时(:644)。

**Q6:AMF 能解码 AV1 吗?**
能,树中四个 AMF 解码器含 av1(amfdec.c:840-843);configure 帮助文本的"仅编码"是陈旧措辞。

**Q7:wrapper 解码器会走 get_format 协商吗?**
会,但语义收窄:只决定输出是 hw 帧还是系统内存——不触发 hwaccel 三回调。

**Q8:QSV 的池为什么 oneVPL 2.9+ 后归零?**
动态池由 SDK 内部管理(qsvdec.c:344-347);旧路径需 FFmpeg 预分配并加 16 余量。

**Q9:D3D12VA 与 dxva2/d3d11va 什么关系?**
码流结构同源(dxva2_internal.h);D3D12VA 是新队列模型,旧后端是 D3D11/9 设备接口。

**Q10:四个后端哪个 flush 语义最完整?**
QSV(有真 session 排水);MediaCodec/AMF 靠 SDK 的 flush 原语包装;D3D12VA 走 hwaccel 通用路径。

## 26.7 小结与深挖方向

本章结论:**后端家族的真正分界是"框架驱动 SDK 还是 SDK 驱动框架"**;QSV 网关、MediaCodec 令牌帧、D3D12 显式同步、AMF 外置池——四种形态四种哲学。深挖:

1. qsv.c 网关的 vendor/driver 硬编码(:471-474)对非 Intel VAAPI 设备的误配风险;
2. MediaCodec 异步回调模式(setAsyncNotifyCallback)若启用的框架改造量;
3. D3D12VA 帧 fence 延迟等待(:644)在多路并发解码的吞吐收益;
4. AMF NO_FREE_SURFACES 自旋 vs QSV fifo 的背压形态对比;
5. wrapper 后端与 12 章 hwaccel 在 ff_get_format 剔除重试(decode.c:1348-1357)中的行为差。
