# 第 11 章 · 字幕与附件管线:不走 AVFrame 的第三种数据

> 基线:commit `9f63b36a`。行号以 libavformat/、libavcodec/、libavfilter/、fftools/ 为准。

## 11.0 全景:字幕在 FFmpeg 中的三重身份

音视频数据的载体是 AVPacket→AVFrame;字幕的载体是一条**旁路**:demuxer 产出普通 AVPacket,但解码产物是 `AVSubtitle`——一个带 rects 数组的独立结构,不是 AVFrame(libavcodec/avcodec.h:2088-2095)。

```
              ┌─ 文本(SRT/ASS/VTT)─→ SUBTITLE_TEXT / SUBTITLE_ASS rect
AVPacket ──→ │
              └─ 位图(DVD/PGS/DVB)──→ SUBTITLE_BITMAP rect(带调色板位图)

消费三路:
  A. 软字幕(流复制):packet 原样进 muxer
  B. 硬字幕:subtitles 滤镜(libass)自 demux+decode+渲染进视频帧
  C. 转封装/转码:avcodec_decode_subtitle2 → AVSubtitle → 再编码
     (CLI 用 AVBufferRef 把 AVSubtitle 挂进 AVFrame.buf[0] 过图,ffmpeg_dec.c:536)
```

`AVSubtitleRect` 的 type 三值定义在 avcodec.h:2041-2057(SUBTITLE_NONE/BITMAP/TEXT/ASS),rects 数组允许一帧多块——PGS 位图字幕天然多 rect,文本类恒为单 rect。

## 11.1 文本字幕的"一次读完"队列模式

SRT/ASS/VTT 三个 demuxer 共享 libavformat/subtitles.c 的全套实现,私有上下文只有一个队列(srtdec.c:30-32;assdec.c:31-34;webvttdec.c:35-39)。模式:

```
read_header:一次读全文件 → 逐条 insert → finalize
read_packet:av_packet_ref 出队(零解析)
read_seek :内存二分(subtitles.c:269-319)
```

**为什么必须全量读?** 文本字幕的包时长常常要靠"下一条的起点"反推——`ff_subtitles_queue_finalize` 用下一条 pts 给无时长包兜底(subtitles.c:222-224,函数体 212-228)。SRT 更微妙:数字行既可能是时间戳也可能是正文,解析器只能先缓存注释道破天机:"we can't be sure of this yet, so we cache it"(srtdec.c:175-182)。**不看后面就无法确定前面**——这是队列模式的逻辑必然,不是实现偷懒。

finalize 同时完成排序与去重,`queue_insert` 保证 O(log n) 有序插入(subtitles.c:111-154)。读取文本的基础设施 `ff_text_r8`(subtitles.c:65-84)统一处理 UTF-8 BOM 与换行归一。

## 11.2 AVSubtitle 解剖与解码入口

字幕解码不走 `avcodec_send/receive` 管线(首卷 03 章),而是同步回调 `avcodec_decode_subtitle2`(decode.c:935):

```c
/* decode.c(节选):回调填 AVSubtitle */
ret = cb.decode_sub(avctx, sub, &got_sub, pkt);
/* :975-980 duration 兜底 */
if (!sub->end_display_time && pkt->duration && got_sub)
    sub->end_display_time = pkt->duration * 1000 / ...;
/* :982-985 format 按 codec descriptor props 判定 */
```

三个语义:回调一次性填满 AVSubtitle;duration 缺失时用 packet 时长兜底;格式(TEXT vs ASS)按 `AVCodecDescriptor.props` 属性判定而非解码器自报——**能力声明集中在描述符表,一处查证**。

## 11.3 ASS 头部协商:extradata 里的样式表

ASS 不是纯文本流——它有 `[Script Info]`/`[V4+ Styles]` 样式头。FFmpeg 的契约:demuxer 把脚本头写进 extradata(assdec.c:160),decoder init 时拷给 `subtitle_header`(libavcodec/assdec.c:31-41),字段契约文档化在 avcodec.h:1732-1745。没有文件头时,`ff_ass_subtitle_header_full` 生成默认模板:PlayRes 384×288(libavcodec/ass.c:29-82,常量在 ass.h:28)——**384×288 是 VobSub 时代的遗产分辨率**,libass 按它缩放字体。

ASS 解码器本体是单函数直通:packet 字符串 → `ff_ass_add_rect2` 生成 SUBTITLE_ASS rect(libavcodec/assdec.c:43-62;恒置 ASS 类型:ass.c:151)。**FFmpeg 内部把所有文本字幕统一为 ASS 方言**,TEXT 类型仅在明确要求纯文本输出时由编码侧降级拆回(assenc.c:44 / srtenc.c:229)。

## 11.4 位图字幕:rect 的另一种填法

DVD 字幕(dvdsubdec.c:375-411):RLE 压缩位图 + 调色板,解码收尾强制**单 rect**,带 FORCED(强制显示)标志处理;PGS(蓝光,pgssubdec.c:531-590):窗口模型,**多 rect 循环**填一帧。位图字幕与文本的转码互通被 CLI 显式禁止(ffmpeg_mux_init.c:847-856)——位图栅格化后无法回到文本,单向转换才有意义。

## 11.5 附件管线:MKV 的"什么都装"

MKV attachments 在 demux 侧变成**流**:每个附件一条 `AVMEDIA_TYPE_ATTACHMENT` 流,内容进 `codecpar->extradata`(matroskadec.c:3537-3541);图片附件走 `ff_add_attached_pic` 复用为 `attached_pic` 封面图(:3533;该函数本体 demux_utils.c:110-143)。mux 侧对称:`mkv_write_attachments` 从 extradata 取回写出(matroskaenc.c:2513-2561,FileData 取 extradata :2550-2551)。

附件的最大用户是字幕:字体文件作为附件存进 MKV,`subtitles` 滤镜加载时判定 attachment 流并 `ass_add_font(extradata)` 注册进 libass(libavfilter/vf_subtitles.c:417-437,判定函数 :340-354)——**内嵌字体的硬字幕**由此成立:字幕样式不依赖系统字体库,容器自带排版环境。

## 11.6 CLI 的胶水:AVSubtitle 怎么过滤镜图

滤镜图节点间流动的是 AVFrame,AVSubtitle 进不去。fftools 的胶水是 `subtitle_wrap_frame`:把 AVSubtitle 挂进 `AVFrame.buf[0]` 的 AVBufferRef 硬塞过图(fftools/ffmpeg_dec.c:536-567)。代码注释直言这是权宜、未来应原生 AVFrame 化(:676-679)——字幕管线在 FFmpeg 里是**公认的待迁移技术债**。相关补丁还有 `fix_sub_duration`:字幕时长缺失时用下一帧到达时间回填(ffmpeg_dec.c:574-588),与 11.1 的 demux 侧兜底形成两道防线。

## 11.7 设计动机

1. **AVSubtitle 独立于 AVFrame 是历史决定**:1990 年代的字幕是 DVD 调色板位图,与"可泛化的媒体帧"模型不合——rects 数组天然多块、坐标以画布像素计、没有时间基只有 display 时窗。迁移到 AVFrame 的成本主要在 API/ABI,而非数据模型;
2. **全量读是文本字幕的语义需求**:时长依赖下一条,这不是可选项。位图字幕(流内自带 duration)理论上可流式,但 demuxer 统一走队列换取实现一致性;
3. **ASS 作为枢纽格式**:一种内部方言承载 SRT/VTT/ASS 全部表达力,编码侧按需降级——N×M 的格式转换收敛为 N+M;
4. **附件=extradata 复用**:不新增 API,用"附件也是流"的视角把封面图、字体统一进既有机制。MKV 的全能再次体现(第 10 章),而字幕是这套能力最大的受益者。

## 11.8 FAQ

**Q1:字幕帧为什么不是 AVFrame?**
历史模型:AVSubtitle/rects(avcodec.h:2088-2095)按"多块+显示时窗"设计,与 AVFrame 的单一平面假设不合。CLI 目前用 AVBufferRef 包装过图(ffmpeg_dec.c:536),原生化是社区共识方向(:676-679 注释)。

**Q2:为什么 SRT demuxer 要一次读全文件?**
包时长常靠下一条 pts 反推(subtitles.c:222-224);SRT 数字行歧义只能看后续才能消解(srtdec.c:175-182)。逻辑上必须前瞻,队列只是把前瞻物化成内存。

**Q3:SUBTITLE_TEXT 和 SUBTITLE_ASS 什么时候用哪个?**
内部一律 ASS rect(ass.c:151);只有目标明确要求纯文本(如烧录为 SRT)时由编码侧拆回(assenc.c:44,srtenc.c:229)。

**Q4:ASS 没有样式头时字体怎么定?**
`ff_ass_subtitle_header_full` 生成默认模板,PlayRes 384×288(ass.c:29-82,ass.h:28)——VobSub 遗产分辨率,libass 据此缩放。

**Q5:字幕 seek 为什么几乎零成本?**
全量在内存,`queue_seek` 内存二分定位(subtitles.c:269-319),无需任何 I/O。

**Q6:MKV 封面图和字体附件在 FFmpeg 里是什么?**
都是流:封面走 attached_pic(matroskadec.c:3533),其余附件 AVMEDIA_TYPE_ATTACHMENT+extradata(:3537-3541)。写出对称还原(matroskaenc.c:2513-2561)。

**Q7:内嵌字体为什么能生效?**
subtitles 滤镜在加载时扫描输入的 attachment 流,`ass_add_font` 把 extradata 注册进 libass(vf_subtitles.c:417-437)——字体解析发生在渲染器内,与系统字体无关。

**Q8:硬字幕和软字幕的链路差在哪?**
软字幕:字幕流独立复制/转码,播放器实时渲染;硬字幕:subtitles 滤镜自己 demux+decode+libass 渲染进视频像素,字幕不再存在为流。

**Q9:fix_sub_duration 解决什么?**
字幕包缺 duration 时,用下一条字幕的到达时间回填上一条的结束时间(ffmpeg_dec.c:574-588)——实时字幕流(SRT 直播)的常见病,demux 侧 subtitles.c:222-224 是第一道同类防线。

**Q10:能把 PGS 位图字幕转成 SRT 吗?**
不能,CLI 显式禁止文本↔位图互转(ffmpeg_mux_init.c:847-856):栅格化不可逆。OCR 属于另一个软件的职责。

## 11.9 小结与深挖方向

本章结论:**字幕 = 队列化 demuxer + AVSubtitle 旁路 + ASS 方言枢纽 + extradata 附件复用**;AVSubtitle 的 AVFrame 化是整条管线最显眼的未完成工程。深挖:

1. WebVTT 的 side data 元数据(webvttdec.c:154-166)与 MKV/MOV 封装时的保留策略;
2. libass 的 PlayRes→视频分辨率映射与字体 fallback 链在 vf_subtitles.c 的配置项;
3. PGS 多 rect 窗口模型(pgssubdec.c:531-590)与蓝光规范 WDS 的对应;
4. 字幕 text↔ass 往返转换的信息损失清单(样式/定位/卡拉OK 标签);
5. AVSubtitle 原生化改造的真实障碍:ABI、avcodec 公开结构体冻结与第三方播放器绑定。
