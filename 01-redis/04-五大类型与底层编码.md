# 第 04 章 · 五大类型与底层编码:44 字节、512、128 的来龙去脉

> 基线:commit `e8726d18`(2025-09-15)。行号均以该 commit 为准。本章同时记录该分支两个实验性方向(kvobj、stream 反查索引),帮助你看到"正在发生的演进"。

## 4.0 robj:16 字节的"类型 + 编码"头

所有键值在 Redis 内部都以 `redisObject`(robj)表示(server.h:1036-1045):

```c
struct redisObject {
    unsigned type:4;        // OBJ_STRING/LIST/SET/ZSET/HASH/...
    unsigned encoding:4;    // 底层编码
    unsigned lru:LRU_BITS;  // 24bit: LRU 时钟或 LFU(低8bit频率+高16bit时间)
    unsigned refcount : OBJ_REFCOUNT_BITS;  // 30bit
    void *ptr;
};
```

- `type` 是对外命令的视图(GET/LPUSH/HSET…),`encoding` 是内存布局的实现选择。**二者解耦,是整个多态编码体系的根**:`checkType()`(object.c:795-802)只看 type,命令实现再按 encoding 分派;
- 编码常量共 13 个(server.h:1019-1031),`ZIPMAP/LINKEDLIST/ZIPLIST` 已废弃但编号从不复用——要兼容旧 RDB 里的编码编号,这是稀缺资源的"历史占用";
- refcount 保留两个哨兵值:`OBJ_SHARED_REFCOUNT`(2^30-1,共享对象永不析构)与 `OBJ_STATIC_REFCOUNT`(栈对象)。

### 类型 × 编码对照表(当前代码的真实默认值,与旧资料多有出入)

| 类型 | 可能的 encoding | 切换阈值(默认) | 配置项 |
|---|---|---|---|
| string | int / embstr / raw | ≤20 位可转 int;≤44 字节 embstr;否则 raw | 硬编码,object.c:329 |
| list | listpack / quicklist | 单节点超 `list-max-listpack-size`(默认 -2 → 8KB/节点) | config.c:3187、3209 |
| hash | listpack / listpack_ex / hashtable | field 数 >512 或任一 field/value >64 字节 | config.c:3252、3258 |
| set | intset / listpack / hashtable | intset ≤512;listpack ≤128 个 / 64 字节 | config.c:3253-3255 |
| zset | listpack / skiplist(+dict) | 128 个或单元素 >64 字节 | config.c:3256、3260 |
| stream | rax + listpack 宏节点 | 节点 4096B / 100 条 | config.c:3243、3259 |

hash 的 `listpack_ex` 编码承载 7.4 引入的 **Hash Field Expiration**:对某 field 设 TTL 后,listpack 从 field/value 二联组变 field/value/ttl 三联组(t_hash.c:1530-1553)。

## 4.1 共享整数池:被低估的优化

`OBJ_SHARED_INTEGERS = 10000`(server.h:132):启动时预创建 0..9999 的 int 编码对象(server.c:2159-2163)。`createStringObjectFromLongLongWithOptions()`(object.c:356-373)对落在 [0,10000) 的值直接返回 `shared.integers[value]`,**零分配**。

一个精妙细节:int 编码对象 `o->ptr = (void*)((long)value)`——**数值就藏在指针槽里,不指向任何内存**(object.c:363-365)。因此 INCR 热路径在 `refcount==1 && encoding==INT` 时直接 `o->ptr = (void*)((long)value)` 原地加,不分配不释放(t_string.c:614-622)。

但共享对象遍布"对象空间",不能携带每键 LRU/LFU 信息——所以启用相关淘汰策略时,`createStringObjectFromLongLongForValue()`(object.c:386-393)拒绝返回共享整数(INCR 类命令绕开共享池)。

string 编码升级的总入口是 `tryObjectEncodingEx()`(object.c:837-895),三步:`refcount>1` 放弃 → `len<=20` 且可解析为 long 转 INT(释放 SDS)→ `len<=44` 且是 RAW 重建为 EMBSTR。**SET 命令在入口处就对 value 做预编码**(t_string.c:303),GET 侧永远是零成本读取。

## 4.2 string:int / embstr / raw 三级

**embstr 的 44 字节阈值**:robj(16B) + sdshdr8(3B) + 数据 + '\0' ≤ 64 字节,恰好塞满 jemalloc 的 64 字节 bin(object.c:323-329 注释原话:"chosen so that the biggest string object ... will still fit into the 64 byte arena of jemalloc")。**旧版(≤3.0)阈值是 39**,因为当时 SDS 头是 8 字节的 `{int len; int free;}`;3.2 重构 SDS 后头缩到 3 字节,阈值才升到 44——这就是"39/44"两代阈值的完整由来。

**embstr 是只读的**:任何修改命令(SETRANGE/APPEND)必须先 `dbUnshareStringValue`(db.c:792)重建为可变 RAW——对共享整数同理,会产生一次隐藏拷贝。

## 4.3 list:listpack → quicklist(分片、双端、可压缩)

list 只有两个编码:小表整表 listpack;超阈值后整表升级为 quicklist——而 **quicklist 内部每个节点自己又是一个 listpack**。

- **升级**(t_list.c:23-56):push 前把待加字节数累进 `lpBytes`,超 `quicklistNodeExceedsLimit` 就把现有 listpack **整体包成 quicklist 的第一个节点**——数据不重排,成本是一次"打包";
- **降级**(t_list.c:67-95):删除后仅当 quicklist 只剩一个节点且低于**半阈值**才转回 listpack——半阈值滞回防止在临界尺寸上反复双向转换。

**fill 参数:一个值表达两种语义**(quicklist.c:472-482):`fill >= 0` 表示单节点最多 N 个**元素**;`fill < 0` 表示按**字节**——-1→4KB、-2→8KB、-3→16KB、-4→32KB、-5→64KB(quicklist.c:49)。默认 -2 = 8KB。生产用负值,因为元素大小差异大时按个数填充会让节点内存极不均匀。另有安全阀 `SIZE_SAFETY_LIMIT 8192`:单元素超 8KB 会被拒之 listpack 外,独占一个 PLAIN 节点(quicklist.c:571-589)。

**compress 参数**:`list-compress-depth N` 表示**首尾各 N 个节点保持明文**,中间以 LZF 压缩。compress=2 的内存布局:

```
      head                                                      tail
       ▼                                                         ▼
  ┌─────────┐   ┌─────────┐   ╔═══════════╗   ╔═══════════╗   ┌─────────┐
  │ listpack │◄─►│ listpack │◄─►║ LZF 压缩块 ║◄─►║ LZF 压缩块 ║◄─►│ listpack │ …
  └─────────┘   └─────────┘   ╚═══════════╝   ╚═══════════╝   └─────────┘
   明文(深度2)  明文(深度2)      中间全部压缩      中间全部压缩     明文(深度2)
```

压缩有两道门槛:节点 <48 字节不压;收益不足 8 字节放弃(quicklist.c:226-238)。中间节点被访问时先解压置 `recompress=1`,用完立即重压(quicklist.c:284-290);**首尾永远明文**——Redis 假定 list 读写集中在中部(LPOP/RPUSH 都在两端),两端热、中间冷。

## 4.4 hash:listpack / listpack_ex / hashtable

查找/写入入口 `hashTypeTryConversion`(t_hash.c:593-623):本次命令 field 数 >512 直接转 HT 且 `dictExpand` 预分配(HMSET 一次到位,避免 rehash);任一 field/value >64 字节转 HT。单条 HSET 在 listpack 内以**步长 1** 找 field(field,value 交替),命中 `lpReplace`,未命中 `lpBatchAppend` 两项(t_hash.c:880-1002)。

设置字段 TTL 后转 `listpack_ex`:三联组(field, value, ttl),`lpFind` 步长变 2,`HASH_LP_NO_TTL` 表示无过期(t_hash.c:927)。转 HT 后 field 用带元数据的 `hfield` + ebuckets 承接过期(→ 第 08 章)。

## 4.5 set:三种编码,且会"优雅降级"

set 是编码最多的类型(t_set.c):

- **创建**:全整数且 ≤512 → intset;否则 ≤128 → listpack;否则 HT 并预扩;
- **加元素**的四条路中有一条亮点:**intset 遇到非整数时,不是无脑转 HT**——先估算 intset 全体元素放进 listpack 的体积,若 ≤128 个且最大元素 ≤64 字节,**先降级成 listpack 再追加**(t_set.c:176-201),放不下才转 HT。这避免了"一个字符串污染全家"的内存跃迁;
- **反向转换**:`maybeConvertToIntset`(t_set.c:72-94)在 SINTERSTORE 等结果全为整数时把 HT 整表重建为 intset——set 是唯一有"HT→紧凑编码"回退路径的类型;
- 删除不触发降级。

## 4.6 zset(重点):skiplist + dict 双结构

**为什么是双结构**(t_zset.c:20-42 注释):dict 提供 ele→score 的 O(1) 查(ZSCORE/ZADD 判重),skiplist 提供 score 有序视图(ZRANGE/ZRANGEBYSCORE/ZRANK)。关键内存技巧:**两份结构共享同一个 ele SDS**,dict 的 value 是 `&node->score`(指向 skiplist 节点内 score 字段的指针,t_zset.c:1528)。因此删除必须**先 dict 后 skiplist**——skiplist 释放时会 free 共享 SDS(t_zset.c:1552-1563 注释)。

```c
typedef struct zskiplistNode {
    sds ele;
    double score;
    struct zskiplistNode *backward;      // 只有第1层有后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;              // 跨过的节点数,用于 O(logN) 求秩
    } level[];                           // 柔性数组,层高即节点大小
} zskiplistNode;
```
(server.h:1546-1565;常量:`ZSKIPLIST_MAXLEVEL 32`("enough for 2^64 elements")、`ZSKIPLIST_P 0.25`,server.h:612-614)

**层高随机算法**(t_zset.c:111-117):每层晋升概率 P=1/4,期望层高 1/(1-P)=1.33。P=1/4 而非教科书的 1/2,是空间换时间的调参:节点平均只多 0.33 个指针,单层期望步长 4,仍保持 O(log N) 且缓存更友好。

**zslInsert**(t_zset.c:122-177)四步:`update[]` 记每层待接节点、`rank[]` 记跨距——自最高层向下扫(同分按 ele 字典序破平),逐层接线并维护 `span`:`x->level[i].span = update[i]->span - (rank[0]-rank[i])`(t_zset.c:156-162)。**span 让 ZRANK/ZRANGE 不用逐节点计数**:沿下降路径累加 span 即得 1-based 秩,O(log N)。

**ZRANGEBYSCORE 的查找路径**(t_zset.c:3257-3358):skiplist 编码入口 `zslNthInRange`(t_zset.c:331-395)——先用 O(1) 的 `zslIsInRange` 短路,再从最高层滑到下界;本分支有个新优化:offset < `ZSKIPLIST_MAX_SEARCH(10)` 时走 level[0] 逐跳,offset 大时才从最高层按 span 跳位(t_zset.c:354-364)——小 offset 避免换算 CPU,大 offset 换 O(log N)。

**listpack 编码的 zset**:ele、score 严格交替且按 score→ele 有序插入;score 能用 `double2ll` 表示时直接以整数编码存放(t_zset.c:1077-1094)。

## 4.7 stream(概览):rax + listpack 宏节点

顶层结构:主数据是 `rax *rax`,key 为 **128bit big-endian 的 streamID**(t_stream.c:487),value 是一个 listpack 宏节点;`cgroups` rax 管消费组(stream.h:16-27)。

**XADD 与宏节点**(t_stream.c:420-663):尾 listpack 达到 `stream-node-max-bytes(4096)` 或 `stream-node-max-entries(100)` 即开新宏节点;每个宏节点头部有 **master entry**(字段名模板),后续条目 flags 含 SAMEFIELDS 位时字段名全部省略、ID 存相对 master 的 delta——**stream 在 listpack 内做了第二层"列压缩 + 差分编码"**。删除不打洞,只置 DELETED 墓碑位(t_stream.c:17-19)。

**消费组与 PEL**:XREADGROUP 投递时为每条消息造一个 NACK,**同一个 NACK 指针同时插入 group->pel 与 consumer->pel 两个 rax**(t_stream.c:1864-1897),避免双份数据;ACK 从两个 PEL 摘除。PEL 的 key 也是 big-endian ID,天然有序。注意 `entries_read` 是"尽力而为的计数器",有空洞时用估算函数兜底(t_stream.c:1818-1830),不能当精确值用。

## 4.8 编码切换:触发条件、成本与三条规律

| 切换 | 触发点 | 成本 |
|---|---|---|
| raw/embstr→int | 写路径 tryObjectEncoding(object.c:862-873) | O(len) 一次,此后 O(1) |
| int/embstr→raw(unshare) | 任何修改命令(db.c:792) | 完整拷贝一次 |
| listpack→quicklist | push 前检查(t_list.c:40-55) | 原数据直接变成第一个节点,近乎免费 |
| listpack→HT(hash) | >512 或 >64B(t_hash.c:604-622) | O(N) 重建 + dict 扩容 |
| intset→listpack/HT(set) | 512 上限/出现非整数(t_set.c:160-209) | O(N),intset 需逐个重编码 |
| listpack→skiplist(zset) | ZADD 前置检查(t_zset.c:1464-1468) | O(N logN):逐个 zslInsert + dictAdd |
| listpack→listpack_ex(hash) | 首次 HEXPIRE(t_hash.c:1147) | O(N):每个 field 后插入 NO_TTL |

三条共性规律:

1. **升级基本单向,降级是例外**(避免抖动):例外是 list 的半阈值滞回、set 的 HT→intset、zset 的受限回退;
2. **转换都发生在写入路径**,读路径只按 encoding 分派——同样是 HGET,listpack 是 O(N) 顺序扫,HT 是 O(1);阈值的意义正是让"小数据付出顺序扫的小成本、大数据付出索引的小内存";
3. **转换是"整键级"的,不在命令的摊销范围内**:把 12 万元素的 listpack zset 转 skiplist = 12 万次 zslInsert + dictAdd,全发生在触发阈值的那一条 ZADD 里。**这就是生产上"大批量导入用 ZADD/SADD 多参数一次喂入"的原因**:命令会把参数个数作为 size_hint 传下去,提前升级并 `dictExpand` 预扩(t_zset.c:1841-1846、t_set.c:599-602),避免逐条触发"中途昂贵转换 + 反复 rehash"。

## 4.9 本分支的两个新动向(读源码时别错过)

1. **kvobj(object.c:30-321)**:把 key SDS + 可选 8 字节 expire 直接内嵌进 value 对象、连续排布,EMBSTR value 在总尺寸 ≤64 字节(CACHE_LINE_SIZE)时整体内嵌。动机是把 "key→robj→value" 的三次指针追逐压成一次缓存行访问,TTL 就地修改。这是对经典布局的架构级改造,尚在实验阶段;
2. **zslNthInRange 的 MAX_SEARCH=10 分界**:小 offset 逐跳、大 offset 按 span 跳位,是一个"按 offset 大小切换算法"的双模实现。

## 4.10 FAQ

**Q1:embstr 的 44 指什么?为什么从 39 涨到 44?**
指字符串内容字节数。16(robj)+3(sdshdr8)+44+1('\0')=64,恰好一个 jemalloc bin;旧 SDS 头 8 字节时是 16+8+39+1=64。

**Q2:INT 编码对象的内存里存的是什么?**
`o->ptr` 本身就是数值(强制转型),不指向任何分配内存(object.c:363-365)。free 时无须释放 ptr。

**Q3:`list-max-listpack-size -2` 是多大?**
按字节限制单节点:-2 → 8KB/节点(quicklist.c:49)。非负数才是按元素个数。

**Q4:128 个元素的 zset 一定是 listpack 吗?**
不一定:任一元素 >64 字节即转 skiplist;且"先大后删"的场景里,删除不触发降级,可能长期停在 skiplist。

**Q5:zset 为什么用 skiplist 不用红黑树?**
官方注释(t_zset.c:35-42)给出的差异:允许重复 score、按 (score,ele) 二元组比较、第 0 层带 backward。工程上:无旋转、实现简单、范围遍历就是链表遍历、层高随机免去 rebalance 语义。

**Q6:span 没有了会怎样?**
ZRANK/ZRANGE BYRANK 就得 O(N) 数节点;span 让秩可以在下降过程中累加出来(t_zset.c:493-534)。

**Q7:hash 的 512/64 是"任一超"还是"全部超"?**
任一超即转(field 与 value 的 sdslen 任一 >64,t_hash.c:886-890);条数检查是插入后 >512。

**Q8:XDEL 后 listpack 里的数据会移动吗?**
不会,只打 DELETED 墓碑位(t_stream.c:17-19);空间回收由 XTRIM/MINID 或宏节点清空完成。

**Q9:共享整数池会给业务带来什么坑?**
所有键共享同一对象(无法单独计量 LRU/LFU,启用相关淘汰策略时 INCR 类命令绕开共享池);对它做写操作必须先 unshare,产生一次隐藏拷贝。

## 4.11 小结与深挖方向

本章的自包含结论:**robj 的 type/encoding 二分解耦,让"命令语义稳定"与"内存布局可换"互不牵绊;五大类型的所有阈值(44/128/512/64/-2)都是在"顺序扫描仍够快"与"内存不再占优"之间的经验平衡点**。深挖方向:

1. kvobj 迁移的收敛性:高 TTL 翻新率下,内嵌 expire 的 realloc 相比独立 expire 表的性能盈亏点(object.c:259-321);
2. quicklist 删到只剩百来个元素时,是否永远停留在"多个近乎空的 8KB 节点"——节点合并逻辑的触发覆盖度;
3. ZSKIPLIST_MAX_SEARCH=10 分界的实测依据:深度分页场景下与纯 span 实现的基准缺失;
4. hash 字段级 TTL 的三态编码演进(listpack→listpack_ex→HT)在灰度放量时的延迟毛刺形状;
5. stream 新增的 cgroups_ref 反查索引把 XADD 的复杂度推到了哪里(stream.h:24-26)。
