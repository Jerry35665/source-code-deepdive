# 第 05 章 · 事件循环与网络 IO:单线程如何跑出百万 QPS

> 基线:commit `e8726d18`(2025-09-15)。行号均以该 commit 为准。
> 一个重要的版本锚点:**unstable 分支的网络 IO 层已经发生代际重写**。2024 年起 Redis 引入 `src/iothread.c`,每个 IO 线程拥有独立的事件循环;网上大量资料(含部分 8.0 书籍)描述的 `io-threads-do-reads` 旧式多路分发已不存在——该配置项已列入废弃列表(config.c:437),`io-threads` 默认仍为 1(config.c:3183)。本章以实际代码为准,并在 5.3 节专门梳理新旧两代设计。

## 5.0 全景:单线程的边界在哪里

Redis 的"单线程"指**命令执行 + 事件调度**发生在主线程的一个 `aeEventLoop` 上(server.c:7665 的 `aeMain`)。但下列工作从来不在主线程:

| 工作 | 线程 | 证据 |
|---|---|---|
| AOF fsync、lazy-free 异步释放 | BIO 后台线程 | bio.c |
| RDB/AOF rewrite 子进程 | fork 子进程 | — |
| **网络 IO(读+写)+ RESP 解析**(可选) | IO 线程池 | iothread.c:707-718(各跑一个 aeMain) |
| 命令执行、过期删除、驱逐、客户端管理 | 仅主线程 | iothread.c:145-154、409 注释 |

单线程够快的根源:每请求 CPU 开销极小——一条 SET 主线程只做"一次解析 + 一次字典写入 + 组装 7 字节回复";真正可能阻塞的 syscall 在数据就绪时几乎不耗时。

`ae` 库本身极简,源自 antirez 早年的 Jim 事件循环(ae.c:1-3),只有文件事件、时间事件、before/after-sleep 钩子三样东西。多路复用后端通过**直接 `#include` 对应的 .c 文件**在编译期确定,优先级 evport > epoll > kqueue > select(ae.c:30-44)——没有函数指针表、没有运行时切换,四个后端各自实现同名的静态函数,谁被 include 谁生效。

## 5.1 ae 事件循环逐段解读

### 核心结构与注册

`aeEventLoop`(ae.h:79-93)以 fd 为下标的 `events` 数组 + 本轮 `fired` 数组 + 时间事件链表构成。事件掩码:`AE_READABLE=1`、`AE_WRITABLE=2`、**`AE_BARRIER=4`**(ae.h:22-28)——BARRIER 是理解 AOF 一致性的关键:它强制同一轮迭代中该 fd 先写后读,保证"先 fsync AOF,再回复客户端"。

`aeCreateFileEvent`(ae.c:145-179)的工程细节:`fd >= setsize` 直接报错;**events 数组惰性增长**(初始只分配 min(setsize,1024) 个槽,注册高 fd 时倍增,ae.c:155-166)——省掉为百万 maxclients 预分配的内存;删事件后若 fd 恰是 maxfd,O(N) 向下重算(极少触发)。

### 时间事件:不用堆,而是一条无序双向链表

`aeCreateTimeEvent` 直接头插 O(1)(ae.c:232-237),删除是惰性的(改 id 为 AE_DELETED_EVENT_ID)。计算"距最近定时器多久"的 `usUntilEarliestTimer` 是 **O(N) 全表扫描**(ae.c:263-276),作者在注释里明说了权衡,并列出"有序插入/跳表"两个"暂不需要"的优化方向。

**为什么不用堆**:主循环里长期存在的定时器屈指可数——主线程只有 `serverCron` 一个(server.c:2939),IO 线程各自只有一个 IOThreadCron(iothread.c:765)。N≈1~2 时,O(N) 扫描快过任何堆的 cache 不友好路径。这是"按真实规模选数据结构"的典型案例。注意 Redis 没有把每个客户端的超时做成 per-client timer,而是统一塞进 serverCron 的周期扫描——如果做成 timer,这个设计才会真正成为瓶颈。

### aeProcessEvents:一轮迭代的骨架(ae.c:360-468)

```
1. beforeSleep → 2. 算 timeout(睡到下个定时器)→ 3. aeApiPoll(唯一阻塞点)
→ 4. afterSleep → 5. 逐个触发文件事件 → 6. 时间事件 → 回到 1
```

fired 事件的分发循环(ae.c:409-461)有 3 个精心处理过的坑:

1. **先读后写**:查询处理完能立刻在同一 fd 上写回复(ae.c:415-419);
2. **BARRIER 反转**:`fe->mask & AE_BARRIER` 置位时先写后读(ae.c:426)——fsync=always 的客户端必须先落盘再处理新读;
3. **失效事件防御**:`fe->mask & mask & AE_READABLE` 双重与——前面回调可能已删除本轮后面仍待触发的 fd(ae.c:434);回调后重新取 `fe` 指针,防数组 realloc(ae.c:437)。

`aeMain` 本体只有 4 行(ae.c:492-499)。

## 5.2 一条 SET 命令的字节级旅程

RESP 报文:`*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n`(34 字节)。

**(0) 建连**:accept 在监听 fd 的读事件里,一轮最多 accept 10 个(`max-new-connections-per-cycle`,socket.c:301-321)——防止连接风暴挤占一轮循环;`accept4(SOCK_NONBLOCK|SOCK_CLOEXEC)` 一步拿非阻塞 fd(anet.c:604-631)。`createClient` **立即开 TCP_NODELAY**、按 `tcp-keepalive`(默认 300s)设 SO_KEEPALIVE 三参数(anet.c:212-252,注释点名 Linux 默认 7200s "more or less garbage"),注册读 handler 为 `readQueryFromClient`。

**(1) 读**:epoll 报 EPOLLIN → `readQueryFromClient`(networking.c:3006),默认读 16KB。小命令客户端首次读时领到的是**线程级可复用查询缓冲** `thread_reusable_qb`(`__thread` 全局 sds):所有客户端轮流复用同一块 16KB,读完归还(networking.c:3042-3061)——把"每客户端 16KB"的内存放大器压成"每线程 16KB"。

**(2) 解析**:`processInputBuffer`(networking.c:2892)按首字节判 MULTIBULK/INLINE;`processMultibulkBuffer` 先读 `*3` 再循环读每个 `$n`,**增量解析**——半包即返回等下次事件。未认证连接有两道防 DoS 闸:参数个数 >10 或 bulk 长度 >16384 直接按协议错误断开(networking.c:2541-2544、2627-2630)。输入路径上最重要的零拷贝优化:**≥32KB 的大参数若恰好独占缓冲,不再拷贝,直接把 querybuf 的 sds 接管为 argv 对象**(networking.c:2679-2694);master 客户端不享受此优化——它的 querybuf 还要原样转发给下级副本(networking.c:2633-2636 注释)。

**(3) 执行**:`processCommand`(server.c:4072)十几道安检 → `call` → `setCommand` 写字典 → `addReply(c, shared.ok)`——共享对象 `"+OK\r\n"` 直接引用,零构造。

**(4) 组装回复**:`_addReplyToBufferOrList`(networking.c:393-440)把 7 字节拷进**静态回复缓冲** `c->buf`(16KB,创建时一次分配,永不 realloc);静态缓冲满或已有链表节点才追加 16KB 块节点;每次追加后即时检查 client-output-buffer-limit(networking.c:379)。注意此时**并未注册写事件**,只是挂进 `clients_pending_write`。

**(5) 写回**:本轮事件处理完进入 beforeSleep:`handleClientsWithPendingWrites` 摘下客户端直接 `writeToClient`——**"写直出"优化**:绝大多数小回复在进入 epoll_wait 之前就写出去了,连 WRITABLE 事件都不用注册;写不完(EAGAIN)才注册 WRITABLE 等下轮。reply 链表非空时走 `writev` 把静态缓冲与链表节点拼成 iovec 一次吞掉(networking.c:2010-2076)。

普通客户端单轮写入上限 64KB(NET_MAX_WRITES_PER_EVENT,server.h:130):超过就让出循环去服务其他客户端,防"loopback 上的 KEYS *"饿死全场;但 **replica 与内存已超限场景不受此限,尽力倾倒**(networking.c:2155-2190)——反直觉但合理:写不出去缓冲就一直占内存,与其被 reply 挤爆,不如尽快送出去。

**(6) 关闭路径**:协议错误打 `CLIENT_CLOSE_AFTER_REPLY|CLIENT_PROTOCOL_ERROR`,写完回复才释放;对端关闭 `nread==0` → `freeClientAsync`;freeClient 的完整清单见第 02 章(两阶段销毁)。

## 5.3 缓冲区工程策略与 io_threads 两代设计

### 输入侧:三层缓存体系

1. 线程级可复用缓冲(默认,per-thread 16KB);
2. 客户端私有缓冲(大参数/复用冲突时);
3. 峰值水位 `querybuf_peak`:serverCron 按 32KB 阈值收缩,避免"一次大命令永久占住大缓冲"。

尺寸闸门:单条 bulk ≤512MB、整缓冲 ≤1GB;**未认证客户端双保险 1MB**(networking.c:3110-3122)。

### 输出侧:三轨制

静态 16KB 缓冲(小回复)→ 链表块(≥16KB/节点)→ **replica 直接走全局复制积压缓冲的共享块引用**(`ref_repl_buf_node`,多个副本共享同一份流,`c->reply_bytes` 对副本无意义,networking.c:2115-2137、4417-4418)。

### client-output-buffer-limit 踢除机制(networking.c:4350-4440)

```
hard:  used_mem >= hard_limit_bytes                      → 立即踢
soft:  used_mem >= soft_limit 且持续 soft_seconds        → 踢
```

软限用 `obuf_soft_limit_reached_time` 水位时间戳实现,首次到达只记时间不踢。**踢除是"标记 + 稍后断开"**:在 addReply 的调用上下文里立即 free 会破坏调用方,只能标记 CLOSE_ASAP,由 beforeSleep 的安全点执行。默认:normal 0 0 0(不限)、replica 256MB/64MB/60s、pubsub 32MB/8MB/60s。

### io_threads:从"共享 epoll 自旋"到"每线程独立事件循环"

**旧设计(7.0 及以前,已删除)**:所有线程共享主事件循环,主线程把待读/待写客户端 round-robin 分发,自旋等全部完成;读线程只 read 不解析,`io-threads-do-reads` 控制是否并行读。

**新设计(iothread.c,2024 重写)**:

- 每个 IO 线程**独立 `aeEventLoop`**,客户端固定归属某线程(accept 时分给最闲的,iothread.c:158-185);
- 职责切分:IO 线程做 read + RESP 解析 + write + 一步轻量命令预查(`iolookedcmd`),然后移交主线程**执行命令**;执行完送回 IO 线程写回复。**解析可以并行,执行绝不能**(iothread.c:409 注释);IO 线程永不释放客户端;
- 线程间通信:mutex 保护的客户端链 + eventNotifier 唤醒,带"免通知"优化(对方在运行时直接挂链不唤醒,iothread.c:327-344);
- 主线程侧逐个执行,还带 **CPU cache 预取**(逐客户端 prefetchCommands,iothread.c:348-367)——把待执行命令的 key 内存提前拉进 cache,降低 dict 查找的 cache miss;
- 主线程要访问 IO 线程的客户端数据时,用 `pauseIOThread` 的原子标志 + 忙等,在对端的干净点自暂停,**避免加全局锁**(iothread.c:205-323);
- master/replica/pubsub/blocked 等特殊客户端必须留在主线程(iothread.c:145-154)。

**为什么重写**:旧设计所有线程挤同一个 epoll + 自旋同步,扩展性差;新设计把"每连接一个归属线程"变成无锁的 owner-worker 模型,主线程只做纯内存计算,IO 线程数可随连接数与带宽扩展——同时保持命令执行的串行一致性。

### 与 Memcached 的对比

Memcached:libevent + worker 线程池,**命令执行也在 worker 里并发**,item 级锁保护哈希表。Redis 走相反的路:**数据结构与命令执行严格单线程**,只把可并行的 syscall 密集部分拆出去。取舍根源:Redis 的核心复杂度在数据结构(渐进 rehash、阻塞语义、事务),加锁的认知与性能成本远高于 item 锁;单请求极轻,IO 才是可并行的部分。两家的选择都对,但前提不同。

## 5.4 连接抽象与 anet

`connection.c` 的 `ConnectionType` 是一张 30+ 项的 vtable(connection.c:385-430),设计初衷是让上层不感知 **TLS 非阻塞握手中断**:TLS 通过 `has_pending_data/process_pending_data` 钩子在 beforeSleep 前把缓冲里未消费的 TLS 记录强制处理掉,配合 `aeSetDontWait` 让本轮不睡眠(server.c:1806-1810)。一个值得记录的"特性退役":**unstable 里已检索不到任何 TCP FastOpen 代码**(anet.c 全文 grep 为空)——8.x 之前存在的 TFO 支持已被移除,基于旧资料介绍 TFO 需更正。

## 5.5 FAQ

**Q1:epoll_wait 挂着的时候新命令要等什么?**
三种之一:任意 fd 就绪(含监听 fd)、最近时间事件到期、或 AE_DONT_WAIT(TLS pending 等场景,beforeSleep 里 aeSetDontWait 置位后下轮 timeout=0)。

**Q2:回复是在哪个阶段发出的?**
优先在进入 epoll_wait 之前的 beforeSleep 直写;写不完才注册 WRITABLE 等下轮。"先读后写"在 ae 层的含义:同一 fd 读事件先于写事件触发,查询处理完立刻能写回复。

**Q3:AE_BARRIER 什么场景用?**
appendfsync=always 时先 fsync AOF 再处理新读与回复,否则可能回复了实际没落盘的数据(networking.c:244-248)。

**Q4:querybuf 是每客户端固定 16KB 吗?**
不是。普通客户端共享线程级可复用缓冲(读后归还);大参数切私有精确分配;峰值超阈值被 cron 收缩。"1 万连接 = 160MB 输入缓冲"的旧算法不再成立。

**Q5:io-threads 开了之后命令就并发执行了吗?**
没有。命令执行仍在主线程串行;收益是 read/write syscall、TLS、协议解析、cache 预取的并行化。

**Q6:一个 fd 同时可读可写,顺序由什么决定?**
默认先读后写,AE_BARRIER 反转;写回调只在与读回调不是同一函数指针时才额外触发(ae.c:441-445)。

**Q7:TCP_NODELAY 默认开吗?**
`createClient` 里无条件开启(networking.c:129);keepalive 由 tcp-keepalive(默认 300s)驱动。

## 5.6 小结与深挖方向

本章的自包含结论:**Redis 的低延迟 = 事件循环的批量收尾(beforeSleep 写直出)+ 缓冲区的分层预算 + "解析并行、执行串行"的 IO 线程新架构**;ae 库本身极简,所有精巧都花在"一轮迭代里的坑"(事件失效、BARRIER、惰性数组增长)上。深挖方向:

1. eventNotifier(eventfd vs pipe)的缓冲满语义:triggerEventNotifier 的错误被有意忽略(iothread.c:336-339),是否可能丢唤醒;
2. prefetch 批量策略 `determinePrefetchCount` 与 jemalloc cache 行为的配合收益(memory_prefetch.c:316);
3. per-slot 流量统计 `net_input_bytes_curr_cmd` 的四段式口径(networking.c:2565-2596 长注释);
4. reusable querybuf 与 processEventsWhileBlocked 重入路径的边界用例;
5. TFO 移除的版本与动机——一个"特性退役"的完整案例。
