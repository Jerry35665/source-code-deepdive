# 第 07 章 · 复制、哨兵与集群:从字节流对齐到 16384 个槽

> 基线:commit `e8726d18`(2025-09-15)。行号均以该 commit 为准。
> 一处代码考古:replication.c:3-7、cluster_legacy.c:2-6 的版权头同时保留 "Redis Ltd." 与 "Valkey contributors"——2024 年 license 变更后,这条分支持续吸收 Valkey 侧的修改,例如 7.x 的 rdb-channel 双连接全量同步就带有明显 Valkey 血统。

## 7.0 全景:三种形态,一个地基

| 形态 | 核心文件 | 解决的问题 | 故障决策者 |
|---|---|---|---|
| 主从复制 | replication.c(5130 行) | 数据冗余 + 读扩展,提供 replid/offset 这套"复制时钟" | 无(手动 SLAVEOF/promote) |
| 哨兵 | sentinel.c(5474 行) | 监控 + 自动故障转移 | 哨兵之间(Pub/Sub + 投票) |
| 集群 | cluster.c + cluster_legacy.c(合计 8246 行) | 16384 slot 分片 + 分片内自动故障转移 | 数据节点之间(cluster bus gossip) |

演进关系一句话:**复制是地基,哨兵和集群是两套互斥的"地基之上的自动化"**。

1. 复制层只负责"字节流的对齐":主库维护全局递增的 `master_repl_offset` 与两个复制 ID `replid/replid2`(replication.c:1862-1893),从库用 `PSYNC <replid> <offset>` 表达"我拥有哪个历史、断在哪里";
2. 哨兵是外置观察者:不参与数据面,用 hiredis 异步连接发 PING/INFO/PUBLISH,靠 `__sentinel__:hello` 频道互相发现;它的"写操作"只有发 `SLAVEOF` 一条(sentinel.c:4869 起);
3. 集群把故障检测内置到数据节点:每节点两条 TCP 通道(客户端口 + 总线口 port+10000,`CLUSTER_PORT_INCR`,cluster_legacy.c:5991),总线走二进制 gossip(11 种消息,cluster_legacy.h:94-105);故障转移由**持有 slot 的 master** 投票完成——"哨兵去进程化"。

边界上最易混淆的一点:**集群节点间的 FAIL 投票与复制完全解耦**——replica 是否有资格发起选举取决于 master 的 FAIL 标记与数据年龄(cluster_legacy.c:4273-4313),而"落后多少字节"仍由 replid/offset 回答。

## 7.1 主从复制:复制时钟与握手

### 三个全局量

- `server.replid`:当前复制历史链的 40 字节随机 ID;
- `server.replid2` + `second_replid_offset`:**次级历史**。实例从 slave 升为 master 时,`shiftReplicationId()` 把旧 replid 存入 replid2,并把边界定为 `master_repl_offset+1`(replication.c:1881-1893)——+1 的语义:别人索要的是"还没收到的第一个字节",所以只能对 `旧offset+1` 以前的历史背书;
- `server.master_repl_offset`:复制流的全局写位置。

主库判定部分重同步的完整条件(`masterTryPartialResynchronization`):replid 匹配 replid 或(replid2 且 offset ≤ second_replid_offset)(replication.c:836-838),且 offset 落在 backlog 现存区间内(replication.c:862-874)。**处处 +1**:offset 语义是"已处理到的最后一个字节的下一个位置"(从库重连发 `reploff+1`,replication.c:2675;backlog 起点同样,replication.c:173)。

### 握手时序(全量同步)

```
 Replica                                          Master
    |  PING                                          |  syncWithMaster 状态机
    |  <+PONG>                                       |  (replication.c:2871)
    |  AUTH / REPLCONF listening-port / ip-address   |  SEND_HANDSHAKE (2914)
    |  REPLCONF capa eof capa psync2 [rdb-channel]   |  (2958-2960)
    |  PSYNC <replid|?> <offset|-1>                   |  SEND_PSYNC (3039)
    |  +FULLRESYNC <replid> <offset>                  |  或 +RDBCHANNELSYNC(见 7.2)
    |  $<len> 或 $EOF:<40字节随机串>                   |  readSyncBulkPayload (2044)
    |  (加载期间每秒发 '\n' 保活)                      |  增量流开始 (2454-2487)
```

两个易漏细节:**PING 是握手第一步**且只接受 `+PONG` 或认证错误(尽早暴露连错端口);**`+FULLRESYNC` 是延迟回复的**——回复里的 offset 必须是"将要生成的 RDB 快照对应的流位置",只有 bgsave 真正 fork 那一刻才有效(replication.c:915-920 注释)。

### 全量同步的三种 CASE(syncCommand,replication.c:1025-1237)

等待全量的 slave 置 `WAIT_BGSAVE_START` 后:

- **CASE 1**:磁盘式 bgsave 进行中,且已有 slave 在积累差异——若新 slave 的能力/需求是其子集(replication.c:1191-1192),直接挂上这次 bgsave,连输出缓冲都复制过来(`copyReplicaOutputBuffer`)——一次 bgsave 服务多个 slave;
- **CASE 2**:无盘式 bgsave 进行中,新 slave 只能等下一次(子进程直写的 socket 集合无法中途加人);
- **CASE 3**:无 bgsave——无盘模式且有 delay 时先登记、等 cron 凑够 `repl-diskless-sync-max-replicas` 再 fork(默认 delay 5 秒,config.c:3197),否则立刻 startBgsaveForReplication。

主库视角的生命周期:`WAIT_BGSAVE_START → WAIT_BGSAVE_END → ONLINE`。无盘模式下靠收到第一个 `REPLCONF ACK` 确认对端活着再上线(replication.c:1335-1352)——**用 ACK 而非"连接关闭"判定 EOF**:EOF 标记可能被截断,ACK 一定来自完整加载后的客户端。

### backlog:块链表,不是环形缓冲区

7.0 之后 backlog 的实现是**全局复制缓冲块链表 + 引用计数**(replication.c:391-491):

- `feedReplicationBuffer()` 把字节追加进 `server.repl_buffer_blocks` 链表尾块(块上限 `repl_backlog_size/16`);**同一链表同时服务 backlog 和所有在线 slave**——每个 slave 用 `ref_repl_buf_node` 指向自己没发完的第一个块并 `refcount++`;
- 修剪(`incrementalTrimReplicationBacklog`,replication.c:318-371)只在头块 `refcount == 1`(没有慢 slave 拖着)时进行——因此**慢 slave 会把实际复制内存顶到 repl-backlog-size 之上**,backlog 大小 ≠ 复制缓冲内存(记账在 `server.repl_buffer_mem`);
- 部分重同步查找走 `blocks_index`(rax,每 64 块一个索引,replication.c:709-742);
- `repl-backlog-ttl` 空闲释放 backlog 时**同时换 replid**——否则会出现"旧主被提升的从库用 replid2 认亲、但自己期间又写过数据"的错乱(replication.c:4749-4772 注释给了完整推理)。

### 命令传播与级联复制

`replicationFeedSlaves()`(replication.c:499-592)第一行就短路:`if (server.masterhost != NULL) return;`——**中间层 slave 不自己合成复制流**,而是把 master 发来的原始字节流原样灌进自己的 backlog(replication.c:629-639),保证全链路共享同一份 replid/offset 空间——这是 PSYNC2 能跨层级续传的前提。

心跳双向:master 周期向复制流塞 PING;slave 周期回 `REPLCONF ACK <offset>`(replication.c:4146-4165)——一个 ACK 同时喂饱三件事:slave 超时检测、`WAIT` 命令计数、min-replicas 写保护。

### rdb-channel:8.x 世代的全量同步新形态

双方都支持 `rdb-channel-repl` 且部分重同步失败时,主库不回 `+FULLRESYNC` 而回 `+RDBCHANNELSYNC <client-id>`(replication.c:1118-1143);slave **新开第二条连接**取 RDB,主连接从 RDB 开始投递时就**并行转发增量流**(先缓存,等 RDB 加载完回放,replication.c:3838 起)。两条连接在主库算一个 replica(`replicationLogicalReplicaCount`)。收益:全量期间的增量堆积从"主库输出缓冲"转移到"从库可控内存块",直击全量同步期间主库输出缓冲暴涨 OOM 的痛点。

### 手动故障转移:`FAILOVER` 命令

replication.c:4954-5059 藏着一个常被忽略的状态机:主库暂停客户端写 → 等"某 slave 的 ACK offset 追平复制流"(`updateFailoverStatus`)→ 自降为从 → 目标 slave 检测到 `FAILOVER_IN_PROGRESS` 发 `PSYNC <replid> <offset> FAILOVER`(replication.c:2686-2690)→ 对方比对 replid 一致后直接变 master。**零数据丢失**的受控切主。

## 7.2 哨兵:sdown → odown → 选举 → 提升

### 发现与连接共享

每个被监控对象是 `sentinelRedisInstance`。哨兵对每个实例维持命令连接 cc 与 Pub/Sub 连接 pc;**对同一 master 的所有哨兵对等体做连接共享**(sentinel.c:121-134 注释:5 哨兵 × 100 master 场景从 500 条连接降到 5 条)。

发现协议是纯 Pub/Sub:每 2 秒向 `__sentinel__:hello` 频道 PUBLISH 一条 8 元组消息(sentinel.c:3000-3040)。收到后三件事:不认识的 runid → 新增对等体;对方 epoch 更大 → 抬升本地;**对方携带的 master config_epoch 更大且地址不同 → 说明别人已完成过故障转移,本地改写监控地址**——config_epoch 大者赢,这是哨兵配置收敛的最终仲裁。

### 状态机

```
 定时器(10Hz,hz 随机化防哨兵同步, sentinel.c:5467-5473)
   → sdown:PING 超时 > down_after_period,或自称 master 却长期 role:slave (4526)
   → 询问对等体: SENTINEL is-master-down-by-addr (4680)
   → odown:自身 sdown 且 票数(含自己) >= quorum (4600-4626)   ★ 只对 master
   → 发起故障转移: odown 且距上次 > 2*failover_timeout
        failover_epoch = ++current_epoch (4937-4948)
   → 等选举 → 选从 → SLAVEOF NO ONE → 等提升 → 重配其余从库
```

**quorum 与多数派是两个不同的数**。odown 用 quorum(弱法定人数,注释明言跨时间窗的消息无同时性保证,sentinel.c:4596-4599);而 leader 选举要求**绝对多数**:>`voters/2` 票**且**不低于 quorum(sentinelGetLeader,sentinel.c:4849-4851)。所以 quorum=2、5 个哨兵时,实际切换仍需 3 票。

**两处随机化构成防分裂机制**(对应 Raft 的 randomized timeout):

1. 投票先到先得(每 epoch 一票,`master->leader_epoch < req_epoch` 守卫,sentinel.c:4738-4763);投给别人时把自己的 `failover_start_time` 加 `rand()%1000` 随机延迟(4757-4758);
2. 每轮定时器对 hz 随机抖动(5467-5473)。

### 新主挑选与提升确认

先过滤(sdown、断连、`slave-priority=0` 永不提升、INFO 过期、**断链时间不能早于 master 故障太久**——注释自嘲 "pretty much black magic",sentinel.c:5058-5083);再按三元组排序:**priority 小者 → offset 大者 → runid 字典序小者**。

**提升确认是间接的**:不等 SLAVEOF NO ONE 的返回值,等该实例 INFO 里 role 变 master(sentinel.c:5163-5176)。重配其余从库按 `parallel-syncs`(默认 1)限流。

**TILT 模式**:定时器间隔为负或超 2 秒(时钟跳变/进程冻结)时,30 秒内"只采集不行动"(sentinel.c:5447-5458)。

## 7.3 集群:gossip、故障检测与选举

### 总线与两个时钟

消息 11 种(cluster_legacy.h:94-105);包头携带 `currentEpoch`(集群逻辑时钟)与 `configEpoch`(slot 配置版本)——**configEpoch 比较决定 slot 归属仲裁**。每对节点两条单向连接(入站/出站);只有出站连接的 PONG 才刷新 `pong_received`(cluster_legacy.c:3005-3007)。MEET 与 PING 的唯一区别是信任级别:MEET 对未知节点无条件建 HANDSHAKE;`CLUSTER MEET` 本身入队即返回,真正的成员关系靠后续 PONG 握手(cluster_legacy.c:2897-2961)。

### gossip 段:概率保证的失败报告

PING/PONG/MEET 携带 gossip 条目,条目数 `max(3, 节点数/10)`(cluster_legacy.c:3668-3670)。注释里有完整概率推导:2×node_timeout 窗内每节点交换约 8 包,1/10 采样保证 PFAIL 节点能收到约 80% master 的失败报告——足以凑多数派。**PFAIL 节点被无条件追加到 gossip 末尾**加速扩散。接收端四件事:收集失败报告(FIFO,窗口 2×node_timeout)、pong 时间借力(间接可达性传播,不超前本机时钟 500ms)、地址纠偏、成员扩张(带黑名单防回流)。

### PFAIL → FAIL 两阶段

```
 clusterCron: 延迟 > cluster-node-timeout → PFAIL(本地怀疑,不影响路由)
   → 失败报告数(含自己)>= size/2+1 → FAIL + clusterSendFail 广播 (1890-1915)
   → 恢复: PFAIL 收到 PONG 直接清;有 slot 的 master 需超时冷却且无人接管 slot (1922-1952)
```

### replica 选举:Raft 风格

1. 资格:master 为 FAIL、master 有 slot(cluster_legacy.c:4273-4283);
2. **rank 延迟选举**:rank = 同 master 下比自己新的 replica 数;发起定时 = `500ms + rand()%500 + rank×1000ms`(4318-4328)——**数据最新的几乎必然先拿到选票**;rank 动态修正(4353-4366);
3. 投票约束(3998-4099):**只有持有 ≥1 slot 的 master 有投票权**(4010——集群法定人数的"size"就是持 slot master 数);每 epoch 一票;同一 master 的 replicas 在 2×node_timeout 内只投一票;候选声称的 slot,其现任主 configEpoch 不得大于请求者;
4. 过半即胜:把自身 configEpoch 提为选举 epoch 并接管 slot,`clusterBroadcastPong(ALL)` ASAP 扩散新配置。

### MOVED/ASK 与 resharding

`keyHashSlot()` = CRC16(key) 低 14 位;**`{...}` 内内容优先参与哈希**(hash tag)。`getNodeByQuery()`(cluster.c:1110-1324)产出七种裁决,核心两条:

- **MOVED**:slot 现任主不是自己——永久指路,客户端应更新路由表;
- **ASK**:slot 正迁出且 key 不在本地——一次性豁免,须先 `ASKING`;**ASK 永不该更新客户端路由表**。

**multi-hop resharding 是三个命令的编排**:源 `SETSLOT MIGRATING` / 目标 `SETSLOT IMPORTING` → 逐 key `MIGRATE`(目标端 RESTORE-ASKING,原子地源删目标建)→ 目标 `SETSLOT NODE` 收尾(源必须已无该 slot 的 key;自增 configEpoch 无需投票——碰撞有专门解决例程 `clusterHandleConfigEpochCollision`)。

### 为什么是 16384

源码视角可复算:slot 归属表是 16384 位位图,**随每一条 PING/PONG/投票请求传播**(cluster_legacy.c:4002 直接校验位图)——2KB/包;若 65536 slot 则 8KB,gossip 在千节点规模下带宽不可接受。antirez 的经典论证 + 位图出现在每个心跳里的乘法效应,16384 是带宽与粒度的折中。

## 7.4 设计动机

1. **哨兵与集群并存是因为定位不同**:集群故障转移粒度是 shard,决策者是持 slot master 多数派,要求集群拓扑成立;哨兵粒度是单组主从,quorum 可以低到 1(弱保证),面向"客户端不支持 cluster 协议"的世界;
2. **集群的数据模型有硬约束**:多 key 操作必须同 slot(cluster.c:1096-1101),事务与 Lua 被限制在单 slot;哨兵+主从没有这一约束;
3. **复制是异步的,强一致被显式做成可选 API**:`WAIT`/`WAITAOF`(replication.c:4420-4498)把"等多少从库追到多少 offset"交给调用方;
4. **故障检测处处用"弱多数 + 时间窗"**而非强一致——分布式系统的实用主义;
5. **心跳里塞业务**(PUBLISH 走总线广播)换取无第三方依赖的 pub/sub,代价是总线带宽与数据面耦合。

## 7.5 FAQ

**Q1:replid2 是备份吗?**
不是,是**历史交接凭证**。故障转移后新主把旧主 replid 存进 replid2 并声明有效边界;旧主和其他从库用它向新主发起 PSYNC 才能命中部分重同步(replication.c:836-838)。

**Q2:repl-backlog-size=1MB 意味着复制缓冲最多 1MB?**
错。慢 slave 以 refcount 钉住头块阻止修剪,实际 `repl_buffer_mem` 可以远超配置;backlog 只保证"无慢从库时能部分重同步的历史长度"。

**Q3:全量同步期间主库的新写入会丢吗?**
不会。fork 后的修改进系统 page cache 由子进程继承(RDB 是一致的 fork 时点快照);之后 slave 在 WAIT_BGSAVE_END 继续收流,RDB 发完再补发累积部分。

**Q4:odown 能出现在 slave 上吗?**
不能。odown 判定只对 master;slave 不可达只有 sdown。集群侧对应:replica 超时不会被投票 FAIL。

**Q5:MOVED 和 ASK 的本质区别?**
MOVED 说"slot 已永久归它,更新路由表";ASK 说"slot 正在搬迁,这一次去问那台机器(先发 ASKING)"。ASKING 标志只对下一条命令生效——只该为导入中的 slot 开一次性后门。

**Q6:集群里所有节点都参与故障投票吗?**
否。投票权要求"是 master 且持有 ≥1 slot";无 slot 的 master 和所有 replica 只传播失败报告。

**Q7:PFAIL 的节点会被客户端路由拒绝吗?**
不会。PFAIL 纯属本地怀疑;只有 FAIL 才影响 clusterUpdateState 的 reachable_masters 计算。slot 未覆盖会直接回 CLUSTERDOWN。

**Q8:从库会自己过期 key 吗?**
主库是唯一权威:主库对 key 的过期/驱逐合成 DEL/UNLINK 走复制流;从库不自己产生写命令(同链路 offset 单调)。

## 7.6 小结与深挖方向

本章结论:**复制层提供"复制时钟"(replid/offset)这一唯一抽象;哨兵和集群都在它之上做各自的自动化,但决策者、粒度、约束完全不同**。深挖方向:

1. 共享复制缓冲的内存上界:refcount 钉块与 client-output-buffer-limit replica 的相互作用,超大块场景是否会漏杀;
2. `clusterUpdateSlotsConfigWith` 的完整正确性论证:configEpoch 仲裁 × 过渡态 × UPDATE 消息三方交互,"SETSLOT NODE 后立刻宕机"的窗口;
3. 哨兵连接共享在地址变更/TLS 切换时的失效路径;
4. cluster 总线认证的演进:`internal_secret` 扩展的语义与安全边界;
5. 两套手动 failover(FAILOVER 命令 vs CLUSTER FAILOVER)的丢数据窗口与 abort 语义对照。
