# 第 08 章 · 内存、过期与淘汰:在"永不 OOM"与"永不卡顿"之间走钢丝

> 基线:commit `e8726d18`(2025-09-15)。本章行号是笔者逐行核对过的源码位置(evict.c/expire.c/ebuckets.h/lazyfree.c/zmalloc)。
> 先给一个重要的事实修正:**键级 TTL 至今仍走"随机采样扫描"的经典设计;ebuckets 这个新结构服务的是 hash 字段级过期(HFE)**。市面上"Redis 8.0 把过期全部改成 ebuckets"的说法不准确——读源码时务必区分这两层。

## 8.0 内存管理全景

Redis 的内存体系分四层:

1. **分配层**:`zmalloc` 包装 malloc,通过 `je_malloc_usable_size`(jemalloc 构建,zmalloc.h:33)拿到每次分配的**实际可用尺寸**——这是 `used_memory` 统计、`MEMORY USAGE`、内存碎片率的数据来源;
2. **统计层**:`zmalloc_used_memory()` 基于原子变量增减(zmalloc.c:503),RSS 通过 `/proc` 采集,`used_memory_rss - used_memory` 即碎片;
3. **对象层**:robj 的 24 位 `lru` 字段一鱼两吃——LRU 策略下存 LRU 时钟,LFU 策略下存"16 位分钟级时间 + 8 位对数频率"(evict.c:220-249);
4. **策略层**:过期(时间维度的回收)与淘汰(空间维度的回收),各有完整的多路径设计。

## 8.1 过期删除:三条路径

### 路径一:惰性删除

键被访问时检查 `keyIsExpired`,过期即删——精确但依赖访问,冷键可能永远占内存。

### 路径二:主动过期(activeExpireCycle)

这是经典设计,**至今未变**,双周期互补:

- **慢周期**:在 `databasesCron`(serverCron 内)调用,时间预算为 CPU 的 `config_cycle_slow_time_perc`(默认 25%:timelimit = `25*1000000/server.hz/100` 微秒,expire.c:331);
- **快周期**:在 **beforeSleep** 每轮事件循环都试(第 02 章),预算 `ACTIVE_EXPIRE_CYCLE_FAST_DURATION` 微秒级(expire.c:335-336)。

核心是**自适应采样**(expire.c:347-431):

```
for 每个 db:
    do {
        sampled = kvstoreScan(db->expires, ...)   /* 逐桶扫描,不重算哈希 */
        /* 重复条件:过期比例 > acceptable_stale(默认 10%,随 effort 收紧) */
        repeat = (expired*100/sampled) > config_cycle_acceptable_stale
    } while (repeat && 时间未超限)
```

"过期比例高就继续扫描,低就收手"——把扫描量与过期密度挂钩。`active-expire-effort` 配置(1-10)同时调节每轮键数、时长、可接受脏比例四个参数(expire.c:271-283)。

### 路径三:ebuckets(为 hash 字段级过期而生)

7.4 引入 Hash Field Expiration 后,新的问题出现了:**字段过期混在 hash 内部,采样扫描 keyspace 根本覆盖不到**。于是有了 ebuckets(ebuckets.h:9-117 的头注释是一份完整规格书)。

**双层注册设计**(server.h:1113-1115、3462-3469):

```
redisDb
 ├── keys     (kvstore)      → 键空间(不含 TTL 信息)
 ├── expires  (kvstore)      → 键级 TTL(经典采样扫描)
 └── subexpires (estore)     → 字段级 TTL,Currently only used for hashes
        │
        ├─ 全局 ebuckets:每个带 HFE 的 hash 以"最小字段 TTL"注册
        │   (dictExpireMetadata 内嵌 ExpireMeta,挂在 dict 元数据上)
        └─ 每个 hash 内部:字段级 ebuckets(hfield 携带 ExpireMeta)
            或 listpack_ex 编码(TTL 编码进 listpack 三联组)
```

ebuckets 本体(ebuckets.h:27-116):

```
ebuckets = rax 树(大) 或 简单链表(小,省掉 rax 分配)
   │  rax key = 过期时间的字节表示(限 6 字节,树深 ≤6)
   ▼
bucket(时间区间,rax 叶子)
   ▼
segment(最多 EB_SEG_MAX_ITEMS 个 item 的循环单链表)
   ▼
item(内嵌 ExpireMeta:48bit 毫秒过期时间 + 4 个链表角色位)
```

三个精妙设计:

1. **segment 聚合**:rax 每个叶子约 40 字节,而 segment 里每多放一个 item 只多 8 字节 next 指针——把同类过期时间的 item 聚进 segment,rax 的修改频率与内存开销都降一个量级(ebuckets.h:16-23);
2. **split 与 extended segment**:segment 满时尝试分裂 bucket 成更细时间区间;若所有 item 过期时间相同(TTL 相同的批量键),分裂无意义,改为把 bucket 链上再挂一个 extended segment(ebuckets.h:49-71 的两个图示);
3. **精度换树深**:`EB_BUCKET_KEY_PRECISION` 低位丢弃(当前 0,注释预留改 10)——主动过期可以容忍 1 秒误差,砍掉"嘈杂"的低位分支;精确性由惰性过期兜底,每个 item 自带毫秒级精确时间(ebuckets.h:77-95)。

**为什么它优于把字段过期映射成 keyspace 扫描**:ebuckets 支持 O(1) 的"下一个要过期的时间"查询(`ebGetNextTimeToExpire`),主动过期直接定位到期 bucket,不再需要随机采样碰运气。

## 8.2 淘汰:performEvictions 的完整循环

入口条件(evict.c:453-465)三个:不在长命令让步中、不在加载中、**replica 默认忽略 maxmemory**(`repl_slave_ignore_maxmemory`——副本是主的精确拷贝,自己驱逐会漂移)。`noeviction` 策略直接返回失败,由 processCommand 拒绝 CMD_DENYOOM 命令(第 02 章)。

### 近似 LRU:16 槽候选池

精确 LRU 需要全局双向链表(每键 16 字节额外开销 + 每次访问的链表搬移)。Redis 的近似方案(evict.c:68-120 注释):

- 每次淘汰,随机采样 N 个键(`maxmemory-samples`,默认 5)进**16 槽候选池**(`EVPOOL_SIZE`,evict.c:34),按 idle 升序;池跨 performEvictions 调用**持续保留**,质量随采样次数提升;
- 池里键名用 255 字节缓存 SDS 复用,注释原话:"according to the profiler, not my fantasy. Remember: premature optimization bla bla bla"(evict.c:197-200)——性能问题真的用 profiler 定位过;
- 池中键可能已成"幽灵"(被别处删除),淘汰时先 `kvstoreDictFind` 确认,幽灵就取下一个(evict.c:611-618);
- 采样起点用 `kvstoreGetFairRandomDictIndex`——分片 kvstore 下保证每个 dict 被抽中概率公平。

### 三种打分(evict.c:142-158)

```c
if (policy & MAXMEMORY_FLAG_LRU)      idle = estimateObjectIdleTime(kv);
else if (policy & MAXMEMORY_FLAG_LFU) idle = 255-LFUDecrAndReturn(kv);
else if (policy == VOLATILE_TTL)      idle = ULLONG_MAX - kvobjGetExpire(kv);
```

分数越高越先淘汰;volatile-* 与 allkeys-* 的区别只在采样源:`db->expires` 还是 `db->keys`(evict.c:566-570)。

### LFU:8 位对数计数器

24 位布局(evict.c:220-249):16 位分钟级最后访问时间 + 8 位对数频率 LOG_C。

```c
uint8_t LFULogIncr(uint8_t counter) {
    if (counter == 255) return 255;
    double r = (double)rand()/RAND_MAX;
    double baseval = counter - LFU_INIT_VAL;      /* 新键从 5 起步 */
    if (baseval < 0) baseval = 0;
    double p = 1.0/(baseval*server.lfu_log_factor+1);
    if (r < p) counter++;
    return counter;
}
```
(evict.c:271-279)

- **对数增长**:counter 越大,增长概率越低——`lfu-log-factor`(默认 10)决定 255 饱和前的访问量级(默认配置下约 100 万次访问饱和);
- **衰减**:`LFUDecrAndReturn`(evict.c:291-298)按 `lfu-decay-time`(分钟,默认 1)计算流逝周期数并扣减 counter——读路径增量衰减,不维护后台任务;访问模式变化(昔日热键冷却)由此体现;
- 16 位分钟时间处理回绕:按"恰好绕一圈"假设计算 `LFUTimeElapsed`(evict.c:263-267)。

### 淘汰循环的时间上限

`performEvictions` 主循环(evict.c:545-670):释放量达标或无键可淘汰即止;**每释放 16 个键检查一次时间预算**(`evictionTimeLimitUs()`,默认与主动过期类似的 CPU 占比),防止"内存严重超限时一次淘汰循环卡死主线程"。被淘汰键走 `deleteEvictedKeyAndPropagate`——**DEL 会传播给副本与 AOF**,保持多机一致。

### 一个防雪崩的细节

AOF 缓冲与复制缓冲**不计入 used_memory**(evict.c:300-319 注释):如果计入,淘汰产生 DEL → DEL 写进这些缓冲 → 缓冲变大 → 触发更多淘汰的**正反馈循环**,极端情况全部键被淘汰。注释还解释了为什么 backlog 可以计入(它最终恒定,无共振效应)——这段注释本身就是一篇微型工程论文。

## 8.3 lazy free:把释放挪出主线程

`LAZYFREE_THRESHOLD = 64`(lazyfree.c:181)。`lazyfreeGetFreeEffort`(lazyfree.c:129)估算释放工作量:listpack 编码的小对象 effort=1(同步删),list/hashtable/zset 元素数超过阈值且 `refcount==1` 时改走异步(bio 的 BIO_LAZY_FREE worker,第 06 章)。

- `UNLINK`/`FLUSHDB ASYNC`/`FLUSHALL ASYNC` 是显式异步入口;**DEL 本身在 4.0 后也会对高 effort 对象自动走异步**;
- 顺带异步化的还有:tracking 表、错误 rax、Lua 脚本缓存、Functions 库(lazyfree.c:221-266)——任何"可能巨大"的释放都不在主线程做。

## 8.4 设计动机与取舍

1. **近似换常数**:LRU 池与 LFU 计数器都在常数内存里完成(24 位/键 + 16 槽池),牺牲精度换掉全局链表与后台线程——`maxmemory-samples` 是精度旋钮;
2. **自适应截止**:主动过期(过期比例)与淘汰(时间预算)都带自适应退出,单线程的"永不卡顿"靠这些预算保证;
3. **ebuckets 的本质**:把"时间排序"从扫描问题变成索引问题——rax 以时间为键,bucket→segment 两级聚合把树开销摊薄;它是"精确时间 + 近似结构"的又一次 Redis 式折中;
4. **副本不驱逐**:数据一致性优先于内存自保——副本宁可超限也不偏离主;
5. **传播一切删除**:过期与淘汰产生的删除都进复制流,保证"从库的数据年龄"永远由主库定义(与第 07 章呼应)。

## 8.5 FAQ

**Q1:LRU 时钟 24 位会回绕吗?怎么处理?**
会。`estimateObjectIdleTime` 对 `lruclock < o->lru` 的情况按"加一圈"计算(evict.c:95-100);时钟分辨率默认 1 秒(`LRU_CLOCK_RESOLUTION`),频率由 serverCron 刷新。

**Q2:LFU 的新键为什么从 5 起步?**
LFU_INIT_VAL:让新键有收集几次访问的机会再参与淘汰,否则新建键 counter=0 最容易被杀(evict.c:241-247)。

**Q3:`maxmemory-samples` 调大有什么代价与收益?**
采样越多候选池质量越高,越接近精确 LRU;代价是每次淘汰的 CPU。官方注释直言默认 5 是"内存换 CPU"的经验点。

**Q4:为什么 volatile-ttl 的打分是 ULLONG_MAX - expire?**
复用同一个"分数大者优先淘汰"的池:把"最快过期"换算成最大分数,三种策略共用一套池逻辑(evict.c:153-155)。

**Q5:淘汰和过期都会传播 DEL 吗?**
都会。`deleteEvictedKeyAndPropagate` 与过期路径均走传播,副本不自行过期/淘汰(与第 07 章 Q8 呼应)。

**Q6:ebuckets 代替了键级过期吗?**
没有。键级 TTL 仍在 `db->expires` kvstore 走采样扫描(expire.c:414-421);ebuckets 目前服务 hash 字段级过期(server.h:1115 注释 "Currently only used for hashes")。

**Q7:一个 hash 设置了字段 TTL,内存布局怎么变?**
listpack 转为 listpack_ex 编码(三联组 field/value/ttl);该 hash 以最小字段 TTL 注册进 db 级 subexpires ebuckets,主动过期先从全局 ebuckets 定位到 hash,再进 hash 内部删字段。

**Q8:UNLINK 一定比 DEL 快吗?**
不一定。小对象(listpack 等)effort=1,同步删反而省去任务调度;只有元素数 >64 的大对象才值得异步(lazyfree.c:181-190)。

**Q9:used_memory 为什么比 RSS 小?**
used_memory 是 zmalloc 记账的分配总量;RSS 含分配器元数据、页对齐、碎片与代码段——差值即 `mem_fragmentation_ratio` 的来源。

**Q10:内存超限时淘汰循环会卡多久?**
受 `evictionTimeLimitUs()` 约束,每释放 16 键检查一次;超时后本轮停止,下轮继续——延迟确定性优先于一次性达标。

## 8.6 卷末小结

到此,第一卷《Redis》的主体闭合了。把八章串成一句话:

> **Redis 用一个全局单例 + 一个事件循环组织进程;用"紧凑编码 + 阈值切换"组织内存;用"渐进式 + 预算制"保证单线程的延迟确定性;用 fork+COW 与追加日志组织持久化;用一套"复制时钟"(replid/offset)支撑哨兵与集群两种自动化;最后用近似算法与两级索引(候选池、ebuckets)在 O(1) 内完成时间的与空间的回收。**

每个设计点都能还原成同一条决策原则:**把不确定性(慢磁盘、慢客户端、慢哈希)挡在主线程之外,把确定性(内存布局、延迟预算)留给主线程**。
