# 第 04 章 · 调度器:过滤、打分与抢占的流水线

> 基线:commit `517a94ff`。行号以 pkg/scheduler/ 为准。
> 演进提示:该基线相对经典教材已有明显演进——PodGroup 调度、OpportunisticBatching(KEP-5598)、异步抢占(KEP-4832)等新机制,以实际代码为准。

## 4.0 全景:串行取件、并行评估、异步落库

调度器本质是一条流水线:**单个 goroutine 循环取件**(scheduler.go:469 的 Pop 循环——不是一 pod 一协程),调度周期同步推进,绑定周期异步并行。函数式视角:`pick(pod) = argmax over filter(snapshot, pod) of score(n, pod)`。

**周期与绑定的分工**:

```
ScheduleOne → schedulingCycle(同步,持有调度线程)
   快照增量更新 → PreFilter → Filter(逐节点并发)→ Score → assume → Reserve → Permit
  → go runBindingCycle(异步,可多线程)
   WaitOnPermit → PreBind → Bind(POST /bind)→ PostBind
```

**CycleState** 是一次调度周期的黑板:插件在 PreFilter 算一次、Filter 阶段 N 次读取——**Filter 得以做到 O(节点内 pod 数) 而非 O(集群 pod 数) 的前提**。抢占模拟时框架克隆 CycleState 增量修正,不污染主周期状态。

## 4.1 并发 Filter 与三条短路

Filter 是"逐节点并发、够数即停"的扇出(schedule_one.go:822-857):Parallelizer(默认 16)切 chunk 并发跑,**找够 numNodesToFind 个就 cancel 其余 goroutine**;失败原因记入 diagnosis.NodeToStatus 供抢占复用。`numFeasibleToFind` 自适应:`percentage = 50 - numAllNodes/125`,下限 5% 且至少 100 节点。

三条提前短路揭示一个容易被忽略的事实——**调度结果并不总是全集群最优**:单节点可行即跳过打分;无打分器时 `numNodesToFind=1` 找到能跑就走;抢占提名节点先试。这是刻意的工程折衷:k8s 用"足够好的节点"换"每秒多调度几百个 pod"。`nextStartNodeIndex` 轮转起点保证字典序靠前的节点不会永远先被评估——调度器里少有的公平性设计。

每个节点的 Filter 前还要 `RunFilterPluginsWithNominatedPods`:把优先级 ≥ 提名 pod 的先"虚加"进 NodeInfo 跑第一遍,全部通过再用原始状态跑第二遍——保守双重检查,防提名 pod 把资源"看起来可用"。

## 4.2 三队列与 in-flight 事件回放

PriorityQueue = activeQ(QueueSort 堆)+ backoffQ(到期时间堆)+ unschedulableEntities(map)。**Pop 用函数 + 条件变量而非 channel**,注释解释:调度一个 pod 可能耗时很长,channel 里的 pod 会"变陈旧",而堆可随时按最新优先级重排(scheduler.go:68-72)。

**in-flight 事件回放**是 v1.31+ 的关键机制:pod 被 Pop 后进入 inFlightPods/inFlightEvents 链表,调度期间发生的集群事件按序追加;pod 失败归来时 `determineSchedulingHintForInFlightPod` **回放调度期间错过的全部事件**,用 QueueingHint 判定失败是否已被某事件修复——是则免退避直接回 activeQ。这解决了"调度中事件丢失"的竞态。

**unschedulable 不是队列而是"带原因的停车场"**:每个实体记着拒绝它的插件集合;集群事件到来时只咨询这些插件注册的 QueueingHintFn,答案是 Queue 才搬走——把无谓重试从"事件数 × 停车场大小"降到"真正相关的 (事件,pod) 对"。backoff 区分两类失败:插件拒绝(等事件)与临时错误(定时兜底)。

## 4.3 关键插件算法

**NodeResourcesFit 过滤**:请求向量 PreFilter 一次算(容器求和、init 容器取 max、加 overhead);Filter 逐维比较;**请求超节点总量时置 Unresolvable**,状态升级为 UnschedulableAndUnresolvable——告诉抢占"别在我身上浪费时间"。

**打分(Binpack vs Spreading 的当代形态)**:LeastAllocated(spreading,默认)/MostAllocated(binpack)/RequestedToCapacityRatio(自定义曲线)三策略共存;默认权重:LeastAllocated=1、PodTopologySpread/InterPodAffinity=2、NodeAffinity=2、TaintToleration=3。一个微妙点:未声明 request 的容器按默认 100m CPU/200Mi 计入。

**InterPodAffinity 的对称问题**:判断节点能否放新 pod P,需同时回答三个方向——P 的亲和、P 的反亲和、**现有 pod 的反亲和拒 P**(前两者 AND、后者 OR)。PreFilter 必须扫全集群构建三张 topologyPair→count 表——O(集群 pod 数) 的开销,抢占的 AddPod/RemovePod 增量回放正是为了不重复建表。自亲和特判:"计数为 0 则放行第一个 pod",否则亲和组永远无法落地。

## 4.4 抢占:全删→回赎

评估流程:候选节点只取 **Filter 阶段 Unschedulable(可解)的节点**(Unresolvable 的直接排除);DryRunPreemption 随机采样;核心 victim 选择是 **"全删→试放→按重要性回赎"**——先把节点所有低优先级 victim 移除,放得下再按重要性降序逐个赎回(先赎 PDB 违反者)——**每一层都在限制抢占的破坏半径与 API 调用量**。绑定周期失败的语义边界:Permit 是最后一个能判 Unschedulable 的点,PreBind/Bind 失败只能进 BackoffQ;抢占可在内存中取消 preBind 阶段的 pod,避免"幽灵占用"。

**assume 两阶段**:选中节点后直接改写 Spec.NodeName 放进 scheduler cache——下一周期的快照已包含本 pod 占用,真实 Bind 在异步周期发生。三条时序风险各有对策:informer 未回流前 `IsAssumedPod` 拦截重复入队;Bind 失败显式 `unreserveAndForget`;绑定中的 pod 被选为 victim 时内存取消。

## 4.5 FAQ

**Q1:调度结果是最优的吗?**
不是。采样截断(Filter 找够即停)+ 打分样本集被截断,是"足够好"换吞吐的刻意取舍;严格最优交给 topology spread 或外部批量调度器。

**Q2:调度失败的 pod 什么时候重试?**
三条件任一:相关事件触发 QueueingHint 判定可回 activeQ;backoff 到期;unschedulable 停车场滞留 5 分钟强制 flush。

**Q3:抢占一定会执行吗?**
不会。DryRun 全程在内存模拟;生成 NominatedNodeName 后原 pod 回队重新调度,真正删除 victim 由后续流程与 GC 完成;抢占可在 preBind 阶段被内存取消。

**Q4:亲和为什么慢?**
双向对称问题 + 需扫全集群建三张拓扑表;hostname 维度有快速路径可绕过全局拓扑图(AND 语义需跨 scope 联合、OR 语义可独立短路——官方注释给了完整推理)。

**Q5:为什么 Pop 用条件变量不用 channel?**
channel 里的 pod 会"变陈旧"且无法重排;堆可以随时按最新优先级调整,唤醒时堆头必是最高优先级。

## 4.6 小结与深挖方向

本章结论:**调度器 = 函数式插件流水线 + 单循环串行 + assume 两阶段 + "带原因的停车场"**;所有设计都指向同一目标——在大集群上维持每秒数百 pod 的吞吐,同时把无谓重试压到与"真正相关的 (事件,pod) 对"成正比。深挖:

1. in-flight 事件链表的裁剪逻辑与内存上界;
2. QueueingHint 的插件注册覆盖度(漏注册 = 永久滞留 or 5min 兜底);
3. 异步抢占(KEP-4832)与同步抢占的语义差异;
4. InterPodAffinity 三张拓扑表在大集群的内存系数;
5. Binpack/Spreading 混合权重在碎片化场景的实测。
