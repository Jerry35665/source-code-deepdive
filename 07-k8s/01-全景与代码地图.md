**与前几卷对照**:K8s 不是"一个程序"而是"一组程序的生态"——控制面三件套(apiserver/controller-manager/scheduler)+ 节点代理(kubelet)+ 基础库(client-go/apiserver framework)。它的规模决定了本卷只能聚焦主干:**声明式 API 的机制、控制循环的通用骨架、调度、节点调和**四大件。

## 1.2 仓库结构(本卷视角)

```
kubernetes/
├── cmd/                各二进制的薄入口(kube-apiserver 仅 1622 行)
├── pkg/
│   ├── controller/     全部内置控制器(72K 行)
│   ├── scheduler/      调度器(49K 行)
│   ├── kubelet/        节点代理(109K 行)
│   └── apis/           API 类型定义
├── staging/src/k8s.io/ 发布为独立模块的基础库
│   ├── apimachinery/   runtime/scheme/watch 等元机制
│   ├── apiserver/      API 服务器框架(149K 行)
│   ├── client-go/      客户端库 + informer 生态(279K 行)
│   └── kube-scheduler/ 调度框架接口(staging 化为 out-of-tree 插件提供 ABI)
└── vendor/             含 etcd client 的 kubernetes 封装
```

**staging 模式是 K8s 独有的工程实践**:基础库放在主仓库的 staging/ 目录开发、CI 保证同步、发布时软链为独立 Go 模块——既避免版本地狱又保持单仓原子提交。

## 1.4 一条主线串起全部文件

```
用户 kubectl apply
  → apiserver:handler chain → registry.Store(乐观锁 CAS)→ etcd
  → watch 事件扇出(Cacher/informer)
  → controller-manager:Reflector→DeltaFIFO→Indexer→workqueue→syncHandler
  → Deployment→ReplicaSet→Pod 逐级调和;scheduler:Pop→Filter→Score→assume→Bind
  → kubelet:syncLoop→podWorker→computePodActions→CRI(containerd)
  → 容器实际运行;状态经 statusManager 异步回写 apiserver → 闭环
```

**一条 requestVersion 主线**:RV(etcd revision)贯穿 apiserver 的乐观锁、watch 游标、informer 的断点续传、调度器与 kubelet 的事件消费——它是整个声明式系统的"时间轴"。

## 1.5 阅读路线

1. **数据主线**(推荐):02 API 服务器 → 03 控制器 → 04 调度器 → 05 kubelet。跟着一个 Pod 从提交到容器运行;
2. **机制主线**:02(watch/RV)→ 03(informer)→ 任意。理解"声明式"的完整闭环后,CRD/Operator 都只是同一模式的应用;
3. **对照主线**:与《etcd/raft 卷》并读——etcd 是 K8s 的存储底座,本卷第 02 章的 CAS/compaction/watch 三件都直接构建在 raft 卷的概念上。
