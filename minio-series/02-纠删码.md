# 第 02 章 · 纠删码:可靠性的数学与工程

> 基线:commit `7aac2a2`。行号以 cmd/erasure-*.go、internal/config/storageclass/ 为准。**最大纠偏:默认 parity 在 ≥8 盘时是 4,不是 N/2**(storage-class.go:354-368 的 DefaultParityBlocks 表;N/2 只是上限 :226);且 **EC 不是自研**——依赖 klauspost/reedsolomon v1.12.4(go.mod:49),MinIO 不带 vendor。

## 2.0 全景:一个对象的纠删分布

```
对象(hashKey(deploymentID+object) 选 set,erasure-sets.go:692-698)
  → set 内 hashOrder(object,N) 决定分片→盘映射(erasure-metadata-utils.go:178-192)
  → 数据分 dataBlocks 份 + parity 份校验(Reed-Solomon,rs-vandermonde :40)
  → 每盘一份分片 + xl.meta;读 dataBlocks 个即可重建
```

**默认 parity 表**(storage-class.go:354-368):1 盘→0;2-3→1;4-5→2;6-7→3;**≥8→4**——不是 N/2!RRS(减少冗余存储)默认 parity=1(:70-71)。RS 参数:data>0、parity≥0、d+p≤256(erasure-coding.go:44-50);块 1MiB(object-api-common.go:37),shard=ceil(1MiB/dataBlocks)(:116-118)。

## 2.1 写路径:分片、bitrot、renameData

PutObject(erasure-object.go:1254-1620):parity 来自存储类头/默认(:1299-1302);**盘离线时动态加 parity 上限 N/2,离线过半直接写失败**(:1306-1333);writeQuorum=dataBlocks,**data==parity 时 +1 防脑裂**(:1338-1341)。每盘一个 streaming-bitrot writer,分片先写 tmp 桶(:1404-1423,:1440),erasure.Encode=Split+Encode 按块循环(erasure-encode.go:69-110);**HH256S 把 `32B hash||shard` 内联写进 part.1**(bitrot-streaming.go:44-75)——bitrot 校验与数据同存,按分片粒度校验。renameData(:1019-1101):每盘原子改名+失败回滚+**版本签名 quorum**(:1564)。

## 2.2 读路径:只读 dataBlocks 个分片

objectQuorumFromMeta 判 xl.meta quorum→按 Erasure.Index 重排盘、本地盘 prefer(:369-388)→Decode 的 **parallelReader 只并发读 dataBlocks 个分片**,失败盘置 nil 由下一盘补读,凑齐 k 个即停(erasure-decode.go:127-235);坏分片(errFileCorrupt)被丢并重建,**若客户端数据已完整则转为后台 MRF heal**(erasure-object.go:400-418)——读时自愈的萌芽。quorum 统一推导 objectQuorumFromMeta(:530-564):读=N-m(dataBlocks);删除标记/0 字节对象读 quorum=N/2+1(:476-479,:513-514);凑不齐读返回 errErasureReadQuorum(:234)。

## 2.3 与前作对照及设计动机

| | MinIO EC | PG 磁盘 | Git pack |
|---|---|---|---|
| 冗余 | RS 校验分片 | 无(靠 PG 备份) | 无(靠 clone) |
| 损坏检测 | HH256 每分片 | 文件系统层 | SHA 内容 |
| 修复 | k 分片重建 | 外部 | 重新 clone |

1. **纠删码 vs 三副本**:同可靠性(4+4=8 盘扛 4 盘坏)下空间 2× vs 3×——容量经济性是对象存储的生命线;
2. **bitrot 内联**:校验与数据同存同读——静默损坏(位翻转)在读取时必然被发现并触发重建(:400-418);
3. **元数据分布每盘一份**:xl.meta 在 N 盘各有副本,quorum 读——**元数据与数据同构分布**,无元数据服务器;
4. **hashOrder 散盘**:分片到盘的映射按对象名 CRC 移位(:178-192)——热点对象的分片天然分散。

## 2.5 FAQ

**Q1:默认 parity 是 N/2 吗?**
不是:≥8 盘默认 4(storage-class.go:354-368);N/2 是上限(:226),需显式配置。

**Q2:读时几个盘坏还能读?**
在线盘 ≥dataBlocks(:148-151):4+4 配置可坏 4 盘;低于则 errErasureReadQuorum。

**Q3:bitrot 怎么发现?**
每分片 HH256 内联(:44-75):读时校验失败即丢片重建+入 MRF heal。

**Q4:写时部分盘离线?**
动态加 parity 上限至 N/2(:1306-1333):数据分片不变,校验分片增多;过半离线写失败。

**Q5:data==parity 时写 quorum 为什么 +1?**
(:1338-1341):防两半脑裂各认自己多数——显式 +1 破平局。

**Q6:shard 大小 1MiB 为什么?**
(:37):RS 编码的矩阵运算粒度与内存的折中。

**Q7:xl.meta 每盘都有,内容一样吗?**
是:每盘存全量元数据副本——quorum 读取任取。

**Q8:读时怎么选盘顺序?**
按 Erasure.Index 重排+本地盘 prefer(:369-388):减少网络与跨盘。

**Q9:heal 是读触发的吗?**
读时发现缺失/损坏会照常服务并静默入 MRF(:400-418)——服务与自愈解耦。

**Q10:EC 的分片映射能变吗?**
hashOrder 按对象名+set 盘数(:178-192):set 不变映射不变。

## 2.6 小结与深挖方向

本章结论:**EC="Reed-Solomon 分片+每分片 bitrot+quorum 判定+读时自愈萌芽"**;默认表的保守性(≥8 盘=4)是可靠性冗余的产品选择。深挖:

1. klauspost/reedsolomon 的 SIMD(avx2/avx512)实现占比;
2. hashOrder(:178-192)的 crc32 移位在热点对象的均匀性;
3. 动态 parity(:1306-1333)对读放大(更多 parity=读更少分片)的反直觉收益;
4. HH256S 内联(:44-75)与传统独立 hash 文件的 IO 差;
5. MRF 队列(100000,卷一 05)满时的降级顺序。
