# 第 03 章 · 对象版本化:xl.meta 里的时间轴

> 基线:commit `7aac2a2`。行号以 cmd/xl-storage-format-v2.go、cmd/erasure-object.go、internal/bucket/ 为准。

## 3.0 全景:一个对象的版本生命周期

```
put v1 → put v2 → delete marker → list(全版本)→ ILM expiry
xl.meta = "XL2 " 魔数 + major/minor + 版本个数
        + 逐版本(16B 短 header + msgp 全量 meta)+ xxhash CRC + 内联数据
数组按 ModTime 降序,versions[0] 恒为最新(xl-storage-format-v2.go:73-88;
addVersion 按 ModTime 头部插入 :1141-1173)
```

条目是 **tag 联合体**:ObjectType(VersionID/DataDir/纠删参数/分片表/MetaSys/MetaUser)、DeleteType(仅 VersionID/ModTime/MetaSys,**零数据占用** :149-153)、LegacyType,外加只对扫描器可见的 free-version(分层内容异步回收跟踪)。

## 3.1 版本化配置与删除语义

VersioningConfiguration(internal/bucket/versioning/):**Enabled/Suspended 的行为差异**:Enabled 时 put 必发版本号(erasure-object.go:1346-1352,mustGetUUID),DataDir 每次一换;Suspended 时写入**原地替换 null 版本**。删除语义三分(:2043 `deleteMarker := opts.Versioned`):

- 未开版本化=摘 null 记录+trash DataDir(用户视角真删);
- 开了且不带 versionID=往数组头插 **DeleteType 删除标记**(数据分毫未动,GET 得 404、指定版本得 405);
- 带 versionID=摘指定记录。

**删除始终是元数据操作**:摘/插记录,数据目录经 rename-to-trash 两阶段回收;盘上仲裁统一 N/2+1;数组空了才删 xl.meta 本体(xl-storage.go:1397-1412)。读版本选择:带 VersionID 走 ReadVersion,否则 ReadXL 取 versions[0](:753-762)。

## 3.2 ILM 与批量删除

ILM(生命周期)由扫描器驱动(05 章 data-scanner 的 applyActions :1036-1162):非 current 过期要求 **NewerNoncurrentVersions 与 NoncurrentDays 同时满足,锚点 SuccessorModTime**(lifecycle.go:412-434)。SSE 密钥材料按版本存于 MetaSys/MetaUser(internal/crypto/metadata.go:24-65)。批量删除先真删后最多一个标记(erasure-object.go:1736-1752)。

## 3.3 设计动机

1. **为什么元数据内联在每盘**:xl.meta 随分片同盘——读一个版本零跨盘;**数据与元数据的物理共存**是 MinIO 极简架构的根;
2. **为什么版本数组最新在前**:读最新(99% 场景)O(1);老版本顺序追加在尾部;
3. **删除标记与 S3 对齐**:DeleteMarker 的 GET 404/指定版本 405 是 S3 API 语义的精确实现(:149-153 的零占用设计);
4. **Suspended 的原地替换**:暂停版本化后 put 覆盖 null 版本——**桶配置变化不改变"最新即全部"的用户视角**。

## 3.4 FAQ

**Q1:xl.meta 是 JSON 吗?**
是 msgp 流(header "XL2 "+二进制)——性能考虑的紧凑编码(:73-88)。

**Q2:删了还能恢复吗?**
版本化桶:删的是标记,数据在;非版本化桶:进 trash 两阶段回收(短暂可救)。

**Q3:一个对象最多多少版本?**
无硬限:数组在 xl.meta 内增长;ILM 负责收缩。

**Q4:指定 versionID 删除是真删吗?**
是(:2043 转 false):摘该记录;数据进 trash 两阶段。

**Q5:free-version 是什么?**
只对扫描器可见的跟踪条目:分层(tiering)内容异步回收的记账。

**Q6:SSE 加密对象的密钥在哪?**
按版本存于 MetaSys/MetaUser(:24-65):元数据随版本生灭。

**Q7:版本顺序会乱吗?**
按 ModTime 头部插入(:1141-1173):时钟偏移可能导致顺序与操作序不一致。

**Q8:ILM 删除与手动删除路径一样吗?**
都走删除标记/摘记录;ILM 由扫描器驱动(:1036-1162)。

**Q9:xl.meta 什么时候重写?**
版本增删时(:1397-1412):每盘重写,quorum 提交。

**Q10:0 字节对象的 quorum 为什么 +1?**
(:476-479):零数据对象靠元数据 quorum 就能判定——防"半个标记"歧义。

## 3.5 小结与深挖方向

本章结论:**版本模型="单 xl.meta 版本数组(最新在前)+tag 联合条目+删除即元数据操作"**。深挖:

1. ModTime 排序(:1141-1173)在时钟偏移多节点的版本倒挂;
2. free-version 的回收进度(:扫描器)与 tiering 的交互;
3. DeleteType 零占用在海量删除标记下的 xl.meta 膨胀;
4. trash 回收的触发时机与磁盘占用峰值;
5. SSE 密钥材料(:24-65)与 KMS 不可达的降级读取。
