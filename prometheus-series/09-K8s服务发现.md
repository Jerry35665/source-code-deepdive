# 第 09 章 · K8s 服务发现:事件、快照与标签映射

> 基线:commit `b0f312b`。行号以 discovery/kubernetes/ 为准。metaLabelPrefix=`__meta_kubernetes_`(kubernetes.go:57)。

## 9.0 全景:K8s 对象到抓取目标

```
client-go informer(LIST+WATCH,protobuf 编码优化 :336)
  → 事件(Add/Update/Delete)→ workqueue(key=namespace/name)
  → 消费端从 informer store 读对象当前快照 → 重算整个 TargetGroup
  → 发 SD manager(通用层,卷二 06 章的"全量快照"消费模型)
```

**Pod 发现是"事件→快照重算"模型**:Add/Update/Delete 三种 handler 一律只把 key 入 workqueue(pod.go:89-102)——workqueue 去重把事件风暴折叠成终态计算;增改是"整组替换",**删除是 store 查无此 key 后发只含 Source 的空 Group**(pod.go:239),由 SD manager 按 Source 删除(discovery/manager.go:485)。

## 9.1 标签映射的两层与 owner 链

通用层 addObjectAnnotationsAndLabels(kubernetes.go:967):每个 label/annotation 生成"值+present"双标签;addObjectMetaLabels(:980)加 name。pod 层 podLabels(pod.go:292-346)输出 ip/ready/phase/node_name/host_ip/uid,再经 **GetControllerOf 做 owner 链回溯**:pod→RS 查 Deployment 名(:313-325),pod→Job 查 CronJob 名(:326-342)——`__meta_kubernetes_pod_deployment_name` 不是直接字段而是**二次 join**。node/namespace/RS/job 变更通过索引反查(ByIndex,pod.go:466-488)波及相关 pod 重算。buildPod(:366-440)按(容器×端口)展开目标:有端口则 podIP:containerPort,无端口产出匿名目标(:409-419)。

## 9.2 resync 禁用与 RBAC

**全包禁用 informer resync**(resyncDisabled=0,kubernetes.go:385-386,注释称重发会扭曲指标)——SD manager 的全量重发模型不依赖 resync;in-cluster RBAC 凭据(ServiceAccount,:307-323);protobuf 编码做**大集群 LIST 优化**(:336);HasSynced 门闩保证"LIST 回放即初始全量"(pod.go:206-211)。

## 9.3 设计动机

1. **为什么"事件→快照重算"而非增量 diff**:K8s 对象的终态计算幂等且简单——事件风暴折叠后只算一次终态(与 K8s 控制器的 level-triggered 同构,第一系列 07 卷);
2. **为什么全包禁 resync**:resync 重发会让 SD manager 的去重计数扭曲指标(:385-386 注释)——正确性考虑压过容错惯性;
3. **owner 链回溯**: Deployment 的元数据要透过 RS 才能到 pod——两层间接是 K8s 对象模型的真实形状;
4. **RBAC 最小权限**:ServiceAccount 只需 list/watch node/pod/service/endpointslice——发现是只读能力。

## 9.4 FAQ

**Q1:Pod 删除怎么传播?**
发只含 Source 的空 Group(pod.go:239):SD manager 按 Source 删除(:485)。

**Q2:`__meta_kubernetes_pod_deployment_name` 怎么来的?**
owner 链回溯:pod→RS→Deployment(:313-325)——二次 join。

**Q3:为什么禁用 informer resync?**
重发会扭曲 SD 指标(:385-386);全量重发由 HasSynced 后的 LIST 回放承担。

**Q4:一个大集群(万 pod)的内存?**
informer store 全量缓存+protobuf LIST(:336):内存换 API server 压力。

**Q5:endpointslice 的 dual-stack 怎么去重?**
(:525-546):同端点双栈地址合并。

**Q6:无端口的 pod 会成为目标吗?**
会:address=podIP 的匿名目标(:409-419)——供 blackbox 类探测。

**Q7:标签冲突(pod 与 namespace 同名标签)怎么办?**
present 双标签+前缀分层:来源可辨(:967)。

**Q8:node 变更为什么影响 pod 目标?**
索引反查(:466-488):调度到该 node 的 pod 需重算 `__meta_kubernetes_node_*`。

**Q9:SD 与 relabel 的分工?**
SD 产 `__meta_*` 原料,relabel(卷二 06 章)消费成最终目标——原料/成品分离。

**Q10:API server 挂了 Prometheus 会停吗?**
informer cache 仍在:最后已知目标继续抓——K8s 系统的自愈惯性。

## 9.5 小结与深挖方向

本章结论:**K8s SD="informer 快照重算+两层标签映射+owner 回溯"**;与 K8s 控制器(第一系列 07 卷)共享 level-triggered 哲学。深挖:

1. workqueue 去重(:89-102)在 pod 风暴(滚动更新)的折叠率;
2. owner 链回溯(:313-342)在自定义 CRD owner 的盲区;
3. protobuf LIST(:336)的兼容开关历史;
4. ByIndex 反查(:466-488)的索引维护成本;
5. dual-stack 去重(:525-546)与 hostNetwork pod 的边界。
