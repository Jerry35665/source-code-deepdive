# 第 03 章 · 磁盘块与查询:不可变的时序档案

> 基线:commit `b0f312b`。行号以 tsdb/block.go、tsdb/index/index.go、tsdb/chunks/chunks.go、tsdb/tombstones/ 为准。

## 3.0 全景:block 的四件套

```
block = ULID 目录:
  meta.json   身份证(ULID/minTime/maxTime/stats/compaction 谱系,tsdb/block.go:164-181)
  index       单文件倒排索引
  chunks/     512MB 分片的样本文件
  tombstones  可选墓碑
OpenBlock = 装四个 reader(block.go:355-406):meta(:365)+chunks mmap(:370)+index mmap(:380)+墓碑整读(:386)
```

meta.json 原子写 tmp+Replace(:291-326);块时间区间半开 [MinT,MaxT)(:750-754)。

## 3.1 index 格式:倒排索引的落地

布局(index.go:41-43;docs/format/index.md):magic 0xBAAAD700→Symbols→Series→Postings→Postings Offset Table→TOC。**TOC 在文件尾 52 字节**(:181-203,:689):先读尾定全部段。Symbols:排序字典,读取端每 32 个符号取一个偏移锚点(symbolFactor=32,:1164),Lookup=锚点跳转+最多走 31 个 uvarint(:1193-1215)。Series 段:每条 **16 字节对齐——series ID=文件偏移/16**(:54,:465-471):4 字节 ref 寻址 64GB;标签存符号序号;chunk 的 mint/maxt/ref 全差分编码(:494-512 写/:1806-1877 读)——**索引里带 chunk 时间范围,不碰 chunks 文件即可时间剪枝**。Postings:raw 编码 `<BE32 len><BE32 ref>×n`(:834-844);查找=偏移表内存抽样二分(:1568)→盘上顺序游走(:1490-1524)→mmap 直读;v2 偏移表打开时只加载 1/32 样本(:1075-1099)。

## 3.2 chunks 与 tombstones

chunks:魔数 0x85BD40DD+8B 段头(chunks.go:34,:41);**块分片默认 512MiB**(:300)(Head 段才是 128MiB,head_chunks.go:59);BlockChunkRef=分片号<<32|偏移(:553),**写盘即生成**;mmap 零拷贝读(:686-724)。tombstones:`<uvarint ref><varint mint><varint maxt>` 扁平流+CRC(tombstones.go:142-154);查询过滤双层:chunk 级 IsSubrange(querier.go:628)+样本级 DeletedIterator(:1338);**trim 伪装成墓碑**的技巧(:648-653)。

## 3.3 查询:三层剪枝

DB.Querier 只开时间重叠的块并 NewMergeQuerier 合并(db.go:2585-2589,:2653);块内三层剪枝(querier.go:582-661):块级 O(1)(时间不相交)→索引求值(postings 交集)→序列游标逐 chunk。跨块合并 NewMergeChunkSeriesSet 与 compaction 共用(D 章)。

## 3.4 设计动机

1. **为什么 2h 一块**:块的不可变性让"写"永远只发生在 Head;2h 是"保留窗口粒度"与"打开文件数"的折中(db.go:55-56);层级 3 倍指数 [2h,6h,18h…](compact.go:41-50);
2. **为什么 index 与 chunks 分离**:索引常驻内存(mmap),样本按需读——读写模式完全不同;
3. **16 字节对齐=ID**:地址即身份,零映射表——与 Git 的"内容即地址"同族(Git 卷一 01 章);
4. **meta.json 是块的身份证**:ULID+时间界+统计——不可变对象的"自描述"让校验/调度/清理都不需要中央注册表。

## 3.5 FAQ

**Q1:一个 block 目录多大?**
chunks 每 512MiB 分片(:300),块内 2h 数据——取决于基数与样本率。

**Q2:删一个 series 立刻生效吗?**
写墓碑,查询过滤(:628/:1338);compaction 重写才物理回收。

**Q3:TOC 为什么放文件尾?**
写完才知道各段偏移:尾部 TOC 一次定位(:181-203)。

**Q4:Postings 查找要读几次盘?**
偏移表在内存(:1075-1099 抽样加载),盘上只走目标区间(:1490-1524)。

**Q5:mmap 的文件还能被压缩删吗?**
compaction 时先 unmmap:块是不可变单元,重写即新块。

**Q6:16 字节对齐换来什么?**
ref=offset/16 的整除关系(:465-471):ID 即地址,校验免费。

**Q7:块的半开区间为什么重要?**
[MinT,MaxT) 保证相邻块无缝不重叠(:750-754):合并的正确性前提。

**Q8:index 的 magic 0xBAAAD700 会变吗?**
version 字段独立(:41-43):格式演进靠版本号+TOC。

**Q9:符号表锚点 32 的取舍?**
(:1164):锚点表内存÷32,查找多走≤31 步 uvarint——抽样加载的经典。

**Q10:查询要开多少个文件?**
重叠块数×(index+chunks 分片)——mmap 使 fd 成本可接受。

## 3.6 小结与深挖方向

本章结论:**磁盘块="自描述四件套+TOC 尾锚+对齐 ID+三层剪枝"**;不可变性是全部简单之源。深挖:

1. symbolFactor=32(:1164)在超大符号表的二分精度;
2. 512MiB 分片(:300)在低配磁盘的 mmap 页表压力;
3. tombstones 增长的查询退化(:628);
4. BlockChunkRef 的高 32 位(:553)在 8TB+ 数据的上限;
5. v2 偏移表抽样(:1075)与真实 posting 分布的匹配。
