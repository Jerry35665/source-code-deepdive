# 源码深读 · 系统开源项目解读系列

> 用 AI 逐行阅读顶级开源项目源码,产出"可对照源码验证"的中文解读卷本。所有行号引用基于明确 pin 的 commit,所有结论可复算、可证伪。
> 总预算:**100,000,000 token**。消耗台账见 [LEDGER.md](LEDGER.md)。

## 一、选型逻辑:一条"从单机到分布式到 AI"的叙事线

八个项目不是随机堆叠,而是一条完整的故事线——**一台机器如何用尽资源 → 多台机器如何协作 → 新时代的计算(推理)**:

| 卷 | 项目 | 语言 | 在叙事线中的位置 | 代码规模 | 状态 |
|---|---|---|---|---|---|
| 一 | **Redis** | C | 单机内存系统:事件循环、编码艺术、复制时钟 | ~17 万行 | ✅ 完成 |
| 二 | **SQLite** | C | 单机磁盘系统:B-tree、事务、最伟大的测试文化 | ~22 万行 | ✅ 完成 |
| 三 | **LevelDB** | C++ | 存储引擎教科书:LSM-Tree 全家桶 | ~2.6 万行 | ✅ 完成 |
| 四 | **etcd(raft)** | Go | 分布式共识:Raft 参考实现 | raft 库 ~1.2 万行 | ✅ 完成 |
| 五 | **Nginx** | C | 事件驱动网络服务:与 Redis 的 ae 互为镜像 | ~20 万行 | 📋 已排期 |
| 六 | **Kafka** | Java/Scala | 分布式日志:把"顺序写"做成平台 | ~40 万行 | 📋 已排期 |
| 七 | **Kubernetes** | Go | 声明式 API 与控制循环 | ~35 万行 | 📋 已排期 |
| 八 | **llama.cpp** | C/C++ | 端侧 LLM 推理:量化、KV cache、计算图 | ~10 万行 | 📋 已排期 |

备选池(PostgreSQL、Git、curl、FFmpeg、Valkey):若上述某卷完成后预算未达,从池中补。

## 三、每卷统一模板

03-核心机制 B      (如:数据结构底座 / 事务与锁)

05-核心机制 D      …
06-核心机制 E      …
07-核心机制 F      …
08-工程收尾         测试文化、性能工程、演进史、全卷小结

每章固定结构:开篇导语 → 逐段解读(ASCII 图 + ≤15 行代码片段)→ 设计动机与取舍 → FAQ(8-12 条)→ 小结与深挖方向。

## 四、预算管理(目标 1 亿 token)

- **记账口径**:subagent 消耗取工具返回的精确计数;主会话消耗按"读入字符数/4 + 产出字符数×1.6"估算,标注为估算值;
- **每卷配额**:约 1,100 万-1,800 万 token(8 卷合计 ≈ 1 亿);
- **消耗模型**:一个卷 = 浅克隆 + 代码调查 + N 份子系统深读报告(每份 300-600 万)+ 主会话审阅与撰写(约 50-150 万);
- **进度追踪**:每会话结束更新 LEDGER.md,预算剩余 = 1 亿 - 累计消耗。

## 五、续作 Runbook(下一会话如何继续)

**第 4 卷《etcd/raft》启动步骤**(预计消耗 ~800 万;raft 库可聚焦,建议单会话完成):

1. 克隆(etcd 仓库较大,浅克隆 + 只需 raft 库与 etcdserver 骨架):
   ```bash
   git clone --depth 1 https://gitee.com/mirrors/etcd.git repos/etcd
   # 失败则: git clone --depth 1 https://gh-proxy.com/https://github.com/etcd-io/etcd.git
   ```
2. 代码调查(pin commit;确认 raft 库位置 raft/ 目录约 1 万行);
3. 串行派出 4 个子系统调研 agent(按预算控量,每份 4000-8000 字):
   - A Raft 核心状态机(raft.go:tick/Step/状态转换/任期与日志)
   - B 日志复制与提交(log.go、进度追踪 progress、flow control)
   - C 选举与安全性(选举随机超时、投票约束、ReadIndex/lease read)
   - D 工程视角(wal 格式、etcdserver 如何驱动 raft、测试与线性一致性验证)
4. 主会话读报告 → 撰写 8-9 篇正文 → 更新 LEDGER.md 与本 README 进度表。

**agent 提示词模板**(替换《》内容即可复用):

> 你是资深《语言》工程师,正在为《源码深读·系统开源项目解读系列》《卷 N·项目》撰写《子系统》调研报告。仓库位置:《绝对路径》(分支与 commit:《x》)。调研范围:《文件清单与要点》。硬性要求:① 必须实际 Read/Grep 源码后再写,禁止凭记忆杜撰,所有结论标注 `文件:行号`;② 用 Write 写入《报告路径》,6000-12000 字,结构:全景→逐段解读(ASCII 图)→设计动机→FAQ 8-12 条→深挖问题 3-5 条;③ 最终回复只给字数、覆盖文件、3 个最有价值发现。

## 六、质量红线

1. 每个论断必须落到 `文件:行号`,不确定的写"未核实";
2. 与流行说法冲突时,以 pin 的 commit 为准并显式指出冲突(卷一范例:backlog 并非环形缓冲、键级 TTL 未迁移 ebuckets、io_threads 已代际重写);
3. 代码片段 ≤15 行,只做"读的引路牌",不替代源码;
4. 每卷必须有"深挖问题清单"——承认边界比假装完整更有价值。
