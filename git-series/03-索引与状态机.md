# 第 03 章 · 索引与状态机:status 为什么有时自己变慢

> 基线:commit `47ce805`。行号以 read-cache.c、dir.c、wt-status.c、sparse-index.c 为准。

## 3.0 全景:三方模型与 index 的本质

```
worktree(磁盘)  ⇄  index(.git/index)  ⇄  HEAD(01 章对象)
      git add ↓          git commit ↓
status = 三方对比:worktree vs index(run_diff_files)
                  + index vs HEAD(run_diff_index CACHED)
                  + untracked 扫描(fill_directory)
        (wt-status.c:865-888,执行序 662/708/830)
```

index 本质=**扁平化的树快照+stat 缓存**:把 HEAD 树全部展开成排序列表,每条目带 stat 字段,使"文件变没变"多数时候不用读文件内容——**拿磁盘上的 stat 换取内容扫描**,这是 git 性能的第一根支柱。

## 3.1 index 文件格式:DIRC 与逐字段

`.git/index`:12 字节头(`"DIRC"` 魔数 0x44495243+版本+entry 数,read-cache-ll.h:12-17)→ 定长字段 entry 序列 → 扩展区(TREE/REUC/LINK/UNTR/FSMN/EOIE/IEOT)→ 尾部整体哈希(read-cache.c:3090)。

entry 二进制(read-cache.c:1681-1698):ctime(8)+mtime(8)+dev/ino/mode/uid/gid/size(各 4,**大端,为跨 NFS**)+oid(20/32)+flags(2:namelen 12bit/stage 2bit/CE_VALID/CE_EXTENDED)+可选 flags2+变长路径。默认版本 v2(整名+8 字节对齐,:2668-2673);**v4 路径前缀压缩**:"相对上一条删除 N 字节(varint)+新增后缀",读端 decode_varint 拼前缀(:1833-1847),写端求公共前缀(:2679-2692)。读默认不重算尾部哈希(:1709,1729-1730)只查魔数;EOIE/IEOT 扩展支撑多线程解析(:2285-2311)。

## 3.2 racy git:stat 缓存的阿喀琉斯之踵

**问题**(read-cache.c:418-433 官方注释):同一秒内"add 后再改内容",mtime+size 可能完全相同——stat 比对判"干净",实际脏了。

三层防线,锚点是 **index 文件自身的 mtime**:

1. 锚定:读时把 index mtime 存 `istate->timestamp`(:2313-2314),写后更新(:3102-3103);
2. 判定:条目 mtime ≥ index mtime 即 racy(is_racy_stat,:353-366)——"比索引还新的条目不可信";
3. 处置:读侧对 racy 条目升级为**内容哈希核对**(ie_match_stat,:434-439);add 侧宁假脏(CE_MATCH_RACY_IS_DIRTY,:729);写侧 `ce_smudge_racily_clean_entry` 核实后把 size 置 0 作永久"可疑"标记(:2574-2622,置 0 在 :2620)——读端识别规则: size==0 且 oid 非空 blob ⇒ 必脏(:344-348)。

**"status 有时自己变慢"就是防线 3 在工作**:racy 条目触发内容哈希,大文件一秒变分钟——机制不是 bug,是正确性的价格。

## 3.3 cache-tree:commit 的免重建

index 里缓存树结构(cache-tree.c):commit 时子树 oid 已在对象库则 `update_one` 早退(:336-339),直接用 `cache_tree->oid`(builtin/commit.c:1938)——**增量提交只重建脏子树**,不需重算全部 tree 对象。与 04 章 pack 的 delta 窗口、02 章引用事务并列:git 的三大"只算增量"设计。

## 3.4 untracked 扫描与 sparse index

untracked 用**目录级剪枝**:`treat_directory`+path_recurse-only(dir.c:1966-2090,2698-2793)——读到一个与 .gitignore 匹配的目录就整棵跳过,status 的 untracked 部分 O(目录数) 而非 O(文件数)。

**sparse index**(近三年大变化):把 index 条目按 cache-tree 的 entry_count 区间**整段替换为 040000 目录条目**(sparse-index.c:95-136)——百万文件仓库的 index 降到千级条目;仅 cone 模式限定(:164,202-203),与 split index 互斥(read-cache.c:2999-3000)。三条 index 膨胀退路的分工:split index(切扩展)、sparse index(切目录)、untracked cache(缓存扫描)。

## 3.5 设计动机

1. **index 是文件而非数据库**(对照 SQLite):格式固定+全量重写+原子 rename——当读写比极高且数据量可控时,"扁平文件+stat 缓存"比 B 树更省;膨胀后才有 split/sparse 的后手;
2. **stat 缓存是乐观并发**:大多数文件不修改——先信 stat,错了再用内容哈希兜底(racy 三层防线);这是"乐观锁+升级路径"的教科书;
3. **格式演进按痛点驱动**:v2→v4(路径压缩,深目录仓库)、EOIE/IEOT(多线程解析)、sparse index(巨型 monorepo)——每次演进都对应一类真实仓库;
4. **大端字段为跨 NFS**:1990 年代的分布式文件系统现实刻进了 2020 年代的格式。

## 3.6 FAQ

**Q1:git status 有时特别慢,为什么?**
racy 条目触发内容哈希核对(:434-439)——刚改过文件的仓库必现;untracked cache/sparse index 可缓解。

**Q2:为什么 add 完立刻改文件会出诡异行为?**
racy git 原始问题:stat 全同判假干净(:418-433)——三层防线把风险压到 index mtime 锚点内。

**Q3:index 里的 size=0 条目是什么?**
smudge 标记(:2620):曾被怀疑 racy,读端按"必脏"处理(:344-348)。

**Q4:commit 为什么不用重建全部树对象?**
cache-tree 缓存子树 oid,脏子树才重建(:336-339,builtin/commit.c:1938)。

**Q5:v4 格式为什么不是默认?**
路径前缀压缩(:2679-2692)只对深目录大仓库收益明显,默认保守 v2。

**Q6:sparse index 和 sparse checkout 是一回事吗?**
不是:后者是"只检出部分文件"的用户功能;前者是 index 存储格式的目录折叠(:95-136),是后者的性能地基。

**Q7:status 的三方对比有顺序讲究吗?**
worktree→index→HEAD(wt-status.c:865-888)——先扫磁盘(最慢),期间可并行预取对象。

**Q8:untracked cache 存的是什么?**
目录扫描结果缓存(失效入口 dir.c:4020):读过且未变的目录不再进文件系统。

**Q9:index 会损坏吗?怎么发现?**
尾部哈希(:3090);读默认不验(:1709)——显式 `git fsck` 或写路径校验兜底。

**Q10:为什么 entry 字段是大端?**
跨 NFS 共享 index 的历史决定(:1681-1698)——1990 年代网络的幽灵。

## 3.7 小结与深挖方向

本章结论:**index = "扁平快照 + stat 乐观缓存 + racy 三层防线"**;性能魔法与正确性风险是同一枚硬币。深挖:

1. index mtime 锚点在 WSL/NFS 高精度 mtime 文件系统上的边界;
2. sparse index 与 partial clone(04 章)组合的 monorepo 全链路;
3. cache-tree 在 merge(06 章冲突三路)后的失效策略;
4. v4 varint 与 fanout(04 章 idx)两种压缩的分界;
5. EOIE/IEOT 多线程解析的内存-并行权衡(read-cache.c:2285-2311)。
