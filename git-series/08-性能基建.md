# 第 08 章 · 性能基建:commit-graph、pack bitmaps 与可达性标记

> 基线:commit `47ce805`。行号以 commit-graph.c、pack-bitmap.c、reachable.c 为准。卷一 01 章 commit-graph 只提了一句,04 章 midx/cruft 已讲——本章专讲"对象库之上的辅助索引"三件套。

## 8.0 全景:对象库之上的加速层

```
对象库(01 章)─ pack(04 章)─ midx
        ↑ 之上的辅助索引(可删可重建,不承载真值)
commit-graph   提交图侧信道:objects/info/commit-graph
pack bitmap    可达性位图:pack 内 EWAH 压缩
reachable      可达性标记器:gc/prune 的前置遍历
```

**三件套都不是存储而是索引**:删掉它们 git 依然正确(变慢),这决定了它们的工程形态——低成本可重建、校验失败即弃用回退。

## 8.1 commit-graph:chunk 格式与零解压读取

chunk 格式(commit-graph.c:44-53 常量表,与 gitformat-commit-graph.adoc:86-170 一一对应):OIDF(256 项扇出)/OIDL(排序 OID)/CDAT(根树+父位置+日期+topo level)/GDA2(修正代偏移)/EDGE(八爪鱼合并)/BIDX+BDAT(changed-path Bloom)。**读路径**:`repo_parse_commit_internal` 先试 `parse_commit_in_graph`,命中即 return——父指针用整数位置查 OIDL,**不再扫 "tree/parent" 文本、不再解压**(commit.c:625);GDA2 的代数值 = 提交日期+31bit 偏移,溢出走 GDO2 八字节表(:899-914),混合链退 topo level(:524-543)。这是 01 章 parse_object 四层优化的第二层(commit-graph 层)的本体。

分片(split)链的合并判据:**第 N 层提交数 ≤ 新层数×2 就合并**(size_mult 默认 2,commit-graph.c:2311-2312,:2291)——几何增长的 LSM 变奏,与 02 章 reftable 栈压实同构。

**Bloom filter(BIDX/BDAT)**:murmur3 双哈希(seed 0x293ae76f/0x7e646e2c,hashes[i]=h0+i*h1,bloom.c:225-243;默认 7 哈希/10bit/路径 512 上限,bloom.h:44-45),key 是**路径的全部祖先前缀**(:286-324),超限写单字节全 1 截断。消费点在 `rev_compare_tree` 挂 `check_maybe_different_in_bloom_filter`(revision.c:810):`git log -- path` 先问 filter,"肯定没动过"即跳过树 diff——**误报只白做一次 diff,正确性无损**,这是概率结构在正确性关键路径的安全用法。

## 8.2 pack bitmap:位图与"字节级复用"

EWAH 压缩位图(RLW:1bit 重复位+32bit 重复数+31bit 字面量数)。**选点策略三段步长**(pack-bitmap-write.c:1014-1036):前 100 个提交必选、中段间隔渐增、2 万之后封顶 5000(MUST_REGION/MIN_COMMITS/MIN_REGION/MAX_COMMITS)——**位点必须少**:每 commit 一次 bitmap 是 O(N²) 存储;间隔内优先 ref 尖端与合并提交。构建按逆拓扑逐 commit OR 父位图,再 `compute_xor_offsets` 压缩。

**复用是本章的皇冠**(pack-bitmap.c):两层——walk 层 wants/haves 各一次 OR/AND_NOT;pack 层 `try_partial_reuse` **只要 delta 的 base 也在复用集内就整体放行,把 pack 原始字节 memcpy 进输出流**(:2366-2367 准入,:2385-2407 首选 pack 全 1 区间按整字 memcpy)——**服务端 fetch 时完全不重算 delta**,这是 GitHub 级 fetch 提速的本体(:2481-2596 的 MIDX 多 pack 复用,末尾 AND_NOT 剔除已复用位 :2592)。verify 用 `rev-list --test-bitmap` 重算可达集比对。

## 8.3 reachable:gc 的前置遍历

`mark_reachable_objects` 汇集索引、refs、worktree HEAD、rebase 状态文件、reflog 为根(roots 集比 fsck 更宽,reachable.c:302-358),然后**优先走位图**标 SEEN——`prepare_bitmap_walk` 命中则 `traverse_bitmap_commit_list` 直接标,普通遍历仅回退(:337-345);最后按 mtime 把宽限期内"无 commit 指着"的松散对象补进遍历。prune(gc)是唯一消费者——04 章 cruft pack 的输入由这里产生。name-rev 从 ref 尖端向父广播名字,merge 分支记 65535 权重,剪枝直接消费 commit-graph 代数。

## 8.4 性能对照与设计动机

| 操作 | 无索引 | 有索引 |
|---|---|---|
| commit 解析 | 解压+文本扫描 | O(1) 位置查(:625) |
| log -- path | 逐提交树 diff | Bloom 否定即跳过(:810) |
| fetch/push | 重算全部 delta | 位图复用 memcpy(:2385) |
| gc/prune | 全图遍历 | 位图标记(:337) |

1. **辅助索引不进对象库本体**:对象库的真值地位不可动摇——索引可删可重建,校验失败即弃;对比数据库的二级索引同构;
2. **Bloom 的安全用法**:概率结构只做"否定优化"(确定没动→跳过),不做"肯定优化"——误报方向必须无害;
3. **位图复用是传输层的缓存**:服务端把"上次算过的 delta 字节"直接送出——缓存命中的单位从对象细到"pack 字节区间";
4. **选点少是特性**:位图位点的稀疏性是存储-命中率的显式权衡(:1014-1036 四常量可读出策略演进)。

## 8.5 FAQ

**Q1:commit-graph 损坏会怎样?**
校验失败即弃用回退普通解析(:625 的回退路径)——索引坏不影响正确性。

**Q2:git log -- path 为什么有时飞快?**
changed-path Bloom"确定没动"即跳过树 diff(revision.c:810);误报只多算一次 diff。

**Q3:大仓库 fetch 提速靠什么?**
服务端 bitmap 复用:delta 字节整块 memcpy(:2385-2407)——不重算 delta,网络与 CPU 双省。

**Q4:位图为什么只有少数 commit 有?**
存储 O(N²) 不可行:选点三段步长封顶 5000(:1014-1036)。

**Q5:gc 什么时候用位图?**
mark_reachable_objects 先试 prepare_bitmap_walk(:337-345),命中免全图遍历。

**Q6:commit-graph 的 split 是什么?**
分片链按几何判据合并(:2311-2312)——避免每次 write 全量重写,与 reftable 栈压实(02 章)同构。

**Q7:Bloom filter 的 key 为什么用路径前缀?**
目录重命名意味着整树变化:祖先前缀命中即否定整目录(:286-324)。

**Q8:GDA2 的代数为什么要修正?**
顶部代数会随时间溢出 31bit,用"日期+偏移"表示(:899-914)——把绝对值变成相对值。

**Q9:位图复用的准入条件?**
delta 的 base 必须也在复用集内(:2366-2367)——否则链断裂,只能现场重算。

**Q10:这些索引怎么重建?**
git commit-graph write / git repack -b(写位图)/ git multi-pack-index write——全部幂等。

本章结论:**性能基建 = "可丢弃的辅助索引 + 概率结构的否定式安全用法 + 字节级复用缓存"**。深挖:
