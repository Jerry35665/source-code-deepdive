# 第 07 章 · 工程文化:20 年 C 项目的自维持体系(卷末)

> 基线:commit `47ce805`。行号以 t/、Documentation/CodingGuidelines、Makefile、tools/coccinelle/ 为准。本章对标 FFmpeg 卷 05 章的 FATE/configure 章。

## 7.0 全景:四柱体系

```
规范柱(CodingGuidelines)──"每条禁令都有真实老平台背书"
测试柱(t/ 1058 脚本 + unit-tests)──"测试即规格"
构建柱(Makefile 4134 行 + 特性开关)──"minimal 可裁剪"
流程柱(邮件补丁 + maint/next/seen)──"无需预授权的评审文化"
        ↓
coccinelle 语义补丁(四柱之外的独特实践:机械重构即代码)
```

## 7.1 规范柱:测试气球制

CodingGuidelines(1025 行)开篇是 **POSIX 三段论**(:4-19):不教条遵守 POSIX,也不鲁莽依赖扩展——每条禁令都有真实平台背书:`%z` 禁用因 MinGW(:324-327),IBM XLC 禁令(:328-330)。C99 特性走**"测试气球"制**逐个试点(:279-330):复合字面量 2024 年入气球、2026 年中拟全量采纳(:314-320)——**语言特性升级像产品发布一样有灰度**。

命名法自带生命周期语义:`struct S` + `S_verb()`、`S_init/release/clear/free`(:614-650)——**文字版 RAII**,不靠语言机制靠纪律。两个容器的注脚是文化样本:strbuf.h:5-8(低层原语禁令)与 strvec.h:3-8(argv 兼容不变量)——**不变量写在头文件最显眼处**。

## 7.2 测试柱:shell 宏与"已知 bug 存档"

1058 个 tNNNN.sh 端到端脚本+t/unit-tests/ 28 个 Clar C 单元测试。框架核心是 shell 宏→退出码→计数器,输出 TAP 可被 prove 接管:

- `test_expect_success`/`test_expect_failure`(t/test-lib-functions.sh:924/:901);
- **`test_expect_failure` 的语义是"已知 bug 的自动化存档"**(t/README:897-900):bug 修复时测试转正会输出 `ok ... # TODO known breakage vanished` 并强制提醒 "please update test(s)"(t/test-lib.sh:841-847,:1251-1253)——**修 bug 必须触碰测试**,否则 CI 留痕;
- 测试代码本身受检:魔法退出码 117 预检测试体 `&&` 链断裂(:1084-1094);
- 可复现性:trash 目录隔离(:370)+test_tick 冻结时间;test_done 写 .counts 六项统计(:1231-1248);
- 运行时 API 迁移执法:废弃的 test_i18ngrep 直接改成 `BUG` 炸弹(:1319-1323)——**用崩溃强制迁移**。

对照 FFmpeg FATE:同样是"端到端+自描述",git 的 shell 框架更轻,FATE 的样本库更重——两种"测试即规格"的形态。

## 7.3 构建柱:特性开关矩阵

手写 Makefile(4134 行)带约 59 个 NO_*/USE_* 开关:NO_CURL(:465)可做无网络最小构建、USE_LIBPCRE 仅 PCRE2(:484);**删除的开关直接 `$(error)`**(:1768-1769)——PCRE1 移除后用旧开关构建即报错而非静默忽略;check-builtins 交叉核对(:3978)。sparse/coccicheck 交叉自检。对照 05 章 ffmpeg configure:同样是"可裁剪矩阵",git 用 make 原语,ffmpeg 用 shell 生成——**复杂度预算花在不同的刀刃上**。

## 7.4 coccinelle:语义补丁的独特实践

tools/coccinelle/:**机械重构写成可执行规则入库**——`xcalloc.cocci` 全文仅 10 行(:1-10):把 `calloc` 参数顺序/溢出检查模式自动改写;`*.pending.cocci` 存放"计划中的大重构",coccicheck 检出即视为回归(tools/coccinelle/README:7-45);spatchcache(Redis 缓存的"coccinelle 版 ccache")控制重写成本。**大规模 C 重构不靠人肉 review 100 个 patch,靠规则文件的一个 diff**——这在开源 C 项目里几乎独一份。

## 7.5 流程柱:邮件补丁与维护模型

- **无需预授权**:直接发 patch 到邮件列表,评审目标是"获取帮助"(SubmittingPatches);
- **commit 规范**:50 字符 `area: summary` 标题+祈使句+正文四要素(:334-384)——`git log` 的可读性是设计出来的;
- **分支模型**:maint(维护)/next(集成,停 7 天)/seen(试验,3 周无人问津即弃);
- **维护者自述**:45% 沟通/50% 集成/5% 自研(howto/maintain-git.adoc:15-20,:52-72,:110-114)——**维护者主要工作是让别人能贡献**;功能版 8-10 周一周期,RelNotes 累计 542 份。

## 7.6 设计动机

1. **可移植性纪律反向塑造代码风格**:老平台禁令(%z、声明位置)让代码"更保守但永不惊讶"——20 年不破的 ABI/平台承诺是靠禁令清单维护的;
2. **测试即规格**:test_expect_failure 的 bug 存档语义+117 魔法码——测试框架自身也在被测试;
3. **重构即数据**:coccinelle 把重构从"人肉系列 PR"变成"规则文件的评审"——大库治理工具化的标杆;
4. **流程的最小强制**:邮件+分支模型没有平台锁定(不依赖 GitHub/GitLab)——**git 项目的开发流程本身不依赖 git 托管平台**,自举式讽刺与自洽。

## 7.7 FAQ

**Q1:git 项目自己用什么托管?**
自托管镜像+邮件列表评审——开发流程不依赖任何 git 托管平台。

**Q2:test_expect_failure 和 xfail 有什么区别?**
它是已知 bug 存档:修复后转正会 CI 报 "known breakage vanished"(test-lib.sh:841-847)强制更新测试。

**Q3:为什么禁用 %z?**
MinGW 的 C 库历史缺陷(:324-327)——禁令清单每条都有平台背书,不是教条。

**Q4:coccinelle 补丁是强制吗?**
pending 系列在 coccicheck 中检出即回归(:README:7-45);已采纳规则自动应用到新代码。

**Q5:60 个特性开关怎么不乱?**
删除即 $(error)(Makefile:1768-1769)——退出的开关永久退出。

**Q6:commit 标题为什么限 50 字符?**
`area: summary` + 邮件正文渲染宽度(SubmittingPatches:334-353);`git log --oneline` 的体验是上游设计出来的。

**Q7:next 分支为什么停 7 天?**
集成节奏(maintain-git.adoc:52-72):给下游 reviewer 固定的观察窗口。

**Q8:垃圾测试怎么防?**
退出码 117 预检 `&&` 链断裂(test-lib.sh:1084-1094):测试体自身语法错误立即暴露。

**Q9:20 年 C 代码怎么防内存错误?**
规范(生命周期命名法 :614-650)+sparse+coccinelle+单元测试四层;无 ASan 时代的遗产纪律仍在。

**Q10:新 C99 特性怎么进代码库?**
测试气球(:279-330):先标'实验'试点一两个周期,稳定后全量——语言升级的灰度发布。
