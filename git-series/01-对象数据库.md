# 第 01 章 · 对象数据库:内容寻址与四类对象

> 基线:commit `47ce805`。行号以 object.h、object-file.c、odb/ 为准。此 commit 正值 ODB(object database)多后端重构期——写路径已迁至 odb/source-loose.c 的 vtable。

## 1.0 全景:一个决定推论出整座建筑

Git 的全部存储建立在一个决定上:**对象名 = SHA-1("<类型> <字节数>\0" + 内容)**——对象头参与哈希(object-file.c:102-111,459-473)。由此免费获得:

```
内容 ──SHA1(头+内容)──→ oid ──首字节──→ .git/objects/xx/yyyy…(fill_loose_path,:46-58)
                │
   头在哈希里 ⇒ 类型/长度不可篡改(完整性免费)
   同内容 ⇒ 同 oid(去重免费)
   引用旧对象 ⇒ 旧对象必须存在(不可变性免费)
```

四类对象共用 4 字段基类 `struct object`(parsed:1 + type:3 + flags:29 + oid,object.h:159-164),blob/tree/commit/tag 以 **C 首部嵌入+指针强转**模拟继承(`object_as_type` 类型定型/冲突报错,object.c:165-183);进程内用开放寻址哈希表缓存,命中且 parsed 即短路(object.c:92-118)。

## 1.1 类型系统与解析四层优化

类型枚举(object.h:98-110):COMMIT=1/TREE=2/BLOB=3/TAG=4;OFS_DELTA=6/REF_DELTA=7 仅存在于 pack 内。`parse_object_with_flags`(object.c:322-396)是读取总入口,四层优化逐级短路:

1. 已 parsed 缓存(:335-337);
2. commit-graph 命中则免解压缩(:339-343,04 章 midx 同族);
3. blob 走流式校验(:345-365,大文件不解全);
4. 全文哈希复验(:380-384,paranoid 模式)。

commit 解析(parse_commit_buffer,commit.c:516-598)验证 "tree " 头(:539-544),parent 循环 `lookup_commit`+`commit_list_insert` **惰性建 DAG 不递归**(:557-577);graft/shallow 可替换 parent(:554-590)——05 章浅克隆的伏笔。

## 1.2 loose object:zlib 与原子发布

写链(hash-object 为入口):`index_fd`(object-file.c:942)→`index_mem`(:564,含 convert+fsck)→`odb_write_object`(odb.c:1021-1061,**已存在则仅 freshen mtime 短路**)→`write_loose_object`(odb/source-loose.c:770-830:deflate+写入后重算 oid 比对 :811-813)→`finalize`(:392-457):同目录写 `tmp_obj_XXXXXX`(0444)再 link()/rename 原子发布,EEXIST 时**逐字节碰撞检查**(:329-381)——SHA-1 碰撞的处理是"内容真不同就报错"而非静默覆盖。

读三件套:`unpack_loose_header`(:177)→`parse_loose_header`(:271,拒绝非规范长度)→`unpack_loose_rest`(:211)。存在性判断可走 per-subdir oidtree 缓存(odb/source-loose.c:28-64)。

## 1.3 tree 与 commit 的二进制格式

tree 条目 = `mode SP name NUL 原始oid(20/32B)` 的拼接;`decode_tree_entry` 有一个精巧防御:尾部必须有 NUL 哨兵,`buf[size-(hashsz+1)]` 校验防截断(tree-walk.c:17-48)。目录在排序中视为带 `/`(tree.c:99-116)——**保证同一目录树的字节级稳定**,这是树对象可缓存可对比的前提。

commit 是纯文本:`tree`/`parent`/`author`/`committer` 行+消息。**commit 是文本、tree 是二进制**的分工:前者面向人读与签名,后者面向机器 diff。

## 1.4 哈希抽象:SHA-256 迁移的接口设计

`struct git_hash_algo` 是函数表 vtable(name/format_id/rawsz/hexsz/函数指针/empty_tree/empty_blob,hash.h:294-335),全局经 `the_hash_algo` 宏引用(:271-274)。迁移策略=**compat 双写**:新对象可同时写两种 oid 映射(odb.c:1041-1056;odb/source-loose.c:849)——老仓库逐步过渡而非断裂切换。

两个边界设计:alternates 递归上限 5 层(odb.c:204-239);**大文件(>512MiB)跳过 loose 直接流式进临时 pack**(repo-settings.c:171;object-file.c:963-976,882-940)——这行代码就是"loose→pack 生命周期"的活样本。

## 1.5 设计动机

1. **内容寻址是唯一根基**:完整性/去重/不可变全部是推论而非实现——对比传统 VCS 的"版本号+差量",Git 把"验证"从运行时义务变成寻址副作用(对照 SQLite 的校验和页、LevelDB 的 CRC,但 Git 做进了键本身);
2. **四类对象最小完备**:blob 纯字节、tree 目录快照(非 diff!)、commit 指向树+父链、tag 签名——每类一个职责;目录快照意味着"看任意版本任意目录"都是 O(树高),这是 Git 分支廉价的产品级根源;
3. **对象头参与哈希**:防篡改不需要额外存储签名;
4. **多后端 vtable 重构**(odb/source-loose.c):存储格式(loose/pack/未来)与对象语义(类型/解析)解耦——20 年老库的模块化仍在推进。

## 1.6 FAQ

**Q1:为什么 git 里相同内容只存一份?**
oid=哈希(内容),同内容同 oid,写路径 EEXIST 短路(odb.c:1021-1061)。

**Q2:SHA-1 碰撞了怎么办?**
finalize 检测到 EEXIST 会逐字节比对(:329-381),真不同即报错拒绝——2017 年 SHAttered 攻击后这套检查成为默认。

**Q3:对象头为什么不直接用内容哈希?**
头含类型与长度:同一字节串按 blob 存与按 tree 存会得到不同 oid——类型本身也被保护。

**Q4:commit 为什么是文本而 tree 是二进制?**
commit 面向人读/签名/GPG;tree 面向机器逐条目 diff——两种读者两种格式。

**Q5:大文件为什么绕过 loose?**
>512MiB 直接流式进临时 pack(repo-settings.c:171):避免 deflate 全量缓冲与目录爆炸。

**Q6:空目录为什么提交不了?**
tree 的条目来自文件;目录只是 tree 对象的组织方式,没有文件就没有条目——内容寻址的自然推论。

**Q7:parse_object 会不会重复解压同一对象?**
不会,parsed 标志+obj_hash 缓存(object.c:335-337)。

**Q8:SHA-256 仓库和 SHA-1 仓库互通吗?**
compat 双写过渡(odb.c:1041-1056);fetch/push 有 oid 映射协商(05 章)。

**Q9:alternates 是什么?**
共享对象库路径(odb.c:204-239,递归≤5)——clone --reference 的基础,读路径透明。

**Q10:graft 和 shallow 是什么关系?**
都是 parent 替换(parse_commit_buffer 的 :554-590);graft 手工配置,shallow 由传输协议自动写(05 章)。

## 1.7 小结与深挖方向

本章结论:**Git 对象库 = "内容寻址(头+内容哈希)+ 四类首部继承对象 + zlib loose + 多后端 vtable"**;不可变与完整性是寻址的推论而非工程补丁。深挖:

1. per-subdir oidtree 缓存(odb/source-loose.c:28-64)在百万 loose 对象下的收益曲线;

3. SHA-256 双写过渡的存储膨胀与裁剪时机;
4. tree 排序"目录视为带 /"(tree.c:99-116)对跨平台大小写敏感性影响;
5. link() vs rename() 原子发布的文件系统差异(:392-457 的 fallback 条件)。
