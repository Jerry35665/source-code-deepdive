## 6.1 merge-ort:计算与落地分离

ort("Ostensibly Recursive's Twin",文件头自述 :2-15)的核心架构决策:**全程内存,工作区/索引零接触**——主索引是 strmap `paths`(:354,key 驻留成指针比较)+`conflicted` 子集(:367)+mem_pool(:377);直到 switch_to_result 才 checkout。**快的原因不是并行(全文件无线程)**,而是六项剪枝:

- 平凡合并短路:三树全等(:1353)/单侧改(:1383-1400)不入队;
- 整目录跳过(deferred/trivial_merges,:91-113,:1564);
- **rename 缓存跨 cherry-pick 复用**:三树记录存档(:5420-5422),merge_check_renames_reusable(:5155)——rebase 连续提交的重复 rename 检测直接命中;
- rename 后重启解锁更多剪枝(redo_after_renames,:5280-5285);
- mergeability_only 提前退出(:4570,"能不能合"不写树)。

为什么重写:recursive 引擎的性能与正确性 bug 双驱动(递归虚拟 base 的 rename 处理是老大难)——**引擎重写的判据不是"慢"而是"不可修复的语义债"**(对照 FFmpeg swscale 的 ops 重构,15 章)。

## 6.2 rename 检测:三级流水

`diffcore_rename_extended`:①精确 oid 配对(find_exact_renames,:347——同内容移动零成本);②**basename 快路径**(find_basename_matches,:903)——Linux 内核 76% 的重命名只挪目录不改名(:910-913),阈值从 50% 抬到 75%(:1503-1504);③NxM 相似度矩阵:`estimate_similarity`(:132)用 64B 窗口 spanhash 直方图重合度(diffcore-delta.c:169-221),超 rename_limit² 弃检(:1086)。与 04 章 pack-objects try_delta 同属"廉价过滤后昂贵比较",但一个输出分数、一个输出 delta 流。

## 6.3 xdiff:冲突块的诞生

`xdl_merge`(xmerge.c:684)对 base↔两侧各做一次 diff 得两个补丁脚本,双指针同步扫描(:545-619):不重叠即收;重叠且逐行相同则**不冲突**(:578-583);否则合成冲突块。zealous 模式把冲突块二次 diff 只留差异行(:363)。`<<<<<<<` 四行标记由 fill_conflict_hunk 逐字节 memset 拼出(:217,238,256,269),宽度默认 7(xdiff/xdiff.h:144)——**你屏幕上的冲突标记是一段 1990 年代风格的字符串工程**。内容级驱动经 ll_merge(文本/二进制/自定义 driver)。

## 6.4 sequencer:rebase 的真相

rebase/cherry-pick/revert 共用同一 todo 引擎(sequencer.c):

- **rebase=逐个 cherry-pick**:`do_pick_commit`(:2283)把每个提交归约为三方合并(revert 就是 base/next 反转,:2392-2407),默认走 ort(:746→merge_incore_nonrecursive,:782);
- **todo list 落盘再走**:pick_commits 主循环(:5091)每步 save_todo 后 current++(:5111-5213);
- **中断状态全在文件**:.git/sequencer/{todo,opts,head,abort-safety}(:68-73)与 .git/rebase-merge/{git-rebase-todo,done,stopped-sha}(:82,:92);continue(:5554)/abort(:3577,abort-safety 防误卷 :3517)/skip(:3626);
- **为什么 rebase 后 hash 全变**:parent/committer/树三者任一变即新 oid(01 章寻址);rebase 只换分支指针(refs_update_ref,:5245——02 章引用事务),旧提交链靠 reflog(02 章)存活。

## 6.5 rerere:冲突解法的缓存

冲突签名=hash(**归一化** side1+NUL+side2+NUL)——丢 base 段、两侧按字典序排序(rerere.c:340-395,注释 :398-406 解释排序理由);存 .git/rr-cache/<id>/preimage+postimage,重放即对两文件做一次 ll_merge(:596)并自动暂存(:682)。"修一次,终身自动"的机制基础。

## 6.6 设计动机

1. **批处理替换递归**:recursive 引擎的递归虚拟 base 使状态分散;ort 用"一次三树遍历+strmap 全集+末尾落地"换来可剪枝、可缓存、可提前退出——**先收集后处理**是搜索引擎式的架构红利;
2. **rename 检测的分层哲学**:精确→basename→相似度,廉价信号先耗尽——与 delta 窗口(04 章)、framesync(FFmpeg 04 章)同族;
3. **rebase 不改对象**:全部成本集中在"重放"而非"存储"——内容寻址(01 章)使"重写历史"变得惊人廉价,这是 git 独有的工程自由;
4. **rerere 的签名设计**:丢 base+排序归一化,使"同一冲突换行号出现"仍命中——缓存系统的键设计教科书。

## 6.7 FAQ

**Q1:merge-recursive 去哪了?**
已整体删除(2.50 起,RelNotes/2.50.0.adoc:112);`-s recursive` 是 ort 的别名(builtin/merge.c:180-184)。

**Q2:ort 为什么快?**
不是并行,是剪枝:平凡短路(:1353)+整目录跳过(:1564)+rename 缓存复用(:5155)。

**Q3:合并中我的工作区会被写吗?**
不会,直到 switch_to_result(:4927-4971)——冲突计算期间磁盘只读,abort 零成本。

**Q4:为什么重命名+修改的冲突特别难?**
rename 相似度有阈值(:1086 上限),超限当删+增处理;basename 快路径(:903)只救"挪目录"型。

**Q5:rebase 和 cherry-pick 是两个实现吗?**
一个:sequencer 的 do_pick_commit(:2283),rebase 只是循环调用它。

**Q6:rebase 中断后 .git 里的文件是什么?**
sequencer 状态文件族(:68-73):todo(剩余)/done(已完成)/abort-safety(防误卷)——continue/abort 都是"读档重放"。

**Q7:rebase 后旧提交还能找回吗?**
reflog(02 章)+对象未被 gc(04 章宽限期)——rebase 只动引用(:5245)。

**Q8:rerere 为什么能记住我的解法?**
归一化冲突签名(rerere.c:371-382)+preimage/postimage 对重放(:596)。

**Q9:两个分支改了同一行但内容相同,冲突吗?**
不冲突:xdl_do_merge 逐行比对相同即收(xmerge.c:578-583)。

**Q10:AUTO_MERGE 引用是什么?**
ort 落地时写的伪引用(:4960):冲突时自动生成的中间树,供 `git diff AUTO_MERGE` 检查。

## 6.8 小结与深挖方向

本章结论:**merge = "内存批处理(ort)+三级 rename 检测+xdiff 冲突扫描";rebase = sequencer 的循环 cherry-pick**。引擎重写(2021-2025)是大库演进的活样本。深挖:

1. rename 缓存(:5155)在 100+ 提交 rebase 中的命中率;
2. xdl_merge zealous 模式(:363)对空行敏感场景(代码规范)的行为;
3. ort 的 strmap 路径驻留(:354)在超大树(10 万文件)的内存水位;
4. rerere 签名对"语义相同、文本微调"解法的失配;
5. merge-ort 多 base 归并(:5313)与 criss-cross 的虚拟 base 消除。
