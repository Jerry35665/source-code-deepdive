> 基线:commit `47ce805`。行号以 src/hash/hash.h、odb.c、loose.c、object-file-convert.c 为准。卷一 01 章讲了哈希抽象(vtable)——本章专讲 **SHA-1→SHA-256 迁移**的完整机制。

## 12.0 全景:哈希抽象与双写过渡

## 12.1 双写机制:映射文件与一致性

仓库格式由 extensions.objectformat+extensions.compatobjectformat(setup.c:660-689)声明。odb_write_object_ext(odb.c:1021-1061)对 blob 同字节重哈希、树/commit/tag 先 convert_object_file 转换再哈希出 compat_oid;落盘后在 **loose-object-idx** 文件追加双向映射行(loose.c:15,头行 `# loose-object-idx`);内存是 to_compat/to_storage **双 khash**(loose.h:8-12);空树/空 blob/null 预置免映射(:82-84);映射未命中重读索引防跨进程盲区(object-file-convert.c:38-48);compat 内容读路径即时反转换(odb.c:743-744,:702-710)。commit 双签 gpgsig/gpgsig-sha256 **按算法实现顺序 SWAP 保证哈希稳定**(commit.c:1821-1827,:1148-1152)。

## 12.2 传输协商

v2 protocol 的 object-format capability:serve.c:165-170+connect.c:497-509/:733-739;缺席默认 sha1(connect.c:508);不一致即 die(:736)。

## 12.3 compat 边界

官方自认未完成(extensions.adoc:15-17):fast-import 内签名 die(fast-import.c:2953-2962);跨格式传输直接断开;pack 只存主格式(repack 用 force_object_loose 补建映射,pack-objects.c:4630-4697)。

## 12.4 设计动机

1. **为什么 SHA-1 碰撞攻击催生了迁移**:SHAttered(2017)证明了实际碰撞可行性;Git 的对象名=内容哈希——**碰撞=数据替换攻击**;迁移的紧迫性由安全模型直接推出;
2. **为什么选双写而非一刀切**:百万级存量仓库不可能一次性重写——**双写是"增量迁移"的数据库标准手法**(对照 PG 的 SLRU 分级、LEVELDB 的 manifest 切换);
3. **vtable 的接口面**:6 个函数指针+3 个几何量(name/format_id/rawsz/hexsz)+预置常量——**接口的最小完备集**;
4. **compat 边界的诚实**:extensions.adoc 明言未完成——**承认不完整比假装完整更有价值**(系列红线 4)。

## 12.5 FAQ

**Q1:SHA-256 仓库和 SHA-1 仓库能互通吗?**
传输协商 object-format(connect.c:497-509);不一致即断开(:736)。

**Q2:双写的对象存几份?**
物理只存主格式一份;compat 格式只存映射行(loose-object-idx)。

**Q3:commit 双签的顺序为什么按算法实现 SWAP?**
(:1821-1827):先 sha1 再 sha256 与反之产出不同的 commit 内容——SWAP 保证同输入同输出。

**Q4:映射文件丢了怎么办?**
(:38-48):miss 后惰性重载索引;持续 miss 则报错。

**Q5:fast-import 在 compat 模式能用吗?**
不能(:2953-2962):签名操作 die——官方自认边界。

**Q6:pack 文件里有 compat 格式吗?**
没有:pack 只存主格式(repack 用 force_object_loose 补建映射 :4630-4697)。

**Q7:2026 新变化:Rust 构建门控?**
repository.c:202-208:compat 算法被门控在 Rust 构建——非 WITH_RUST 直接 die。

**Q8:默认算法怎么决定?**
WITH_BREAKING_CHANGES 编译开关(hash.h:196-200):否则仍 sha1。

## 12.6 小结与深挖方向

本章结论:**SHA-256 迁移="vtable 抽象+compat 双写+映射文件+传输协商"**;增量迁移的每一步都有明确的边界声明。深挖:

1. loose-object-idx 的锁并发(:append-only+lockfile)在高并发写的瓶颈;
2. convert_object_file(:树/commit/tag)对 graft/shallow 的处理;
3. pack-objects 的 force_object_loose(:4630-4697)在大仓的 IO 冲击;
4. 传输协商在 v0 协议(无 object-format capability)的降级行为;
5. Rust 构建门控(repository.c:202-208)对 cgo 绑定的影响。

> Git 卷三完——SHA-256 迁移补齐了哈希可插拔的完整故事。
