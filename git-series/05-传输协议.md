# 第 05 章 · 传输协议:从 v0 全量广告到 v2 命令化

> 基线:commit `47ce805`。行号以 pkt-line.c、protocol.c、serve.c、upload-pack.c、fetch-pack.c、builtin/receive-pack.c 为准。

## 5.0 全景:一次 fetch 的两种时序

```
v0: 服务端开场全量广告所有引用 ──→ 客户端 want/have 多轮 ──→ done ──→ PACK
v2: 版本握手 → capability(=命令)广告 → 客户端按需 command=ls-refs
    → command=fetch 会话式状态机 → 分段响应(acknowledgments/shallow-info/
      wanted-refs/packfile)
```

底层都是 **pkt-line**:4 字节十六进制长度+payload;len 0/1/2 分派 flush(0000)/delim(0001)/response-end(pkt-line.c:434-445);帧上限 DEFAULT_PACKET_MAX=1000、LARGE_PACKET_MAX=65520(pkt-line.h:232-234)。

## 5.1 v0 的痛点:全量广告

v0 fetch:服务端开场把**全部引用**广告一遍(upload-pack.c:1383-1389 两个 for_each,首条捎带 capability :1196-1237)→ 客户端发 want/shallow/deepen+flush(receive_needs,:1048-1156)→ have/ACK 多轮(get_common_commits,:538-611;`ACK <oid> common/continue/ready` 语义 :590-595)→ done 后打 PACK。HTTP stateless 下**每次 RPC 重付全量广告**——百万引用仓库的 fetch 在广告阶段就超时,这是 v2 的全部动机。

## 5.2 v2:能力即命令

客户端默认 v2(protocol.c:46)。握手后服务端逐行广告能力,**每个能力就是一条命令**(serve.c:146-190);会话核心一行:`command->command(r, &reader)`(serve.c:357)——按命令分派。

- **ls-refs**:客户端带 `ref-prefix` 前缀过滤只拿需要的引用(ls-refs.c:181-184);前缀超 65536 个则整体放弃过滤(:48,防滥用);
- **fetch**:会话式状态机 PROCESS_ARGS→SEND_ACKS→SEND_PACK(upload-pack.c:1728-1798),响应分段(acknowledgments/shallow-info/wanted-refs/packfile)——一次连接内状态保留,不再重复广告;
- **push 不需要 v2**:push 本来就不做引用广告协商(客户端明确说"把这个 ref 从 old 改成 new"),收到 v2 请求直接回落 v0(builtin/receive-pack.c:2534-2540;connect.c:1459-1460)。

## 5.3 协商算法:have 多轮的减负

客户端如何少发 have:**v0 窗口常量** 16 起、非 stateless 每轮 +32、stateless 翻倍至 16384(fetch-pack.c:272-274);连续 256 个 have 无 ACK 即放弃发 done(MAX_IN_VAIN,:64-68,604-607)——**大分叉仓库 fetch 慢的元凶在此**。v2 把算法抽象成 negotiator 接口(fetch-negotiator.c:8-25):

- default:逐层回溯父链(default.c:108-150);
- **skipping**:TTL=`original_ttl*3/2+1` 指数跳步(:130-171)——更少的 have 覆盖更深历史,`fetch.negotiationAlgorithm=skipping` 或 feature.experimental 启用(repo-settings.c:53-54)。

## 5.4 push:更新行与三级 hook 位点

push 的更新行格式 `<old> <new> <ref>\0caps`,严格解析 old SP new SP ref(send-pack.c:666-675;receive-pack.c:2134-2155);删除/新建用 null-oid,**force 没有专门指令**(只是客户端允许发 old 不匹配的更新)。服务端三级位点:pre-receive(receive-pack.c:2081)→ update(:1592,每 ref)→ 事务提交(02 章)→ post-receive(:2604);report-status 回 `unpack ok`+逐 ref `ok/ng`(:2412-2434),v2 加 option 行(:2436-2470)。**force push 的防线就是服务端 pre-receive 的职责**——协议层故意没有"拒绝 force"的开关,策略留给服务端钩子。

## 5.5 浅克隆:graft 的协议化

deepen 消息让服务端算切割点回发 shallow/unshallow(upload-pack.c:787-858);客户端写入 `$GIT_DIR/shallow`(shallow.c:61-93),每个切割点注册 **nr_parent=-1 的 commit_graft**(:32-45)——01 章"graft 可替换 parent"的自动化应用:**浅仓库的深度限制只是解析层的视错觉**,对象层 unaware。

## 5.6 设计动机

1. **v2 的本质是把"会话状态"从协议里解放出来**:v0 的广告是隐式状态(连接开头一次性),HTTP 下被迫重复;v2 显式命令化后,stateless RPC 每次只带需要的增量——与 gRPC 的流式调用同构;
2. **协商是"猜服务端有什么"的猜谜**:have/ACK 本质是布谷鸟式二分——skipping 算法用指数 TTL 跳步,把 O(深度) 降到 O(log 深度) 级别的消息数;
3. **策略留给钩子**:协议只保证"更新被完整表达",接受与否全是服务端事务(02 章)+hook 的事——协议与策略分离;
4. **浅克隆借graft 而不改对象**:对对象层零侵入的"视错觉"设计,是分层架构红利(01 章 commit 解析的可插拔点)。

## 5.7 FAQ

**Q1:为什么大仓库 fetch 第一阶段就卡?**
v0 全量引用广告(upload-pack.c:1383-1389);v2 的 ref-prefix 过滤(ls-refs.c:181-184)即为此。

**Q2:v2 带来了什么实质变化?**
命令化(ls-refs/fetch 按需)+会话化状态机(upload-pack.c:1728-1798)——广告成本从每次 RPC 变为一次。

**Q3:push 为什么还是 v0?**
push 无协商需求:客户端直接声明更新行,服务端裁决(receive-pack.c:2534-2540 回落逻辑)。

**Q4:have/ACK 的 256 上限是什么?**
MAX_IN_VAIN(fetch-pack.c:64-68):连续 256 个 have 全无 ACK 说明没有共同祖先线索,发 done 硬结束。

**Q5:skipping 协商算法为什么快?**
指数 TTL 跳步(skipping.c:130-171):消息数与深度的对数成正比,深度大仓库收益最大。

**Q6:force push 在协议里长什么样?**
没有特殊指令:更新行 old 填服务端当前值之外任意值,服务端 pre-receive 决定收不收(:2081)。

**Q7:浅克隆的 shallow 文件删了会怎样?**
graft 失效,父链解析撞缺失对象——shallow 文件是浅仓库的"创可贴"(shallow.c:61-93),unshallow 即撕掉。

**Q8:HTTP 和 SSH 协议有区别吗?**
只有传输入口不同(connect.c 子进程封装);pkt-line 层之上完全一致——smart http 把请求包在 POST 里而已。

**Q9:一次 fetch 会打几个包?**
v2 分段响应里 packfile 是最后一段(upload-pack.c:1728-1798);包内对象按 04 章 delta 流水线生成。

**Q10:为什么引用广告首条要捎 capability?**
v0 在广告行 1 内嵌 capability(:1196-1237)——省一个往返的报文挤位设计。

## 5.8 小结与深挖方向

本章结论:**传输协议 = "pkt-line 帧 + v0 全量广告 → v2 命令化 + negotiator 抽象 + 服务端事务裁决"**。深挖:

1. skipping 算法 TTL 参数(:130-171)在不同分叉拓扑的收敛速度;
2. bundle-uri capability(离线包+增量)与 v2 的配合;
3. partial clone 过滤器(list-objects-filter.c:72-112)在 push 侧的镜像问题;
4. cross-repo oid 映射(SHA-1↔SHA-256 fetch)的协商扩展;
5. 服务端事务(receive-pack)与 reftable 后端(02 章)组合的吞吐上限。
