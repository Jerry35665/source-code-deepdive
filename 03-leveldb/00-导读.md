# 《LevelDB 卷》导读:如何使用本卷

> 本卷是《源码深读 · 系统开源项目解读系列》的第三卷。全部结论来自对 LevelDB 1.23(commit `7ee830d0`)源码的逐行阅读,每处关键论断标注 `文件:行号`,可对照源码验证。

## 这卷写给谁

有 1-5 年后端经验、想理解"LSM-Tree 存储引擎到底怎么工作"的工程师;或读过《SQLite 卷》、想看"另一种存储范式"的读者。不需要 C++ 专家背景——LevelDB 的代码风格本身就是教程,本卷的行号引用让你能随时回到源码对照。

## 为什么选 LevelDB

1. **2.6 万行的完备存储引擎**:MemTable、WAL、SSTable、版本管理、compaction、bloom filter 一个不少,但没有任何历史包袱;
2. **教科书地位**:RocksDB、HyperLevelDB 及无数引擎的共同祖先;本卷会在深挖方向标注"这里后来被 RocksDB 怎么改",让你看到复杂度出现之前的朴素形态;
3. **注释即文档**:Jeff Dean 与 Sanjay Ghemawat 亲写的格式说明与 trade-off 注释密度极高,源码可当论文读。

## 环境准备

```bash
git clone https://github.com/google/leveldb.git
cd leveldb && git checkout 7ee830d0        # 与本卷行号一致

# 构建(需要 CMake;零强制第三方依赖)
cmake -DCMAKE_BUILD_TYPE=Release -DLEVELDB_BUILD_TESTS=ON .. && make -j

# 与源码互动的三把钥匙
./db_bench                       # 官方压测工具(理解吞吐特征)
./leveldb_tests --gtest_filter=DBTest.*   # 核心语义测试
```

没有环境也可以读:所有代码片段 ≤15 行,GitHub 网页版按 `文件名 + 行号` 跳转。

## 三种用法

1. **系统通读**(约 4-5 小时——三卷中最短):01 全景 → 02 执行框架 → 03 内存 → 04/05 磁盘 → 06/07 版本与 compaction → 08 WAL → 09 工程;
2. **面试冲刺**:各章 FAQ(全卷约 80 条)——"为什么 L0 允许重叠""删除标记为什么到底层才能丢""WAL 为什么 32KB 分块""bloom 的 k 为什么存进 filter"都是高频误区;
3. **对照设计**:正在自研存储/缓存/日志系统的读者,按第 09 章的借鉴清单逐条对照自己的设计。

## 本卷的四个统一约定

- **行号即凭证**:全部基于 1.23;与流行资料冲突处显式勘误(`file_overreaded`/`maxcompactionbytes` 在 LevelDB 中不存在、`db/merger.cc` 实为 `table/merger.cc`);
- **与前两卷互为镜像**:LevelDB 的"解锁读 + 引用计数"对照 Redis 的"单线程免锁"与 SQLite 的"两阶段销毁";LevelDB 的 32KB 块 WAL 对照 Redis 的 AOF 三策略与 SQLite 的 Multi-Part AOF;
- **代价公式给原文**:allowed_seeks 的定价推导、bloom 误判率闭式、compaction 的 IO 推算都附出处;
- **结论可复算**:InternalKey 编码实例、WAL 切割图、group commit 时序图都可手工验证。
