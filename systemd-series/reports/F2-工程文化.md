## 1. meson 组织:一套模板驱动的测试声明体系

### 1.1 根 meson.build 的测试声明方式

根 meson.build 共 3207 行,直接写死的 `test()` 调用**只有一处**(符号表健康检查):

```meson
test(
        'libshared-unused-symbols',
        find_unused_library_symbols_py,
        suite : 'unused-symbols',
        args : [libshared, libcore] + nss_targets + pam_targets + symbol_analysis_exes,
)
```
(meson.build:2921-2926)

其余全部测试/可执行体走"声明式字典 + 模板展开":根文件先聚合四张表(meson.build:1823-1828
`simple_tests`/`libsystemd_tests`/`simple_fuzzers`/`executables`),各子目录的 meson.build
只做 `simple_tests += files('test-foo.c')` 式追加(如 src/test/meson.build:58),最后由根文件
统一展开(meson.build:2270-2280)。命名的强约定被写成断言:**每个测试/模糊目标必须以
`test-`/`fuzz-` 开头**——`assert(name.split('-')[0] in ['test', 'fuzz'])`
(meson.build:2286),再按前缀分流 `is_test`/`is_fuzz`(meson.build:2289-2290)。

`test_template` 统一规定测试二进制的属性:默认参与构建(`want_tests != 'false'`)、可选安装到
`unittestsdir`(meson.build:2065-2074;安装路径定义在 meson.build:187-189)。测试专属编译
旗标只有一条 `-DTEST_CODE=1`(meson.build:2023),外加 `link_depends : runtest_env`——
一个生成 `SYSTEMD_TEST_DATA`/`SYSTEMD_CATALOG_DIR` 环境文件的自定义目标(meson.build:2013-2021)。

### 1.3 test/ 目录(不在本地)的构建脚本旁证

## 2. 测试基建宏:src/shared/tests.h(718 行)

### 2.1 不用外部框架:TEST() 宏 + 链接期节表

systemd 单测不依赖 check/cmocka,而是自建微型框架:`TestFunc` 结构(函数指针联合 + 名字 +
`has_ret`/`sd_booted` 位域,src/shared/tests.h:93-102)通过 `REGISTER_TEST` 放进
`SYSTEMD_TEST_TABLE` 链接期节(src/shared/tests.h:105-115),`TEST()`/`TEST_RET()` 一步
声明+注册(src/shared/tests.h:117-125),`DEFINE_TEST_MAIN()` 生成 main 并遍历节表:

```c
#define DEFINE_TEST_MAIN_FULL(log_level, intro, outro)    \
        int main(int argc, char *argv[]) {                \
                test_prepare(argc, argv, log_level);      \
                _r = _intro ? _intro() : EXIT_SUCCESS;    \
                if (_r == EXIT_SUCCESS)                   \
                        _r = run_test_table(__start_SYSTEMD_TEST_TABLE, __stop_SYSTEMD_TEST_TABLE); \
                _q = _outro ? _outro() : EXIT_SUCCESS;    \
                static_destruct();                        \
                ...
        }
```
(src/shared/tests.h:134-152)

### 2.2 ASSERT_* 家族与 Coverity 感知

约 500 行是 `ASSERT_OK/ASSERT_EQ/ASSERT_STREQ/ASSERT_SIGNAL/...` 断言宏,每个宏都有
`#ifdef __COVERITY__` 分支,用 `__coverity_check__` 替换运行期打印(如 src/shared/tests.h:177-193),
让静态分析仪理解断言语义;`ASSERT_SIGNAL` 甚至 fork 子进程验证表达式确实死于预期信号
(src/shared/tests.h:649-670)。框架自身的正确性由 meta 测试保证:test-tests.c 的
`TEST(ASSERT)` 用 `ASSERT_SIGNAL(ASSERT_OK(-1), SIGABRT)` 验证"断言失败必须 abort"
(src/test/test-tests.c:9-15)。

### 2.3 环境感知:跳过、慢测与 CI 识别

测试基建对"运行环境差异"有一等公民支持:`log_tests_skipped` 返回 `EXIT_TEST_SKIP`
(src/shared/tests.h:55-70);`manager_errno_skip_test` 容忍 EPERM/EACCES 等权限性失败
(src/shared/tests.h:36-45);`slow_tests_enabled()`(src/shared/tests.c:109)配合
`-Dslow-tests`(meson_options.txt:537-538);`ci_environment()` 识别 travis/semaphore/
github-actions/autopkgtest/salsa-ci 五种环境(src/shared/tests.c:338-378),让测试在 CI 上
自动放宽时序敏感断言。src/shared/test-tables.h:7-35 的 `_test_table` 宏则对每个枚举做
"N → 字符串 → N"往返断言,test-*.tables.c 系列测试专用。

## 5. AGENTS.md:AI 协作纪律全文解读(46 行,仓库亮点)

CLAUDE.md 是指向 AGENTS.md 的 9 字节指针文件(实测 `cat CLAUDE.md` 输出 `AGENTS.md`),对
Claude Code 与通用 agent 用同一份纪律;AGENTS.md 自身用 MIT-0 许可(AGENTS.md:2),鼓励外部复用。逐条解读:

1. **文件的存在理由(AGENTS.md:7-8)**:"Only add instructions to this file if you've seen
   an AI agent mess up that particular bit of logic in practice."——**事故驱动**:只收录 AI
   真实犯过错的规定,不写空泛口号。这是全文最浓缩的工程哲学。
2. **HARD RULE:人工复核闸门(AGENTS.md:12)**:改任何源文件前,必须在 README.md 顶部加
   `> [!IMPORTANT]` + `> Remove this line to confirm you've reviewed this PR before
   submitting.` 两行,且"Never remove these lines yourself"——用机器可验证的标记把
   "人类真的看过这个 PR"变成合并前置条件,防止 agent 自循环提交。
3. **署名只给人类(AGENTS.md:16-17)**:commit 信息禁止 Co-Developed-By/Co-Authored-By
   之类 AI 署名,版权与责任链条保持纯人类。
4. **必读文档(AGENTS.md:21-26)**:docs/ARCHITECTURE、HACKING、CODING_STYLE、
   CONTRIBUTING 四件套("must-read before writing code")。
5. **禁用 mkosi box 包装(AGENTS.md:30-31)**:在哪个环境就用哪个环境的工具,不许
   `mkosi box` 包命令——避免 agent 在嵌套环境里迷路。
6. **构建/测试命令纪律(AGENTS.md:35-40)**:禁止单文件编译,必须
   `meson compile -C build <target>`;禁止 compile/test 分两步,必须直接
   `meson test -C build -v <TEST-NAME>`(meson 自动增量重建);"Never invent your own
   build commands"。
7. **输出保真(AGENTS.md:41-42)**:禁止 `head`/`tail`/管道截断构建测试输出——失败诊断
   需要全量日志,直接回应 agent 爱截断输出的通病。
8. **shell 陷阱(AGENTS.md:46)**:集成测试里禁 `grep -q` 管道(避免 SIGPIPE),改用
   `grep >/dev/null`。

一句话:AGENTS.md 把"维护者踩过的坑"编译成 agent 可执行的守则,是大型 C 项目 AI 协作的范本。

## 10. 设计动机

1. **为什么单测与生产代码同目录(或集中 src/test/)?** 归属清晰:改 `src/resolve/` 的
   DNS 缓存,测试就在同一目录里;公共工具函数被几十个组件共享,集中放 src/test/ 避免重复。
   meson.build:2286 用断言把 `test-`/`fuzz-` 前缀焊死,使命名即协议——任何人(如今包括
   AI agent)凭文件名就能推断构建行为。
2. **为什么 mkosi 全系统镜像?** PID 1、udev、cgroup、mount 这些东西单测里跑不真:
   tests.h 里大量 `manager_errno_skip_test`(tests.h:36-45)恰恰说明单测环境权限残缺。
   mkosi 造一个真实发行版镜像并启动,让 test/TEST-* 集成测试在"生产态"运行;连 mkosi
   配置都随 install-tests 分发(meson.build:2699-2703),外部复现者拿到同一套弹药。
3. **为什么 fuzz 只对解析面?** 解析器输入完全受攻击者控制、分支稠密、无需特权与环境,
   是投入产出比最高的 fuzz 目标;有副作用的路径交给集成测试与镜像层。53 个目标里
   unit-file/network-parser/journald 五输入源/bus-message 的选择,是"攻击面=解析面"的字面执行。
4. **为什么 AGENTS.md 事故驱动?** 规则的价值与"它阻止过的事故"成正比:只记 AI 真实
   犯过的错(AGENTS.md:7-8),避免守则膨胀成没人读的清单;README.md 复核标记
   (AGENTS.md:12)把最痛的点——AI 生成的 PR 没人真正审过——变成流程上不可跳过的一行字。
   这是把 postmortem 文化应用到 AI 协作上。
5. **为什么文档(man/docs/NEWS)与代码同仓?** 因为三者被构建系统互相锁死:手册示例按
   10 种 C 标准编译(man/meson.build:323-331)、D-Bus 文档过期即测试失败
   (man/meson.build:226-231)、NEWS 格式由 check-version-history 把关(man/meson.build:232-236)。
   文档同仓且进 CI,"文档腐烂"就从道德问题变成了构建错误。
6. **为什么自研 TEST()/ASSERT_* 而不用框架?** 单个测试即一个可执行文件、零外部依赖、
   断言打印带文件行号与 errno 名(tests.h:185-192),链接期节表让每个 .c 独立成主体——
   与 systemd"少依赖、可剪裁"的哲学一致;Coverity 分支(tests.h:177 起)让静态分析直接理解测试语义。
7. **为什么版本纪律如此啰嗦?** systemd 是全世界的 PID 1,下游以 NEWS 为迁移契约:前瞻栏
   (NEWS:5)给一版缓冲、每条不兼容变更写明迁移路径、实验特性显式免责(NEWS:1820-1822),
   把兼容性承诺的边界写成白纸黑字。
