# 第 04 章 · 服务进程管理:从 spawn 到收割的生命周期

> 基线:commit `1f66b524`。核心:src/core/service.c(6767 行)、execute.c、exec-invoke.c。

## 4.0 全景:六种 Type 的 started 判定点

```
simple/idle : spawn 成功即 started(无启动超时)
exec        : exec_fd 管道 EOF(execve 真正成功)才 started——可捕获"可执行文件不存在"
forking     : ExecStart 进程(control)退出→读 PIDFile/猜主 PID→started
oneshot     : 主进程退出且退出码成功→started(多条 ExecStart 逐条串行)
dbus        : 总线出现 BusName= 属主→started(运行期属主消失有 2 秒宽限重验)
notify      : 收到 READY=1→started;主进程未通知就退出按协议错误处理
```

状态机 30 个低层状态经 state_translation_table 折算成 8 个高层状态(service.c:75-106)。装载期就掐掉非法组合(service_verify):非 oneshot 必须有 ExecStart、oneshot 禁 Restart=always、Type=dbus 必配 BusName、forking 禁 PrivatePIDs。

## 4.1 executor 化:PID 1 不再 fork 业务进程

`exec_spawn` 先把整个执行上下文**序列化到临时文件**,再以 `posix_spawn_wrapper`(CLONE_VM|CLONE_VFORK;内核 5.7+ 用 pidfd_spawn **直接 clone 进目标 cgroup**)拉起钉死路径的 `systemd-executor` 二进制(execute.c:525-530,process-util.c:2080-2148)。安全上下文(用户/组/命名空间/seccomp/能力/PAM/keyring)全部在 executor 的 `exec_invoke`(exec-invoke.c:5172-6761)内按序应用,最后 fexecve。动机注释明说三点:COW 内存翻倍(pid1 memory.current 超 memory.max 时的 OOM 陷阱)、安全上下文代码膨胀拖累 PID1、升级期行为漂移(executor 二进制被钉死)。**传统双 fork 仅残留在辅助路径**(safe_fork 的 FORK_DETACH)。

## 4.2 主 PID:猜测 + notify 修正,以 cgroup 兜底

forking 的主 PID 靠 PIDFile(仅信 root 属主的文件)与启发式搜索;notify 服务可用 `MAINPID=`/`MAINPIDFD=`/`MAINPIDFDID=` 让管理器换主进程,pidfd 从根上封死 PID 复用竞态(service.c:5436-5500)。控制命令(ExecStartPre/Post 等)放 `.control` 子 cgroup。cgroup 是最终兜底:连 PID 都不知道时,空 cgroup 事件也能推进状态(service.c:4626-4640)。

## 4.3 超时:一个定时器多种语义

服务只有一个 `timer_event_source`,`service_arm_timer` 按状态重新解释:TimeoutStartSec 覆盖启动各阶段(失败模式 terminate/abort/kill 三分支);RuntimeMaxSec 到点**不 kill 而是发起正常停止**;TimeoutStopSec 覆盖停止各阶段;RestartSec 复用同一枚定时器倒数;WatchdogSec 独立成源且刻意放在 sd-event IDLE 优先级——喂狗消息等其他事件先行,避免"活着的进程被误判死亡"。daemon-reload 后 coldplug 按状态反推绝对截止时刻重建——死等半程的服务不重置超时。

## 4.4 停止与 KillMode

停止链:ExecStop→SIGTERM→超时 SIGKILL→ExecStopPost→FINAL_*→dead。`unit_kill_context` 一条 if 决定 KillMode 差异(unit.c:5106-5153):**control-group** 遍历整棵 cgroup 树 `cg_kill_recursive`(能杀死孤儿孙进程的完备选项);**mixed** 仅 SIGKILL 阶段才 cgroup 扫射;**process** 永远只有 main+control 两个 PID。SIGKILL 阶段先把 pids.max 写 0 阻止垂死进程 fork。服务主动 STOPPING=1 走"视同已发 SIGTERM"的优雅路径。`unit_kill_context` 返回 0(没打到进程)时直接沿链条快进,不等 SIGCHLD。

## 4.5 result 码与收割

11 种 ServiceResult(success/timeout/exit-code/signal/core-dump/watchdog/oom-kill/…,service.h:79-93)——粗粒度 failed 无法支撑 Restart=on-watchdog、RestartPreventExitStatus= 与 $SERVICE_RESULT 驱动的 ExecStopPost 清理。收割两段式:WNOWAIT 偷看→按 PidRef 找 unit 扇出 sigchld_event→真收尸;**通知消息处理排在 SIGCHLD 之前**(否则 READY=1 后立刻退出会丢最后一条通知)。自动重启走两段 dead 态(BEFORE_AUTO_RESTART),让外部观察者能看到"短暂 inactive"——服务死过这件事对监控系统可见。

## 4.6 设计动机

1. **notify 优于 forking**:forking 靠守护进程自觉写 PIDFile,管理器只能猜;READY=1 让服务自证初始化完成;
2. **cgroup 是真相之源而非 PID 表**:PID 表只覆盖已知角色,守护进程的子孙只有 cgroup 能兜住;"任何用户代码绝不在 cgroup 外执行";
3. **executor 化**:一并解决 COW/OOM、PID1 膨胀、升级漂移三问题,且出生即入 cgroup;
4. **KillMode 分级**:control-group 完备但可能误杀协作者;process/mixed 照顾遗留守护进程;
5. **result 细分**:每一项细分对应一个可编程决策点(Restart 策略/清理钩子/告警)。

## 4.7 FAQ

**Q1:Type=exec 比 simple 强在哪?**
execve 真正成功才算 started,可捕获文件不存在/沙箱失败,不留 RUNNING 空壳。

**Q2:forking 怎么找主 PID?**
PIDFile(仅信 root 属主)+启发式搜索(service_search_main_pid)。

**Q3:RuntimeMaxSec 到点会杀进程吗?**
不:发起正常停止并记 FAILURE_TIMEOUT。

**Q4:sd_notify 需要什么权限?**
NotifyAccess 四级 none/main/exec/all,main 只认主 PID。

**Q5:KillMode=none 还在吗?**
枚举含 none 共 4 种;control-group/mixed/process 是常用三级。

**Q6:怎么防止停止时进程再 fork?**
SIGKILL 阶段先写 pids.max=0。

**Q7:重启有退避吗?**
指数曲线+随机抖动;两段 dead 态让外部看到 inactive 瞬间。

**Q8:ExecStartPost 失败会怎样?**
主进程仍要体面停掉:走 STOP_SIGTERM 而非直接 dead。

**Q9:ExecCondition 退出码 1 是失败吗?**
(0,254] 视为"跳过"而非失败(SERVICE_SKIP_CONDITION)。

**Q10:SendSIGKILL=no 的服务有什么额外约束?**
启动前若 cgroup 有残留进程直接拒绝启动。
