# 第 12 章 · 测试基础设施与工程文化(卷二)

> 基线:commit `1f66b524`(版本 262~rc2)。本地 sparse 检出仅 src/ 与 man/;test/、docs/、.github/、mkosi/ 不在本地——凡涉及处均标注"构建脚本/文档推断",不编造行号。

## 12.0 全景:质量金字塔

```
        CI 治理层(GitHub Actions/Semaphore/Coverity/OSS-Fuzz/OpenSSF Scorecard)
       mkosi 全系统镜像层(构建完整发行版镜像并启动验证;构建脚本旁证 meson.build:2671-2703)
      集成测试层(integration-tests 套件;默认 test setup 排除,meson.build:13-18)
     Fuzz 层(53 个目标,全部砸向解析面;OSS-Fuzz 目标与 meson 回归测试双职)
    单元测试层(406 个 test-*.c;ASSERT_* 宏+TEST() 链接期节表+框架自测)
```

## 12.1 meson:声明式测试体系

根 meson.build 直接写死的 test() 调用**只有一处**(符号表健康检查);其余走"聚合表+模板展开":各子目录只做 `simple_tests += files('test-foo.c')` 式追加,根文件统一展开。**命名即协议被写成断言**:每个测试/模糊目标必须以 test-/fuzz- 开头——`assert(name.split('-')[0] in ['test','fuzz'])`(meson.build:2286)。单测与生产代码同目录(resolve 22 个、sd-bus 18 个…)或集中 src/test/(264 个)——库层测试贴着库,守护进程测试贴着守护进程,公共工具集中收纳。

## 12.2 自研测试框架:TEST() 节表 + ASSERT_* 家族

不用 check/cmocka:`TestFunc` 经 REGISTER_TEST 放进链接期节表,`DEFINE_TEST_MAIN` 遍历;约 500 行 ASSERT_* 宏每个都有 `#ifdef __COVERITY__` 分支让静态分析理解断言语义;ASSERT_SIGNAL fork 子进程验证表达式确实死于预期信号。框架自测是 meta 的:test-tests.c 用 `ASSERT_SIGNAL(ASSERT_OK(-1), SIGABRT)` 验证"断言失败必须 abort"。环境感知一等公民:log_tests_skipped 返回 EXIT_TEST_SKIP、manager_errno_skip_test 容忍权限失败、ci_environment() 识别五种 CI 环境放宽时序断言。

## 12.3 fuzz:只打解析面

53 个 fuzz 目标几乎全是无网络、无 root 也能触发的解析/反序列化面:.unit 文件、.network/.netdev、journald 五种输入源、sd-bus 消息、序列化快照、bootspec/catalog/json/varlink-idl。同一二进制双职:OSS-Fuzz 构建链 FuzzingEngine,普通构建链 fuzz-main.c 回归驱动(把命令行文件喂给 LLVMFuzzerTestOneInput)。**"攻击面=解析面"的字面执行**:有副作用的路径交给集成测试与镜像层。

## 12.4 AGENTS.md:事故驱动的 AI 纪律

CLAUDE.md 是 9 字节指针文件(内容只有 "AGENTS.md")。AGENTS.md(46 行,MIT-0)的哲学浓缩在一句话:"Only add instructions if you've seen an AI agent mess up that bit of logic in practice"——**只收录 AI 真实犯过的错**。硬规则:改任何源文件必须先在 README 顶部加 `> [!IMPORTANT]` 人工复核行且"只有人类能移除"(把"人审过 PR"变成机器可验证的前置条件);commit 禁止 AI 署名;必须 `meson compile/test` 禁止单文件编译;禁止截断构建测试输出;集成测试里禁 grep -q 管道。这是把 postmortem 文化应用到 AI 协作上的范本。

## 12.5 文档与版本纪律

man/ 下 486 个手册源,与代码同仓且被构建互相锁死:22 个 C 示例真的横跨 10 种 C 标准各编一遍(-pedantic -Wall -Werror);D-Bus 文档过期即测试失败;NEWS 格式由 check-version-history 测试把关——**"文档腐烂"从道德问题变成构建错误**。NEWS 23388 行 87 个版本段:前瞻性弃用栏制度化(提前一版预告破坏性变更)、每条不兼容变更写明迁移路径、实验特性显式免责。许可:主体 LGPL-2.1+(约 3100 文件)+内嵌内核 UAPI 头 GPL2(147 个)。src/ 129 个子目录"一守护进程一目录",每个的 meson/测试/fuzz 都住在自己目录里。

## 12.6 设计动机

1. **单测同目录**:归属清晰,命名断言让任何人(包括 AI)凭文件名推断构建行为;
2. **mkosi 全系统**:PID1/udev/cgroup 单测里跑不真(tests.h 大量 skip 宏恰是证据);镜像让集成测试在"生产态"运行,且配置随 install-tests 分发;
3. **fuzz 只打解析面**:输入完全受攻击者控制、分支稠密、无需特权——投入产出比最高;
4. **AGENTS.md 事故驱动**:规则价值与它阻止过的事故成正比,避免守则膨胀成没人读的清单;
5. **文档进 CI**:手册示例跨标准编译、D-Bus 文档同步检查、NEWS 格式校验——三者与代码互相锁死;
6. **自研框架而非第三方**:单测试即可执行文件、零依赖、断言带文件行号与 errno 名——与"少依赖可剪裁"哲学一致。

## 12.7 FAQ

**Q1:测试必须叫什么名字?**
test-* 或 fuzz-* 前缀——meson.build:2286 的断言把命名焊死。

**Q2:fuzz 目标怎么选的?**
全部对准解析面:unit-file/network-parser/journald 输入/bus 消息等;副作用路径交给集成测试。

**Q3:普通构建下 fuzz 代码运行吗?**
运行:fuzz-main.c 把命令行文件喂给同一入口,默认 4 遍,兼作回归。

**Q4:AGENTS.md 的金丝雀是什么?**
README 顶部的 [!IMPORTANT] 复核行:只有人类作者能移除,机器可验证"人审过"。

**Q5:文档会烂吗?**
机制上很难:手册示例跨 10 种标准编译、D-Bus 文档同步检查、NEWS 格式测试。

**Q6:systemd 用什么测试框架?**
自研:TEST() 链接期节表+ASSERT_* 宏(Coverity 感知),零外部依赖。

**Q7:慢测试和危险测试怎么管理?**
-Dslow-tests 开关;-Dtests=unsafe 解锁会动系统的测试;默认 test setup 排除 integration-tests。

**Q8:NEWS 有多长?**
23388 行、87 个版本段;前瞻弃用栏提前一版预告破坏性变更。

**Q9:systemd 是纯 LGPL 吗?**
主体 LGPL-2.1+;src/include/uapi 内嵌的内核头是 GPL2(147 个文件)。

**Q10:mkosi 在构建里的角色?**
custom_target 直接送 `mkosi build`;配置随 install-tests 分发,外部复现者拿同一套弹药。
