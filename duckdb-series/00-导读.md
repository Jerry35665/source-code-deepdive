# 《DuckDB 卷一》导读:如何使用本卷

> 本卷是《源码深读 · 系统开源项目解读系列》**第五系列**之九。全部结论来自对 duckdb/duckdb(commit `7e886f44`,2026-09-17 主干)源码的逐行阅读,每处关键论断标注 `文件:行号`。

## 定位与三大纠偏

DuckDB 是 C++ 写的**进程内分析型 OLAP 数据库**:"SQLite 的外壳(SQLite of Analytics)+ 列存向量化内核"。卷一覆盖从 SQL 字符串到事务提交的完整主干。

**三大纠偏**(与流行认知相反):

1. **libpg_query 已被移除**——2026 主干的 SQL 解析切换为**自研 PEG 解析器**(src/parser/peg/,41 个 `.gram` 文法文件 + packrat 缓存),`src/README.md:4` 那句 "uses the parser of Postgres" 是**过时表述**(C 报告专节);
2. **Vector 已"瘦身"为 type + buffer 指针两个成员**(vector.hpp:238-240),行数与 vector_type 都下沉到 VectorBuffer 内——旧文章里"Vector 持有 data/validity/count"的描述已失效(B 报告);
3. **"单写者"≠同时只允许一个写事务**——BEGIN 永远成功,冲突在写操作时刻即时抛异常(update_segment.cpp:683 "Conflict on update!"),提交段才由 WAL 锁串行(F 报告)。

## 三种用法

1. **通读**:01→06,骨架→数据基座→编译前端→优化→并行执行→事务;
2. **答疑**:为什么 WHERE 里 LIKE '%x' 能变 prefix→04;一个 chunk 多少行→02;两线程写同一行会怎样→06;join 的 build 为什么先于 probe→05;
3. **自研借鉴**:06 章"把提交状态折叠进版本号本身"与 04 章"固定顺序流水线 vs cascade"是两个可直接移植的架构决策样本。
