# 报告 A2 · 存储总览:SingleFileStorageManager 与数据库持久化

> 基线:commit `7e886f44`。卷一(《事务与 MVCC》)已覆盖 WAL 的提交语义与组提交时序;本报告讲**文件格式与磁盘侧**:三个 header 的布局、block 分配与 free list、meta block 链、catalog 序列化、attach/恢复流程与版本兼容。WAL 条目格式的逐条解析留给报告 D。所有 `文件:行号` 均在基线 commit 上核对。

## 0. 全景:一个数据库文件的磁盘布局与内存对象对应

```
dbFile (duck.db)                                内存侧
┌──────────────────────────────────┐
│ [0,8)    checksum(u64)           │   DatabaseInstance
│ [8,12)   "DUCK"  ← magic bytes   │    └─ AttachedDatabase (每库一个)
│          MainHeader (占 4096B 页) │        ├─ catalog   : DuckCatalog
│          版本/flags/加密元数据    │        ├─ storage   : SingleFileStorageManager
├──────────────────────────────────┤   │            ├─ block_manager : SingleFileBlockManager
│ [4096, 8192)    DatabaseHeader 1 │   │            │    ├─ MetadataManager (meta 链)
│ [8192, 12288)   DatabaseHeader 2 │   │            │    └─ BlockHandle 注册表
│   iteration ↑ 仲裁活跃头         │   │            └─ wal : WriteAheadLog → duck.db.wal
│   meta_block → catalog 序列化根  │   │                (副 WAL:.wal.checkpoint/.wal.recovery)
│   free_list  → 空闲块链根        │   └─ BufferManager/BufferPool(块缓冲,BlockAllocator 供内存)
│   block_count/alloc_size/vector  │
├──────────────────────────────────┤   BLOCK_START = 3 × 4096
│ block 0                          │   block_id → 文件偏移:id × block_alloc_size(默认 256KB)
│ block 1     数据块(压缩列段/索引)│   普通块:数据列段;metadata 块:一切"小对象"
│ ...                              │
│ ┌─ meta 块内部 ─────────────────┐│   1 个磁盘块切 64 个 metadata block
│ │[8B 下一链块指针][分片0][分片1]…││   MetaBlockPointer = block_id(低56位) | 分片号(高8位)
│ └───────────────────────────────┘│   catalog / 表指针 / free list 全挂在这条链上
└──────────────────────────────────┘
duck.db.wal    重放日志(checkpoint 完成后清空/换新)
```

Catalog(`DuckCatalog`)不直接碰磁盘:持久化内容全部经 `MetadataWriter` 写进 meta block 链,根指针记录在 `DatabaseHeader.meta_block`;表数据(压缩列段)占普通数据块,由 catalog 流里的 `table_pointer` 间接索引。读写一条数据块都要过校验和(加密库再过一层加解密),块内布局是"8 字节校验和 + 块体"。

## 1. 文件格式:一个 MainHeader + 两个 DatabaseHeader

### 1.1 常量与 magic bytes

文件偏移速查(默认配置):

| 偏移 | 内容 | 大小 |
|---|---|---|
| 0 | 校验和(u64) | 8B |
| 8 | `"DUCK"` magic bytes | 4B |
| 0-4096 | MainHeader 页(序列化体只占前几百字节) | 4096B |
| 4096-8192 | DatabaseHeader 1(校验和 + 体) | 4096B |
| 8192-12288 | DatabaseHeader 2(校验和 + 体) | 4096B |
| 12288(`BLOCK_START`) | block 0 起,块 i 在 `12288 + i × 256KB` | — |

关键常量集中在 storage_info.hpp:`FILE_HEADER_SIZE = 4096`(:56)、默认块分配 256KB(:33)、块头 8 字节(:35,:64)、`INVALID_BLOCK = -1`(:28)、`MAXIMUM_BLOCK = 2^62`(:30)。文件前 8 字节是校验和,紧随其后是 4 字节 `"DUCK"`——`MAGIC_BYTES` 定义于 single_file_block_manager.cpp:29,校验偏移 `MAGIC_BYTE_OFFSET = DEFAULT_BLOCK_HEADER_SIZE(=8)`(storage_info.hpp:247,64)。attach 前的文件嗅探(magic_bytes.cpp:16-27)顺带识别 `SQLite format 3`/`PAR1`,给出更友好的报错;识别为 DuckDB 文件时还会把 3 个 header 页整块预取进内存,供随后的打开路径直接命中(magic_bytes.cpp:43,54-56;storage_manager.cpp:540)。

### 1.2 MainHeader:写一次的"身份证"

MainHeader 只在建库时写一次(single_file_block_manager.cpp:543,593-594):版本号、4 个 flag(第 0 位=加密,storage_info.hpp:291-296)、32 字节库版本串 + 32 字节 git hash、8 字节加密元数据(kdf/aad/cipher/版本/密钥长度,:463-478)、16 字节 `db_identifier`(加密时兼作 KDF 盐,:551-554)、以及加密库的 canary"DUCKKEY"密文+nonce+tag——解密时先验 canary,错钥匙第一时间报错而不是烂在数据里(:101-174,507-518)。自 v2.0.0 起 main header 的版本号固定写 999(`DEPRECATED`),权威版本移到 database header(:178-181)。除版本迁移/降级外它不再被改写(`RewriteMainHeader`,:868-876,调用点 :1396-1405)。

### 1.3 DatabaseHeader ×2:互为校验的"提交点"

建库时写两份内容相同、iteration=0 的 header,h2 为活跃头,首次写落在 h1(single_file_block_manager.cpp:596-629);打开时读两份、取 iteration 大者(single_file_block_manager.cpp:707-724)。写路径 `WriteHeader` 每次自增 iteration、写到**非活跃**那份、再翻转指针(:1338,1413-1416)——任何时刻崩溃,磁盘上必有一份完整一致的元数据。序列化就是七个字段的定长写出:

```cpp
// src/storage/single_file_block_manager.cpp:274-289
void DatabaseHeader::Write(WriteStream &ser) {
    ser.Write<uint64_t>(iteration);
    ser.Write<idx_t>(meta_block);
    ser.Write<idx_t>(free_list);
    ser.Write<uint64_t>(block_count);
    ser.Write<idx_t>(block_alloc_size);
    ser.Write<idx_t>(vector_size);
    if (storage_compatibility < StorageVersion::V2_0_0) {
        string storage_version_string = StorageVersionInfo::GetStorageVersionString(storage_compatibility);
        auto ser_version = GetSerializationVersionDeprecated(storage_version_string.c_str());
        ser.Write<idx_t>(ser_version);
    } else {
        ser.Write<idx_t>(static_cast<idx_t>(storage_compatibility));
    }
}
```

字段含义(struct 定义 storage_info.hpp:377-398):

| 字段 | 含义 | 写入/读取 |
|---|---|---|
| `iteration` | 每次 checkpoint +1,双头仲裁依据 | single_file_block_manager.cpp:1338 / :350 |
| `meta_block` | catalog 序列化流的根 `MetaBlockPointer` | checkpoint_manager.cpp:296 / :351 |
| `free_list` | 磁盘空闲块链的根(经 meta 链存) | :1360 / :352 |
| `block_count` | 逻辑块数,其后空间隐式全空闲 | :1381 / :353 |
| `block_alloc_size` | 块分配粒度,建库后不可变 | :279 / :354-359(0 回退默认) |
| `vector_size` | 编译期向量大小,不符即拒开 | :280 / :361-370 |
| `storage_compatibility` | 权威存储版本 | :282-288 / :372-376 |

### 1.4 校验和与块 IO 路径

所有 header 与数据块的读写都走 `ChecksumAndWrite`/`ReadAndChecksum`:校验和存在块体前 8 字节;加密库的 MainHeader 保持明文以便解密前读取参数(:797-804),其余块先算校验和再加密写(:805-822),读时先解密再验(:776-790);不一致抛 `DataCorruptionException`(:744-749)。普通块 IO:`Read`/`Write` 即"定位 + 上述读写"(single_file_block_manager.cpp:1198-1202,1225-1228),支持一次多块的批量读(:1204-1219)。

## 2. SingleFileStorageManager:LoadDatabase 与 checkpoint 入口

### 2.1 LoadDatabase 的三分支

attach 一个文件时,`AttachedDatabase` 构造 `SingleFileStorageManager`(attached_database.cpp:156),`Initialize` 先 `catalog->Initialize` 再 `storage->Initialize`(attached_database.cpp:287-296),后者进入 `LoadDatabase`(storage_manager.cpp:423):

- **内存库**(`:424-431`):挂 `InMemoryBlockManager`,存储版本直接取最新;
- **新建文件**(`:478-518`,可写且文件不存在):删遗留 WAL、按选项确定块大小/加密/存储版本,`CreateNewDatabase`、开空 WAL;
- **打开既有文件**(`:520-599`):`LoadExistingDatabase` 读 header(:545-547)→ `SingleFileCheckpointReader::LoadFromStorage` 从 meta_block 重建 catalog(:580-581)→ `WriteAheadLog::Replay` 重放 WAL(:595-596)。

加载完成后 `load_complete = true`(:609),此后 `GetWAL()` 才返回非空(:211-216)。行组大小等选项也有版本门槛:≥122880 的行组要求存储版本 ≥ v1.2.0(:602-607)。

### 2.2 checkpoint 的三个触发面

1. **自动**:事务提交后 `AutomaticCheckpoint`(duck_transaction_manager.cpp:153 → storage_manager.cpp:857-874):预计 WAL 大小(`GetWALSize` + 本事务估算)超过 `checkpoint_threshold`,或 WAL 条目数超限即触发;
2. **显式**:`CHECKPOINT` 语句 / DETACH / 进程关闭。`AttachedDatabase::Close` 依 `checkpoint_on_shutdown` 配置与库名空间决定(attached_database.cpp:366-395,:388);
3. **入口很薄**:`SingleFileStorageManager::CreateCheckpoint`(storage_manager.cpp:753)先挡掉 read_only/未加载完(:754-756),尝试拿事务管理器的 vacuum 锁(拿不到则 FULL 降级为 CONCURRENT,:757-769),`GetWALSize()==0` 就没有可做的(:777-778);真正干活的是 `CreateCheckpointWriter` 产出的 `SingleFileCheckpointWriter`(:745-751,788-789),失败则 invalidate 整库(:792-803)。

一次持久 checkpoint 的时间线(checkpoint_manager.cpp:199-376):写两条 MetadataWriter(:215-216)→ 取 meta_block(:219)→ `WALStartCheckpoint`(向 WAL 写标记并切副 WAL,:235)→ 扫 catalog 摊平条目(:244-253)→ BinarySerializer 写 catalog 流 + 各表数据流(:275-284)→ 组装新 DatabaseHeader 并 `WriteHeader`(:294-299)→ `Truncate` 文件尾(:336)→ `WALFinishCheckpoint` 收尾副 WAL(:343-355)→ 提交 checkpoint 事务(:375)。另有两个测试/扩展钩子:`PRAGMA checkpoint_abort` 在 free list 写完、header 写前、truncate 前、WAL 收尾前四个点位可注入崩溃(checkpoint_manager.cpp:286-292,331-340;single_file_block_manager.cpp:1386-1389);存储扩展可在 checkpoint 起止收到回调(storage_manager.cpp:771-773,806-808)。

### 2.3 双 WAL 交替

checkpoint 先向主 WAL 写一条带 meta_block 的 `CHECKPOINT` 标记并关闭主 WAL(storage_manager.cpp:294-299;write_ahead_log.cpp:291-295),期间事务改写 `.wal.checkpoint` 副 WAL(storage_manager.cpp:301-312;路径 :357-363)。收尾时若副 WAL 为空,直接删主 WAL 重建(:322-330);否则先 `WaitForDurability` 等在途 sync,再把副 WAL 原子改名顶替主 WAL(:332-344)。这套两代 WAL 是"checkpoint 期间并发提交不丢"的根基,细节归报告 D。

### 2.4 commit 侧的存储配合(与卷一衔接)

`SingleFileStorageCommitState` 实现卷一第 6.4 节的 Revert/Flush 两阶段:RevertCommit 截断 WAL 回初始大小(storage_manager.cpp:674-683),FlushCommit 按 `sync_now` 决定就地 fsync 还是只写 flush marker 等组提交(:685-699)。它还携带"乐观写"的 row group 数据(大 append 在提交前已把整行组写进数据块),供 checkpoint 判定哪些块可跳过重写(:616-624,701-735)。

### 2.5 attach 选项面与 WAL 记账

存储侧的 ATTACH 选项在 `StorageOptions::Initialize` 统一解析(storage_manager.cpp:90-154):`block_size`(实际是块分配粒度,注释特意澄清它不是内存量,:94-96)、`storage_version`(:118-120)、`row_group_size`(:116-117)、`encryption_key/cipher`(:97-115)、`io_mode`(BUFFERED/MMAP/DIRECT,:129-141)、`compress`(仅内存库,:121-126);加密密钥在加载完成后立即从内存擦除(:148-153,390-392)。WAL 的记账在 StorageManager 上:`wal_size` 由写入方累加、重放后校准(:187-209),`AutomaticCheckpoint`(§2.2)与 `GetDatabaseSize` 都读它;`GetWAL()`/`HasWAL()` 在内存库、只读、或加载未完成时返回空——**只读连接没有 WAL**(:211-216,244-249)。路径约定:主 WAL `path.wal`、副 WAL `path.wal.checkpoint`、恢复合并 `path.wal.recovery`(:353-363;默认后缀 storage_manager.hpp:105)。

## 3. BlockManager:block id 分配、free list 与"重映射"的现状

### 3.1 抽象层

`BlockManager` 是抽象基类(buffer/block_manager.cpp:11-15):持有 `MetadataManager`,维护 block_id→`BlockHandle` 的**弱指针**注册表(`RegisterBlock`,:40-57——同 id 的活跃句柄直接复用,无人引用则句柄消亡、块回归磁盘),并把缓冲池里的临时块转正为持久块(`ConvertToPersistent`,:59-118:以目标 id 注册新句柄、复制/改写 buffer、写盘、原地换成持久句柄、进入驱逐队列)。`SingleFileTableIOManager` 把索引、行数据统一指到同一个块管理器(storage_manager.cpp:395-417)。

### 3.2 分配与回收

磁盘 block id 的分配在 `SingleFileBlockManager`:

- **分配**:`GetFreeBlockIdInternal` 优先取 free_list 最小 id,否则 `max_block++` 扩张(single_file_block_manager.cpp:906-925);checkpoint 预写用 `GetFreeBlockIdForCheckpoint`(不进 newly_used 集,:931-933);`PeekFreeBlockId` 只看不动(:935-942);
- **回收两跳**:DROP/UPDATE 释放的旧块先记入 `modified_blocks`,**本次 checkpoint 期间不可复用**(在途读快照可能还在引用),`WriteHeader` 尾部才转入 free_list(:972-1007,1419-1430);新分配但尚未落盘的块记在 `newly_used_blocks`,崩溃即自然消失(:918-920);
- **共享块计数**:`multi_use_blocks` 记录多 row group 共享,引用减到 1 退出共享(:972-988,1009-1019),free list 持久化时一并存取(:891-897);
- **调试对账**:`VerifyBlocks` 断言每个 block id 恰好出现在 使用/空闲/新用/共享 之一(:1021-1109)。

### 3.3 free list 的持久化

打开时从 header 的 `free_list` 指针沿 meta 链读回:空闲块数、每个空闲 id、multi-use 表,以及 metadata 管理器自身的分片位图(`LoadFreeList`,single_file_block_manager.cpp:878-900)。checkpoint 写出前先估算要写的总量,据此**预分配**全部目标块(`GetFreeListBlocks`,:1254-1286),再用专用的 `FreeListBlockWriter` 只往预分配块里写——否则"写 free list"这个动作本身又要消耗 free list,形成自举悖论(:1288-1306,写路径 :1352-1376;无块可写时 `free_list = INVALID`,:1373-1376)。

### 3.4 文件收缩与打洞

`Truncate` 逆序吃掉 free list 尾部连续块并截断文件(single_file_block_manager.cpp:1230-1252);`TrimFreeBlocks` 把 checkpoint 后完全空闲的连续区间 `Trim` 归还文件系统(打洞),受 `trim_free_blocks` 配置开关(:1450-1477)。`GetDatabaseSize`/`GetMetadataInfo` 把块统计与 meta 块占用暴露给 PRAGMA(storage_manager.cpp:838-855)。

### 3.5 辨析:BlockAllocator 是内存池,不是磁盘分配器

`BlockAllocator`(block_allocator.cpp)服务的是 BufferManager 的**内存**:一次性 `VirtualAlloc/mmap` 预留大段虚拟地址(:24-37),按块大小切成 32 位池内编号,线程本地攒批分配/回收、全局 `ConcurrentQueue` 找零(:88-199,324-337),淘汰时对连续区间 `madvise` 归还物理页(:378-419)。它决定吞吐与内存上限;磁盘 block id 的正确性与之无关——两层解耦让任一侧重构不波及文件格式。

### 3.6 "block remapping"去哪了

老版本(0.10 之前)checkpoint 会整体重写数据并重映射 block id,恢复读侧需要 id 翻译表。现行格式下 block id 在 checkpoint 间**稳定不变**,等价机制有二:(a) metadata 块**写前转瞬态**——磁盘块一旦要改写,先整体复制到 ≥`MAXIMUM_BLOCK` 的瞬态块,Flush 时以原 block_id 转正回写(metadata_manager.cpp:82-87,130-150,295-300;转正在 buffer/block_manager.cpp:59-118);(b) 上面 (3.2) 的 COW + modified_blocks 延迟回收。于是"重映射"从恢复期搬到了写入期,且只发生在真正被改写的块上。

## 4. MetadataManager:meta block 链

一个 meta 磁盘块的内部(64 分片,块首 8 字节是后继指针):

```
磁盘块 (256KB, block_id = N)
┌──────────┬──────────┬──────────┬─────────┬──────┬──────────┐
│next = M  │ 分片0     │ 分片1     │ 分片2    │ ...  │ 分片63    │
│(u64,链)  │ catalog… │ 统计…     │ rowgrp… │      │ free 空闲 │
└──────────┴──────────┴──────────┴─────────┴──────┴──────────┘
     └──→ 磁盘块 M(block_id = M):[next = P][分片0]…
```

catalog、表指针、统计、free list 这类 KB 级小对象若各占一个 256KB 数据块,写放大不可接受。做法是**一个磁盘块切 64 份**(`METADATA_BLOCK_COUNT = 64`,metadata_manager.hpp:58;切片大小对齐计算 metadata_manager.cpp:344-346),块内用位图(`uint64_t`)管理空闲分片(:356-384)。磁盘指针采用位打包:

```cpp
// src/storage/metadata_manager.cpp:196-208
MetaBlockPointer MetadataManager::GetDiskPointer(const MetadataPointer &pointer, uint32_t offset) {
    idx_t block_pointer = idx_t(pointer.block_index);   // 低 56 位:block_id
    block_pointer |= idx_t(pointer.index) << 56ULL;     // 高 8 位:64 分片之一
    return MetaBlockPointer(block_pointer, offset);
}
block_id_t MetaBlockPointer::GetBlockId() const {
    return block_id_t(block_pointer & ~(idx_t(0xFF) << 56ULL));
}
```

追加写时 `MetadataWriter::NextBlock` 把**下一块的磁盘指针写进当前分片所在块的头部 8 字节**,形成块级单向链(metadata_writer.cpp:43-61;`WriteData` 跨块自动续链,:63-80);读侧 `MetadataReader::ReadNextBlock` 读出该指针、遇 `idx_t(-1)` 终止(metadata_reader.cpp:60-86)。所以 header 里一个 64 位 `meta_block` 能串起任意长的 catalog 流;每张表另有自己的链根(`table_pointer`)。分配侧 `AllocateHandle` 找第一个有空分片的块、没有就开新块,发现要写"磁盘已有"的块就先转瞬态(metadata_manager.cpp:54-96)。checkpoint 把链上被重写的旧分片登记为"已修改",header 切换后统一归还(`MarkBlocksAsModified`,metadata_manager.cpp:386-419;调用点 single_file_block_manager.cpp:1334);Flush 时瞬态块经线程安全版 `ConvertToPersistent` 转正写盘,已是持久块的直接写(metadata_manager.cpp:277-313)。

## 5. Catalog 持久化:CatalogSet 如何"写盘"

`CatalogSet` 只管内存里的条目版本链(catalog_set.hpp:54 起),它不直接写盘;持久化由 checkpoint 驱动:`DuckCatalog::ScanSchemas` 遍历已提交 schema(duck_catalog.cpp:191),`GetCatalogEntries` 把每个 schema 的自定义类型、sequence、表(按外键依赖重排)、视图、trigger、宏、索引**摊平成有序列表**(checkpoint_manager.cpp:117-197),依赖管理器再整体重排一次(:251-253),交给一个 `BinarySerializer`:

```cpp
// src/storage/checkpoint_manager.cpp:275-281(格式示意见同文件 259-274 注释)
BinarySerializer serializer(*metadata_writer, SerializationOptions(db));
serializer.Begin();
serializer.WriteList(100, "catalog_entries", catalog_entries.size(), [&](Serializer::List &list, idx_t i) {
    auto &entry = catalog_entries[i];
    list.WriteObject([&](Serializer &obj) { WriteEntry(entry.get(), obj); });
});
serializer.End();
```

- **条目 ↔ CreateInfo 往返**:每个条目先写"catalog_type"标签(:416),再按类型分发(`WriteEntry`,:415-467);内容以 `GetInfo()` 产出的 CreateInfo(解析层结构)承载,如 `SchemaCatalogEntry::GetInfo`(schema_catalog_entry.cpp:79-85)、`TableCatalogEntry::GetInfo`(table_catalog_entry.cpp:99);读侧 `ReadCreateInfo` 反序列化并校验类型(:477-488),随后走正常 `catalog.CreateXxx` 路径重建(:535-543 等)。**序列化代码由脚本生成**,位于 src/storage/serialization/*.cpp,以字段 id + `ShouldSerialize(StorageVersion)` 做字段级版本门控(serialize_create_info.cpp:22-38;serialize_storage.cpp:37-46)。
- **schema 与表数据分流**:表的列/约束进 catalog 流;行数据由 `SingleFileTableDataWriter` 写**另一条** `table_metadata_writer` 链——全局统计、逐个 row group 指针依次序列化,最后把链根作为 `table_pointer`(101)与 `total_rows`(102)写回 catalog 流(checkpoint_manager.cpp:694-713;table_data_writer.cpp:97-190,链根取自 :108,回写 :189)。数据本体是普通数据块上的压缩列段,行组写块时经 `PartialBlockManager` 拼块以减少半空块(checkpoint_manager.cpp:94-98)。
- **未变的表零写入**:`WriteUnchangedTable` 只重写指针,并把旧链上的块从 modified 集合豁免(table_data_writer.cpp:84-91,146;读侧对应 checkpoint_manager.cpp:733-734)。
- **索引**:catalog 流只存索引定义 + root block 指针/`IndexStorageInfo`,老文件缺字段用显式默认值兼容(checkpoint_manager.cpp:603-653,:610-611;表侧 :738-758)。
- **读回**:`SingleFileCheckpointReader::LoadFromStorage` 以 header 的 `meta_block` 起一条 `MetadataReader`,可选先预取全部 metadata 块(:393-413,预取 :402-407),`LoadCheckpoint` 反序列化逐条重建(:378-387)。

## 6. Open 流程:恢复判定与 WAL 重放

`LoadExistingDatabase` 先验 magic bytes、读 MainHeader(加密库在此验钥)、读双 header 并按 iteration 仲裁,再读 free list(single_file_block_manager.cpp:633-727)。catalog 重建后,`WriteAheadLog::Replay`(wal_replay.cpp:359-363)先**整体扫描**主 WAL 找 `CHECKPOINT` 标记及其字节区间(:484-502),再与 header 对账:`IsCheckpointClean` 判断标记里的 meta_block 是否就是当前 header 的 meta_block(storage_manager.cpp:741-743;调用 wal_replay.cpp:540)。四种结局:

```
扫描到 CHECKPOINT 标记?
├─ 否 → 直接逐条重放(撕裂尾容忍)                    (:609-667)
└─ 是 → IsCheckpointClean(标记.meta_block == header.meta_block)?
    ├─ 干净 & 无副 WAL   → checkpoint 已完成,WAL 作废  (:541-546)
    ├─ 不干净 & 无副 WAL → 截掉标记尾部,重放主 WAL     (:547-549,593-608)
    ├─ 有副 WAL & 干净   → 副 WAL 顶替主 WAL,只重放它  (:552-571)
    └─ 有副 WAL & 不干净 → 主+副合并进 .wal.recovery 再重放 (:576-584,403-461)
```

随后真正重放(:609-667):每个 `WAL_FLUSH` 边界提交一个事务、注册重放出的索引(:625-643);遇到序列化异常按"撕裂尾"容忍——回滚未完事务,WAL 从最后成功偏移继续用(:645-659,666-667),除非 `abort_on_wal_failure`。WAL 头部带版本号、db_identifier 与 checkpoint iteration,防止拿错库的 WAL(write_ahead_log.cpp:32,255-289;校验 wal_replay.cpp:588-592;副 WAL 版本不一致显式报错 :430-434)。只读连接不修改任何文件,按只读路径组合重放两个 WAL(:556-557,663-665)。

另注:**本基线已无 `checkpoint_on_attach` 选项**(全仓 grep 无命中,相关能力并入 `checkpoint_on_detach`/`checkpoint_on_shutdown`,attached_database.cpp:250-259):attach 时总是先 LoadFromStorage 再强制重放 WAL;重放器若发现 WAL 里的 checkpoint 标记与 header 对得上,WAL 直接作废——等价于老语义"attach 时顺便收尾 checkpoint",只是不再由选项控制。

## 7. 版本兼容:64-69 的窗口与 legacy 只读

- 当前 `VERSION_NUMBER = 69`(v2.0.0),可读窗口 `[64, 69]`(storage_info.cpp:14-16,141);越界一律 `ShowUnsupportedStorageVersionError`,报错里指明文件出自哪个 DuckDB 版本(single_file_block_manager.cpp:217-237)。**没有更老的读取路径**:v0.10(64)之前的文件需用老二进制迁移;所谓 legacy 支持即 64 起的文件仍可打开(读写皆可,格式不符处按版本门控回退)。
- 版本号高度多对一:v0.10.0-v1.1.3 全部映射 64,v1.2.x=65、v1.3.x=66、v1.4.x=67、v1.5.x=68、v2.0.0=69(storage_info.hpp:119-148),细分行为靠独立的"序列化版本"(Deprecated,storage_info.cpp:104-137)与字段门控补足;老编码(含历史上误把 64 写进序列化版本字段的 bug)在 `SetStorageVersionInDatabaseHeader` 里逐值映射回 StorageVersion(single_file_block_manager.cpp:291-346)。
- 双版本号体系:main header 的 version_number 自 v2.0.0 起写 999,权威版本在 database header 的 `storage_compatibility`(single_file_block_manager.cpp:178-181,282-288);发生 64→65 升级或从 999 降级时,写 header 会顺带重写 main header(:1396-1405)。
- 方向性约束:显式 `STORAGE_VERSION` 只能 ≥ 文件现版本,否则拒开(:836-848);`StorageCompatibility::Compare` 是所有字段门控的裁判(storage_compatibility.cpp:66-72),`FromString` 负责 ATTACH 参数解析(:22-38)。行 id 空洞持久化等新能力要求 v2.0.0(:70-72)。
- 结构性硬校验:`vector_size` 必须与编译期一致(single_file_block_manager.cpp:366-370),`block_alloc_size` 建库后不可改、非法值按损坏处理(:824-830,858-863;校验规则 storage_info.cpp:264-301)。

## 8. 设计动机

1. **双 DatabaseHeader + iteration**:元数据提交被简化为"写另一份 header + 翻转指针"。任何时刻断电,iteration 大者必是最后一次完整提交;旧 header 天然是一致回退点。元数据一致性不需要日志,只需要一次原子切换。
2. **meta block 链 + 64 分片**:catalog/统计/row group 指针是 KB 级小对象,独占 256KB 块浪费两个数量级;"块首 8 字节后继指针"的单向链让根指针只有 64 位,读写都按分片 pin——缓冲池粒度仍是大块,小对象却按字节排布。
3. **block id 分配独立于内存池**:磁盘 block id(空闲性、共享计数、free list 持久化)与 BufferManager 的内存分配(BlockAllocator)彻底解耦——前者决定崩溃后的正确性,后者只决定吞吐。任一侧重构不波及文件格式,也让只读打开可以完全不碰内存池。
4. **COW checkpoint + modified_blocks 延迟回收**:checkpoint 期间旧块对在途读快照依然有效,新数据全部写新块,checkpoint 结束(header 翻转)后旧块才回 free list。老格式所需的 checkpoint 期 block 重映射因此消失,"标记干净即丢弃 WAL"的快速恢复成为可能。
5. **catalog 流与表数据流分离**:catalog 流小而每次全量重写,表数据流大且可按表短路(未变表只重写 64 位 `table_pointer`)。两条 MetadataWriter 让"DDL 少、数据常变"的负载 checkpoint 开销接近 O(变化量),也让表数据可以并行写(row group writer)而不搅动 catalog 流。
6. **WAL 内嵌 CHECKPOINT 标记**:"checkpoint 是否完成"这一控制信息放进与数据相同的持久化通道,而非独立标志位,恢复只需一次字节对账(`IsCheckpointClean`);配合双 WAL,checkpoint 进行中的并发提交也有确定的归属。
7. **保留 legacy 窗口而非无限兼容**:嵌入式场景下用户文件是长期资产,64-69 的可读窗口 + 字段级版本门控让兼容成本可控;更老格式交给"用旧版本导出"的一次性迁移,读路径不必背上十年包袱。999 哨兵则把"权威版本"干净地移交给 database header,main header 退化为纯身份信息。
