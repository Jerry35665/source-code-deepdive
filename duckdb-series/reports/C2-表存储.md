## 1. 层级与常量:DataTable → RowGroupCollection → RowGroup → ColumnSegment

四层结构的落点:

- `DataTable` 持有一个 `shared_ptr<RowGroupCollection> row_groups`(src/include/duckdb/storage/data_table.hpp:64、src/include/duckdb/storage/data_table.hpp:335),构造时即创建 collection(src/storage/data_table.cpp:80)。
- `RowGroupCollection` 持有表类型、`row_group_size` 与一棵 `RowGroupSegmentTree`(src/storage/table/row_group_collection.cpp:138-154,`row_group_size` 在 141 行初始化)。行组以 `SegmentTree<RowGroup,true>` 组织,节点为 `SegmentNode<RowGroup>`(src/include/duckdb/storage/table/segment_tree.hpp:23、src/include/duckdb/storage/table/segment_tree.hpp:104)。
- `RowGroup : SegmentBase<RowGroup>`,持有 `version_info`(MVCC)与惰性加载的 `columns`(src/include/duckdb/storage/table/row_group.hpp:98、src/include/duckdb/storage/table/row_group.hpp:111-116)。
- `ColumnSegment : SegmentBase<ColumnSegment>` 是最小的存储单元(src/include/duckdb/storage/table/column_segment.hpp:40)。`SegmentBase` 只有 `atomic<idx_t> count` 一个字段(src/include/duckdb/storage/table/segment_base.hpp:16-24)。

两个关键常量:

```cpp
// src/include/duckdb/storage/storage_info.hpp:26,33,68
#define DEFAULT_ROW_GROUP_SIZE 122880ULL          // = 2048 * 60,即 60 个 vector
#define DEFAULT_BLOCK_ALLOC_SIZE 262144ULL        // 256KB
constexpr static idx_t DEFAULT_BLOCK_SIZE =
    DEFAULT_BLOCK_ALLOC_SIZE - DEFAULT_BLOCK_HEADER_SIZE;  // 去掉块头
// storage_info.hpp:58
constexpr static const idx_t MAX_ROW_GROUP_SIZE = 1ULL << 30ULL;
```

122880 = 60 × STANDARD_VECTOR_SIZE(2048)。row group 大小可通过 ATTACH 参数配置,但必须被 vector 大小整除(src/storage/storage_manager.cpp:463-474);`TableIOManager::GetRowGroupSize()` 把它下发给每张表(src/include/duckdb/storage/table_io_manager.hpp:35)。**段(segment)大小上限则是块大小**:`ColumnSegment::segment_size` 受 `GetBlockSize()` 约束(src/include/duckdb/storage/table/column_segment.hpp:182-183),一个 row group 的每一列通常被切成约 60 个块级段(每段一个 vector 的整数倍)。

打开数据库时并不立即加载所有行组:`RowGroupSegmentTree::LoadSegment` 按需反序列化 `RowGroupPointer` 构造 `RowGroup`(src/storage/table/row_group_collection.cpp:114-127);列数据(`ColumnData`)更是扫描到哪列才加载哪列(src/include/duckdb/storage/table/row_group.hpp:302-319 的 `is_loaded` 机制)。

## 2. ColumnSegment 的两种形态

形态由枚举决定(src/include/duckdb/storage/table/column_segment.hpp:37):`TRANSIENT`(内存中、未压缩、可追加)与 `PERSISTENT`(引用磁盘块、压缩、只读)。

```cpp
// src/storage/table/column_segment.cpp:55-66  transient:注册一块临时内存
auto block = buffer_manager.RegisterTransientMemory(segment_size, block_manager);
return make_uniq<ColumnSegment>(db, std::move(block), ColumnSegmentType::TRANSIENT,
                                0U, function, BaseStatistics::CreateEmpty(type),
                                INVALID_BLOCK, 0U, segment_size);
// src/storage/table/column_segment.cpp:44-49  persistent:按 DataPointer 挂回磁盘块
auto function = config.GetCompressionFunction(compression_type, type.InternalType());
if (block_id != INVALID_BLOCK) {
    block = block_manager.RegisterBlock(block_id);
}
auto segment_size = block_manager.GetBlockSize();
```

持久化段的全部身份信息编码在 `DataPointer` 里:`row_start / tuple_count / block_pointer / compression_type / byte_size / statistics / segment_state`(src/include/duckdb/storage/data_pointer.hpp:51-76)。从磁盘恢复时,`ColumnData::InitializeColumn` 逐 pointer 调 `CreatePersistentSegment` 重建段并合并统计(src/storage/table/column_data.cpp:919-938,创建点在 934)。

两个方向的转换:

- **内存→磁盘(checkpoint)**:`ColumnSegment::ConvertToPersistent` 不重写数据,只把已 pin 的内存块"转正"为磁盘块,改元数据(src/storage/table/column_segment.cpp:252-275);若统计显示整段是常量,则连块都不要,换成 `COMPRESSION_CONSTANT` 并置空 block(268-274)。
- **压缩重写**:checkpoint 的主路径不是上面的零拷贝转换,而是 `ColumnDataCheckpointer` 把 transient(以及带更新的 persistent)段整体重扫描、重新压缩成新块(见 §6)。`MarkAsPersistent/SetBlock`(src/storage/table/column_segment.cpp:277-287)用于 partial block manager 把多个小段拼进共享块的场景。

`GetDataPointer` 是持久化段的出口:把 block_id、偏移、压缩类型、字节占用量和(可选的)压缩私有状态序列化出去(src/storage/table/column_segment.cpp:289-305)。

## 3. 写入路径:append → 段的分配与封满

入口链:`RowGroupCollection::InitializeAppend` 选定目标行组(src/storage/table/row_group_collection.cpp:630-669)→ `RowGroup::Append` 逐列下发(src/storage/table/row_group.cpp:1311-1321)→ `ColumnData::AppendData` 逐段写入(src/storage/table/column_data.cpp:645-675)。

```cpp
// src/storage/table/row_group.cpp:1311-1321  行组内按列下发
void RowGroup::Append(RowGroupAppendState &state, DataChunk &chunk, idx_t append_count) {
    for (idx_t i = 0; i < GetColumnCount(); i++) {
        auto &col_data = GetColumn(i);
        auto prev_allocation_size = col_data.GetAllocationSize();
        col_data.Append(state.states[i], chunk.data[i], append_count);
        allocation_size += col_data.GetAllocationSize() - prev_allocation_size;
    }
    state.offset_in_row_group += append_count;
}
```

**行组层面的封满判定**在 collection 的 append 循环里:

```cpp
// src/storage/table/row_group_collection.cpp:688-689
idx_t append_count = MinValue<idx_t>(
    remaining,
    row_group_size - state.row_group_append_state.offset_in_row_group);
// ... 装不下时(708-717):finalize 当前行组、AppendRowGroup 开新行组、
//     RowGroup::InitializeAppend 重置各列的 ColumnAppendState
```

`InitializeAppend` 还决定"要不要开新行组":行组树为空、append 模式为 `REQUIRE_NEW`(如 VARIANT/GEOMETRY 列、或 checkpoint 过后 `SUGGEST_NEW`)时新建;有索引且 vacuum 无法重建时则尽量续写旧行组(src/storage/table/row_group_collection.cpp:640-655)。新行组的创建即 `AppendRowGroup` → `RowGroup::InitializeEmpty` 为每列建一个 `ColumnData`(src/storage/table/row_group_collection.cpp:258-263、src/storage/table/row_group.cpp:250-257)。

**段层面的分配与封满**在 `ColumnData::InitializeAppend`:最后一若是 persistent 段(或压缩函数不支持 append)就再开一个 transient 段,绝不写历史数据(src/storage/table/column_data.cpp:630-634);`AppendData` 中段满则先把本段统计 `FlushSegmentStats` 归并进列统计(src/storage/table/column_data.cpp:569-584),再开新段(668)。

transient 段的尺寸策略颇有讲究(src/storage/table/column_data.cpp:793-835):首段取 `initial_column_segment_size` 设置(默认很小),之后逐段翻倍(804),到 1024 字节以上对齐到"2 的幂 − 块头"(817-819),上限是块大小(824);validity 段因位图按 vector 对齐,有 `STANDARD_MASK_SIZE` 的下限(807-811)。小段+倍增是为了冷表省内存,热表很快收敛到整块。函数固定为 `COMPRESSION_UNCOMPRESSED`(827)——**写入路径永远不压缩,压缩只发生在 checkpoint**。

最后,提交时 `FinalizeAppend` 把版本信息按行组分摊写入(`AppendVersionInfo`,src/storage/table/row_group_collection.cpp:731-762,742 行),并把线程本地的 distinct 统计合并进全局统计(753-759)。

## 4. 读取路径:压缩函数多态、scan state 与过滤下推

`ColumnSegment` 本身不认识任何压缩格式,所有读写都转发给 `CompressionFunction` 函数表:

```cpp
// src/storage/table/column_segment.cpp:137-139,161-167(节选)
void ColumnSegment::InitializeScan(ColumnScanState &state) {
    state.scan_state = function.get().init_scan(state.context, *this);   // 138
}
void ColumnSegment::Filter(ColumnScanState &state, ..., const TableFilter &filter, ...) {
    ...
    function.get().filter(*this, state, scan_count, result, sel, sel_count,
                          filter, filter_state);                          // 166
}
```

即 `init_scan/scan_vector/scan_partial/filter/select/fetch_row/skip`(src/storage/table/column_segment.cpp:141-190)。持久化段在 `CreatePersistentSegment` 里按 `DataPointer.compression_type` 查出函数表(src/storage/table/column_segment.cpp:44),transient 段固定为 uncompressed —— **读哪个解压器,由段自己携带的元数据决定,调用方无感**。

扫描状态分三层:`CollectionScanState`(行组游标)→ `ColumnScanState`(列/段游标,`scan_state` 存压缩私有状态)→ 各压缩格式的 `SegmentScanState`。`RowGroup::InitializeScanInternal` 为每列建 `ColumnScanState` 并递归初始化 validity 子列(src/storage/table/row_group.cpp:385-431);`PrepareScan/ProcessPreparedScan` 按 vector 推进(src/storage/table/row_group.cpp:910、src/storage/table/row_group.cpp:979),`RowGroup::Scan` 的循环即"准备→预取→产出一个非空 chunk"(src/storage/table/row_group.cpp:1099-1107)。

过滤下推两级配合:

1. **行组级 zonemap**:扫描新行组时用行组统计裁剪,`FILTER_ALWAYS_FALSE` 直接跳过整组(src/storage/table/row_group.cpp:738-808);多列表达式过滤器也能用各列统计求值(770-776);rowid 列用 `[row_start, row_start+count)` 区间精确判定(788-790)。
2. **段级 zonemap + 向量化 filter**:`CheckZonemapSegments` 用段统计把游标直接快进到不可能命中的段之外(src/storage/table/row_group.cpp:810-867,跳段循环在 860-863);活下来的 vector 再走 `ColumnSegment::Filter`,由压缩函数在解压/不解压的情况下产出选择向量(161-167)。validity 统计还支撑 `IS NULL` 直查(src/storage/table/column_data.cpp:50-58)。

点查则走 `FetchRow`(src/storage/table/column_segment.cpp:185-190),经 `RowGroup::Fetch` 先做可见性过滤(src/storage/table/row_group.cpp:1213-1224)。

### 4.1 并行扫描与 I/O 预取

扫描状态的核心是 `CollectionScanState`(src/include/duckdb/storage/table/scan_state.hpp:267):它持有当前行组节点、行组内 vector 游标 `vector_index`、每列的 `ColumnScanState` 数组、可见行选择向量 `valid_sel` 以及"已准备未产出"的 `prepared_vector`(src/include/duckdb/storage/table/scan_state.hpp:271-291)。多线程并行时,`NextParallelScan` 以行组为单位分发任务:每个线程原子地认领下一个非空行组的一个 vector 区间(src/storage/table/row_group_collection.cpp:362 起,`InitializeParallelScan` 在 352 行),`batch_index` 让上层算子保持有序输出。

I/O 侧的配合分两步:认领任务后先 `PrefetchScanIO` 同步预取本区间要读的块(src/storage/table/row_group.cpp:880),其内部 `RegisterScanIO` 按段注册 block 预取(869;持久化段调用压缩函数的 `init_prefetch` 或直接加块,src/storage/table/column_segment.cpp:125-135);异步版 `CollectScanIOTasks` 则只收集任务不下发(896 行的 `PrefetchRowCount` 还会用 zonemap 把区间尾部注定被裁掉的 vector 排除在预取之外)。

checkpoint 侧还有个细节:`RowGroupReorderer` 允许按 `RowGroupOrderOptions`(如按删除率/行数)重排行组的 checkpoint 顺序,为 vacuum 腾出合并空间(src/include/duckdb/storage/table/row_group_reorderer.hpp:25)。

## 5. validity 段:与数据段同构的独立位图列

每个 `StandardColumnData` 都挂一个子 `ValidityColumnData`(src/storage/table/standard_column_data.cpp:15-18),类型是 `LogicalTypeId::VALIDITY`,同样是 `ColumnData : 段树` 的完整形态(src/include/duckdb/storage/table/validity_column_data.hpp:16、src/storage/table/validity_column_data.cpp:7-15)——所以 null 掩码享受与数据完全相同的段管理、checkpoint、统计与惰性加载。扫描时 validity 作为 child_states[0] 与数据并行推进(src/storage/table/standard_column_data.cpp:46-56),任一侧需要 flat vector 则整体 flat(26-36)。

它与数据段的"不同构"之处有两点:其一,压缩格式是位级专用实现(empty_validity/uncompressed validity,src/storage/compression/empty_validity.cpp:6-8);其二,若数据段压缩自带 null 处理(如 dict_fsst、bitpacking 的 no-validity 变体),checkpoint 时 validity 会被替换成 `COMPRESSION_EMPTY`,连块都不落(src/storage/table/column_data_checkpointer.cpp:301-321,320 行取空函数)。反之,更新 null 位时若发现 validity 段是 `COMPRESSION_EMPTY`,要先从数据段读回真实掩码再改(src/storage/table/validity_column_data.cpp:23-29)。

## 6. 字符串段:内联字典、溢出块与 dict_fsst 读取

**未压缩(写入态)字符串段**本身就是个"块内字典":块头 8B 记录 `dict_size/dict_end`(src/include/duckdb/storage/string_uncompressed.hpp:52-53),字符串数据从块尾向下生长,行索引数组存的是 `int32` 偏移。追加逻辑(src/include/duckdb/storage/string_uncompressed.hpp:96-195):

- null 复制前一个偏移,保证 `string_length` 计算便宜(110-127);
- 串长 ≥ 块限制(`GetStringBlockLimit`)则走溢出块:字符串写入独立 block,段内字典区只写 12B 的 `(block_id, offset)` marker,且行索引存**负偏移**标识"这是个溢出引用"(src/include/duckdb/storage/string_uncompressed.hpp:138-172);
- 读取时正偏移直接在块内字典取串,负偏移先 `ReadStringMarker` 解出 block_id+offset,再去读溢出块(src/include/duckdb/storage/string_uncompressed.hpp:239-267,263-266)。

**checkpoint 时**该格式让位于字典压缩。classic dictionary 的段头只 20B(src/include/duckdb/storage/compression/dictionary/common.hpp:10-16),且明确拒绝超长串(45-48);现行默认是 dict_fsst 组合编码(src/storage/compression/dict_fsst.cpp:49)。读取侧按块内固定顺序解开(src/storage/compression/dict_fsst/decompression.cpp:46-124):

```cpp
// src/storage/compression/dict_fsst/decompression.cpp:70-73(布局)
auto dictionary_dest       = AlignValue<idx_t>(DICTIONARY_HEADER_SIZE);
auto symbol_table_dest     = AlignValue<idx_t>(dictionary_dest + dictionary_size);
auto string_lengths_dest   = AlignValue<idx_t>(symbol_table_dest + symbol_table_size);
auto dictionary_indices_dest = AlignValue<idx_t>(string_lengths_dest + string_lengths_space);
```

扫描时一次性把整本字典解压成可复用的 `DictionaryVector`,行数据只做选择(src/storage/compression/dict_fsst/decompression.cpp:110-123);FSST 符号表在 `Initialize` 里导入 decoder(84-97),这是"字典压缩下读取"的核心:每行付出一次索引查表,字符串本体零重复解压。

## 7. RowGroup 的版本管理接口与 delete/update 的物理布局

RowGroup 对 MVCC 只暴露接口(src/include/duckdb/storage/table/row_group.hpp:187-198、259-263):`AppendVersionInfo / CommitAppend / RevertAppend / CleanupAppend / Delete / CheckpointDeletes / CompressVersionInfo`。实现委托给 `RowVersionManager`,它按 vector(2048 行)持有 `ChunkVectorInfo`(src/include/duckdb/storage/table/row_version_manager.hpp:61),提供 `GetSelVector` 把"对该事务不可见的行"变成选择向量(src/include/duckdb/storage/table/row_version_manager.hpp:32),`DeleteRows` 打删除标记(41),`CompressVersionIds` 把所有可见性边界之下的版本号坍缩成常量(48)。版本信息的持久化形态是 `deletes_pointers`(元数据块指针),扫描用到时才反序列化回内存(src/storage/table/row_group.cpp:1141-1157,1153 行)。事务如何用这些接口做快照判定,卷一已述。

**DELETE 的物理布局**:`RowGroup::Delete` 把 row id 归约到行组内偏移,交给 `VersionDeleteState` 按 vector 批量 flush(src/storage/table/row_group.cpp:2129-2141)。行数据一个字节都不动——删除只是版本信息里的标记。

**UPDATE 的物理布局**:数据同样原地不动,新值写进 `UpdateSegment`(挂在 `ColumnData` 上,src/include/duckdb/storage/table/column_data.hpp:277-281)。链路是 `RowGroup::Update` → `col_data.Update` → `UpdateSegment::Update`(src/storage/table/row_group.cpp:1344-1365,统计合并见 1363)。`UpdateSegment` 按 vector 组织 `UpdateNode → vector<UndoBufferPointer>`,每条 `UpdateInfo` 头部之后**内联**存放 `[sel_t 元组id][新值]`,一条恰好覆盖一个 2048 行向量(src/storage/table/update_segment.cpp:81-104):

```cpp
// src/storage/table/update_segment.cpp:102-104
idx_t UpdateInfo::GetAllocSize(idx_t type_size) {
    return AlignValue<idx_t>(sizeof(UpdateInfo) +
        (sizeof(sel_t) + type_size) * STANDARD_VECTOR_SIZE);
}
```

分配走事务 undo buffer(src/include/duckdb/storage/table/update_segment.hpp:113-115 的 `UndoBufferAllocator`),因此回滚=整条链回退,提交=版本号翻转,这与卷一的 MVCC 闭环衔接。字符串新值放在专属 `StringHeap`(src/include/duckdb/storage/table/update_segment.hpp:68-69)。多个事务更新同一 vector 时,`UpdateInfo` 结成 prev/next 链(每事务一条),读取时按快照挑最新可见版本。checkpoint 时这些增量要么合并重写进新段,要么随整组元数据复用而保留(src/storage/table/column_data.cpp:95-120 的变更判定)。

## 8. Checkpoint:WriteToDisk 触发压缩与统计汇聚

入口两级:catalog 序列化调 `CheckpointReader::WriteTable`,拿到 `TableDataWriter` 后调 `WriteTableData`(src/storage/checkpoint_manager.cpp:707-712),后者一行转手给 `table.GetStorage().Checkpoint`(src/storage/checkpoint/table_data_writer.cpp:37-40)。

`RowGroupCollection::Checkpoint` 是并行调度中枢(src/storage/table/row_group_collection.cpp:1712-1763):先按行组调度 vacuum 任务(1745 行顺带做 `CompressVersionInfo`),再为每个行组排一个 `CheckpointTask`,任务体就两行——拿 `RowGroupWriter`,调 `RowGroup::WriteToDisk`(src/storage/table/row_group_collection.cpp:1150-1169,1160 行)。

`RowGroup::WriteToDisk` 先尝试省事:行组无任何变化且支持元数据复用时,直接返回 `REUSE_EXISTING_ROW_GROUP_METADATA`;否则按列粒度决定 `FULLY_CHECKPOINT` 还是 `PARTIALLY_REUSE`(src/storage/table/row_group.cpp:1634-1677);真正要写的列走 `CheckpointColumn`(1732)。

真正触发压缩的是 `ColumnDataCheckpointer`(由 `ColumnData::Checkpoint` 构造,src/storage/table/column_data.cpp:887-913):它把该列整个行组的所有段重扫描,让每种候选压缩算法跑 `analyze` 计分,`final_analyze` 分数最小者胜出(src/storage/table/column_data_checkpointer.cpp:172-271,238-249);然后 `init_compression → compress(逐 vector) → compress_finalize` 写出新块(src/storage/table/column_data_checkpointer.cpp:310-357,340-352),旧块经 `DropSegments` 标记为可复用(356、284-298)。无变更的列则零拷贝,只重发 `DataPointer` 并合并段统计(src/storage/table/column_data_checkpointer.cpp:363-398)。这解释了 §3 的结论:**transient 段的"flush"= 重新压缩落盘,而非原样写出**。

每组的产物汇回 `RowGroup::Checkpoint`:生成 `RowGroupPointer`(row_start/tuple_count/各列 DataPointer/删除指针,src/storage/table/row_group.cpp:1759-1766),序列化列元数据并记录每列的额外元数据块(1852-1906),最后由 collection 统一 `writer.AddRowGroup` 并把新行组挂进新段树(src/storage/table/row_group_collection.cpp:1873-1887)。

**统计**在行组级维护:每列每段有 `SegmentStatistics`,行组可 `MergeStatistics/GetStatistics`(src/storage/table/row_group.cpp:1389-1411);全局 `TableStatistics` 由各组的统计逐级 merge 而来(src/include/duckdb/storage/table/table_statistics.hpp:30-44),checkpoint 结尾重放(src/storage/table/row_group_collection.cpp:1808 及 1840-1844)。append 期间用线程本地统计缓存降低 distinct 统计的锁竞争(src/storage/table/row_group_collection.cpp:721-726、753-759)。优化器拿到的 zonemap 正是这些行组/段级 min-max(src/storage/table/row_group.cpp:792);`GetPartitionStats` 还能把行组粒度统计暴露给更激进的分区裁剪(src/storage/table/row_group.cpp:2061)。表整体无变化时连统计都直接复制旧值(src/storage/table/row_group_collection.cpp:1796-1798)。

## 9. 表元数据:与 A2 catalog 序列化的衔接

`SingleFileTableDataWriter::FinalizeTable` 把行组指针与统计写成一段自包含的元数据流(src/storage/checkpoint/table_data_writer.cpp:97-136):先记下元数据起始 `MetaBlockPointer`(108),序列化全局统计(112-116),再逐个 `RowGroup::Serialize`(132;字段见 src/storage/table/row_group.cpp:1995-2015)。catalog 侧只落三样东西:`table_pointer`(指向上面那段元数据的指针)、`total_rows`、`next_row_id`(src/storage/checkpoint/table_data_writer.cpp:189-220)。启动读取时对称:`CheckpointReader::ReadTableData` 取回 `table_pointer`(src/storage/checkpoint_manager.cpp:731-735),`RowGroupCollection::Initialize(PersistentTableData)` 据此挂上 `MetadataReader` 惰性加载行组(src/storage/table/row_group_collection.cpp:202-212、persistent_table_data.hpp:22-27),并把指针存起来供下次 checkpoint 做元数据复用判定(src/storage/table/row_group_collection.cpp:214-218;复用路径见 1767-1800)。

## 10. 设计动机

1. **为什么 122880 行一组(60 个 vector)?** 行组是并行扫描/裁剪/统计的粒度:60 个 vector 让一个行组足够大到让 zonemap 与压缩发挥价值(压缩需在块内积累重复度),又足够小到让多线程Scan负载均衡;且必须是 vector 大小整数倍才能按 vector 无拷贝切片与做删除选择向量(src/storage/storage_manager.cpp:470-474、src/include/duckdb/storage/table/row_version_manager.hpp:61)。可配置但受 `MAX_ROW_GROUP_SIZE` 约束(storage_info.hpp:58)。
2. **为什么 persistent/in-memory 双形态?** 写入路径追求吞吐:append 只碰无锁化的内存块、不压缩(column_data.cpp:622-643、827),把"选算法、算分、重写"的成本推迟到 checkpoint 一次性摊销;持久化段则把身份压缩成几十字节的 `DataPointer`,重启后不必触碰数据块即可恢复表骨架(data_pointer.hpp:51-76)。两形态间的 `ConvertToPersistent` 甚至支持零拷贝转正(column_segment.cpp:252-275)。
3. **为什么按列段(而非行组)为压缩单元?** 一个行组的列数据远大于一个块,只有切到块级段才能:每段独立携带压缩类型与统计,冷热混合(新 transient + 旧 persistent)共存于一个行组(row_group.cpp:1924-1954 的 `HasChanges/IsPersistent` 逐列判定);`CompressionFunction` 函数表让每个段自带解压器,新压缩格式可渐进混存(column_segment.cpp:44、137-139)。
4. **为什么统计放在行组/段级?** 裁剪是分层的:行组级 zonemap 砍掉整组(一次省 122880 行),段级 zonemap 砍掉 2048 行,vector 内再靠 `filter` 选择向量;每层统计随数据同地存储、同地更新(append 时即合并,column_data.cpp:569-584),checkpoint 时上卷成全局统计供优化器(table_statistics.hpp:41-44),不需要独立的索引维护。
5. **为什么 validity 独立成段?** 与数据同构地复用整套段机制(压缩、统计、惰性加载、更新),但可整体省略:数据压缩若自带 null 语义,checkpoint 直接换成 `COMPRESSION_EMPTY` 一块不落(column_data_checkpointer.cpp:313-321);`IS NULL` 过滤还能直接用它的 zonemap 回答(column_data.cpp:50-58)。
6. **为什么 update/delete 是"旁路"而不是原地改?** 基线段保持不可变,读多写少场景下扫描零锁;增量(update 链、删除位图)足够小且按 vector 对齐,checkpoint 时批量合并回新段。这使"事务可见性(卷一)"与"物理布局(本卷)"解耦:两者只在 `GetSelVector` 一处交汇(row_group.cpp:1201-1211)。
7. **为什么元数据复用值得做到列级?** 分析型库的典型负载是"追加新行组、老组纹丝不动"。`REUSE_EXISTING_ROW_GROUP_METADATA`/`PARTIALLY_REUSE_COLUMN_METADATA` 让未变行组连元数据块都不重写(row_group.cpp:1634-1677),checkpoint 成本与实际变更量成正比,而非表大小。
8. **为什么版本信息挂在行组(而非表)上?** 行组的行号区间 `[row_start, row_start+count)` 是 row id 的天然分片:删除/插入可见性只需定位单个行组再按 vector(2048 行)细分(row_version_manager.hpp:61),判定与存储都免全局锁;未被动过的行组连版本信息都无需反序列化,`deletes_pointers` 指针原样复用即可(row_group.cpp:1979-1993)。
