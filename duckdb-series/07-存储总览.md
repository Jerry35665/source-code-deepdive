# 第 07 章 · 存储总览:SingleFileStorageManager 与数据库持久化(卷二)

> 基线:commit `7e886f44`(与卷一相同)。本卷聚焦磁盘侧:文件格式、block 管理、meta 链、catalog 序列化与恢复。

## 7.0 全景:一个数据库文件的磁盘布局

```
duck.db
│ [0,8) checksum │ [8,12) "DUCK" magic │ MainHeader(4096B 页,建库写一次)
│ [4096,8192) DatabaseHeader 1 ─┐ 互为校验:iteration 大者为活跃头
│ [8192,12288) DatabaseHeader 2 ┘ 七字段:iteration/meta_block/free_list/
│                                block_count/block_alloc_size/vector_size/version
│ [12288(=BLOCK_START)起] 数据块:block_id × 256KB(可调 16-256KB)
│   普通块:压缩列段/索引;meta 块:1 块切 64 分片(meta_block = 低56位block_id|高8位分片)
duck.db.wal    逻辑重放日志;副 WAL .wal.checkpoint / .wal.recovery
内存对应:AttachedDatabase → SingleFileStorageManager → SingleFileBlockManager
         → MetadataManager(meta 链) + BufferManager;catalog 根指针 = header.meta_block
```

## 7.1 文件格式:双 header 的提交点

MainHeader 是"身份证":版本、加密 flag、32 字节版本串+git hash、加密元数据与 canary"DUCKKEY"(错钥匙第一时间报错而不是烂在数据里,single_file_block_manager.cpp:101-174);自 v2.0.0 起其版本号固定写 999,权威版本移到 database header(:178-181)。**DatabaseHeader ×2 是唯一的提交点**:每次 checkpoint iteration+1、写到非活跃份、翻转指针(:1338,1413-1416)——任何时刻崩溃,磁盘上必有一份完整一致元数据,元数据一致性不需要日志,只需要一次原子切换。序列化就是七个字段的定长写出(:274-289)。所有块读写走 ChecksumAndWrite/ReadAndChecksum,不一致抛 DataCorruptionException(:744-749)。

## 7.2 block 分配与 free list 的自举

磁盘 block id:分配优先取 free_list 最小 id,否则 `max_block++` 扩张(:906-925);**回收两跳**——DROP/UPDATE 释放的旧块先入 modified_blocks(本次 checkpoint 不可复用,在途读快照还引用着),WriteHeader 尾部才转 free list(:972-1007);新分配未落盘的记 newly_used_blocks,崩溃自然消失。free list 持久化有个自举悖论:写 free list 本身要消耗块——解法是先估算总量**预分配**全部目标块,再用专用 writer 只往预分配块写(:1254-1306)。纠偏:老版本的"checkpoint 期 block 重映射"已不存在,现行等价物是 metadata 块写前转瞬态 + COW 的 modified_blocks 延迟回收;"BlockAllocator"是 BufferManager 的**内存池**(虚拟地址预留),与磁盘块号解耦。

## 7.3 meta block 链:64 分片

catalog/统计/行组指针这类 KB 级小对象若各占 256KB 块,写放大两个数量级。做法:**一个磁盘块切 64 份**(位图管理空闲分片),指针位打包——低 56 位 block_id + 高 8 位分片号(metadata_manager.cpp:196-208);追加写把下一块指针写进当前块头 8 字节形成单向链(metadata_writer.cpp:43-61)。checkpoint 重写整条链,旧块经 MarkBlocksAsModified 归还。catalog 流小而全量重写;表数据流大且**未变表只重写 64 位 table_pointer**(table_data_writer.cpp:84-91)——checkpoint 成本与变化量成正比。

## 7.4 恢复:CHECKPOINT 标记的三路对账

LoadExistingDatabase:读双 header 按 iteration 仲裁→LoadFromStorage 重建 catalog→WAL 重放。重放先整体预扫描找 WAL 内嵌的 CHECKPOINT 标记(含 meta_block),再对账(wal_replay.cpp:519-587):无标记→直接重放(撕裂尾容忍);有标记且 meta_block 与 header 相符→**checkpoint 已完成,WAL 作废连重放都不需要**;不符→截掉标记尾部重放;有副 WAL→按相符与否改名顶替或合并进 .wal.recovery。`checkpoint_on_attach` 选项已不存在——attach 时总是 LoadFromStorage+强制重放。版本兼容:可读窗口 [64,69](v0.10~v2.0.0),更老格式交给"旧版本导出"一次性迁移。

## 7.5 设计动机

1. **双 header+iteration**:元数据提交=写另一份 header+翻转指针,断电时 iteration 大者必是完整提交;
2. **meta 链+64 分片**:小对象按字节排布,缓冲池粒度仍是大块,根指针只有 64 位;
3. **磁盘块号与内存池解耦**:前者决定崩溃正确性,后者只决定吞吐;
4. **COW checkpoint+延迟回收**:checkpoint 期间旧块对读快照仍有效,"标记干净即丢弃 WAL"的快速恢复成为可能;
5. **catalog 流/表数据流分离**:DDL 少数据多的负载 checkpoint 接近 O(变化量)。

## 7.6 FAQ

**Q1:断电后元数据会坏吗?**
不会:双 header 互为校验,iteration 仲裁;元数据一致性靠原子切换而非日志。

**Q2:meta_block 指针多大?**
64 位:低 56 位块号+高 8 位分片(metadata_manager.cpp:196-208)。

**Q3:free list 自己存在哪?**
meta 链上的专属块;写前预分配避免"写它要消耗它"的自举。

**Q4:旧版本 DuckDB 文件还能读吗?**
64-69 窗口内可读(读写皆可);v0.10 之前需用旧二进制导出。

**Q5:DROP TABLE 的块立即复用吗?**
不:先入 modified_blocks,本次 checkpoint 后才回 free list——在途快照仍引用。

**Q6:checkpoint 做一半崩了怎么办?**
WAL 里的 CHECKPOINT 标记+meta_block 对账判定;副 WAL 有则合并恢复。

**Q7:加密库的密钥校验在哪?**
MainHeader 的 canary"DUCKKEY"密文,解密前先验(:101-174)。

**Q8:块分配大小能改吗?**
建库后不可变,存于 database header(:279)。

**Q9:checkpoint 期间的新提交写到哪?**
副 WAL .wal.checkpoint,收尾时原子改名顶替主 WAL。

**Q10:vector_size 不符会怎样?**
拒开:结构硬校验(:366-370)。

## 7.7 小结与深挖方向

本章结论:**持久化="双 header 原子提交+meta 链 64 分片+COW 延迟回收+标记对账恢复"**。深挖:

1. PRAGMA checkpoint_abort 四个注入点的崩溃演练(checkpoint_manager.cpp:286-340);
2. TrimFreeBlocks 打洞归还文件系统(:1450-1477);
3. 加密 WAL v3 的 nonce/GCM tag 布局(write_ahead_log.cpp:167-189);
4. StorageVersion 64-69 多对一映射与字段级门控(storage_info.hpp:119-148);
5. 未变表零写入与 index storage info 的显式默认值兼容。
