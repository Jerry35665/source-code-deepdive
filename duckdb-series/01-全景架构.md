# 第 01 章 · 全景架构:进程内的数据库引擎

> 基线:commit `7e886f44`。行号以仓库根相对路径为准。

## 1.0 全景:对象层次与查询生命周期

```
应用进程(Python/R/CLI/C++)
│ duckdb::DuckDB(database.hpp:131)—— 薄壳
│ └ DatabaseInstance(database.cpp:82)—— 真引擎
│    ├ DBConfig / DatabaseManager(N× AttachedDatabase: Catalog+Storage+TxnMgr)
│    ├ StandardBufferManager / TaskScheduler / ExtensionManager / ConnectionManager
└ duckdb::Connection(connection.cpp:22)—— 门面
   └ ClientContext(client_context.hpp:90):TransactionContext + ClientData + 扩展状态
一条 SQL:Query(client_context.cpp:1114)→ Parser(PEG)→ Planner/Binder
        → Optimizer(client_context.cpp:525)→ PhysicalPlanGenerator(:541)→ Executor 多线程
```

链条里**没有网络层**:从 ClientContext 到 Executor 全是同进程函数调用。README 自述 "high-performance analytical database system"(README.md:18);打开不存在的路径就新建文件(storage_manager.cpp:478),连不上任何文件退化为内存库(database.cpp:499)——"SQLite of Analytics" 的外壳,列存 OLAP 的内核。

## 1.1 启动八步:`DatabaseInstance::Initialize`

`DuckDB` 构造只是"创建实例→Initialize→装载扩展→收尾"(database.cpp:375-381)。Initialize(database.cpp:302-373)顺序是理解全局的钥匙:①Configure 折叠配置、定默认内存(系统可用内存八成,:531-533)与线程数(核数,:534-539);②发布静态链接扩展清单(:311);③依序创建 DatabaseManager/BufferManager/TaskScheduler 等(:316-340);④system catalog(:343-346);⑤解析打开目标(:349);⑥把未识别配置归因到扩展(:363);⑦用内部 Connection 走完整 ATTACH 挂主库(:365);⑧最后才启动调度线程(:369)。原则:**先元数据后并发,先系统表后用户库**。

注意:主库就是一次普通 ATTACH(CreateMainDatabase,database.cpp:230-242),每个 AttachedDatabase 三件套 = DuckCatalog + SingleFileStorageManager + DuckTransactionManager(attached_database.cpp:138-160)——sqlite_scanner 等外部存储与主库共享同一抽象,"lakehouse 前端"由此铺路。

## 1.2 打开一个文件的六步

①实例缓存(C API 专有:仅 `duckdb_create_instance_cache`+`duckdb_get_or_create_from_cache` 路径命中,duckdb-c.cpp:69-77;普通 `duckdb_open` 直连 new——常见误解"open 走缓存"不成立);②路径登记:只读可共存累加引用,读写混用抛 ResourceInUseException(database_file_path_manager.cpp:37-58);③ATTACH 自旋等并发附加(database_manager.cpp:165-183);④构造三件套;⑤magic bytes 识别:sqlite 前缀/SQLite 文件/Parquet/CSV(`__open_file__` 替换扫描)/普通 DuckDB(database_path_and_type.cpp:22-60);⑥加载或新建(storage_manager.cpp:476-494):**文件存在→加载+WAL 恢复;不存在且可写→新建;只读打不开→报错**。

## 1.3 配置与扩展

配置三层:编译期默认(`checkpoint_wal_size=1<<24`,config.hpp:92)、命名设置表 `internal_options[]`(config.cpp:71 起,每个带 global/local 回调)、扩展设置(`AddExtensionOption`,config.cpp:553)。`SetOptionByName` 的三分支:内置→SetOption;扩展→按索引写;都不认识→进 `unrecognized_options` 等启动归因(config.cpp:360-378)。DBConfig 还持有可注入的 FileSystem/Allocator/BufferPool(config.hpp:186-210)——嵌入式"宿主接管资源"的典型。

扩展双轨:**静态链接**(发布版默认 icu/json/parquet/autocomplete,bundled_extensions.cmake:17-26;CMake 生成 loader 模板把每个扩展注册成 lambda 压进 `config.linked_extensions`,generated_extension_loader.cpp.in:12-16)与**动态 autoload/install**(TryAutoLoadExtension→InstallExtension→LoadExternal,extension_helper.cpp:238-255;ABI 校验在 extension.cpp:42-99)。同一条路径既能加载静态也能加载下载的动态扩展——**静态是动态的特例**。

## 1.4 设计动机

1. **为什么 in-process**:数据不跨进程搬运,查询全链一次函数调用;代价是失去多进程共享与权限隔离,所以同文件只允许一个读写实例;
2. **为什么单文件**:可拷贝可版本管理零部署;block/压缩/WAL/checkpoint 全收进 SingleFileStorageManager;
3. **为什么自研 PEG 取代 libpg_query**:扩展语法要能随版本演进,PG 单文件 LALR 文法无法拆分与注入(03 章展开);
4. **为什么扩展静态链接**:parquet/json/icu 是分析的事实核心,免去首次下载与供应链风险;
5. **为什么 ATTACH 统一主库**:外部存储与主库共享 Catalog/事务抽象。

## 1.5 FAQ

**Q1:DuckDB 与 SQLite 谁快?**
不同负载:OLAP 列存扫描/聚合 DuckDB 快(向量化+压缩);点查 OLTP 不是它的目标。

**Q2:同一进程能 open 两次同一文件吗?**
只读可共存;读写互斥(database_file_path_manager.cpp:54-57)。官方绑定经实例缓存让多次 connect 幂等。

**Q3:C API 和 C++ API 打开行为一致吗?**
不一致:普通 duckdb_open 不走缓存(capi/duckdb-c.cpp:81-89),C++ DuckDB 构造直连 Initialize。

**Q4:编译期怎么知道链接了哪些扩展?**
CMake 生成清单,启动注册进 config.linked_extensions(database.cpp:311)。

**Q5:版本号在哪定义?**
不硬编码:构建期由 release_version.txt+git 计数合成(CMakeLists.txt:428-503),SOURCE_ID 是 10 位 hash。

**Q6:内存上限默认多少?**
系统可用内存的 80%(database.cpp:531-533)。

**Q7:同一连接能并发查询吗?**
不能:context_lock 串行化本连接所有操作(client_context.cpp:228-230)。

**Q8:SYSTEM_DATABASE 是什么?**
常驻的无存储库(database_manager.cpp:25),系统函数都挂它的 catalog。

**Q9:未知配置项会报错吗?**
启动时尝试归因到扩展设置;归因失败才报(database.cpp:363)。

**Q10:能打开 SQLite 文件吗?**
能:magic bytes 识别后走 sqlite 扩展(database_path_and_type.cpp:22-60)。

## 1.6 小结与深挖方向
