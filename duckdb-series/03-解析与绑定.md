# 第 03 章 · 解析与绑定:自研 PEG 解析器与 Binder

> 基线:commit `7e886f44`。

## 3.0 全景:一条 SQL 到 BoundStatement

```
"SELECT name FROM t WHERE id=?"
 → NormalizeSQLString(UTF-8 校验,parser.cpp:229-237)
 → Tokenizer → MatcherToken 流
 → Parser::ParseQuery(parser.cpp:239-309):循环"匹配一条→翻译一条"
    PEG 匹配(packrat 缓存,parser_packrat.cpp:15-18)→ ParseResult 树
 → Transformer(REGISTER_TRANSFORM 注册表,peg_transformer_factory.cpp:126)
    → SQLStatement(未绑定 AST)
 → PendingStatementInternal(client_context.cpp:961-980)
 → Planner::CreatePlan(planner.cpp:147)→ Binder::Bind(binder.cpp:78-142)
    名字解析/类型绑定/查 catalog → BoundStatement{plan,types,names}
```

## 3.1 纠偏:libpg_query 已被移除

本主干 `third_party/` 与全文 grep 均无 pg_query/postgres_parser;**SQL 解析已切换为自研 PEG 解析器**(src/parser/peg/)。`src/README.md:4` "uses the parser of Postgres" 是未更新的陈旧表述。仓库无正式迁移公告,代码结构给出四条推断依据:文法按语句拆成 41 个 `.gram`+5 个关键字表(可被扩展增量注入);`GrammarChange` 提供运行期增删规则 API(grammar_change.cpp:7-34);parser 扩展契约改为 token 流(扩展报告消耗 token 数,parser.cpp:316-349);错误定位基于最深失败 token(peg_transformer_factory.cpp:79-94)。文法系统起源于 autocomplete 扩展(src/parser/peg/README.md:1-3),后被扶正为主解析器。

## 3.2 PEG 的取舍

有序选择 `/` 首个成功者胜:候选顺序敏感——`YEAR TO MONTH` 必须排在 `YEAR` 前(README.md:29-36);`NEAREST BY` 为防贪婪吃掉别名拆成 bare/aliased 两候选手工消歧(select.gram:107-109);指数回溯风险由 packrat 缓存压制(parser_packrat.cpp:15-18)。表达式文法**不用**优先级阶梯,`ColumnReference` 的五个候选把 catalog/schema/table 限定组合全部枚举(expression.gram:1-6)——把部分名字解析提前到文法层。负向前瞻 `!` 能写进文法但匹配器目前忽略(README.md:99-103 TODO)。

解析循环的容错:某语句 PEG 失败→把剩余 token 流交给 parse_function 扩展接力,扩展报告消耗量、游标推进(TryParseExtensionStatement,parser.cpp:311-352)。彩蛋:CHECKPOINT 语法在 transformer 层被降糖为 `CallStatement`(transform_checkpoint.cpp:11-13),没有专门的 Statement 子类。

## 3.3 Transformer:注册表 + 生成式 wrapper

每条文法规则对应一个 transform 函数,`REGISTER_TRANSFORM` 宏按函数名注册(peg_transformer_factory.cpp:126);SELECT/INSERT 等核心规则保持手写(:153-160),其余由 `generate_transformer.py` 依据 `grammar_types.yml` 生成强类型 trampoline(transform_generated.cpp)——"按下标取子节点"的样板自动化,手写体只留语义构造。SELECT 链:CTE 先转出存 `stored_cte_map` 使内部子句可见,最后挂回 `node->cte_map`(transform_select.cpp:55-92);`FROM` 缺省补 EmptyTableRef,`FROM x SELECT *` 方言兜底补 SELECT *(:1397-1420)。

## 3.4 Binder:名字解析决策树

入口链:PendingStatementInternal → Planner::CreatePlan → `Binder::Bind` 按 StatementType 分派 30+ 重载(binder.cpp:78-142)。列名解析核心 `ColumnQualifier::QualifyColumnName`(column_qualifier.cpp:140-193)顺序固定:①USING 列→改写 primary 列或 COALESCE;②lambda 参数;③普通列(bind_context.GetMatchingBinding);④宏参数;⑤失败给 "did you mean"。表发现顺序:**CTE→catalog→replacement scan**(bind_basetableref.cpp:142 起)——`FROM 'file.csv'` 的扩展名落地就在第三级兜底。CTE 沿 binder 父链上溯,只返回"可引用"的 CTE,循环引用跳过继续向上(binder.cpp:198-219)。

函数绑定:按 catalog 类型分派 scalar/macro/aggregate/window(bind_function_expression.cpp:296-324);聚合归属最内层能解析其参数的层级;重载选择由 `FunctionBinder::BindFunctionFromArguments` 按最大公共类型打分(function_binder.cpp:337)。裸词 `current_date` 在 binder 层改写成零参函数调用(column_qualifier.cpp:59-71)。

## 3.5 Prepared statements:复用与正确性的平衡

PREPARE 以 `BindingMode::PREPARE` 试绑一次,存 names/types/value_map/`unbound_statement`(planner.cpp:226-241);EXECUTE 时 `RequireRebind` 判定是否重绑——判据:参数从未定型、**catalog 身份(版本)变化**(对读写过的库逐一 `CheckCatalogIdentity`)、参数类型漂移(prepared_statement_data.cpp:107-134)。变了就现绑新计划,`LogicalExecute` 带新旧两套(bind_execute.cpp:83-108)。这是 prepared 缓存正确性的根基:否则可能执行在已被 DDL 改掉的表结构上。

## 3.6 设计动机

1. **自研解析器**:扩展自带文法增量在 PG 单文件 LALR 下不可行;
2. **PEG 换报错精度与可组合性**:代价是手工排候选 + packrat 压回溯;
3. **parse/transform 分离**:文法改动与 AST 构造解耦,生成式 wrapper 消样板;
4. **bind 期展开宏**:宏体限定需要外层作用域与 catalog,parse 期没有这些信息;
5. **子 binder 整体替换作用域**:防嵌套作用域链按 2^depth 膨胀(binder.cpp:271-282 注释)。

## 3.7 FAQ

**Q1:DuckDB 还用 PostgreSQL 的解析器吗?**
不用,已换自研 PEG(src/README.md:4 是陈旧表述)。

**Q2:.gram 文法是手写还是生成?**
文法手写,匹配器/transformer 骨架由 build_grammar.sh+generate_transformer.py 生成(README.md:141-186)。

**Q3:扩展能加自己的语法吗?**
能:编译期注入 .gram 或运行期 GrammarChange 增删规则(grammar_change.cpp:7-34)。

**Q4:语法错误怎么定位?**
token 迭代器的最深失败位置(peg_transformer_factory.cpp:79-94)。

**Q5:`SELECT x AS y ORDER BY y` 为什么能绑上?**
裸列名落空时 TryResolveAliasReference 查 SELECT 别名(bind_columnref_expression.cpp:84)。

**Q6:USING(a) 的列怎么解析?**
改写为 primary 表列或对各表 COALESCE(column_qualifier.cpp:142-158)。

**Q7:宏在哪个阶段展开?**
bind 期:dummy binding 换元后重新 BindExpression(bind_macro_expression.cpp:169-213)。

**Q8:DDL 之后 EXECUTE 旧 prepared 会错吗?**
不会:catalog 身份比对触发整体重绑(prepared_statement_data.cpp:124-134)。

**Q9:递归 CTE 在哪处理?**
planner(bind_recursive_cte_node.cpp),优化器只保守保护。

**Q10:相关子查询怎么去相关?**
子 binder 随 BoundSubqueryExpression 携带,供 plan 阶段 FlattenDependentJoins 使用(bind_subquery_expression.cpp:177)。
