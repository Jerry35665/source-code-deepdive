# 第 04 章 · 优化器:固定顺序流水线、DPhyp 与统计传播

> 基线:commit `7e886f44`。核心目录 src/optimizer/。

## 4.0 全景:一条固定顺序的流水线(非 cascade)

```
Optimizer::Optimize(optimizer.cpp:555)
 ├ LowerMandatoryAggregateRewrites(:545)GroupingSets 强制多阶段聚合
 ├ ExpressionRewriter(:71-107 注册 37 条表达式规则,自底向上重写表达式树)
 ├ 结构 pass ~45 个(:229-543),关键顺序:
 │   CTE内联 → 函数改写 → FILTER_PULLUP(:267)→ FILTER_PUSHDOWN(:273)
 │   → 大IN→MARK join(:296)→ Deliminator → GROUPING_SETS 展开
 │   → JOIN_ORDER(:350)★ DPhyp+贪心 → PK-FK join 消除 → 剪未引用列
 │   → CSE(:394)→ build/probe 定侧 → TOP_N(:440)
 │   → STATISTICS_PROPAGATION(:457)★ → 多阶段聚合成本制(:466)
 │   → PROJECTION_PLACEMENT → PARTITIONED_EXECUTION(:515)→ join filter 下推
 └ extension optimize → VerifyPlan
```

每个 pass 由 `RunOptimizer` 包裹:可 `SET disabled_optimizers` 单独关闭(optimizer.cpp:125-132)、profiler 计时、DEBUG 下过 LogicalPlanVerifier(:148-150)。**顺序即语义**:CSE 在 join order 之后、统计传播之前;统计传播刻意放很晚——join 重排会整棵重建子树,过早传播的统计会失效。

## 4.1 规则引擎:matcher + Apply

规则基类两件套:`root` 表达式匹配器 + `Apply` 回调(rule.hpp:17-32)。驱动循环是显式栈的**自底向上**遍历——"让父规则看到已简化的子节点"(expression_rewriter.cpp:64);命中即改写并重新进入该节点直到定住,**不做全局搜索**。样板:`LikeOptimizationRule` 把常量 pattern 四分类——无通配→等值、尾%→prefix、头%→suffix、两端%→contains(like_optimizations.cpp:132-171);正则同族(regex_optimizations.cpp)。

## 4.2 Filter Pushdown:一算子一文件

`FilterPushdown::Rewrite` 按算子类型分派(filter_pushdown.cpp:108-163),16 个 pushdown_*.cpp 各答一个问题:**穿 project**(列引用替换为表达式;volatile/可能抛错的表达式留下,pushdown_projection.cpp:163-170);**穿 aggregate**(仅下推引用 group 列且被所有 grouping set 覆盖的谓词,pushdown_aggregate.cpp:70-84);**inner join 先拆条件再临时降级 cross product**,横跨两侧的 filter 重组为 join 条件、有条件就重建 ComparisonJoin(pushdown_cross_product.cpp:43-64);**MARK→SEMI/ANTI**(filter 只引用 marker 列时,pushdown_mark_join.cpp:59-99)。前置的 FILTER_PULLUP 把 "WHERE 套子查询" 与 "ON 条件" 归一成同一份 filter 集合再统一分配。终点:剩余谓词挂到 `get.table_filters` 直通存储层(pushdown_get.cpp:160)。

## 4.3 Join Order:DPhyp 精确 DP + 贪心兜底

图构建三步:抽关系→抽边→建超图(query_graph_manager.cpp:170-204)。枚举用 **DPhyp**(Moerkotte & Neumann,出处注释 plan_enumerator.cpp:565-567):DP 表 = JoinRelationSet→DPJoinNode;等价 cost 时"右基数大者胜"减少 LEFT 翻转(:218-232)。**两道保险丝**:DP 对数超 10000 强制放弃(:237-251);关系数 ≥ `approximate_join_order_threshold`(默认 12,settings.hpp:320-332)直走近似。贪心每轮选最小 cost 可连接对;贪心也失败则**原样返回原 plan**(join_order_optimizer.cpp:96-100)——正确性兜底做到极致。图未连通时 `ActivateRequiredCrossProducts` 按需开启 cross product 边重跑。

## 4.4 统计传播:边传播边改写

`StatisticsPropagator` 自底向上单次后序遍历,载体 `statistics_map`(列绑定→BaseStatistics)(statistics_propagator.cpp:29-171)。传播顺带改写:filter 恒真→删;恒假→`LogicalEmptyResult`(propagate_filter.cpp:343-348);join 条件恒假→按类型剪枝(SEMI/INNER 整节点空、ANTI 取左孩子),恒真→降级 cross product(propagate_join.cpp:16-81);条件间统计互相收紧并**反向下推成 filter**(:348-392)。无统计对象返回 nullptr 即"不知道",改写自动退化为保守——免维护独立统计目录。删了条件会留孤儿列,故 `removed_expressions` 为真时重跑 UNUSED_COLUMNS+COLUMN_LIFETIME(optimizer.cpp:492-500)。

## 4.5 其他值得记住的守门条件

| 优化 | 触发 | 主动放弃 |
|---|---|---|
| 大 IN→MARK join | 常量数 ≥6(in_clause_rewriter.hpp:31) | 不可折叠元素 |
| TopN | LIMIT 常量+底下是 ORDER BY | limit>5000 且 >基数 0.7%(全排序更快,topn_optimizer.cpp:49-53) |
| LIMIT 下穿 | LIMIT<8192 且下一层是 PROJECTION | OFFSET 为表达式/含 volatile(limit_pushdown.cpp:13-32) |
| CTE 内联 | 0/1 引用直接删/内联 | `base_table_references*ref_count>10` 等(cte_inlining.cpp:215-217) |

CSE 单独成 pass 而非 Rule:要**在兄弟表达式间**共享,须新建 projection、分配 table index(cse_optimizer.cpp:161-174),超出"单表达式进单表达式出"的 Rule 模型。

## 4.6 设计动机

1. **固定顺序而非 cascade**:嵌入式 OLAP 优化须毫秒级完成;行为可预测、每 pass 可单独关闭+验证,代价是改顺序需谨慎;
2. **DP+贪心混合**:最坏指数的编译时间被两道保险丝封顶;
3. **统计内嵌传播**:min/max 随条件收紧,生命周期与计划绑定;
4. **pushdown 按算子拆文件**:每个算子的"谓词能否穿过"是独立知识;
5. **filter 先 pullup 再 pushdown**:两个 pass 让谓词先归一再全局最优分配。

## 4.7 FAQ

**Q1:优化器是 RBO 还是 CBO?**
混合:结构改写靠规则,join order 与多阶段聚合靠统计(有统计用统计,无统计退启发)。

**Q2:能关掉某个优化吗?**
能:`SET disabled_optimizers='...'`(optimizer.cpp:125-132)。

**Q3:LIKE '%abc' 会全扫吗?**
会,但 LIKE 'abc%' 会被改写成 prefix 等值类比较(like_optimizations.cpp:160-162)。

**Q4:多少表 join 会走贪心?**
≥12 个关系(settings.hpp:320-332)或 DP 对数超 10000。

**Q5:恒假 WHERE 会扫表吗?**
不会:统计传播把子树换成 LogicalEmptyResult(propagate_filter.cpp:343)。

**Q6:IN (1,2,3) 怎么执行?**
<6 个折 OR 链;≥6 物化常量表走 MARK join(可能再转 SEMI)。

**Q7:统计从哪来?**
表扫描注入(propagate_get.cpp:155-215),沿传播收紧;Parquet/CSV 的元数据也供统计。

**Q8:EXPLAIN 三种输出?**
logical_plan/logical_opt/physical_plan(plan_explain.cpp:37-49)。

**Q9:递归 CTE 会被内联吗?**
不会:在 planner 生成,优化器整体跳过相关改写(optimizer.cpp:201-214)。

**Q10:PK-FK join 能消掉吗?**
能:JOIN_ELIMINATION pass(optimizer.cpp:370)。
