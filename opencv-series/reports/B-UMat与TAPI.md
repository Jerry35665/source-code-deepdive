## 0. 一图看懂:UMat 数据流与拷贝/映射边界

```
              同一份算法代码:cv::blur(src, dst)          ← T-API 目标
                              |
              dst 是 Mat                    dst 是 UMat 且 OpenCL 可用
              (CV_OCL_RUN 条件不成立)        (_dst.isUMat() == true)
                    |                              |
      [CPU 路径]    v                    [OpenCL 路径] v
   Mat::data 指针直接运算        ①Mat→UMat  ————— 边界 A(上传,可能一次拷贝)—————
   (simd/IPP/HAL)              Mat::getUMat() (umatrix.cpp:571)
                                 └ OpenCLAllocator::allocate(ocl.cpp:5511)
                                    TEMP_UMAT: clCreateBuffer(USE_HOST_PTR)
                                    或 CL_MEM_COPY_HOST_PTR (ocl.cpp:5607/5618)
                               ②kernel 执行(异步,数据不离开 GPU)
                                 ocl_boxFilter (box_filter.dispatch.cpp:115)
                                 kernel.run → clEnqueueNDRangeKernel
                                              (ocl.cpp:3934)
                               ③UMat→Mat ————— 边界 B(回传,阻塞同步)—————
                                 UMat::getMat (umatrix.cpp:1071)
                                 └ OpenCLAllocator::map (ocl.cpp:5879)
                                    clEnqueueMapBuffer(CL_TRUE) 或
                                    clEnqueueReadBuffer(CL_TRUE) (ocl.cpp:5926/5956)
   结果:Mat                    结果:Mat(与 GPU 上数据一致)
```

两个边界是理解 T-API 性能的钥匙:边界 A 与 B 各对应一次主机-设备间传输(PCIe DMA,
`ocl.cpp:5605-5606` 的注释原文就点明 "pinned memory ... enables fast DMA-transfers over PCIe");
而边界之间(多个 kernel 链式调用)数据可以一直留在设备端,这正是 UMat 存在的意义。

## 1. T-API 设计目标与 Mat/UMat 的关系

T-API(Transparent API)的目标:用户只换数据类型(`Mat`→`UMat`),算法代码不变,由库决定
在哪台设备上执行。入口签名统一为 `InputArray/OutputArray`,内部用 `_dst.isUMat()` 分流
(如 `modules/imgproc/src/box_filter.dispatch.cpp:373-378`)。

**Mat 与 UMat 不共用一套实现,但共用一个"数据控制块"概念 `UMatData`**(`modules/core/include/opencv2/core/mat.hpp:562-601`):
`UMatData` 同时持有主机侧 `data`(mat.hpp:590)与设备侧句柄 `handle`(mat.hpp:595)、双引用
计数 `urefcount`(UMat 侧)/`refcount`(Mat 头侧)(mat.hpp:588-589)、状态标志位
`COPY_ON_MAP/TEMP_UMAT/DEVICE_MEM_MAPPED...`(mat.hpp:564-568)以及跨对象链接
`originalUMatData`(mat.hpp:599)。两个方向的转换语义不同:

- **Mat→UMat(`Mat::getUMat`,umatrix.cpp:571)**:创建一个**新的** UMatData,并令
  `new_u->originalUMatData = u` 指回原 Mat 的控制块(umatrix.cpp:601-602),随后调用
  OpenCLAllocator 的第二形态 `allocate(u,...)` 为其绑定 cl_mem(umatrix.cpp:607)。此路径
  产生 `TEMP_UMAT` 语义的临时缓冲——在 `ocl::useOpenCL()` 且分配器为 OpenCL 分配器时
  断言 `new_u->tempUMat()`(umatrix.cpp:621-624)。**即 Mat 与 UMat 各持一个 UMatData,
  通过 originalUMatData 弱链接,而不是共享同一个。**
- **UMat→Mat(`UMat::getMat`,umatrix.cpp:1071)**:返回的 Mat 头**直接复用 UMat 的同一个
  `u`**:`CV_XADD(&u->refcount,1)` 后 `map(u)` 把设备数据映射到主机,再拿 `u->data+offset`
  拼一个 Mat 头、`hdr.u = u`(umatrix.cpp:1080-1090)。

分配器是行为开关:`UMat::getStdAllocator()` 在 `ocl::useOpenCL()` 时返回
`ocl::getOpenCLAllocator()`,否则回落 CPU 默认分配器(`modules/core/src/umatrix.cpp:464-471`);
`UMat::create` 走该分配器分配(umatrix.cpp:695-703)。MatAllocator 是抽象接口,规定
`allocate/deallocate/map/unmap/download/upload/copy` 全套虚函数
(`mat.hpp:497-525`,map/unmap 声明在 511-512 行)。

## 2. OpenCL 运行时封装(modules/core/src/opencl/ 与 ocl.hpp)

- **动态加载,编译期不强依赖**:OpenCL 库在运行期 dlopen/LoadLibrary
  (`modules/core/src/opencl/runtime/opencl_core.cpp:93,132`),库路径可用环境变量
  `OPENCV_OPENCL_RUNTIME` 指定,设为 `disabled` 可整体关闭(ocl.cpp:1173-1181)。
  自动生成的 `opencl_core.hpp` 把每个 C 函数重定义为函数指针
  (`modules/core/include/opencv2/core/opencl/runtime/autogenerated/opencl_core.hpp:223,342`)。
- **Context 缓存**:`ocl::Context` 是进程级单例,`Context::Impl` 持有原生 `cl_context`
  (ocl.cpp:2691),在首次使用时 `clCreateContext` 创建(ocl.cpp:2600);同一 Impl 里还挂
  三样按 context 复用的资源:设备列表(ocl.cpp:2692)、两级 buffer pool
  (ocl.cpp:2703-2716)与 program 缓存表 `phash`+`cacheList`(ocl.cpp:2697-2701)。
  线程级切换由 `OpenCLExecutionContext` 承担(`modules/core/include/opencv2/core/ocl.hpp:801`)。
- **程序源码内嵌**:`modules/core/src/opencl/*.cl` 是 core 模块的 kernel 源;imgproc 等模块
  同理(如 `modules/imgproc/src/opencl/boxFilter.cl`)。构建期由 `cmake/cl2cpp.cmake` 把每个
  `.cl` 转成字符串常量 `ProgramEntry`,**取内容的 MD5 作为 sourceHash**
  (`cmake/cl2cpp.cmake:73-75`),生成 `cv::ocl::imgproc::boxFilter_oclsrc` 之类的符号。
- **cv::ocl 命名空间**(`modules/core/include/opencv2/core/ocl.hpp`):全局 API
  `haveOpenCL/useOpenCL/setUseOpenCL/finish`(ocl.hpp:54-59);类 `Device`(ocl.hpp:72,
  含 `available()` ocl.hpp:111、`hostUnifiedMemory()` ocl.hpp:165、`isAMD()/isIntel()`
  ocl.hpp:198-199)、`Context`(ocl.hpp:258)、`Queue`(ocl.hpp:395)、`KernelArg`(ocl.hpp:422,
  提供 `PtrReadOnly/WriteOnly/...` 便捷工厂,ocl.hpp:431-449)、`Kernel`(ocl.hpp:461)、
  `Program`(ocl.hpp:554)、`ProgramSource`(ocl.hpp:599)、`PlatformInfo`(ocl.hpp:673,
  配套 `getPlatfomsInfo` ocl.hpp:712)、`OpenCLExecutionContext`(ocl.hpp:801)。
- **USE_OPENCL 判定链**:编译期宏 `HAVE_OPENCL`(ocl_defs.hpp:15-20,未定义时
  `isOpenCLActivated()` 恒 false)→ 运行期 `haveOpenCL()`:枚举平台
  `clGetPlatformIDs`(ocl.cpp:1189)→ `useOpenCL()`:读 TLS 缓存的线程级开关,首次才初始化
  (ocl.cpp:1202-1222)→ `isOpenCLActivated()`:若进程从未激活 OpenCL 则短路返回,避免
  无谓的运行时加载(ocl.cpp:1224-1229)。用户可用 `cv::ocl::setUseOpenCL(false)` 关闭
  (ocl.cpp:1231)。

## 3. UMat 的映射机制:map/unmap、访问标志与同步点

访问标志定义于 `mat.hpp:65-66`:`ACCESS_READ=1<<24, ACCESS_WRITE=1<<25, ACCESS_RW, ACCESS_FAST`。
OpenCL 分配器按"映射优先"策略工作,由 `getBestFlags` 决定:主机统一内存(hostUnifiedMemory)
或 Intel 设备上直接映射,否则打上 `COPY_ON_MAP`(ocl.cpp:5417-5435);可用
`OPENCV_OPENCL_BUFFER_FORCE_MAPPING/FORCE_COPYING` 强制(ocl.cpp:5406-5415)。

- **map(ocl.cpp:5879-5962)**:非 copy-on-map 时,`clEnqueueMapBuffer(q, ..., CL_TRUE,
  CL_MAP_READ|CL_MAP_WRITE, ...)` 阻塞式把 cl_mem 映进主机地址空间并写回 `u->data`
  (ocl.cpp:5926-5929);映射失败则降级为 copy-on-map(ocl.cpp:5940)。copy-on-map 路径
  改用 `fastMalloc` 主机副本 + `clEnqueueReadBuffer(CL_TRUE)` 拉数据(ocl.cpp:5943-5957)。
  注意 ACCESS_WRITE 会先 `markDeviceCopyObsolete(true)`(ocl.cpp:5883-5884),即"主机数据
  将过时,设备为准"。
- **unmap(ocl.cpp:5964-6034)**:映射路径 `clEnqueueUnmapMemObject`(ocl.cpp:6008),AMD
  平台补一次 `clFinish`(ocl.cpp:6010-6014);copy-on-map 路径用
  `clEnqueueWriteBuffer(CL_TRUE)` 把脏数据推回设备(ocl.cpp:6027-6030)。
- **同步点在哪里(clFlush 何时发生)**:本代码库中真正的 `clFlush` 只有极少两处,且都在
  `Image2D::Impl` 为非连续 Mat 搭建中转 buffer 之后(ocl.cpp:7458,7471)。常规同步靠三件事:
  1) 所有 map/read/write/unmap 调用一律 `CL_TRUE` 阻塞;2) `Kernel::Impl::run` 检测到参数
  里有临时 UMat(TEMP_UMAT)或需要计时(ocl.cpp:3922-3932)时强制 `sync=true`,
  随后 `clFinish`(ocl.cpp:3934-3959)——这是"kernel 链里混入临时对象就变同步"的关键;
  3) temp UMat 析构时的回读路径:deallocate 判定 `ASYNC_CLEANUP` 进清理队列
  (ocl.cpp:5682-5685,`addToCleanupQueue` ocl.cpp:6623),`deallocate_` 对
  `hostCopyObsolete` 的 temp UMat 执行 `clEnqueueReadBuffer`/map+unmap 并 `clFinish`
  把结果拷回原 Mat 内存(ocl.cpp:5753,5763-5774)。全局栅栏是 `cv::ocl::finish()`
  (ocl.cpp:1421-1423 → `Queue::finish` ocl.cpp:3391)。
- **UMat::handle()** 是 kernel 取 cl_mem 的口:要求 `refcount==0`(没有活的 Mat 头),
  设备副本过时就先 unmap 回写,ACCESS_WRITE 则标记主机副本过时
  (`modules/core/src/umatrix.cpp:1103-1119`)。

```cpp
// modules/core/src/umatrix.cpp:1071-1090(有删节)
Mat UMat::getMat(AccessFlag accessFlags) const {
    // TODO Support ACCESS_READ (ACCESS_WRITE) without unnecessary data transfers
    accessFlags |= ACCESS_RW;                    // 1076:任何 getMat 都按读写映射
    UMatDataAutoLock autolock(u);
    if(CV_XADD(&u->refcount, 1) == 0)
        u->currAllocator->map(u, accessFlags);   // 1081:阻塞式映射/回读
    Mat hdr(dims, size.p, type(), u->data + offset, step.p);
    hdr.u = u;                                   // 1086:与 UMat 共享同一 UMatData
    ...
}
```

## 4. kernel 的编译与缓存

编译入口:`Kernel::create(kname, ProgramSource, buildopts)` →
`Context::getDefault().getProg(src, buildopts, errmsg)`(ocl.cpp:3672-3684)。
`Program::Impl` 构造中完成 **build options 常量拼接**:`joinBuildOptions` 合并调用方参数与
ProgramSource 自带选项(ocl.cpp:4332-4342,4362),按厂商追加 `-D AMD_DEVICE` /
`-D INTEL_DEVICE`(ocl.cpp:4365-4368),再并入环境变量 `OPENCV_OPENCL_BUILD_EXTRA_OPTIONS`
(ocl.cpp:233-239)。而真正的类型/尺寸常量(`-D srcT=... -D cn=...`)是各算法 C++ 侧用
`format`/`snprintf` 现拼的(如 box_filter.dispatch.cpp:197-216,238-248),让一个 `.cl`
模板长出成百上千个特化 kernel。

缓存共三层:

1. **进程内 program 缓存**:`Context::Impl::getProg` 以
   `module+name+sourceHash(内容MD5)+设备前缀+buildflags` 为 key 查 `phash`
   (ocl.cpp:4894-4911);设备前缀由厂商名/设备名/驱动版本拼出(ocl.cpp:2633-2658)。
   超过 `OPENCV_OPENCL_PROGRAM_CACHE` 上限按 LRU 逐出并告警(ocl.cpp:2355,4912-4931);
   **编译失败的 Program 也被缓存**,避免反复触发失败的编译器调用(ocl.cpp:4935-4939)。
2. **磁盘二进制缓存**:`compileWithCache` 按 `module--name_<hash>.bin` 落盘,命中则
   `createFromBinary` 免编译(ocl.cpp:4418-4451);开关为 `OPENCV_OPENCL_CACHE_ENABLE/WRITE`
   (ocl.cpp:215-217),缓存目录按设备前缀隔离(ocl.cpp:4420-4423)。
3. **cl_program → cl_kernel**:命中缓存后仍需 `clCreateKernel` 创建轻量 kernel 对象
   (ocl.cpp:3461)。旧的 `Program::getPrefix` 也能看到 key 构造的同构逻辑
   (ocl.cpp:4865-4879)。

   (box_filter.dispatch.cpp:373-376),不成立再试
   `CV_OCL_RUN(_dst.isUMat(), ocl_boxFilter(...))`(box_filter.dispatch.cpp:378);
3. `ocl_boxFilter`(box_filter.dispatch.cpp:115)先做设备能力检查:不支持 double、

5. 拼接 build options(box_filter.dispatch.cpp:197-216 Intel 小核特化分支 /
   238-248 通用分支,含 `borderMap` 边界模式字符串化,box_filter.dispatch.cpp:142);
6. `kernel.create("boxFilter", cv::ocl::imgproc::boxFilter_oclsrc, opts)`
   (box_filter.dispatch.cpp:254;3x3 特化为 `"filterSmall"`,219 行)——kernel 名对应
   `modules/imgproc/src/opencl/boxFilter.cl:166` 的 `__kernel void boxFilter(...)`;

8. `kernel.run(2, globalsize, localsize, false)` 提交异步执行(box_filter.dispatch.cpp:285

## 6. 降级逻辑:CV_OCL_RUN 宏

```cpp
// modules/core/include/opencv2/core/opencl/ocl_defs.hpp:61-73(默认变体)
#define CV_OCL_RUN_(condition, func, ...)     \
try {                                         \
    if (cv::ocl::isOpenCLActivated() && (condition) && func) { \
        CV_IMPL_ADD(CV_IMPL_OCL);             \
        return __VA_ARGS__;                   \
    }                                         \
}                                             \
catch (const cv::Exception& e) {              \
    CV_UNUSED(e); /* TODO: Add some logging here */ \
}
```

要点:①`isOpenCLActivated()` 是廉价的短路检查(ocl.cpp:1224-1229),未激活进程连 OpenCL
运行时都不加载;②`func` 即 OpenCL 实现本身,**返回 false 或抛异常都会自然掉到宏后面的
CPU 代码**——降级不是 if/else,而是"顺序执行 + 提前 return";③`CV_IMPL_ADD(CV_IMPL_OCL)`
做实现统计埋点(`modules/core/include/opencv2/core/utils/instrumentation.hpp:27`)。
另有 `CV_OPENCL_RUN_VERBOSE`(打印哪个实现在跑)与 `CV_OPENCL_RUN_ASSERT`(失败即报错)
两个调试变体(ocl_defs.hpp:28-59)。未编译 OpenCL 时整个宏退化为空(ocl_defs.hpp:76-78)。

## 7. 与 HAL 的关系(一句话)

HAL(`modules/core/include/opencv2/core/hal/`,如 `interface.h:6-10` 的 CV_HAL 错误码)
是**纯 CPU**的底层加速替换入口,在 OpenCL 分支之后的 CPU 路径里通过 `CALL_HAL` 调用
(如 box_filter.dispatch.cpp:399),与 T-API 属于互不重叠的两级加速层。

## 8. 性能边界:数据来回拷贝的代价

- **每个 Mat↔UMat 边界 ≈ 一次全量传输**:temp UMat 创建时 `CL_MEM_COPY_HOST_PTR` 拷上去
  (ocl.cpp:5618-5622),析构时若 `hostCopyObsolete` 再同步拷回来(ocl.cpp:5750-5774,
  含 clFinish)。写法不当的混合流水线(Mat/UMat 反复转换)会把 GPU 收益全部吃掉。
- **离散 GPU 默认 copy-on-map**(ocl.cpp:5424-5435):映射/回退为读写两份主机内存,
  `UMat::getMat` 目前一律 `ACCESS_RW` 映射,即使只需读(umatrix.cpp:1075-1076 的 TODO
  原文承认了这层浪费)。
- **同步语义的隐性代价**:kernel 参数带 temp UMat 时 run 强制同步(ocl.cpp:3927-3930),
  temp UMat 析构回读也阻塞——单次调用视角是"安全",流水线视角是"串行"。
- **缓解手段**:buffer pool 复用 cl_mem 避免 `clCreateBuffer` 反复分配
  (ocl.cpp:5483,池上限 `OPENCV_OPENCL_BUFFERPOOL_LIMIT` ocl.cpp:5362);program 三级缓存
  消除编译抖动;`ASYNC_CLEANUP` 把释放推迟到清理队列(ocl.cpp:5682-5683)。
- 官方给的答案很直白:整条流水线都喂 UMat、让数据驻留设备端,中间插入的每次 `getMat()`
  都要付一次往返的代价。

## 9. 设计动机

1. **为什么造 UMat 而不是给 Mat 的每个函数加 OpenCL 重载**:重载方案要为每个 API 写
   双份签名与分发,且 Mat 的 `data` 裸指针语义与设备内存模型冲突;UMat 把"数据在哪"
   下沉到 `UMatData + MatAllocator` 抽象(mat.hpp:497-525,562-601),算法层只看到
   `_dst.isUMat()` 一个分支条件(box_filter.dispatch.cpp:373-378),同签名 API 天然双端。
2. **为什么映射(map)而非总是拷贝**:`clEnqueueMapBuffer` 在主机统一内存/Intel 平台上
   零拷贝(ocl.cpp:5424-5430 的分支即是为此),离散 GPU 上 pinned memory 映射也能让
   DMA 直接进出用户可见地址(ocl.cpp:5605-5606 注释),比"分配+读"少一次内存搬运;
   映射不可用时才退回 copy-on-map(ocl.cpp:5940)。
3. **为什么 kernel 要三层缓存**:OpenCL 编译一次数十至数百毫秒,若每次调用都编译,T-API
   的"透明"就变成"透明的慢";用内容 MD5 + 设备前缀 + buildflags 做 key(ocl.cpp:4894),
   进程内 LRU 防内存膨胀(ocl.cpp:4912-4931),磁盘二进制缓存跨进程复用(ocl.cpp:4429-4451),
   连失败结果也缓存以免重复撞编译器(ocl.cpp:4935)。
4. **为什么用 CV_OCL_RUN 宏而不是虚函数/运行时多态**:分发条件是逐调用点定制的数据形状
   检查(尺寸、深度、边界类型),宏允许每个调用点写自己的 `condition`,且宏展开为
   try/catch 包裹的顺序代码——OpenCL 失败即"穿透"到紧随其后的 CPU 实现
   (ocl_defs.hpp:61-73),无需注册表,也无虚表开销;`isOpenCLActivated()` 前置短路
   保证无 OpenCL 环境下几乎零成本。
5. **为什么默认走 CPU(useOpenCL 默认关闭语义、条件苛刻)**:OpenCL 运行时质量参差
   (代码中对 AMD 驱动的特判、#6293/#9960 等 workaround 散布各处,如 ocl.cpp:6010-6014、
   5762-5774),小尺寸/不支持的数据类型上 GPU 反而更慢;因此每个 OCL 分支都自带类型/尺寸
   条件(box_filter.dispatch.cpp:125-127,smooth.dispatch.cpp:652-654),失败回退,用户
   不显式开 UMat 就始终是成熟的 CPU 路径。
6. **为什么 UMatData 要双引用计数 + ASYNC_CLEANUP**:UMat 侧 `urefcount` 与 Mat 头侧
   `refcount` 分开计数(mat.hpp:588-589),才能支持"同一 UMatData 上派生 Mat 头"
   (umatrix.cpp:1080-1090)与"Mat 派生 temp UMat"(umatrix.cpp:601-602)两种链接并存;
   kernel 异步执行期间参数缓冲由 `Kernel::Impl` 增持 urefcount、完成事件里延迟释放
   (ocl.cpp:3501-3512,3470-3499),避免用户提前销毁 UMat 导致设备端悬空。
